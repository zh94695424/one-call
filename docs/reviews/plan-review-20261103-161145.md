## 4. Findings

### F-01 — High — Command-role `SELECT` is under-specified and contradicts the frozen V009 tests and trigger semantics

**Failure scenario.** Implementing the command-role grants literally as "SELECT the command workflow's lookup/guard/read columns" and "share_access_event: INSERT only … do not grant SELECT absent a frozen workflow read" produces a command role that cannot run the preserved V009 probes: (a) `guard_share_admission` is `SECURITY INVOKER` and executes `SELECT * FROM sharing.evidence_share_grant`, so an admission insert by the command role fails with `42501` unless it has `SELECT` on every grant column; (b) `v009S3Facts` executes `to_jsonb(g)` and `to_jsonb(a)`, which also require all-column SELECT on the grant and admission; (c) the S3 admission/replay tests select and join `share_access_event` columns and read `payload_redacted`/`payload_sha256`, so "INSERT only" on events breaks them; (d) the plan's command-role bullet grants membership `(organization_id,account_id,status)` but §10.21 and `V009_FOREIGN_COLUMNS` also require `role`, which the preserved cross-module ACL probe reads. An implementer must either under-grant (tests fail) or expand beyond the plan's stated set (plan is not the implementation contract).

**Evidence.** Plan lines 29–33; `V009__sharing.sql:256–279`; `PostgresContainerIT.java:3665–3722`, `3760–3764`, `4482`, `4727`; docs/14 lines 4005–4007, 4017–4024, 4050.

**Impact.** The plan's "change only the role in the existing V009 behaviour tests, keep assertions intact" is impossible with the stated command grants; the command role either cannot support the frozen create/admission/lifecycle semantics or must silently receive broader privileges than the plan records. This is both a test-suite failure and a least-privilege specification failure.

**Actionable correction.** Specify the command role's owned-table grants exactly as §10.21: `SELECT` on **all** columns of `sharing.evidence_share_grant`, `sharing.share_admission` and `sharing.share_access_event`; `INSERT` on all columns; the eight frozen grant UPDATE columns; no UPDATE on admissions/events. For cross-module reads, enumerate the exact lists from §10.21, explicitly including `organization_membership.role` and `evidence_record.identity_at_capture`. Remove "derive … before implementation" for these owned tables; cite the trigger `SELECT *` and `to_jsonb` requirements as the reason.

### F-02 — High — Command-role `UPDATE(max_admissions)` is an over-grant and breaks its own preserved test

**Failure scenario.** The plan grants `UPDATE` on `max_admissions` (line 29). The frozen guard treats `max_admissions` as immutable (`V009__sharing.sql:184`), §10.21 excludes it from the UPDATE list (docs/14 line 4005), and V009 does not grant it. The preserved V009 ACL probe loops every grant column except `V009_UPDATE_COLUMNS` and asserts `42501` (`PostgresContainerIT.java:3097–3106`); `max_admissions` is not in that list (4719–4721), so the probe would succeed after V010 and fail its assertion. The exact column-catalog assertion (5148–5153) would also fail.

**Evidence.** Plan line 29; `V009__sharing.sql:184`; docs/14 line 4005; `PostgresContainerIT.java:3097–3106`, `4719–4721`, `5148–5153`.

**Impact.** Direct violation of the least-privilege goal and an internal contradiction with the plan's "keep test assertions intact" rule.

**Actionable correction.** Remove `max_admissions` from the command-role UPDATE list. Use exactly `status, admissions_used, revocation_generation, revision, expires_at, code_salt, code_hash, code_generation`, matching §10.21 and `V009_UPDATE_COLUMNS`.

### F-03 — High — The revoke design is not PostgreSQL-correct for column-level ACLs and does not pin owner execution; the query role can retain V009 grants

**Failure scenario.** The plan says to "revoke ALL on both roles for all V009 table grants" and "explicitly revoke table-level SELECT". In PostgreSQL, table-level and column-level privileges are separate ACL entries (`pg_class.relacl` vs `pg_attribute.attacl`); `REVOKE ALL ON TABLE t FROM r` without a column list does not revoke column grants. V009 granted column-level `SELECT` on evidence/subject/customer/org tables and column-level `UPDATE` on the grant (lines 313–315, 329–362). A naive V010 would leave the column `UPDATE` on `evidence_share_grant` and the evidence/subject column `SELECT`s in place, so `sharing_role` would remain able to update grant lifecycle/secret columns and read foreign tables — exactly what the goal forbids. Separately, V009 performs each owner's grants under `SET LOCAL ROLE <owner>` (lines 326, 336, 344, 354, 366, 373); a `REVOKE`/`GRANT` executed by a non-owner/non-grantor only warns and changes nothing, so V010 could "succeed" while silently leaving the broad ACLs. The plan's "Use explicit `SET LOCAL ROLE` only if needed" does not determine this.

**Evidence.** `V009__sharing.sql:313–315`, `326–362`; plan lines 13–15, 29–33; PostgreSQL ACL model (table vs column entries).

**Impact.** Core security goal can be silently unmet. This is the highest-risk failure mode in the plan.

**Actionable correction.** Enumerate exact statements: per cross-module table, `REVOKE SELECT (all V009-granted columns) ON TABLE ... FROM sharing_role`; on the grant table, `REVOKE UPDATE (status, admissions_used, revocation_generation, revision, expires_at, code_salt, code_hash, code_generation) ON TABLE ... FROM sharing_role` (and any other V009 column grants); table-level revokes for SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER; schema USAGE revokes for evidence/subject/platform/audit; function EXECUTE revokes for the trigger/outbox/audit functions. Execute each object-owner section under the corresponding owner role (as V009 does), and require the migration identity to be superuser or a member able to `SET ROLE` each owner. State explicitly that `REVOKE ALL ON TABLE` alone is insufficient.

### F-04 — High — Required changes to existing tests/fixtures are materially understated; the "one slice" write set is incomplete

**Failure scenario.** The plan says PostgresContainerIT needs only role-principal changes and that "V009 database invariants remain covered unchanged". In fact V010 forces: (a) rewrite of `assertV009AclCatalog` (exact schema/table/column/function ACLs at `PostgresContainerIT.java:5029–5170`), which currently asserts broad `sharing_role` grants and zero command-role-related ACLs; (b) split/rewrite of `v009OwnerPublicRuntimeAndCrossModuleAclsAreExact`, which mixes query-role denial probes with command-role writes and cannot simply be switched to `sharing_command_role` with assertions intact; (c) staging/history changes in `v001ThroughV009MigrateCleanPostgres16WithoutSkipping` (the exact nine-row history loop at 1283–1366 and `initialMigration.migrationsExecuted == 1` at 1236/1116); (d) Flyway-count updates in `SharingQueryFixture.java:70–72`, `CustomerMeFixture.java:86–95` and `SharingQueryServiceIT.java:36`, all hard-coded to nine; (e) `CustomerMeFixture` is the site that provisions the sharing login (`GRANT sharing_role`, lines 91–95) but is absent from the plan's named consumer/inventory list. Any one omission fails the suite or leaves an old broad-ACL assertion in the tree.

**Evidence.** `PostgresContainerIT.java:1116`, `1229–1379`, `3070–3131`, `5029–5170`; `SharingQueryFixture.java:70–72`; `CustomerMeFixture.java:86–95`; `SharingQueryServiceIT.java:36`; plan lines 39–47, 59, 69.

**Impact.** The slice cannot be implemented as scoped; "existing 159 tests remain green" is false until these files are changed, and the plan's file ownership/inventory misses at least one provisioning file.

**Actionable correction.** Add an explicit existing-test delta table: file, method/line, current assertion, required V010 change. Include `assertV009AclCatalog` (replace broad ACL expectations with V010 exact query/command sets), the ACL/behaviour split in `v009OwnerPublicRuntimeAndCrossModuleAclsAreExact`, the V009→V010 staging and 10-row history in `PostgresContainerIT`, the 9→10 counts in `SharingQueryFixture`, `CustomerMeFixture`, and `SharingQueryServiceIT`, and `CustomerMeFixture` as a login-provisioning/inventory site. Do not describe V009 ACL invariants as unchanged.

### F-05 — High — Validation commands do not execute the integration tests; "full suite" coverage is false

**Failure scenario.** Plan validation step 2 runs `./mvnw -DskipTests=false -Dtest=none -Dit.test=... verify` and step 3 runs `./mvnw verify`. In this repository the `maven-failsafe-plugin`, its `<includes>` and `failIfNoTests=true` exist only inside the `container-smoke` profile (`backend/pom.xml:168–197`). A reviewer following the plan would report a green validation that never exercised V010.

**Evidence.** `backend/pom.xml:168–197`; `.github/workflows/ci.yml:57–59`; `backend/README.md:236`, `255–256`, `297`; plan lines 73–81.

**Impact.** The validation contract cannot prove any of the plan's security claims, and step 3's claim that the full integration suite includes `/me`, `/shares` and V009 behaviour is inaccurate.

**Actionable correction.** Use the documented `./mvnw -B -ntp -Pcontainer-smoke verify` (or an equivalent explicitly profile-enabled selector) for both the focused and full runs; state that plain `./mvnw verify` is unit/architecture-only and is not container evidence. If a focused Failsafe selector is retained, keep `-Pcontainer-smoke`, use `-Dsurefire.failIfNoSpecifiedTests=false` or the project's established pattern, and state that `Docker` is required.

**Impact.** Not code-generation-ready; the command role's least-privilege boundary is not reviewable as a fixed contract.

### F-08 — Low — Test-design precision: membership-negative probe, 25006 separation, and 42501 transaction isolation need to be pinned

**Failure scenario.** (a) The plan proves "query login cannot assume command role" with `pg_has_role` language but does not require an explicit `SET ROLE sharing_command_role` / `SET LOCAL ROLE` attempt from the provisioned login and does not distinguish `pg_has_role(...,'MEMBER')` from `'USAGE'`; because fixture logins are `NOINHERIT`, a `'USAGE'`-only assertion can be false while `SET ROLE` still succeeds. (b) The plan says to prove `25006` "in the existing read-only test", but the existing read-only probe (`CustomerSharesFixture.java:328–349`, via `CustomerSharesIT.java:239`) runs as `sharing_role`, which after V010 is no longer authorised to update; a `25006` there would not prove "otherwise authorised write blocked by transaction mode". The separate proof must run as `sharing_command_role` (or another genuinely UPDATE-authorised role) in a read-only transaction. (c) ACL `42501` probes must run in a writable/autocommit transaction with per-probe savepoints; otherwise a prior failed statement leaves the transaction aborted (`25P02`) and subsequent probes do not test the intended privilege.

**Evidence.** `CustomerSharesIT.java:249–250` already shows the explicit `SET ROLE customer_iam_role` → `42501` pattern; `CustomerSharesFixture.java:328–349`; plan lines 53–56.

**Impact.** Tests can pass for the wrong reason or fail with the wrong SQLSTATE; the membership-path and 25006 separation claims become less trustworthy.

**Actionable correction.** Require an explicit login-level `SET ROLE sharing_command_role` denial (`42501`) plus `pg_has_role(login, 'sharing_command_role', 'MEMBER')` false; run the 25006 probe under `sharing_command_role` in a read-only transaction; run all 42501 probes in writable transactions with savepoints.

## 6. Open questions

1. Should the command role's owned-table `SELECT` be table-wide (recommended, matching §10.21 and the invoker trigger) or column-enumerated? The plan should choose explicitly; F-01 assumes table-wide is intended.
2. Are the trigger guard/reject functions to remain without direct `EXECUTE` for either runtime role, and will docs/14 §10.22 be updated to say so? Trigger invocation does not require `EXECUTE`, so this is a documentation choice, not a functional blocker.
3. Should the V001–V009 hash check in validation step 6 use canonical LF bytes (as `assertV001ThroughV009MigrationDigestsUnchanged` does) rather than raw CRLF bytes? This export is CRLF; a cross-platform raw-byte baseline would produce a false mismatch.
4. Does the new 16.15-pinned IT plus its container fit the 30-minute `java-runtime` CI ceiling alongside the existing 92 Failsafe methods? The plan adds a fifth container class without discussing the ceiling.

## 8. Verdict

**`fail`.**

The plan's goal alignment and the exact query-role read set are correct, and the single-migration/no-view/no-SECURITY-DEFINER design is the right shape. However, the plan cannot be implemented as written without either failing the frozen V009 behaviour suite or silently deviating from its own least-privilege contract:

- the command role's `SELECT` set omits all-column reads required by the `SECURITY INVOKER` admission guard and the preserved `to_jsonb`/event replay probes (F-01);
- it grants an `UPDATE` on immutable `max_admissions` that its own preserved test asserts must fail (F-02);
- its revoke design does not handle column-level ACLs and does not pin owner execution, so V009's column grants can survive (F-03);
- the required existing-test/fixture changes are understated and one provisioning file is missing (F-04);
- the validation commands never run the Failsafe ITs (F-05);
- the command cross-module/function grant set is still "derive before implementation" (F-06);
- README/CI/docs counts are not fully updated (F-07);
- membership/25006/42501 test mechanics need explicit pinning (F-08).

These are bounded, correctable plan defects, not a rejection of the goal. The plan should be revised to enumerate the exact V010 statements and the exact existing-test/README/CI/doc deltas, then re-reviewed. This artifact is a review conclusion only; it does not implement, approve, authorize a gate, or modify the plan, source, tests, migrations, control document, inputs or Git metadata.
