## 4. Findings

### 1-未修复-中-§4 token shape vs canonical URI gate: whitespace/percent-encoding error-code contradiction is not closed for implementation

- **位置**: Plan §4 items 2–3 and 6 (`pa15-sharing-public-share-read-plan.md` lines 92–96); test row `PublicShareWebTests.tokenShapeAndLookupFailuresUseClosedProblems` (line 214)
- **问题类型**: 契约缺失 / 测试缺口 / 不可直接实施
- **当前写法**:
  - §4.2–4.3: admit only servlet path matching `/api/v1/public/shares/[^/;%]+`; retain `(contextPath + servletPath).equals(requestURI)`; “percent-encoded aliases/token segments … retain sanitized 404 `NOT_FOUND`, before verifier/service calls.”
  - §4.6: “A valid-shaped but wrong token, including an **altered-case/whitespace-bearing value** that has no matching exact digest, is 404 `SHARE_TOKEN_INVALID`.”
  - §4.6 also: “Test 1/512 acceptance and 513 rejection; direct service tests own Unicode/invalid-surrogate/NUL cases unrepresentable under the canonical URI gate.”
  - Test row requires “unknown/replaced token→404” among closed Problem assertions without distinguishing route-level `NOT_FOUND` vs token-domain `SHARE_TOKEN_INVALID` for whitespace/encoded shapes.
- **反例/失败场景**: A token value containing a space (or other character that requires percent-encoding in a URI) cannot satisfy both the canonical URI equality and the `[^/;%]+` segment regex when presented as a normal HTTP request. The filter’s noncanonical-path branch returns `NOT_FOUND` before any digest lookup; §4.6 simultaneously claims a “whitespace-bearing” wrong token yields `SHARE_TOKEN_INVALID`. An implementation agent must invent which branch wins, and the named web test can be written either way and still claim plan compliance.
- **为什么有问题**: Goal Confirmation requires “exact route/filter/controller behavior” and “exact 404/410/422/503 problem mappings.” Two plan clauses prescribe different `code` values for overlapping client-visible 404 shapes on the same operation. OpenAPI binds this operation’s 404 to `ShareTokenInvalid` (`SHARE_TOKEN_INVALID`), while generic route rejection historically uses `NOT_FOUND` (plan line 193 explicitly keeps them separate)—the plan never states which code a whitespace/percent-encoded token segment produces, despite naming that case in §4.6.
- **直接证据**: Plan lines 92–96 and 193; filter source `CustomerBoundaryFilter.java:51–62` (equality + exact matchers, else `problems.notFound`); OpenAPI 3686–3687 (`'404': ShareTokenInvalid`); OpenAPI token schema 3671–3674 (string 1–512, no alphabet/pattern).
- **影响**: Implementation agent ambiguity → wrong Problem `code` on a concealment-critical path; web test assertions may freeze the wrong mapping; review/acceptance cannot objectively verify “uniform invalid-token concealment” for URI-unsafe token bytes without a plan correction.
- **建议改法和验证点**: In a bounded plan correction, state explicitly: (a) which token byte sequences are admissible under the canonical URI gate (e.g. only path-segment-safe, unencoded forms after container decoding); (b) that percent-encoded/noncanonical presentations are route-level `404 NOT_FOUND` and are **not** `SHARE_TOKEN_INVALID`; (c) that `SHARE_TOKEN_INVALID` applies only after a canonical admitted segment fails digest resolution; (d) move “whitespace-bearing” wrong-token cases to the service-level test row (or delete the HTTP-level claim). Verify by asserting distinct Problem `code` values in `PublicShareWebTests` for (i) noncanonical/encoded path → `NOT_FOUND`, (ii) canonical unknown token → `SHARE_TOKEN_INVALID`.
- **修复风险（低）**: Single-paragraph plan clarification + test-row wording; no design change.
- **严重程度（中）**

### 2-未修复-中-Item 19 freezes neither the PUBLIC_READ_FILES inventory nor its source bans, while sibling architecture items freeze exact sets

- **位置**: Plan §3 item 19 (line 73); contrast items 18 and 20 (lines 72, 74); §5 named-interface assertions (line 107); existing `SharingQueryBoundaryTests`
- **问题类型**: 不可直接实施 / 测试缺口 / 契约缺失
- **当前写法**: Item 19: “Add explicit PUBLIC_READ_FILES third classification and named API inventory; preserve exact original customer-query and command sets and bans.” Item 18 pins `25→26` files and exact sharing imports/profile/signatures. Item 20 pins `2→3` allowed interfaces and exact named-interface lists. §5 requires enumerating four top-level public-query types and nested safe types but does not give the expected simple-name set or the source-ban list for public-read files.
- **反例/失败场景**: `SharingQueryBoundaryTests` today classifies **every** file under `sharing/internal` that is not in `QUERY_FILES` as a command path and asserts an exact 19-file inventory plus command bans (including bans on `capability_token_hash`/`content_snapshot` for non-persistence command paths and additional bans for persistence command paths). The eight new allowlisted public files (publicquery ×5 + persistence PublicShare ×3) would fail this test until reclassified. If PUBLIC_READ_FILES bans are invented by copying **query** bans, `JooqPublicShareQueryRepository` cannot legally select `capability_token_hash`/`content_snapshot` (required by plan §5 SQL) and the test contradicts the design; if bans are invented too weakly (e.g. omit `INSERT`/`FOR UPDATE`/`customer_iam` imports), the architecture layer stops enforcing the no-write/cross-module rules the plan claims architecture tests still own.
- **为什么有问题**: The plan’s own success criteria require architecture tests to be “extended precisely, not weakened globally” (line 47) and CI/source/XML exactness. Items 18/20 are code-generation-ready at inventory granularity; item 19 is not—the implementation agent must design the third partition’s file list, named-interface type enumeration, and ban strings, which is exactly the “re-design during implementation” failure mode plan review is meant to catch. Wrong bans either block a required SELECT or silently drop safety assertions.
- **直接证据**: `SharingQueryBoundaryTests.java:17–21` (QUERY_FILES), `:52–57` (exact query file names), `:85–95` (query-file bans incl. `capability_token_hash`, `content_snapshot`), `:97–115` (commandPaths = all non-query files + exact 19-name inventory + command bans), `:60–71` / `:128–130` (named interfaces exactly `customer-query`/`customer-command`); plan lines 47, 72–74, 107.
- **影响**: High risk of mid-implementation plan correction or of a “passing” architecture test that no longer encodes the intended public-read isolation; weakens the reviewability of the layering guarantee for the new named interface.
- **建议改法和验证点**: In a bounded plan correction, freeze in item 19 (or §5): (a) exact PUBLIC_READ_FILES path set (the eight allowlisted sharing/internal files); (b) exact expected public-query simple names + nested type names for `NamedInterface` assertions; (c) exact source ban list for public-read files (must include write/lock/audit/`SELECT *`/`customer_iam`/`organization_access`/`Logger`-style bans, and must **explicitly allow** `capability_token_hash` and `content_snapshot` in persistence read files while banning them from publicquery application files if desired); (d) confirmation that customer-query QUERY_FILES and command 19-file sets stay byte-identical. Verify by reading the updated test row against the existing test structure before implementation.
- **修复风险（低）**: Spec-only addition; no production design change.
