### CR-001-未修复[严重程度（高）]-跨动作事件键会覆盖幂等记录并允许同一录音事件再次扣量
- **入口/函数**: `confirmIvrSession`、`consumeTrial`、`claimSubject`、`createOrder`、`applyPaymentResult`、`issueEntitlements` 经 `eventResult` 读写 `processedEvents`。
- **文件(行号)**: `shared/onecall-business.js:249`, `shared/onecall-business.js:323`, `shared/onecall-business.js:339`, `shared/onecall-business.js:373`, `shared/onecall-business.js:381`, `shared/onecall-business.js:578`
- **输入场景**: 先用事件键 `COLLIDE` 成功消费 60 秒试用，再用同一个字符串作为认领 `requestId`，随后重放原录音消费事件。另一条独立场景是支付事件先得到 `UNKNOWN`，订单之后被另一事件推进为 `PAID`，再重放第一个事件。
- **实际分支**: `eventResult` 遇到同名但不同 `type` 的记录直接返回 `null`；各写入口随后用 `draft.processedEvents[key] = ...` 覆盖旧类型。重放消费时已找不到原 `EVIDENCE` 记录，于是再次进入新证据和扣量分支。支付重放则按 `objectId` 重新读取当前订单，而不是返回首次处理时的结果。
- **预期行为**: 事件键必须有明确的全局或按动作命名空间所有权；不同动作复用时应拒绝或互不覆盖。重复事件必须返回首次结果且不产生第二次业务副作用。
- **实际行为**: 只经过公开函数即可把同一录音事件执行两次：试用使用量从 0 变为 120 秒并生成两条各 60 秒的证据。支付 `P1` 首次返回 `UNKNOWN`，订单后续变为 `PAID` 后，重放 `P1` 返回的却是当前 `PAID`。此外 `id()` 接受 `__proto__`；把它作为确认事件键会改变普通对象 `processedEvents` 的原型，动作仍返回成功，但随后的 `snapshot` 返回 `INVALID_TRANSITION`。
- **直接证据**: 类型检查只在 `eventResult` 内进行（578-581），而认领、证据、订单、支付和权益分别直接覆盖同一个普通对象键（255、339、363、381、399）。审查期只读 Node 探针复现结果为 `first=OK, claim=OK, replay=OK, used=120, evidence.length=2`；支付探针为 `first=UNKNOWN, replay=DUPLICATE/PAID`；`__proto__` 探针显示动作 `OK`、该键不是 own property、快照校验失败。现有测试只在没有跨类型复用、没有后续状态变化时重放（`shared/qa/business.test.js:73`, `shared/qa/business.test.js:92`, `shared/qa/business.test.js:265`），没有覆盖这些路径。
- **影响**: 同一个 IVR 录音事件可能重复扣减试用并重复生成证据；幂等回包可能与首次事实不一致；特殊键可使本地业务状态在一次“成功”写入后不可导出。这直接破坏 S1 的一次性试用、事件重放和跨端快照契约。
- **建议改法和验证点**: 明确事件键命名空间，使用 `Map`/null-prototype 字典或安全编码键，并在任何写入前检查同键的动作类型与输入指纹；事件记录保存不可变的首次结果快照，而非只保存可变对象 ID。增加“证据键被认领/支付键复用后再重放”、同类型键指向不同对象、后续状态变化后重放以及 `__proto__`/`constructor`/`prototype` 键测试，逐项断言完整状态和首次返回值不变。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### CR-002-未修复[严重程度（高）]-合法导入的序列值可让下一次写入生成重复业务 ID
- **入口/函数**: `loadReviewSnapshot` 导入动态快照后，由任一使用 `nextId` 的修改函数创建对象；最短复现路径是 `loadReviewSnapshot` → `createOrder`。
- **文件(行号)**: `shared/onecall-business.js:420`, `shared/onecall-business.js:429`, `shared/onecall-business.js:434`, `shared/onecall-business.js:557`, `shared/onecall-business.js:584`
- **输入场景**: 一个其余结构和引用均合法的 schema 1 快照含已有订单 `ORDER-001001`，同时 `sequence=1000`；该快照被导入后创建下一笔订单。
- **实际分支**: `validateState` 只要求 `sequence` 是 0 到 `MAX_SAFE_INTEGER` 的整数，不验证它与现有 ID 的下一可用值关系。`nextId` 无条件把 1000 加到 1001 并返回 `ORDER-001001`；`mutate` 在提交 draft 前不调用 `validateState`，直接替换原状态。
- **预期行为**: 任何被 `loadReviewSnapshot` 接受的动态快照，在后续合法转换中仍应保持 ID 唯一和引用可判定；分配器应跳过已使用 ID，或导入校验应证明序列不会冲突，并在提交前复验完整状态。
- **实际行为**: 审查期只读 Node 探针显示候选快照 `snapshot=OK`、导入 `load=OK`、创建订单也返回 `OK`，但订单列表随后包含两个 `ORDER-001001`，再次 `snapshot` 立即变为 `INVALID_TRANSITION`。
- **直接证据**: 序列校验位于 434 行且没有关联任何集合；ID 生成只有 `sequence += 1` 和字符串拼接（584-586）；成功 mutation 未做提交前状态校验（563-565）。当前动态往返测试从模块自己的高水位序列导出（`shared/qa/business.test.js:191`），没有覆盖一个结构合法但“下一 ID 已占用”的导入快照。
- **影响**: 跨端 fixture handoff 可在成功导入后被下一次正常操作永久破坏；`one()` 对重复 ID 返回 `null`，后续支付、权益或详情解析会变成 `NOT_FOUND`/`INVALID_TRANSITION`，且成功返回与不可导出状态不一致。
- **建议改法和验证点**: 让 `nextId` 在对应集合或全部业务 ID 中循环寻找未占用值，并在每个成功 mutation 替换前执行完整 `validateState`；也可在导入时校验/归一化可证明的序列高水位，但不能依赖任意动态 ID 都可解析为序号。为 `ORDER`、`TRIAL`、`SUBJ`、`ACT`、`EVID`、`CLAIM`、`ENT`、`IVR` 各补“下一候选已占用”的导入后创建测试，并断言动作成功时快照仍有效且 ID 唯一。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
