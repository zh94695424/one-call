## Findings

### A-01-未修复-中-canonical JSON 对控制字符使用大写 `\u` 转义，违反 RFC 8785，导致 shareId/content/fingerprint 摘要漂移

- **入口/函数**: `DefaultCustomerShareCommandService.execute` → `create` → `canonical()`/`quote()`, reached by `digest()` and `json()` for `shareId`, `scopeDigest`, `creationFingerprint`, `content_sha256`, Outbox payload and stored `content_snapshot`.
- **文件(行号)**: `backend/src/main/java/com/onecall/core/sharing/internal/commandservice/DefaultCustomerShareCommandService.java:302-342` (canonical/quote), especially `:339-342` (`return JsonMapper.builder().build().writeValueAsString(value);`); callers `:142`, `:152`, `:158-160`, `:177-178`, `:197`, `:292-293`. Acceptance of control characters: `CustomerShareCommandJsonBinder.java:24-27,45-51` and `DefaultCustomerShareCommandService.java:269-281` reject only blank/NUL/unencodable; they do not reject other U+0000–U+001F characters. Contract: `docs/14-production-data-model-and-flyway-schema-spec.md:184` ("Canonical JSON is an RFC 8785-compatible serialization").
- **输入场景**: A valid `POST /api/v1/customer/shares` with a JSON-escaped control character in `creationRequestId` (e.g. `"a\u001Fb"`, 3 code points, nonblank, no NUL, UTF-8 encodable), or an evidence `identityAtCapture`/`artifact.mediaMimeType` string containing a control character (V008 `identity_at_capture` is JSONB and `mime_type` has only length/blank checks).
- **实际分支**: Binder text check and service `validate()` accept the string; `canonical()` sorts the `{creatorAccountId, creationRequestId}` object, then `quote()` calls a default `JsonMapper` whose `JsonWriteFeature.WRITE_HEX_UPPER_CASE` is enabled by default in the managed Jackson 3.1.7 dependency (verified by `javap` on `tools.jackson.core.jackson-core:3.1.7`: `WRITE_HEX_UPPER_CASE` is constructed with `_defaultState=true`; `WriterBasedJsonGenerator.getHexChars()` selects `HEX_CHARS_UPPER`). The control character is serialized as `\u001F`.
- **预期行为**: Per the frozen canonical-JSON contract (RFC 8785 §3.2.2.2), control characters U+0000–U+001F must be escaped with `\u` followed by four lowercase hexadecimal digits (`\u001f`); the same bytes must feed `shareId`, creation/content digests, fingerprints and Outbox payload hashes.
- **实际行为**: The implementation emits uppercase hex escapes (`\u001F`, `\u000B`, etc.). The service is self-consistent at runtime, but the persisted/returned `shareId`, `scopeDigest`, `creationFingerprint`, `content_sha256` and Outbox `payload_sha256` are not the canonical values required by RFC 8785/§2.5 for these accepted inputs.
- **直接证据**: `DefaultCustomerShareCommandService.java:341` uses a fresh default `JsonMapper` for every string/key escape; `canonical()` invokes `quote()` at `:306` and `:314`; `creationRequestId` flows into the `shareId` canonical object at `:177-178`; content strings (including `identityAtCapture` and `mimeType`) flow into `digest(scope)`/`digest(complete)` at `:142` and `:160`. The canonical test vector at `CustomerShareCommandServiceTests.java:96-99` and all identity fixtures use no control characters, so this path is untested.
- **影响**: Contract and cross-implementation correctness: a conforming verifier or future owner that recomputes the §2.5 canonical JSON (or RFC 8785) for these valid inputs obtains a different deterministic `shareId`/digest. Runtime replay/conflict remain internally consistent, but the frozen identity/integrity contract is not met, and the defect is invisible to the current tests.
- **建议改法和验证点**: Disable `JsonWriteFeature.WRITE_HEX_UPPER_CASE` on the canonicalization mapper (or implement an explicit RFC 8785 string escaper) and add test vectors containing `U+000B` and `U+001F` in `creationRequestId` and in an evidence/content string, asserting the expected lowercase escape, `shareId`, `scopeDigest`, `content_sha256` and fingerprint. Reuse one configured thread-safe mapper instead of constructing a new `JsonMapper` per string (see Residual Risk).
- **修复风险（低/中/高）**: 低. Inputs without control characters are unchanged; no deployed PA14 data exists; tests need only new control-character vectors. A mapper-level fix must keep object-key sorting and number formatting unchanged.
- **严重程度（低/中/高/严重）**: 中. It is a valid-input violation of the explicitly required canonical identity/fingerprint contract, but it does not create an immediate authorization, transaction or data-loss failure for ordinary inputs.

## Open Questions

- **Digest member names vs. design source.** `docs/14` lines 254–255 define `scopeDigest` from canonical `{content, verification}` and `content_sha256` from canonical `{content, verification, creation}` (the stored member names), while the accepted plan lines 21/140 and the implementation hash literal members `contentObject`, `verificationObject`, `creationObject` (`DefaultCustomerShareCommandService.java:139-160`; codified by `CustomerShareCommandsIT.java:378-382`). The implementation is self-consistent, but a verifier following docs/14 computes different hashes. Please have the design owner confirm whether the plan's names are placeholders for the stored members or are the literal canonical members. This is not counted as a finding because the accepted plan is explicit and the implementation follows it.
- **Explicit `"bindingId": null` in `identity_at_capture`.** `JooqSharingCommandRepository.java:116-121` treats key presence with a non-string value as malformed and returns an empty/blocked snapshot, despite the V008 `ck_evidence_capture_shape` permitting a null member. If an evidence producer can emit an explicit null, a legitimate current-binding fallback is denied with `SHARE_RISK_BLOCKED`. Please confirm the evidence producer's null policy; this does not block the current verdict.
- **`databaseFailureCode` breadth.** Any SQLState `23514` is mapped to the 503 material branch, not only sharing-table CHECKs; this is what aggregate finding B-1 required, but non-sharing CHECK failures will be reported as retryable 503 rather than 500. Residual observability risk, not re-reported as a defect.

## Residual Risk

- **Static-only validation.** No Maven, Docker, build, packaging or PostgreSQL command was run in this review. The 185-test/PostgreSQL 16.15 evidence and the fix-3 failure-injection logs are author-provided artifacts outside the snapshot and were not independently reproduced.
- **Canonicalization performance.** `quote()` constructs a new `JsonMapper` for every object key and string value (`DefaultCustomerShareCommandService.java:341`); a create canonicalizes the same content/verification/creation nodes several times, causing roughly one hundred mapper constructions per accepted request. This is a statically provable CPU/GC overhead on the create path; a shared configured mapper should be used when fixing A-01.
- **Numeric precision boundary.** Canonical numbers are reduced through `double` (`DefaultCustomerShareCommandService.java:315-334`) per RFC 8785's number domain, while `evidence.media_object.size_bytes` is an unbounded `bigint > 0` (V008). A media size above 2^53 would be rounded in `content_snapshot`/digests, so content would not be byte-reproducible from the exact evidence fact. Highly unlikely in practice; no test.
- **Request-body bound.** `CustomerSharesController.java:59` reads the entire body with `readAllBytes()` and has no size limit. This was already deferred to gateway/security by Control; it remains a deployment residual risk.
- **Observability.** The command/provider sources are intentionally log-free (the boundary tests reject `Logger`/`System.out`); diagnosis depends on Problem codes and the trace ID. No metrics/audit of rejected projection/risk/policy branches beyond durable facts.
- **Remaining test gaps.** No failure-injection coverage for command-context (`readActiveCallerContext`) SQL/decode → 503, `readEvidenceReference` SQL failure, `sampleDatabaseTime` failure, or `findCreationIdentity`/`findGrantIdByTokenHash` DB failure; risk and projection failures are covered. No control-character canonicalization vector (the A-01 test gap).
- **Environment.** No hosted CI run or production PostgreSQL/ACL rehearsal is included in this snapshot; prior `pg_default_acl`/abnormal-routine-grantor risks remain owned by Platform/Database/Security per Control.
