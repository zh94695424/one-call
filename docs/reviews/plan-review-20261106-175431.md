## Findings

### 01-未修复-[高]-The new independent `sharingAdmissionSha256Provider` can suppress the existing command `sha256Provider` in the normal both-enabled persistence context

- **位置**: Plan §4 line 106 (new `@Bean("sharingAdmissionSha256Provider") Sha256Provider` in `ShareAdmissionPersistenceConfiguration`, allowlist item 20) and §6 line 259 (admission-enabled/command-disabled test); §3 line 70 (independent admission pool); §4 items 1–3/33 and §6 line 270 (PA15/PA16 regression run). Existing `SharingCommandPersistenceConfiguration.java` is **not** in the 36-path allowlist.
- **问题类型**: 架构边界 / 过度耦合 / 不可直接实施 / 并发-启动顺序风险
- **当前写法**: The plan makes the admission configuration own an independent `Sha256Provider` bean and injects it by `@Qualifier("sharingAdmissionSha256Provider")`; it explicitly forbids the new bean from using `@ConditionalOnMissingBean(Sha256Provider.class)` or the command bean name. The plan's only cross-configuration test is `onecall.sharing-admission.datasource.enabled=true` with `onecall.sharing-command.enabled=false`.
- **反例/失败场景**: In the deployment where both feature sets are needed (`@Profile("persistence")`, `onecall.sharing-command.enabled=true` for PA15/PA16 create/revoke/rotate/list/public-read, and `onecall.sharing-admission.datasource.enabled=true` for PA17), both `ShareAdmissionPersistenceConfiguration` and `SharingCommandPersistenceConfiguration` are component-scanned under `com.onecall.core`. If the admission configuration is processed first (e.g. the common alphabetical class order `ShareAdmission…` before `SharingCommand…`), its `sharingAdmissionSha256Provider` bean definition is registered before the command configuration's `@Bean @ConditionalOnMissingBean(Sha256Provider.class) sha256Provider()` is evaluated. The type-based condition then sees the admission bean and suppresses `sha256Provider`; `customerShareCommandService` and `publicShareQueryService` both require `@Qualifier("sha256Provider")` and the application context fails to start. If the command configuration is processed first, both beans exist and startup succeeds — so the behavior is classpath/scan-order dependent, not deterministic.
- **为什么有问题**: Fix-4 fixes the admission-only startup gap but introduces a second producer of the same `Sha256Provider` type into a context where the pre-existing producer is registered behind a **type-based** `@ConditionalOnMissingBean`. Spring Boot explicitly limits the reliability of `@ConditionalOnMissingBean` to beans processed so far and recommends it only in auto-configuration; these are user `@Configuration` classes. The plan’s allowlist forbids editing `SharingCommandPersistenceConfiguration.java`, so the implementation gate cannot make the fallback name-based or unconditional within its permitted writes. The plan’s own `PublicShareAdmissionIT#publicGetAndCreatorCreateRevokeRotateListMeRemainUnchanged` and §6 PA15/PA16 regression claims require a context in which both graphs work, but the plan only tests command-disabled.
- **直接证据**: `backend/src/main/java/com/onecall/core/sharing/internal/persistence/SharingCommandPersistenceConfiguration.java:41–42` (`@Profile("persistence")` + `@ConditionalOnProperty(prefix="onecall.sharing-command", name="enabled", havingValue="true")`), `:96` (`@Qualifier("sha256Provider") Sha256Provider` in `customerShareCommandService`), `:130–137` (`@Bean @ConditionalOnMissingBean(Sha256Provider.class) Sha256Provider sha256Provider()`); `PublicSharePersistenceConfiguration.java:29–31` (same command enablement) and `:92–99` (public-read service also `@Qualifier("sha256Provider")`); `OneCallApplication.java:6` (`@SpringBootApplication` scanning `com.onecall.core`); plan §4 line 106, §6 line 259, allowlist items 1–36 (no `SharingCommandPersistenceConfiguration.java`); `pom.xml:9–10` (Spring Boot 4.1.2).
- **影响**: The normal production/regression persistence context can fail at startup (no `sha256Provider` for command/public-read) or wire nondeterministically across environments; the implementation can pass the command-disabled unit test while the both-enabled deployment and the required PA15/PA16 regression cannot run. This is a code-generation blocker for the frozen allowlist.
- **建议改法和验证点**: Add `backend/src/main/java/com/onecall/core/sharing/internal/persistence/SharingCommandPersistenceConfiguration.java` to the allowlist (36 → 37) and change its SHA fallback to a name-based condition (`@ConditionalOnMissingBean(name = "sha256Provider")`) or make it unconditional under the command gate, so the admission bean cannot suppress it; alternatively adopt a single explicitly shared SHA bean contract with deterministic precedence and update the plan/sets/counts. Add an `ApplicationContextRunner`/context assertion with `persistence` + `onecall.sharing-command.enabled=true` + `onecall.sharing-admission.datasource.enabled=true` proving both `sha256Provider` and `sharingAdmissionSha256Provider` exist, both services wire, and the command graph is present; keep the command-disabled probe. Update the 36-path arithmetic and CI inventories if a path is added.
- **修复风险（中）**: Touches an existing persistence configuration and the frozen 36-path/CI arithmetic; must preserve the exact command gate and PA15/PA16 behavior.
- **严重程度（高）**: Deterministic order-dependent startup failure in the production both-enabled context; masked by the plan's current tests and unfixable within the frozen allowlist.

## Open questions

1. **`verificationResult` in the `ADMISSION_GRANTED` payload (non-blocking).** Plan §2.3 line 46 freezes `{verificationMode, verificationResult, revocationGeneration, codeGeneration, grantExpiresAt, admissionExpiresAt, sessionExpiresAt}`. docs/14 line 253 enumerates the durable witness as `verificationMode`, the two member recipient IDs, `revocationGeneration`, `codeGeneration`, `grantExpiresAt`, `admissionExpiresAt`, `sessionExpiresAt`; it does not name `verificationResult`. The V009 `ck_share_access_event_admission_facts` CHECK requires presence of the listed keys but does not forbid extras (`V009__sharing.sql:127–128`), so this is not a schema violation, but the plan should state whether the extra field is intentional and whether docs/14 should be read as an exact payload contract. If the intent is exact docs/14 alignment, remove `verificationResult`; if it is an admitted extension, record it as such.
2. **Secret-bearing record `toString()` (non-blocking hardening).** The plan redacts `ShareAdmissionCapabilityToken.toString()` but defines `ShareAdmissionRequest.Verification.ExtractionCode` as a record holding the write-only `code` and `ShareAdmissionRequest` as a record holding the raw `admissionRequestId`; Java’s generated `toString()` echoes both components. The plan’s “never echoed/logged” invariant therefore relies on the implementation never logging/including the request object. Requiring redacted `toString()` for the secret-bearing verification records (and a unit assertion) would make the invariant structural.
3. **Frozen manifest provenance (non-blocking).** File count (1,423) and bytes (52,738,766) match exactly and no relative private path was found. The documented “sorted relative path + lowercase per-file SHA-256 lines” recipe variants did not reproduce `601A10943A4DB5FB4AAEC37F4A1E84F68B8B88D96AF83D3971A5BB242D6441A9` from this tree; the freeze-time Control write ordering or a recipe detail is the likely cause. The declaration is accepted as provenance; the Controller’s freeze recipe remains authoritative.
