**F-02 — P3（Low，non-blocking，test-hardening）：partial-index predicate assertions in `PostgresContainerIT` use loose multi-substring `.contains` and would also match an inverted predicate.**

- Locations：`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:607-621`
- Evidence：The three partial-index checks assert `indexdef` `.contains("WHERE", "status", "'NEW'|'PENDING'|'FAILED'")`. An `indexdef` such as `... WHERE status <> 'NEW'` or `... WHERE status = 'FAILED' AND status <> 'NEW'` would satisfy the same three substrings. The immediately preceding exact 12-index-name `containsExactly`（`:593-605`）and the V001-only migration source bound the index *names*, but do not discriminate the *predicate polarity*.
- Impact：Inventory discrimination gap only. V001 as authored writes the correct positive predicates（`ix_idempotency_new_alert … WHERE status = 'NEW'`; `ix_outbox_pending_available … WHERE status = 'PENDING'`; `ix_outbox_failed_available … WHERE status = 'FAILED'`）, and the migration/container tests passed against that SQL. The gap would only matter if a future V001 edit（or Flyway checksum-breaking rewrite under a new history）inverted a predicate while keeping the index name.
- Concrete fix：Assert the full normalized `indexdef` string, or parse the predicate（e.g. require the exact substring `WHERE (status = 'NEW')` / `WHERE (status = 'PENDING')` / `WHERE (status = 'FAILED')` as PostgreSQL renders them）, or add a catalog query on `pg_index`/`pg_get_expr` that compares the predicate expression exactly.
