## Findings

### 01-未修复-中-The documented 5s total request deadline is not actually enforced; an activation-filtered list can hold one of four pool connections far beyond 5s

- **入口/函数**: `DefaultOperationsSubjectReadService.list(...)` (activation-filtered loop) reached through `GET /api/v1/operations/subjects`; transaction wiring in `OperationsSubjectReadPersistenceConfiguration.operationsSubjectReadTransactionTemplate`.
- **文件(行号)**: `backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/DefaultOperationsSubjectReadService.java:60-90` (up to 100 batches; two owner SELECTs per batch at 62 and 75); `backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/OperationsSubjectReadPersistenceConfiguration.java:107-110` (`setTimeout(5)`); `backend/src/main/java/com/onecall/core/operations_iam/subjectread/OperationsReadContext.java:31-33` (`SET LOCAL statement_timeout='2000ms'`, lock/idle timeouts). Plan claim: `docs/gateflow/pa33-operations-subject-read-foundation-plan.md:129` ("total request deadline also enforced by transaction timeout"); implementation report §3 lists "timeout 5 seconds".
- **输入场景**: Authenticated current ACTIVE `ADMIN`/`OPS` repeatedly calls the list endpoint with `activationStatus=INACTIVE` (or another activation value) while the matching `subject_number`/activation data makes each candidate/activation statement approach, but stay under, the 2000 ms DB statement timeout. No match or insufficient matches forces the full 100-batch scan.
- **实际分支**: `filtered == true`, `batchSize == 101`; the loop executes up to 100 iterations of `fetchCandidates` + `activationReader.find`; only the per-statement `statement_timeout=2000ms` is DB-enforced; at 100 full batches the service throws sanitized 503.
- **预期行为**: Plan §6.3 says the request has a total 5-second deadline ("total request deadline also enforced by transaction timeout"); on deadline exhaustion the read should fail closed promptly with 503/rollback, leaving the pool usable.
- **实际行为**: `TransactionTemplate.setTimeout(5)` is a `DataSourceTransactionManager` transaction hint, not a wall-clock abort for direct jOOQ statements. The DSL uses `DataSourceConnectionProvider`/`TransactionAwareDataSourceProxy` and does not apply the Spring `ConnectionHolder` timeout as a `JdbcTemplate` per-statement timeout; the only enforced bound is the 2 s `SET LOCAL statement_timeout` per statement (and the idle timeout only applies between statements). With 200 statements this permits a request to stay active for on the order of hundreds of seconds (e.g. ~190 s if each statement takes ~0.95 s; up to ~400 s at the 2 s per-statement ceiling). Because the pool maximum is 4 and connection timeout is 3000 ms, four concurrent such requests can starve unrelated reads with 503s.
- **直接证据**: Batch loop bound `filtered ? 100 : 1` (line 60), per-batch `owner(... fetchCandidates)` (62) and `owner(... activationReader.find)` (75), `SET LOCAL statement_timeout = '2000ms'` (Context 31), `template.setTimeout(5)` (PersistenceConfiguration 110). No elapsed-time/remaining-budget check exists anywhere in the loop or before the per-batch SQL; no servlet/async request timeout is configured for these routes.
- **影响**: Availability/resource-exhaustion under authenticated (but low-privilege) read traffic or slow/adversarial data; contradicts the plan's explicit total-deadline guarantee and the accepted "bounded" validation story. No data/authorization impact; no writes.
- **建议改法和验证点**: Enforce a real wall-clock budget: capture the request start in the transaction and before each batch reject with 503 when elapsed >= 5 s; optionally set `SET LOCAL statement_timeout` to the remaining budget before each owner query. Add a Failsafe test that installs an execute listener sleeping below 2 s per candidate/activation statement across enough batches to exceed 5 s, and assert (a) 503 within roughly the budget, (b) rollback/no partial body, (c) the same physical connection/pool remains clean. Document the actual bound if the Controller instead accepts a query-count-only bound.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-低-`owner()` converts unknown implementation failures from owner ports into retryable 503 instead of the frozen 500 INTERNAL; the 500 test bypasses the wrapper

- **入口/函数**: `DefaultOperationsSubjectReadService.owner(Supplier<Result>)`, used by every list/detail owner-port call (`fetchCandidates`, `detail`, `ActivationReader.find`, `TrialReader.find`, `EvidenceCounter.count`, `OrderCounter.count`).
- **文件(行号)**: `backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/DefaultOperationsSubjectReadService.java:178-181` (catch all `RuntimeException` → `unavailable()`); contrast the outer `read` mapping at 140-152; plan `docs/gateflow/pa33-operations-subject-read-foundation-plan.md:59` and implementation report §3 ("ordinary unknown implementation failure → 500 INTERNAL").
- **输入场景**: A programming/runtime fault inside a port implementation that is not a SQL/data/transaction/role/timeout/bean failure — e.g. a future `NullPointerException`/`IllegalStateException` in a row-mapping helper, or a custom `SubjectReader`/`ActivationReader` implementation throwing an unexpected runtime exception.
- **实际分支**: The port call is wrapped by `owner()`; every `RuntimeException` is caught and rethrown as a new `Failure(Code.SERVICE_UNAVAILABLE)`.
- **预期行为**: Plan §3.2 distinguishes sanitized 503 for SQL/connection/transaction/role/timeout/bean/structural owner failures from ordinary unknown implementation failures, which remain 500 INTERNAL (the same distinction the outer `read`/controller mapping implements).
- **实际行为**: Any unknown runtime exception from an owner port is reported as `503 SERVICE_UNAVAILABLE`, a retryable unavailable signal, hiding the internal defect and defeating the service/controller 500 path. `owner()` also discards a non-503 `Failure` code if an adapter ever throws one.
- **直接证据**: `owner()` catch at 180; the only 500-path test (`OperationsSubjectReadServiceTests.sqlBeanTransactionAndUnknownFailuresMapWithoutLeakingCauses`, lines 403-456) throws `IllegalStateException` from `dsl.fetchOne` in `authority` (line 424), i.e. **outside** `owner()`; no test exercises an unknown runtime exception through a port call.
- **影响**: Wrong error classification/observability and retry semantics for internal bugs on the read endpoints; no data leak or authorization impact, but the frozen failure contract and the report's claim are not met for this path.
- **建议改法和验证点**: Narrow `owner()` so expected infra exceptions (`org.jooq`/Spring `DataAccessException`, `TransactionException`, `BeansException`, and `Failure`) retain the intended 503/code, while other `RuntimeException` propagate to `read`/the controller's `unexpected` handler for sanitized 500 INTERNAL. Add a service/web test with a mock port throwing `IllegalStateException` and assert 500/problem envelope/no cause leak.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
