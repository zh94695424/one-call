- **输入场景**: Negative skew (JVM clock behind database clock) after an Operations write: Operations suspends with `updated_at = T_db1`, then a subsequent customer ACCEPT/DECLINE allegedly writes `service_activation.updated_at` backwards with `Instant.now() = T_jvm < T_db1`, supposedly tripping `ck_service_activation_time_order` → 23514 → sanitized 503 on the customer path (F-1 mode 2).
- **实际分支**: The alleged subsequent customer write does not exist on any reachable branch. `DefaultCustomerSubjectActivationService` writes `service_activation` only via `createHead` (line 125, only when `currentHead.isEmpty()`) and `advance` (line 127, only when `transitionNeeded`, i.e. head status `INACTIVE`, line 110). After any committed head, status is `ACTIVE` or `SUSPENDED`: ACCEPT on `SUSPENDED` throws `FORBIDDEN` at line 102 before any head write; ACCEPT on `ACTIVE` takes `transitionNeeded=false` and writes nothing to `service_activation`; DECLINE returns at lines 97–100 without touching the head; `OperationsLifecyclePersistenceConfiguration`-backed Operations transitions only produce `ACTIVE↔SUSPENDED` (`DefaultOperationsSubjectLifecycleService:26–27, 70–74`), never `INACTIVE`, and `INACTIVE` exists only inside the customer’s initial create+advance transaction (rolled back together on failure). The repo-wide scan shows exactly two `service_activation` writers (customer repository and Operations repository) and exactly one `Instant.now()` in production (customer activation). Additionally, `ck_service_activation_time_order` is `CHECK (updated_at >= created_at)` (V007:94–95) — it is not a monotonicity check against the previous `updated_at`; a backwards `updated_at` that remains `>= created_at` would not raise 23514 at all. The `guard_service_activation` trigger (V007:174–195) protects only `id`/`subject_id`/`created_at`.
- **预期行为**: The F-1 disposition record should claim only failure modes reachable on the two-writer topology. Positive skew (JVM ahead of DB) is reachable and correctly claimed: customer writes `head.updated_at = T_jvm`, Operations `decisionTime = clock_timestamp() = T_db < T_jvm`, guard at `DefaultOperationsSubjectLifecycleService:68` throws sanitized `SERVICE_UNAVAILABLE` → 503 with rollback and no partial facts (with `ck_service_activation_time_order` as backstop if the guard were absent). Negative skew produces no cross-path failure: the guard passes (DB time ahead of customer-written head), the CHECK passes (`updated_at = T_db >= created_at = T_jvm`), the customer path performs no clock comparison against the head, and the Operations witness pairs `head.updatedAt` with `transition.occurredAt` from the same writer in every reachable sequence.
- **实际行为**: Control :93 states “either skew direction can produce sanitized 503 with rollback and no partial facts”; the fix-matrix clock row (aggregate-fix-1 :35) lists “negative JVM-behind/DB-ahead skew” alongside the positive direction as cross-path risk scope. The negative direction as described is unreachable and the cited constraint semantics are incorrect.
- **直接证据**: (a) writer scan — only `JooqSubjectActivationRepository.createHead/advance` (customer) and `JooqOperationsLifecycleRepository.advance` (Operations) write `service_activation`; (b) customer branch trace `DefaultCustomerSubjectActivationService:97–130` shows no post-initialization head write under any reachable status; (c) Operations never writes `INACTIVE` (`from`/`target` are only `ACTIVE`/`SUSPENDED` at `DefaultOperationsSubjectLifecycleService:26–27`); (d) CHECK text `V007:94–95` compares only to `created_at`; (e) guard `DefaultOperationsSubjectLifecycleService:67–68` is the only cross-path timestamp comparison and fires only when DB time is behind the stored head — i.e. positive skew; (f) `validateAnchor` (`DefaultCustomerSubjectActivationService:177–180`) performs no time comparison.
