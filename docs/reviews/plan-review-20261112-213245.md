## 3. Findings

### 1-未修复-中-staged Invalid/Unavailable 在按行身份判 replay conflict 之前被启用，可能以 422/503 覆盖应得的 409 CLAIM_REPLAY_CONFLICT

- **位置**: plan §5 决策矩阵（L145–L146 行相邻、未钉死判定顺序）；§5 身份句（L156）；§6.3 两阶段（L222–L223「Staged invalid/unavailable stored reference is acted on only if that row is actually needed after risk/replay precedence」）；测试清单 I09/U06（覆盖 risk 先于 staged Invalid/Unavailable，但未覆盖「行身份不匹配先于 staged Invalid」）
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口
- **当前写法**:
  - L145：`| Same request, any logical identity component changed; CLAIM_REPLAY_CONFLICT | 409 ... |`
  - L146：`| Stored reference unresolvable; CLAIM_REPLAY_UNRESOLVABLE | 422 ... |`
  - L156：「Subject/account/null organization/method are row identity; binding/number/proof are decrypted payload identity. A request key owned by another account/subject is a generic replay conflict...」——陈述了身份规则，但未规定 phase 1 已 stage 的 Invalid/Unavailable 必须在**行身份比较之后**才可被启用。
  - L222–L223：phase 1 对「collected stored references」全部执行 open 并 stage 为 decoded payload 或 typed Invalid/Unavailable；phase 2 仅说 staged Invalid/Unavailable「acted on only if that row is actually needed after risk/replay precedence」，「needed」未定义为「该行通过了 subject/account/null-org/method 行身份比较」。
- **反例/失败场景**:
  1. 客户端以 request key `R` 重放，但绑定/主体/账户与首存行不同（他人账户或同账户改上下文）。
  2. Phase 1 对 `findByRequestId(R)`（无账户过滤）收集到该行，open 其存储 reference 失败（provider Unavailable、密文版本不符等）→ stage 为 typed Invalid 或 Unavailable。
  3. Phase 2 锁内 reread 同一行：按 T-S1-06 step 5，**先**比较行身份（subject/account/null-org/method）→ 不匹配即应返回 409 `CLAIM_REPLAY_CONFLICT`（且不依赖解密结果）。
  4. 若实现按「stage 的 Invalid/Unavailable 在该行被选中时启用」理解 L223，会先消费 staged Invalid/Unavailable → 返回 422 `VALIDATION_FAILED` 或 503 `SERVICE_UNAVAILABLE`，把本应 409 的 replay conflict 降级/改写。
  5. 反向同理：同账户上下文改写（应 409）也会被 422/503 覆盖。这直接违反 Goal Confirmation「risk 409 before replay」的 replay 段语义与冻结矩阵 L145 的公开码。
- **为什么有问题**: T-S1-06 step 5 明确先比行身份、再解密比较 payload identity；OpenAPI 只允许三个域 409（`CLAIM_RISK_BLOCKED`/`CLAIM_REPLAY_CONFLICT`/`CLAIM_CONTEXT_CONFLICT`），`CLAIM_REPLAY_UNRESOLVABLE`→422 是「该行确实通过身份比较后的存储参考不可解」结局。plan 矩阵把两行并列而未写判定顺序，phase 2 又用未定义的「needed」授权 staged 结论，implementation agent 有两种合理读法，其中一种产生公开码错配（用户可见、可审计错因）。
- **直接证据**:
  - plan L145、L146、L156、L222–L223（上文原文）。
  - `docs/14-production-data-model-and-flyway-schema-spec.md` T-S1-06 step 5：行身份（subject/account/org/method）比较先于 decrypted payload（bindingId/numberHmac/proofRef）比较。
  - `api/openapi/onecall-v1.openapi.yaml`（该 operation 三个域 409；无 400；`x-onecall-replay-order: risk-before-replay`）。
  - plan 测试清单：I09 证明 risk 先于 staged Invalid/Unavailable，但无用例断言「行身份不匹配 → 409，即使 staged 为 Invalid/Unavailable」。
- **影响**: 实施 agent 生成错误优先级 → 用户可见公开码错配（409→422/503）；审计/验收按矩阵无法对齐；replay 防护语义与 Goal Confirmation「replay identity」段落偏差；评审不可验收直至补测。
- **建议改法和验证点**:
  1. 在 §5 矩阵 replay 两行处显式写死判定序：`risk → 行身份比较（不匹配 ⇒ 409 CLAIM_REPLAY_CONFLICT，不解密、不消费 staged Invalid/Unavailable）→ 行身份匹配后才允许 staged decoded/Invalid/Unavailable 参与 payload 比较与 422/503 决策`。
  2. 在 §6.3 把 L223 的「actually needed after risk/replay precedence」改定义为「该行已通过 subject/account/null-org/method 行身份比较」。
  3. 新增/扩展 I 系测试：staged Invalid 与 staged Unavailable 各一例，断言行身份不匹配时返回 409 而非 422/503；并断言该路径不触发 provider open 消费。
  - 验证点：上述两条断言在 Surefire 落地且 CI 计数按 §10 重算一致。
- **修复风险（低）**: 仅 plan 措辞 + 1–2 个测试，不改锁序/SPI/manifest 主干。
- **严重程度（中）**: 用户可见公开码错配，但有明确单点修复、不涉及架构返工。

### 2-未修复-中-两阶段 preparation/PreparationChanged 机制由 deferred KMS 假设驱动，超出 S1 confirmed goal 的最小设计（过度设计/非最优方案）

- **位置**: plan §6.3（L222–L225，尤其 L225「The small prepare phase is necessary because later KMS-backed opening must not hold PG locks」）；Goal Confirmation no-overdesign / fail-closed SPI、无真实 provider/KMS 条款；测试 U06/I24/U17/U18 中与 stale-prep、PreparationChanged 重启相关部分
- **问题类型**: 过度设计 / 非最优方案 / 目标漂移（把 deferred Q2 的 KMS 需求升级为当前 slice 的结构性机制）
- **当前写法**: 每次尝试拆为 unlocked preparation（SELECT-only tx、关连接后 verify/seal/open、stage payload/Invalid/Unavailable）+ authoritative locked tx（rediscover、PreparationChanged 整事务回滚并在三预算内重启 phase 1）；正当性直接引用「later KMS-backed opening must not hold PG locks」。
- **反例/失败场景**:
  1. S1 生产默认 SPI 为 fail-closed Unavailable，proof/input open 在进 claim 事务**之前**即可终止（plan 自述 L222「Input proof/cipher unavailability can terminate before the claim transaction」）；存储 reference open 同样是只读 SPI。当前无任何真实网络/KMS 依赖必须在持锁期间调用。
  2. 单事务实现（锁内全部谓词从 reread 得出，测试 fake 在无事务/外置条件下被调用一次即可）同样满足 T-S1-06 一步式原子性，且**更少**状态机分支。
  3. 两阶段引入额外失败模式：stale prep 与锁内 reread 分叉、`PreparationChanged` 消耗总三尝试预算（把本可用于 23505/40001 的预算挪给内部准备失效）、双读放大、U06/I24 等额外测试与 gate 成本。
  4. 若 deferred Q2 KMS 落地时 SPI 契约改为「必须在锁外 open」，届时再引入 preparation 是有证据的驱动；在 S1 以 deferred 需求预先支付结构成本，正落入 no-overdesign 条款挑战的模式。
- **为什么有问题**: Goal Confirmation 明确 fail-closed proof/reference SPI、禁止真实 provider/KMS、one behaviorally coherent slice、no-overdesign。L225 的必要性论证依赖**本 slice 不存在**的 KMS 后端。更简单路径（单 authoritative 事务 + 外置测试 fake）在行为上等价于 T-S1-06 文本（其本身即单事务模型），却少了 PreparationChanged 状态机与预算耦合。plan 未对比该替代方案。
- **直接证据**:
  - plan L225（KMS 必要性原句）、L222（生产 Unavailable 可在 tx 前终止）。
  - `docs/gateflow/project-execution-control.md` PA30 Goal Confirmation：fail-closed SPI、无 provider/KMS、one slice、no-overdesign。
  - `docs/14` T-S1-06：单事务锁序与谓词顺序，无 prepare 阶段。
  - plan §9 测试清单中 U06（stale preparation）、I24（PreparationChanged 重启）、U17/U18 相关段为该机制独有成本。
- **影响**: 实施与 review 面扩大；三尝试预算被 PreparationChanged 稀释 → 更易 `CLAIM_CONCURRENCY_EXHAUSTED`/503；测试与 gate 成本上升；若 agent 理解偏差可能把 prep 值误当授权（plan 已警告但增加实现面）。
- **建议改法和验证点**:
  1. **推荐**：S1 改为单 authoritative 事务方案——锁内 reread 全部谓词；verify/seal/open 作为无 Spring 事务的协作调用置于获取行锁之前或按 T-S1-06 步骤嵌入单 tx（测试 fake 断言无 active tx 的要求可保留在「不得在行锁后做 I/O」的等价约束上）；删除 PreparationChanged 与 phase 重启，三预算只服务 23505/40001。
  2. **或**：保留两阶段，但把 L225 改为绑定本 slice 自身的理由（如：stored-reference open 与 risk reread 的先后在单 tx 内无法满足「staged 不先于 risk」的测试注入点），并删除 KMS 措辞；同步在 §3 non-goals 声明 preparation 结构不为 Q2 预留 API。
  3. 任一路径：在 plan 中显式对比「单 tx vs 两阶段」的取舍一句，供 implementation agent 不再自行发明第三种。
  - 验证点：U06/I24 的存在性或删除与所选路径一致；§10 计数随之重算。
- **修复风险（中）**: 改单 tx 需要重写 §6.3/§7 相关段与部分 U/I 测试条目；仅收紧措辞则风险低。
- **严重程度（中）**: 不阻断正确性目标，但直接违反 no-overdesign/最小设计并放大实施失败面。
