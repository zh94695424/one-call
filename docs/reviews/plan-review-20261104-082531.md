### PB-02-未修复-高-create 的确定性身份与指纹输入被写成包含证据投影与采样DB时间，与 §2.12/§9.29 冻结输入集直接冲突

- **位置**: plan:38（"Creation builds the deterministic share identity and canonical fingerprint from validated request, trusted caller/context, evidence projection and one sampled DB timestamp"）、plan:22、plan:36、plan:72/76。
- **问题类型**: 契约缺失 / 状态机漏洞 / 数据损坏风险 / 不可直接实施
- **当前写法**: plan:22 只声明身份的**形状**（`share:`+64hex / 81 字符），没有声明哈希输入；plan:38 是唯一一处定义 create 身份与指纹来源的句子，把四项输入并列为"validated request, trusted caller/context, evidence projection and one sampled DB timestamp"。
- **反例/失败场景**: docs/14 §2.12 明确 `share_id` 是"derived **only** from the trusted authenticated creator account and the stable creation-request/action ID: `share:` plus the lowercase SHA-256 of the canonical JSON `{creatorAccountId, creationRequestId}`"，§9.29 step 1 同样只写"Derive `share_id` from the authenticated canonical account and stable `creationRequestId`"。同一句里的 `creationFingerprint` 输入集被 §2.12 闭合为 `content_snapshot.creation` 的 11 个语义字段，且"excluding creationFingerprint itself, generated IDs, capability/code secrets **and only generated or observed transport, network, persistence or server-decision timestamps**"，`valid_from` 只是 §9.29 step 4 冻结的 grant 列，不在语义字段内。于是两种读法都错：(读法 A) 把投影/context/timestamp 混入 `share_id` → 同一 `creationRequestId` 的重试因时钟采样或工作区选择差异算出不同 `share_id`，`ON CONFLICT (share_id)` 永不触发，plan:38 的 replay 分支失效并**插入第二个 grant**（两个公开 capability token、两份 audit/Outbox 事实），这是不可事后修正的持久化损坏；(读法 B) 身份正确但指纹含 `valid_from` → 每次同身份重试指纹必然变化，按 plan:38 返回 409 `SHARE_CREATION_CONFLICT`，直接违反 §2.12"Same identity and fingerprint return the existing grant metadata only"与 §9.29 step 4"A lost creation response returns metadata only"，并使 plan:76 的 `createReplayReturnsMetadataAndDoesNotPersistOrReturnSecrets` 与 `createConcurrentSameAndDifferentIdentities` 无法同时成立。
- **为什么有问题**: 这是上一轮以"身份/指纹推导时机"名义接受并关闭的同一冻结契约；本轮只修正了顺序（plan:36/40），却把**输入集**写成了与冻结真源不相容的闭包。plan 又声明"Stop and report the exact conflict if a frozen schema signature … cannot support this plan"（plan:94），因此实施 Agent 既不能自行裁剪输入集，也不能发明第三个。
- **直接证据**: plan:22/36/38/72/76/94；`docs/14-production-data-model-and-flyway-schema-spec.md:253`（transition 身份/指纹）、`:254`（`share_id` "only …"与 `creationFingerprint` 排除规则）、`:3398`（§9.29 step 1 首句）、`:3402`（step 4 冻结 `valid_from` 为列）；`api/openapi/onecall-v1.openapi.yaml` create 200 描述"Same creationRequestId with the unchanged frozen scope fingerprint replays the metadata-only ShareState … without reissuing a new share identity"；`backend/src/main/resources/db/migration/V009__sharing.sql:31`（`uq_share_grant_share_id`）。
- **影响**: 数据损坏 / 重复 grant 与重复一次性 token / 幂等重放失效 / 生成错误代码 / 不可恢复的持久化事实
- **建议改法和验证点**: 拆成两句并逐字段闭合：`share_id` = `share:` + SHA-256( canonical `{creatorAccountId, creationRequestId}` )，仅此二输入；`creationFingerprint` = §2.12 列出的 `content_snapshot.creation` 语义字段闭包（含 `expiresAt`、`scopeDigest`、`creationRequestDigest`），显式声明 `valid_from`/`occurredAt`/`revision`/生成 secret **不进入**指纹；`valid_from` 仅作为列写入与 `expiresAt >` 比较及 access-event `occurred_at`。在 `createBuildsDeterministicIdentityAndFingerprint` 中断言：跨两次 `clock_timestamp()` 采样、跨 workspace 选择、跨证据事实的重试仍得到**同一** `share_id`；同身份同语义重放得到 200 metadata-only 且 `sharing.evidence_share_grant` 行数恒为 1。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Final conclusion

**fail**。fix-5 retry 确实把 round-2 全部接受项按字面关进了 canonical 文本（身份推导时机、rotate 事件快照、`rotationPolicy` 的新 transition 调用与 403/503 分列、create 的事务后校验、create typed-code 表、terminal 优先级、READ COMMITTED、Decision 单一记法、Surefire 断言范围），并且 12/18/197 计数、身份长度、dedupe 双前缀、事实追加序与 V001/V009/V010 ACL 全部经代码事实复核成立。

但压缩后的 plan 仍不可交付 implementation：PB-01 是硬阻断——三个 POST 在最高优先级过滤器处必然 404，而唯一被授权的 Problem 输出器无法发出任何已声明的 403/409/410/422 映射，且被钉住的既有测试与 CI 名单断言相反行为；PB-02 把 create 身份/指纹的输入集写成与 §2.12/§9.29 冻结闭包冲突的形式，最坏后果是同一 `creationRequestId` 产生第二个 grant 与第二个一次性 token；PB-03/PB-04/PB-05 分别在被接受的 R02 另一半路径、两个冻结摘要输入以及 secret/policy provider 端口与 required 文件白名单上留下必须由实施 Agent 自行设计的契约面；PB-06 使新冻结的 typed-code 表没有任何可验收的断言归属。建议下一轮 fix 只需在现有 canonical 文本上做定向补写（无需重写结构），并同步把过滤器/输出器/名单文件纳入白名单后再复审。
