## 3. Findings

### F-01 (blocker) — §6.2 template expectation contradicts the S1 slice boundary

- **Evidence**: §6.2 (plan lines 185–194) states the shared template command must print `groups=9 complete=0 incomplete=9`. §4.2 line 128 defines S1 with 7 groups; S2 "追加 2 组" (`backupRecovery`, `capabilityEvidence`). S1 boundary (line 224) explicitly excludes backup/capability, and S1 exit (line 225) requires "§6.2 template 与 stage=s1 全过". A S1-only calculator therefore reports `groups=7`, failing the very command S1 must pass; a S1 calculator that already emits 9 groups must implement the S2 groups early, which S1 forbids.
- **Impact**: S1 cannot satisfy its own exit criterion as written; the implementing agent has no single consistent target.
- **Bounded alternative**: split the expectation — S1 exit asserts `groups=7` (or `groups=7 + 2 deferred INCOMPLETE stubs with no formulaIds`, explicitly stated); the `groups=9` template assertion moves to the S2 exit only. State exactly which of the two the author intends; do not leave both in §6.2 with a shared S1 exit.

### F-02 (blocker) — `SPOOL_CATCHUP_SPARE_BPS` semantics contradict `F-SPOOL-03`; continuing production can be subtracted twice

- **Evidence**: input table line 89 names `SPOOL_CATCHUP_SPARE_BPS` as "恢复追赶的**空闲**吞吐" and warns "不得把总吞吐当空闲". `F-SPOOL-03` line 122 computes `drain = peakBacklog / (catchUpSpare - continuing)` and rejects `catchUpSpare <= continuing` as `DRAIN_IMPOSSIBLE`. If the input is truly spare/idle throughput (already net of continuing production), subtracting `SPOOL_CONTINUING_BPS` again double-subtracts; if the input is gross recovery-window throughput, the name and the "spare" warning are wrong and users following the description will understate drain rate.
- **Impact**: either infinite `DRAIN_IMPOSSIBLE` false positives or overstated drain speed — both directly corrupt the outage-recovery story this spec exists to make honest.
- **Bounded alternative**: pick one contract and align name, description, formula, and fixture `s1-05`: (A) `SPOOL_RECOVERY_TOTAL_BPS` (gross) with `drain = backlog / (total - continuing)` and `total <= continuing ⇒ DRAIN_IMPOSSIBLE`; or (B) keep `SPOOL_CATCHUP_SPARE_BPS` (net idle) with `drain = backlog / spare` and `spare <= 0 ⇒ DRAIN_IMPOSSIBLE`. Also state that `spare`/`total` are measured for the recovery window, not daily averages.

### F-03 (medium) — `F-NODE-02` N-1 failover check drops the headroom applied by `F-NODE-01`

- **Evidence**: `F-NODE-01` (line 108) sizes nodes with `measuredPerNodeRate * (1 - headroomRatio)`. `F-NODE-02` (line 109) validates failover as `peakRate <= measuredPerNodeRate * (deployedNodes - 1)` with no headroom factor. Adversarial lens requires sizing headroom and N-1 reserve to be consistent; as written, a deployment can pass failover while failing the headroom-aware sizing formula, or vice versa, with no stated rationale.
- **Bounded alternative**: use `peakRate <= measuredPerNodeRate * (1 - headroomRatio) * (deployedNodes - 1)` (same per-role `headroomRatio` as F-NODE-01), or explicitly document why failover may run at 100 % of measured per-node rate (e.g., failover is a short excursion) and mark that as an owned operational assumption with an owner in §8.

### F-04 (medium) — `F-BACKUP-01` uses truthiness, cannot express valid zero RPO, and conflates `included=false` with missing

- **Evidence**: line 123 requires all six dependencies to satisfy `included && rpoSeconds && rtoSeconds && restoreTestedAt && evidenceRef`. A legitimate approved `rpoSeconds: 0` (synchronous/zero-loss target) fails the `rpoSeconds` truthiness test. `included: false` (deliberately out of scope) and a missing `included` field both produce the same incomplete result with no distinct code. Empty-string `restoreTestedAt` passes a naive truthiness check in some encodings and no ISO-date validation is specified, though §4.3 lists `APPROVAL_INVALID`-class failures for meta only.
- **Impact**: either false `COPIES_ONLY_INCOMPLETE` on a strict-but-valid recovery target, or silent acceptance of an invalid restore-test date — undermining the "recovery is a dependency closure" claim.
- **Bounded alternative**: typed checks — `included === true`, `typeof rpoSeconds === 'number' && rpoSeconds >= 0`, same for `rtoSeconds`, `restoreTestedAt` must be non-empty ISO-8601 parseable and not in the future relative to input time, `evidenceRef` non-empty string; distinct flags/codes for `DEPENDENCY_EXCLUDED` (`included=false`) vs `DEPENDENCY_MISSING`. Fixture `s2-02` should include a zero-RPO complete case and an `included=false` case.

### F-05 (medium) — no named formula for original recording upload peak/average bandwidth

- **Evidence**: the controller success signal (execution-control line 41) requires "recording/upload/playback bandwidth". The plan derives playback (`F-PB-01..03`) and storage (`F-REC-01..06`) but the only upload-side numbers are raw inputs `SPOOL_NEW_PEAK_BPS`/`SPOOL_NEW_AVG_BPS` (line 86–87) with no derivation from `REC_*` (e.g., validated bytes per recording × per-day count over an upload window, or concurrent uploads × bitrate). There is no formula tying carrier-room upload egress to measured recording parameters, and no explicit statement that upload bandwidth is an owned measured input with no derivation.
- **Impact**: a required success-signal surface is silently uncovered; the implementing agent may invent an upload formula or omit the section without a stop condition.
- **Bounded alternative**: either add one bounded formula (e.g., `F-UP-01: uploadBps = REC_PER_DAY * F-REC-02 * 8 / uploadWindowS` with `uploadWindowS` as a typed measured input, peak variant = concurrentUploads × F-REC-01) with the same unknown propagation, or state in §1/§4 that original upload peak/average bandwidth is a measured input (`UPLOAD_*_BPS`) with provenance and no derived formula, owned by Telephony/IVR line integration. Do not leave it undefined.

### F-06 (medium) — `F-REC-05` partial derived types conflict with global unknown propagation; derived bytes inherit original version/retention

- **Evidence**: §4.3 line 133 mandates "任何必填操作数为 unknown，组结果为 INCOMPLETE 且 values 为 null". `F-REC-05` line 118 says derived types are "逐类型独立，缺失类型保留 partial". The two rules cannot both hold for the same group output shape (line 136 has a single `values` per group, no partial-value channel). Additionally `F-REC-05 = F-REC-04 * sum(derivedRatios)` multiplies derived bytes by the original's `REC_RETENTION_DAYS` and `REC_ORIGINAL_VERSION_FACTOR`; whether preview/transcript/summary/export objects share the original's immutable-history factor and retention window is an unstated policy assumption that can overcount or undercount.
- **Impact**: undefined output contract for a common real state (some derived types not produced); silent storage policy coupling.
- **Bounded alternative**: declare derived types individually optional — per-type outputs with their own `status/missing`, group `COMPLETE` only when every present type is computed and a `partial:true` flag marks absent types; OR treat the derived set as all-or-nothing unknown. Separately state explicitly that derived-type ratios are defined as "bytes per original byte over the same retention window and version factor" (making the coupling intentional and reviewable), or add separate derived version/retention inputs with the same missing-is-unknown rules.

### F-07 (low) — `F-CAP-01` accepts caller-supplied `evidenceRef` as capability evidence without provenance

- **Evidence**: line 91/124 accept `{status: VERIFIED, evidenceRef, verifiedAt}` and count it as "能力有证据". Unlike capacity inputs, capability entries carry no `provenance`/`approvedBy` meta binding; any caller string satisfies the check. The plan correctly keeps `productionReady`/`procurementReady` false and states evidence ≠ procurement approval, which bounds the damage, but the output wording "capability evidence" can still read as cloud verification performed by the calculator.
- **Bounded alternative**: rename the group output to `claimedCapabilityEvidence`, require `evidenceRef` to be a non-empty URI-or-record-ID pattern plus `verifiedAt` ISO date, and add a standing limitation string: "calculation never verifies evidenceRef against any cloud/API; VERIFIED is caller assertion only; CV-1..5 closure remains Infrastructure/Security with live evidence." Keep fixture `s2-03` as-is plus one case asserting the limitation flag is present when any `VERIFIED` exists.

### F-08 (low) — `s1-07` NaN/±Infinity fixtures are not representable in strict JSON

- **Evidence**: line 203 requires fixtures asserting NaN/±Infinity rejection, but fixtures are `.json` (line 40–42) and strict JSON has no NaN/Infinity literal. The plan never specifies an encoding (string sentinels `"NaN"`/`"Infinity"`, or non-JSON JS fixture modules).
- **Bounded alternative**: specify the encoding — e.g., string sentinel values that the calculator must reject with `INVALID_NUMBER`, and/or allow `fixtures/s1-07.mjs` exporting raw JS objects with real `NaN`/`Infinity` loaded only by `validate.mjs`. State it in §6.1/§6.3 so the implementation does not silently weaken the negative test.

### F-09 (low) — `F-IVR-01` failure wording conflicts with the explicit-zero rule

- **Evidence**: line 99 marks the group `INCOMPLETE` on "任一缺/0 分母", but `F-IVR-01` has no denominator, and §4.3 line 132 allows explicit `0` for counts/new traffic when provenance and units are complete (zero inbound rate is a legitimate measured quiet window). The copied "0 分母" phrase is ambiguous about whether `IVR_IN_RATE_PS = 0` (with provenance) is `INCOMPLETE` or a valid zero producing zero channels.
- **Bounded alternative**: reword to "缺 → INCOMPLETE；分母类输入为 0 → `DIVISION_BY_ZERO`；显式 0 的率输入（带来源与单位）→ 合法零值输出 0 channels". Only `F-IVR-05`'s `usable` and any true denominators keep the division-by-zero code.

## 8. Conclusion

**Fail.**

The plan is goal-faithful, structurally minimal, and largely dimensionally careful; the confirmed-sound list in §4 is substantial. However, two blockers prevent code-generation-ready acceptance:

1. **F-01** — S1's own exit criterion (`groups=9` template pass) is unsatisfiable under the S1/S2 group split, leaving the implementing agent no consistent target.
2. **F-02** — spool catch-up input semantics contradict the drain formula, risking double-subtraction of continuing production or a mislabeled spare/total contract in the outage-recovery centerpiece of the spec.

Five medium findings (F-03 headroom/N-1 inconsistency, F-04 backup truthiness/zero-RPO, F-05 missing upload-bandwidth contract, F-06 derived-partial vs unknown-propagation conflict) and four low findings (F-07..F-09) require bounded wording/formula fixes but do not change the slice count, artifact layout, or non-goals.

Recommended path: a single bounded plan fix addressing F-01 through F-09 (all are local formula/expectation/wording changes; no new slices, no contract changes, no invented numbers), then re-review. No implementation, staging, commit, push, or next gate is authorized by this report.
