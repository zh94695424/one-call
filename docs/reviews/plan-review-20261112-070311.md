## 4. Open questions

1. **List-wide versus page-local OPEN-risk denial.** Plan §5.1 (line 119) pins whole-request 403 when *any* owned subject that has evidence, including off-page subjects, has any OPEN risk. Control:21 says OPEN risk over the evidence subject uses the existing FORBIDDEN boundary but does not explicitly choose whole-list denial. Triggering scenario: a tenant with many owned subjects and one OPEN-risk subject behind page 2; a request for page 1 containing no risky subject still returns 403, denying all evidence access until cleared and revealing (to the owner) that an off-page risk exists. This is not a cross-tenant leak and avoids a partial page, but it is a product/security policy not explicitly confirmed. Confirm all-set semantics before implementation; if page-local exclusion is preferred, the plan must also define the partial-response/paging-oracle behavior. The plan already labels this a review point, so it is not counted as a finding, but it is a blocking product confirmation for the stated success signal.
2. **Whole-JSONB column grant.** Plan §7.1 (line 244) grants `SELECT` on all of `evidence_record.identity_at_capture`, so the raw customer DB role can read `subjectId`, `sourceChannel`, and any `bindingId` beyond the API's extracted `capturedAt`. The plan explicitly labels this a trusted-application boundary and says stricter raw-role confinement requires a view/function and new goal confirmation. Security/Database must accept that residual before implementation; the API owner SQL must never select or log the full JSON. Do not claim JSON-path/RLS enforcement.
3. **`artifactRoles` always present versus optional.** Control:23 calls `artifactRoles` optional; plan §3 (line 54) makes it always present, including `[]`. This is within the closed schema and deterministic, but it is a stronger client-visible commitment than "optional". Confirm it is the intended projection and keep the exact eight-key summary test if so.
4. **Validated duration on a DERIVED artifact that shares the source media.** Plan §5.2 (line 128) correlates duration by `recording.id = source_ref_id AND recording.media_object_id = artifact.media_object_id AND recording.status = 'VALIDATED'` without a role predicate. V008's unique constraint is `(evidence_id, artifact_role, media_object_id)`, so a legal ORIGINAL and DERIVED row can point at the same media. In that case the DERIVED artifact would also receive `validatedDurationSeconds`, while plan §5.2/§9.6 says derived duration is omitted and a test pins that. Either add `artifact_role = 'ORIGINAL'` to the duration association or explicitly define and test the duplicate-media behavior; do not leave the role ambiguity.
5. **Base/HEAD and Git limitation.** The plan says the checkout's Git pointer is unusable and uses `ef9d0823` as the diff base. In this review workspace, `git status` works and HEAD is the Control goal-confirmation commit `73813534`. Confirm the implementation base (`73813534` or `ef9d0823`) and exclude the Controller's Control commit from any "no unlisted changes" check; otherwise the §11.2 diff will report a Controller-owned path. Also confirm whether the implementation host really has the broken pointer or can use normal Git.
6. **V017 checksum/PA25 seal.** The plan correctly refuses to invent the final Flyway checksum. Confirm the implementation derives it from the final file and seals the same literal in V017/PA25/tests/report, with no wildcard, placeholder, or self-oracle.
