### 02-未修复-高-Exact DDL order and grant ownership are not executable as written

- **位置**: plan §4.1 lines 100-121 (steps 9-17), §6.2 line 431; docs/14 §11.4 lines 4226-4229; accepted V004 pattern lines 26-37 and 408-495.
- **问题类型**: 不可直接实施 / 架构边界 / 权限与所有权.

- **反例/失败场景**: (a) `entitlement_metering_owner` is not the owner of schema `platform` or function `platform.outbox_append`; executing step 15 as that role raises `42501` ("must be owner of schema platform"/"permission denied for function"). (b) `catalog_order_owner` owns no new V006 table and not the `entitlement_metering` schema; step 17's `GRANT USAGE ON SCHEMA entitlement_metering TO catalog_order_role` and the required column `SELECT` grants on `entitlement_issuance`/`entitlement_grant` to `catalog_order_role`, and on `entitlement_balance`/`entitlement_grant` to `ivr_role`, must be issued by `entitlement_metering_owner`; issuing them as `catalog_order_owner` raises `42501`. - **为什么有问题**: PostgreSQL grantors must own the object or have grant option; the plan's own "owner-issued DDL under `SET LOCAL ROLE <owner>`" claim is false for these steps. The plan is required to be code-generation-ready and to derive exact grants from docs/14 §10.12/§11.4; the accepted V004/V005 migrations demonstrate the required role blocks. The missing function creation step is also a direct inconsistency inside the "exact order".
- **直接证据**: Plan lines 110-112 (7 trigger functions/7 triggers/revoke eight functions), 116 (F-02 grant under `entitlement_metering_owner`), 118 (cross-module grants by `catalog_order_owner`), 431 ("Implement §4.1 ... in one migration"); V004:26-37 (platform grants by `platform_reliability_owner`), V004:475-481 (subject_number grants by `subject_number_owner`), V004:490-495 (entitlement_metering schema grants by `entitlement_metering_owner`); docs/14:4226-4229 (create `issue_first_trial` after four tables, F-02 grants, V006 cross-module grants).
- **影响**: The V006 migration cannot apply cleanly under the stated role order; S1's 41-method checkpoint fails at Flyway execution. An implementation agent forced to improvise ownership/order may create a grant path that is not the frozen one, or may use the migration identity/superuser to bypass role boundaries, invalidating the exact ACL evidence.
- **建议改法和验证点**: Add an explicit `CREATE FUNCTION entitlement_metering.issue_first_trial(...)` step immediately after `entitlement_balance` exists and before the trigger/grant blocks. Add a `SET LOCAL ROLE platform_reliability_owner ... RESET ROLE` block for the F-02 owner grants. Keep `entitlement_metering_owner` active (or re-enter it) for all grants on the seven new tables and the `entitlement_metering` schema to `ivr_role`/`catalog_order_role`; keep `subject_number_owner` for `subject_number` USAGE and column grants; remove `catalog_order_owner` from step 17 unless it has a concrete new grant. Verify by applying V001-V006 to clean PostgreSQL 16 with a non-superuser Flyway identity, then asserting exact `proacl`/`nspacl`/column ACLs.

### 04-未修复-高-S2 concurrency cleanup `TRUNCATE` of the seven tables is invalid under the late FK

- **Status**: accepted-candidate
- **位置**: plan §6.3 item 4 line 487, §7.3 line 574; docs/14 §5.4 line 2582; V006 late FK target `ivr.ivr_decision.reservation_id`.
- **问题类型**: 并发恢复风险 / 测试缺口 / 数据隔离.
- **当前写法**: The concurrency method's `finally` cleanup reconnects as the migration identity and runs "one `TRUNCATE` of the seven `entitlement_metering` tables", then deletes method-local V005/V004/V003/V002 parents in FK-safe order.
- **反例/失败场景**: `entitlement_metering.usage_reservation` is referenced by the new FK `ivr.ivr_decision.reservation_id → usage_reservation(id)` (docs/14:2582). PostgreSQL refuses `TRUNCATE` on a table that has a foreign-key reference from a table not included in the same `TRUNCATE` command, even when the referencing table is empty, unless `CASCADE` is specified. The single `TRUNCATE` of the seven entitlement tables does not include `ivr.ivr_decision`, so it raises `0A000`/`cannot truncate a table referenced in a foreign key constraint`. Using `TRUNCATE ... CASCADE` instead would also truncate `ivr.ivr_decision` (and potentially further dependent rows), causing cross-module data loss or interference with other methods' committed fixtures in the shared container.
- **为什么有问题**: The S2 completion signal requires the full 45-method suite green and zero method-local rows; the stated cleanup cannot execute. The plan's invariants ("no append-only row survives cleanup") are unattainable as written. A naive CASCADE workaround weakens test isolation and can delete V005/V004 facts outside the method.
- **直接证据**: Plan line 487 ("one `TRUNCATE` of the seven `entitlement_metering` tables") and line 574; docs/14:2582 (late FK decision); V006 §4.5 row 16 (late `fk_ivr_decision_reservation`).
- **影响**: S2 suite fails in cleanup; or the implementer uses CASCADE and creates cross-module truncation risk; test isolation and evidence determinism are compromised.
- **建议改法和验证点**: Replace the single `TRUNCATE` with an explicit FK-safe `DELETE` order: delete method-local `ivr.ivr_decision` rows (and any other external referencing rows), then `usage_fact`, `usage_reservation`, `entitlement_balance`, `entitlement_issuance`, `trial_grant`, `entitlement_grant`, `trial_policy_version`, then V005/V004/V003/V002 parents; or use `TRUNCATE ... CASCADE` only if the plan explicitly includes and restores every cross-module table and proves method-local isolation. Assert zero rows for every table touched. Keep the separate runtime `TRUNCATE` denial probe.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 高.
