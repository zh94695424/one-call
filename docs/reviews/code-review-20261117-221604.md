### 01-未修复-低-PA37 ships a service-local 5-second budget that is neither injectable nor checked before or between the work it is meant to bound
- **入口/函数**: `DefaultOperationsCatalogProductReadService.execute(Caller, Supplier)` -> `list` / `detail`, reached from `GET /api/v1/operations/catalog/products[/{productId}]` via `OperationsCatalogProductReadController`.
- **文件(行号)**: `backend/src/main/java/com/onecall/core/operations_iam/internal/catalogread/DefaultOperationsCatalogProductReadService.java:100`-`:113` (deadline `:101`, the only two checks `:108` and `:112`); frozen sibling `backend/src/main/java/com/onecall/core/operations_iam/internal/ivrread/DefaultOperationsIvrSessionReadService.java:42`, `:46`, `:128`-`:148`, `:171`; shared plumbing `backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/OperationsSubjectReadPersistenceConfiguration.java:107`-`:110`.
- **输入场景**: a healthy-but-loaded deployment - `limit=100` with several versions per root, or a request that arrives while the small Operations read pool is saturated - so that connection acquisition plus `enter()` (1 identity query + 4 `SET LOCAL` + 1 assert), the authority query, two `Role.ORDER` handoffs (4 `SET LOCAL ROLE` + 4 identity asserts), the root read, the phase-two summary read and the cursor encode together exceed five seconds. Every individual statement stays under the frozen `SET LOCAL statement_timeout = '2000ms'`, so nothing fails earlier.
- **实际分支**: the budget is sampled only at `:108`, i.e. after `action.get()` has already executed every SQL statement and produced the page, and again at `:112` after `transaction.execute` has returned (commit already done). `require(deadline - System.nanoTime() > 0)` then throws `Failure(Code.SERVICE_UNAVAILABLE)`. There is no check before `context.enter()` (`:105`), none after `authority(caller)` (`:106`), none between the two catalog phases and none around `codec.encode`.
- **预期行为**: follow the accepted shipped contract for this exact slot: the sibling builds `deadline` from an injected `LongSupplier nanoTime` (`DefaultOperationsIvrSessionReadService.java:42`, `:46`, `:129`) and calls `checkBudget` before `enter()`, after `enter()`, after `authority()`, and at every I/O boundary inside the action (`:53`, `:57`, `:59`, `:81`, `:83`, `:108`, `:110`, `:133`-`:141`, `:171`), so an exhausted budget short-circuits *before* further database work and the path is deterministically testable.
- **实际行为**: the new bound can only discard completed work. A request that consumed the full pool wait, both role handoffs and both catalog queries, and whose transaction committed successfully, is answered 503; and because `System.nanoTime()` is hard-coded, no PA37 test can drive the branch. `rg -n "nanoTime" backend/src/main/java` returns only these three PA37 lines - the sole time-budget implementation in the whole production tree that is not clock-injected.
- **直接证据**: `DefaultOperationsCatalogProductReadService.java:101` `long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(5);` versus `DefaultOperationsIvrSessionReadService.java:129` `long deadline = nanoTime.getAsLong() + ...` plus `:171` `private void checkBudget(long deadline) { if (deadline - nanoTime.getAsLong() <= 0) throw unavailable(); }`. The production template already carries `template.setTimeout(5)` (`OperationsSubjectReadPersistenceConfiguration.java:110`), so the service budget equals the frozen transaction bound instead of being tighter than it, and `OperationsReadContext.java:38`-`:40` already bounds each statement (2 s), lock wait (250 ms) and idle-in-transaction (5 s). None of the 18 frozen `OperationsCatalogProductReadServiceTests` identities (`docs/gateflow/pa37-operations-catalog-product-read-foundation-plan.md:253`) names or exercises a budget/timeout path, and the report does not claim one - `docs/gateflow/pa37-operations-catalog-product-read-foundation-implementation.md` section 5 asserts only that "Existing context guards enforce ... timeouts", which is true of the reused guards, not of `:101`.
- **影响**: (a) an PA37-only aggregate bound fails to protect the database and the pool and instead converts a committed read into a client-visible 503 that is indistinguishable from a dependency outage, so on-call pages for a catalog dependency that actually succeeded; (b) because the value is duplicated against the template's own 5 s, the guard is simultaneously ineffective and load-bearing in the worst way - it fires only in the window after the last statement; (c) the branch has zero regression coverage, so a future edit to `:101` cannot redden any test.

Verification points: all 18 service identities keep their exact names (they are pinned in `pa37_unit_additions` and `ci.yml:1832`+), so coverage must be added *inside* an existing method (e.g. `usesOneRepeatableReadTransaction` or `restoresRoleOnFailure`) with the injected clock, never as a new `@Test`; `OperationsCatalogProductReadConfigurationTests.doesNotConstructNewResources` still expects exactly one declared configuration method, and the `848`/`592`/`1441` CI literals must not move.
