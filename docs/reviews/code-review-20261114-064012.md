## Findings

### F-1 (Medium, composed) — Clock-domain split between customer and Operations writes to `service_activation` yields fail-closed 503 under positive or negative host/container skew

**Class:** composition-only defect (invisible in single-path reviews). Integrity is fail-closed (rollback); availability under skew is the impact. Same defect class previously observed and fixed in PA4 (~73 ms host/container skew broke `ck_customer_order_time_order`).

**Evidence anchors:**

| Path | Clock source | Code |
| --- | --- | --- |
| Customer PA31 head create/advance | JVM `Instant.now()` | `DefaultCustomerSubjectActivationService.java:109` (`Instant occurredAt = Instant.now()`); `JooqSubjectActivationRepository.java:66,71` write that Instant into `created_at`/`updated_at` as `?::timestamptz` |
| Operations PA32 decision time | DB `clock_timestamp()` | `JooqOperationsLifecycleRepository.java:44–47` (`SELECT clock_timestamp() AS decision_time`) |
| Operations PA32 head advance | DB decision time | `JooqOperationsLifecycleRepository.java:51–52` (`SET … updated_at=?::timestamptz` with the DB-sourced Instant) |
| Fail-closed monotonicity guard | compares DB time to stored head | `DefaultOperationsSubjectLifecycleService.java:67–68` — `if (time == null \|\| time.isBefore(head.updatedAt())) throw new Failure(Code.SERVICE_UNAVAILABLE)` |
| Schema time-order constraint | `updated_at >= created_at` | `V007__activation_and_consent.sql:94–95` `CONSTRAINT ck_service_activation_time_order CHECK (updated_at >= created_at)` |
| Prior same-class incident | PA4 order path | `docs/gateflow/pa4-v004-catalog-order-payment-foundation-pr-fix-1.md:39,63` — container clock lagged Windows JVM by ~73 ms; fixed by anchoring to DB `now()` |

**Failure modes (composed only):**

1. **JVM ahead of DB (positive skew).** Customer creates/advances head with `T_jvm`. Operations takes `decisionTime = clock_timestamp() = T_db < T_jvm = head.updatedAt`. Guard at `DefaultOperationsSubjectLifecycleService.java:68` throws sanitized `SERVICE_UNAVAILABLE` / **503** before transition. Even if the guard were bypassed, `advance` writing `updated_at = T_db` while `created_at = T_jvm` would violate `ck_service_activation_time_order` → 23514 → 503.
2. **JVM behind DB after an Operations write (negative skew).** Operations suspends with DB time `T_db1` on `updated_at`. A subsequent customer ACCEPT/DECLINE path that still uses `Instant.now() = T_jvm < T_db1` writes `updated_at` backwards → `ck_service_activation_time_order` 23514 → 503 (customer path). Conversely, a customer advance that jumps `updated_at` forward in JVM time can make a later Operations `decisionTime.isBefore(head.updatedAt)` true → 503.
3. **Witness interaction.** Operations witness requires `head.updatedAt.equals(transition.occurredAt)` after advance (`OperationsLifecycleSemantics`). Both sides of that equality on the Operations path use the same DB decision time, so the witness is internally consistent; the cross-path hazard is the guard and the CHECK against customer-written timestamps, not the Operations-internal witness.

**Why composition-only:** single-path reviews correctly proved each path’s internal ordering (Operations: DB clock vs DB-written head; customer: JVM clock vs JVM-written head). The defect appears only when both writers share `activation_consent.service_activation` and a frozen CHECK/guard compares timestamps produced by different clocks — exactly the PA32 customer↔Operations lifecycle join.

**Impact:** sanitized 503 (availability), transaction rollback, no partial transition/audit/Outbox. Not a data-integrity or authz bypass. Likelihood depends on host/container clock discipline; this repository has already observed ~73 ms skew in CI/container runs (PA4). Control :86 lists “clock discipline” as a residual owner but does not record the concrete cross-path failure modes or file:line anchors; plan §12 residual owners do not mention clocks at all.

**Suggested Controller adjudication (not implemented here):** require either (a) both writers anchor to DB `clock_timestamp()`/`now()` (PA4 pattern), or (b) an explicit residual-owner acceptance that documents both skew directions, the 503/CHECK outcomes, and an operational clock-sync precondition — with a named owner and destination artifact. Either closes F-1; silence does not.
