## New findings

### F-1-未修复-中高-V013 “migration state is not V012” precondition contradicts the role-present replay branch

- **位置**: Fixed decisions §8 (“Before action, fail if … migration state is not V012 … role present means verify … This makes replay safe”), V013 exact matrix line 31, and the planned replay proof in the new role IT.
- **问题类型**: 状态机漏洞 / 不可直接实施 / 测试缺口.
- **当前写法**: V013 must fail if the database “migration state is not V012”, while also promising “replay safe” via the role-present branch.
- **反例/失败场景**: The established replay pattern (`SharingAdmissionRoleLeastPrivilegeIT.v012CreatesExactAdmissionRoleAndIsReplaySafe`, lines 32–53) re-executes the migration SQL on the fully migrated fixture. After Flyway records V013, `flyway_schema_history`'s latest version is 013, not 012. A literal predicate `max(version) = '012'` fails before the role-present branch runs, so manual replay of V013 is impossible; the new role IT's replay method fails and the “replay safe” claim is false.
- **为什么有问题**: The plan does not define whether “migration state” means “V012 is the latest recorded version” or “V012 has been applied”. The two readings produce opposite results for exactly the replay scenario the Control and the new IT require. A code-generation agent can choose the wrong reading and produce a migration whose own replay test fails.
- **直接证据**: Plan §8 line 31; V012’s replay test pattern at `SharingAdmissionRoleLeastPrivilegeIT.java:32–53`; Flyway records the applied version after each successful migration; Control lines 41 and 48 require replay-safe V013 preconditions.
- **影响**: Implementation agent produces a V013 that fails its replay/compatibility test, or invents an unstated predicate; plan cannot be validated as code-generation-ready.
- **建议改法和验证点**: Define the exact predicate, e.g. require that V012 is present/successful (`EXISTS … version='012' AND success`) and that no incompatible V013-era state exists, or drop the version check and rely on Flyway ordering; state explicitly that manual replay is performed on a V012-state DB and that role-present replay must reach the compatibility checks. Add a role-IT replay method that re-executes the V013 SQL twice and asserts success, then `flyway.migrate()` executes zero.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中高.

### F-2-未修复-中-V013 “no dependencies” precondition fails on the role’s own ACL dependencies during replay

- **位置**: Fixed decisions §8 (“no memberships/dependencies/role settings”), V013 matrix “Role identity … owned object/dependency”, and the planned replay proof.
- **问题类型**: 状态机漏洞 / 不可直接实施 / 测试缺口.
- **当前写法**: A present role must have “no memberships/dependencies/role settings” and “unexpected direct grant” must fail. The plan does not distinguish ACL dependencies from ownership/policy dependencies.
- **反例/失败场景**: On PG 16.15, a role with one schema `USAGE` and 15 column `SELECT` grants has exactly 16 `pg_shdepend` rows with `deptype='a'` (1 `pg_namespace`, 15 `pg_class`) and no rows of other deptypes. A literal `EXISTS (SELECT 1 FROM pg_shdepend WHERE refobjid = role)` check fails on replay even when every grant is the expected allowlisted grant, before the expected-grant comparison can run.
- **为什么有问题**: V012’s postcondition explicitly ignores `deptype <> 'a'`; the fixed plan omits that qualifier while claiming replay safety and “do not silently alter” a compatible role. This is the same replay method the plan requires.
- **直接证据**: Empirical PG 16.15 result (16 `deptype='a'` rows after the planned grants); V012 postcondition (`SharingAdmissionRoleLeastPrivilegeIT`/V012 SQL) uses `deptype <> 'a'`; plan §8/line 31 and line 58.
- **影响**: V013 replay test fails or the implementation must guess a predicate; plan not fully code-generation-ready.
- **建议改法和验证点**: State the exact predicate: fail only on `pg_auth_members`, `pg_db_role_setting`, ownership/policy `pg_shdepend` rows (`deptype <> 'a'`), and grants outside the allowlist; permit the plan’s own `deptype='a'` ACL rows. Add the replay assertion to the role IT.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-3-未修复-中-V013 null-password verification names `pg_roles` but only `pg_authid` can observe it

- **位置**: V013 matrix “Role identity … `rolpassword IS NULL`”, line 58 catalog list (“must query `pg_roles`, …”), and §8 “null password”.
- **问题类型**: 契约缺失 / 不可直接实施.
- **当前写法**: Required state is `rolpassword IS NULL`, and the precondition/postcondition catalog list enumerates `pg_roles` but not `pg_authid`.
- **反例/失败场景**: On PG 16.15, `pg_roles.rolpassword` is always the masked literal `********`, even for a role created with `PASSWORD NULL`; `pg_authid.rolpassword IS NULL` is the only observable nullness. An implementation that follows the enumerated `pg_roles` list sees a non-null masked value and either fails every compatible role or skips the required check.
- **为什么有问题**: The plan’s “exact” role-attribute matrix cannot be verified as written with the listed catalogs; V012 and the existing admission IT already use `pg_authid` for this exact check, so the omission is actionable.
- **直接证据**: Empirical `SELECT rolpassword FROM pg_roles` → `********`; `SELECT rolpassword IS NULL FROM pg_authid` → `true`; V012 precondition and `SharingAdmissionRoleLeastPrivilegeIT.java:296` use `pg_authid`.
- **影响**: V013 precondition/postcondition either fails on the compatible role or silently omits the password-null proof; role IT cannot assert the matrix exactly.
- **建议改法和验证点**: Add `pg_authid` to the required precondition/postcondition catalog list, state that it is read as the migration superuser (and that postconditions run after `RESET ROLE`), and keep `pg_roles` for the visible attributes and `rolvaliduntil`/`rolconfig`.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-4-未修复-低-Migration byte-identity command glob silently omits V010–V012

- **位置**: “Commands and required assertions” item 1.
- **问题类型**: 测试缺口 / 不可直接实施.
- **当前写法**: `sha256sum src/main/resources/db/migration/V00*.sql` is named as the V001–V012 individually hash command.
- **反例/失败场景**: `V00*.sql` matches V001–V009 only; V010–V012 do not match `V00*`. The command emits 9 digests, not 12, so a literal run under-verifies the three newest frozen migrations. The plan does list all twelve expected digests and command 7 requires twelve before/after values, which mitigates but does not correct the command.
- **为什么有问题**: The migration byte-identity invariant is a plan-level safety condition; a wrong command can let a V010–V012 edit pass the named check.
- **直接证据**: `ls src/main/resources/db/migration` (V001…V009 for `V00*`; V010–V012 require `V01*`); plan command 1.
- **影响**: Under-verification of frozen migrations; possible false completion report.
- **建议改法和验证点**: Use `V0*.sql` or `V00*.sql V01*.sql`, and assert the command returns exactly 12 rows/digests before comparing to the pinned list.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

The defensive Java check is harmless, but the planned “duplicate ORIGINAL/ambiguous joins” test must be a mocked/mapping test or documented as defensive-only; a DB fixture cannot create that state. Owner: implementation/test design; destination: reader unit test or stop-condition note.

The plan implies but does not say “nested”; owner: implementation; destination: reader API file.

Owner: implementation; destination: configuration unit tests.
- **Existing residuals remain correctly owned**: recording hash/subject integrity (Evidence service/integrity), externally provisioned role password (deployment/DB ops), PG16/Docker availability (implementation/CI runner), `Missing`/`Unavailable` playback mapping (PA19), V008 linkage semantics (Evidence implementation stop condition).

## Conclusion

**fail**

`PR-01` through `PR-06` are genuinely closed, and no goal drift or over-design was found: the allowlist, POM/Failsafe execution, outer-join `Missing`/`Unavailable` contract, opaque media UUID/safe-metadata boundary, 22-path count and source=CI=XML arithmetic all check out against the frozen tree. The blocking issue is the V013 replay/precondition contract, which the re-review is specifically required to test for precision and internal consistency: the stated “migration state is not V012” check defeats the role-present replay branch (F-1), the “no dependencies” check conflicts with the role’s own ACL dependencies created by its grants (F-2), and the `rolpassword IS NULL` check is unobservable through the enumerated `pg_roles` catalog (F-3). These are small, bounded plan fixes, but until they are pinned the plan is not unambiguously code-generation-ready for V013 and its required replay test.
