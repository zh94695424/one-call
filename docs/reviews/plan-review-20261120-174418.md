## 5. Open Questions

1. **Bigint vs strict ECMAScript number formatting.** docs14 §2.5 says "ECMAScript-compatible shortest round-trip number formatting"; plan §5.1 deliberately serializes `priceCents`/`quantity` as exact integers up to `Long.MAX_VALUE` without IEEE-754 coercion. This only diverges from strict RFC 8785 for values > 2^53, is documented and pinned by tests, and has no in-scope consumer that re-hashes `catalog_version.snapshot_sha256` with a strict JCS library. Confirm the Controller accepts the exact-integer rule as the catalog-draft canonicalization (it is arguably more correct for `bigint` columns than a lossy double).
2. **Monotonic `versionNo`.** docs14 `:1100` describes "Positive monotonic version within the product", but the only enforced rules are `version_no >= 1` + `uq_catalog_version_no`. Plan §2/§11 declines any MAX-scan/monotonic admission. Same open question as prior Review A; the plan documents its interpretation and no frozen contract mandates monotonic enforcement.
3. **Derived-vector hash recomputation coverage.** The empty-P canonical hash was recomputed exactly, and all other lengths are arithmetically consistent, but the environment's command allowlist (only `sha256sum`/`grep`/`wc`/`tr` on on-disk files were permitted; `python3`/`printf`/`sed`/`awk`/heredocs were gated) prevented independent byte-level hashing of the P2 and response vectors. This is a tooling limitation of this review, not plan evidence; the underlying golden vectors are deterministic from the verified P bytes and fixed ordering.
