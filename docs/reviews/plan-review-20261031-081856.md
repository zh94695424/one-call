## 3. RR-01 / RR-02 verification

### 3.1 RR-01 — extension eligibility (resolved)

Plan §4.1 (line 234) states exactly:

> Increasing expiry requires `OLD.status = 'ACTIVE'` and `clock_timestamp() < OLD.expires_at` (`SHARE_GRANT_EXTENSION_INVALID`); the resulting `NEW.status` need not be ACTIVE. This predicate applies only when `NEW.expires_at > OLD.expires_at`.

Plan §7.4 (line 368) requires all four witness classes:

1. lock-only `ACTIVE → LOCKED`, expiry unchanged, revision +1, generations/count unchanged, success; extension predicate not invoked;
2. pure extension `ACTIVE → ACTIVE`, strict future expiry increase, revision +1, generations/count unchanged, success;
3. mixed `ACTIVE → LOCKED` plus strict future expiry increase, success structurally but service-forbidden, with the exact mixed SQL in line 369;
4. for each `OLD.status` in `LOCKED`, `EXPIRED`, `REVOKED`, a same-state strict expiry increase is refused `P0001/SHARE_GRANT_EXTENSION_INVALID`, with old expiry safely future to isolate the status predicate from the clock predicate.

The witnesses use `sharing_role`, the frozen guard enabled, lock/read baseline, SAVEPOINT, exactly-one-row/only-specified-delta assertions, `ROLLBACK TO SAVEPOINT`, full-row/history restoration, transaction `ROLLBACK`, and fresh-connection equality. This binds eligibility to `OLD.status`/`OLD.expires_at`, independent of `NEW.status`, and matches design §4.44/§7.4 ("extension … on an ACTIVE, not-yet-expired grant"). **Resolved.**

### 3.2 RR-02 — generation rules (resolved)

Plan §4.1 (line 234) states exactly:

> Generation decreases are always structurally forbidden. Exact revocation_generation +1 for named status-changing revoke/expiry edges applies only when `OLD.status IS DISTINCT FROM NEW.status`; ACTIVE → LOCKED remains generation-neutral. Same-state generation increases are not subject to an exclusive named-status-edge allow-list; exact code-rotation coupling and generation increments still apply whenever code values/code_generation change, including same-state rotation.

Plan §7.4 (line 366) requires generation-decrease negatives with `P0001/SHARE_GRANT_GENERATION_INVALID` on otherwise valid nonnegative results, edge-exact revoke/expiry deltas only when status changes, ACTIVE→LOCKED generation neutrality, exact code-rotation coupling, and the same-state terminal successes of line 367. Line 367 requires committed valid `EXPIRED` and `REVOKED` fixtures and a rollback-isolated `revocation_generation = old + 1`, `revision = old + 1`, same-status update that must succeed structurally (no SQLSTATE), classified service-forbidden, with full baseline restoration and no committed mutation. Line 238 states the same structural-vs-service classification and forbids adding a terminal-row DDL prohibition. Fix-2 §4 confirms named admission/lock/extension actions keep service-level unchanged-generation obligations while the guard must not ban same-state increases. **Resolved.**

No new contradiction or regression was introduced by the fix-2 edits to §4.1/§7.4.

## 5. Material findings

### PA9-RR3-01-未修复-低-early-expiry-refusal-has-no-planned-witness

- **位置**: Plan §4.1 line 234 (`SHARE_GRANT_EXPIRY_INVALID`) versus §7.1 line 321 and §7.4 lines 366–369 (S2 lifecycle witnesses).
- **问题类型**: 测试缺口 / 状态机漏洞 (validation gap).
- **当前写法**: §4.1 declares "Persisting expiry before old expiry is refused (`SHARE_GRANT_EXPIRY_INVALID`)" and the matrix row ACTIVE/LOCKED→EXPIRED requires `clock_timestamp() >= old expires_at`. §7.4 enumerates revision negatives (`old/old−1/old+2`), the six legal directed status changes, terminal outgoing edges, extension witnesses (1)–(4), and the mixed-action probe, but never requires an ACTIVE→EXPIRED or LOCKED→EXPIRED update attempted before `OLD.expires_at`, and never asserts the `SHARE_GRANT_EXPIRY_INVALID` label.
- **反例/失败场景**: An implementation that omits the early-expiry time check, uses transaction-stable `now()` instead of `clock_timestamp()`, or raises a different label passes every planned S2 witness, because none exercises an ACTIVE grant whose `expires_at` is still in the future while setting `status = 'EXPIRED'`. A service could then persist EXPIRED early and prematurely invalidate an ACTIVE grant, or a clock/label mismatch could ship unverified.
- **为什么有问题**: The plan's own S2 stop condition includes "missing legal/negative edge"; a named structural refusal should have a bounded witness. The method-title word "expiry" is not a binding oracle; the detailed §7.4 witness list is what the implementer will follow, and it omits this case.
- **直接证据**: Plan lines 229, 234, 321, 366–369; design §7.4 ("ACTIVE → EXPIRED at/after `expires_at`") and §10.22 guard row.
- **影响**: A guard rule can be implemented incorrectly or not at all while S2 stays green; the structural backstop for premature expiry is unproven.
- **建议改法和验证点**: Add to `v009GrantLifecycleRevisionMatrixAndImmutabilityBackstops`, under `sharing_role` with the guard enabled and rollback isolation, bounded probes: (a) ACTIVE grant with `valid_from` earlier and `expires_at` safely in the future, UPDATE `status = 'EXPIRED'`, `revocation_generation + 1`, `revision + 1`, expect `P0001/SHARE_GRANT_EXPIRY_INVALID`, zero mutation; (b) the same for LOCKED→EXPIRED; then `ROLLBACK TO SAVEPOINT` and fresh-connection baseline equality. Alternatively, explicitly classify early expiry as a service-only rule and remove the structural label from §4.1 so the guard contract and tests agree.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.
- **Status**: `accepted-candidate`.
