## 3. Material findings

### PA26-PLAN-A-01-未修复-[中]-§8.2/§10 把实际存在的 contract-validator 输入误判为缺失，可能让 A2/A3/A5 被错误归类为 blocked evidence

- **位置**: Plan §8.2 (lines 336-355) and §10 residual table (line 426).
- **问题类型**: 测试缺口 / 验证证据不完整 / 事实误述；非 ACL 设计阻断。
- **当前写法**: “The export contains `backend`, `docs` and `.github`, but not the `api/openapi`, `protocol/ivr`, `security`, `deployment/capacity` or `acceptance` tool/model trees referenced by the contract-regression job.” 随后说明若前置缺失就把 A2/A3/A5 记为 blocked external evidence。
- **反例/失败场景**: 当前实际仓库包含 `api/openapi/`（含 `onecall-v1.openapi.yaml`、`package-lock.json` 等）、`protocol/ivr/validate.mjs`、`security/validate.mjs`、`acceptance/validate.mjs`、`deployment/capacity/`。只有生成的 `tmp/openapi-client/onecall-v1.bundle.json` 不存在（`ls tmp` 返回不存在）。PA26 按 §2.3/§10 必须改 `docs/14` 与 `docs/17`，而 A2/A3/A5 正是解析这两个文档的 CI validator（ci.yml:1503-1554）；如果 implementation agent 相信“tool/model trees 缺失”，就会把 A2/A3/A5 记为 blocked，而不是生成 A1 bundle 后运行，PA26 引入的文档契约回归就会被归类为 baseline/blocked，未被执行证据发现。
- **为什么有问题**: §8.2 的 extractor 先 `assert` 四个前置全部存在（含 A1 bundle），但没有包含 A1 生成步骤；A1 恰是 `tmp/openapi-client/onecall-v1.bundle.json` 的生成者（ci.yml:1497-1502，`npm ci` + `npm run check:s3`）。对当前 repo，可运行的是 A1 + A2/A3/A5，而不是“trees 缺失”。这会让“blocked external evidence”的归类不成立，削弱 docs/14/17 overlay 的唯一自动契约验证。
- **直接证据**: 实际目录清单（`api/openapi`、`protocol/ivr`、`security`、`acceptance`、`deployment/capacity` 全部存在；`tmp/openapi-client/onecall-v1.bundle.json` 不存在）；ci.yml:1497-1554；plan §2.3/§8.2/§10。
- **影响**: 实施 Agent 可能跳过 A2/A3/A5；文档 overlay 或 Q17/Q23 表述漂移未被发现；接受报告会把“未运行”误报为“前置缺失”而不是“可运行但未运行”；后续返工和 review 不可验收。
- **建议改法和验证点**: 更新 §8.2/§10 为实际输入清单；明确 A1 生成（在 `api/openapi` 执行锁定 toolchain 的 `npm ci` 与 `npm run check:s3`，或由 Controller 提供已生成 bundle）是 A2/A3/A5 的前置；对 `docs/14`/`docs/17` 的 overlay 必须运行 A2/A3/A5（A3 当前非 baseline drift），仅当 A1 bundle 确实无法生成时才记录精确 blocked 条目并指定 owner；report 中记录每条 validator 的 exit status 与输入 SHA256。
- **修复风险（低/中/高）**: 低（只影响验证步骤和文档证据，不影响 V014/ACL 设计；可能需要 npm/网络或外部 bundle，需按环境授权）。

### PA26-PLAN-A-02-未修复-[低]-§4.1 #4 对 LC/LW 的“safe external-login attributes”未显式允许已分发密码，存在拒绝真实 PA25-provisioned 数据库的实现歧义

- **位置**: Plan §4.1 #2 vs #4 (lines 131-133), §4.3 (line 152), §8.3 (lines 359-370).
- **问题类型**: 契约缺失 / 可实施性歧义 / 测试缺口；needs-evidence。
- **当前写法**: #2 对 target roles 要求 NOLOGIN、password NULL、no role GUCs、expected INHERIT 等；#4 只写“safe external-login attributes”，未明确 LC/LW 是 LOGIN、可持有非 NULL 密码/password verifier，也未明确该属性集与 target-role 属性集不同。
- **反例/失败场景**: 一个已经按 PA25 runbook 分发 credentials 的数据库，LC/LW 的 `pg_authid.rolpassword` 非 NULL。若 V014 preflight 复用 #2 的“password NULL”检查，V014 会拒绝这个数据库；这正是 §4.3/§8.3 要求 V014 支持的 already-PA25-provisioned upgrade/replay 路径。另一个失败是 test 只在密码为 NULL 时 replay V014，未覆盖 credential-assigned graph，真实升级时才暴露。
- **为什么有问题**: PA25 的角色属性 oracle 明确区分 external login 与 target role：external logins 允许非 NULL 密码（`pa25-runtime-identities.sql:2898-2907` 只在 `NOT expected_login` 时要求 password null），并允许 username/password 的 byte-identical 保留；V014 必须镜像这一点。当前 plan 的 #4 依赖实现者自行推断，可能导致实现把 PA25 的真实 credential 状态当作 unsafe。
- **直接证据**: Plan §4.1 #4、§4.3、§8.3；PA25 `2898-2907`；`ProductionDatabaseIdentityProvisioningIT.setPasswords()` 在 apply 之后设置密码并在其后 replay/check；PA25 runbook line 35 说明 credentials 外部生成。
- **影响**: V014 拒绝合法 PA25-provisioned DB；或 test 只覆盖 password NULL 的合成图，acceptance 未证明 credential-assigned replay；实施者可能为了通过而放宽 provenance/attribute guard。
- **建议改法和验证点**: 在 §4.1 #4 明确列出 LC/LW 的 exact safe attribute set：LOGIN、NOINHERIT、NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION/NOBYPASSRLS、connlimit -1、validuntil NULL、rolconfig NULL、exact PA25 v1 comment、no direct ACL/ownership/GUCs、**password/verifier may be non-NULL and must be preserved**；增加一条 synthetic credential-assigned PA25 graph 的 V014 upgrade + replay 测试，断言 apply/check 成功、密码 verifier 与 comment byte-identical、OID/edge 不变；negative tests 只覆盖 wrong slot/marker/attributes。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

### PA26-PLAN-A-03-未修复-[低]-§6.3 #6 的“evidence effective role 不能 SET ROLE into each other”会与 LW 的 approved evidence/sharing_command 切换相冲突

- **位置**: Plan §6.3 item 6 (line 209), with §3.3 (line 112-120) and §6.2 identity transitions (line 198).
- **问题类型**: 测试缺口 / 状态机边界表述 / needs-evidence。
- **当前写法**: “Customer/evidence effective roles cannot SET ROLE into each other or any unrelated principal.” 同时 §3.3 说明 LW 是 `sharing_command_role` 和 `evidence_role` 两个 role 的 member，§6.2 说明 LW “assumes command then evidence and back on same PID”。
- **反例/失败场景**: PostgreSQL 的 `SET ROLE` 权限检查基于 **session_user** 的 membership，不是 current_user。LW（session_user）同时是 `sharing_command_role` 和 `evidence_role` 的 member，因此在 `current_user = evidence_role` 时，`SET ROLE sharing_command_role` 是**允许的**，且正是 Java 的 approved restoration path。如果新 negative matrix 把 evidence_role -> sharing_command_role 断为 42501，测试会失败；如果为了让测试通过而移除 LW 的 command edge，会破坏实现并被 PA25 拒绝。
- **为什么有问题**: 这是 plan 自身的测试矩阵与 §3.3/§6.2 的 approved topology 之间的表述冲突；实施 Agent 可能写出错误的 negative test，或弱化 assertion（只测 evidence->customer，不测 evidence->command）而掩盖边界。
- **直接证据**: PA25 edge loop `3147-3154`（LW 同时获得 `sharing_command_role` 和 `evidence_role`）；plan §3.3/§6.2；PostgreSQL `SET ROLE` 的 session-user membership 语义。
- **影响**: negative test 失败或边界被弱化；implementation 可能被误导去修改 role graph/Java，超出 allowlist。
- **建议改法和验证点**: 按 session login 重写该矩阵：LC 仅能进入 customer_iam_role；LW 只能进入 sharing_command_role 与 evidence_role（两者之间的 evidence<->command 切换是 positive，不要求 42501）；LC/LW 不能进入 owner/direct/predefined/unrelated；customer_iam_role/evidence_role 不能进入 customer/owner/direct/predefined（除 LW 的 approved 第二个 role）；positive test 证明同一 PID 的 switch/restore，negative 只覆盖真正未 approved 的 target。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

## 4. Open questions

1. **Partial PA25 topology acceptance**: §4.1 #4 接受“只有 LC -> customer_iam_role 和 LW -> evidence_role”的 already-provisioned graph；由于措辞是“may have only”，实现可能接受只有一条 edge 或零条 edge 的 partial graph。PA25 check 会拒绝不完整六-login graph，因此安全上可接受；请确认 V014 是意图接受 partial affected topology，还是要求“两条都有或都没有”，并在 V014 IT 中固定该语义。
2. **PA25-provisioned upgrade coverage mapping**: §4.3 要求“upgrade from V013 both before provisioning and with a synthetic PA25-compatible already-provisioned graph”，但 §7.1 的 12 个 method 名称没有显式命名为该双场景。请确认 `v014UpgradesFrozenPrefixAndMatchesIndependentAclOracle` 同时覆盖 clean upgrade 与 PA25-provisioned upgrade，且 `v014FreshChainHasExactHistoryAndImmutablePredecessors` 只覆盖 fresh；否则 acceptance 可能漏掉 credential-assigned upgrade。
3. **Customer guard positives on latest state**: §6.2 的 owner-vs-runtime proof 主要描述 evidence guard/deferred cycle；capping `PostgresContainerIT` 后，三条 customer IAM guard（`guard_customer_account`/`guard_auth_identity`/`guard_identity_profile`）的 positive/negative 行为只在 V013 historical prefix 执行。请确认 new suite 的 `ownerInvokerGuardsAndSharingWritesRemainOperational` 或 structural snapshot 覆盖这三条 definition/behavior（至少 definition 不变），或将其登记为 residual。
4. **Firewall probe count**: Plan §8.2 说“preserve all 82 adversarial probes”，而 ci.yml 的 firewall 在同一 step 中先 `assert probes == 82`（dependency coordinates），后 `assert probes == 116`（含 34 个 JAR probes）。请确认指令是“run the step unchanged/全部 116 probes”，而不是只保留 82；当前 no-dependency-change 决定下两者一致，但 evidence wording 应精确。
5. **`info().all()` / `pending()` / `validate()` after capping**: §6.4 要求用 Flyway state API 断言 V014 是 above target；请确认 `flyway.info().all()` 的 14-script 断言、`pending()` 为空、target-013 `validate()` 的具体实现（现有 target-11 先例只直接证明 `validate()`，未直接断言 `pending()`）。
6. **Contract validator A1 bundle**: see PA26-PLAN-A-01. 若 implementation 环境无法生成 `tmp/openapi-client/onecall-v1.bundle.json`，请记录精确 blocked 条目（owner: Protocol/Data/Backend）与可复现输入，不要把整个 `protocol/ivr`/`security`/`acceptance`/`api/openapi` 树误报为缺失。

## 6. Final plan review conclusion

**pass-with-risks**

The core contract is source-grounded and arithmetically exact: the 39/42 -> 12/16 derivation, 300 -> 247 total, 219 unchanged tuples, the 15-column evidence projection, the customer 10-column projection, the `LW -> evidence_role` / `identity_at_capture` retention, the no-Java-change decision, V001-V013 hashes, the 64-method historical suite, the 12-method/555/556/15 inventory and the 20-path allowlist all check out against the actual repository. The V014 design is replay-safe on both clean and PA25-provisioned databases in principle, and the historical-prefix cap is technically compatible with Flyway target/above-target behavior.

The plan is not yet entirely ambiguity-free for implementation: the contract-validator input statement is factually wrong for the actual repository and can cause A2/A3/A5 to be classified as blocked rather than run; the external-login preflight does not explicitly allow already-distributed PA25 passwords on LC/LW; and the SET ROLE negative matrix conflicts with LW's approved evidence/sharing_command switch. None of these invalidates the ACL/RBAC design, but they should be closed before the implementation evidence is accepted; PA26-PLAN-A-01 is the material gate-evidence finding, and A-02/A-03 are needs-evidence test/precondition tightenings.
