## Findings

### [P1] Stale `platform`/`audit` relation and column ACLs survive V010 and are effective for `sharing_command_role`

V010's superuser reset enumerates relations only in `sharing`, `evidence`, `customer_iam`, `organization_access`, and `subject_number` (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:52-67`). It then grants `sharing_command_role` schema `USAGE` on `platform` and `audit` (`...:137-145`), but never resets relation or column ACLs in those schemas. The final fail-closed checks are likewise scoped to the same five schemas (`...:157-165`, `...:167-168`), while the broad effective check at `...:169` rejects only command-role `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER`, not `SELECT`, `INSERT`, or `UPDATE`.

A pre-existing `sharing_command_role` with the exact accepted attributes/membership state is explicitly allowed by the preflight (`...:22-38`). If that role already has, for example, `SELECT` on `audit.audit_fact` or `INSERT`/`UPDATE` on `platform.outbox_event`, V010 neither revokes nor rejects it. Because V010 grants schema `USAGE`, the stale privilege is directly usable after migration. This violates the accepted requirement that the command role receive only `USAGE` and the two named functions in these schemas, with no table privilege there, and that empty-denial matrices include `platform` and `audit` (`docs/gateflow/pa13-sharing-role-least-privilege-plan.md:45`, `...:87`).

The catalog oracle repeats the omission: relation and attribute comparisons cover only the five schemas (`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5117-5147`), and the later effective check omits command-role `SELECT`/`INSERT`/`UPDATE` outside `sharing` (`...:5159`). Therefore the frozen XML can pass while this stale state remains. The same omission covers PUBLIC relation/column ACLs in `platform`/`audit` and third-party grantors there.

Correction required: reset/revoke relation and column ACLs for `PUBLIC`, `sharing_role`, and `sharing_command_role` in `platform`/`audit` before regrant, or reject any residue; add exact grantor/grantable/PUBLIC postconditions and catalog rows for those schemas; add a stale-state test that starts with an exact-attribute command role carrying one of these ACLs.

### [P1] The final membership postcondition rejects legitimate production `sharing_role` memberships

The final check rejects any membership row whose `roleid` or `member` is `sharing_role` or `sharing_command_role` (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:154-155`). That includes the required, legitimate `query_login -> sharing_role` edge: in that row, `roleid = sharing_role`. The dedicated IT itself creates exactly that edge after migration (`backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:47-48`), and the accepted final-state contract calls for it.

The direct replay test hides the contradiction by revoking both role memberships before executing V010 and restoring them afterward (`...:110-116`). On an existing V009 deployment where the non-superuser query login has already been granted `sharing_role`—the normal way to make the read-only principal usable—V010 reaches the end and fails, rolling back the migration. The accepted plan requires excluding a path between `sharing_role` and the command role, not forbidding ordinary logins from assuming `sharing_role` (`docs/gateflow/pa13-sharing-role-least-privilege-plan.md:59`, `...:85`).

Correction required: assert forbidden command-role edges/paths only, while preserving `query_login -> sharing_role`; replay the migration in the actual accepted membership state rather than removing those memberships first.

### [P2] Stale-state rollback evidence stops before the ACL mutation path

Both induced failures in `v010MigrationIdentityAndPostgres16` are raised by the first preflight block: the stale membership test at `backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:133-139`, and the BYPASSRLS test at `...:149-152`. Those checks execute before the reset block at `backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:42`, so no owner-context revoke/regrant has occurred when rollback is asserted.

The residue helper checks only schema `USAGE` and relation ACLs in `sharing` (`...SharingRoleLeastPrivilegeIT.java:65-71`). It does not cover the other six schemas, column ACLs, functions, PUBLIC state, or third-party grantors. The XML's two “Changes successfully rolled back” messages (`review-evidence/failsafe-reports/TEST-com.onecall.archtests.container.SharingRoleLeastPrivilegeIT.xml:124,129`) therefore prove preflight rejection, not rollback after the dangerous ACL mutation sequence. This gap allowed the `platform`/`audit` omission above to remain invisible.

Correction required: within the existing eight-method budget, induce a failure after at least one owner-context reset/regrant, assert the specific rejection, and compare a full pre-failure snapshot across all seven bounded schemas, relations, columns, procedures, and PUBLIC ACLs.
