- It adds one behavioral S1 and no independently useful split; attestation, named seam, HTTP adapter, codec and tests are implementation steps of the same end-to-end behavior (plan §1, §7).

## 4. Design verification

### 4.1 Workspace representation, `/me` compatibility and authority

- `SelectedCustomerWorkspace(WorkspaceType, UUID organizationId)` in customer application, with PERSONAL ⇒ null organization and ORGANIZATION ⇒ non-null organization, is the minimum shape needed for the confirmed server-attested selection. It carries no role, token, provider subject or membership snapshot.
- Extending `VerifiedCustomerSession` and `TrustedCustomerCaller` with a nullable selected workspace, while retaining the existing three-/two-argument compatibility constructors, preserves compile-time compatibility with the existing tests and adapters I inspected: `CustomerSessionBoundaryTests`, `CustomerContextServiceTests`, `CustomerMeWebTests`, `CustomerWebConfigurationTests`, `CustomerMeFixture` and `CustomerMeIT` all use the shorter constructors.
- `CustomerBearerAuthenticator` already preserves exactly-one-verifier, opaque bearer, fixed audience and fail-closed behavior. Adding selected-workspace structural validation and leaving null selection for legacy `/me` is consistent with the current code. The controller deriving `/shares` scope only from `CustomerRequestPrincipal.caller()` and never from request attributes/headers/body/cookies is correct.
- `/me` continues to call only `CustomerContextService.getCustomerMe`; the current repository already builds PERSONAL first and active organizations in repository UUID order and ignores any selection. The plan's promise not to add a selected-workspace response field is consistent with the frozen `CustomerContext` shape.
- `customer_iam -> sharing::customer-query` changes the discovered graph from empty to exactly one edge. The broader allowed map does contain the potential path `sharing → evidence → entitlement_metering → catalog_order → customer_iam`; the plan correctly does not claim the allowed graph is acyclic and requires the discovered graph/cycle check, not a false architectural claim.

### 4.2 Cursor wire format and validation

The v1 arithmetic is correct:

- Fixed prefix: 1 version + 32 binding + 8 epoch seconds + 4 nanos + 1 scalar-count = 46 bytes.
- Maximum scalar count 128: `46 + ceil(21*128/8) = 46 + 336 = 382` payload bytes.
- Unpadded base64url of 382 bytes is `ceil(382*8/6) = 510` characters, within the frozen `CursorParam`/`nextCursor` maximum of 512.
- Decoding at most 384 bytes after a 512-character wire-length check is sufficient; the canonical re-encode equality, nonzero-pad-bit rejection, trailing-byte/payload-length check, padding rejection, scalar range/surrogate/NUL/all-space checks and microsecond/year bounds are all executable and match PA10's `ShareQueryService.validate` and DB constraints.
- Binding only account + normalized workspace (not channel or limit) matches the query's visibility/order: channel and page size do not widen or reorder scope. Reconstructing `ShareCursor` account/organization from the trusted caller and taking only anchor fields from decoded bytes is the correct security boundary. The unkeyed binding is explicitly not an authentication credential; an altered anchor cannot escape the mandatory creator/workspace predicates.
- The choice to exclude a signed-token policy, TTL, key registry or server-state cursor is consistent with the confirmed non-goals and avoids inventing policy.

The codec complexity is therefore justified by the frozen 512-character bound and legal DB identifiers, not extraneous framework work. I found no arithmetic or canonicalization error in §4.1.

### 4.3 HTTP, error precedence, filter and no-DB behavior

The filter's existing admission logic (`CustomerBoundaryFilter.java:47-51`) is a single exact method/servletPath/requestURI predicate. Extending it to exactly `/api/v1/customer/me` and `/api/v1/customer/shares` is the minimal change; HEAD, OPTIONS/preflight, POST/PUT/PATCH/DELETE/TRACE, aliases, trailing slash, encoded paths, semicolon parameters, repeated slashes, public/provider/mutation paths and direct `/error` remain rejected before authentication; ERROR dispatch retains the separate sanitized error controller. This is consistent with the current tests and PA11 behavior.

The Problem writer currently maps six customer codes and has no `CURSOR_INVALID`; appending the code and adding 400/`Invalid cursor` while preserving the five existing fields and headers is compatible with OpenAPI `ProblemCode`/`CursorInvalid` and the frozen OpenAPI `Problem` shape (OpenAPI permits optional detail, but the existing writer's stricter five-field output is preserved).

The default/no-profile path remains non-web and database-free because the new controller is `@Profile("web")`/servlet-conditional and the sharing persistence bean is `@Profile("persistence")`. A `web`-only context with a test verifier correctly has no sharing bean; the controller's lazy `ObjectProvider` should yield sanitized 503 rather than a fallback query. A `web,persistence` context keeps the existing explicit credential requirements and separate customer/sharing pools. The plan's exact qualifiers match `SharingPersistenceConfiguration` and `CustomerPersistenceConfiguration`.

One precedence ambiguity remains; see A-02.

### 4.4 ACL, role ownership and no-write proof

V009 confirms the plan's key database claims:

- `sharing_role` has `SELECT, INSERT` on all three sharing tables and column-level `UPDATE` on `evidence_share_grant` (`status, admissions_used, revocation_generation, revision, expires_at, code_salt, code_hash, code_generation`). The plan correctly does not claim the role has no UPDATE grant; it requires a read-only transaction to fail writes with SQLSTATE 25006.
- `sharing_role` has the exact foreign reads needed: `customer_iam.customer_account(id,status)`, `organization_access.organization(id,status)`, `organization_access.organization_membership(organization_id,account_id,role,status)`, plus the already frozen evidence/subject grants. No new grant is needed.
- `sharing_role` stays inside the sharing transaction and the existing `setReadOnly(true)`, READ_COMMITTED, REQUIRES_NEW, `SET LOCAL ROLE`/`current_user` assertion path is reused. No new pool, transaction or fallback credentials are introduced.
- The current PA10 fixture already proves 42501 for foreign columns/writes/locks and 25006 for an authorized sharing write inside the read-only query transaction (`SharingQueryFixture`/`SharingQueryServiceIT`). The plan's new IT can reuse those mechanisms rather than inventing a weaker proof.

No missing grant or reverse-dependency requirement was found. The "no index" performance point is a residual, not an ACL defect (see §7).

## 5. Findings

### A-01 — Medium — named interface on an `internal` package is unverified; package-level export is broader than stated

Locations: plan §3 (line 49) and §7 (line 159); current `sharing/package-info.java:1`; `sharing/internal/application` contains the eight public application types; `SharingQueryBoundaryTests.java:41-46`; `ModuleBoundaryTests.java:97-118`.

Impact: The central structural seam is `@NamedInterface("customer-query")` on `com.onecall.core.sharing.internal.application`. The plan asserts that Spring Modulith 2.1.2 will accept this as an explicit supported seam despite the `internal` path. No executed test in the frozen snapshot proves that; the proposed `ModuleBoundaryTests`/`ApplicationModules.verify()` change is the first executable proof. If Modulith treats the package as internal regardless of the annotation, the S1 implementation cannot pass its own boundary test and the plan's "no class relocation" assumption fails. If it does accept it, the named interface exports the entire package, so `ShareQueryDiagnostic` (a public record) and the public `CustomerShareQueryService` constructor are externally accessible; the statement "consumers may use only the service, caller/request/cursor/page/summary and typed exception; diagnostic construction stays sharing-owned" is a source-import/test convention, not a Java module-system restriction. The proposed exact import allowlist can enforce the intended consumer list at source-text level but cannot make those public types inaccessible.

Destination: Architecture/Backend, early S1 spike and the exact `ModuleBoundaryTests`/`SharingQueryBoundaryTests` assertions; if the named interface is rejected, a separately authorized seam/package decision is required. No plan edit is authorized by this review.

### A-02 — Medium — malformed selected workspace vs Accept precedence is contradictory

Locations: plan §2 (line 35: authenticator rejects a non-null structurally invalid selection with 503); plan §5 (line 123: (2) bearer/verifier/audience, (3) Accept negotiation, (4) trusted selection); `CustomerBearerAuthenticator.java:43-49`; `CustomerBoundaryFilter.java:52-64`.

Impact: The authenticator runs before the filter parses `Accept`. If it rejects malformed selection during authentication, a request with both a malformed selection and an incompatible/malformed `Accept` returns 503, not the §5 step (3) 500. The plan's test list covers invalid selection in one method and Accept negotiation in another, but not the combined case. This is a real exact-precedence ambiguity in a plan that otherwise specifies precedence precisely. It also affects `/me`: the plan promises legacy null-selection `/me`, but a structurally invalid non-null selection yields 503 before `/me` can ignore it; that behavior is not stated as intended.

Destination: Backend/API contract fix: either move structural selection validation to the controller after Accept, or explicitly state that authentication-time 503 wins and add a combined test. Do not leave the implementation to guess.

### A-03 — Low — test feasibility has unspecified injection points

Locations: plan §8.1 `CustomerSharesWebTests` #9 (serialization/downstream failure), §8.2 `CustomerSharesIT` #5 (both pools), #7 (sharing/evidence snapshot), #8 (denied-role/missing graph); current `CustomerMeFixture.java:46-50, 108-140, 208-221, 294-301`; `SharingQueryFixture.java:234-288`.

Impact: The tests are conceptually feasible, but the plan does not identify executable seams for three claims:

- A simple `CustomerSharePage`/`ShareSummary` record cannot be made to fail Jackson serialization on demand without a test hook; the plan forbids production test bridges. The "downstream" failure path is feasible via a test verifier/repository/response, but the "serialization failure" clause is not specified.
- `CustomerMeFixture` records a named `pools` map only for the web-only context; in the dual context it records only `allPools`, and its `snapshot()` does not include sharing/evidence tables. The new fixture must add dual-pool name mapping and a broader snapshot; this is feasible in the new file but is not described in the plan's write set.
- `CustomerMeFixture` has a single `sharingLogin` and static session map; a denied-role sharing login, a missing-sharing-graph context and a second verifier context need explicit context construction. The plan says "composition" but does not pin these hooks.

Destination: Backend QA/implementation; specify the fixture hooks and fault-injection mechanism, keep them test-only, and do not add production accessibility.

### A-04 — Low residual — no supporting index for the `/shares` access path

Locations: plan §2/§6 (no migration/index change), V009 lines 71-72 (indexes only on `evidence_id,status` and `status,expires_at`), `JooqShareQueryRepository.java:55-67` (filter by creator/workspace, order by `valid_from DESC, share_id DESC`).

Impact: The confirmed non-goals forbid a new index, so the plan is correct not to add one. However, the production query has no index for `created_by_account_id`, `owner_organization_id` and the sort, so it may scan the full share table per request. Small fixture data will pass while production capacity degrades. This is a residual, not a plan-scope violation, but it should be an explicit owner/capacity decision rather than an unmentioned assumption.

Destination: Backend/Database/Platform capacity owner; separate authorized schema/index work if the production volume requires it. Do not add it inside S1.

### A-05 — Observation — controller signature and null-serialization wording

Locations: plan §3 line 37 ("controller accepts only `CustomerRequestPrincipal`"), §7 line 155 (`getCustomerShares(Principal,HttpServletRequest)`); current `CustomerMeController.java:31-40`; plan §4 line 78 (record-local ALWAYS "if necessary").

Impact: The signature is consistent with the existing `/me` pattern (`Principal` parameter plus `instanceof CustomerRequestPrincipal`), so this is a wording inconsistency rather than a semantic drift. Likewise, Jackson's default includes null record components, so `nextCursor:null` will serialize without a global setting; a record-local `@JsonInclude(ALWAYS)` is a safe explicit guarantee, and the test should pin the null property rather than rely on incidental defaults.

Destination: Backend implementation/QA; use the existing `/me` pattern and pin `nextCursor:null` explicitly.

### A-06 — Observation — concrete service exported by the named interface

Locations: plan §3 line 49; `CustomerShareQueryService.java:16`; `ShareQueryDiagnostic.java:5`.

Impact: The plan's phrase "declared query interface" is a Spring Modulith named-interface seam, not a Java `interface`; `CustomerShareQueryService` is a public final class with a public constructor. This is minimal for the existing code and consistent with docs/12's public application-service rule, but the plan should not imply class-level restriction. Combine with A-01's package-export point.

Destination: Documentation wording in a later authorized edit; no S1 code change required.

## 6. Open questions

1. Does Spring Modulith 2.1.2 actually discover and authorize a `@NamedInterface` declared on a package whose path contains `internal`? This is the highest-risk structural assumption (A-01). An early compile/`ApplicationModules.verify()` probe should settle it before the full S1 build.
2. For a request with malformed selected workspace **and** incompatible/malformed `Accept`, is the intended status 503 (authentication/selection failure) or 500 (Accept failure)? The plan's §2 and §5 order disagree (A-02); choose one and add the combined test.
3. Should `/me` return 503 for a session with a structurally invalid non-null selection, or should `/me` ignore the selected workspace entirely and preserve its response for any otherwise valid session? The plan promises only legacy null-selection preservation and an inaccessible-but-valid organization; it does not state the invalid-structure case.
4. Does the plan intend a test-only hook for serialization failure, or should the test assert only downstream/response-buffer failures? The current wording is not executable without deciding this (A-03).
