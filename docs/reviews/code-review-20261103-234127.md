# Code Review — PA13 Sharing Role Least Privilege B

## Findings

### F-01 — High — Stale membership paths are not rejected or reset by V010

V010 validates only owner-role existence and `sharing_command_role` scalar attributes before continuing (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:8`–`:30`). It contains no `pg_auth_members` precondition or membership revocation, and no final membership-path assertion (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:34`–`:100`). Therefore, on a cluster whose V009 state already contains `sharing_command_role` membership, `GRANT sharing_command_role TO sharing_role`, or an indirect equivalent, V010 can complete and preserve an escalation path.

The standalone IT checks these paths only on a clean Testcontainers database (`backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:113`–`:124`); clean-cluster success does not establish the required stale-cluster fail-closed behavior. This is material because the accepted contract requires migration to reject incompatible state rather than rely on later test discovery.

### F-02 — Medium — Existing command-role compatibility is under-specified

The only pre-existing-role compatibility check is `(rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolinherit)` (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:22`–`:27`). It does not reject `rolreplication`, `rolbypassrls`, a changed `rolconnlimit`, membership edges, ownership of unexpected objects, or incompatible ACL grantors. The migration also has no final catalog assertion corresponding to the accepted plan’s step 9.

The existing IT does check the full ten-field attribute tuple after migration (`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5045`–`:5056`), but that is again a clean-cluster witness, not a migration precondition on an arbitrary stale PostgreSQL 16 cluster.

### F-03 — Medium — Grantor-sensitive exact ACL assertions are absent

The accepted plan makes the per-fixture allowed grantor set the sole exact grantor comparison and requires owner grantors for V010-created ACLs. Neither test path implements that contract. `assertV009AclCatalog` compares `grantee`, privilege, and grantability but not `grantor` (`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5107`–`:5148`). The standalone “exact catalog” tests are only seven effective `has_*` booleans for the command role and six for the query role (`backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:128`–`:147`), with no `aclexplode` comparison at all.

Consequently, the successful runtime evidence proves effective privileges but not that V010 produced the required grantor identity. A grant with the correct grantee/privilege but the wrong grantor would pass the current suites.

### F-04 — Medium — Stale PUBLIC column ACLs are not explicitly reset

V010 revokes sharing table privileges from the two sharing roles (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:39`) and explicitly resets column ACLs only for `sharing_role` and `sharing_command_role` (`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:40`–`:42`). It does not issue explicit column-level revokes from `PUBLIC`.

On a stale cluster carrying column ACL residue, the accepted relation-versus-column reset requirement means table-level revocation is insufficient. In that state, PUBLIC access to secret/content columns could survive migration even though a clean-cluster run has no such ACL.

### F-05 — Low — Current test prose still names the narrowed query role

`backend/README.md:323` says the V009 S3 transaction and race evidence runs “Under real `sharing_role`,” but the current V009 S3 method switches to `sharing_command_role` for lifecycle writes (`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:3076`, and additional command-role switches in the same test family). The adjacent totals are updated, but this behavioral sentence is not marked historical and no longer describes the current code path.

## Residual Risk

- The absence of grantor-sensitive assertions leaves the successful ACL end state compatible with a wrong-grantor migration even when effective privileges are correct.
- Runtime evidence is present in the runner stream but is not independently reproducible from XML/log files inside this frozen snapshot.
