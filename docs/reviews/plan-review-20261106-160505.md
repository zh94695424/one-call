## Findings

### 01-未修复-[中]-The `public-admission` named interface exports the whole implementation package, contradicting the plan's controller-facing-only API claim

- **位置**: Plan §4 line 110 (“only controller-facing request/view/exception/service/trusted-caller types belong to this exported API”) and allowlist items 5–20 (all new types directly under `sharing/internal/admission/` with the single `package-info.java` named interface).
- **问题类型**: 架构边界 / 过度耦合
- **当前写法**: All 15 production types — `ShareAdmissionRequest`, `ShareAdmissionView`, `ShareAdmissionException`, `TrustedShareAdmissionCaller`, `ShareAdmissionService`, `ShareAdmissionRepository`, `JooqShareAdmissionRepository`, `DefaultShareAdmissionService`, `ShareAdmissionJsonBinder`, the five provider seams, and `ShareAdmissionPersistenceConfiguration` — live in the same `com.onecall.core.sharing.internal.admission` package that carries `@NamedInterface("public-admission")`.
- **反例/失败场景**: Spring Modulith applies the named interface to the annotated package. `customer_iam` is therefore allowed to depend on the repository, jOOQ implementation, binder, providers, and persistence configuration, not just the controller-facing types. This is wider than the plan's stated boundary and wider than the established pattern: the existing `publicquery`, `application`, and `command` named interfaces contain only exported types, with `persistence`, `commandservice`, and `provider` in separate unnamed packages (`SharingQueryBoundaryTests` exact type sets confirm this). The new architecture test cannot simultaneously assert “only five exported types” and match the actual named interface.
- **为什么有问题**: The accepted A03 fix correctly removes the reverse dependency, but it over-exports the new implementation. This is an architecture-boundary and overcoupling regression relative to the project's own convention, and it makes the plan's line-110 contract false.
- **直接证据**: Plan lines 90–110, allowlist items 5–20; `backend/src/main/java/com/onecall/core/sharing/internal/publicquery/` (four exported files + `package-info`), `application/` and `command/` (exported sets only), `persistence/`, `commandservice/`, `provider/` (unnamed); `SharingQueryBoundaryTests.java:63-100`; `ModuleBoundaryTests.java:126-131`.
- **影响**: Exported implementation types invite cross-module use of the repository/persistence configuration; the exact `public-admission` architecture assertion is ambiguous; future refactors of internal admission types become cross-module breaking changes.
- **建议改法和验证点**: Either move implementation types into an unnamed subpackage (for example `admission/service`, `admission/persistence`, `admission/provider`) and keep only the controller-facing types in the named package — which requires adding those paths to the allowlist — or explicitly accept and enumerate all 15 exported types in plan §4 and `SharingQueryBoundaryTests`, and revise line 110 so the contract is truthful. Verify that `customer_iam` imports only the controller-facing types and that `modules.verify()` plus the exact named-interface assertions pass.
- **修复风险（低）**: No runtime behavior; test/allowlist precision only.
- **严重程度（中）**: Non-blocking (the implementation remains feasible), but material to the boundary contract.

### 02-未修复-[中]-`SharingQueryBoundaryTests` catch-all file-set and command-loop assertions will fail on the new admission package

- **位置**: Plan §4 item 32; `backend/src/test/java/com/onecall/archtests/architecture/SharingQueryBoundaryTests.java:106-121`.
- **问题类型**: 测试缺口 / 过度耦合（test contradiction）
- **当前写法**: Item 32 says only “exact `public-admission` exported types/methods and no customer IAM import; method count unchanged.”
- **反例/失败场景**: `SharingQueryBoundaryTests` walks every file under `sharing/internal` and classifies it as `queryFile`, `publicReadFile`, or otherwise `commandPaths` (`:106`). The new `admission/*` files are in neither exact set, so they enter `commandPaths`; the exact `containsExactlyInAnyOrder(...)` inventory at `:107-113` then fails, and the loop at `:115-121` applies command/provider prohibitions (`pg_advisory`, `FOR UPDATE`, `selectFrom(`, `content_snapshot`, `share_access_event`, `code_salt`, `code_hash`) that the admission repository and proof adapters necessarily use. The plan does not state the required admission file set or exclusion.
- **为什么有问题**: The plan's exact allowlist includes the test, but its described edit is insufficient to make the test pass. An implementation agent following the plan literally will hit a deterministic Surefire failure and must invent the rest of the test design.
- **直接证据**: `SharingQueryBoundaryTests.java:106-121`; plan item 32 (line 147); new admission files are not in `QUERY_FILES` or `PUBLIC_READ_FILES`.
- **影响**: Deterministic test failure; unplanned architecture-test redesign; possible accidental weakening of command/provider assertions.
- **建议改法和验证点**: Specify an `ADMISSION_FILES` exact set (or a `publicAdmissionFile` predicate) and exclude those files from `commandPaths`; add tailored admission assertions (exact exported types, no customer IAM import, no raw SELECT/secret logging, advisory/`FOR UPDATE` only in the repository); keep the single existing `@Test` method. Verify `SharingQueryBoundaryTests` and the exact inventory pass.
- **修复风险（低）**: Test-only edit already allowlisted.
- **严重程度（中）**: Non-blocking but material to the exact test inventory.
