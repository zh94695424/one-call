### Findings

#### 1-未修复-中-Port return type doubles as the public wire record, leaving §3 row-validation ownership unspecified

- **位置**: section 4.1 rows `OperationsActivationReadPorts` and `DefaultOperationsActivationReadService`; section 3 "Exact result mapping"; section 4.3 validation paragraph; test E `nullMalformedAndInvalidLookaheadRowsFailClosed` / `allPersistableStatusChannelAndDomainCombinationsProjectExactly`
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: `ActivationHistoryReader.fetch(Optional<Anchor>,int)` returns `List<ActivationSummary>`, where `ActivationSummary` is the public eleven-field record nested in `OperationsActivationReadService`; section 4.3 additionally says "Validate every mapped row (including lookahead)" while section 4.1 gives the service a `validate` helper and the reader "validate mapping".
- **反例/失败场景**: A unit test must hand the service a row with `fromStatus("BOGUS")`, a null `statusEventId`, `toRevision != fromRevision + 1`, an over-long `reasonCode` or a non-microsecond `occurredAt`. If the implementer enforces the section 3 invariants inside the `ActivationSummary` canonical constructor (the natural reading, since the table header is literally "Java representation and returned-row invariant"), such rows cannot be constructed at all and test E becomes unwriteable as specified; the implementer then either deletes/weaken the assertions or moves validation into the reader, which contradicts test G's expectation that malformed rows fail the *page* with 503 from the service.
- **为什么有问题**: PA33 — the pattern the plan says it is "patterned narrowly on" — separates the two roles: `OperationsSubjectReadPorts` declares `Candidate`/`SubjectFacts`/`DetailFacts` as owner facts, and only the service builds the wire `SubjectSummary`. The plan deviates from its own cited precedent without stating which layer owns the public-contract validation, so two reviewers/implementers can produce structurally different code from the same plan.
- **直接证据**: `backend/src/main/java/com/onecall/core/operations_iam/subjectread/OperationsSubjectReadPorts.java` (facts records) vs `OperationsSubjectReadService.java` (`SubjectSummary` built by `DefaultOperationsSubjectReadService.summary(...)` after `validateSubject(facts)`); plan section 4.1/4.3 text quoted above.
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 测试缺口 / 后续返工
- **建议改法和验证点**: Freeze one option in the plan — either (a) add a port-owned `TransitionFacts` record with eleven raw columns (nullable boxed types) to `OperationsActivationReadPorts` and keep `ActivationSummary` construction+validation exclusively in the service, mirroring PA33; or (b) keep the current shape but state explicitly that `ActivationSummary` is a permissive carrier with no canonical-constructor validation, that all section 3 invariants are enforced by service `validate`, and that the reader only maps boxed columns to avoid `null → 0`. Verification point: test E must be able to construct every malformed/lookahead-malformed row through a stubbed port and still assert zero serialized output plus 503.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

#### 2-未修复-中-A second mandatory key-ring prefix is an operator-visible delta that no planned artifact records

- **位置**: section 4.2 property list (`onecall.operations-activation-read.cursor.*`); section 3 step 5 ("even on first/empty pages=>503 for invalid/missing keys"); section 10 risk register; section 5 allowlist (no config path)
- **问题类型**: 非最优方案 / 过度设计
- **当前写法**: A dedicated endpoint-specific property prefix and key ring; PA33 keys are explicitly insufficient; the whole endpoint returns sanitized 503 when the new keys are absent, including for the first/empty page.
- **反例/失败场景**: A deployment provisions exactly what PA33 required. PA34 ships, all PostgreSQL16/HTTP tests pass because `OperationsActivationReadFixture` injects synthetic keys, and every real request returns 503 until an operator adds 1–3 fresh 32-byte secrets. The plan's own section 4.2 concedes the shared-key alternative is sound ("Cryptographically a common AES key can support independent authenticated purposes if every envelope uses distinct AAD and nonces"), and its planned test D already asserts that a *same-key, different-AAD* subject token returns 400 — i.e. the safety property the separation is meant to buy is already proven to come from the AAD/purpose, not from a second ring.
- **为什么有问题**: Control's binding cursor paragraph authorises isolation "only as the accepted plan proves from current code" and the proven defect is the *filter-bound codec semantics*, not the key material. Separating the codec (kept in this plan) is therefore justified; separating the configuration is an added mandatory operational input with no repo-side provisioning destination: section 10's documentation delta is only the implementation report, and neither `backend/src/main/resources/application*.yml` nor `deployment/` carries any cursor-key inventory today, so the delta silently lands in a later deployment/production-readiness gate.
- **直接证据**: Plan section 4.2 quoted text and property list; `OperationsSubjectReadPersistenceConfiguration.java:40`–`:49` (PA33 prefix + hardcoded regex, confirming the plan's separate-check requirement) and `OperationsSubjectReadProperties.java:20`–`:35` (ring rules the plan reuses); repo-wide grep shows `onecall.operations-subject-read` appears only in main/test Java and historical review docs, never in YAML/deployment; `.github/workflows/ci.yml:1858`–`:1864` proves today's JAR smoke never supplies cursor keys, hence 503-only probes.
- **影响**: 风险后移 / 不可恢复 (endpoint dead in production until an undocumented secret set exists) / 后续返工
- **建议改法和验证点**: Prefer reusing the existing `onecall.operations-subject-read.cursor.*` ring as the key source for the new purpose-bound codec (endpoint binding continues to come from `onecall:operations-activation-list:cursor:v1\0` AAD + distinct envelope length, and D/G already assert subject tokens are `CURSOR_INVALID`), so no new operator secret appears. If the separate prefix is kept, the plan must add it to section 10 as an explicit required-delta row with a destination (deployment/production-readiness goal confirmation), state that absence is a permanent 503 rather than a startup failure, and add a JAR-smoke expectation that distinguishes "keys unprovisioned" from "dependency unavailable".
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

#### 3-未修复-中-No captured-log leakage test, breaking the PA33 data-minimisation test convention

- **位置**: section 6 G (`OperationsActivationReadsIT`, 18 methods) and A/B leakage assertions; section 7 "no attempt to equate …"
- **问题类型**: 测试缺口
- **当前写法**: Leakage is proven only through response/problem bodies (A `problemsHaveExactSafeEnvelopeHeadersAndChallenge`, A `unknownAndPartialResponseFailuresDoNotLeak`), redacted `toString` (B `propertiesKeysRequestsAndCodecsRedactToString`) and a jOOQ-observer/serialization assertion (G `onlyTransitionFactsAreReadAndNoHiddenFieldsLeak`).
- **反例/失败场景**: The plan deliberately reuses shared infrastructure that touches SQL text, connection baselines, key identifiers and the raw query map. A future log-level change (jOOQ `withExecuteLogging(false)` at `OperationsSubjectReadPersistenceConfiguration.java:119`, Hikari/`Failure` printing, or an added `catch` that logs a cause) puts cursor ciphertext, an employee UUID or a JDBC URL into stdout while every response assertion still passes. - **影响**: review 不可验收 / 观测缺口导致失败被隐藏 / 后续返工

### Open questions

1. **docs/15 §5 filter-digest rule vs the no-digest envelope.** `docs/15-production-openapi-surface-spec.md:260` states every list cursor binds "稳定排序键、最后记录内部排序值与规范化过滤摘要"; the plan ships an anchor-only envelope with no digest field. Control's binding cursor paragraph authorises exactly this and the contract defines no filters, so the plan is almost certainly right — but it never cites that authorization. Should section 4.2 add one sentence recording the deliberate deviation and its authority? (Destination: plan text only.)
2. **Where does the "no unindexed global sort" consequence land?** Every existing index on `activation_consent.service_activation_transition` is either a uniqueness constraint or `ix_activation_transition_occurred (subject_id, occurred_at DESC)` (`backend/src/main/resources/db/migration/V007__activation_and_consent.sql:161`–`:162`); none can serve `ORDER BY occurred_at DESC, id DESC`, and the reuse of PA33's 2000 ms statement timeout / 250 ms lock timeout / 5 s budget (`OperationsReadContext.java:38`–`:40`, template timeout) means a large ledger turns every page into 503. Because V018 is frozen out of scope, the plan's "accept bounded query failure" is compliant — but is the intended disposition a documented known limitation at this gate, or a renewed goal confirmation the moment real row counts are known? (Destination: residual risk / goal confirmation, not an implementation change.)
3. **`statusEventId`/`reasonCode` "1–N Unicode code points" vs `length()` in text.** The plan correctly mirrors `btrim`/`length` semantics; it does not say whether the *returned* value must also satisfy the OpenAPI `maxLength` after JSON serialization (astral characters are 2 UTF-16 units but 1 PG character). Is the intended guarantee "database character count" (which can exceed a UTF-16-based validator reading)? Worth one clarifying line in section 3.

### Residual risks and destinations

- **Unindexed ledger-wide keyset sort** → known limitation to be carried in the PA34 implementation report and re-evaluated at the production-readiness gate; any index requires renewed user authorization because it is a migration delta. Not an implementation task in S1.
- **Non-linearizable revocation** (employee disable or transition appended after snapshot is visible only on the next request) → already stated in section 4.4; keep as an accepted semantic in the implementation report, matching PA33 precedent.
- **Connector canonicalization behaviour** (`EncodedSolidusHandling.PASS_THROUGH` at `CustomerWebConfiguration.java:38`–`:40`) can make some encoded variants never reach the filter → plan section 10 and test G already require "never data/auth success" rather than a specific status; keep verifying, and do not weaken CI probes to force a 404.
- **Secret-provisioning burden** (finding 2) → destination is deployment/production-readiness goal confirmation if the separate prefix survives.
- **Inventory coupling to CI history dictionaries** → PA34 must edit the whole `paNN_start_*` subtraction chain; low ambiguity but highest churn risk. Destination: implementation-gate XML/source equality checks (`ci.yml:438`–`:456`) already prove it mechanically.

### Verdict

**Conclusion: pass-with-risks.**

The plan is scope-faithful to the PA34 goal confirmation with no goal drift or scope creep detected: one endpoint, eleven fields, one slice, no invented filter/field/endpoint, and no frozen-input delta. Its load-bearing assumptions were independently re-proved — the raw-byte frozen manifest (21 hashes, V001–V017, no V018), the V007 owner-local SELECT privilege with `operations_iam_role` genuinely denied, the exact `58 + keyIdLength` cursor envelope arithmetic, unsigned-UUID tie-breaking, the 70/644 + 29/476 = 99/1120 baseline with 1121 token lines and 29 POM includes (all reproduced from this tree), and the customer-filter lockstep necessity. Its honesty about NOT RUN at the plan gate is accurate.

Three material findings remain, all fixable in the plan with low or medium repair risk and none invalidating the architecture: the port/wire record identity ambiguity (finding 1, which is the one most likely to make the implementation agent re-design), the undocumented operator-side key-provisioning delta (finding 2), and the missing log-leakage evidence class relative to the PA33 convention (finding 3). Finding 1 and finding 3 should be resolved before implementation authorization; finding 2 should be resolved either by reusing the existing ring or by carrying an explicit destination.

Implementation is still not authorized by this artifact; the author/fix artifact does not self-pass this gate.
