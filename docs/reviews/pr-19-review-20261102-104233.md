### F-B-01 (Medium, observability) — the returned `traceId` is never recorded server-side, so every failure is undiagnosable

- **Files**: `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerBoundaryFilter.java:44`, `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerProblemWriter.java:55`, `backend/src/main/java/com/onecall/core/customer_iam/internal/application/CustomerContextException.java:8`, `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerMeController.java:42-50`.
- **Condition**: any 401/404/500/503, including a real database outage or a verifier adapter failure.
- **Actual**: a fresh `UUID` is generated per request, returned in the Problem body and stored only as a request attribute. Every failure path swallows the throwable: `CustomerContextException` is built with `super(code.name(), null, false, false)` (no cause, no suppression), the filter catch at `CustomerBoundaryFilter.java:76-80` discards the exception, the controller advice at `CustomerMeController.java:42-50` discards it, and `rg "Logger|System.out|printStackTrace"` over `customer_iam` returns zero hits. No log record of code, status or traceId exists anywhere.
- **Expected** (per `docs/gateflow/pa11-customer-auth-api-foundation-plan.md:222`): "Application failure diagnostic, **if emitted**, is limited to fixed operation `getCustomerMe`, fixed error code and generated traceId". The plan permits this minimal record; PA11 emits nothing, so a customer-supplied `traceId` cannot be resolved, and 500/503 rates are invisible to log-based alerting on the only shipped customer operation.
- **Impact**: incident triage and support loops are impossible in production shape; the public contract advertises a trace identity that has no server counterpart. Sanitization is not the problem — the current tests forbid exactly the leaky form (throwable objects, raw messages), and a message-only fixed diagnostic satisfies them (the assertions test `doesNotContain("CANARY", "Bearer", "Authorization")` plus `getThrowableProxy()).isNull()`, which a cause-free log line keeps true).
- **Recommendation**: emit the plan-sanctioned single diagnostic line (operation + frozen code + status + traceId, no cause, no bindings, no `toString` of any request object) at the filter/problem-writer boundary, and add the existing-but-absent residual row for "no server-side trace sink" to the plan §11 table owned by Platform/Security/Observability (the current row `:429` only covers external log policy and edge/connector limits).
- **Verification point**: a focused web test asserting one captured root-log event per failure containing the emitted code and the same `traceId` the client received, while the existing canary assertions stay green.

### F-B-02 (Low, HTTP semantics / error taxonomy) — client-caused negotiation failures are reported as server failures

- **Files**: `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerBoundaryFilter.java:54-64`, `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerApiErrorController.java:30-36`.
- **Condition**: authenticated request whose `Accept` is incompatible (`text/html`, `application/x-unknown`, `application/json;q=0`), unparseable (`application/json;q=oops`), or any container `sendError` status outside `{401, 404, 503}`.
- **Actual**: `500 INTERNAL` with `title "Internal error"`. The error controller maps 400/403/405/406/415/422/429 to 500 as well; `CustomerMeWebTests.applicationNegotiationAndErrorDispatchUseFrozenProblems` freezes this table.
- **Expected**: a client-input failure should not be counted as a server failure. RFC 9110 gives 406 for unacceptable negotiation, and `ProblemCode` already contains `VALIDATION_FAILED` (→ 422), which is already listed in the frozen `/me` `x-onecall-error-codes` and in `api/openapi/onecall-v1.openapi.yaml` responses.
- **Impact**: no security or contract breach — this is *disclosed* at `backend/README.md:59` ("authenticated unsupported/malformed negotiation maps to sanitized 500") and registered as a PA11-owned choice in `docs/gateflow/pa11-customer-auth-api-foundation-plan.md:433`. The cost is operational (error-budget/SLO attribution, misleading client retry semantics) and the odd asymmetry that the reserved `VALIDATION_FAILED` vocabulary is never used for the one client-input error the boundary can actually see.
- **Recommendation**: either map negotiation failure to `VALIDATION_FAILED` (422, already contract-listed, needs no canonical edit) or keep 500 and make the A1/docs/15 Problem-convention task explicitly own the choice, so the next surface does not inherit it silently.
- **Verification point**: `CustomerMeWebTests.applicationNegotiationAndErrorDispatchUseFrozenProblems` plus the CI `("/api/v1/customer/me", {"Accept": "text/html", ...})` probe expectation must be changed together with whatever the controller decides.
