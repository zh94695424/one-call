### PA41-A-02-未修复-中-Success-path zero-delta oracle omits catalog tables although "no catalog mutation" is binding
- **位置**: Plan §8.2 zero-delta oracle (`:338`), §5 step 5 ("no need for owned catalog row locks", `:104`), Control non-goals (`docs/gateflow/project-execution-control.md:14`, `:26`).
- **问题类型**: 测试缺口 / 状态机漏洞.
- **当前写法**: The oracle snapshots `customer_order`, `consent_record`, `platform.idempotency_record`, `outbox_event`, `audit_fact`, payment tables, entitlement/trial tables and activation heads/transitions; success requires exactly +1 order/+1 consent/+1 completed PURCHASE/+2 Outbox/+2 audit and "zero everywhere else" within that set.
- **反例/失败场景**: A checkout implementation bug bumps `catalog_order.catalog_version.revision` (or rewrites `catalog_offer.updated` fields) while successfully creating the order. The success delta still shows +1 order/consent/idempotency and zero for the enumerated tables, so the test passes, yet a binding non-goal ("no catalog mutation") is violated. The fault-injection test's "snapshot all tables" only covers failed/aborted paths, not a successful-path catalog write.
- **为什么有问题**: `catalog_order_role` legitimately has `UPDATE (sale_status, offer_type, audience, price_cents, currency, billing_cycle, installments, grant_interval_months, snapshot, snapshot_sha256, published_at, revision)` on `catalog_version`, `UPDATE (offer_status, version_token, revision)` on `catalog_offer` (V004 `:426`–`:431`), so the runtime role *can* mutate catalog; only the intended SELECT-only code shape prevents it. The user's binding scope explicitly excludes catalog mutation, and the plan relies on tests to prove it.
- **直接证据**: V004 grants above; plan §8.2 oracle list; Control non-goals. `OperationsCatalogVersionBoundaryTests.rejectsSelectStarForbiddenTablesAndContentWrites` (`:15`) shows the project already treats "no catalog write" as a guard-worthy invariant for the operations path, but the PA41 plan does not carry the equivalent catalog-write assertion for its new checkout SQL.
- **影响**: A successful checkout can silently mutate catalog state (revision/token/status), causing later commercial inconsistency and defeating the "no catalog mutation" acceptance criterion without a red test.
- **建议改法和验证点**: Include `catalog_product`, `catalog_version`, `catalog_offer`, `catalog_benefit_line` (including revisions and mutable timestamps) in the before/after byte oracle for success, replay and denial; add a static boundary assertion that checkout SQL contains no `INSERT`/`UPDATE`/`DELETE` on catalog tables other than the single `customer_order` insert, and no `FOR SHARE`/`FOR UPDATE` on them.
- **修复风险**: 低.
- **严重程度**: 中.

- **影响**: Authorization race on the primary success path; lock-order/witness tests may encode the omission rather than catch it.

### PA41-A-05-未修复-中-Approved `terms` canonicalization and error mapping are undefined while the snapshot hash covers them
- **位置**: Plan §4 (`:80`, `:92`), §3.1 item 7 (`:67`), §8.1 `snapshotHashUsesCanonicalFullSnapshotNotProjection`.
- **问题类型**: 契约缺失 / 不可直接实施 / 状态机漏洞.
- **当前写法**: The full stored snapshot is "all docs14 §10.19 fields", including an "immutable terms" object. The plan's canonicalizer accepts bounded integral/string/boolean/null/object/array shapes and rejects unsupported numbers rather than rounding; it does not define the approved `terms` object's allowed shape, nor the public/internal error mapping for a lawful approved terms object containing a non-integer or >2^53 number.
- **反例/失败场景**: Finance lawfully approves a terms object containing a decimal rate (e.g., a tax/fee ratio). The fixture-based success tests use integer-only terms and pass; in production the new checkout either rejects a valid payable offer with `VALIDATION_FAILED` (false negative) or throws `INTERNAL`/`SERVICE_UNAVAILABLE` because the canonicalizer cannot faithfully canonicalize the value. The plan's §3.1 item 7 maps only "absent/unapproved terms/schedule → 422" and "internally contradictory facts → 500"; a non-integer number is neither.
- **为什么有问题**: docs14 §10.19 leaves `terms` shape open but the snapshot hash is binding and immutable; the plan's own bounded canonicalizer therefore needs an explicit, testable domain. Without it, the primary success path's behavior depends on unpublished Finance input shape, and the implementation agent must invent the decision.
- **直接证据**: docs14 `:4046` (`"terms": "<approved immutable commercial terms object>"`), `:4053`–`:4055`; plan §4 canonicalization rules; plan §3.1 error precedence.
- **影响**: Valid approved offers become uncheckoutable or produce the wrong frozen code; snapshot hash determinism is unproven for a lawful input.
- **建议改法和验证点**: Define and validate the approved `terms` JSON shape (e.g., object of strings/booleans/integers/arrays/objects with bounded depth) as part of snapshot validation; map unsupported numbers to `VALIDATION_FAILED` before any write and add a fixed test vector; if broader numeric terms are required, implement ECMAScript shortest round-trip formatting and test it independently.
- **修复风险**: 中 (depends on the approved terms shapes).
- **严重程度**: 中.

## Final plan review conclusion

`fail`

The core architecture is credible: the PERSONAL-only slice maps to real frozen contracts, the LO writable template/role grants exist, the schema supports the order/consent/idempotency/Outbox/audit writes, and the module/dependency direction is sound. The plan is nevertheless not yet code-generation-ready as its exhaustive claims state: the modified-guard list omits two production-manifest methods that the allowlisted 18-file delta definitely changes (High), and there are evidenced medium gaps in the success zero-delta oracle (catalog), the PERSONAL account-lock specification, the frozen `payment_order` contract mismatch, and the approved `terms` canonicalization. These are bounded corrections; after adding the two guard methods/counts and resolving A-02..A-05, a fresh plan re-review should be expected.
