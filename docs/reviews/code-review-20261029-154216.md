### F-PA6-AGG-B-02 — ISSUED terminality and settlement-at-most-once are plan-claimed but not DB-enforced; S2 lifecycle tests overclaim terminal coverage

- **Entry / function**: `entitlement_issuance` state machine (`guard_entitlement_issuance` + `ck_issuance_state_shape`); `usage_reservation` settlement (`guard_usage_reservation` + `ck_usage_reservation_state_shape`); S2 method `v006TrialBalanceIssuanceLifecycleAndAppendOnlyBackstops`
- **File / line**:
  - Plan claim: `docs/gateflow/pa6-v006-entitlement-reservation-usage-foundation-plan.md:411-412` (`PENDING → ISSUED` terminal; settlement at most once)
  - Guard: `backend/src/main/resources/db/migration/V006__trial_entitlement_issuance_reservation_usage.sql:548-583`
  - Shape check: same file `:359-361`
  - UPDATE column grant (mutable terminal columns): same file `:650`, `:653`
  - Test: `PostgresContainerIT.java:10073-10098` (ISSUED block); `:10515-10535` (SETTLED/RELEASED positive inserts only)
- **Triggering scenario**:
  1. After an issuance row is `ISSUED` with `grant_id` + `issued_at` set, an `entitlement_metering_role` caller runs `UPDATE entitlement_issuance SET status='PENDING', grant_id=NULL, issued_at=NULL, last_error_code=NULL, updated_at=now(), revision=revision+1 WHERE id=?`.
  2. Same class: `status='FAILED'` with `grant_id`/`issued_at` cleared and `last_error_code` set.
  3. Reservation: after `SETTLED` with `settled_units=5`, `terminal_at` set, caller rewrites `settled_units` or clears terminal shape back to `HELD` and settles again.
- **Actual branch**: `guard_entitlement_issuance` freezes only `id, order_id, installment_no, entitlement_type, source_event_domain, source_event_id`. `guard_usage_reservation` freezes only `id, call_id, balance_id, subject_id, authorized_units, authorization_expires_at, created_at`. `status`, `grant_id`, `issued_at`, `last_error_code`, `settled_units`, `terminal_at` are all in the column-level `GRANT UPDATE` and are **not** guard-protected. `ck_issuance_state_shape` is shape-only: `(status='ISSUED') = (grant_id IS NOT NULL AND issued_at IS NOT NULL) AND (status='FAILED') = (last_error_code IS NOT NULL)`. Un-ISSUE by clearing `grant_id`+`issued_at` and setting `status='PENDING'` satisfies that equation (`false = false`).
- **Expected behavior**: Plan §5.1: `PENDING → ISSUED` **terminal** (no later transition out of ISSUED); `usage_reservation` **settlement at most once**. Either the DB (guard/trigger/transition check) or a documented application-ownership boundary must make that true; tests must not imply DB terminality they do not probe.
- **Actual behavior**: DB allows leaving ISSUED and re-settling. S2 test comment “Terminal ISSUED requires grant_id + issued_at” (10087) describes the positive UPDATE input, and the only negative probe is status-only `ISSUED→FAILED` with `grant_id`/`issued_at` left set (10093-10098), which `ck_issuance_state_shape` correctly rejects. The test does **not** probe un-ISSUE, `ISSUED→FAILED` via clearing grant/issued_at, or any SETTLED mutation / second settlement. Reservation probes are legal-shape inserts plus named-check rejects, not terminality.
- **Direct evidence**:
  - Guard body 548-583 (immutable column list)
  - `GRANT UPDATE (status, attempt_count, last_error_code, grant_id, first_attempt_at, issued_at, updated_at, revision)` at 650
  - `ck_issuance_state_shape` 359-361
  - Test 10073-10098 vs plan 411-412
  - Plan §4.9 classifies both tables as “Mutable head … Status/terminal-time retirement, conditional revision” without assigning terminality to triggers
- **Impact**: State-machine ownership is ambiguous. An application service that assumes DB-enforced “ISSUED is forever” / “settle once” can double-settle or resurrect a failed/pending line after issue. Evidence method name includes “Lifecycle” and comments say “Terminal ISSUED”, which over-reads as covered terminality. No current S2 assertion is false-green because of this (the probed reject is real); the gap is untested contract, not a wrong green.
- **Fix / validation (suggested, not applied)**: Controller chooses one: (a) **Document-and-test** — classify terminality as application-owned in the residual register and add bounded S2-style probes that *characterize* the actual DB transitions (un-ISSUE succeeds; re-settle succeeds) so evidence stops implying enforcement; (b) **Defer enforcement** to the future application service / V007+ guard, with a named owner; (c) if DB enforcement is required now, it cannot land in frozen V006 and must be a later migration (out of this aggregate scope). Validation: static predicate analysis above is sufficient to show the transition is legal; a live probe is optional confirmation and would be test-only.
- **Fix risk**: (a) Low (test/comment/residual only). (b) Low now, service-critical later. (c) High (frozen migration; needs V007+).
- **Severity**: **Medium** (state-machine ownership / test-strength; not a current ACL or data-loss bug)
- **Disposition for controller**: **accepted** as contract/test gap requiring (a) or (b) / **deferred-with-owner** to application service / **rejected-with-reason** if plan “terminal”/“at most once” is explicitly read as app-layer and S2 comments are accepted as shape-only / **needs-more-evidence** if a live mutation probe is required
