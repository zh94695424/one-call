2. **Membership terminal `REVOKED` is service-owned, not DB-enforced.** The partial unique index prevents a second live row and prevents reviving a revoked row while a live row exists, but a direct runtime-role update can revive a revoked row when no live row exists (direct PG16.15 probe). Plan §6.6/R-08 assigns the terminal transition and pairing advisory lock to the organization-access service. Controller action: keep V002 as accepted and require the service slice to enforce terminality; do not add a new V002 guard (docs §10.8.1 does not include one).
3. **Last-admin protocol is test-only.** The advisory-lock/count/conditional-update protocol is transient SQL in the IT, not a database function or production service; plan §6.6/R-09 assigns the production implementation to operations-iam. Controller action: no V002 change; later service must implement the same order.
4. **S2 evidence cleanup wording.** §8 line 151 of the S2 evidence states that uncommitted methods roll back and assert zero residue; the FK helper rolls back deterministically but does not query zero residue, while the lifecycle, collision, immutability and concurrency helpers do assert zero. The statement is best read as scoped to the concurrency scenarios and does not affect executable behavior. Optional evidence clarification or additional FK-helper zero assertions; Backend/QA.
5. **S3 evidence “whole probe runs in one transaction”** is a slight simplification: the owned/cross/schema/guard runtime probes use one rolling-back transaction, and the schema/guard catalog assertions use a separate read-only connection. Executable behavior is correct; optional wording clarification; Backend/QA.
6. **RR-09 precision.** `awaitBlockedBackend` filters `wait_event_type='Lock'` but not `wait_event='advisory'`. Direct two-session PG16.15 evidence shows the same advisory key produces `wait_event_type='Lock'`, `wait_event='advisory'`; the last-admin loser's first statement is that advisory lock, so the test is not falsely positive.
