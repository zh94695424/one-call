### RR3B-01-未修复-中-RR2-04 shared-pool read-availability subcase has no pinned overlap witness and its window is the same 250 ms it must prove
- **位置**: plan §9.3 `:366` (`OperationsCatalogVersionLifecycleIT.concurrentPublishersYieldOneActiveWinner` bounded-contention subcase), with §6.1 `:193`, §12 `:553` and fix3 §2 RR2-04 / §4
- **问题类型**: 测试缺口 / 并发恢复风险 / 不可直接实施
- **当前写法**: "While that command waits, run an existing catalog-product read through the unchanged read service/template on another connection of the **same raw pool** and assert success with exact data and restored read settings… Use latches/SQL observation, not arbitrary sleeps; a generous 10-second harness deadline bounds the test, not a false exact250ms HTTP assertion."
- **反例/失败场景**: (a) *vacuous pass* — an implementer runs the read after the waiting command has already returned `55P03`/409. Every literal assertion is still satisfiable (three effective `SET LOCAL` values observed on the writer PID, write terminates 55P03 → sanitized 409, zero lifecycle/audit/Outbox deltas, admin lock released in `finally`, post-rollback read succeeds, guard baselines match), yet nothing proves that a read can obtain and use a slot while a write occupies one. §12 and fix3 §4 both present this subcase as the mandatory pool/read-availability proof, so the controller-accepted RR2-04 obligation would be satisfied in form only. (b) *flaky acceptance gate* — an implementer instead enforces strict overlap. The read path costs a Hikari checkout from a pool with `minimumIdle=0` (possibly a new physical connection), then `OperationsReadContext.enter()` = identity `fetchSingle` + 3 `SET LOCAL` + `SET LOCAL ROLE` + `assertRole` (≈6–8 round-trips) plus the product query, and the plan caps the observable wait at the command's own `lock_timeout=250ms` — one-eighth of the `connectionTimeout=3000ms` budget it also relies on. On a loaded runner the read can legitimately finish after the cancellation, and because the subcase must live inside a **frozen existing identity** (no new test may be created and weakening is forbidden), the natural failure response is pressure to relax the assertion.
- **为什么有问题**: the accepted RR2-04 wording is "test pool/read availability or classify residual with owner if not"; fix3 claims both. The plan pins the *inputs* (same raw pool, unchanged read template, restored settings) but not the *witness that the two overlapped*, so the single most load-bearing claim of the fix ("one blocked write does not consume the whole pool", §12/`:553`) is neither proven nor bounded deterministically, and the mandatory-before-acceptance flag is attached to it.
- **直接证据**: plan `:193` (`SET LOCAL lock_timeout='250ms'` per command transaction), `:366` (subcase text, 10 s harness deadline, "not a false exact250ms HTTP assertion"), `:367` (`auditFailureRollsBackLifecycle` real-`57014` sibling), `:553` (subcase declared "mandatory before implementation acceptance"); `OperationsSubjectReadPersistenceConfiguration.java:78-81` (`maximumPoolSize(4)`, `minimumIdle(0)`, `connectionTimeout(3000)`, `initializationFailTimeout(-1)`); `OperationsReadContext.java:28-42` (identity `fetchSingle`, three `SET LOCAL`s at `:38-40`, `SET LOCAL ROLE` and `assertRole` per `enter()`); `OperationsCatalogProductReadConfiguration.java:25-27` (the read really shares this datasource).
- **影响**: 实施 Agent 跑偏 / review 不可验收 — the accepted availability proof can be green without proving availability, or intermittently red on a frozen identity and later weakened.
- **建议改法和验证点**: in §9.3 pin one of two deterministic shapes and forbid the third reading. Preferred: the fixture-admin connection acquires the advisory lock and **retains it until after the read's result is recorded**, and the subcase asserts the monotonic witness chain — command PID observed in the lock wait (`pg_stat_activity.wait_event_type='Lock'` sampled through the admin connection, or the DSL execute-listener's pre-lock stage), read start strictly after that sample, read success strictly before the command's `55P03` return, then 409 + zero fact deltas + admin release in `finally`. Alternative (explicitly sequential): assert occupancy instead of overlap — pool active/idle counters (or `pg_stat_activity` count for the pool) show exactly one LO session in use while the command waits, the concurrent read succeeds, and the post-rollback read succeeds — and in that case downgrade §12 `:553` and fix3 §4 so the availability claim is worded as "a blocked write does not exhaust the pool's other slots", not "read availability under contention". Either way state that the read must use the unchanged read template on this datasource (no second pool, no raw JDBC shortcut) and keep the "no arbitrary sleeps / no weakened assertions" rule.
- **修复风险（低/中/高）**: 低 (text-only clarification of one existing subcase; no count, identity, contract or inventory change)

### RR3B-02-未修复-低-`55P02 → 409` is an unreachable branch whose only real source is pinned to 503
- **位置**: plan §6.1 `:206` and §9.3 `:365` (`mapsUnmatchableStateToConflict` injected-`55P02` subcase, `restoresRoleOnSuccessAndFailure`)
- **问题类型**: 契约缺失 / 状态机漏洞 / 过度验收标准
- **当前写法**: "After complete rollback, SQLSTATE `55P02` maps to `409 CATALOG_PUBLICATION_CONFLICT` as explicitly required by the accepted RR2-04 contract… Setup failure remains503, even if the failed SET reports55P02."
- **反例/失败场景**: PostgreSQL 16 raises `55P02 cant_change_runtime_param` only when a `SET` targets a GUC that cannot be changed at runtime. The only `SET`s PA38 issues are `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout` (all runtime-settable, as `OperationsReadContext` proves daily) and `SET LOCAL ROLE` (whose failure is `42501`). So the only reachable source of `55P02` is precisely the `SET LOCAL` installation whose failure §6.1/`:193` and §9.3/`:365` pin to sanitized `503`. The mandated `55P02` unit subcase therefore can only be produced by injection, and the classifier contains a branch that real execution cannot take — an implementation agent must both write it and explain it, and a later reader can reasonably conclude the 409/503 precedence rule is inconsistent.
- **为什么有问题**: the Control's accepted RR2-04 wording itself mislabels `55P02` as "lock unavailability"; fix3 correctly mapped the real `55P03 lock_not_available` and kept `55P02` for literal contract continuity, but did not say so. Carrying an unreachable mapping without a reachability note invites either dead-code pushback or an implementation that quietly re-points setup failures at 409.
- **直接证据**: plan `:193` (installation failure → 503), `:206` (`55P02` → 409 plus the PG16 naming note), `:365` ("Setup failure remains503, even if the failed SET reports55P02"); Control `:~97` accepted `PA38-PLAN-RR2-04` text; `OperationsReadContext.java:38-40` (the same three GUCs are installed successfully on every shipped read).
- **影响**: 生成错误代码 / review 不可验收 (one classifier branch and one test subcase verify nothing about production behavior; precedence is easy to invert)
- **建议改法和验证点**: add one sentence at `:206`/`:365`: `55P02` is retained **only** to honour the accepted RR2-04 wording, is schema/execution-unreachable for the three planned GUCs, is proven by injection alone, and may never override the 503 precedence for `SET LOCAL` installation failure. Keep the injected subcase, and assert in `restoresRoleOnSuccessAndFailure` that an installation failure carrying `55P02` still yields 503 with zero facts.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## 6. Open questions

1. **Unmapped SQLSTATE default.** §7.1/§7.2 map states and §6.1 maps `23505`/`40001`/`55P02`/`55P03`/`57014`, pool-acquisition and cleanup failures, but nothing pins the outcome for other database errors the plan can actually meet: `42501` (ACL drift), `P0001` from `guard_catalog_version_published`/`audit.append_fact`/`platform.outbox_append` argument validation, and connection-loss/`57P01`-style backend termination (possible once `idle_in_transaction_session_timeout=5000ms` equals the Spring 5-second transaction timeout).
