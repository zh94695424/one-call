### PA37-PLAN-A-03-未修复-中-§10's `catalog_order_role` ACL assertion contradicts V004: the role has table-wide SELECT/INSERT on all seven owner tables, UPDATE grants and function EXECUTE, not "SELECT only on approved catalog tables"

- **位置**: Plan §5 lines 249-252; plan §10 lines 426-429; plan success signal §1 item 6 (line 28).
- **问题类型**: 架构边界 / 契约缺失 / 测试缺口.
- **当前写法**: "V004 currently grants `catalog_order_role` table access for the catalog owner tables ... The implementation must prove the existing grant is sufficient. No grant change is permitted." §10 requires "Direct catalog-role ACL assertions show SELECT only on approved catalog tables and no unauthorized column/table/function access; `INSERT`, `UPDATE`, `DELETE`, DDL, `FOR UPDATE`, advisory locks, audit/outbox writes, and mutation attempts fail or are absent as appropriate."
- **反例/失败场景**: V004 grants `catalog_order_role` table-level `SELECT, INSERT` on all seven `catalog_order` tables: `catalog_product` (`:424`), `catalog_version` (`:425`), `catalog_offer` (`:429`), `catalog_benefit_line` (`:432`), `customer_order` (`:433`), `payment_order` (`:436`) and `payment_event` (`:439`). A test written to the plan's wording will either fail (if it probes payment/order tables) or become vacuous. It also misattributes mutation denial to ACL rather than to the read-only transaction, and the plan does not record the over-privilege as a residual risk owned by Database/security. PA35 explicitly avoided this trap with `forbiddenQueriesStayOutsideProductionSqlWithoutPretendingOwnerColumnAcls` (`OperationsIvrSessionReadRoleLeastPrivilegeIT.java:98-101`).
- **直接证据**:

  - `V004__catalog_order_and_payment.sql:426-438` — `UPDATE` grants.

  - `V004__catalog_order_and_payment.sql:421-422` — schema `USAGE`.
  - `OperationsIvrSessionReadRoleLeastPrivilegeIT.java:98-101` — established "no pretending owner column ACLs" convention.
- **影响**: The implementation agent writes an impossible/vacuous ACL test, the success signal "ACL" is not actually proven, and the plan's evidence overstates security. A real ACL probe would expose the over-privilege and could be mistaken for a PA37 regression.
- **建议改法和验证点**:

  4. Record "pre-existing `catalog_order_role` over-privilege; no PA37 grant change" as a residual risk owned by Database/security, with the existing PA36/PA25 ACL oracles as evidence.

### PA37-PLAN-A-04-未修复-中-List pagination SQL is under-specified: a root left-join with `limit+1` does not guarantee `limit+1` root products and can over-read or return short pages

- **位置**: Plan §5 product list query lines 210-227; plan §3 lines 102-105; plan §7 lines 306-317.
- **问题类型**: 架构边界 / 不可直接实施 / 状态机漏洞（分页）.
- **当前写法**: "The root query is `catalog_product` with a left join to `catalog_version` on `catalog_version.product_id = catalog_product.id`; order roots by `product_code ASC, product_id ASC` and version arrays deterministically by `version_no ASC, catalogVersionId ASC`. The adapter must not multiply product roots..." §3 says "Query `limit+1` products, retain at most `limit`"; §7 says "`limit=100` still fetches `101` root products, not `101` version rows."
- **反例/失败场景**: If the implementation follows the literal "left join" with `ORDER BY product_code, id, version_no, id LIMIT :limit+1`, the limit applies to joined rows. A product with three versions consumes three rows of the lookahead, so the page can contain fewer than `limit` products, `hasMore`/`nextCursor` can be wrong, and a continuation can skip products. If the implementation instead fetches all joined rows and groups in Java, it can read an unbounded version history for many products (over-read) and still must track distinct roots for the lookahead. A `LEFT JOIN` on `catalog_offer` with two channels duplicates each version unless a channel is chosen or the join is pre-aggregated/EXISTS. The plan states the outcome ("must not multiply") but not the query form that guarantees it.
- **为什么有问题**: The frozen page contract is over product roots. The plan's prescribed SQL shape does not establish a deterministic root page, and it leaves the implementation agent to invent a two-phase query. This is a correctness and over-read risk directly in the requested "owner-local SQL without row multiplication" area.
- **直接证据**:
  - Plan `:220-227` — left join root query and "must not multiply".
  - Plan `:102-105` — `limit+1` product semantics.
  - Plan `:311-314` — "`limit=100` still fetches `101` root products".
  - V004 `:112-115` — `uq_catalog_version_active` / `ix_catalog_version_product_status`; `:126` — `uq_catalog_offer_version_channel` (up to two channels per version).
- **影响**: Pagination can return short/duplicated pages, skip products, or over-read version/offer history; the implementation may appear to work on single-version fixtures and fail on multi-version products.
- **建议改法和验证点**:
  1. Specify the exact two-phase list read, preferably:
     - Root page: `SELECT id, product_code, product_family FROM catalog_order.catalog_product WHERE (product_code, id) > (:cursorProductCode, :cursorProductId) ORDER BY product_code ASC, id ASC LIMIT :limit + 1`;
     - Version page for the returned root IDs: `SELECT id, product_id, version_no, sale_status, offer_type, audience FROM catalog_order.catalog_version WHERE product_id IN (:rootIds) ORDER BY product_id ASC, version_no ASC, id ASC`.
     Both in the same transaction/snapshot. If a single-query form is chosen, use `WHERE id IN (SELECT ... ORDER BY ... LIMIT ...)` or an equivalent bounded form, never a bare root-left-join with one LIMIT.
  2. State explicitly whether `catalog_offer` is read at all (see A-05) and, if it is, use a pre-aggregated/EXISTS form that cannot drop or duplicate versions.
  3. Add tests with a multi-version product at the page boundary, `limit=1`, `limit=100`, an exact-boundary page, a last page, and a product with more versions than the lookahead.
- **修复风险**: 低.
- **严重程度**: 中.

### PA37-PLAN-A-05-未修复-中-The optional `catalog_offer` join/EXISTS is ambiguous and can hide valid DRAFT versions or produce a 503

- **位置**: Plan §5 lines 217-218, 224-226, 239-243; plan §4 lines 186-194; plan §10 detail/list assertions.
- **问题类型**: 契约缺失 / 过度设计 / 非最优方案.
- **当前写法**: "the minimum approved `catalog_offer` relation needed to enforce the catalog projection's offer/version relationship, if the current owner contract requires it"; "If an offer join is used, constrain it to the one-to-one `(catalog_version_id, channel)` relation or pre-aggregate/EXISTS it"; "The adapter may verify an existing offer relation through explicit keys/EXISTS, but must not return `catalog_offer.id`, `channel`, `offer_status`, or `version_token`."
- **反例/失败场景**: The frozen `CatalogProductVersionSummary` and `CatalogVersionSummary` have no offer-derived field; `offerType` and `audience` come from `catalog_version`. V004 does not require a version to have an offer: `catalog_offer` has a FK to `catalog_version` and a unique `(catalog_version_id, channel)`, but no reverse constraint. A DRAFT candidate may legitimately have no offer yet, and the frozen detail description explicitly includes draft candidates. If an implementation uses an inner join or an `EXISTS` filter to "enforce" an offer, a valid offer-less DRAFT version is dropped or treated as inconsistent (503). If it left-joins both channels, versions are duplicated. The docs15 wording "产品详情 + 版本/offer/权益摘要（含 DRAFT）" (`docs/15-production-openapi-surface-spec.md:121`) is not reflected in any frozen offer field, so "offer summary" is undefined.
- **为什么有问题**: The plan leaves a data-dependent include/exclude/503 decision to the implementation. That can violate the "all three version states" and "draft candidates" contract, and it invites an unnecessary read of an offer table whose sensitive columns (`version_token`, `offer_status`, `channel`, `id`) must not be exposed.
- **直接证据**:
  - Plan `:217-218, 224-226, 239-243`.
  - OpenAPI `:5606-5740` — no offer field in either summary DTO.
  - V004 `:117-132` — offer shape; `:507-510` — `fk_catalog_offer_version`; no constraint requiring an offer per version.
  - `docs/15-production-openapi-surface-spec.md:121`.
  - Plan `:191-193` — draft candidates and nullable `publishedAt`.
- **影响**: A correct DRAFT fixture can be hidden or turned into a 503; the list/detail can become data-dependent in a way the frozen contract does not allow; an implementation may read offer columns it does not need.
- **建议改法和验证点**:
  1. Decide explicitly that neither DTO requires `catalog_offer`; absence of an offer row is not an inconsistency and must not drop or fail a version.
  2. Remove the optional offer join/EXISTS from this plan, or define exactly what it enforces and prove it cannot drop a valid DRAFT/ACTIVE/OFFSALE version. If docs15's "offer summary" is meant to require an offer-derived field, stop and return to goal/contract confirmation — do not invent a field.
  3. Add a fixture with a DRAFT version that has no offer and assert it is returned with the exact DTO; add a version with both MINIAPP and WEB offers and assert no duplication (if offers are read at all).
- **修复风险**: 低.
- **严重程度**: 中.

### PA37-PLAN-A-06-未修复-中-§6 parses the request and resolves the key ring before the transaction/authority, contradicting PA35's authority-first precedence and Control's "existing sanitized precedence"

- **位置**: Plan §6 steps 3-6 lines 270-281; plan §3 error matrix lines 128-146; plan §10 authority assertions lines 409-425.
- **问题类型**: 最佳实践偏离 / 架构边界（authority timing）.
- **当前写法**: Step 3 parses/validates the request shape; step 4 resolves the cursor key-ring provider; step 5 executes the transaction; step 6 calls `OperationsReadContext.enter()` and reads server-derived employee authority.
- **反例/失败场景**: PA35's `DefaultOperationsIvrSessionReadService.execute` enters the transaction, calls `context.enter()`, calls `authority(caller)`, and only then invokes the read lambda that parses the request (`DefaultOperationsIvrSessionReadService.java:128-160`; list parse at `:50-55`). Its tests include `authorityPrecedesParsingAndOwnerDependencyResolution` and `missingOperationsMembershipFailsClosedBeforeParsing`. Under the catalog plan's fixed flow, an ACTIVE-but-DISABLED employee sending `?limit=bad` gets `422 VALIDATION_FAILED` instead of `403 FORBIDDEN`; sending `?cursor=` gets `400 CURSOR_INVALID`; with a missing/ambiguous key ring gets `503 SERVICE_UNAVAILABLE` before the authority check. A tampered cursor can also be rejected before the disabled check. This contradicts Control `:25` "unauthorized/disabled employees are rejected by the existing sanitized precedence". The §10 requirement to assert the role sequence "on every failure path" is also unachievable for pre-transaction 422/400/503 paths.
- **为什么有问题**: The plan claims to follow the PA34/PA35 shape, but its fixed sequence changes the established sanitized precedence and can reveal dependency state (missing ring) to callers who should receive 403. It also makes the role-sequence test requirement internally inconsistent.
- **直接证据**:
  - Plan `:270-281` — parse/ring before transaction/authority.
  - `DefaultOperationsIvrSessionReadService.java:128-160` — transaction → `enter()` → `authority()` → parse/read.
  - `OperationsIvrSessionReadRoleLeastPrivilegeIT.java:82-84` — `missingOperationsMembershipFailsClosedBeforeParsing`.
  - Control `:25` — "existing sanitized precedence".
- **影响**: Disabled employees can probe validation/dependency state; the frozen precedence is changed without a goal confirmation; the planned role-sequence assertions cannot cover the early failures; PA35-compatible tests/expectations may be inconsistent.
- **建议改法和验证点**:
  1. Align with PA35: resolve only the lazy service in the controller; open the one transaction; `enter()`; perform the server-derived authority check; then parse the request, resolve the key ring/cursor and call the owner reader inside the same transaction. This keeps `REPEATABLE_READ` and the one-snapshot guarantee.
  2. Alternatively, if the early-parse design is intentional, return to goal confirmation because it changes the binding "existing sanitized precedence", and explicitly test the new precedence and error matrix.
  3. Add tests: disabled/wrong-audience/missing-account callers with malformed limit, blank/tampered cursor and missing ring receive the authority code (403/401/503-as-defined) rather than 422/400/503 from parse/ring; ACTIVE ADMIN/OPS with the same inputs reaches the expected 422/400.
- **修复风险**: 低.
- **严重程度**: 中.
