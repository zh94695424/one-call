## Findings

### F-01 — Replay of a missing/immutable-violating purchase-consent reference is surfaced as a 409 client code, not 500 INTERNAL (Low; defensive branch, normally unreachable under DB integrity)

- Location: `backend/src/main/java/com/onecall/core/activation_consent/internal/purchase/DefaultPurchaseConsentService.java:29-31` (`validateReplay` → `validate(..., true)`), `:52-56`; `backend/src/main/java/com/onecall/core/activation_consent/internal/purchase/JooqPurchaseConsentRepository.java:64-66` (`describe(null)` → `Failure(REQUIRED)`); mapping at `DefaultCustomerOrderCreationService.java:40-48`.
- Triggering input: an existing `COMPLETED` PURCHASE idempotency record whose stored result points at an order whose `purchase_consent_id` has no corresponding consent row (or an immutable row that no longer matches its id). Replay request same key/subject/offer.
- Actual branch: `repository.consent(consentId)` → `null` → `describe(null,false)` throws `Kind.REQUIRED`; outer mapping returns `PURCHASE_CONSENT_REQUIRED` (409). A stored `DECLINE` action throws `Kind.DECLINED` (409); a replay identity divergence throws `Kind.CONFLICT` (409).
- Expected behavior: plan §3.1 step 6 / §4 / §3.3 — corrupt/unsupported **stored immutable replay facts** are `500 INTERNAL`; 409 is reserved for differences attributable to the current request. `request_fingerprint` already forces request-side subject/channel/event changes to 409 at `idempotency_begin`, so a validator-internal identity divergence is corruption.
- Actual behavior: corrupt stored consent is classified as a retryable client denial.
- Direct evidence: the replay validator receives `replay=true` but only uses it for `CONFLICT` vs `REQUIRED`; `action != ACCEPT` and `row == null` are replay-independent. Unit `PurchaseConsentServiceTests.declinedMismatchedAndConsumedConsentFailClosed` (`:62-68`) codifies 409/DECLINED in the replay-validator path.
- Impact: Low. `activation_consent.consent_record` has an immutability trigger (`V007__activation_and_consent.sql:189-190`) and `customer_order.purchase_consent_id` FK references it (`V007:311`), so this branch requires privileged DB tampering; the practical effect is a client-visible 409 where an integrity 500 is specified, which can push a caller to re-consent rather than surface corruption. No partial writes occur.
- Concrete fix: in `validate(...)`, when invoked by `validateReplay`, map a missing row / non-ACCEPT stored action / stored identity divergence to `Kind.INTEGRITY` (500) while keeping `CONFLICT`/`DECLINED` for NEW-time request semantics; pass the replay flag to `repository.describe`/`consent` or add a distinct `Failure(INTEGRITY)` for `consent == null`.
- Fix risk: Low. Touches one unit test expectation; must not change §3.1 step 7 NEW-reuse mappings (DECLINE/CONSUMED remain 409).

### F-02 — Unsupported non-string scalar types inside an approved `benefitLines` snapshot escape as 500 instead of the plan's 422 for unsupported NEW catalog input (Low)

- Location: `backend/src/main/java/com/onecall/core/catalog_order/internal/customerorder/CustomerOrderSemantics.java:118` (`UUID.fromString(line.get("lineKey").asString())`), `:121-123`, `:130-134` (`.asString()` on `entitlementType`/`validFrom`/`expiresAt`); only the initial `JSON.readTree` region `:98-100` converts failures to `invalid()`.
- Triggering input: an ACTIVE PERSONAL offer whose `catalog_version.snapshot` is structurally unsupported, e.g. `"lineKey": 5` (or an object), or a `schedule` window whose `entitlementType`/`validFrom` is a non-string node.
- Actual branch: `exact(...)` (`:116`) only checks key names, not value node types. `JsonNode.asString()`/`UUID.fromString` then throws an unchecked exception that is not translated to `invalid()`; it propagates out of `DefaultCustomerOrderCreationService.checkout`, is caught by the generic `catch (RuntimeException)` at `DefaultCustomerOrderCreationService.java:49-52`, and `JooqCustomerOrderRepository.translate(..., false)` returns `INTERNAL` (500).
- Expected behavior: plan §4 — "missing/unsupported approved input is `422 VALIDATION_FAILED` on NEW with zero delta"; `500` is for a structurally supported snapshot whose digest/row agreement is false.
- Actual behavior: zero delta is preserved, but the public classification is 500 rather than 422.
- Direct evidence: `terms(...)` (`:147-170`) performs exhaustive bounded type checks and maps to 422, but the sibling `benefitLines`/`schedule` extraction does not type-check before conversion. Neither the unit semantics tests (`approvedSchedulesMustMatchEveryLineAndInstallment`) nor the IT (`completeApprovedScheduleIsFrozenAndNeverComputed`) exercise non-string scalar types in a line/window.
- Impact: Low; a lawful full approved snapshot is well-typed, so this is corrupt/unlawful catalog input. It changes error classification/observability only, not atomicity.
- Concrete fix: validate `isString()` (and UUID-parseable `lineKey`) for every line/window scalar before conversion, throwing `invalid()` so unsupported NEW input is 422; keep `storedSnapshot`'s 500 wrapping for replay.
- Fix risk: Low; one helper change plus a semantics test case; must not relax the existing field/value equality checks.

### F-03 — Two test oracles can pass vacuously / assert too weakly (Low, test evidence)

- Location: `backend/src/test/java/com/onecall/archtests/container/CustomerOrderRoleLeastPrivilegeIT.java:72-73` — `entries.stream().filter(...).allSatisfy(...)`; `backend/src/test/java/com/onecall/archtests/container/CustomerOrdersIT.java:122-130` — `assertThat(received.get()).contains("left,right")`.

- Direct evidence: `allSatisfy` semantics; `contains` vs `isEqualTo`.
- Impact: Low evidence-quality risk only.
- Concrete fix: assert the filtered streams are non-empty and capture the expected pre-SQL statements; assert `received.get()` exactly equals the intended received representation (or assert `received.get().startsWith(" ")`/`endsWith(" ")` if the container is expected to preserve OWS, otherwise drop the OWS-preservation claim for the IT).
- Fix risk: Low; test-only; the report wording may need narrowing if the container trims OWS.
