- **问题类型**: 状态机漏洞 / 契约缺失 / 不可直接实施
- **当前写法**: §4 规定 detail root 缺失 = 404、认证后 digest 变化 = 400 CURSOR_FILTER_MISMATCH、未知编程/运行时失败 = 500，并要求「Reuse `OperationsSubjectReadService.Failure/Code` throughout」。计划没有说明 `Failure` 在新 service 与新 controller 里如何穿越，也没有指明应复制 PA33 还是 PA34 的写法。
- **反例/失败场景**: 实施 Agent 复制它被指示复用的 PA34 激活读取链（最贴近的两端点 GET 模板），得到两处 code-substituting switch：service 层 `catch (Failure known) { throw switch (known.code()) { … -> known; default -> new Failure(Code.INTERNAL); } }` 与 controller 层 `@ExceptionHandler(Failure.class)` 的同款 switch。PA34 的清单里没有 `NOT_FOUND`，也没有 `CURSOR_FILTER_MISMATCH`。于是 detail root 缺失返回 500 INTERNAL 而不是 404，changed-filter 游标返回 500 而不是 400 CURSOR_FILTER_MISMATCH — 两处同时违反 Goal Confirmation 的 binding errors 条款与 §4 自己的优先级表，且两层各犯一次。
- **为什么有问题**: 同一「reuse baseline」在两个兄弟服务里给出两种互不兼容的错误穿越语义：PA33 的 `DefaultOperationsSubjectReadService.java:168` / `:204` 是 `catch (Failure known) { throw known; }`，`OperationsSubjectReadController.java:80-83` 原样透传 code；PA34 的两处都把未列出的 code 折叠成 INTERNAL（`DefaultOperationsActivationReadService.java:60-63`、`OperationsActivationReadController.java:72-77`）。计划自称 complete / non-conditional / directly implementable，却把这个必须选边的决定留给实施 Agent；§8 没有任何静态身份断言新文件不含 code 折叠 switch，只有行为测试 (C14/D10/G16/G20) 能事后发现——那正是返工半径最大（D/G/C 三个家族同时改）的时机。
