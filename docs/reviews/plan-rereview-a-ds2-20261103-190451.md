### A-02 — unfixed — High — Existing read-only `25006` witnesses are not converted to a valid `42501` ACL-denial mechanic

- **位置 / Position**: Plan delta rows for `SharingQueryFixture` (line 67) and `SharingQueryServiceIT…` / `CustomerSharesFixture` (line 71); new-IT mechanics (line 85).
- **问题类型 / Problem type**: 测试缺口 / 并发恢复风险 / PostgreSQL semantics (validation mechanics and 42501/25006 separation).
- **当前写法 / Current wording**: `SharingQueryFixture` is "Migration assertions only"; the existing tests must "Replace the claim that the query role has an authorized write blocked by read-only mode with ACL denial"; expected result "Query role unauthorized writes/foreign reads produce `42501`". The new-IT rule says all expected `42501` attempts occur in writable transactions.
- **反例/失败场景 / Counterexample**: `SharingQueryFixture.java:267-270` executes `UPDATE sharing.evidence_share_grant SET revision = revision + 1` inside the production **read-only** pool and records the SQLSTATE; `SharingQueryServiceIT.java:317-319` asserts `25006`. `CustomerSharesFixture.java:331-340` explicitly sets `connection.setReadOnly(true)`, `SET LOCAL ROLE sharing_role`, then executes the same update and asserts `25006`; `CustomerSharesIT.java:236-239` calls it. In PostgreSQL 16 the read-only transaction check for DML is performed in `standard_ExecutorStart` before the executor permission check, so an update that is both unauthorized and inside a read-only transaction still raises `25006`, not `42501`. Changing only the expected SQLSTATE to `42501` fails; leaving it at `25006` passes but no longer proves ACL denial, contradicting the plan's expected value.
- **为什么有问题 / Why it matters**: The plan correctly separates the mechanics for the **new** IT (writable `42501`, authorized read-only `25006`), but the existing fixture delta is internally inconsistent: it tells the implementer to replace the claim with ACL denial while also declaring `SharingQueryFixture` migration-only and without moving the probe to a writable transaction. This is exactly the implementation-time decision the prior B-05 finding required the plan to settle.
- **直接证据 / Direct evidence**: `SharingQueryFixture.java:267-270`; `SharingQueryServiceIT.java:317-319`; `CustomerSharesFixture.java:331-340`; `CustomerSharesIT.java:236-239`; plan lines 67, 71, 85. The plan's new-IT mechanics themselves state the writable-transaction requirement, confirming the ordering risk.
- **影响 / Impact**: The implementation gate either goes red on these CI-pinned tests or keeps a `25006` assertion that no longer separates authorization from transaction mode. The query role's `42501` write denial would be proven only in the new IT, not in the existing suite, which weakens the exact delta the plan claims.
- **建议改法和验证点 / Suggested fix and validation**: Keep the production read-only test as a `25006` witness but state it proves read-only mode, not authorization; add a separate **writable** query-role probe against `sharing.evidence_share_grant` (e.g. `UPDATE … SET revision = revision + 1`) expecting `42501`, isolated by a savepoint. Update the `SharingQueryFixture`/`CustomerSharesFixture`/`SharingQueryServiceIT` rows accordingly and state the expected SQLSTATE for each transaction mode.
- **修复风险 / Fix risk**: Low–Medium (small fixture/test change, but ordering semantics must be stated).
- **严重程度 / Severity**: High.

### A-04 — unfixed — Low–Medium — Catalog assertions do not pin `coalesce(acl, acldefault(...))` / default-ACL treatment, so PUBLIC/default ACLs can be invisible

- **位置 / Position**: Plan `New integration-test mechanics` (lines 83–84).
- **问题类型 / Problem type**: 测试缺口 / 最佳实践偏离 (catalog evidence completeness).
- **当前写法 / Current wording**: "Use direct `has_schema_privilege`, `has_table_privilege`, `has_column_privilege` with explicit role names and `aclexplode` over `pg_class.relacl`, `pg_attribute.attacl`, `pg_namespace.nspacl`, `pg_proc.proacl`, plus catalog membership. … Compare exact grants including grantor/grantee/privilege/grantable; include PUBLIC."
- **反例/失败场景 / Counterexample**: When a catalog ACL column is `NULL`, `aclexplode(NULL)` returns no rows. An empty-set assertion ("no unexpected grantee", "no PUBLIC") then passes vacuously, even though PostgreSQL's implicit default ACL (`acldefault`) may grant PUBLIC privileges on a function/schema. The existing proven pattern at `PostgresContainerIT.java:5052-5066` uses `aclexplode(coalesce(acl, acldefault(type, owner)))` precisely for this reason. The revised plan does not state the `coalesce/acldefault` requirement, so the prior B-08 finding is only partially closed.
- **为什么有问题 / Why it matters**: Exact catalog evidence must distinguish "no ACL rows" from "no privileges"; otherwise the new IT can report a false green for PUBLIC/default EXECUTE/USAGE. `has_*_privilege` covers effective rights, but the exact grantor/grantable/PUBLIC comparison still needs the default ACL representation.
- **直接证据 / Direct evidence**: `PostgresContainerIT.java:5052-5066` (existing `coalesce(acl, acldefault('n'/'r'/'c'/'f', owner))` pattern); plan line 83; prior B-08's requirement.
- **影响 / Impact**: A vacuous denial assertion could hide an unintended PUBLIC or default grant; the exact-ACL proof is weaker than the plan claims.
- **建议改法和验证点 / Suggested fix and validation**: Pin `aclexplode(coalesce(acl, acldefault('r'|'c'|'n'|'f', owner)))` (or an equivalent `acldefault`-aware query) for every catalog class, and state the expected empty-set semantics for NULL ACLs. Keep `has_*_privilege` for role-effective positives/negatives.
- **修复风险 / Fix risk**: Low.
- **严重程度 / Severity**: Low–Medium.
