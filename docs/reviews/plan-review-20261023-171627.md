## Findings

### F-10-未修复-[中]-Customer task endpoints use IVR decision reason codes as Problem codes, contradicting the plan's own global Problem-code rule

- **位置**: Plan C6 L350; C8 L352; §4.6 L222; §9.2 Problem row L677; §9.3 rule 3 L691; docs/14 stable IVR reason registry L220.
- **问题类型**: 契约一致性 / RFC 9457 registry / 校验不可实施 / 跨面语义.
- **当前写法**: C6 returns 409 `TASK_CONFLICT`/`CALL_IN_PROGRESS`/`TASK_UNAVAILABLE`; C8 returns 409 `TASK_CLAIMED`/`TASK_CONFLICT`. The plan's Problem assertion says `CONFIRMATION_NOT_ALLOWED`/`TASK_CONFLICT`/`CALL_IN_PROGRESS` must not be Problem codes (L677/L691), and §4.6 states `CONFIRMATION_NOT_ALLOWED` is no longer a Problem code. F-04 removed `TASK_CONFLICT`/`CALL_IN_PROGRESS` from the IVR 409 paths and from the Problem registry. The representative Problem table does not define either code.
- **反例/失败场景**: An implementer adds C6/C8 error codes to `x-onecall-error-codes`; `onecall/problem-complete` rejects the document because the codes are prohibited. If they omit the codes, C6/C8 have undocumented 409 responses and generated clients cannot map them. If they substitute different codes, the inventory, docs/15 and tests disagree with the plan. The same document cannot satisfy both C6/C8 and the global rule.
- **为什么有问题**: A single `ProblemCode` enum/registry is the accepted contract; the plan itself forbids these A0 IVR decision reasons as HTTP Problem codes after F-04. Reusing them on the customer surface reintroduces the exact cross-surface confusion F-04 was intended to remove.
- **直接证据**: Plan L350/L352 vs L677/L691; L222; docs/14 L220 lists `TASK_CONFLICT`/`CALL_IN_PROGRESS` in the IVR reason registry; fix-1 L42 states F-04 removed them from IVR 409 and the Problem registry.
- **影响**: S3 cannot pass `npm run check` if the rule is implemented as written; customer task creation/cancellation have no valid stable error contract; generated clients and QA cannot distinguish IVR decisions from customer transport conflicts.
- **建议改法和验证点**: Define customer-surface stable Problem codes for these cases (for example `ACTIVE_CALL_CONFLICT` and `TASK_STATE_CONFLICT`), or explicitly scope the prohibition to IVR surfaces and add the customer codes to `ProblemCode`, `x-onecall-problem-registry`, docs/15 and C6/C8. Add a negative test that C6/C8 never emit `TASK_CONFLICT`/`CALL_IN_PROGRESS` as Problem codes, and a positive test for the replacement codes.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-11-未修复-[中]-The four DRAFT candidate operations map `platform.idempotency_record` without an approved A0 scope or A0 transaction

- **位置**: Plan O18 L385, O19 L386, O20 L387, O21 L388; §4.7 L274-275; §7.1 L529; §9.3 rule 1 L689; docs/14 L222 and T-S2-14 L3340-3349.
- **问题类型**: A0 映射 / 幂等契约 / 不可直接实施 / 范围边界.
- **当前写法**: O18-O21 use `Idempotency-Key` 1-128 and their `x-onecall-a0-models` includes `platform.idempotency_record`. §4.7 gives candidate natural unique keys `(product_id, version_no)` and `(campaign_key, version_no)` but does not name a platform idempotency scope. §7.1 says the DRAFT group has no new A0 transaction. A0 states the platform idempotency scope registry is exactly `IVR_CONFIRM` and `PURCHASE`; T-S2-14 only publishes an already-existing DRAFT/never-published candidate and does not define draft create/replace.
- **反例/失败场景**: The implementer calls `platform.idempotency_begin` with a new scope such as `CATALOG_DRAFT`/`TRIAL_POLICY_DRAFT`; this silently adds an A0 scope not in the accepted contract. Alternatively the implementer reuses `PURCHASE`/`IVR_CONFIRM`, colliding with order/IVR keys. If the implementer instead relies only on the natural unique key, the `Idempotency-Key` header has no stored fingerprint, so same-key/different-content behavior is undefined and `x-onecall-a0-contracts` cannot be populated from any accepted A0 transaction.
- **为什么有问题**: A1 must not invent A0 scopes, tables or transactions; the success signal requires a stable write identity and direct A0 mapping. The F-06 fix adds the operations but leaves their idempotency persistence/contract anchor ungrounded. A static exact-name check will pass while the semantic mapping is false.
- **直接证据**: Plan L385-388 (platform table), L274-275 (Idempotency-Key/natural key), L529 (“不新增 A0 事务”); docs/14 L222 (“scope registry remains exactly `IVR_CONFIRM` and `PURCHASE`”); docs/14 L3347/L3349 require a pre-existing candidate for publication and define no create/replace transaction.
- **影响**: S2's four new operations are not safely code-generation-ready; an implementer must choose between an unapproved A0 scope, an invalid mapping, or an undefined replay rule. The S2 completion report cannot honestly claim exact A0 transaction coverage.
- **建议改法和验证点**: Choose one bounded resolution before S2: (a) obtain a controller/A0-approved platform scope plus the draft create/replace transaction/state; or (b) remove `platform.idempotency_record` from O18-O21 and define create idempotency as the natural unique key plus a canonical content fingerprint, with same-content replay and changed-content conflict; keep replace state-conditional on `expectedRevision`. Update §4.7, `x-onecall-idempotency`, `x-onecall-a0-contracts`, docs/15 and S2 tests; add negative tests for a new unapproved scope and for same-key/changed-content.
- **修复风险（低/中/高）**: 中.
- **严重程度（低/中/高/严重）**: 中.

### F-12-未修复-[低]-`listOperationsSubjects` is the only resource list without a stable sort and filter-bound cursor

- **位置**: Plan O1 L368; §4.8 L288-294; §1.3 item 7 L59; §9.2 cursor row L680; docs/12 L283.
- **问题类型**: Cursor 契约 / 分页完整性 / 测试缺口.
- **当前写法**: O1 returns `SubjectPage` with `cursor/limit` and server-side filtering, but gives no stable sort keys or filter digest. §4.8 lists deterministic sorts for C2, C9, C11, C13, C16, O5, O6, O8, O12, O15 and O17, but not operations subjects. O1 also does not name `CURSOR_INVALID`/`CURSOR_FILTER_MISMATCH` in its specific error set.
- **反例/失败场景**: The implementation chooses `created_at` only, a UUID order, or database order; page boundaries can duplicate or skip subjects as statuses change. A cursor created under one status/source filter can be reused against another result set because no filter digest is bound. QA has no stable contract to assert.
- **为什么有问题**: Success signal #7 requires every resource list to have stable sort fields, `nextCursor`/`hasMore`, no offset and fail-closed invalid cursors. F-07 corrected exactly this class for C9; O1 remains the same class of incomplete resource list.
- **直接证据**: Plan L368 vs L288-294 and L59; docs/12 L283 requires stable sorting and cursor pagination.
- **影响**: One operations list is not implementation-ready; pagination behavior is inconsistent with the other lists; generated clients and QA cannot rely on a deterministic order.
- **建议改法和验证点**: Add a deterministic sort such as `createdAt desc, id desc` (A0 `business_subject.created_at` exists) or a stable subject ID order, bind the normalized status/source filter digest into the cursor, and add `CURSOR_INVALID`/`CURSOR_FILTER_MISMATCH` to O1's error set. Add duplicate/skip tests across subject state changes.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### F-13-未修复-[中]-The final 49-count versioned-path rule is not slice-aware while S1/S2 require `npm run check` to pass with smaller counts

- **位置**: Plan §9.3 rule 8 L696; §9.2 surface counts L666; S1 validation L606; S2 validation L619; S3 validation L632; S1 allowed files L602.
- **问题类型**: Slice 验证 / 静态校验可复现性 / 停止条件.
- **当前写法**: `onecall/versioned-paths` asserts customer=18, operations=21, ivr=6, public-share=3, provider-callback=1, total=49. `contract-rules.mjs` is created in S1. S1 validation requires `npm run check` exit 0 and expects customer=7/operations=7/total=14; S2 expects customer=11/operations=21/total=32. The plan neither parameterizes rule 8 by slice nor explicitly defers it to S3. If rule 8 is implemented as written in S1, S1/S2 lint fails on counts; if it is omitted until S3, S1/S2 do not prove versioned paths/counts, and the plan does not say the rule is final-only.
- **反例/失败场景**: S1/S2 implementation stops at `npm run check` despite all S1/S2 operations being correct, or an implementer weakens/removes the count assertion to make S1/S2 pass. The final S3 validation may then be the first proof of F-09, while S1/S2 reports claim path coverage that was never checked.
- **为什么有问题**: The slice principle requires each slice's validation to be independently reproducible and to justify its stop condition. A final-only assertion placed in the shared rule set without slice awareness makes the declared validation sequence internally inconsistent.
- **直接证据**: L696 vs L606/L619; L666 states per-slice counts; L602 allows creation of `contract-rules.mjs` in S1; no text says rule 8 is S3-only or accepts expected counts.
- **影响**: S1/S2 cannot satisfy the stated check or F-09 is unproven until S3; implementation agents face an ambiguous validation decision that can mask a path regression.
- **建议改法和验证点**: Parameterize rule 8 with the expected surface counts for the current slice (S1 7/7/0/0/0, S2 11/21/0/0/0, S3 18/21/6/3/1), or explicitly mark rule 8 final-only and add per-slice prefix/versioned-path assertions. Add tests that each slice's expected counts pass and a final-only mismatch fails.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.
