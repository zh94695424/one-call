### F-PR5-01 (Minor) — two construction-guaranteed summary fields survive F-AGG-01 and are asserted by fixtures

- **Entry point:** `security/validate.mjs` `STAGE_CONFIG` `:49-86`; `machineSummary()` `:2653-2665`; fixture assert steps (≈14 across ≈13 fixtures).
- **Defect:** for all three stages `config.forbidden` is `[]` (`:54`, `:66`, `:78`), so the `s2s3Sections` counter — which increments only when `config.forbidden.includes(key)` (`:2660-2665`) — is construction-guaranteed `0` for every possible input. Similarly `futureInvariantPattern` is the always-empty-string regex `/$^/` at every stage (`:57`, `:69`, `:81`), so `futureInvariantIds` counts only empty-string projected values and can never count a future invariant id (`:2657`). Both are pinned as `0` by many fixture assert steps (e.g. `sec-s2-04:175-177`, `sec-s1-06:86-88`, `sec-s3-08:304-306`).
- **Trigger:** any fixture assert step that includes `futureInvariantIds`/`s2s3Sections`.
- **Impact:** this is the same class of vacuous evidence F-AGG-01 removed — the two fields cannot fail, so fixture assertions on them prove nothing. Not a fail-open: the real premature-future protections are the exact invariant count/text checks (`:3014-3029`), the INV-A3-22+ string scan (`:3033-3037`), fixture string guards (`:3639-3650`) and top-level premature-section detection (`:2885-2905` → `stage_field_premature`), all of which remain live. `futureFixtureIds` (`:2658-2659`) is live by contrast.
- **Fix (suggested):** either wire `forbidden` to the actual later-slice section names per stage (making `s2s3Sections` discriminative), or remove the two fields from `machineSummary` and drop the corresponding fixture assert keys — mirroring the F-AGG-01 remedy. `futureFixtureIds` may stay.
- **Risk if unfixed:** future readers/mutations may treat the fixture zeros as proof of stage isolation that those fields do not provide; a later refactor could also silently make them non-zero without a real defect.
- **Severity:** Minor.

### F-PR5-02 (Minor) — provider nonce uniqueness is keyed by bare nonce, not `(serviceIdentity, nonce)`, diverging from the frozen policy and the IVR path

- **Entry point:** provider callback path `security/validate.mjs:1787-1790` (`state.providerNonces.has/add(nonceValue)`); contrast IVR path `:1688-1692` (`${mtls.serviceIdentity}:${nonceValue}` into `state.nonceSeen`); frozen policy `EXPECTED_NONCE_POLICY.uniqueness = '(serviceIdentity, nonce)'` `:303` (mirrored in model `security-design-v1.json` `noncePolicy.uniqueness`).
- **Defect:** the provider path enforces uniqueness on the bare nonce string only, while the frozen policy and the IVR path both scope uniqueness by service identity.
- **Trigger:** two provider callbacks from different `serviceIdentity` values reusing the same nonce string; today the machine would reject the second as `NONCE_REPLAY` even though policy treats the pair as distinct.
- **Impact:** machine-vs-policy drift in the reference evaluator. Currently unobservable because only the single `provider` identity is simulated (A1 provider operation count = 1; `EXPECTED_AUTH_DOMAINS` op counts 18/21/6/3/1), so behavior is equivalent under today's fixture set. A future multi-identity provider fixture would expose a false replay denial. No security fail-open in the opposite direction (the machine is stricter than policy for the one live identity).
- **Fix (suggested):** scope the provider nonce set the same way as IVR — key on `${serviceIdentity}:${nonceValue}` (or a composite) — one-line change plus, optionally, a two-identity discriminator fixture if/when a second provider identity exists.
- **Risk if unfixed:** latent false-replay if a second provider identity is ever simulated; inconsistency between the two transport paths weakens the reference machine as an executable projection of the frozen policy.
- **Severity:** Minor (latent; no current fixture exposure, stricter-than-policy not weaker).

### F-PR5-03 (Minor) — `Q15` cited for mTLS cert TTL / vendor signature window but absent from the 23-row deferred registry and mismatched to the A0 Q15 definition

- **Entry points:** `docs/17-production-security-design-spec.md:327` (C03 `ttlInput` Q7/Q15), `:329` (C05 Q6/Q15), `:366` ("vendor signature 算法、canonicalization、payload 字段与窗口全部 Q6/Q15"), `:700` (`R-A3-MTLS-CAPABILITY` Q7/Q15), `:701` (`R-A3-PROVIDER-VERIFY` Q6/Q15); model `security/v1/security-design-v1.json:356` (`"ttlInput": "Q7/Q15"`), `:378` (`"ttlInput": "Q6/Q15"`), `:524-527` (`"deferred Q6/Q15"` ×4 for vendorAlgorithm/Canonicalization/Payload/Window).

- **Trigger:** a reader or later owner following `Q15` from any of the seven citation sites for cert TTL or vendor window is routed to the wrong A0 open input; the residual rows name an input the A3 deferred map does not track.

### F-PR5-04 (Minor) — doc and model still state an unrestricted masked-variant allow; only the validator enforces the safe-class allowlist (reimplementation divergence risk for F-S3-R1-01)

- **Entry points:** human contract `docs/17:524` ("masked 变体（如 `calleeNumberMasked`）允许" — no safe-class restriction); machine model `security/v1/security-design-v1.json:1901` (`"maskedVariantsAllowed": true` — boolean, no class list); contrast executable contract `security/validate.mjs:937` (`MASKED_DISPLAY_SAFE_CLASSES = new Set(['PHONE','IDENTITY_NUMBER','LEGAL_NAME'])`), classifier `:939-949`, fail-closed for non-safe/unknown masked keys at `:1005-1007`, shared by support-view `:2530`; durable negatives `sec-s3-06:313-369` (`capabilityTokenMasked`/`randomMasked` blocked) and `sec-s3-07` support-view denials. - **Defect:** after F-S3-R1-01 the executable contract restricts masked display to three classes, but both the canonical doc and the machine model still state an unrestricted "masked variants allowed" rule.
- **Trigger:** a reimplementation (or a later refactor) that follows only doc+model as the source of truth can reintroduce the Medium fail-open F-S3-R1-01 closed — any `*Masked` key (e.g. `capabilityTokenMasked`) treated as display-safe.
- **Impact:** contract-divergence residual, not an open fail-open in the current executable path (validator + fixtures are authoritative and enforce the allowlist). Severity rises to Medium only if doc/model are treated as the sole implementation source.
- **Fix (suggested):** add to `docs/17:524` and model `redactionPolicy` an explicit safe-class list (e.g. `maskedDisplaySafeClasses: ["PHONE","IDENTITY_NUMBER","LEGAL_NAME"]`), stating that any other `*Masked` key follows unknown-field fail-closed.
- **Risk if unfixed:** latent reintroduction of the F-S3-R1-01 class of defect by any consumer that trusts doc/model over the validator.
- **Severity:** Minor (executable path closed; documentation/model lag).
