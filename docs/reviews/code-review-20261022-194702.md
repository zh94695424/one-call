### F-01 — 未修复 — 高 — S2 cross-module SELECT grants are unusable without schema USAGE

- **Entry/function**: S2 IVR resolve/confirmation/direct authorization, catalog order creation, activation/issuance reads; any S2 runtime role executing a declared cross-module `SELECT`.
- **File (line)**: `docs/14-production-data-model-and-flyway-schema-spec.md:2953-2966` (§10.12 preamble and schema grants), `:3001-3022` (cross-module `SELECT` grants), `:2863-2866` (S1 schema `USAGE`) and `:3246` (V006 grant step).
- **Trigger/input**: `ivr_role`, `catalog_order_role`, `activation_consent_role` or `entitlement_metering_role` reads `customer_iam`, `organization_access` or `subject_number` columns that the specification explicitly grants.
- **Actual branch**: The S2 grant matrix grants schema `USAGE` only on `platform`, `audit` and the four S2 schemas. The S1 grant matrix grants `organization_access` `USAGE` only to `customer_iam_role`/`subject_number_role` and `customer_iam` `USAGE` only to `subject_number_role`. No S2 role receives `USAGE` on `customer_iam`, `organization_access` or `subject_number`; V006 step 3 repeats only `entitlement_metering`/`platform` `USAGE`.
- **Expected behavior**: PostgreSQL requires `USAGE` on the containing schema in addition to the table/column privilege. Every S2 role that reads a cross-module table must receive the schema `USAGE` without `CREATE` in the owning wave.
- **Actual behavior**: The declared cross-module `SELECT` grants fail with schema permission denial. The IVR access/activation/entitlement predicates, order access checks and issuance reads cannot run under the specified least-privilege roles.
- **Direct evidence**: `:2961-2964` lists S2 schema `USAGE` (`catalog_order`, `ivr`, `entitlement_metering`, `activation_consent`); `:2865-2866` lists S1 schema `USAGE` only for the S1 roles; `:3001-3022` grants `ivr_role`/`catalog_order_role`/`activation_consent_role`/`entitlement_metering_role` `SELECT` on S1 tables; `:3246` grants V006 `USAGE` only on `entitlement_metering` and `platform`.
- **Impact**: Core S2 transactions cannot execute as specified; an implementer must guess or widen grants, violating the owner boundary. This is a code-generation/privilege feasibility blocker, not a runtime-verified claim.
- **Suggested fix and verification**: Add exact `GRANT USAGE ON SCHEMA customer_iam, organization_access, subject_number TO <the exact S2 roles that read them>` without `CREATE`, in each role's creation wave (V004 for the four roles; cross-read additions in V004-V007), and update the §10.12 grant matrix and the V004-V007 steps. Add a privilege assertion to T-S2-41 that each S2 role can execute its declared reads and still cannot write another module's table. Do not grant table writes.
- **Fix risk**: 低 (schema `USAGE` only; no table write).
- **Severity**: 高.
