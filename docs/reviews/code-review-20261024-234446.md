## Findings

### F-PR-01 `[低]` Optional `ClaimResult.acceptedAt` has no A0 column name, no docs/15 §3.5 mapping, and disagrees with sibling `ClaimSummary.verifiedAt` for the same `subject_claim.verified_at` fact

- **Entry point / location**: `components.schemas.ClaimResult` (`api/openapi/1.openapi.yaml:4554-4570`), returned by `createCustomerSubjectClaim` 200 (`:504-509`). `acceptedAt` is optional `date-time` (`:4568-4570`); it is not in `required: [claimId, status, subjectId]` (`:4557`). Sibling `ClaimSummary.verifiedAt` is also optional `date-time` (`:4821-4823`) on the list projection of the same table.
- **Input scenario**: A client reads `ClaimResult.acceptedAt` on a 200 from `createCustomerSubjectClaim`, or a future edit makes it required; a server implementer maps it to a column.
- **Actual branch**: A0 `subject_number.subject_claim` has no `accepted_at` column; the accepted-claim decision timestamp is `verified_at`, nullable and non-null exactly for `ACCEPTED` (`docs/14-production-data-model-and-flyway-schema-spec.md:899`, check `ck_claim_verified_shape` `:907`). The accepted plan lists `acceptedAt?` under `ClaimResult` mapped only as “A0 `subject_claim`” without naming a column (`docs/gateflow/a1-production-openapi-surfaces-spec-plan.md:459`). docs/15 §3.5 documents the `TrialPolicyDraft.createdAt` removal and the exact `declaredAt`/`completedAt` renames but does **not** document an `acceptedAt` mapping (`docs/15-production-openapi-surface-spec.md:165-169`). `client-compat.ts` has no assertion on `acceptedAt` or `verifiedAt` (grep empty). No prior review artifact adjudicates this field.
- **Expected**: By the standard the aggregate fix-1 established for `declaredAt`/`completedAt` (docs/15 §3.5) and for removing unowned timestamps, every public response timestamp must either carry its A0 column name or have an explicit documented rename mapping. When two wire projections expose the same A0 fact, they should use one name or document the split.
- **Direct evidence**: YAML `:4554-4570,4804-4823,504-509`; A0 `docs/14:899,907`; plan `:459`; docs/15 `:165-169`; `client-compat.ts` (no claim-timestamp assertions). Contrast: `RecordingDeclaration.declaredAt` / `RecordingCompletion.completedAt` are explicitly mapped in docs/15 §3.5 (`:168`) and `TrialPolicyDraft.createdAt` was removed with a negative pin; `acceptedAt` received neither treatment.
- **Impact**: Optional today, so not a hard wire break and weaker than the closed F-02 (which was a required field with no A0 column at all). But the field name invites an implementation to invent wall-clock time or map to the wrong column, and the `ClaimResult.acceptedAt` vs `ClaimSummary.verifiedAt` split means two public names for one A0 fact with no documented ownership. A future requiredness change would escalate this to the F-02 class.
- **Suggested correction / fix direction**: Either (a) rename `ClaimResult.acceptedAt` to `verifiedAt` to match A0 and `ClaimSummary`, (b) keep the name and add an explicit docs/15 §3.5 mapping `acceptedAt <- subject_number.subject_claim.verified_at` with a contract-rule pin and a `client-compat` assertion, or (c) remove the optional field entirely as unneeded for the create response. Prefer (a) or (b); do not make it required without a named A0 column.
- **Verification / fix risk**: Very low; optional field rename/removal/mapping plus regenerated types and one docs/15 line. No wire status, error-set, stage or trust-boundary change.
- **Severity / classification**: 低; `accepted` (documentation/ownership gap; controller adjudication required before any fix pass).

No other material finding is raised against the current composed interface. The adversarial pass did not reopen F-01..F-07 and did not identify a new correctness, ownership, protocol-boundary, error-inventory or generated-client defect beyond F-PR-01.

## Read-Filter Exception Verification (aggregate fix-2)

The adjudicated predicate is implemented exactly at `contract-rules.mjs:2601-2606`:

```js
function isApprovedReadFilterParameter(operation, method, parameter) {
  if (method !== 'get' && method !== 'head') return false;
  if (parameter.in !== 'query') return false;
  const digest = operation?.['x-onecall-filter-digest'];
  return Array.isArray(digest) && digest.some((filter) => filter === parameter.name);
}
```

`validateParameterTrust` skips only the top-level trusted-fact rejection under that predicate (`:2636-2641`). Adversarial challenge results (all closed):

| Challenge | Result | Evidence |
| --- | --- | --- |
| Write methods (POST/PUT/PATCH/DELETE) | closed | `:2602` rejects anything not literally `get`/`head` before digest lookup; digest-bound write probe `:3263-3271` requires rejection |
| Path/header/cookie locations | closed | `:2603` requires `in === 'query'` with no normalization; digest-bound path/header/cookie probes `:3272-3297` |
| Unbound query name | closed | `:2605` requires `Array.isArray(digest) && digest.some((f) => f === parameter.name)`; unbound probe `:2299-3306`; `validateCursorListings` independently requires digest↔parameter bidirectionality (`:993-998`) |
| Nested trusted properties inside an approved filter | closed | Exception applies only to top-level name check; nested walk `:2649-2664` unconditional; nested probe `:3307-3322` |
| Forbidden secrets | closed | `FORBIDDEN_PROPERTY_NAMES` check `:2642-2644,2657-2659` has no exception predicate; digest-bound `objectKey` probe `:3324-3338` |
| Digest membership equality | closed | Strict `===` per element; no coercion, case folding or prefix matching; `Array.isArray` guards fake digests |
| Path-item parameter inheritance | closed (code path) | Digest read from `operation`, never `pathItem` (`:2604`); path-item `paymentStatus` inherited by sibling POST is rejected by the method conjunct |
| Canonical surface | confirmed | Only trusted-name parameter in the whole YAML is O15 `paymentStatus` (`onecall-v1.openapi.yaml:2182`), digest-bound `['subjectId','paymentStatus']` (`:2169-2171`) and order-exactly pinned (`contract-rules.mjs:1029-1038`); no other trusted-name parameter exists |
