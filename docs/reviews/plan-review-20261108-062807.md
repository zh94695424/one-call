### 3-未修复-高-查询形状不能按计划可靠区分 `Missing` 与 `Unavailable`

- **位置**: Plan §"Query, mapping, failure behavior", line 27.
- **问题类型**: 契约缺失 / 不可直接实施 / 状态机漏洞
- **当前写法**: "starting from `evidence_record er`, join artifact `a` on `a.evidence_id=er.id`, then media object `m` ..., for `CALL_RECORDING`, join recording `r` ... Filter `er.id=?` and `a.artifact_role='ORIGINAL'`. ... A genuinely absent evidence id returns `Missing`; an existing evidence row with no valid original artifact returns `Unavailable` (distinguish with an existence check in the same query result/left join, not a second transaction)."
- **反例/失败场景**: Three realistic rows produce zero rows with the stated inner-join/WHERE-filter shape: (a) the evidence row exists but is `PENDING`/`QUARANTINED`/`FAILED`, so a `WHERE er.status='SOLIDIFIED'` filter removes it; (b) the evidence row is `SOLIDIFIED` but has no `ORIGINAL` artifact; (c) the artifact exists but no matching validated recording exists, so an inner join on `recording` removes it. A literal implementation maps all three to `Missing` because it sees zero rows, while the plan requires `Unavailable`. Even a left join does not help if `a.artifact_role='ORIGINAL'` or `er.status='SOLIDIFIED'` is placed in `WHERE` rather than the `ON`/post-fetch validation.
- **为什么有问题**: `Missing` versus `Unavailable` is part of the public reader contract and will drive PA19's user-visible denial/retry behavior. The plan gives an ambiguous join shape and does not state where status/role filters are evaluated, so the implementation agent must guess; the two possible guesses produce different observable results.
- **直接证据**: Plan line 27; V008 `evidence_record` status shape (lines 110-171) and the `uq_evidence_original_artifact` partial index (lines 194-196); V008 `recording` status/media state shape (lines 56-102).
- **影响**: PA19 may map a corrupted/incomplete evidence row to "not found" instead of "unavailable", weakening fail-closed behavior and producing wrong test assertions; the reader IT (zero-artifact case) will expose the defect only after the implementation has already chosen a shape.
- **建议改法和验证点**: Specify the exact query: `SELECT ... FROM evidence.evidence_record er LEFT JOIN evidence.evidence_artifact a ON a.evidence_id=er.id AND a.artifact_role='ORIGINAL' LEFT JOIN evidence.media_object m ON m.id=a.media_object_id LEFT JOIN evidence.recording r ON r.id=er.source_ref_id AND r.media_object_id=m.id WHERE er.id=?` (or an equivalent one-query shape). Fetch at most two rows; if zero rows, `Missing`; if the evidence row exists but any of `er.status`, `er.source_type`, `a`, `m`, `r`, `r.status`, duration or media linkage is null/mismatched, `Unavailable`; if more than one row, `Unavailable`. Add explicit IT cases for `PENDING`, no-artifact, missing-recording and mismatched-media.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 4-未修复-高-不必要地授予 `bucket`/`object_key`/`object_version_id`，违反“最小列”约束

- **位置**: Plan §"First-principles decisions" decision 3, line 19; §"PostgreSQL privilege proof requirements" line 79; §"Risks and ownership" line 108; public DTO/decision 5 line 21.
- **问题类型**: 范围漂移 / 过度设计 / 安全边界
- **当前写法**: V013 grants `evidence.media_object(id, bucket, object_key, object_version_id, sha256, size_bytes, mime_type)`. The plan says the location columns "are necessarily readable by this dedicated evidence capability to resolve the opaque reference" and the positive ACL probe must read "exact media columns including location columns".
- **反例/失败场景**: The stated query returns only `ResolvedMediaObject(UUID mediaObjectId, String sha256, long sizeBytes, String mimeType, Integer durationSeconds)`. It does not return or use bucket, key or version. The opaque reference is `media_object.id`; the location values are unused by the DTO, by the reader contract and by the PA19A non-goals (no streaming/range/transport). The dedicated role therefore receives a read capability for private location facts that the unit does not need. If the dedicated credential or its datasource is ever misused, or if future code logs a row, the extra grant expands the blast radius beyond the confirmed goal.
- **为什么有问题**: The Control requires "exactly the minimum evidence schema/table/column read privileges needed for one object-resolution query" and "give PA19 only opaque resolved-object facts and safe bounded metadata, never bucket/key/version". Granting location columns contradicts both the minimum-privilege requirement and the validated media object's own DTO boundary; the plan's necessity claim is false for the described query.
- **直接证据**: Plan lines 19, 21, 79, 108; `ResolvedMediaObject` field list (plan line 21); V008 `media_object` columns (lines 19-51); existing `JooqShareableEvidenceProjectionReader` reads only `sha256`, `size_bytes`, `mime_type`, `validated_duration` and never location columns.
- **影响**: Over-broad credential and an avoidable security regression; the "least privilege" proof becomes a proof of a broader grant than the goal authorizes; PA19 future streaming work will need a separate scoped decision anyway.
- **建议改法和验证点**: Remove `bucket`, `object_key`, `object_version_id` from the V013 grant, the query, and the positive ACL probe. Keep only `id`, `sha256`, `size_bytes`, `mime_type` on `media_object`. If PA19 later needs location facts, that belongs to the PA19 gateway slice with its own goal confirmation. Verify with a negative probe that the reader role cannot select any location column.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open questions

1. **Replay-safe V013**: V012 is explicitly replay-safe (`SharingAdmissionRoleLeastPrivilegeIT.v012CreatesExactAdmissionRoleAndIsReplaySafe`). Should V013 use a `DO` precondition / conditional role creation and be manually replayable, or is Flyway's one-time execution sufficient? The plan does not state the exact role-creation/grant SQL.
2. **Grantor and `SET LOCAL ROLE`**: V012 grants evidence columns under `SET LOCAL ROLE evidence_owner`. Should V013 do the same so the recorded grantor is the owner, and should its postconditions assert grantor/owner consistency? The plan says "catalog assertions" but not the grantor mechanism.
3. **Role attribute completeness**: The plan lists the main attributes but does not mention `rolconnlimit=-1`, `rolvaliduntil IS NULL`, `rolconfig IS NULL`, `pg_shdepend`, or default ACL checks that V012 asserts. Are these part of the exact proof?
4. **Hash consistency**: The reader returns `media_object.sha256` but does not read or compare `recording.validated_sha256`; the plan also does not compare `recording.call_id`/subject with the evidence record. Is `source_ref_id`'s service-validated immutability considered sufficient, or should the reader cross-check these facts?
5. **Datasource binding location**: The allowlist has no `application-persistence.yml` (or equivalent) entry. Is the new `onecall.evidence-media-read.datasource.*` configuration expected to be supplied only through external environment properties, or should a resource file be added/updated?
6. **PA19 mapping of `Unavailable`**: The plan chooses `Unavailable` for non-`SOLIDIFIED` evidence, missing artifacts and inconsistent facts. Is PA19 expected to map all of these to one external failure mode, and is `Missing` reserved only for a nonexistent evidence id? This should be explicit before implementation.

- **Dedicated role secret provisioning**: The role is created with no password and must be provisioned out of band. Owner: deployment/database operations; destination: PA19A deployment runbook after plan/implementation authorization; no secret/config deployment is part of this unit.

Owner: PA19 implementation/review; destination: PA19 architecture review; consider package-private bean access/qualifier discipline.
- **Docker/PostgreSQL 16 availability**: Environmental; Docker unavailability must fail, not skip. Owner: implementation/CI runner; destination: `-Pcontainer-smoke verify`.
- **CI XML reports absent in the frozen checkout**: Current XML arithmetic is not measurable here. Owner: implementation agent; destination: exact Maven run and CI inventory in the implementation report.
- **V013 replayability and grantor**: If the project expects manual replay safety, the migration must be idempotent. Owner: Evidence implementation; destination: V013 test design/open question 1-2.
- **Potential hash/call/subject cross-check**: If the service-validation guarantee is not considered sufficient for a read path, an additional column grant and check would be needed. Owner: Evidence implementation; destination: future evidence integrity slice, not PA19A scope expansion.

## Conclusion

**fail**

The plan is not code-generation-ready at the plan gate. The blocking evidence is concrete: (1) the exact path allowlist omits two Failsafe files with hardcoded `hasSize(12)` assertions and under-enumerates `PostgresContainerIT`'s migration/role inventory; (2) the Failsafe include list is explicit, the plan leaves `backend/pom.xml` conditional, and the named Maven command omits `-Pcontainer-smoke`, so the planned PostgreSQL proof may not run; (3) the stated query shape cannot reliably distinguish `Missing` from `Unavailable` for non-solidified, artifact-less or recording-less evidence; and (4) V013 grants unused location columns, contradicting the minimum-column and opaque-fact boundary. The `ai_orchestration` narrowing and incomplete CI baseline/line-scan arithmetic are additional material risks. These are plan-fixable, but the current artifact should not be handed to an implementation agent unchanged.
