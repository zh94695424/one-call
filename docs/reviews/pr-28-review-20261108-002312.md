## Residual Risk

- **Production provider absent (accepted plan residual)**: the only production `ShareMediaCredentialProvider` bean is `UnavailableMediaCredentialProvider`, whose inherited default `issueOrReplay` returns `Unavailable`; the new endpoint therefore always fails closed with 503 in the shipped application until a provider is supplied. Owner/destination: Sharing backend + Platform/Security production integration. The PR alone does not deliver an operational media-authorization path.
- **Provider determinism / replay guarantee (accepted plan residual)**: the 200 replay guarantee ("same `authorizationRequestId` + same purpose returns the first credential") and identical-payload `REUSED_IDENTICAL` depend on the external provider honoring `eventId` idempotency; no credential digest is stored (intentional per plan A08). A non-idempotent provider would yield 503 conflicts on replay and could return a fresh credential with the first durable expiry. Owner: Sharing backend/provider integration + Platform/Security; verify before production provider activation.
- **Concurrency residuals (A R-A18-06, deferred-with-owner)**: concurrent first calls with the same request key and different purposes can both pass the admission-scoped pre-provider lookup and append both purpose events; a partial provider outage can append both a SUCCESS and a FAILURE. Sequential replay/outage tests do not close this. Owner: Sharing backend/provider integration + Platform/Security.
- **Durable-failure DB outage (B-R-03, deferred-with-owner)**: if the database is unavailable while appending the deterministic FAILURE, the row cannot be guaranteed; the request still stays fail-closed 503. Owner: Sharing persistence/backend + Platform database reliability.
- **Binding/risk TOCTOU**: `readCurrentBindings` (`DefaultShareMediaAuthorizationService.java:155`) and `readSubjectRisk` (`DefaultShareMediaAuthorizationService.java:162`; `JooqShareAdmissionRepository.java:82-89`) are separate READ_COMMITTED statements without a binding-row lock; a binding retired or risk opened between them (or after the check, before provider I/O) can be authorized at decision time. Impact is bounded by decision-time semantics and the credential/session TTL; the same pattern exists in PA17 admission. Owner: Sharing backend, if policy requires an explicit binding/risk lock for atomicity.
- **Replay-after-expiry observability**: replaying an existing success after the provider credential expiry fails closed 503 but, because `priorSuccess != null`, appends no FAILURE event; repeated expired replays are unaudited. Owner: Sharing backend/observability, if audit parity is required.
- **Unbounded repeated authorization**: distinct `authorizationRequestId`s are distinct semantic requests and can append unbounded success events/credentials for the admission until session expiry; no 429 rate limiter is implemented (429 is declared in OpenAPI). Owner: Platform edge/Sharing, if abuse policy requires a cap.
- **Unavailable production policy/secrets**: Q22 TTL/skew/revocation/signing/Redis/media-provider values remain unavailable and fail closed; media gateway/COS/object resolution/streaming/range/buffered-byte recall remain outside PA18. Owners: Security/Platform/Sharing production integration; media delivery work unit.
- **Verification gaps**: unit tests use mock repositories and a deterministic fake provider; PostgreSQL IT is real but does not exercise a real Redis or media gateway; the two-connection test bounds transaction/lock behavior only. No external CI or GitHub check was observed. The frozen manifest/hash and LF/whitespace claims were not independently recomputed.
- **Contract residual**: `SHARE_GENERATION_STALE` remains the only listed 409 business code and is overlaid for request-identity conflicts; this is the documented contract-forced overload, not a generation-staleness claim.
