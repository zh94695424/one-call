### PA37-PLAN-REREVIEW-A-01-未修复-中-`deniesAdvisoryLock` cannot prove database denial: advisory locks are allowed in a read-only transaction and `catalog_order_role` can execute the built-in function

- **位置**: Plan §5, `OperationsCatalogProductReadRoleLeastPrivilegeIT` method list (line 175: `deniesAdvisoryLock`) and ACL ownership paragraph (lines 186-194: "`deniesForUpdate`, `deniesDdl`, and `deniesAdvisoryLock` retain lock/DDL coverage").
- **问题类型**: 测试缺口 / 契约缺失 / 过纠正.
- **当前写法**: The plan mandates a container IT identity `deniesAdvisoryLock` alongside `deniesInsertByReadOnlyTransaction`, `deniesUpdateByReadOnlyTransaction`, `deniesDeleteByReadOnlyTransaction`, `deniesForUpdate` and `deniesDdl`, and describes these as "lock/DDL coverage" attributed to read-only/trigger behavior.
- **反例/失败场景**: A test that runs `SELECT pg_advisory_xact_lock(...)` (or `pg_advisory_lock`) under `SET LOCAL ROLE catalog_order_role` in the read-only `REPEATABLE_READ` transaction succeeds. PostgreSQL's read-only guard covers DML (`INSERT/UPDATE/DELETE/MERGE`), `SELECT ... FOR UPDATE/SHARE`, and DDL; a plain `SELECT` calling an advisory-lock function is not a read-only violation. `pg_catalog.pg_advisory_xact_lock` is executable by `PUBLIC`, and V014 does not revoke that; docs14 `:3065` even notes that runtime roles receive explicit EXECUTE if a deployment revokes `PUBLIC`, confirming advisory functions are intended to be callable. A test expecting `42501` or `25006` therefore fails, while a test expecting success contradicts the method name and the plan's "denial" claim.
- **为什么有问题**: The plan says tests must be exact and behavior-bearing and claims ACL/lock denial is proven. An unsatisfiable container test with an exact identity cannot be reconciled with the mandated inventory; the implementation agent must either violate the plan or ship a failing/void assertion. PA35 avoided this: `OperationsIvrSessionReadRoleLeastPrivilegeIT.readOnlyTransactionRejectsAllDmlAndLockingQueries` (`:94-96`) tests only INSERT/UPDATE/DELETE/FOR UPDATE → 25006, and its plan says "read-only rejects DML", never advisory denial. The static scan `OperationsCatalogProductReadBoundaryTests.rejectsWritesAndLocks` already excludes `pg_advisory` from production source, so a DB denial claim adds no proof.
- **直接证据**:
  - Plan §5 lines 175, 186-194.
  - `backend/src/test/java/com/onecall/archtests/container/OperationsIvrSessionReadRoleLeastPrivilegeIT.java:94-96` (DML/FOR UPDATE only, 25006).
  - `docs/14-production-data-model-and-flyway-schema-spec.md:3065` (advisory built-in callable by runtime roles).
  - `backend/src/main/resources/db/migration/V014__database_runtime_acl_rbac_hardening.sql` does not revoke `pg_catalog` EXECUTE; V004 grants no restriction on advisory functions.
- **影响**: Deterministic PostgreSQL16 IT failure or a vacuous test; the exact container inventory 36/592 cannot be truthfully produced; the ACL success signal overstates what the database proves.
- **建议改法和验证点**: Keep the 16-method inventory and the existing identity if possible, but redefine `deniesAdvisoryLock` as a behavior-bearing "no advisory lock is used/held" assertion (e.g., after a list/detail read, assert `SELECT count(*) FROM pg_locks WHERE pid = pg_backend_pid() AND locktype = 'advisory'` is 0, or assert the production reader source has no `pg_advisory`), or rename it to `assertsNoAdvisoryLocks` and update the CI dictionary. Do not claim `42501`/`25006` for advisory locks. Add a note that read-only defends DML/DDL/FOR UPDATE but not advisory locks, and keep `deniesForUpdate`/`deniesDdl` as real denial probes.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### PA37-PLAN-REREVIEW-A-02-未修复-中-The cursor frame has no key identifier and no stated key-selection rule, so it cannot be shown to preserve the shared ring's rotation semantics or the `rejectsMissingAndRetiredKeys` behavior

- **位置**: Plan §4 cursor framing (lines 111-117) and `OperationsCatalogProductCursorCodecTests` method list (line 166: `rejectsMissingAndRetiredKeys`); plan §1 "shared cursor key ring".
- **问题类型**: 契约缺失 / 状态机漏洞（key rotation） / 不可直接实施.
- **当前写法**: The cursor frame is fixed as "version byte, purpose byte, 4-byte big-endian limit, 16-byte request-digest prefix, 16-byte UUID, one-byte UTF-8 code length, UTF-8 product code, then a 12-byte nonce, ciphertext, and 16-byte tag." No key identifier is included, and the plan does not state whether the codec uses only the active key or tries every key in the shared ring.
- **反例/失败场景**: The shared `OperationsSubjectReadProperties.Cursor` allows up to three keys with an active key (`OperationsSubjectReadProperties.java:23-36`). PA35's codec puts a version byte, key-id length and key id in the envelope header (`OperationsIvrSessionCursorCodec.java:87-90`) and its IT proves that after rotation an old cursor still pages while the old key remains in the ring, and is rejected once the key is removed (`OperationsSubjectReadsIT.java:191-216`). A PA37 codec with no key id can only use the active key (invalidating every outstanding cursor at rotation, contrary to the shared ring's purpose) or try all keys (possible, but then the AAD cannot include a per-key header, and the plan must say so). The test name `rejectsMissingAndRetiredKeys` is undefined until this is pinned.
- **为什么有问题**: The plan claims "exact cursor framing" and "reuses the shared cursor key ring" and requires a retired-key test. The frame as written has no mechanism to select a retired-but-still-valid key; this is either a silent behavior regression from PA35 or an under-specified implementation decision that the implementation gate must invent.
- **直接证据**:
  - Plan §4 lines 111-117; plan §5 line 166.
  - `OperationsSubjectReadProperties.java:23-36` (up to three keys, active key).
  - `OperationsIvrSessionCursorCodec.java:55-90` (key-id header and AAD).
  - `OperationsSubjectReadsIT.java:191-216` (rotation continuity and retired-key rejection).
- **影响**: Outstanding cursors break across key rotation, or the codec silently diverges from the shipped ring; the `rejectsMissingAndRetiredKeys` test may be tautological or unsatisfiable; key delivery remains an unowned implementation decision.
- **建议改法和验证点**: Either (a) add the PA35-style key identifier to the frame (e.g., 1-byte id length + 1..32-byte id before the nonce, with the id bound in the AAD), or (b) explicitly state "active-key-only" semantics and remove/redefine the retired-key test. In either case state the AAD components (purpose, endpoint, sort, key id) and prove the worst-case frame length still produces `<= 512` base64url characters for a 64-character code (the current plaintext is 1+1+4+16+16+1+64 = 103 bytes; 12+103+16 = 131 bytes → 175 characters, so there is ample room). Update the codec test to cover a cursor from a retired ring key and a wrong-purpose cursor.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

## 7. Final plan review conclusion

**fail**

The binding goal, the one-S1-slice shape, the two exact routes/DTO families, authority-first precedence,
the shared datasource/transaction/context/key-ring reuse, the no-write boundary, the nine prior accepted
findings and both fix1-intake closures are all verified in this snapshot:
the plan is largely code-generation-ready and the inventory arithmetic is self-consistent
(`89/848 + 36/592 = 125/1,440`, scan 1,441, Failsafe 34→36, all-POM includes 36→38, manifest 291→299).

It still should not be handed to implementation without a bounded plan-text fix because:

- **A-01 (Medium, blocking)**: `deniesAdvisoryLock` cannot prove database denial — advisory locks are
  allowed in a read-only transaction and `catalog_order_role` can execute `pg_advisory_xact_lock`; the
  exact IT identity would fail or become vacuous.
- **A-02 (Medium)**: the "exact" cursor frame has no key identifier and no key-selection rule, so it
  cannot be shown to preserve the shared ring's rotation semantics or to make
  `rejectsMissingAndRetiredKeys` meaningful.
- **A-03/A-04/A-05 (Medium/Low)**: the plan's CI-literal and historical-subtraction wording is
  partially contradictory or only present in fix2; the "global Failsafe includes" label misstates the
  POM facts; the test paths/FQCNs, reader registration, configuration annotations, exact authority
  SELECT and digest recipe are not pinned.
- **A-09 (Low)**: the "not nonexistent privilege denial" sentence is imprecise for DELETE, which has
  no V004 grant (read-only masks it as 25006).

These are plan-text corrections, not a redesign. No OpenAPI, migration, grant, role, datasource, pool,
key-ring, product-source or later-gate change is needed or authorized. After a bounded fix closes
A-01/A-02/A-03/A-04 (and the low-precision items), a fresh independent re-review should be able to
accept the plan. This artifact records a review only; it does not accept the plan, authorize
implementation, or perform any stage, commit, push, PR, comment, approval, mark-ready, reviewer-request,
merge or close action.
