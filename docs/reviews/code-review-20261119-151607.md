## Findings

### PA38-AGGB-01 — Medium (documentation truth: the accepted `PA38-AGG-REV-03` Outbox "uniqueness error" backstop is contradicted by the frozen schema)

- Evidence. `docs/gateflow/pa38-operations-catalog-sale-lifecycle-implementation.md:18` states the durable replay backstop is "advisory lock + post-lock state short-circuit + unique `platform.outbox_event(event_domain, dedupe_key)` … an Outbox uniqueness failure rolls both back", and `docs/gateflow/pa38-operations-catalog-sale-lifecycle-aggregate-deepreview-fix-1.md:40` is stronger: "a duplicate paired Outbox raises a uniqueness error and rolls back the transaction, including its audit append." The frozen schema does the opposite for a duplicate: `backend/src/main/resources/db/migration/V001__platform_schemas_roles_idempotency_outbox_audit.sql:344-351` inserts with `ON CONFLICT (event_domain, dedupe_key) DO NOTHING`, then `:357-369` re-selects the existing row `FOR UPDATE` and, when `payload_sha256` is equal (`:367-368`), simply `RETURN v_id` — no error, no abort, no rollback; only a *different* payload raises `OUTBOX_DEDUPE_CONFLICT` P0001 at `:371`. Two consequences follow directly: (1) `uq_outbox_domain_dedupe` can never surface SQLSTATE `23505` through this function, so the `23505`/`40001` recovery classifier in `backend/src/main/java/com/onecall/core/catalog_order/internal/operationscommand/DefaultOperationsCatalogSaleCommand.java:27-30` is only ever triggered by `uq_catalog_version_active` on the catalog row, never by the Outbox dedupe key; and (2) `JooqCatalogSaleLifecycleRepository.java:184-187` discards the function's returned id, so Java cannot distinguish "new outbox row" from "silently skipped duplicate" at all. Branch `codex/pa38-next-work-unit`.
- Impact. An accepted remediation's stated safety property is over-claimed. In the hypothetical state that layers 1–2 fail to prevent (lock loss plus a state-machine miss), PA38 would commit a second, unpaired `audit.audit_fact` while the Outbox row is silently skipped and the HTTP call still returns 200 — i.e. the exact "unpaired audit writer" condition that the text claims the unique index would roll back. Reachability today is nil, which is why this is Medium and not High: the product advisory lock (`…Repository.java:110`), the post-lock replay/conflict short-circuit (`:119-122`), the revision CAS (`:129-131`) and `ck_outbox_payload_sha256` ordering all prevent it, and the 38 live IT identities exercise the preventions. The defect is in the *attribution of the guarantee*, and it is precisely the "audit-correlator versus Outbox dedupe boundary" this gate was asked to verify.
- Fix direction. Documentation-only in the next authorized doc write: restate the third layer as "`platform.outbox_append` is idempotent-on-identical-payload (`ON CONFLICT DO NOTHING` + `payload_sha256` compare); it rolls the transaction back only on a payload *mismatch* (P0001), and never raises a uniqueness error, so duplicate audit pairing is prevented by the advisory lock and the post-lock state machine alone, not by the unique index." Add one residual line with an owner (Platform/Operations + Backend): "silent identical-payload Outbox skip leaves an unpaired audit fact undetectable from Java; pairing detection would require comparing `payload_sha256` or verifying a newly inserted row in a later slice." Do not add an index, migration or V019 — `PA38-AGG-REV-03` forbids it and `OperationsCatalogVersionRoleLeastPrivilegeIT.java:44-45` proves the 18-migration/no-V019 boundary.
- Fix risk. Zero product risk (two gateflow documents plus the residual table). Two constraints: editing any file under `backend/src/main/**` would move the 310-file manifest digest and reopen the just-closed `PA38-AGG-FIX1-PIN-01` lockstep, so the correction must stay inside `docs/gateflow/**`; and the `32`-path candidate aggregate `e7ab6038…` intentionally includes `…-implementation.md`, so the custody table must be re-emitted with whatever listing method the Controller declares authoritative (see PA38-AGGB-03).
