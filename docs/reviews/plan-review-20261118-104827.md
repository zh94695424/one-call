### RR2-02-未修复-中-writable path inherits the 4-connection read pool with no enforced statement/lock bound and no residual classification
- **位置**: plan §2.3 `:71`, §6.1 `:183,194`, §6.2 (advisory lock `docs/gateflow/pa38-operations-catalog-sale-lifecycle-plan.md:202`), §12 residuals table `:499-505`
- **问题类型**: 过度耦合 / 最佳实践偏离 / 并发恢复风险 / open question 未收敛
- **当前写法**: Writes are bound to the existing LO pool ("Adding a manager/template is not adding a pool") with template `timeout 5 seconds`, and the recovery reread is described as a fresh transaction with a "5-second timeout"; §12 lists pool/contention nowhere.
- **反例/失败场景**: Two administrators publish versions of one product while Operations reads are busy. The loser blocks inside `SELECT pg_advisory_xact_lock(...)` (and later on the `uq_catalog_version_active` speculative lock) with **no** client-side query timeout and **no** server-side `statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout` provisioning. Spring's `TransactionTemplate.setTimeout(5)` is applied only to statements prepared via `DataSourceUtils.applyTransactionTimeout`, which jOOQ never calls; the shipped DSL `Settings` set `executeLogging`, `ParamType`, `StatementType` only. Each blocked publication holds one of only four `operations-subject-read` connections (`setMaximumPoolSize(4)`, `setConnectionTimeout(3000)`), so concurrent subject/activation/IVR/catalog-product reads start failing with sanitized `503` — and the new fixture's `TERMINATE_BEFORE_ROLE_RESTORE`/eviction cases shrink that same shared pool further.
- **为什么有问题**: The plan turns an Operations **read** surface into a write-contention tenant while claiming "one pool is not a coupling change", and does not record the availability trade-off as an owner-classified residual. The shipped architecture deliberately keeps writes on their own Hikari pool (`OperationsLifecyclePersistenceConfiguration.java:29-52`, default max 10) and the shipped read path deliberately bounds itself (`OperationsReadContext.java:38-40`: `statement_timeout 2000ms`, `lock_timeout 250ms`, `idle_in_transaction_session_timeout 5000ms`) — the new writable path inherits neither bound. Pool reuse itself is mandated by the Goal Confirmation, so this is not a scope objection; the defect is the unbounded wait plus the un-recorded coupling and the aspirational "5 seconds" wording that an implementation agent will read as an enforced bound.
- **直接证据**: `OperationsSubjectReadPersistenceConfiguration.java:76-81`; `OperationsReadContext.java:38-40`; `OperationsLifecyclePersistenceConfiguration.java:29-52`; grep for `statement_timeout|lock_timeout|idle_in_transaction` across `backend/src/main`, `backend/ops`, `deployment`, `security`, `api` returns only the read context; plan `:71,183,194`.
- **影响**: 状态不一致 / 读接口 503 雪崩 / 风险后移 / §12 分类不完整 / 实施 Agent 依据错误假设省略 timeout 语句
- **建议改法和验证点**: Decide and state one of: (1) issue the same bounded `SET LOCAL statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout` on the writable command transaction (safe with the existing guard, because `SET LOCAL` reverts before the close-time baseline probe), and extend the closed failure mapping so SQLSTATE `55P02`/`57014` have an explicit outcome instead of falling through to `INTERNAL` 500; or (2) keep the unbounded path and add an explicit §12 residual ("catalog publication shares the four-connection Operations read pool; write contention can starve Operations reads") with an owner plus one IT observation proving read availability while a publication holds the advisory lock. In both cases correct "timeout 5 seconds" / "5-second timeout" to describe what is actually enforced.
- **修复风险（低/中/高）**: 中 (touches SQL sequence and the closed code table, or requires an IT observation plus residual text)
