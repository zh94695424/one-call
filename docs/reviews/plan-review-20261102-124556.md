### 5. Custom cursor wire format, 512 bound and canonical validation — necessary, correct, safe

The design is contract-driven, not invented. `api/openapi/onecall-v1.openapi.yaml:4022` freezes the cursor as "bound to the stable sort and **normalized filter digest**", `docs/15-production-openapi-surface-spec.md:260` requires binding the stable sort keys, the last record's internal sort value and the normalized filter summary, `docs/15…:182` defines `CURSOR_INVALID` as covering unparseable/tampered/cross-context reuse, and `docs/15…:249` fixes `listCustomerShares`' domain code set to exactly `CURSOR_INVALID` — which is why the plan correctly does **not** introduce `CURSOR_FILTER_MISMATCH` (`docs/15…:183`). Necessity of the exotic encoding is arithmetic, not taste: V009's `CHECK (length(share_id) BETWEEN 1 AND 128 …)` (`V009__sharing.sql:35-36`) counts characters, so a legal 128-code-point ID can be 512 UTF-8 bytes, and naive UTF-8+base64url would be ≈683 characters against the frozen 512 ceiling (`…yaml:4356`); 21-bit fixed-width scalars give `46 + ceil(21·128/8) = 46 + 336 = 382` bytes → `ceil(4·382/3) = 510` characters ≤ 512, re-derived here and exact. Decoding is bounded before parse ("at most 384 bytes after enforcing wire length"), canonical-only by re-encode equality with pad-bit/trailing-byte/padding/alphabet rejection, scalar domain enforced (no surrogates, ≤ U+10FFFF, no NUL, non-all-space), and the decode rule set mirrors PA10's live `validate()` predicates (`CustomerShareQueryService.java:71-91`: default 20, 1-100, codePointCount 1-128, `replace(" ","").isEmpty()`, NUL, UTF-8-encodable, `nano % 1000`, UTC year −4712..294276 with `DateTimeException` → `CURSOR_INVALID`), so client-supplied and internally-derived anchors are judged by one rule set. Safety posture is right and explicitly stated: unkeyed fingerprint, "not an integrity-signed token", scope always re-derived from the principal and repository predicates, account/organization never decoded as authority (`ShareCursor` is reconstructed from the *caller*), a within-scope forged anchor can only mis-paginate and can never escape the creator predicates, and the cursor is never logged. Changing limit while keeping the cursor is correctly allowed since limit is excluded from the binding. `hasMore=true` uses PA10's last-returned-row cursor, not the lookahead row, which matches the service's actual construction and its `hasMore == nextCursor.isPresent()` invariant.

## Findings

- **F-B-01 (Medium) — §2 and §5 state two different positions for the malformed-selection 503.** Plan line 34 (§2) puts the rejection of a non-null structurally invalid selected workspace *inside* `CustomerBearerAuthenticator.authenticate`, which `CustomerBoundaryFilter.java:53` runs **before** Accept negotiation; plan §5's order line instead lists "trusted selection (503)" as step **(4)**, i.e. after "existing Accept negotiation (500 if incompatible/malformed)" at step (3), and the §5 table attributes "malformed trusted selection" to the same 503 row without a position. For the single combined input (valid bearer, structurally invalid selection, unacceptable Accept) the two readings give 503 versus 500. No §8 method pins that combination: §8.1#2 pins audience-401-before-selection-503, §8.2#2 pins verifier-shape failures, §8.2#9 pins Accept-vs-authenticated-success. Because the code layout naturally implements §2, the risk is that the *binding artifact* documents the other order and the implementation silently diverges. Destination: plan author/controller — one canonical precedence sentence (recommend "selection structure is validated inside `authenticate`, hence at §5 step (2); §5 step (4) denotes only the shares adapter's null-selection rejection"), and the assertion folded into an existing §8 method so the frozen 67/92/159 inventory is untouched.
- **F-B-02 (Medium) — `/me` acquires a new 503 failure mode that the goal line calls "unchanged".** Control line 21 requires "existing `/me` behavior … remain unchanged", yet §2's authenticator-level selection check is shared by both routes, so `GET /api/v1/customer/me` served by a verifier that returns a structurally invalid non-null selection now returns 503 where PA11 returned 200. §2's `/me` paragraph does not mention it, and §8.2#7 (`meRemainsCompatibleWithLegacyAndSelectedSessions`) exercises only null, PERSONAL and now-inaccessible-ORGANIZATION selections — all structurally *valid*. Reachability is limited to a test-owned verifier (no production verifier exists), and fail-closed is the safer direction, so this is a goal-boundary precision issue rather than a defect. Destination: plan author — either state the `/me` 503-on-contract-violation response explicitly as an intentional, controller-signed delta and pin it with one assertion, or narrow the structural rejection to the shares adapter so `authenticate` stays behavior-identical for `/me`. Reviewer B prefers the second as the smaller goal delta.
- **F-B-03 (Low) — the conditional record-local `@JsonInclude(ALWAYS)` is unnecessary; measure it instead of hedging.** §4 requires "always serialize exactly `items`, `nextCursor`, `hasMore`; explicitly include nextCursor even when null using a property/record-local ALWAYS annotation **if necessary**". Destination: Backend/API at implementation — record the measured behavior, keep §8.1#6 as the normative wire assertion, and add the annotation only if the assertion fails; a redundant annotation is harmless but should be a decision, not a guess.
- **F-B-04 (Low) — §8.2#6 does not name the mechanism for the 25006 proof.** "Sharing own permitted write attempted within query read-only transaction gives 25006" describes the app's own transaction, which runs on the sharing pool inside `CustomerShareQueryService` with `PROPAGATION_REQUIRES_NEW` and pool size 1 in tests, and exposes no hook through which a test could execute SQL inside it without touching production sources (the sharing-side bans also rule out an `ExecuteListener`). Destination: Backend/QA at implementation — assert `NamedInterfaces` explicitly; no plan change required.
