### 1-[Low]-`readsAuthorityWithoutLocking`'s non-empty guard can be satisfied by harness setup statements, so the negative oracle still does not prove the `publish` call emitted SQL

- **Finding class**: residual test false-green / oracle shape (no product defect).
- **Files(lines)**: `backend/src/test/java/com/onecall/core/catalog_order/internal/operationscommand/CatalogSaleLifecycleRepositoryTests.java:22-24`; harness setup `:63-90`; statement capture `:72-83`; `@BeforeEach` at `:20`.
- **Input scenario**: any future regression in which `repository.publish(...)` stops recording/executing statements while `readsAuthorityWithoutLocking` still runs.
- **Actual branch**: line 24 is `publish(null, 1); assertThat(statements).isNotEmpty(); assertThat(statements).allSatisfy(...)`. But `statements` is already populated before the test body: the `@BeforeEach setup()` (`:20`) calls `initialize()` (`:63`), which calls `repository.begin()` (three `SET LOCAL …` via `dsl.execute`, plus `identity()` and the limits `dsl.fetchSingle`) and `repository.catalogRole(witness)` (`SET LOCAL ROLE`, `identity()`). Every one of those is appended to `statements` by the stubs at `:66-72`. Therefore `isNotEmpty()` is true independently of the `publish(...)` call, and if `publish` recorded zero statements the `allSatisfy` would still iterate the setup statements (none containing `EMPLOYEE_ACCOUNT`, `OPERATIONS_IAM.` or `FOR UPDATE`) and pass.
- **Direct evidence**: `initialize()` is run for every test at `:20`; the `dsl.execute`/`dsl.fetchSingle` stubs unconditionally `statements.add(sql)` (`:66-72`); `readsAuthorityWithoutLocking` does not capture a `statements.size()` mark before `publish(null, 1)` and does not assert any publish-specific statement.
- **Impact**: no behavioural defect today — all 12 repository tests and the 10 semantics tests are green per the fix2/fix3 evidence, and the forbidden-token assertions are exact. The residual risk is that the accepted fix's literal requirement ("assert the statement list is nonempty before `allSatisfy`") is met while its intent (non-empty *publish* evidence) is still not guaranteed, so this specific oracle could decay to a no-op without a red signal. The other eleven repository tests pin concrete statement sequences and would catch most such regressions.
- **Fix direction**: mark the list before the call and assert the tail, e.g. `int mark = statements.size(); publish(null, 1); assertThat(statements.subList(mark, statements.size())).isNotEmpty();` and apply the negative `allSatisfy` to that tail (or assert `contains("SELECT ...FROM catalog_order.catalog_version...")`). Identity- and count-preserving; no product change.
