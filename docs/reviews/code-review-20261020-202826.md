# Code Review

## Findings

### A-01 - Unfixed - High - Missing EVIDENCE event records survive import and permit double consumption

- **Entry point / function**: `B.snapshot`, `B.loadReviewSnapshot`, `replayEvent`, and `consumeTrial` in `shared/onecall-business.js`.
- **Files / lines**: `shared/onecall-business.js:317-344`, `:437-473`, `:512-532`, `:568-569`, and `:617-624`; current related tests at `shared/qa/business.test.js:567` and `:712`.
- **Expected behavior**: A locally metered evidence delivery must have durable, one-to-one idempotency ownership. Removing an event record from an imported snapshot must either invalidate the snapshot or leave enough durable provenance for redelivery of the same event ID to replay the original result without consuming more trial allowance.
- **Actual behavior**: Validation checks every event record that exists and checks evidence references, but it does not check the reverse relationship from a locally metered evidence item to exactly one EVIDENCE event. Evidence items do not retain their event ID. A snapshot with the EVIDENCE record deleted is therefore accepted, and the next delivery of that event ID is treated as new.
- **Direct evidence**: A confirmed IVR session consumed event `EVIDENCE-DELIVERY` for 60 seconds. After export, deleting only `processedEvents.EVIDENCE['$EVIDENCE-DELIVERY']` left both `snapshot(candidate)` and `loadReviewSnapshot(candidate)` at `OK`. Redelivering the same event changed usage from 60 to 120 seconds and evidence count from one to two, with two evidence IDs.
- **Impact**: A review snapshot that has lost one idempotency record can double-charge trial allowance and duplicate evidence. This recreates the central consequence of CR-001 through a new omission path even though the prior present-record replay counterexample is fixed.
- **Recommended fix and verification**: Persist durable event provenance on locally metered evidence and validate one-to-one reverse coverage on import. If historical or externally sourced evidence is allowed without a local event, model that provenance explicitly instead of exempting all evidence. Add deletion/import/redelivery tests that assert snapshot rejection or exact replay, unchanged usage, unchanged evidence count, and atomic failure.
- **Fix risk**: Medium. The repair must preserve legitimate historical/external evidence while closing local event omission.

### A-02 - Unfixed - Medium - Same-account claims bypass CONFLICT and RECYCLED risk

- **Entry point / function**: `claimSubject` in `shared/onecall-business.js`, consumed by the Mini and Web claim flows.
- **Files / lines**: `shared/onecall-business.js:244-268`, especially the same-account return at `:256-258` before risk checks at `:261-262`; `prototype/onecall-miniapp-pages.html:4177` and `:4877`; `web-prototype/evidence-hub.html:1635` and `:2371`.
- **Expected behavior**: `CONFLICT` and `RECYCLED` must always block self-service claim and hide trial/evidence history, including when the subject was previously associated with the same account. This is required by the accepted plan at `docs/gateflow/cross-channel-alignment-plan.md:77` and the rule in `docs/10-cross-channel-rules.md:29`.
- **Actual behavior**: The same-account branch returns `{ok:true, code:'DUPLICATE'}` before evaluating `claimRisk`. Both clients treat `ok` as successful verification and can expose the subject's trial/evidence state.
- **Direct evidence**: A helper-created IVR subject was claimed successfully and had evidence. Changing its otherwise valid `claimRisk` to either `CONFLICT` or `RECYCLED` left the snapshot valid. A new same-account claim returned `DUPLICATE` with `ok:true`, rather than the required risk rejection.
- **Impact**: A subject whose risk changes after association can bypass the offline-review boundary and expose protected history through either client.
- **Recommended fix and verification**: Evaluate blocking risk before same-account idempotency. Add shared and client-adapter tests for a previously associated subject whose risk later changes to each blocked state; assert failure, no claim mutation, and hidden history. Normalize or document the duplicate result shape when no explicit `SubjectClaim` record exists.
- **Fix risk**: Low.

### A-03 - Unfixed - Medium - Catalog type and billing invariants exist only in the admin UI

- **Entry point / function**: Catalog validation and checkout in `shared/onecall-business.js`.
- **Files / lines**: Shared validation at `shared/onecall-business.js:167-186`, checkout at `:348-369`, transactional selection near `:762`, and the admin-only matrix at `operations-prototype/onecall-operations-admin.html:1090-1091`.
- **Expected behavior**: The shared contract must enforce the accepted type/term matrix from `docs/gateflow/cross-channel-alignment-plan.md:103`: subscriptions use recurring monthly/quarterly/annual schedules; one-time and add-on offers use `ONCE`, one installment, and interval zero; quote offers use `QUOTE`, one installment, and interval zero. Valid configured subscription schedules, including a three-month interval with four installments, must remain legal.
- **Actual behavior**: Shared validation checks enum membership and some audience/QUOTE rules, but not type-to-billing coherence. The admin form enforces a stricter matrix that shared snapshot import and checkout do not own.
- **Direct evidence**: `SUBSCRIPTION + ONCE`, `ONE_TIME + ANNUAL`, and `ADD_ON + MONTHLY` all passed shared validation, snapshot import, token generation, and order creation. A one-time annual offer with 12 installments also progressed through payment and entitlement issuance.
- **Impact**: Imported state or any caller outside the admin form can create nonsensical recurring products, orders, and entitlements. This is semantic ownership drift between the UI and the canonical validator.
- **Recommended fix and verification**: Centralize the full matrix in `validateCatalogVersion` and make all mutations depend on it. Add positive coverage for monthly, quarterly, annual, and custom subscription schedules, plus negative coverage for every invalid cross-product of type, cycle, interval, and installments through snapshot import and order creation.
- **Fix risk**: Medium because existing fixtures and frozen order snapshots must continue to validate.

### B-01 - Unfixed - Medium - Reopening the exhausted IVR scenario rewinds consumption and corrupts canonical state

- **Entry point / function**: Operations admin -> prototype review -> IVR demo -> `exhausted`; complete recording, close the demo, then start `exhausted` again.
- **Files / lines**: Direct rewind in `operations-prototype/onecall-operations-admin.html:1133-1145`, especially `:1136`; snapshot hook at `:1166`; frozen-grant validation at `shared/onecall-business.js:700-703`; incomplete loop coverage at `operations-prototype/qa/qa.js:120-131`.
- **Expected behavior**: Consumed allowance is monotonic. Reopening a scenario must keep the canonical snapshot valid and either remain exhausted or use an explicit, isolated full-fixture reset that cannot conflict with retained events/evidence.
- **Actual behavior**: Every `demoStart` writes `grant.usedSeconds=280` directly. The first completion consumes through the shared helper to 300 and freezes 300 in the EVIDENCE event result. Starting the scenario again rewinds only the live grant to 280 while retaining the event and evidence.
- **Direct evidence**: The visible flow completed once with `usedSeconds=300`, one evidence item, and a valid snapshot. Closing and reopening the scenario changed usage to 280. `B.snapshot(raw)` then returned `INVALID_TRANSITION`, because the historical event result froze 300 seconds. `businessSnapshot()` threw and a later confirm could not repair the state.
- **Impact**: A normal review interaction can make the canonical state unexportable, block cross-surface handoff, and regress already consumed allowance. The UI is mutating state owned by the shared transition layer.
- **Recommended fix and verification**: Do not patch the canonical grant in `demoStart`. Seed a legal pre-event fixture before the scenario begins, preserve EXHAUSTED on subsequent runs, or explicitly rebuild the complete isolated fixture. Add a complete-run/close/reopen regression that checks snapshot validity after every action, nondecreasing usage, stable prior events/evidence, and successful export.
- **Fix risk**: Medium because the admin scenario seed must stay aligned with shared IVR fixtures and Mini/Web expectations.

### C-01 - Unfixed - Medium - Mini fixed-line activation reports success without a business mutation

- **Entry point / function**: Mini fixed-line flow `landlineBind` -> `landlineVerify` -> `landlineReady`.
- **Files / lines**: Fixed-line pages at `prototype/onecall-miniapp-pages.html:4479-4492`; generic handler at `:4940-4946`, which gates only `data-phone-submit`; text-only QA at `prototype/qa/qa.js:183-196`; accepted requirement at `docs/gateflow/cross-channel-alignment-plan.md:121`.
- **Expected behavior**: A successful fixed-line setup must create or select the canonical subject and perform the shared activation mutation before showing success. Failure must remain on the input/review flow without state changes.
- **Actual behavior**: The fixed-line route navigates to the success page without calling `B.activateService` or making any equivalent canonical mutation.
- **Direct evidence**: Completing the visible flow showed `Fixed line verified and activated` and `ONECALL internal recording service activated` in the UI. The complete `businessSnapshot()` remained byte-for-byte unchanged. No subject for `010 **** 6688`, activation, or trial existed before or after.
- **Impact**: The UI asserts an activation that downstream surfaces cannot observe. The S3 mobile activation repair did not cover the parallel fixed-line entry path.
- **Recommended fix and verification**: Route fixed-line submission through the same canonical subject/activation owner, with explicit fixed-line verification fixture semantics. Gate navigation on a successful validated candidate commit. Extend QA to assert the subject, activation, trial policy, duplicate idempotency, failure atomicity, and cross-surface visibility rather than only success copy.
- **Fix risk**: Medium because fixed-line identity/verification rules need an explicit local contract.

### C-02 - Unfixed - Medium - Web stop/reactivate is UI-only and fabricates a carrier receipt

- **Entry point / function**: Web number detail for `phone-6208`, then stop and reactivate.
- **Files / lines**: Seed authorization fields at `web-prototype/evidence-hub.html:1643-1650`; status/detail rendering at `:2094`, `:2214-2216`, and `:2227`; local stop/reactivate handler at `:2495-2505`; accepted requirement at `docs/gateflow/cross-channel-alignment-plan.md:129`.
- **Expected behavior**: Add/reactivate must update canonical internal `activationId` and `activationStatus` through the shared owner, and product copy must describe an internal ONECALL result rather than a carrier receipt.
- **Actual behavior**: Stop/reactivate changes local view state only. The canonical activation is unchanged, no activation/grant record is added, reactivation invents hardcoded `ACT-DEMO-742924`, and authorization detail still labels the value as `carrier receipt / carrier result`.
- **Direct evidence**: The visible UI moved from available for evidence to disabled and back to available. Throughout the flow, canonical `WEB-ACCOUNT-001` remained `activation:'ACTIVE'` at revision 1. No new activation or grant appeared.
- **Impact**: The Web surface can display a lifecycle and proof artifact that do not exist in canonical state, so other surfaces and exports disagree with what the user sees.
- **Recommended fix and verification**: Move stop/reactivate to shared, validated activation transitions; derive displayed status and IDs from the committed snapshot; remove carrier semantics. Add visible-flow assertions for canonical revision/status/ID, cross-surface consistency, replay/idempotency, and atomic rejection.
- **Fix risk**: Medium because stop/reactivate needs a defined shared state transition and grant policy.

- **Cross-channel consistency**: S3's repaired mobile/account/schedule flows remain aligned, but fixed-line and Web activation lifecycle actions still produce visible states that cannot be handed off through the canonical snapshot.
