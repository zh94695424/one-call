## 2. Finding status for `PA25-PLAN-A-01`

**Status: `fixed`.**

The initial finding was that `apply` could silently adopt a compatible but unrelated pre-existing login (chosen name) and grant it the approved memberships, after which structural `check` would pass. The fixed plan now:

- Permits `COMMENT ON ROLE` only on the three roles **newly created by the script**, before any membership grant, in the same transaction (§4.1, §4.2 step 4, §4.4 line 119/121/127).
- Rejects **every existing unmarked chosen-name login in both modes** with `PA25_PROVENANCE_REJECTED` **before any CREATE/ALTER/COMMENT/GRANT anywhere in the transaction**, including before creating an earlier absent slot (§4.2 step 3, §4.4 line 123, test 18).
- Makes the marker a creation-time binding of database OID, role OID, fixed slot and validated name, compared byte-for-byte and never inferred from attributes, name, password, memberships or a prefix (§4.4 lines 121–125).
- Preserves first apply (absent → create + mark), full replay (marker bytes/OIDs not rewritten), and missing-edge repair only for proven/marked roles (§4.4, test 10), while wrong/extra/reversed edges still reject.
- Adds negative tests proving no creation/attribute/edge mutation for unrelated compatible roles with and without apparently approved edges (test 18), and marker tamper/loss/version/slot-copy/rename/drop-recreate rejection (test 18), with redacted diagnostics (test 20).
- Adds no adoption mode, operator-attestation input, override flag, helper object/schema/table, V014, object ACL change, credential, datasource or runtime surface.

This directly satisfies the adjudication: explicit nonsecret provenance rule; preserve first apply, replay and permitted repair; reject unrelated compatible names before mutation; negative test proving no mutation. A OQ-1 is answered by the same mechanism (creation-only, no adoption); the other initial questions (OQ-2/3/4) were not used to expand the fix.

## 5. Open questions

1. **Trust-boundary wording (forge authority).** The plan says an “authorized catalog-writing administrator” can forge an exact marker. In PostgreSQL 16, `COMMENT ON ROLE` is governed by role ownership/membership (superusers and members of the role), not only superuser/CREATEROLE, so an existing chosen-name role could in principle be self-commented by one of its own members. The practical adoption path still requires the operator to choose a *pre-existing* name, contrary to the plan's primary control (“choose absent approved names”), and the plan already routes custody/audit to Platform/Database/Security. Suggested action at implementation-gate intake: broaden the residual wording from “administrator” to “any identity able to write that role's comment (role members/superusers/CREATEROLE)”, without adding an override. Not material to this fix.
2. **Missing-marker copy across databases in test 18.** Test 18 names “copy another slot's marker”; §4.4 also forbids copying between roles/databases. The byte-for-byte `db`/`role`/slot/name comparison already makes a cross-database copy reject, but the implementer could add an explicit cross-database copy case at implementation time. Test-precision strengthening, not a plan defect.
3. **Explicit transaction for transaction-local GUCs.** `set_config('pa25.*', ..., true)` must live inside the same explicit `BEGIN … COMMIT` as the guarded DO block; otherwise it resets at statement end. The plan says “both modes run all validation in one transaction,” which is sufficient for a careful implementer, but the explicit `BEGIN/COMMIT` requirement should be stated/verified at implementation.
4. **Direct-login / NOLOGIN provenance.** These roles retain the frozen migration/history contract and receive no PA25 marker. V011–V013 validate their attributes/password/topology; on a fresh database, a pre-existing exactly-compatible role with a direct-login name could in principle be accepted by the frozen migration's idempotent branch. This is pre-existing frozen-migration behavior, explicitly outside this fix's authorized scope (no V014/byte change), and is not a regression introduced by the fix. Suggested tracking: Platform/Database deployment review; not a PA25 fix blocker.
