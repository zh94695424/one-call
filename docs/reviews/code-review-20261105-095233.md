## Findings

### 1-未修复-中-content_sha256/scopeDigest canonical input keys diverge from the frozen docs14 §2.12 formula

- **入口/函数**: `DefaultCustomerShareCommandService.create(...)` — canonical snapshot/scope/content digest construction (executed on every first creation; replay recomputes the same fingerprint).
- **文件(行号)**:
  - `backend/src/main/java/com/onecall/core/sharing/internal/commandservice/DefaultCustomerShareCommandService.java:140-143` (`scope.set("contentObject", content)`, `scope.set("verificationObject", verification)`, `scopeDigest = digest(scope)`).
  - `backend/src/main/java/com/onecall/core/sharing/internal/commandservice/DefaultCustomerShareCommandService.java:159-161` (`complete = scope.deepCopy()`, `complete.set("creationObject", creation)`, `contentHash = digest(complete)`).
  - Contract: `docs/14-production-data-model-and-flyway-schema-spec.md:254-255`; accepted-plan literal wording: `docs/gateflow/pa14-sharing-command-service-foundation-plan.md:21` and `:140`.
- **输入场景**: Any successful create request (any verification mode) that reaches snapshot construction.
- **实际分支**: Unconditional digest path. `scopeDigest` is computed over canonical JSON with member names `contentObject`/`verificationObject`; `content_sha256` is computed over `contentObject`/`verificationObject`/`creationObject`. These wrapper keys are also stored inside `creation.scopeDigest`/`creation.creationFingerprint` (the fingerprint hashes `creation`, which contains `scopeDigest`).
- **预期行为**: The frozen design contract requires the digests to be taken over the persisted snapshot member structure: `scopeDigest = SHA-256(canonical({content, verification}))` and `content_sha256 = SHA-256(canonical({content, verification, creation}))` (`docs/14…:254`: “the frozen content and verification members”; `:255`: “the complete `content_snapshot` `{content, verification, creation}`”). The persisted V009 snapshot itself uses the member names `content`/`verification`/`creation` (`V009__sharing.sql:56`).
- **实际行为**: The stored `content_sha256` is not the digest of the persisted `content_snapshot` structure; it is the digest of a differently-keyed wrapper object owned only by this implementation. The same applies to `scopeDigest`, and thus to `creationFingerprint`, because `scopeDigest` is embedded in `creationObject`.
- **直接证据**:
  - Code uses `contentObject`/`verificationObject`/`creationObject` (`DefaultCustomerShareCommandService.java:141-143`, `:160-161`).
  - Docs14 §2.12 explicitly defines the same digests over `{content, verification}` / `{content, verification, creation}` (`docs/14…:254-255`).
  - The IT “recomputes the digests from read-back objects” but builds the expected wrapper with the implementation's own key names (`backend/src/test/java/com/onecall/archtests/container/CustomerShareCommandsIT.java:420-424`: `scope.set("contentObject", …)`, `scope.set("verificationObject", …)`, `scope.set("creationObject", …)`), and the unit test asserts expected strings with the same wrapper keys (`backend/src/test/java/com/onecall/archtests/sharing/CustomerShareCommandServiceTests.java:121-134`). The evidence is therefore self-consistent with the implementation but cannot detect divergence from the frozen formula.
  - The accepted plan's literal formula (`plan.md:21`, `:140`) uses the same wrapper names, so the conflict is between two authoritative sources (accepted plan and frozen docs14), not a random coding error.
- **影响**: `content_sha256` is a durable, immutable, audit-relevant column. An independent verifier/auditor or a later downstream consumer recomputing the documented formula from the persisted `content_snapshot` will get a different digest, so the frozen snapshot cannot be verified against the schema specification. Because `creationFingerprint` includes `scopeDigest`, any correction after data exists would change replay identity/conflict behavior for existing rows. There is no runtime failure today (V009 only checks 64-hex shape), which makes the drift silent. The feature is currently unwired/disabled, so the fix cost is still low.
- **建议改法和验证点**: Choose one authority. If docs14 is authoritative (it is frozen and describes the schema), compute both digests over the persisted member names `{content, verification}` and `{content, verification, creation}` and update `creationFingerprint` consistently; if the accepted-plan wrapper names are intentional, record an explicit contract amendment for docs14 §2.12 and document that `content_sha256` is not a digest of the persisted snapshot. Add an independent test vector that builds the expected canonical JSON from the persisted snapshot keys (`content`, `verification`, `creation`) rather than from the production wrapper names; keep the existing `jsonb_typeof` object-node and read-back assertions. Re-run focused Surefire + `CustomerShareCommandsIT` in a container-capable environment after the change.
- **修复风险（低/中/高）**: 中（changes stored `scopeDigest`, `content_sha256`, and `creationFingerprint`; no production rows exist yet because the command feature is unwired/disabled, but replay/conflict semantics and all digest assertions must be updated atomically).
- **严重程度（低/中/高/严重）**: 中

## Residual Risk

- **Request body cap**: `CustomerSharesController.createCustomerShare` calls `request.getInputStream().readAllBytes()` with no size limit. This is a known, explicitly deferred reviewer-B item in `aggregate-review-fix4` (gateway/security + later backend hardening), not re-raised as a new finding; it remains an unbounded-memory residual risk for this route.
- **Provider I/O under advisory locks**: The create transaction acquires ranks 7→8→9 advisory locks before `creationPolicyProvider.evaluate(...)` and before token/code/mobile material generation. Defaults fail closed and no production provider is approved, but a future external policy/provider adapter would hold these locks across network I/O; docs/14 §9.0/§9.0.2 forbid holding locks across network calls. Future provider integration must revisit call placement.
- **Unlocked risk/evidence reads**: `readRiskOwnership` uses non-locking reads (per plan). A concurrent `OPEN` risk committed after the read but before insert is not observed by this create; this is a documented/contract-accepted window, not a regression, but it remains a residual authorization-race risk.
