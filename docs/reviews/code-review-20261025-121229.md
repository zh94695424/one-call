## Findings

### AR-01（中）——Mini 呼叫状态页在证据可用态无条件宣称“系统拨号盘已打开”，与同屏任务事实行及绑定目标的真实性要求矛盾

- Entry / function: Mini 呼叫状态渲染 `callStatusHtml()`（`prototype/onecall-miniapp-pages.html`，非生成块内的应用区）。
- File / line: `prototype/onecall-miniapp-pages.html:5502`（头部三元分支）；支撑 `:5499`（`launched` 定义）、`:5504`（同屏任务事实行如实显示拨号盘状态）。
- Input scenario: 任何 `progress === 'EVIDENCE_READY'` 且任务 `dialerLaunchedAt === null` 的呼叫记录渲染呼叫状态页。该状态可由切片自身跨端 QA 真实到达：Mini UI 点击创建任务至 `dialHandoff` 而不点击“打开系统拨号盘”（`shared/qa/cross-channel.js:231-234`）→ `resolveIvrInbound` 原子领取（`shared/qa/cross-channel.js:248`）→ 事实链推进至 `EVIDENCE_READY`（`:261-264`）→ `loadCallTaskSnapshot` 导入三端（`:270`）→ `mgo('callStatus')` 渲染并断言“证据可用”（`:274`）。
- Actual branch: `:5502` 的头部三元把 `evidenceReady` 放在最前且不读取 `launched`：`evidenceReady ? "系统拨号盘已打开 · 证据可用" : launched ? …`。只有后续分支才以 `launched` 为闸。
- Expected behavior: 绑定目标成功信号要求 Mini“truthful return states without presenting dialer launch as connection success”；设计 `docs/13` §1.7 与 §9.1 明确“不能把系统拨号成功展示为通话接通/不表示用户拨出”；同屏任务事实行（`:5504`）以 `dialerLaunchedAt` 为真值源显示“已打开（仅客户端）/未打开”。因此 `evidenceReady` 分支的拨号盘前缀必须同样以 `launched` 为条件（或直接省略前缀仅显示“证据可用”），不得在从未拉起拨号盘时宣称已打开。
- Actual behavior: 证据可用态头部无条件输出“系统拨号盘已打开 · 证据可用”，即使 `dialerLaunchedAt` 为 `null`；同屏“待拨任务事实”行同时显示“系统拨号盘 未打开”——同一页面自相矛盾。
- Direct evidence: 受跟踪工作流截图 `prototype/qa/screenshots/alignment-cross-call-task-393.png` 原尺寸可见：页标题“系统拨号盘已打开 · 证据可用”，其下 CT-2001 任务卡“系统拨号盘 未打开”、任务状态“已完成”、领取“已领取 · CALL-QA-TASK-01”、进度“证据可用”。QA 缺口：Mini QA 对等待态断言了拨号盘与接通的分离（`prototype/qa/qa.js:354` 要求含“系统拨号盘已打开”与“尚未接通”），但对证据态仅断言“证据可用”存在（`:370`），未断言头部真实性；cross-channel 亦只断言“证据可用”文本（`shared/qa/cross-channel.js:274`）。Mini 自身 `buildCallDemoState('evidence')` 恒先调用 `recordDialerLaunch`（`:5542`），故 Mini 单端 runner 的证据态巧合为真，掩盖了该缺口；跨端导入路径打破了该巧合。
- Impact: 直接违反绑定目标的成功信号与设计 §1.7/§9.1 的客户端事实真实性契约；错误声明被固化进已接受切片的工作流所有截图，作为验收证据对外可见；削弱本切片“拉起拨号 ≠ 接通/领取/录音”语义归属同步的可信度。不涉及共享状态机突变或跨账户数据泄漏，故为中而非高。
- Fix / validation: 在 `:5502` 的 `evidenceReady` 臂以 `launched` 为条件输出拨号盘前缀（例如 `launched ? "系统拨号盘已打开 · 证据可用" : "证据可用"`）；为跨端（或 Mini）证据态增加断言：未拉起拨号盘的证据可用页头部不得含“系统拨号盘已打开”；经 `shared/build-prototypes.js` 再生成受控块后复跑 Mini 与 cross-channel runner，并重采 `alignment-cross-call-task-393.png` 原尺寸复检。
- Fix risk and severity: 低——单行渲染分支收敛 + 一条 QA 断言，不触碰共享状态机、其他两面或夹具；需再生成内联副本。Severity: 中。

### AR-02（低）——`resolveIvrInbound` 领取分支仅按规范主叫 + `PENDING` 匹配任务，缺少 CF-09 已在 SUSPENDED 分支落实的六字段归属匹配，验证通过的导入态可跨归属领取并外呼他方冻结被叫

- Entry / function: `resolveIvrInbound` 有效任务领取分支（`shared/onecall-business.js`）。
- File / line: `shared/onecall-business.js:887-888`（领取匹配谓词）；对照 `:862-868`（CF-09 SUSPENDED 六字段匹配）、`:778-779`（`createCallTask` 跨归属 `sameOwner` → `CALLER_BUSY`）、`:1044-1048`（`uniqueCallerBinding` 仅返回唯一 `active` 绑定）、`:1201-1202`（`validCallTask` 校验任务绑定的身份字段但不要求该绑定 `active`）。
- Input scenario: 经 `loadCallTaskSnapshot` / `validateCallTask` 接受的合法快照：同一 `normalizedCaller` 下绑定 A（`active: true`，owner1）与绑定 B（`active: false`，owner2）并存，且存在经绑定 B 冻结的 `PENDING` 任务；随后 `resolveIvrInbound` 以该 `normalizedCaller`、`callerTrusted: true`、`callerState: 'ACTIVE'`、`availableSeconds > 0` 呼入。
- Actual branch: `uniqueCallerBinding`（`:858`）返回唯一活动绑定 A；激活/权益闸通过后，`:887` 以 `item.normalizedCaller === normalizedCaller && item.status === 'PENDING'` 选中唯一待拨任务——不比对 `callerBindingId`/`ownerType`/`ownerId`/`workspaceId` 是否等于绑定 A；`:888-916` 将 owner2 的任务置 `CLAIMED` 并返回 `DIAL_TASK_CALLEE`，`maskedCallee` 为 owner2 的冻结被叫。
- Expected behavior: 设计 `docs/13` §3 要求任务冻结归属且“权限撤销不能由旧任务绕过”，§6.3 要求领取时核验唯一任务与当前空间权限；CF-09 已确立“任务六字段与解析出的唯一活动绑定全匹配才允许归属内写入”的不变量。领取路径应以同一六字段谓词选取待拨任务：仅领取本唯一绑定拥有的任务；匹配失败的任务不得被本会话领取（不得返回其冻结被叫），应按无任务语义落入 `ENTER_CALLEE` 或失败关闭，而不是跨归属授权外呼。
- Actual behavior: 跨归属领取与外呼授权——owner1 的 IVR 会话领取 owner2 的任务，并在决策中取得 owner2 的冻结被叫明文（脱敏形态），构成归属/隔离语义缺口。
- Direct evidence: `:887` 谓词仅两条件（`normalizedCaller` + `PENDING`），与 SUSPENDED 分支 `:862-868` 的六条件形成精确对比；`createCallTask:766` 拒绝非活动绑定建任务、`:778-779` 拒绝跨归属替换，说明唯一缺少归属匹配的写路径是领取；`validCallTask:1201-1202` 不要求任务绑定 `active`，故上述状态可通过验证门；`shared/qa/call-task.test.js` 15 用例中无“第二非活动绑定 + 他方 PENDING 任务”的领取用例（SUSPENDED 回归 `:342-403` 仅覆盖 SUSPENDED 路径）。
- Impact: 在验证通过的状态上产生跨归属被叫外呼授权——状态机主写路径的隔离缺陷。当前演示域没有使绑定失活的变更 API（建任务即要求绑定活动），正常 UI 流不会自产该触发态，故实际可达性受限、定为低；但跨端导入是切片一等评审面，`validateCallTask` 是失败关闭边界，缺口真实存在且无测试看守。
- Fix / validation: 领取分支改用与 `:862-868` 同族的六字段谓词选取 `PENDING` 任务；若同主叫的 `PENDING` 任务不匹配当前唯一活动绑定，则不领取、不返回其被叫（按无任务路径或失败关闭，取设计 §6.3 语义）；新增回归：活动绑定 A + 非活动绑定 B + B 名下 PENDING 任务，断言不领取、不泄漏被叫、状态按所选语义原子变更；复跑三个共享测试文件。
- Fix risk and severity: 低至中——收紧领取谓词；合法数据中任务创建时从其绑定复制全部六字段（`:786-807`），`uniqueCallerBinding` 解析的正是同一活动绑定，正常路径谓词恒真、行为不变；需确认无夹具依赖跨绑定代领取。Severity: 低。
