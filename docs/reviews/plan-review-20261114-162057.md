## 3. Findings

### 01-未修复-[中]-GET media validation is not assigned to a post-authority path, while the existing filter validates Accept before the controller and maps incompatibility to 500 INTERNAL
- **位置**: Plan §3.2 lines 49 and 53; plan §8 allowlist line 234 (`OperationsBoundaryFilter` responsibility: “exact GET admission and POST-only command requirements”); existing `backend/src/main/java/com/onecall/core/operations_iam/internal/web/OperationsBoundaryFilter.java:47-55`.
- **问题类型**: 不可直接实施 / 契约缺失 / 错误优先级
- **当前写法**: The plan orders “(3) transaction/pool/role and trusted current employee authority” before “(5) acceptable JSON response media”, requires incompatible/malformed/q=0 Accept to be `422` **after authority**, and requires preventing Spring-generated 406/405/HTML. The filter responsibility is described only as exact GET admission plus POST-only command requirements; the read controller is allowed, but the plan does not pin that GET must bypass the filter's existing unconditional Accept block or that the read controller must avoid a `produces` condition. The existing POST controller uses `@PostMapping(..., produces = "application/json")` and the filter's incompatible-Accept branch throws `Failure(Code.INTERNAL)`, which the filter writes as **500**, not 422.
- **反例/失败场景**: A request with a valid opaque bearer for a currently DISABLED employee sends `Accept: text/html`. If the existing filter's Accept block still runs for GET, it throws `INTERNAL` before the read service learns the employee is DISABLED, so the caller receives 500 instead of the required 403. Alternatively, if the new read controller declares `produces = "application/json"`, Spring MVC's produces condition or message-converter negotiation can return 406 before the service runs authority, again bypassing the required 403/422 order. A malformed Accept would also be caught by the filter's broad `catch (Exception)` as 500 rather than 422.
- **为什么有问题**: The task and plan explicitly require authentication/authority before request/media validation and frozen `422 VALIDATION_FAILED` for unacceptable media. The current filter is unmodified in the plan's existing-code responsibility and its media branch is not POST-specific. The implementation agent has no stated instruction for the GET branch, the controller's `produces` behavior, or the exact 422 code path, so the most natural copy of the existing controller/filter pattern violates the plan.
- **直接证据**: Plan lines 49 (“(3) ... authority; (4) ...; (5) acceptable JSON response media”), 53 (“A supplied Accept ... is 422 after authority”, “Prevent Spring-generated 406/405/HTML”), and 234 (“POST-only command requirements”); `OperationsBoundaryFilter.java:47-55` unconditional `parseMediaTypes`/`INTERNAL` branch; `OperationsSubjectsController.java:26,30` `produces = "application/json"`; existing `OperationsProblemWriter.write` maps lifecycle `INTERNAL` to 500.
- **影响**: Wrong public status and order (500/406/HTML instead of 403/422), failing the exact error-precedence tests and the route/media contract; implementation churn or an unplanned filter/controller redesign.
- **建议改法和验证点**: State explicitly: (a) the GET branch of `OperationsBoundaryFilter` performs only route admission and bearer verification and does **not** parse or reject Accept; (b) `OperationsSubjectReadController` does not use `produces`, copies every Accept value into the raw request, and returns success with an explicit `application/json` content type; (c) the post-authority read parser rejects malformed, incompatible and q=0 Accept as `VALIDATION_FAILED`/422 using the read Code/Failure; (d) add assertions: disabled employee + `Accept: text/html` → 403; valid employee + `Accept: text/html` → 422; valid employee + `application/json;q=0` → 422; malformed Accept → 422; no 406/HTML/500 and no Spring error body.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-[低]-Cursor payload states “PostgreSQL microsecond precision required” but the rejection list does not explicitly require non-multiple-of-1000 nanos to be CURSOR_INVALID
- **位置**: Plan §4 line 65; existing `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerBusinessNumberCursorCodec.java:44`.
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: The payload is “signed epochSecond int64 + nano int32 (0–999999999, PostgreSQL microsecond precision required)”; the rejection list says “invalid Instant/nanos/UUID structure as CURSOR_INVALID” but does not state `nano % 1000 == 0`.
- **反例/失败场景**: An implementation that only checks `0 <= nano < 1_000_000_000` accepts an authenticated cursor with `nano = 1`. PostgreSQL `timestamptz` stores microseconds; seeking with a non-microsecond anchor can compare as if truncated/rounded, producing an inconsistent page boundary or a cursor that can never equal a stored `created_at`. The existing CustomerBusinessNumber codec explicitly rejects `nanos % 1000 != 0`, so the project convention already treats this as invalid.
- **为什么有问题**: The plan requires “parameter anchors retain full stored precision” and exact seek semantics; the codec must reject anchors that cannot be represented at PostgreSQL precision rather than silently carrying them. This is low severity because valid cursors are authenticated and issued only from DB timestamps, but it is a concrete codec rule.
- **直接证据**: Plan line 65; `CustomerBusinessNumberCursorCodec.java:44` `nanos % 1000 != 0 → CURSOR_INVALID`.
- **影响**: A codec test may miss the non-microsecond case; a malformed-but-authenticated cursor could be accepted and produce an inconsistent seek. No data is written.
- **建议改法和验证点**: Add `nano % 1000 == 0` to the strict payload validation and to `invalidNanosAndPlaintextShapesNeverReachQueries`; reject noncanonical/non-microsecond nanos as CURSOR_INVALID before any query.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## 4. Open questions

1. **Detail and candidate capacity ceilings are not settled by the binding scope.** The plan proposes 503 for the 101st binding/claim and for an activation-filtered scan that exceeds 100 batches/10,100 candidates, and explicitly says “if Controller interprets the frozen detail as guaranteeing successful unbounded histories, this design cannot be accepted” (plan lines 35, 87, 497). Control lines 26–28 fix the safe detail shape and forbid a new schema/grant/public-contract delta but do not explicitly authorize a capacity ceiling. Owner: Product/Controller/Backend at adjudication. If unbounded success is required, the plan must stop for new schema/API authorization; otherwise record the 503 behavior as an accepted residual before implementation.
2. **Unknown-role/status/revision injection is required but the test seam is not pinned.** Plan line 45 requires tests to inject unknown roles to prove refusal; V002:139–141 constrains role/status, and the read fixture login is specified as exactly six SET memberships without owner/DDL authority. The plan says corrupt reader results may be supplied via test doubles, but the authority read is service-owned SQL and no authority-reader port or package-private test seam is in the allowlist. Owner: Backend/Test. Pin whether this is done through a test-only DSL/result double, a controlled rolled-back admin fixture, or a small service-local seam; do not add an unlisted type silently.
3. **Trial expiry source/consistency remains formally ambiguous.** Plan line 83 says `expiresAt=original trial/grant expiry`; the detail SQL selects both `trial_expires_at` and `grant_expires_at` (plan lines 173–183). `issue_first_trial` enforces equality for rows it creates (V006:224–236), but the schema alone does not. Decide explicitly whether a mismatch is 503 and which validated value is used; the existing `missingOrInconsistentTrialRelationsFailWithoutRepair` test should state the mismatch case.
4. **Key-ring deployment encoding is not pinned for the allowed kid alphabet.** Plan line 63 allows kid `[A-Za-z0-9_-]{1,32}` and binds `.keys.<kid>` from deployment-controlled configuration. If the deployment uses environment-variable property names, case, `-` and `_` can be lossy/ambiguous under Spring relaxed binding. Owner: Security/Platform. Pin the property source (file/secret mount vs env) or restrict kid spelling to a deployment-representable canonical alphabet.
