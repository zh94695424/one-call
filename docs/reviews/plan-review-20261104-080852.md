## Findings

### PA14-R3-A-01-未修复-高-Creation identity and fingerprint inputs contradict the frozen deterministic formula
- **位置**: Plan §HTTP and domain contract lines 36–38; docs/14 §2.12 creation identity/fingerprint and §9.29 step 4.
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: Line 38 says both the deterministic share identity and canonical fingerprint are built from the validated request, trusted caller/context, evidence projection and the one sampled DB timestamp.
- **反例/失败场景**: The frozen `shareId` is derived only from `{creatorAccountId, creationRequestId}`. If evidence projection or `valid_from` participates in the identity, an exact resend gets a different `shareId`; `ON CONFLICT (share_id)` no longer finds the first grant, so a changed projection can create a second grant or a nominal replay can miss entirely. The frozen creation fingerprint excludes generated/observed server timestamps; if `valid_from` participates, every retry has a new fingerprint and returns `SHARE_CREATION_CONFLICT` instead of metadata replay.
- **为什么有问题**: Lines 22 and 36 already distinguish stable identity from sampled creation time, while line 38 collapses them. This directly breaks the Goal's deterministic creation identity/replay and the one-time-secret guarantee.
- **直接证据**: Plan line 22 (70-character identity), lines 36–38; `docs/14-production-data-model-and-flyway-schema-spec.md:255` defines `shareId = share:` + SHA-256 of canonical `{creatorAccountId, creationRequestId}` and excludes server/generated timestamps from `creationFingerprint`; §9.29 step 4 separately freezes `valid_from`.
- **影响**: Duplicate grants/tokens for one creation request, failed concurrent same-identity replay, false conflicts, or a one-time secret returned on an unintended second grant.
- **建议改法和验证点**: Freeze two separate formulas: `shareId` uses only the trusted creator account UUID plus exact `creationRequestId`; `creationFingerprint` uses the §2.12 semantic request/context/content fields (including business `expiresAt`) and excludes `valid_from` and all generated/observed server timestamps. Make `createBuildsDeterministicIdentityAndFingerprint`, `createReplaysMetadataWithoutSecrets` and `createConcurrentSameAndDifferentIdentities` assert time advancement does not change replay identity or fingerprint.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PA14-R3-A-02-未修复-高-Transition action fingerprint omits frozen revoke semantics
- **位置**: Plan §HTTP and domain contract line 40; docs/14 §2.12 transition action fingerprint.
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: Event ID and action fingerprint are derived “from the locked grant UUID and action key”; revoke also accepts an optional semantic `reason`.
- **反例/失败场景**: A revoke succeeds with `Idempotency-Key: K` and reason `ACCIDENTAL`. The client retries key K with reason `SECURITY_INCIDENT`. The transition event ID is the same, but the frozen action fingerprint must change because it includes null-safe `reasonCode`; the required result is 409 `SHARE_TRANSITION_CONFLICT` and no mutation. If the plan's literal two-input fingerprint is implemented, the retry silently replays the first outcome and loses the changed semantic content.
- **为什么有问题**: The event identity can be derived from locked grant UUID + action type + request key, but the fingerprint must include the full accepted semantic input. The current plan conflates identity and fingerprint inputs and makes `revokeChangedFingerprintAndStaleWitnessConflict` unable to distinguish which changed input it proves.
- **直接证据**: Plan lines 34 and 40; `docs/14-production-data-model-and-flyway-schema-spec.md:252` defines event ID from `{shareGrantId, actionType, sourceIdentity}` and `actionFingerprint` from `{shareGrantId, actionType, reasonCode (null-safe), newExpiresAt, actionRequestDigest | expiresAt | sourceRevision}`.
- **影响**: Same-action changed-content revokes are accepted as replays; audit/event semantics become stale and the exact conflict test can be false-green.
- **建议改法和验证点**: After the grant lock, derive event ID using `{grant UUID, actionType, request-key digest/identity}` and derive fingerprint using the complete frozen §2.12 fields, including null-safe revoke reason. Add explicit same-key/changed-reason and same-key/exact-retry assertions to `revokeChangedFingerprintAndStaleWitnessConflict`.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PA14-R3-A-05-未修复-中-Revoke/rotate still allow a time-expired ACTIVE/LOCKED grant
- **位置**: Plan §HTTP and domain contract lines 42–44 and test line 78; docs/14 §7.4, §9.29 step 6 and §2.12 time rules.
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口
- **当前写法**: Revoke says persisted `EXPIRED` maps to 409 and `ACTIVE`/`LOCKED` may be revoked; rotate says revoked/expired state maps to 409. Neither algorithm samples the DB clock after the grant lock or denies an ACTIVE/LOCKED row whose `clock_timestamp() >= expires_at` before persistence.
- **反例/失败场景**: A grant is still stored `ACTIVE` with `expires_at = 10:00:00`, and the revoke transaction locks it at `10:00:00`. The plan's “ACTIVE may be revoked” branch can update it to `REVOKED`, while frozen rules require the at/after-expiry predicate to deny even before the expiry owner persists `EXPIRED`. Rotate has the same hole for a stale but still-ACTIVE row.
- **为什么有问题**: Persisted status is not the whole expiry state. The plan's test prose mentions expiry-boundary precedence but does not define the algorithm or expected no-write outcome, so implementation and tests can disagree.
- **直接证据**: Plan lines 42, 44 and 78; `docs/14-production-data-model-and-flyway-schema-spec.md:258` requires `clock_timestamp()` after lock acquisition; §9.29 step 6 says `clock_timestamp() >= expires_at` denies even before persistence; OpenAPI customer revoke/rotate expose `SHARE_TRANSITION_CONFLICT` and do not expose customer `SHARE_EXPIRED`.
- **影响**: An expired share can be revoked/rotated successfully; events/generations/revisions mutate after expiry; user-visible state and tests diverge from the frozen contract.
- **建议改法和验证点**: After grant lock and exact replay lookup, sample `clock_timestamp()` once and reject at/after `expires_at` with 409 `SHARE_TRANSITION_CONFLICT` for both commands unless a prior persisted terminal status dictates 410 for revoke. Add exact before-boundary, at-boundary and after-boundary no-write assertions to the existing revoke/rotate methods.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
