### F-01-未修复-[高]-S2 direct-authorization fingerprint 把 transport 确认 event ID 纳入哈希，并缺少 accepted 的 session/protocol identity

### F-03-未修复-[高]-S2 reconciliation 在持有 canonical-caller/reservation 锁时查询外部 authoritative IVR

- **入口/函数**: `T-S2-06` reservation reconciliation scheduler；`entitlement-metering` settlement/reconciliation。
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3216-3218`；`§9.0.1:2994` 的 “No lock is held across a network call”；`§9.0:2961`；source `docs/12-technology-stack-and-system-architecture.md:298`、`docs/13-ivr-call-task-and-inbound-design.md:271`。
- **输入场景**: 一个 `HELD` reservation 的 `authorization_expires_at` 已过且没有 accepted terminal usage fact；scheduler 按 T-S2-06 步骤 1 取得 canonical-caller advisory lock 和 reservation row lock，然后步骤 3 查询 authoritative IVR record；IVR 慢或不可用。
- **实际分支**: 锁在步骤 1 取得，步骤 3 没有 commit/release 边界，直接查询外部 IVR；authority unknown 时仍保持 locks 并告警。
- **预期行为**: 先提交/释放 `HELD → RECONCILING` 或读取当前 state 的阶段，再在无 PostgreSQL lock 的情况下查询 IVR；查询完成后按 §9.0.1 顺序重新加锁、重读并收敛。任务明确禁止跨 Redis/COS/媒体/外部网络调用持锁。
- **实际行为**: 外部网络 I/O 发生在 canonical-caller 和 reservation row locks 持有期间；慢 IVR 会阻塞同一 canonical caller 的新 resolve/claim/reservation，并可能触发 lock timeout 和 category-3 重试。
- **直接证据**: `:3216` 的 lock 取得、`:3218` 的 “Query the authoritative IVR record by `callId`”；`:2994` 的全局 prohibition；source docs 将 self-developed IVR 定义为外部 authoritative record（`docs/13:271`、`docs/12:298`）。
- **影响**: 违反明确的 lock/network boundary；scheduler 和同一 caller 的正常 IVR 路径可被慢/不可用外部系统拖住；unknown-use reservation 的占用时间被放大。
- **建议改法和验证点**: 拆成两阶段：阶段 A 在短事务中完成 state/alert 并释放锁；阶段 B 在锁外查询 IVR，再按全局顺序重新加锁、重读 state、执行 settlement/release/quarantine。增加慢/超时 IVR 的锁不持有测试；若 authoritative record 实际是本地 `ivr.call_record`，则必须改为本地 owner service/read contract，不能在 settlement role 直接读未授权的 IVR 表。
- **修复风险（低/中/高）**: 中（改变 reconciliation transaction 边界，但不改状态机或 schema）。
- **严重程度（低/中/高/严重）**: 高。

### F-04-未修复-[中]-S2 reconciliation 先锁 reservation 再锁 balance，反转 rank-12 suborder

- **入口/函数**: `T-S2-06` reconciliation；`entitlement-metering.settle_call_usage` 的 balance/reservation 锁序。
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3216`、`:2983`、`:3203`。
- **输入场景**: reconciliation 与同一 balance 上的 settlement 或其他 reservation 并发；reconciliation 已锁 reservation，settlement 已按 rank-12 锁 balance 并等待 reservation。
- **实际分支**: reconciliation 步骤 1 先 “Acquire ... the reservation row lock”；后续 settlement 路径按 §9.0.1 item 12 需要先锁 balance rows（ascending UUID），再锁 reservation。这形成 reservation→balance 与 balance→reservation 的反向锁序。
- **预期行为**: 所有 rank-12 transaction 先锁 balance rows in ascending UUID，再锁 `usage_reservation`，再写 `usage_fact`；任何 transaction 不得在 later key 后取得 earlier key。
- **实际行为**: reconciliation 在进入 balance 之前先持有 later key，存在 deadlock/lock timeout；category-3 回滚会延迟 unknown-use 的收敛。
- **直接证据**: `:3216` 的 reservation row lock 与 `:2983` 的 “balance rows in ascending UUID, then the `usage_reservation` insert/lock” 直接冲突；`:3203` 的 settlement 使用该 suborder。
- **影响**: 并发 reservation/settlement/reconciliation 可死锁或超时；调度器 stall，unknown use 保持更久；不是业务状态机错误，但违反 accepted global lock order。
- **建议改法和验证点**: reconciliation 先无锁读取 `balance_id`，按 ascending UUID 锁 balance，再锁 reservation；或调用已按该 suborder 实现的 settlement owner service。增加 reconciliation vs settlement 两序并发测试。
- **修复风险（低/中/高）**: 低/中（锁顺序局部调整，不改 schema）。
- **严重程度（低/中/高/严重）**: 中。
