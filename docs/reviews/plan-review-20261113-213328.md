### 02-未修复-[中]-The employeeAdministratorLock bean declaration/ownership is not pinned; the only allowed config files conflict with the plan's own boundary and profile conditions

- **位置**: Plan §4 lines 61, 67 and 69; plan §6 line 153; plan §3 lines 41-44; plan §8.5 test 2 (lines 318-319: `activationImportsOnlyPublishedOperationsInterfaces`); plan §8.4 test 5 (line 311: `employeeCollaboratorUsesSameManagerAndContextWithoutPool`).
- **问题类型**: 架构边界 / 过度耦合 / 不可直接实施。
- **当前写法**: `DefaultEmployeeAdministratorLock` is placed under `operations_iam/internal/employeelock`; the only operations-iam configuration in the allowlist is `OperationsWebConfiguration`, explicitly `@Profile("web")` with "no DB requirement"; the only persistence/property configuration is `activation_consent/internal/operations/OperationsLifecyclePersistenceConfiguration`, whose listed responsibility is pool/manager/DSL/template/repository/owner-service wiring. Plan §6 nevertheless says "Employee lock bean is `employeeAdministratorLock`, under the same persistence/property conditions, constructed with those same qualified manager/DSL; no extra pool or transaction manager in operations-iam." The plan does not state whether the bean is a `@Component` on `DefaultEmployeeAdministratorLock`, a `@Bean` in an operations-iam configuration, or a bean declared by activation-consent.
- **反例/失败场景**: If the implementation declares the bean in `OperationsLifecyclePersistenceConfiguration` (activation-consent), that class must import and instantiate the operations-iam internal implementation, or use reflection, violating plan §3 ("activation-consent ... calls the separate Operations-owned employee lock interface") and the planned `activationImportsOnlyPublishedOperationsInterfaces` test. If it declares the bean in `OperationsWebConfiguration`, the bean is web-only, so a persistence-enabled but non-web owner service has no collaborator (or the bean is not "under the same persistence/property conditions"), producing startup failure or an unavailable command path in that profile combination. The plan's configuration tests do not pin persistence-only behavior.
- **为什么有问题**: The collaborator is a required part of the same-transaction role handoff and its exact owner is part of the architecture boundary. Leaving the declaration/annotation unspecified forces the implementation agent to choose between two readings that conflict with the plan's own module-boundary test, profile contract and configuration-test claims. This is a code-generation-readiness gap, not a style preference.
- **直接证据**: Plan §4 line 61 (`OperationsWebConfiguration` is web-only authenticator/problem/controller-boundary beans and filter registration); line 67 (`DefaultEmployeeAdministratorLock` responsibility has no bean/component declaration); line 69 (activation-consent persistence config lists owner-service wiring but not employee-lock bean); plan §6 line 153 ("under the same persistence/property conditions"); plan §8.5 test 2 (no internal import or reverse edge); existing `ModuleBoundaryTests` package boundary and the absence of any operations-iam persistence configuration in the allowlist.
- **影响**: Implementation agent must invent the wiring; risk of architecture-test failure, an owner service that cannot construct its collaborator in persistence-only mode, or a web-only bean that contradicts "same persistence/property conditions." It also leaves the employee lock's role/profile activation untested.
- **建议改法和验证点**: Pin one exact declaration within the allowlist. The minimal option is to specify `DefaultEmployeeAdministratorLock` as `@Component("employeeAdministratorLock")` with `@Profile("persistence")` and the same `@ConditionalOnProperty(prefix="onecall.operations-lifecycle", name="enabled", havingValue="true")`, constructor parameters qualified with `operationsLifecycleTransactionManager` and `operationsLifecycleDsl`; otherwise add an operations-iam-owned persistence configuration to the allowlist. Add a configuration test that starts persistence without web and asserts the employee-lock bean exists with the same manager, and that web-only mode creates none. Preserve activation-consent imports to the two published interfaces only.
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

## 4. Open questions

1. **Control hash mismatch.** Plan §11 line 533 records `docs/gateflow/project-execution-control.md` as `79b305fe7ca474a40823eef309f5ef855abfddb950fbbc1164f09630c2ae8f9b`; the actual file in this frozen snapshot hashes to `5ee4dfd6e3b17c5b6400045fdb397d8baf050aab3ce1fc29a8a2b75f146c9039`, which is also the Control SHA in the review target. Plan §13 line 592 says the Controller's Control modification is preexisting. The Goal Confirmation content at Control lines 15-39 matches the plan's citations, so this appears to be gate/intake bookkeeping, not goal drift. Recommend updating the §11 row or explicitly marking the hash as the pre-intake historical hash and excluding Control from any frozen-byte expectation.
2. **`Failure(Code)` type and propagation.** Plan §4 line 53 says the port contains "nested records and redacted typed failure"; plan §5.1 lines 105-118 lists `Failure(Code code)` among nested types. The two service methods return `ActivationTransition`; a Java record cannot be thrown. The plan does not state whether `Failure` is a `RuntimeException` subclass, a sealed result, or mapped by a separate exception. Pin the exact failure channel before implementation.
3. **"No foreign reads/locks" wording.** Plan §7.1 line 193 says "No foreign reads/locks execute under activation_consent_role", but the same SQL block lines 174-182 reads `subject_number.business_subject` under that role; V007 lines 234-236 explicitly grant that column read and docs/14 T-S2-41/T-S2-51 describe declared cross-module reads. Clarify that the invariant means "no undeclared/new foreign read or row lock" (the subject read is existing and declared) or restructure the read through an owner collaborator. This is not by itself a privilege violation, but the current invariant text is self-contradictory.
4. **Validation gitdir portability.** Plan §10.4 lines 515-523 pins `git --git-dir=/mnt/d/codex-call/.git/worktrees/codex-call16`; this review snapshot's `.git` points to `D:/codex-call/.git/worktrees/pa32-plan-review-20261113-2118-A`. The command is environment-specific and may not resolve in the implementation worktree. The plan does provide a native-git equivalent; confirm the implementation operator substitutes the actual worktree gitdir.
5. **Dedicated datasource reuse.** Plan §6 creates a second pool/manager/DSL and a new runtime login with three SET memberships, while an existing `activationCommand*` pool/manager/DSL exists for the same activation owner. This is coherent only if production will provision the new credentials and memberships; the plan classifies that as external. Confirm that a new pool is intentional rather than an unnecessary second data-access path; if retained, keep it explicitly residual.
