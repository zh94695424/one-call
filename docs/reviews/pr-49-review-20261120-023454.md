## 6. Independent product re-verification (31 unchanged candidate paths)

The product bytes did not move, so this section is a fresh read, not a restatement of RR18. Nothing here found a defect.

- **Auth/error precedence.** Admission runs before identity and before any body read: `OperationsBoundaryFilter.java:46-53` requires `POST`, the exact regex `/api/v1/operations/catalog/versions/[^/;%]+/(publications|offsales)` and `(contextPath + servletPath).equals(requestURI)`; anything else, including matrix segments, percent-encoded separators, alternate methods and context mismatches, returns the sanitized `404` with no authentication attempt. Only then `authenticator.authenticate(...)` (`EmployeeBearerAuthenticator.java:16-33`: missing/duplicate/malformed header and audience mismatch → 401; verifier absence/ambiguity/unknown error → 503), then the single `Content-Type` check → 422, then the `Accept` negotiation, then the controller's principal check → 401, then structural parsing → 422, then the ACTIVE+ADMIN witness → 403, then state → 404/409/422/503. `BufferedResponse` guarantees no non-`problem+json` ≥400 escapes the filter. The Customer filter's pass-through (`CustomerBoundaryFilter.java:48-53`) is the byte-identical predicate and neither authenticates nor wraps an admitted catalog request, so the two surfaces cannot impersonate each other. `OperationsCatalogVersionWebTests` covers exactly this ordering by name (`authenticationPrecedesStructuralParsing`, `structuralValidationPrecedesAuthorityWitness`, `disabledEmployeeReturnsForbiddenAfterValidParsing`, `concealsOtherCatalogMethodsAndUris`, `classifiesReadsSubjectsAndCatalogCommandsSeparately`, `catalogCommandsDoNotRequireIdempotencyKey`).
- **Lifecycle and concurrency.** `JooqCatalogSaleLifecycleRepository.transition` takes `pg_advisory_xact_lock(hashtextextended('catalog_order.publication:' || productId, 0))` before reading target/active/`clock_timestamp()`, so the whole decision is serialized per product and the lock outlives the transaction. Ordering is enforced: OFFSALE candidate or DRAFT offsale → `CATALOG_PUBLICATION_CONFLICT`; expected-active or revision mismatch → `PUBLICATION_STALE_VIEW`; already-in-target-state with matching revision → zero-write current-state replay (200). Both mutations are CAS `UPDATE … WHERE sale_status=… AND revision=?` under `exactlyOne`, retirement strictly precedes activation, `increment` refuses `Integer.MAX_VALUE`, and a re-read builds the response. A displacement therefore writes one audit fact and two Outbox rows, which `docs/14` §9.26 sanctions.
- **Audit / Outbox.** Dedupe key is `catalog_version:<versionId>:<published|offsale>`, shared between the audit fact and the candidate Outbox event so the two are correlatable, and distinct per version on a displacement. Because a version can occupy each transition at most once (re-publishing an OFFSALE version is a conflict), the key space cannot collide.
