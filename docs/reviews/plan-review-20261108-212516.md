## 3. Findings

### PA20-REV-A-01-未修复-中-Positive IT bearer is not reconciled with the new bearer grammar against the reused fixture credential
- **位置**: Plan §3.1 step 3 (line 70), §8.6 (lines 255-266), §8 intro (line 198); `backend/src/test/java/com/onecall/archtests/container/MediaPlaybackIT.java:37,303,465,511`.
- **问题类型**: 不可直接实施 / 测试缺口 / fixture reuse 未收敛.
- **当前写法**: The gateway accepts exactly one `Authorization` value of the form case-insensitive `Bearer` + one space + 1-2048 ASCII matching `[A-Za-z0-9._~+/-]+={0,}`. The IT section says it reuses the PA19 fixture, builds a fresh service and a "test verifier with independently bound claims", but never pins the positive HTTP bearer value or states that the fresh verifier accepts a token distinct from the reused canary.
- **反例/失败场景**: The existing fixture's credential is `CANARY = "PA19_PRIVATE_cos://bucket/key?version=secret"` (`MediaPlaybackIT.java:37`) and is passed as `OpaquePlaybackCredential` (`:303,:465`); the fixture verifier asserts `credential.value().equals(CANARY)` (`:511`). `CANARY` contains `:` and `?` and a mid-string `=`, so it cannot match `[A-Za-z0-9._~+/-]+={0,}`. If the new IT reuses the existing service/verifier pattern (the natural fixture-reuse template) or sends `CANARY` as the bearer, every positive full-GET/range request is rejected at the bearer layer with 401 before the verifier, so the `200`/`206` methods cannot pass.
- **为什么有问题**: The plan separately pins every other transport byte (grammar, route, statuses, headers) but leaves the one value that must cross both the PA19 fixture and the new grammar unstated. "Build a fresh service" removes the stronger constraint in principle, but it does not say the positive token must be grammar-valid, and the redaction requirement (`§8.6 #6`, "canaries for credential") invites reuse of `CANARY` as the credential probe.
- **直接证据**: `MediaPlaybackIT.java:37` (`CANARY`), `:303`/`:465` (`new OpaquePlaybackCredential(CANARY)`), `:511` (`assertThat(credential.value()).isEqualTo(CANARY)`); plan line 70 grammar; plan lines 255-266 reuse text.
- **影响**: The real-HTTP IT can be red or silently degraded to "all requests 401", invalidating the only integration proof of exact bytes, open/read/close counts and transaction/lock claims.
- **建议改法和验证点**: Pin a grammar-valid positive HTTP bearer (for example a URL-safe token) that the fresh test verifier maps to the fixture claim, keep `CANARY` only for database canary rows and negative/redaction presentation probes, and add the positive-token/negative-canary split to §8.6. Verify by asserting `200`/`206` for the positive token and `401` for the `CANARY` presentation probe.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### PA20-REV-A-02-未修复-低-Namespace terminal/pass-through predicate is not pinned, so route-alias assertions are not deterministic
- **位置**: Plan §3.1 step 1 (lines 64-68), §8.1 `gatewayRouteMethodQueryAndBodyAreClosed` (line 207).
- **问题类型**: 契约缺失 / 测试缺口.
- **当前写法**: "For paths outside `/internal/media-gateway` the gateway filter calls `chain.doFilter` exactly once" and, in the same paragraph, "It owns exact route matching, including rejecting prefix aliases, trailing slash, additional segments, semicolon, percent/encoded spellings ...".
- **反例/失败场景**: For lookalikes such as `/internal//media-gateway/v1/playback`, `/internal/media-gatewayx`, or `/Internal/media-gateway/v1/playback`, the two sentences allow opposite behavior: terminal gateway 404 vs pass-through to `CustomerBoundaryFilter`. In the full app both can surface as 404 (the customer filter 404s non-allowlisted paths), but the unit test invokes the gateway filter with a mock chain and asserts "aliases ... 404" and "nonnamespace filter passes through untouched" (`line 207`). If the implementation treats a lookalike as outside the namespace, the chain is invoked and the unit assertion fails; if it treats any `/internal/...` as inside, it may terminate unrelated future internal routes.
- **为什么有问题**: The unit test is the only place the gateway's routing is isolated from the customer filter's catch-all 404, so the exact namespace predicate is load-bearing. It is not currently pinned as an exact boolean/set.
- **直接证据**: Plan lines 64-68 and line 207; `CustomerBoundaryFilter.java:51-69` (non-allowlisted paths 404, confirming the full-app masking).
- **影响**: Route/method unit test can disagree with the implementation; alias handling may leak to the customer filter or over-capture unrelated `/internal` paths.
- **建议改法和验证点**: Pin the terminal predicate and alias set (for example terminate iff the raw decoded path is exactly `/internal/media-gateway` or begins with `/internal/media-gateway/`, and enumerate the enumerated lookalikes that must 404) and use the same predicate in test and implementation.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### PA20-REV-A-03-未修复-低-`ByteInterval` ownership is ambiguous between the parser and the evidence byte API
- **位置**: Plan §4 (lines 106-121, especially "These nested types remain in this one file" and line 119), §5.1 (lines 127-152), §8.5 `gatewayUsesExactOwnedFilesAndEvidenceNamedInterface` (line 250).
- **问题类型**: 架构边界 / 不可直接实施.
- **当前写法**: §4 says `SingleByteRange` defines the sealed spec/`ParseResult`/`Resolution` types and "these nested types remain in this one file", with `Resolution.Selected(ByteInterval interval, boolean partial)`. §5.1 defines `record ByteInterval(...)` inside `ControlledMediaByteSource` (evidence) and `OpenRequest(ResolvedMediaObject media, ByteInterval interval)`. §8.5 requires "byte API has exact signatures/nested types and contains no sharing dependency".
- **反例/失败场景**: An implementation can read §4 as defining `SingleByteRange.ByteInterval` and §5.1 as defining a second `ControlledMediaByteSource.ByteInterval`. `OpenRequest` would then need a conversion; if the gateway passes the parser type, it does not compile; if it defines the evidence type, it contradicts the "remain in this one file" idiom. A duplicate type also makes the descriptor-equality test (`session.request().equals(request)`) and the "no sharing dependency" assertion fragile.
- **为什么有问题**: The plan is otherwise byte-exact about public API signatures; the one shared value type that crosses the parser/provider boundary is not given a single owner.
- **直接证据**: Plan lines 108, 119, 133-137, 250.
- **影响**: Implementation churn or a wrong evidence->sharing dependency direction (which would fail `ModuleBoundaryTests`/the new gateway architecture test).
- **建议改法和验证点**: State that exactly one `ByteInterval` exists, defined in the evidence named interface (`ControlledMediaByteSource.ByteInterval`), and that `SingleByteRange.Resolution.Selected` references it; keep the parser's sealed spec/result types nested in `SingleByteRange.java` only.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### PA20-REV-A-04-未修复-低-Deterministic servlet write-failure injection vs. real-HTTP IT and the terminal `HIGHEST_PRECEDENCE` filter
- **位置**: Plan §8 intro (line 198), §8.6 #5 (line 261), §8.6 #6 (line 262).
- **问题类型**: 测试缺口 / 不可直接实施.
- **当前写法**: §8 says "real container tests use embedded Tomcat/Java HttpClient". §8.6 #5 says "Inject deterministic ServletOutputStream failures using the actual filter/service/PG fixture (not unreliable TCP-disconnect timing)"; #6 is a real-HTTP/log/redaction method.
- **反例/失败场景**: The gateway filter is terminal and registered at `Ordered.HIGHEST_PRECEDENCE` (plan line 64). A test `FilterRegistrationBean` wrapper that must wrap the response before the gateway cannot be ordered below `Integer.MIN_VALUE`, and a tie at `HIGHEST_PRECEDENCE` has no defined relative order. If #5 is implemented as real HTTP, there is no deterministic way to make `ServletOutputStream.write` throw at a chosen offset; if it is implemented by invoking the real filter with a throwing mock response (while still using the real PG/service fixture), it is not "real container" as §8 intro describes. The plan does not pin which mechanism is intended.
- **为什么有问题**: The committed-response and cleanup-count contract is the highest-risk part of the state machine; the test mechanism must be unambiguous for the implementation agent and for the CI's real-HTTP guarantee.
- **直接证据**: Plan line 64 (`HIGHEST_PRECEDENCE` terminal), lines 198, 261, 262.
- **影响**: #5 can be unimplementable as written, silently weakened to a mock-only proof, or conflict with the "real container" classification.
- **建议改法和验证点**: Pin #5 as a direct invocation of the real filter with a deterministic throwing `HttpServletResponse`/`ServletOutputStream` while using the real PG-backed service, and keep #6 as the real-HTTP socket/truncation proof; alternatively, define an explicit test-only response-wrapper registration ahead of the gateway and assert its order.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.
