### 1-未修复-严重-新 ACCEPT 对 SUSPENDED 头映射为 409 CONSENT_REQUIRED，违反用户确认的 FORBIDDEN 边界

- **位置**: Plan §3 ordered decision table row 10 (line 75); plan line 79 (“A legitimate new ACCEPT on SUSPENDED cannot reactivate” without code); plan risk table line 433 (“new ACCEPT is CONSENT_REQUIRED”); planned tests `suspendedRejectsNewAcceptButNeverMutatesOnHistoricalReplay` (§7) and `suspendedCannotBeReactivatedByNewCustomerEvent` (§7); Goal registry G5 (line 25) states the invariant but not the public code.
- **问题类型**: 动机不成立 / 目标漂移 / 契约缺失（binding-goal violation；错误语义误用）
- **当前写法**: “| 10 | New event, valid policy, ACCEPT, current head SUSPENDED | **409 CONSENT_REQUIRED**, no writes; never use global-catalog `ACTIVATION_STATE_CONFLICT`, which C5 does not permit |” and risk row “new ACCEPT is CONSENT_REQUIRED”.
- **反例/失败场景**:
  1. Client sends a **new** valid ACCEPT while subject head is `SUSPENDED`. Plan returns `409 CONSENT_REQUIRED`. User-confirmed boundary requires **403 FORBIDDEN**. Implementation agent generating from this plan will hard-code the wrong status/code into problem mapping and tests (`suspended*` methods assert CONSENT_REQUIRED), locking the violation into the S1 deliverable and CI oracles.
  2. `CONSENT_REQUIRED` is frozen in docs/15 as policy/prompt/content staleness (“当前开通提示/政策缺失、过期或内容无效”). A lifecycle `SUSPENDED` head with a **valid current policy** is not that condition. Callers and operators will mis-classify a lifecycle refusal as a consent/policy defect; runbooks and alert routing keyed to CONSENT_REQUIRED will fire on the wrong class of failure.
  3. The plan explicitly considered and rejected `ACTIVATION_STATE_CONFLICT` (not in C5) but never evaluated `FORBIDDEN`, which **is** in the frozen nine-code set and already used at order 4 for access/resource predicates. The chosen code stretches frozen semantics instead of using the available correct channel.
- **为什么有问题**: Dispatch states the user-confirmed boundary is FORBIDDEN and requires adjudication as binding goal alignment. Control :26 binds the no-reactivation invariant; Control does **not** authorize CONSENT_REQUIRED for this case. Goal Confirmation is a binding scope contract: selecting a different public error code for a confirmed boundary is goal drift, not an implementation detail. docs/15 defines FORBIDDEN as resource/access-predicate refusal — the closer frozen semantic for “subject exists, is accessible, but customer command may not move SUSPENDED→ACTIVE”.
- **直接证据**:
  - Dispatch: “The user-confirmed boundary says a new ACCEPT against a SUSPENDED subject returns FORBIDDEN. The plan currently appears to choose 409 CONSENT_REQUIRED for that case. Verify and adjudicate this as binding goal alignment rather than treating the plan's choice as authority.”
  - Plan line 75: order 10 → `409 CONSENT_REQUIRED`.
  - Plan line 433: “new ACCEPT is CONSENT_REQUIRED”.
  - Control :26: “A SUSPENDED subject cannot be reactivated by this customer command; only the existing Operations lifecycle may perform `SUSPENDED -> ACTIVE`.”
  - docs/15 :179 `FORBIDDEN` 403 access/resource predicate; :188 `CONSENT_REQUIRED` 409 policy/prompt/content.
  - OpenAPI frozen error set includes FORBIDDEN; does not assign CONSENT_REQUIRED to lifecycle SUSPENDED.
- **影响**: Implementation generates wrong public contract; tests and CI encode the wrong mapping; user-visible error class is wrong; Controller goal confirmation is not honored; post-implementation rework across problem writer, ordered decision table, and at least two named tests; risk of shipping a non-conforming operation against frozen docs/15 semantics.
- **建议改法和验证点**:
  1. Change plan §3 order 10 (and line 79 / risk table :433) to: new event + valid policy + ACCEPT + head `SUSPENDED` → **`403 FORBIDDEN`, zero writes** (no consent/head/transition/trial/Outbox/audit).
  2. Keep order 4/5 precedence unchanged (access FORBIDDEN before NOT_FOUND; SUSPENDED case is after ownership/lifecycle valid, so no subject-existence disclosure change).
  3. Rewrite both suspended tests to assert `403 FORBIDDEN` and no mutation; keep historical exact-replay-while-suspended returning frozen first result as a separate assertion.
  4. Explicitly cite user-confirmed FORBIDDEN + Control :26 + docs/15 FORBIDDEN definition in the goal-alignment note; do not invent a new code.
  5. Verification point: regenerated problem-mapping table shows SUSPENDED new-ACCEPT → FORBIDDEN; unit/IT assertions match; no test still expects CONSENT_REQUIRED for that branch; frozen OpenAPI error set unchanged (FORBIDDEN already present).
- **修复风险（低）**: Low — localized to order-10 mapping, risk row, two test names/bodies, and problem writer branch; no schema/lock/inventory redesign required.
- **严重程度（严重）**: Severe — direct violation of a user-confirmed binding boundary with user-visible, test-locked wrong behavior.

### 2-未修复-高-版本化 replay descriptor 被发明为 consent snapshot 内的持久化契约，超出 Control/docs14 已确认的冻结结果要求

- **位置**: Plan §4 “Freeze the first result without a new result table” (lines 103–111); §3 order 7 (line 72); §5 descriptor allocate/validate path (lines 107, 111, 134); §6 file `DefaultCustomerSubjectActivationService` “descriptor validation” (line 158); S1 checkpoint 2 “replay descriptor” (line 193); risk table descriptor corruption → INTERNAL (line 434).
- **问题类型**: 目标漂移 / 过度设计 / 契约缺失 / 过度耦合（invented persistence format coupling consent snapshot to activation result projection）
- **当前写法**: Invent a bounded redacted descriptor with exact root keys `schemaVersion` integer 1, `policyCode`, `policyVersion`, `promptVersion`, `contentSha256`, `activationResult` (null for DECLINE; for ACCEPT object with `activationStatus`/`activationRevision`/`transitionId`/`trialOutcome`/`trialPolicyVersionId`), hash into consent `snapshot_sha256`, validate shape/hash on every replay; corrupt descriptors fail INTERNAL with no repair.
- **反例/失败场景**:
  1. Control :26 requires the **behavior** “returns the first frozen ACCEPT result”, and docs/14 §9.25 step3 / §10.20 describe replay as returning the first consent/transition/activation/trial result from **existing immutable rows**. Nothing in Control, docs/14 §10.17 fingerprint registry, §10.20 `record_client_activation`, or V007 `consent_record` defines a nested `activationResult` document or `schemaVersion` descriptor as part of consent snapshot identity. An implementation agent may treat the descriptor as a frozen-design contract and design INTERNAL failure paths, tests, and corruption handling around an invented format.
  2. Reconstruction from existing rows is at least partially sufficient for the bound behaviors: `consentId` from consent; `transitionId`/`activationRevision`/`to_status` from the original transition; permanent trial units/expiry/outcome from `trial_grant`/`entitlement_grant` (plan §4 already requires loading these on replay). Freezing `trialOutcome=GRANTED` instead of a later `REPLAY` can be derived from the original granting trial row keyed by source domain/event — the plan itself loads “the unique original trial by subject with matching grant/balance”. The descriptor largely duplicates durable facts already owned by V006/V007 while adding a second representation that can disagree (plan acknowledges “descriptor hash and bounded shape” validation and INTERNAL on mismatch).
  3. Hashing `activationResult` into `snapshot_sha256` changes what consent snapshot digest means relative to docs/14 §4.29/§10.17 expectations that the snapshot is the consent evidence payload; future readers comparing snapshot content to frozen fingerprint inputs may mis-understand why trial/transition projection fields live inside consent.
  4. Failure surface: any descriptor shape/hash drift becomes INTERNAL (line 434) with “no repair/synthesis”, creating a new class of unrecoverable replay outages that pure row reconstruction would not introduce.
- **为什么有问题**: Goal-bound minimal design requires each durable artifact to map to a confirmed goal or necessary correctness/safety condition. Freezing the first *result* is confirmed; *how* is not confirmed as a new versioned document inside consent snapshot. This is goal drift toward an unstated persistence contract and couples activation result projection to consent immutable payload — overcoupling two independently owned historical facts (consent vs activation/trial). Optimal-solution lens: prefer reconstructing the public `ActivationResult` from existing immutable consent + transition + trial/grant rows (already required for validation), and only if Controller identifies a concrete reconstruction hole that those rows cannot close, return to goal confirmation rather than silently inventing `schemaVersion:1` descriptor format.
- **直接证据**:
  - Control :26: “exact same `activationEventId` and semantic fingerprint returns the first frozen ACCEPT result or the same DECLINE refusal” — behavior, not format.
  - docs/14 §9.25 step3: “Same fingerprint returns the first consent/activation/trial result and performs no effect” — existing rows.
  - docs/14 §10.17: frozen fingerprint registries; no descriptor schema.
  - V007 `consent_record`: `snapshot jsonb` + `snapshot_sha256`; immutable trigger; no activationResult column/table.
  - Plan lines 105–111 define the full invented schema and INTERNAL-on-corruption policy.
  - Plan line 434 residual: “Replay descriptor corruption … INTERNAL, no repair/synthesis.”
- **影响**: Implementation effort and test surface expand around a non-confirmed format; risk of INTERNAL on legitimate historical data if any field set diverges; consent snapshot semantics drift from frozen docs; Controller may reject S1 for inventing persistence contract; unnecessary coupling of replay projection to consent digest.
- **建议改法和验证点**:
  1. Preferred: remove the descriptor document; define replay reconstruction strictly from immutable consent + transition + original trial/grant/balance rows (and latest ACTIVE anchor for later-ACTIVE no-transition events per Control “current latest transition anchor”).
  2. If a frozen-result gap remains after explicit row-by-row reconstruction analysis, **stop for Controller goal confirmation** of the descriptor schema — do not ship it as plan-resolved (plan §6 stop rule already requires stop on unexpected schema needs; apply the same discipline to invented payload contracts).
  3. Do not hash projection fields into `snapshot_sha256` unless Goal Confirmation explicitly expands consent snapshot contents.
  4. Verification point: either (a) no descriptor keys remain in plan §4/§5 and replay tests pass using only V006/V007 row facts, or (b) Controller-approved descriptor spec is cited as a binding addendum before implementation.
- **修复风险（中）**: Medium — requires reworking §4/§5 replay narrative, several unit/IT cases, and possibly dropping INTERNAL descriptor-corruption paths; no migration required if removed.
- **严重程度（高）**: High — invented durable contract + extra failure class + goal-drift risk on a frozen-adjacent persistence boundary; not user-visible on happy path but blocks code-generation readiness without re-confirmation.

### 3-未修复-中-DECLINE 决定审计超出 Control「only refusal fact」，并发明新 audit action code

- **反例/失败场景**:
  1. Control :25: “`DECLINE` appends **only** the replayable `SERVICE_ACTIVATION/DECLINE` refusal fact and returns `409 ACTIVATION_CONSENT_DECLINED`”. Plan order 9 adds a second durable write (audit) on DECLINE. An implementation following Control literally would omit it; an implementation following the plan would add it — split-brain acceptance between Controller goal text and plan.
  2. `CUSTOMER_ACTIVATION_DECIDED` / `CLIENT_ACTIVATION_*` appear **nowhere** in source, migrations, docs/14 action-code inventories, or Control (grep over repo: plan only). docs/14 §9.25 step6 says “Append Outbox/audit and commit” for the activation path generally, which supports *some* audit on fresh activation, but does not freeze this action code, reason codes, or `{decision,activationChanged}` snapshot shape.
  3. Plan makes audit failure roll back consent/head/transition/trial together (line 138). That is correct atomicity **if** audit is required; if audit is optional/invented, the plan has added a new rollback dependency and failure mapping (audit exception → whole transaction abort) without Goal Confirmation — expanding the failure surface of ACCEPT/DECLINE for non-confirmed evidence.
- **为什么有问题**: Goal-bound minimal design: durable side effects must map to confirmed requirements. Control binds DECLINE’s write set as “only” the refusal fact. ACCEPT Control text lists consent/transition/issue_first_trial and does not mention decision audit. docs/14’s “Outbox/audit” is necessary evidence that *some* audit may be intended on fresh activation, but the plan’s dual-use new action code and mandatory DECLINE audit exceed the binding write-set language and invent public-adjacent audit taxonomy without confirmation. This is scope creep on the audit boundary, not a style issue.
- **直接证据**:
  - Control :25 “appends only the replayable … refusal fact”.
  - Control :24 ACCEPT write set: consent + transition + issue_first_trial (no audit named).
  - docs/14 §9.25 step6: “Append Outbox/audit and commit.”
  - Plan lines 74, 134, 138.
  - Repo grep: `CUSTOMER_ACTIVATION_DECIDED` / `CLIENT_ACTIVATION_ACCEPTED` / `CLIENT_ACTIVATION_DECLINED` only in the plan file.
  - V004 already EXECUTE-grants `audit.append_fact` to `activation_consent_role` (privilege exists; question is goal authority, not ACL).
- **影响**: Risk of Controller rejecting S1 for extra DECLINE write; contradictory acceptance criteria; unnecessary audit-induced rollback coupling; if retained without confirmation, goal-drift finding at implementation review; if stripped ad-hoc by implementer, plan §7 tests asserting decision audit fail.
- **建议改法和验证点**:
  1. Return to Controller: (a) DECLINE write set = consent only vs consent+audit; (b) whether a decision audit is required on ACCEPT; (c) if yes, frozen action/reason/snapshot shape.
  2. Until confirmed, plan should mark decision audit as **open question / residual**, not as resolved G3/G4 design, and should not name new action codes as settled.
  3. Prefer aligning strictly to Control :25 for DECLINE (consent only) and to docs/14 §9.25 step6 only for fresh ACCEPT if Controller confirms Outbox+audit pairing.
  4. Verification point: write-set table for DECLINE matches Control word-for-word; any audit action code is cited from a confirmed source or removed; tests assert exact durable rows.
- **修复风险（低）**: Low — text + one audit append path + related tests; grants already exist.
- **严重程度（中）**: Medium — real goal-drift / write-set ambiguity with rollback coupling; less severe than SUSPENDED mapping because it does not contradict a user-confirmed public error boundary as directly.
