### PA38-PLAN-A-01-未修复-[严重]-Proposed command-port direction creates a Spring Modulith dependency cycle and fails the existing module oracle

- **位置**: Plan §5 (`:155-184`), §6.1 file 1 (`:190-195`), §6.2 (`:220-223`); Goal Confirmation "Overdesign judgment" and module ownership.
- **问题类型**: 架构边界 / 过度耦合 / 非最优方案 / 不可直接实施.
- **当前写法**: §5 bullet 1 says "`operations_iam` owns ... the public command port", but §5's following paragraph and §6.1 file 1 place `OperationsCatalogSaleCommand` in `catalog_order/operationscommand`, and §6.2 adds `catalog_order::operations-catalog-command` to `operations_iam`'s module declaration. `operations_iam` is therefore made to depend on `catalog_order`.
- **反例/失败场景**: `catalog_order/package-info.java` already declares `allowedDependencies = {"customer_iam", "subject_number", "operations_iam::operations-subject-read"}` and `JooqOperationsCatalogProductReader` implements an `operations_iam` named-interface port. Adding the proposed reverse edge makes the module graph cyclic (`operations_iam -> catalog_order -> operations_iam`). `ModuleBoundaryTests.verifiesNoCyclesOrBoundaryViolations` calls `ApplicationModules.verify()`, which rejects cycles (the test suite itself proves cycles throw via `rejectsCycleFixture`). `ModuleBoundaryTests.assertsExactAllowedDependencyMapFromPlan62` also asserts the exact map (`operations_iam` = `{operations_audit}`; `catalog_order` = `{customer_iam, subject_number, operations_iam::operations-subject-read}`), and `discoveredProductionEdgesStayInsideTheConfiguredMap` asserts exactly thirteen production edges. The implementation cannot pass the existing module gate.
- **为什么有问题**: The established project pattern (PA32/PA37) is that `operations_iam` owns the named command/read port and the owning domain (`activation_consent`, `catalog_order`) implements it, preserving the dependency direction. The plan inverts that direction while also contradicting its own §5 statement that `operations_iam` owns the port. This is not just a suboptimal choice: it is structurally unsafe and blocks the module verifier.
- **直接证据**: `backend/src/main/java/com/onecall/core/catalog_order/package-info.java:1`; `backend/src/main/java/com/onecall/core/operations_iam/package-info.java:1`; `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsread/JooqOperationsCatalogProductReader.java:3-6,24`; `backend/src/test/java/com/onecall/archtests/architecture/ModuleBoundaryTests.java:40-55,76-115,117-120,159-165`; plan `:157-167,190-195,220-223`.
- **影响**: The implementation either fails `ApplicationModules.verify()`/the exact-map/edge tests or must modify architecture guards outside the declared file allowlist. Either way the plan is not code-generation-ready and cannot pass the full gate.
- **建议改法和验证点**: Define the command port in `operations_iam` (e.g., a new `operations_iam` named interface, mirroring `subjectlifecycle`), have `catalog_order` implement it, and keep the dependency direction `catalog_order -> operations_iam`. If a reverse edge is genuinely intended, stop and renew the architecture decision with an explicit module-map change and authorization to update `ModuleBoundaryTests`; do not add the edge silently. Verification: `ModuleBoundaryTests` exact map/edge count/`verify()` and a boundary test proving the command port is the only `operations_iam` surface.
- **修复风险（低/中/高）**: 中 (requires moving the port/DTO ownership and adapting the configuration, but preserves the established pattern).
- **严重程度（低/中/高/严重）**: 严重.

### PA38-PLAN-A-02-未修复-[高]-Authority re-read cannot run under the single catalog role and the plan does not specify the operations-role handoff or login membership

- **位置**: Plan §3.5 (`:115-118`), §5 role handoff (`:169-183`), §8.1 steps 2-3 (`:290-292`), §9.1 role tests (`:388-389`), §9.2 privilege tests (`:430-436`).
- **问题类型**: 权限/架构边界 / 不可直接实施 / 契约缺失.
- **当前写法**: §5 says "enter the catalog owner runtime role inside the transaction, assert `current_user`, execute all authority/state/mutation/fact SQL on that same connection". §8.1 says "Assert the authenticated employee is still ACTIVE and ADMIN in the same transaction" and then "Enter/assert the catalog-order runtime role". §3.5 claims "The existing Operations runtime datasource/role switching path can enter the catalog owner role and restore the login role; no broader grant is needed."
- **反例/失败场景**: `catalog_order_role` is granted `USAGE` on `customer_iam`, `organization_access`, `subject_number`, `activation_consent`, and `entitlement_metering`, plus `SELECT/INSERT` and selected `UPDATE` on `catalog_order` tables. It has **no** privilege on `operations_iam.employee_account`; only `operations_iam_role` has `SELECT` there. The lifecycle login is `NOINHERIT` and cannot read `operations_iam.employee_account` directly. If the plan enters `catalog_order_role` first and then executes the authority `SELECT`, the transaction fails with `42501`; if it omits the role switch, it also fails. The existing `EmployeeAdministratorLock` proves the required pattern: it temporarily `SET LOCAL ROLE operations_iam_role` for the authority read and restores the prior role.
- **为什么有问题**: The plan's sufficiency proof says "no broader grant is needed", but the algorithm needs a role other than `catalog_order_role` for the authority read. The allowed role transition and the exact login membership are part of the effective database path, not merely source grants. The plan also uses the ambiguous term "catalog owner runtime role" without pinning `catalog_order_role` versus `catalog_order_owner`; `catalog_order_owner` is not a member of the operations login in PA25 and is not the least-privilege runtime role.
- **直接证据**: `V004__catalog_order_and_payment.sql:421-444`; `V002__identity_organization_and_employee.sql:345-350`; `V018__evidence_role_ivr_association_read_privileges.sql:4-9,767-800`; `backend/ops/postgresql/pa25-runtime-identities.sql:39-44,4091-4104`; `DefaultEmployeeAdministratorLock.java:36-43`; plan `:115-118,169-183,290-292`.
- **影响**: The command fails closed with `SERVICE_UNAVAILABLE` (or a raw `42501` that the sanitizer must hide), so publication/offsale never works; the authority-before-input requirement is also unproven. The privilege tests will either fail or be written to a different role than the implementation.
- **建议改法和验证点**: Specify the exact role sequence: start as the lifecycle login, `SET LOCAL ROLE operations_iam_role`, assert `current_user`, read `operations_iam.employee_account(id,status,role,revision)` under that role, then `SET LOCAL ROLE catalog_order_role`, assert, perform lock/reads/lifecycle updates/audit/Outbox, restore to the prior role/login in `finally`. Pin the exact role name (`catalog_order_role`, not `catalog_order_owner`). Add a container assertion that the catalog role cannot read `operations_iam.employee_account` and that the authority witness is read under `operations_iam_role`; assert the login's PA25 membership (`SET TRUE`, `INHERIT FALSE`) in the test fixture/provisioning check.
- **修复风险（低/中/高）**: 中.
- **严重程度（低/中/高/严重）**: 高.

### PA38-PLAN-A-03-未修复-[高]-Offsale stale revision is mapped to the wrong frozen error code

- **位置**: Plan §8.3 (`:339-352`, especially `:344-347`), §7.1 (`:243-247`); OpenAPI offsale description (`:1780-1788`); docs15 `:202`, `:244`; docs17 `:645`.
- **问题类型**: 契约缺失 / 状态机漏洞 / 错误优先级.
- **当前写法**: §8.3 says "A stale revision, DRAFT candidate, non-current ACTIVE, missing current condition, or other unexpected state is `CATALOG_PUBLICATION_CONFLICT` with no write." §8.2 says a publication mismatch is "`PUBLICATION_STALE_VIEW` inside `CATALOG_PUBLICATION_CONFLICT`".
- **反例/失败场景**: Offsale with `expectedRevision` equal to the pre-transition revision after a lost response (or any stale revision) will be emitted as `CATALOG_PUBLICATION_CONFLICT`. The frozen OpenAPI offsale description explicitly says a stale revision returns `CATALOG_PUBLICATION_CONFLICT`/`PUBLICATION_STALE_VIEW`; docs15 defines `PUBLICATION_STALE_VIEW` for "expected ACTIVE version/revision no longer matches"; docs17's high-risk map gives `PUBLICATION_STALE_VIEW` as the `conflictCode` for **both** `publishOperationsCatalogVersion` and `offsaleOperationsCatalogVersion`. `PUBLICATION_STALE_VIEW` is a peer `Problem.code` in the frozen error registry, not a nested detail of `CATALOG_PUBLICATION_CONFLICT`.
- **为什么有问题**: The error code is the only machine branch key in the Problem envelope. Returning the wrong peer code breaks the frozen contract and docs17's high-risk map, and makes the web/container tests unable to prove the required stale distinction.

- **影响**: Callers cannot distinguish stale expectations from an unexpected state; the frozen error-set assertion (`NOT_FOUND`, `CATALOG_PUBLICATION_CONFLICT`, `PUBLICATION_STALE_VIEW`) is implemented with the wrong member; docs17 acceptance fails.
- **建议改法和验证点**: Make publication and offsale stale expectations return `PUBLICATION_STALE_VIEW` with HTTP 409; reserve `CATALOG_PUBLICATION_CONFLICT` for non-stale unexpected/concurrent state. State both as peer `Problem.code` values. Add exact-code assertions to `staleOffsaleMakesNoChange`, `stalePublicationMakesNoChange` and `mapsFrozenErrors`.

### PA38-PLAN-A-04-未修复-[高]-The existing boundary filter requires `Idempotency-Key` for every POST, contradicting the two new state-conditional routes

- **位置**: Plan §7.1 item 7 (`:254-256`), §6.2 filter edit (`:224-226`), §9.1 `doesNotRequireIdempotencyKey` (`:403`).
- **问题类型**: 契约缺失 / 不可直接实施 / 错误优先级.
- **当前写法**: "Do not read or require `Idempotency-Key` for either route. Its presence is not a new idempotency mechanism; if the frozen boundary rejects it for these state-conditional commands, map to validation without side effects."
- **反例/失败场景**: `OperationsBoundaryFilter` applies one unconditional `!read` branch to every POST: it requires exactly one `Idempotency-Key` header of 1-128 valid text before it checks Content-Type and dispatches. The two new POST routes are not GET reads. A missing or repeated key therefore produces `VALIDATION_FAILED` 422 before the controller ever runs, and the planned `doesNotRequireIdempotencyKey` test cannot pass. The hedge "if the frozen boundary rejects it" does not define a different outcome because the frozen boundary does reject it.
- **为什么有问题**: The plan says the routes are state-conditional and must not use `Idempotency-Key`, but it does not specify how the shared filter distinguishes the subject-lifecycle POSTs (where the key is mandatory) from the catalog POSTs (where it must not be required). A code-generation agent must invent this branch, violating the "exact request binding" requirement.
- **直接证据**: `operations_iam/internal/web/OperationsBoundaryFilter.java:46-55`; `OperationsSubjectsWebTests.java:96-101` (current key-mandatory behavior); OpenAPI `x-onecall-idempotency: state-conditional` at `:1736,1812`.
- **影响**: The new routes return 422 for every request without a key; the planned route behavior is unreachable; the web test identity is not executable.
- **建议改法和验证点**: Specify an exact branch: either admit the two catalog POST templates before the subject-lifecycle key check and skip key validation for them, or split the filter path classification into "subject lifecycle (key required)" and "catalog publication (key ignored/rejected by exact rule)". Add tests for missing, repeated, empty and valid keys on both route families; preserve the subject lifecycle key behavior.

### PA38-PLAN-A-05-未修复-[高]-Controller-local binding plus a parsed command record makes authority-before-input precedence impossible

- **位置**: Plan §6.1 file 1 (`:190-195`) and file 8 (`:214-216`), §6.2 last paragraph (`:230-233`), §7.1 items 3-4 (`:244-247`), §9.1 `authorityPrecedesMalformedBody` (`:400-401`).
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施.
- **当前写法**: The command port takes already-parsed `PublishCommand`/`OffsaleCommand` records (caller, UUID, nullable expected active UUID, positive expected revision). §6.2 says "Strict catalog JSON binding is controller-local in the new controller." §7.1 says authority must be checked "Only then parse the path UUID/body." - **反例/失败场景**: The controller must parse the path and body to construct the command record before it can call `publish(PublishCommand)`/`offsale(OffsaleCommand)`. The authority check live in the command transaction (after the port call). Therefore an OPS or disabled employee with malformed input receives 422 `VALIDATION_FAILED`, not 403/401. The shipped PA37 read path avoids this by passing a `RawDetailRequest` into the service and calling `authority(caller)` before `OperationsCatalogProductReadRequest.detail(raw)`. The shipped subject-lifecycle controller also parses in the controller (and its web test only asserts authentication, not role authority), so the plan cannot claim the stronger write precedence by pattern.
- **为什么有问题**: This is not a test detail; it determines the externally visible precedence contract. The plan's own test identity cannot pass with controller-local parsing and a parsed command port. The plan also does not state whether the binder or the command service owns Content-Type/path/body validation order.
- **直接证据**: `OperationsCatalogProductReadRequest.java:38-44` and `DefaultOperationsCatalogProductReadService.java:44-46,123-155` (authority before parse); `OperationsSubjectsController.java:34-42` (parse before service); plan `:190-195,214-216,230-233,244-247`.
- **影响**: Unauthorized malformed requests leak a distinct 422 path; `authorityPrecedesMalformedBody` fails; the implementation must be redesigned around raw input, adding files or changing the port shape.
- **建议改法和验证点**: Either (a) put a raw-input adapter/port in `operations_iam` that enters the transaction, checks ACTIVE/ADMIN authority, and only then parses the canonical UUID/body, or (b) move binding into the command service and pass raw path/body through the port. Pin the precedence matrix: boundary 404, authentication 401/503, authority 403, path UUID 422, Content-Type 422, body 422, then state conflict. Add tests with OPS and disabled callers plus malformed/invalid media inputs.
- **修复风险（低/中/高）**: 中.
- **严重程度（低/中/高/严重）**: 高.

### PA38-PLAN-A-07-未修复-[中]-Publication/offsale preconditions and replay semantics contradict themselves; `expectedRevision` has no defined meaning when no ACTIVE version exists

- **位置**: Plan §8.2 (`:304-337`), §8.3 (`:339-352`), §8.4 (`:354-366`), §7.2 (`:258-277`); OpenAPI `:5780-5802`; docs15 `:122-123`; Control Goal Confirmation `:22-24`.
- **问题类型**: 状态机漏洞 / 契约缺失 / 并发恢复风险.
- **当前写法**:
  - §8.2: "Candidate must be `DRAFT` and `published_at IS NULL`" and later "A candidate already `ACTIVE` is a current-state replay only when the request can be proven to describe that candidate/current state."
  - §8.3: "Candidate must be the current `ACTIVE` version" and later "A matching already-`OFFSALE` row is an idempotent current-state read."
  - §8.2: "Compare both caller expectations to the locked reread: nullable expected current ACTIVE identity and its positive revision."
  - No rule defines `expectedRevision` when `expectedActiveVersionId` is `null` (no current ACTIVE), or when a lost-response retry carries the **pre-transition** expected values.
- **反例/失败场景**:
  1. No-ACTIVE publication requires `expectedRevision` (OpenAPI requires it) but there is no current ACTIVE revision to compare. An implementation may compare it to the candidate revision (1) or ignore it; the plan does not say which, so stale/replay behavior diverges.
  2. A lost-response publish retry sends `expectedActiveVersionId = <old or null>` and `expectedRevision = <old revision>`. The candidate is now ACTIVE. Under "only when the request can be proven to describe that candidate/current state", the retry is not provable and returns a conflict, not the current `CatalogVersionState`. The success signal says "current-state replays return the current `CatalogVersionState`"; the exact proof rule is missing.
  3. A lost-response offsale retry sends the old revision; the row is now OFFSALE with revision+1. "Candidate must be the current ACTIVE version" rejects it, while "a matching already-OFFSALE row" requires the new revision. The two bullets cannot both hold.
  4. A DRAFT candidate cannot simultaneously be "already ACTIVE"; a non-current OFFSALE version cannot simultaneously be "the current ACTIVE version". The preconditions are written as absolute commands but the replay clauses are exceptions.
- **为什么有问题**: The contract is state-conditional and has no `Idempotency-Key`; the only replay mechanism is current-state matching. Without exact rules, the implementation cannot distinguish stale, replay, and unexpected state, and the tests named `stalePublicationMakesNoChange`, `staleOffsaleMakesNoChange`, `matchingOffsaleReplayIsCurrentStateOnly` do not pin the behavior.
- **直接证据**: Plan `:306,313-316,340-347`; OpenAPI `CatalogVersionPublicationRequest`/`CatalogVersionOffsaleRequest` `:5780-5802`; docs15 `:122-123`; docs14 T-S2-14 `:3451`; Control `:22-24`.
- **影响**: Wrong 409 code or wrong 200 replay; a second revision/audit/Outbox or a lost-response conflict; concurrent loser may be classified inconsistently; review cannot accept the state machine.
- **建议改法和验证点**: Define exact state/expectation matrix: for publish, (a) DRAFT + expected current active identity/revision match -> transition; (b) target already ACTIVE and `expectedActiveVersionId == target` and `expectedRevision == target.revision` -> current-state replay; (c) target ACTIVE with pre-state expectations -> stale; (d) any other state -> conflict. Define `expectedRevision` for `null` expected active explicitly (for example, the candidate's current revision or a sentinel rule). For offsale, (a) current ACTIVE + revision match -> transition; (b) target OFFSALE + revision match -> current-state replay; (c) target OFFSALE with pre-state revision -> stale; (d) DRAFT/non-current -> conflict. Add tests for no-active publication, lost-response replays, and target-OFFSALE-with-another-active.
- **修复风险（低/中/高）**: 中.

## 6. Conclusion

**Verdict: `fail`.**

The plan correctly identifies the two frozen routes, the V004 lifecycle substrate, the retirement-before-activation ordering, the audit/Outbox families and the one-slice shape. However, it is not yet safe to hand to implementation: the proposed command-port direction creates a Modulith cycle and breaks the existing exact module oracle; the authority re-read is specified under a role that has no `operations_iam.employee_account` privilege; the offsale stale code contradicts the frozen OpenAPI/docs15/docs17; the boundary filter still mandates `Idempotency-Key`; controller-local binding contradicts the claimed authority-before-input precedence; and the mandatory existing guard-test/CI lockstep edits are neither authorized nor enumerated. The state-machine replay rules and audit snapshot contract are also insufficiently pinned. These are correctable with a bounded plan fix, but they are material and block implementation.
