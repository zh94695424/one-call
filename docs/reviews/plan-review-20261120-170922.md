### RB-01-未修复-高-复用250ms锁预算下的并发结论与55P03分类互相矛盾
- **位置**: plan §6.1 line 212, §6.2, §6.3, §6.4 line 251, §6.5 lines 253-279, §7.2 items 16-21 and the concurrency protocol at line 437
- **问题类型**: 并发恢复风险 / 契约缺失 / 状态机漏洞
- **当前写法**: §6.1 requires copying the PA38 transaction preamble verbatim, including `lock_timeout = 250ms`; §6.4 states that lock or statement timeout maps to sanitized 503; §6.5 has no lock-timeout row at all; §7.2 mandates four deterministic race identities plus `draftReplaceAndPublicationShareProductLockAndCoherentSnapshot`, and line 437 requires tests that prove the second transaction is *waiting on the intended first transaction before release*.
- **反例/失败场景**: A draft replace and a publication for the same product contend on the single reused advisory key `catalog_order.publication:<productId>`. The holder keeps the lock across authority read, version write, up to four benefit inserts, two offer token updates, one audit append and commit. The waiter exceeds 250ms, PostgreSQL aborts it with 55P03, and under §6.4 the caller receives 503 — while §6.5 and §7.2 items 18-20 promise 200 replay, 409 stale view or a coherent-snapshot outcome. The same contention in the sibling path returns 409 today.
- **为什么有问题**: The shipped and already-accepted PA38 behavior is the opposite: lock timeout is classified as a domain conflict, and the shipped container test asserts exactly that. The plan therefore both contradicts shipped behavior for the same physical lock and leaves its own mandated race identities unsatisfiable, which is precisely the class of ambiguity an implementation agent must not be left to guess.
- **直接证据**: `backend/src/main/java/com/onecall/core/catalog_order/internal/operationscommand/JooqCatalogSaleLifecycleRepository.java:39`; `backend/src/main/java/com/onecall/core/catalog_order/internal/operationscommand/DefaultOperationsCatalogSaleCommand.java:33` maps 55P02/55P03 to `CATALOG_PUBLICATION_CONFLICT`; `backend/src/test/java/com/onecall/archtests/container/OperationsCatalogVersionLifecycleIT.java:93-94` asserts a 409 problem and `fixture.states` containing 55P03 after observing the wait; plan lines 212, 251, 437 and the §6.5 matrix above.
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / CI 不稳定或被迫放宽断言 / 合法同产品并发出现用户可见 503 / 后续返工
- **建议改法和验证点**: Pin one classification for 55P02/55P03 on both new commands and justify any divergence from the shipped catalog write path; add explicit §6.5 rows (including durable-state preservation) for lock-wait exhaustion during create and replace; restate §7.2 items 16-21 so each names its expected status for winner and loser; state how the observation demanded by line 437 fits inside a 250ms wait budget, or bound it by asserting 55P03 plus the chosen code as PA38 does. ### RB-03-未修复-中-canonical投影字节序偏离docs14§2.5且snapshot_sha256不可逆
- **位置**: plan §5.1 lines 178-194, §11 first-principles paragraph, residual list
- **问题类型**: 架构边界 / 契约缺失 / 风险后移
- **当前写法**: P is defined by an explicit semantic member sequence and "Serialization helpers use explicit member order", and §5.1 makes a stored-hash mismatch a data-integrity 503 that is never repaired or backfilled.
- **反例/失败场景**: The frozen design source defines canonical JSON as RFC 8785 compatible with object keys sorted by UTF-16 code units, which for these eleven members is a different byte string, so any future component that follows §2.5 — the customer order snapshot, an audit verifier, or a corrected writer — computes a different digest for the same draft. Because §5.1 treats a bad stored hash as 503 and the non-goals forbid backfill, every PA39-written draft becomes permanently unreadable for replace and permanently conflicting for create replay, with no in-scope repair path.
- **为什么有问题**: The plan pins the digest with a golden vector and stores it in an irreversible column, so a canonicalization decision is a permanent contract, not an implementation detail. It is presented as the single canonical truth while the source of truth it cites for that very concept specifies a different rule, and the residual list does not own the deviation.
- **直接证据**: `docs/14-production-data-model-and-flyway-schema-spec.md` §2.5 (canonical JSON, sorted keys, and every persisted `snapshot_sha256` is the digest of that canonical snapshot) and §2.10; plan lines 190, 178-190, and §11; in-repo counter-practice `backend/src/main/java/com/onecall/core/sharing/internal/commandservice/DefaultCustomerShareCommandService.java:470` sorts with a `TreeMap`, while `catalog_order/internal/operationscommand/CatalogSaleLifecycleSemantics.java:23-25` hand-builds unsorted strings, which shows the codebase already contains both conventions and needs an explicit decision.
- **影响**: 不可恢复 / 数据损坏风险 / 后续返工 / 跨切片合同漂移
- **建议改法和验证点**: Choose and record one rule. Either order P per §2.5 and recompute the golden bytes and digest, or state that catalog `snapshot_sha256` intentionally uses the catalog-order ordered-member form, list that as a residual owned by the Contract plus catalog-order owners, and make §5.1 verification semantic (member set, types, values and column/child agreement) so a canonicalization change cannot silently turn stored rows into permanent 503s. Add an identity that proves the stored-hash check survives a jsonb key reorder, which it already claims, and one that proves a digest produced by the other convention is detected as a documented condition rather than an unrecoverable one.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
- **状态**: accepted-candidate
