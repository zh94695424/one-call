### F-S2-01 — non-string `evidenceOwner` bypasses owner equality and is admitted (Medium)

- Entry/function: `validateEvidence` manifest loop — owner missing/mismatch checks, `acceptance/validate.mjs:2961-2963` and `acceptance/validate.mjs:2970`.
- Triggering input: valid RUNTIME manifest for `A5-IDENT-NORMAL-01` with `"evidenceOwner": 42` (also `true`, `{}`, `[]`), all other fields/digest correct.
- Actual branch: missing check only fires on absent/`null` (`hasOwnProperty && !== null`); mismatch check is guarded by `isString(manifest.evidenceOwner)`, so any non-string non-null value skips both; manifest proceeds to `stats.admitted += 1` / `manifestState.set(id,'EVIDENCE_VALID')` at `acceptance/validate.mjs:3064-3065`.
- Expected behavior: plan §8.3.9 "manifest evidenceOwner 必须等于 scenario evidenceOwner" and docs/19 §9.2 "evidenceOwner 必须等于 scenario 的 evidenceOwner" require the equality to fail closed; plan §8.2.5 requires present-but-invalid values to be rejected, not silently accepted.
- Actual behavior: probe `p01-owner-number` (fixture-harness probe, `admissionOnly=true`) → `expectedPrimaryCodes=[]`, exit 0, `stats={"manifests":1,"admitted":1,...,"admittedState":"EVIDENCE_VALID","runtimeEvidence":"EVIDENCE_SUBMITTED"}` — zero issues raised.
- Direct evidence: independent probe fixture `/tmp/a5probe/fixtures/s2-01-evidence-admission.json` case `p01-owner-number`; harness output line `p01-owner-number: ... got [] exit=0 stats={"manifests":1,"admitted":1,...}`.
- Impact: an admitted `EVIDENCE_VALID` manifest can carry an unvalidated owner, defeating evidence-owner accountability (a core A5 field, plan §4.7/§6.2). Does not reach PASS (empty `authorityRegistry` + main's `productionAccepted` hard guard at `acceptance/validate.mjs:3678-3681`), but is a fail-open in a required manifest field and will silently mis-attribute ownership when real ledgers arrive.
- Concrete fix + validation: change the mismatch check to reject any non-string owner, e.g. `if (!isString(manifest.evidenceOwner) || manifest.evidenceOwner !== scenario.evidenceOwner) root(issues,'A5_EVIDENCE_OWNER_MISMATCH',...)` (keep `A5_EVIDENCE_OWNER_MISSING` for absent/`null`). Add fixture cases `owner-non-string-number` / `owner-non-string-object` to `s2-01` expecting exactly `["A5_EVIDENCE_OWNER_MISMATCH"]`; re-run s1/s2 twice and confirm s1 stdout hash `085752ae…` unchanged.
- Fix risk: low — only wrong-typed owners newly fail; string owners and the `manifest-missing-owner` case are unaffected.
- Severity: Medium.

- Fix risk: low — real ledgers bind record.scenarioId to manifest.scenarioId by construction; only mismatched/duplicated identities newly fail.
- Severity: Medium.

### F-S2-03 — FAIL acceptance records never transition scenario evidence state; aggregate `runtime_evidence` ignores FAIL (Medium)

- Entry/function: `validateEvidence` record loop `acceptance/validate.mjs:3137` (`if (record.result === 'FAIL') continue;`) and aggregate derivation `acceptance/validate.mjs:3183-3194`.
- Triggering input: CLI ledger with 90 generated manifests (one per represented scenario, correct owner/tiers/roles/digests, probe `ledger-all-fail.json`) plus one structurally valid FAIL record for `A5-IDENT-NORMAL-01`.
- Actual branch: a valid FAIL record passes manifest/digest/time checks, then `continue`s — `manifestState` stays `EVIDENCE_VALID`, no fail counter exists, and the `runtime_evidence` derivation (rejected → blocked → NOT_RUN → all-represented-admitted→`EVIDENCE_VALID` → `EVIDENCE_SUBMITTED`) never consults records.
- Expected behavior: plan §7.2 defines the terminal transition `EVIDENCE_VALID → FAIL` when an acceptance record explicitly fails; plan §7.3 requires "no FAIL/BLOCKED/EVIDENCE_REJECTED/NOT_RUN" for completeness; docs/19 §9.4 states the S2 state machine includes `EVIDENCE_VALID → FAIL`. A terminal FAIL must be visible in scenario state and must not be masked by an `EVIDENCE_VALID` roll-up.
- Actual behavior: `ledger-all-fail` run → exit 0, `evidence_manifests=90 evidence_admitted=90 acceptance_records=1 blocked=0 runtime_evidence=EVIDENCE_VALID production_accepted=false` — the FAIL record has zero effect on any derived state or output beyond the raw `acceptance_records` count. - Direct evidence: `/tmp/a5r/ledger-all-fail.out` vs `/tmp/a5r/ledger-all.out` (byte-differ only in `acceptance_records=1` vs `0`); code path `acceptance/validate.mjs:3137` and `acceptance/validate.mjs:3183-3194`.
- Impact: state-machine ownership violation (review dimension 4: "no return/state inconsistency"). No fake-PASS vector (`production_accepted` stays false; main also hard-guards `evidenceStats.productionAccepted` at `acceptance/validate.mjs:3678-3681`), but an operator reading `runtime_evidence=EVIDENCE_VALID` is told the matrix evidence is valid while a terminal FAIL acceptance record exists — exactly the ambiguity plan §7.2/§7.3 forbids.
- Concrete fix + validation: on a structurally valid FAIL record set `manifestState.set(record.manifestId, 'FAIL')` (or maintain a `failScenarios` set) before `continue`; exclude FAIL scenarios from the `EVIDENCE_VALID` roll-up and add e.g. `failed_records=<n>` to the s2 summary (update docs/19 §8.5-style output block and reason registry if a new counter is added). Add s2-01 case `fail-record-state` asserting the FAIL state/counter and `expectRuntimeEvidence` ≠ `EVIDENCE_VALID` for the affected derivation; re-run s1/s2 twice (s1 hash must stay `085752ae…`) + `--check-doc-links` + A0-A4.
- Fix risk: low-medium — changes only the roll-up when a validated FAIL record exists; no-ledger and all-admitted-no-record outputs are unchanged; summary line changes only when records with FAIL are present (document it).
- Severity: Medium.
