### F-01-未修复-中-§4 cursor byte framing omits the key-ring identifier and puts the anchor key in the clear, so the mandated cursor tests are unsatisfiable as written

- **位置**: `P:111-118` (framing), `P:166` (`rejectsMissingAndRetiredKeys`, `rejectsMalformedFrame`, `roundTripsExactFrame`, `rejectsOversizedEncodedCursor`, `keepsGeneratedCursorWithinOpenApiMaximum`), `P:232` (§6 "cursor framing/512 maximum"), against `P:15-17` "shared cursor key ring".
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口.
- **当前写法**: "Its byte framing is fixed: version byte, purpose byte, 4-byte big-endian limit, 16-byte request-digest prefix, 16-byte UUID, one-byte UTF-8 code length, UTF-8 product code, then a 12-byte nonce, ciphertext, and 16-byte tag".
- **反例/失败场景**: (1) The ring is a multi-key map with a separate active id (`OperationsSubjectReadProperties.Cursor.validatedKeys()/activeKeyId()`, consumed at `OperationsSubjectCursorCodec.java:26-31,38,66-68`); the shipped envelope therefore carries `version ‖ keyIdLength ‖ keyId ‖ nonce ‖ ciphertext(76) ‖ tag` and validates `envelope.length != 2 + length + 12 + 76` (`:59`). `P`'s frame has no key identifier, so decode cannot choose a key, and the mandated `rejectsMissingAndRetiredKeys` has no field to vary — the implementer must either write a vacuous test (a "missing key" path that cannot be expressed) or invent the very field `P` declares fixed. (2) Read literally, `product_code`, the 16-byte product UUID and the digest prefix sit *before* the nonce, i.e. unencrypted, while the ciphertext's plaintext is left undefined; that emits a cursor carrying a raw SQL key/ID, contradicting `P:111` "opaque" and the frozen `Cursor` description "never an offset, SQL key or raw ID" (`openapi:4356-4360`). (3) No AAD/purpose-binding rule is stated, so `rejectsWrongPurpose` (cross-endpoint replay) becomes implementation-invented, whereas the shipped convention binds purpose through AAD (`OperationsSubjectCursorCodec.java:93`, pinned by `OperationsIvrSessionCursorCodecTests.java:53,68-70`).
- **为什么有问题**: `PA37-PLAN-REV-09` was accepted precisely to "define exact cursor byte framing and maximum-size formula"; the replacement definition is internally inconsistent with the reuse claim in `P:15-17` and with `P:166`'s own test list, and it is the only place in the plan where a security-visible wire format is decided. Rotation semantics are live in this repository (`OperationsSubjectReadsIT.java:198-213` issues a next key and a wrong key), so a frame that cannot name a key is a behavior regression, not a style point.
- **直接证据**: `P:111-118`, `P:166`, `P:232`; `OperationsSubjectCursorCodec.java:26-31,38,41-45,59,66-68,85,93`; `OperationsIvrSessionCursorCodec.java:20,26-38,41-59,85`; `OperationsIvrSessionCursorCodecTests.java:42,53,68-70`; `OperationsSubjectReadsIT.java:198-213`; `openapi:4356-4360`.
- **影响**: 生成错误代码（cleartext anchor 或自造 key-id 字段）/ 生成不可满足或空转的测试 / 冻结 contract 违规 cursor / 轮换语义回归 / 后续返工.
- **建议改法和验证点**: restate the frame as an envelope: `version byte ‖ 1-byte key-id length ‖ ASCII key id (1..32) ‖ 12-byte nonce ‖ AES-GCM ciphertext ‖ 16-byte tag`, where the *encrypted* plaintext is exactly `purpose byte ‖ 4-byte big-endian limit ‖ 16-byte request-digest prefix ‖ 16-byte product UUID ‖ 1-byte UTF-8 code length ‖ UTF-8 product code`; pin the AAD construction (purpose string + `"GET <route>"` + sort string, per shipped) and the key-id source as the existing `onecall.operations-subject-read` ring, so no new key material or configuration is introduced; give the length formula `2 + keyIdLen + 12 + (39 + codeLen) + 16` with the worst case (`keyIdLen=32`, `codeLen=64`) = 165 bytes → 220 base64url chars ≤ 512. Verification points: `roundTripsExactFrame` asserts the byte layout; active key issues and a retired-but-known key still decodes; an unknown/absent key id is `CURSOR_INVALID`; a subject/activation/IVR cursor on the catalog endpoint and a catalog cursor on those endpoints are both rejected by purpose/AAD; assert the encoded cursor never contains the product code or product UUID substring; `rejectsOversizedEncodedCursor` uses a >512-character string, and generated cursors stay ≤ 512.
- **修复风险（低）**: low — plan-text only; no schema, OpenAPI, properties or key-ring change.
- **严重程度（中）**: medium.
