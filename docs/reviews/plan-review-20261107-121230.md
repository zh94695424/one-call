## 4. Findings

### F1-未修复-[高]-并发首次请求在 post-provider `CONFLICT` 时的失败方响应路径未冻结：返回哪个 credential、provider 输出不匹配时怎么办、以及收敛测试均未明确，与 PA17 的 503 先例相冲突

- **位置**: Plan §3 step 10（"append/reuse… Provider output must match the stored event facts"）、§4.3（replay 读取 first durable expiry；"Provider output must use the event identity, pre-provider fingerprint, and first durable expiry facts"）、§6.2（两连接测试仅证明事务闭合）、§7 验证清单、§8 row 4（residual）。
- **问题类型**: 契约缺失 / 并发恢复风险 / 测试缺口 / 不可直接实施（code-generation-ready 缺口）。
- **当前写法**: 两个并发的同 key 同 purpose 首次请求都能通过 step 8（pre-provider fingerprint 不含 `credentialExpiresAt`），各自在自己的 post-lock 事务外采样 `databaseNow`；当 `databaseNow + approvedQ22MediaCredentialTtl` 是 `min(...)` 的绑定项时，两者的 post-provider durable payload 不同。`JooqShareAdmissionRepository.insertAccessEvent` 对第二者的 `INSERT … ON CONFLICT DO NOTHING` 返回 `CONFLICT`（`payload_sha256` 不同），而不是 `REUSED_IDENTICAL`。计划只写 "append/reuse"、"Provider output must match the stored event facts"，未写明 CONFLICT 分支的响应构造。
- **反例/失败场景**:
  1. 实现者沿用 PA17 先例 `DefaultShareAdmissionService.java:324`（append `CONFLICT` → `DEPENDENCY_UNAVAILABLE` 503）或 `:259`（同 identity、payload hash 不符 → 503）→ 合法的并发重复请求拿到 503 而不是第一个 credential，违反 Goal Confirmation "replay the first credential … without a second credential" 的确定性重放成功信号；
  2. 实现者返回本地 provider 输出 + 存储的 `credentialExpiresAt` → 若 provider 的 credential 派生包含 `credentialExpiresAt`（计划未禁止），响应是"第二个 credential + 第一个 expiry"的错配对，即产生第二个 effective credential；
  3. 实现者正确地丢弃本地输出并以 first durable facts 重放 provider，但计划未规定重放调用/校验顺序与不匹配时的 fail-closed 码，且 §6 没有任何"两个并发首次请求收敛为一 credential 一 event"的测试（唯一名为 two-connection 的测试只证明锁/事务在 provider 回调前闭合），错误实现可通过全部计划内测试。
- **为什么有问题**: Controller fix-1 intake（control `:35`）明确要求对此给出 "an explicit code-generation-ready answer"。计划的三个候选结局（replay 返回 first credential / `409` / PA17 先例 `503`）都能从现有文本中"推导"出来，且代码先例指向 503——这正是 code-generation-ready 标准下实现 Agent 必须重新设计的分叉点。
- **直接证据**: plan:76、plan:122、plan:250、plan:272、plan:294；`JooqShareAdmissionRepository.java:110-116`；`DefaultShareAdmissionService.java:324,259`；Goal Confirmation control `:21-22`；Controller focus control `:35`。
- **影响**: 并发重复请求返回 503/409 而非首个 credential（goal 失败）或泄露第二个 effective credential（幂等/安全失败）；验收无法证明 "one credential and one event"；风险在实现期才暴露且现有测试测不出。
- **建议改法和验证点**: 在 step 10/§4.3 明文冻结 CONFLICT 分支：(a) 同 purpose/同 event type/同 pre-provider fingerprint 的 append `CONFLICT` 一律按 replay 处理——丢弃本地 provider 输出，读取 first durable event，以 first durable facts 调用 `issueOrReplay`（或证明本地输出与存储事实逐字段相等），返回 first credential + 存储的 `credentialExpiresAt`；(b) provider 输出无法与存储事实匹配时 fail-closed 为 `DEPENDENCY_UNAVAILABLE`；(c) 明确禁止返回本地 `credentialExpiresAt` 或未校验的本地 credential；(d) 新增具名并发测试（两个连接同时发送同 key 同 purpose）断言单 event、单 credential、双方 200 同值。验证点：该测试 + `providerIoOccursOnlyAfterPostgresTransactionClosure` 全绿。
- **修复风险（低）**: 仅 plan 文本与具名测试，不改 scope/allowlist。
- **严重程度（高）**。

### F2-未修复-[中]-durable `FAILURE` 之后同 key 同 purpose 重试的结局未被显式冻结且无测试：step 8 字面给出永久 409，step 10 的 "reuse the first identical failure" 又指向 503 重放

- **位置**: Plan §3 step 8（"prior success **or failure** row with a different purpose **or event type**"）、§3 step 10（"Reuse the first identical failure…"）、§4.5、§6.1 `providerFailureAppendsOnlyDeterministicFailureWithoutSuccess`、§6.2 `providerUnavailableOrMalformedAppendsFailureWithoutSuccess`。
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口。
- **当前写法**: FAILURE 行的 `eventType=FAILURE`，与重试时按 purpose 映射的 `PLAYBACK_AUTHORIZED`/`SEEK_AUTHORIZED`/`RENEWED` 不同。按 step 8 字面，"different event type" → 永久 `409 SHARE_GENERATION_STALE`、不调 provider、不追加事件；但 step 10 又要求 "Reuse the first identical failure"，自然被读成"重试重放首个失败（503）"。计划从未用陈述句冻结三选一（first-failure replay / fresh success decision / 其它 frozen outcome），两个具名失败测试都只覆盖单次失败追加，没有 same-key retry-after-FAILURE 用例。
- **反例/失败场景**:
  1. 实现者按 step 10 实现"重试重放 503"，另一个实现者按 step 8 实现"重试 409"——两者都可声称忠于计划；测试对二者都通过（因为没有该用例）；
  2. 若意图是 fresh success decision（重试可成功并追加 SUCCESS 行），则 step 8 的 "or event type" 措辞直接禁止了它——计划文本与目标行为之间没有对账；
  3. 客户端对未变更输入收到 `SHARE_GENERATION_STALE`（标题 "generation stale"），与 Goal Confirmation "fail a **changed** semantic input with a stable conflict" 的触发表述张力，且该结局从未被 Controller/测试确认。
- **为什么有问题**: Controller fix-1 intake（control `:35`）要求 "one frozen outcome … tests/event identities unambiguous"。事件身份（`eventType=FAILURE` 的 `share-access:` 公式）已冻结，但重试结局未冻结；这是本 slice 的状态机语义，不是风格问题。
