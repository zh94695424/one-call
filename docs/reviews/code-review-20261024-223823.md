## Findings

### F-01 `[中]` O17 `AuditFact` exposes an invented actor vocabulary and an internal-ID shape that does not map to A0 `audit.audit_fact`

- **Entry point / location**: `components.schemas.AuditFact` (`api/openapi/onecall-v1.openapi.yaml:5936-5994`), returned by `listOperationsAuditFacts` (`:2271-2325`). `actorType` enum `CUSTOMER|EMPLOYEE|SYSTEM|PROVIDER` (`:5955-5957`); `actorId` optional nullable uuid (`:5958-5962`); `actionCode` string 1-64 (`:5963-5966`); `objectId` required string 1-128 (`:5971-5974`); `reasonCode` nullable string 1-64 (`:5975-5980`); `traceId` required string 1-128 (`:5991-5994`). Generated declaration: `tmp/openapi-client/onecall-v1.d.ts:2093-2111` (`actorType: "CUSTOMER" | "EMPLOYEE" | "SYSTEM" | "PROVIDER"`; `objectId: string`; `traceId` required).
- **Input scenario**: An operations employee lists audit facts after a customer, employee, service or system action.
- **Actual branch**: A0 `audit.audit_fact.actor_type` is exactly `ACCOUNT`, `EMPLOYEE`, `SERVICE` or `SYSTEM` (`docs/14-production-data-model-and-flyway-schema-spec.md:561,574`). A1 invents `CUSTOMER` and `PROVIDER`, and omits `ACCOUNT` and `SERVICE`. A0 `actor_id` is required for `ACCOUNT`/`EMPLOYEE`/`SERVICE` and null only for `SYSTEM` (`docs/14:562,575`); A1 makes it optional for every actor type. A0 `action_code` is 2-128 characters with `^[A-Z][A-Z0-9_]{1,127}$` (`docs/14:563,576`); A1 allows 1-64 and no pattern. A0 `object_id` is a nullable `uuid` required unless `object_type = 'SYSTEM'` (`docs/14:565,578`); A1 requires a non-UUID-bounded string 1-128. A0 `reason_code` is nullable 1-128 (`docs/14:566,579`); A1 caps it at 64. A0 `trace_id` is nullable 1-128 (`docs/14:570,583`); A1 requires it. The A0 catalog row itself is the mapping source (`docs/14:361`); the plan's component list (`docs/gateflow/a1-production-openapi-surfaces-spec-plan.md:478`) names the fields but no alternate actor vocabulary, and plan §4.10 (`:332`) requires A0/09/13 exact enum values.
- **Expected**: A public audit projection must either copy the A0 actor classes and column domains exactly, or declare an explicit, documented transformation and a safe synthesized value for every nullable/internal column.
- **Direct evidence**: YAML lines above; A0 §4.5 `:561-570,574-583`; generated d.ts `:2093-2111`; plan §4.10 `:332` and §5.6 `:478`; docs/15 §3.1 row O17 (`docs/15-production-openapi-surface-spec.md:130`) describes only redacted snapshots, not an alternate actor vocabulary. No client-compat assertion covers `actorType`, `actionCode`, `objectId`, `actorId` or `traceId` (`client-compat.ts` has no `AuditFact` assertion).
- **Impact**: The only operations audit endpoint misreports the actor class and cannot represent valid A0 rows with `actor_type = ACCOUNT|SERVICE`, a null `object_id` on `SYSTEM` rows, a 65-128 character action/reason code, or a null trace. A generated client bakes the wrong vocabulary and the wrong internal-ID type into the public contract. This is direct semantic-ownership drift, not a runtime-only concern.
- **Suggested correction**: Decide with the A0/audit owner whether the public vocabulary is A0's `ACCOUNT|EMPLOYEE|SERVICE|SYSTEM` (preferred) or a documented mapping. Align `actorId`/`objectId`/`traceId` requiredness and nullability, `actionCode`/`reasonCode` bounds and pattern, and `objectId` `format: uuid` to A0. Add contract-rule pins and client-compat assertions for the final enum and nullability split. If the API intentionally abstracts actor classes, add the mapping to plan/docs/15 and state how null internal fields are represented.
- **Verification / fix risk**: Low-medium; this is a schema/projection correction plus regenerated types. It does not claim the audit service exists.
- **Severity / classification**: 中; `accepted` (current contract defect).

### F-02 `[中]` O20/O21 require `TrialPolicyDraft.createdAt`, a timestamp with no A0 column and no docs/15 ownership

- **Entry point / location**: `components.schemas.TrialPolicyDraft.required` and `createdAt` (`api/openapi/onecall-v1.openapi.yaml:6204-6217,6244-6246`), returned by `createOperationsTrialPolicyDraft` 201/200 (`:1957-1968`) and `replaceOperationsTrialPolicyDraft` 200 (`:2550-2555`). Generated d.ts `:2189-2208` (`createdAt: string` required).
- **Input scenario**: An ADMIN creates or replaces a never-published trial-policy draft and reads the returned draft projection.
- **Actual branch**: `TrialPolicyDraft.createdAt` is a required public response field. A0 `entitlement_metering.trial_policy_version` has exactly `id`, `campaign_key`, `version_no`, `granted_seconds`, `valid_days`, `enabled`, `snapshot`, `snapshot_sha256`, `published_by_employee_id`, `published_at`, `revision` (`docs/14:1598-1610`); there is no `created_at`. docs/15's canonical DRAFT projection lists `{campaign_key, version_no, granted_seconds, valid_days, snapshot_sha256}` and does not include a creation timestamp (`docs/15:159-160`). The accepted plan's component dictionary does include `createdAt` (`plan §5.6:477`), so this is an accepted-plan-level ownership gap as well as an implementation field.
- **Expected**: Every public response timestamp must map to an approved A0 column or an explicitly documented derivation. The prior F-04 correction removed an analogous invented share `createdAt` because A0 had no `created_at`; the same standard applies here.
- **Direct evidence**: YAML lines above; A0 §4.29 `:1598-1610`; docs/15 `:160`; plan §5.6 `:477`; generated d.ts `:2206`. Related lower-risk projections: `RecordingDeclaration.declaredAt` (`YAML:6960-6962`) and `RecordingCompletion.completedAt` (`YAML:6999-7001`) are also absent from plan §5.6 (`:481-482`) and docs/15; they plausibly rename A0 `recording.created_at` / `validated_at` (`docs/14:2098-2099`) but no mapping is declared.
- **Impact**: A required field cannot be populated from the approved draft row. An implementation must derive it silently from an audit/outbox event or synthesize it, creating exactly the type of unowned response fact the contract success signal forbids. The generated client requires a value the A0 model does not own.
- **Suggested correction**: Remove `TrialPolicyDraft.createdAt` (and the two unlisted recording timestamps) from the contract, or declare an explicit source: for O20/O21, the draft-create audit fact's `occurred_at` is a candidate because `audit.audit_fact` is already in the operation's A0 model set; for recordings, map `declaredAt`/`completedAt` to `recording.created_at`/`recording.validated_at`. Update plan §5.6, docs/15, contract rules and client-compat assertions together. Add a regression rule that forbids an unowned timestamp on the DRAFT schemas.
- **Verification / fix risk**: Low; removing or explicitly mapping an optional/required timestamp is a bounded plan/docs/schema correction and regenerates types.
- **Severity / classification**: 中; `accepted` (current schema-to-A0 drift; plan owner must approve the mapping or removal).

### F-03 `[中低]` `ingestIvrCallEvent` declares `EVENT_ID_CONFLICT` but wires its 409 response to the `SessionIdentityMismatch` component

- **Entry point / location**: `ingestIvrCallEvent` (`api/openapi/onecall-v1.openapi.yaml:3344-3431`); declared domain codes `IVR_ARGUMENT_INVALID`, `CALL_UNKNOWN`, `EVENT_ID_CONFLICT` (`:3379-3388`); `'409': $ref: '#/components/responses/SessionIdentityMismatch'` (`:3422-3423`); response component description (`:4193-4198`). The exact-set validator pins `EVENT_ID_CONFLICT` (`contract-rules.mjs:809`) and docs/15 §4 pins the same set (`docs/15:243`).
- **Input scenario**: The IVR replays the same `(IVR_EVENT, eventId)` with a changed semantic fingerprint, or another I4 conflict that A0 maps to `EVENT_ID_CONFLICT`.
- **Actual branch**: The operation's machine-readable error set says `EVENT_ID_CONFLICT`, but its 409 response is named and described as a session/identity mismatch (`The frozen session, decision, access-number or fingerprint identity cannot be reconciled for this call`). `SESSION_IDENTITY_MISMATCH` is not in the I4 error inventory, while the I1-I3 operations use the same response component for their allowed identity-conflict code. An implementer following the 409 response name/description would emit the wrong code; the validator passes because the response schema is the generic `Problem` and only the existence of a 409 status is checked.
- **Expected**: The I4 409 response component must describe `EVENT_ID_CONFLICT` (or be a generic conflict response whose description does not name a different domain code). I1-I3 keep `SESSION_IDENTITY_MISMATCH`.
- **Direct evidence**: YAML `:3379-3388,3422-3423,4193-4198`; `contract-rules.mjs:809`; docs/15 `:243`; plan §5.3 I4 (`plan:414`) and §4.6 (`:221-223`) reserve `SESSION_IDENTITY_MISMATCH` for I1-I3 and require `EVENT_ID_CONFLICT` for the same-identity/different-fingerprint event path.
- **Impact**: The response/status/error mapping is internally inconsistent. A generated client or server that branches on the response component's identity-conflict description can return a code the operation does not declare.
- **Suggested correction**: Add a dedicated `EventIdConflict` 409 response component (or a neutral conflict response) with the correct description and point `ingestIvrCallEvent` at it; keep the exact error set and docs/15 unchanged. Add a static rule that the response component family matches the operation's declared conflict code where a component is code-specific.
- **Verification / fix risk**: Very low; documentation/response-ref correction, no wire schema or status change.
- **Severity / classification**: 中低; `accepted`.

### F-04 `[中低]` The trust-boundary validators still do not cover parameter locations, path-item `$ref`s, or audience/role/scheme semantics

- **Entry point / location**: `validateTrustedRequestFacts` walks only request-body schemas (`api/openapi/contract-rules.mjs:1319-1369`); `operationParameters` is used for cursor/security checks but never fed to the trusted-fact/secret walker (`:297-303`); `Idempotency-Key` is detected only as an exact header (`:1010-1012`). `eachOperation` reads `pathItem[method]` without dereferencing a path-item `$ref` (`:284-295`). Audience is enum-only (`:509-514`); required roles are optional and only checked as a subset (`:566-570`); security-scheme definitions are only checked for name existence (`:581-592`). The request walker traverses only `properties`, `items`, `prefixItems`, schema-valued `additionalProperties` and `allOf`/`anyOf`/`oneOf` (`:1202-1236`).
- **Input scenario**: A future contract edit adds a trusted fact or secret to a query/header/cookie parameter; introduces a `$ref` Path Item; changes a customer operation's audience to `employee`; drops an `OPS` role; redefines `customerSession` as a query API key; or adds `patternProperties` to a "closed" request object.
- **Actual branch**: All of these pass the enabled custom rules. A query parameter named `accountId` or `currency` is invisible to the body-only trusted-fact walker; a path-item `$ref` hides the whole operation from every `eachOperation`-based rule (metadata, security, problem, cursor, idempotency, drafts, opaque IDs); audience/role/scheme drift is not cross-checked; `patternProperties` can admit arbitrary properties under `additionalProperties: false` without being traversed.
- **Expected**: The success signal says the static validators must fail closed on server-derived facts, secret locations and trust-boundary drift, not only on the current happy-path schema. The prompt explicitly asks to challenge refs, parameter locations, compositions and optional/required shape drift. A validator that only protects request bodies and path-prefix metadata is incomplete.
- **Direct evidence**: `contract-rules.mjs:284-295,509-514,566-570,581-592,1010-1012,1202-1236,1319-1369`; `redocly.yaml:34-47` enables the relevant rules; `check-doc-map.mjs` checks only path/surface/models, not audience/roles/schemes or parameter trust. The current canonical contract has no such bypass, so this is a validator-coverage finding rather than a current wire defect.
- **Impact**: A future regression can ship a trusted fact, wrong audience/role, or wrong auth scheme while `check:s1/s2/s3` stays green. This directly weakens the "strict static validator" success signal and the A1 trust-boundary claim.
- **Suggested correction**: (1) Run the trusted-fact/forbidden-name walk over all path/query/header/cookie parameter schemas, with explicit approval for the documented opaque inputs; (2) resolve path-item `$ref`s in `eachOperation` and fail closed on external/unresolvable/cyclic refs; (3) pin a surface→audience map and the required-role matrix per operation/surface; (4) validate scheme `type`/`in`/`name`/`bearerFormat`; (5) fail closed on unrecognized request-schema keywords that can admit data (`patternProperties`, `dependentSchemas`, `unevaluatedProperties`, `if`/`then`/`else`, `not`, `contains`, `propertyNames`, `$defs`). Add executable negative probes for each.
- **Verification / fix risk**: Low-medium; hardening only, no wire change. It may require adding the approved parameter locations to an allowlist so the current contract stays green.
- **Severity / classification**: 中低; `accepted` (validation hardening; the current contract is clean).

### F-05 `[低]` Several response requiredness/nullability projections remain weaker than A0 and are not asserted

- **Entry point / location**: `CatalogVersionDraft.snapshotSha256?` (`api/openapi/onecall-v1.openapi.yaml:6104-6107`) and `TrialPolicyDraft.snapshotSha256?` (`:6247-6250`) are optional, while A0 `snapshot_sha256` is `NOT NULL` (`docs/14:1021,1607`). `ShareState`/`ShareSummary`/`ShareCreated.evidenceId?` and `codeGeneration?` are optional (`YAML:6360,6386,6402,6427,6443,6469`), while A0 `evidence_id` and `code_generation` are `NOT NULL` (`docs/14:2264,2270`). `ShareCreated`/`PublicShareView`/`ShareCodeRotation` status unions include terminal/other states on first-response shapes (`YAML:6369,6410,6452,7013,6529,6561`). `OutboundCallTask.expiresAt`'s shape guard only rejects `type` arrays containing `null`, not a direct `type: 'null'` (`contract-rules.mjs:2208-2218`).
- **Input scenario**: A server serializes a valid A0 draft/share row, or a future schema edit changes one of these fields to null/optional.
- **Actual branch**: The fields can be omitted or over-broadened without failing the current static rules; the generated client treats them as optional/looser than A0. The `TrialPolicyDraft.createdAt` issue in F-02 is the material case; these are lower-risk projection gaps.
- **Expected**: Required A0 facts should be required in public projections, and response status unions should be as narrow as the operation can return; the shape guards should fail closed on direct null types.
- **Direct evidence**: YAML and A0 lines above; `client-compat.ts` has no assertion for `snapshotSha256`, share `evidenceId`, share `codeGeneration`, share status union, or `CatalogVersionDraft.snapshotSha256` (it only asserts selected draft/trial fields); `contract-rules.mjs:2208-2218`.
- **Impact**: Generated clients cannot rely on fields that A0 always has; a future regression can turn a non-null fact into an omitted/null value. Not a current wire contradiction, but it weakens the exact-mapping claim.
- **Suggested correction**: Make `snapshotSha256`, creator-context `evidenceId` and `codeGeneration` required where A0 is NOT NULL, or document the projection omission; narrow first-response status unions to the states the operation can actually return; change the `expiresAt` guard to reject both `type: 'null'` and type arrays containing `null`. Add client-compat assertions.
- **Verification / fix risk**: Low; schema/type tightening and regenerated fixtures.
- **Severity / classification**: 低; `accepted` (projection hardening).

### F-06 `[低]` The P1 optional-content TypeScript assertions are vacuous

- **Entry point / location**: `client-compat.ts:474-490`; generated `PublicShareView` has `content?` and `verificationChallenge?` (`tmp/openapi-client/onecall-v1.d.ts:2502-2526`); canonical optionality is in `YAML:7002-7057` and is independently pinned by `validateShareSemantics` (`contract-rules.mjs:1488-1499`).
- **Input scenario**: A future schema change makes `PublicShareView.content` or `verificationChallenge` required.
- **Actual branch**: The assertions compare the string literal `'content'` / `'verificationChallenge'` to `Required<PublicShareView>`, an object type, so the conditional is always false and the assertions always pass. They do not test optionality. The key-existence assertion at `:475-476` only proves the key exists.
- **Expected**: The fixture should assert that the properties are present and optional, e.g. `'content' extends keyof Required<PublicShareView>` is false or `undefined extends PublicShareView['content']` is true.
- **Direct evidence**: `client-compat.ts:477-490`; generated d.ts `:2510,2522`; YAML `:7006,7019-7057`; `contract-rules.mjs:1488-1499` still protects the canonical shape, so this is a test-evidence defect, not a current contract defect.
- **Impact**: The generated-client compatibility claim overstates P1 coverage; a future required-content regression would not fail `tsc` even though the canonical rule would still fail `check:s3`. The claimed two-layer protection is one layer.
- **Suggested correction**: Replace the two assertions with the intended `undefined extends ...` / `keyof Required<...>` form and keep the canonical rule. Add a negative fixture that fails if the property becomes required.
- **Verification / fix risk**: Very low; fixture-only.
- **Severity / classification**: 低; `accepted` (validation/test hardening).
