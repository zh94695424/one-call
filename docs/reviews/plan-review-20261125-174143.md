### B3-未修复-[高]-§5 单语句 SQL 无法产出 `hasMore`，且与 §6 的"聚合前校验原始值"互斥

- **位置**: §3 List（`hasMore` 定义）、§4（stable keyset）、§5 List SQL（`candidates`/`page` CTE + `LEFT JOIN LATERAL`）、§6（"Validate raw values before aggregation can conceal invalid data"）、§10 断言 "no offset gaps/duplicates"
- **问题类型**: 状态机/执行语义缺失（契约缺失）/ 不可直接实施 / SQL 投影不完整
- **当前写法**: plan 要求"一条 bounded SQL、不得 N+1"，并在同一语句里用 `candidates LIMIT :limit_plus_one` → `page LIMIT :limit` → 只 join `page`，同时声称"extra candidate 仅用于推导 hasMore"。
- **反例/失败场景**: 该语句的最终 SELECT 只从 `page`（≤ `limit` 行）取数，多出的那一行既不返回也没有任何列承载计数，因此调用方**无法**从结果集判定 extra row 是否存在：`hasMore` 只能被实施 Agent 现场发明（窗口计数 `count(*) OVER ()`、返回 `limit+1` 行再在 Java 端裁剪、或额外一条语句）。三种做法语义不同：返回 `limit+1` 行裁剪会破坏"最多返回 limit"的冻结投影断言；额外语句违反 plan 自己的单语句要求；窗口计数则从未在 plan 的投影列清单中出现（`SELECT p.<projection>` 未定义该辅助列，且 §7/§9 未授权把它放进 DTO）。典型可观测后果：最后一页返回 `hasMore=true`、或 `nextCursor` 与 `hasMore` 互相矛盾（`nextCursor=null` 但 `hasMore=true`）。
- **第二个冲突**: §6 要求"先校验每行 raw status 非空且属于 V006 三值，再让聚合掩盖无效数据"，但 §5 的语句只输出 `total/pending/issued/failed` 四个计数，raw 值根本不在结果里；`pending+issued+failed=total` 只能**检测**存在异常值，无法实现 §6 描述的校验语义（也无法产出 §6 声称的"safe invariant metadata"日志内容，因为行不可见）。
- **为什么有问题**: 这是 plan 的内部执行语义不一致，不是风格问题：实施 Agent 必须在实现门自行重设计投影和失败检测机制，而 plan §5/§6 又把它们当作已定案。Control 明确要求 plan 是 code-generation-ready（"The exact mapping will be fixed by the plan and validated against PostgreSQL 16"）。
- **直接证据**: plan §5 原文（`WITH candidates ... LIMIT :limit_plus_one), page AS (SELECT * FROM candidates ... LIMIT :limit) SELECT p.<projection>, COALESCE(i.total,0)...`）、§3 原文（"`hasMore` is true iff the extra row exists"）、§6 原文（"Validate raw values before aggregation can conceal invalid data"）；`V006...sql:16-40`（`ck_issuance_status`/`ck_issuance_state_shape`，即 raw 值必须逐行读取才可见）；`api/openapi/onecall-v1.openapi.yaml:5588-5603`（`OrderPage.required = [items,nextCursor,hasMore]`，`hasMore` 无默认 ⇒ 服务端必须可判定）
- **影响**: 实施 Agent 跑偏 / 生成错误代码（`hasMore`/`nextCursor` 语义漂移）/ 状态不一致 / review 不可验收
- **建议改法和验证点**: 在 plan 固定一个机制并写出投影列，例如：最终 SELECT 增加 `count(*) OVER () AS candidate_total`（由 `candidates` 的 `limit+1` 与 `page` 裁剪共同决定），Java 侧 `hasMore = candidate_total > limit`，并且 `items`/`nextCursor` 只取前 `limit` 行；或明确改为"返回 `limit+1` 行 + 应用层裁剪"并声明该辅助行不进入 DTO。为 §6 指定 raw-status 校验的可实现形态（例如在同一语句用 `bool_and(status IN ('PENDING','ISSUED','FAILED'))` 与 `count(*) FILTER (WHERE status IS NULL)` 作为不变量列，或声明该检查仅在 mapper/单元测试 mock 路径实现）。验证点：恰好 `limit` 行 / `limit+1` 行 / 空页 / 末页四种边界下 `hasMore` 与 `nextCursor` 的组合矩阵必须写进 §8 并被 IT 覆盖。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

- **为什么有问题**: 冻结设计把"每面独立 key"写成要求而非偏好：docs17:75 "**Explicit independent** `onecall.customer.evidence.cursor-hmac-key` must be canonical base64 of exactly 32 bytes; there is no production default"；README:108 对 catalog offers 写 "endpoint-isolated HMAC cursor. The cursor key is supplied **only by** `ONECALL_CUSTOMER_CATALOG_OFFER_CURSOR_HMAC_KEY`"；docs17:122 "All replicas require one consistent key; replacement invalidates prior cursors"。docs17 属 PA42 禁改真源，所以实现必须服从它；而 plan 的"不加任何配置变量"在同一真源下不可满足。
- **直接证据**: `docs/17-production-security-design-spec.md:75,122`；`backend/README.md:108,155,202`；`backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerBusinessNumberCursorProperties.java:5-10`、`CustomerCatalogOfferCursorProperties.java:5-10`；`backend/src/main/resources/application-web.yml:9,11`；plan §4/§7/§11 原文
- **影响**: 实施 Agent 跑偏 / 生成错误代码（跨面共享秘密）/ 运维轮换导致用户可见 cursor 大面积失效 / scope 违规

- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### B5-未修复-[中]-遗漏冻结的错误优先级与 lazy key resolution 语义

- **位置**: §3 Errors、§4（cursor 校验清单把结构校验与 HMAC 校验并列）、§8（`cursorAndLimitErrorsUseFrozenCodes`、`malformedTamperedAndDigestMismatchCursorsFailClosed`）
- **问题类型**: 契约缺失 / 状态机漏洞（错误映射次序）/ 测试缺口
- **当前写法**: plan 只列出每个 operation 的错误码集合与"422/400/503/404/401"归属，没有规定判定顺序，也没有写"结构校验先于 key 解析、detail 永不解析 cursor key"。
- **反例/失败场景**: docs17:122 把优先级冻结为 `route 404 → authentication 401/503 → workspace 503 → limit 422 → structural cursor 400 → key 503 → MAC/scope 400 → lifecycle 403`，并且 docs17:75 要求 "Key/service resolution stays lazy after structural input validation; detail never resolves the cursor key"。若实施 Agent 在构造 codec 时（构造函数即读 key，如现有 `CustomerCatalogOfferCursorCodec:41-51`）先解析 key，则"未配置 key + 非法 cursor"会返回 503 而非契约要求的 400；若先解析 cursor 后校验 limit，则非法 limit 的 422 次序也会漂移。这类差异在 happy-path 测试下完全不可见，只在配置缺失/故障注入时暴露，属用户可见且难发现。
- **为什么有问题**: plan 的验收集合与 §8 测试清单里没有优先级/懒解析矩阵（只有"错误码正确"），而该次序是被冻结 doc 明确钉住的安全行为；Control 要求 plan 提供可直接实施的契约语义。
- **直接证据**: `docs/17-production-security-design-spec.md:75`（lazy resolution / detail 不解析 key）、`:122`（优先级链）；`backend/README.md:155,202`（同文重复）；`backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerCatalogOfferCursorCodec.java:41-51,53-76`（构造期解析 key、`validateStructure` 为独立静态入口）
- **影响**: 生成错误代码 / 状态不一致（同一输入在不同部署态得到 400 vs 503）/ 用户可见错误语义偏离冻结契约 / 后续返工
- **建议改法和验证点**: 在 §3/§4 写出该优先级链，并显式规定 orders 沿用"结构校验入口静态、无 key 依赖；MAC/scope 校验才解析 key"。在 §8 增加断言：`key 未配置时非法 cursor ⇒ 400 CURSOR_INVALID`、`key 未配置时合法 cursor ⇒ 503`、`非法 limit + 非法 cursor ⇒ 422 优先`、`detail 全路径不触碰 key`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### B6-未修复-[中]-issuance 无效值的数据库级 canary 在冻结约束下不可实现

- **位置**: §6（null/未知 status 的 fail-closed 与"canaries impossible in a valid database, but unit/repository failure tests must exercise them"）、§8 "Failure canaries"、§10（"failure cases"、"503 canary"）、§11 第三条 Residual
- **问题类型**: 测试缺口 / 不可直接实施 / 与冻结约束冲突
- **当前写法**: §8 指示"只在 constraints 可被安全绕过处，用 rollback-scoped owner 事务或 unit mock 播种无效/Null issuance 数据"，同时要求"不得削弱 schema 约束"。
- **反例/失败场景**: PostgreSQL 的 `ck_issuance_status`/`NOT NULL`（V006:16-20、docs14 §4.33）无法通过 DML 绕过：普通 `INSERT` 直接被约束拒绝；唯一可行绕过是 `ALTER TABLE ... DROP/NO INHERIT` 之类的 DDL 或改约束，而这正是 plan §1/§9 与 Control 非目标明令禁止的动作（"it may not create or alter tables, constraints, indexes..."）。因此 `CustomerOrdersReadIT.readsAndFailuresHaveZeroWriteDelta` 所依赖的"503 失败用例"与 §6 的 fail-closed 行为没有可执行的 PostgreSQL 证明路径；实施 Agent 只能（a）悄悄跳过该断言（测试被削弱）、或（b）在 IT 里加 DDL（scope 违规）、或（c）临场改用一个未声明的 503 触发源。
- **为什么有问题**: plan 把一个不可能完成的验证指令写成必做项，并把替代方案（unit mock）与必做方案混在同一句里，没有确定归属。可实现的等价证明路径其实存在但 plan 未指定，例如 docs17:122 规定"key 缺失/非法 ⇒ sanitized 503"，可作为零写入失败用例的合法 503 触发源。
- **直接证据**: `V006__trial_entitlement_issuance_reservation_usage.sql:16-20`（status CHECK/NOT NULL）；`docs/14-production-data-model-and-flyway-schema-spec.md:1850-1866`（§4.33 同一约束与 "mutable head" 生命周期）；plan §8/§10/§11 原文；Control `:28` 与 §1 非目标
- **影响**: 测试缺口（失败路径只被 happy 数据库态"证明"）/ 实施 Agent 擅自 DDL / 风险后移
- **建议改法和验证点**: 把 §6 的无效值 fail-closed 明确降级为 mapper/单元层证明（构造 mock 行 + 断言 `SERVICE_UNAVAILABLE` 与"日志不含行内容"），并删除 PostgreSQL 播种无效数据的要求；PostgreSQL 侧改为以"key 未配置/非法 ⇒ 503"作为零写入失败用例。若确实需要 DB 级不变量证明，改为断言约束本身拒绝非法 status（期望 `23514`）而不是绕过约束。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### B8-未修复-[中]-新读路径的访问计划与成本完全没有被评估

- **位置**: §4（stable keyset）、§5（PERSONAL/ORGANIZATION 谓词与 `ORDER BY created_at DESC, id DESC` + `LIMIT :limit_plus_one`）、§1 Non-goals（禁止 object/schema DDL）、§10（无成本类断言）
- **问题类型**: 最佳实践偏离 / 非最优方案 / 可行性风险后移
- **当前写法**: plan 详细规定谓词与排序键，但没有提到 `customer_order` 上现有索引能否支撑该形状，也没有把"无 account 索引"记为 Residual。
- **反例/失败场景**: V004 仅有 `ix_customer_order_subject_status (subject_id, payment_status, created_at DESC)`、`ix_customer_order_organization (owner_organization_id, created_at DESC)`、`ix_customer_order_version (catalog_version_id)`（`:204-208`），**没有任何以 `account_id` 打头的索引**。PERSONAL 谓词是 `account_id = :acc AND owner_organization_id IS NULL`，`ix_customer_order_organization` 虽然能覆盖 `IS NULL` 前缀并按 `created_at DESC` 免排序，但该索引段是**全库所有账户的 personal 订单混合体**：`account_id` 只能作为过滤谓词。于是一个订单很少、或订单都很旧的客户，翻到深页时需要沿索引扫描并丢弃大量他账户行才凑够 `limit+1`；`limit` 最大 100 时最坏接近全 personal 分区扫描。这是典型的可被单个用户放大的热路径成本问题（客户小程序首屏列表），而且失败方式不是错误而是延迟/DB CPU。
- **为什么有问题**: plan 冻结了"不得加索引"（object/schema DDL 属非目标），同时把 cursor 深翻列为成功信号，却没有说明成本上界、没有引用容量真源（docs18）确认该形状可接受，也没有把"缺 account 维度索引"登记为有 owner 的 Residual。按 planreview 的最佳实践 lens，一个已知缺索引的 keyset 读路径必须要么给出证据（数据规模 + 实测计划），要么给出明确的风险归属。
- **直接证据**: `backend/src/main/resources/db/migration/V004__catalog_order_and_payment.sql:204-208`；plan §4/§5/§1 Non-goals 原文；Control `:28`（禁止 DDL）
- **影响**: 用户可见延迟 / 数据库成本风险后移（本切片验收不含性能证据，后续返工）
- **建议改法和验证点**: plan 至少补一条：以 PostgreSQL 16 `EXPLAIN (ANALYZE, BUFFERS)` 固定场景证明页查询有界（或声明最坏成本可接受的理由与引用 docs18 预算），并把"为 `(account_id, owner_organization_id, created_at DESC, id DESC)` 增加读索引"作为带 owner 的 deferred risk 交给独立的 ACL/DDL scope，而不是留在实现 Agent 手上。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
