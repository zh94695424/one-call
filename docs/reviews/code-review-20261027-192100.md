### F-01 — Low — Cross-module `FOR UPDATE` denial for `organization_membership` is not isolated (false-success pattern)

- **Entry:** `runtimeAndCrossModulePrivilegesAreExactAndWritesDenied` → `assertCrossModuleRuntimePrivileges`
- **File/line:** `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:1295-1298` (`customer_iam_role`), `:1344-1346` (`subject_number_role`)
- **Trigger:** negative cross-module row-lock probe on `organization_access.organization_membership`
- **Actual branch:** The `customer_iam_role` probe is `SELECT id, organization_id, account_id, role, status ... FOR UPDATE`. `id` is not in the cross-module grant (`organization_id, account_id, role, status`), so PostgreSQL raises `42501` at column `SELECT` permission before it evaluates the row-lock (`UPDATE`) privilege. The `subject_number_role` block issues only a plain undeclared-`id` read (`:1345`) and no membership `FOR UPDATE` probe. The probe therefore passes for a different reason than the property it claims to prove.
- **Expected:** A membership `FOR UPDATE` probe that selects only cross-granted columns (e.g., `account_id`) must raise `42501`, proving no cross-owner row-lock privilege for both `customer_iam_role` and `subject_number_role`.
- **Actual:** Membership `FOR UPDATE` denial is not behaviorally isolated; it is effectively inferred from the catalog. Organization and `customer_account` `FOR UPDATE` probes are valid because they select the granted `id` column.
- **Evidence:** Disposable `postgres:16.15` probe (container removed) showed `has_table_privilege(role, table, 'UPDATE') = false` even when a column-level `UPDATE` exists, and that column-level `UPDATE` alone permits `SELECT ... FOR UPDATE`; therefore selecting an ungranted column masks the row-lock privilege check. The accepted S1 exact matrix at `PostgresContainerIT.java:5240-5255` does assert column-level `UPDATE = false` for all cross roles on all V002 tables, so the frozen catalog still guards the actual grant.
- **Impact:** The S3 behavioral claim overstates the membership row-lock/write proof. A future regression that granted column-level `UPDATE` on a non-`status` membership column to a cross role would evade this S3 probe (the S1 catalog would still catch it). No current V002 defect.
- **Fix/validation:** Change the customer probe to a granted-column projection (e.g., `SELECT account_id FROM organization_access.organization_membership WHERE account_id = ? FOR UPDATE`) and add the same probe for `subject_number_role`; then rerun the focused S3 method and the full 18-method container suite.
- **Fix risk:** Low — test-only; no V002/grant/schema change.
- **Severity:** Low (evidence/coverage; catalog-compensated).

A second pair is committed for the demote scenario (`:1542`) and cleaned in `finally`. The artifact says “after each success the method-local pair is cleaned so the final-enabled-admin checks run with an empty global enabled-admin set (precondition asserted)”.

- **Impact:** Evidence-only truthfulness defect; it does not change the executable result or V002. It could mislead a checkpoint reader about the global-count precondition.
- **Fix/validation:** Correct the evidence wording; optionally add an explicit `assertNoLeftoverEnabledAdministrators()` after the first cleanup and before the demote pair so the wording and code match. No V002 change.

## 4. Adversarial pass — results

- **Identity/role leakage:** Every behavioral privilege probe switches with `switchLocalRole`/`setLocalRole`, which does `RESET ROLE` + `SET LOCAL ROLE` and asserts `current_user`. The full suite passing means the `42501` denials occurred under the intended runtime roles; a role leak would have turned a denial into success and failed the test. Migration/superuser identity is used only for setup/cleanup, catalog reads and post-probe observation, consistent with plan §7.3/§8.3.
- **Unauthorized columns in positive reads:** Owned reads use table-level `SELECT`; cross-module positive reads use only the granted columns and `WHERE` on granted columns (`organization.id/display_name/status`, `membership.organization_id/account_id/role/status`, `customer_account.id/status`). The only confound found is F-01's membership `FOR UPDATE` projection.
- **False success on wrong SQLSTATE:** `expectSqlFailure`/`expectSqlQueryFailure` assert the exact `42501`/`23505`/`P0001` and, where required, the exact marker; they call `fail(...)` if the statement unexpectedly succeeds. Savepoint rollback always runs in `finally`.
- **Aborted transaction / savepoint leaves:** Expected failures are savepoint-scoped; the owning-guard direct call and last-admin failures roll back to savepoint. The suite passing implies no `25P02` aborted-state leak.
- **Residue:** Privilege probes run in one transaction and roll back; the forbidden `CREATE TABLE` probe leaves zero `s3_runtime_probe_forbidden` relations; last-admin committed employees are deleted by id with zero-residue assertions in `finally`; no runtime `DELETE`/`TRUNCATE` succeeds; no append-only table is touched.
- **Guard direct invocation:** The owning runtime role receives a non-`42501` error whose message contains `trigger` (trigger-context error), while foreign runtime roles receive `42501`; catalog checks assert EXECUTE only to the owning runtime role and not `PUBLIC`/other runtime roles. This correctly distinguishes EXECUTE privilege from trigger-context failure.
- **Last-admin protocol:** The exact advisory key `pg_advisory_xact_lock(hashtextextended('operations_iam.admin_mutation', 0))` is used; the target row is locked `FOR UPDATE` under `operations_iam_role`; the enabled-admin count is global and taken after the lock; the conditional update requires `role='ADMIN' AND status='ACTIVE' AND revision=<expected>` and increments revision; `LAST_ENABLED_ADMIN` (`P0001`) is raised before any write. Sequential disable and demote both succeed with revision+1 when two admins exist; final-admin disable and demote each fail closed and leave `ACTIVE|ADMIN|1`. The two-connection race holds the winner's xact advisory lock through commit, the loser is observed blocked (`wait_event_type='Lock'`, bounded 15 s), then acquires the lock, recounts, raises `P0001`, rolls back, and leaves `ACTIVE|ADMIN|1`; final pair enabled count is 1. Session-scoped locking would have hung `awaitFuture` (30 s), so the test does distinguish xact scope. Empty-global-admin precondition is explicit at method start and before the race (F-02 concerns the evidence wording, not fail-closed behavior).
- **Order/global state:** Other suites do not commit employees; the shared container starts with no enabled admins. If any leftover enabled admin existed, `assertNoLeftoverEnabledAdministrators` fails closed rather than weakening the protocol (RSK-S3-01).
- **Prior regression / scope:** The content-only IT diff is one javadoc hunk plus the addition hunk; all sixteen S1/S2 methods and their helpers are unchanged. CI/README only move the count/set to 18 and describe S3; no step, pin, permission, path filter, boot smoke, firewall or contract job was weakened.
