## 4. Findings

### PA17-RR4-A-01-未修复-中-`risk` 与 `count` 的求值顺序自相矛盾

- **位置**: §2.2 line 36；§2.3 steps 2/4（lines 43、45）；§5 `problemCodesPreserveFrozenStatusPrecedence`/`revokedExpiredLockedAndStaleGenerationMapExactly`；OpenAPI `x-onecall-replay-order`。
- **问题类型**: 状态机漏洞 / 错误优先级 / 契约不一致。
- **当前写法**: §2.2 line 36 明确“Risk is checked before count and again on replay/reconstruction”。但 §2.3 replay/final 的 re-check 列表写作 `status/time/generation/count/risk/member`，把 `count` 放在 `risk` 之前。
- **反例/失败场景**: grant 已达 `max_admissions`，且 subject_risk_state 为 `OPEN`。若实现按 §2.3 列表先判断 count，会返回 `SHARE_ADMISSION_LIMIT_REACHED`（409）而不是 `SHARE_RISK_BLOCKED`（403）。同一输入在两种求值顺序下产生不同冻结 error code/status。
- **为什么有问题**: OpenAPI 明确 `x-onecall-replay-order: verification-and-risk-before-count`；Goal Confirmation 要求 exact error mapping；plan 自己的 binding rule 是 risk-before-count。实现 Agent 无法从 plan 判断应以哪一处为准，且测试若编码错的一侧仍会“通过”。
- **直接证据**: plan lines 36、43、45；`.github/workflows` 无涉；`api/openapi/onecall-v1.openapi.yaml:3759`；plan 测试名 lines 201、216。
- **影响**: 安全敏感的 OPEN-risk 阻断可能被 limit 结果掩盖；HTTP code/status 与 OpenAPI 不一致；验收/回归失败或错误测试固化。
- **建议改法和验证点**: 冻结唯一求值顺序（建议 status/terminal → time/expiry → generation → risk → member/tenant → existing-key replay → limit → insert，与 `verification-and-risk-before-count` 一致），并让 §2.2、§2.3、§5 三处使用同一顺序。在既有 `problemCodesPreserveFrozenStatusPrecedence` 或 `revokedExpiredLockedAndStaleGenerationMapExactly` 中加入“OPEN risk + max reached”组合断言，不新增方法。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

### PA17-RR4-A-02-未修复-中-PA17 error code → HTTP status/title 映射与异常出口未冻结

- **位置**: §2.5 line 59；§4 lines 94/108/110；§5 lines 201/216；`CustomerProblemWriter`/`PublicSharesController` 现有代码。
- **问题类型**: 契约缺失 / 不可直接实施 / 错误映射。
- **当前写法**: plan 枚举 18 个 `ShareAdmissionException.Code`，明确 `VALIDATION_FAILED=422`、`SHARE_TOKEN_INVALID=404`、`SHARE_EXPIRED=410`、policy/dependency=503 等少数映射；其余（`SHARE_VERIFICATION_FAILED`、`SHARE_WRONG_TENANT`、`SHARE_LOCKED`、`SHARE_ADMISSION_LIMIT_REACHED`、`SHARE_GENERATION_STALE`、`SHARE_REVOKED`、`SHARE_SESSION_EXPIRED`、`FORBIDDEN`、`RATE_LIMITED` 等）未给出完整 status/title 表，也没有明确 `@ExceptionHandler(ShareAdmissionException.class)`。
- **反例/失败场景**: `ShareAdmissionCapabilityToken` 构造器或 binder 抛 `ShareAdmissionException`；现有 `PublicSharesController` 只有 `@ExceptionHandler(PublicShareQueryException.class)` 和 `@ExceptionHandler(Exception.class)`，后者会把它映射为 `INTERNAL` 500。`CustomerProblemWriter` 当前 `switch` 的 `default -> 500` 也会把未列出的 PA17 code 变成 500。结果：422/403/404/409/410/429/503 全部可能退化为 500；或者 `SHARE_LOCKED`/limit 被不同实现分别映射为 403/409。
- **为什么有问题**: Goal Confirmation 要求 exact Problem/status mappings；§2.5 的精确排序没有可执行表；测试 `problemCodesPreserveFrozenStatusPrecedence` 需要冻结期望值，否则实现与测试可一起固化错误契约。OpenAPI 只列出 401/403/404/409/410/422/429/503 响应，未逐 code 给出 403-vs-409 的区分。
- **直接证据**: plan lines 59、94、108、110、201、216；`backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerProblemWriter.java`（public overload 仅覆盖 `CustomerContextException.Code`/`PublicShareQueryException.Code`/`ShareCommandException.Code`，private switch `default -> 500`）；`PublicSharesController.java` 现有两个 handler；OpenAPI lines 3782–3802。
- **影响**: 用户可见错误状态错误；错误优先级测试不可验收；generic 500 掩盖真实 PA17 语义；后续返工。
- **建议改法和验证点**: 在 §2.5 或 §4 增加 exact PA17 code → status/title 表，至少覆盖全部 18 个 code，并明确 `@ExceptionHandler(ShareAdmissionException.class)`（或等价 dedicated problem mapping）优先于既有 generic handler；保留 GET/creator 现有映射。让 `problemCodesPreserveFrozenStatusPrecedence` 与 `revokedExpiredLockedAndStaleGenerationMapExactly` 对表断言。

### PA17-RR4-A-03-未修复-低-“raw admissionRequestId never fingerprinted”与必需的 SHA-256 派生矛盾

- **位置**: §2.2 line 30 与 line 32；§2.3。
- **问题类型**: 安全契约 / 措辞矛盾。
- **当前写法**: line 30 在定义 `admissionKey = "admission:" + lowercaseSha256(canonicalJson({shareGrantId, admissionRequestId}))` 的同时说“raw `admissionRequestId` is never persisted, logged, fingerprinted, or emitted”。line 32 又定义 `requestKeyDigest` 为“lowercase SHA-256 of the exact stable request key”。
- **反例/失败场景**: 实现 Agent 按“never fingerprinted”拒绝/避免计算 admission key 或 requestKeyDigest；或测试把“request ID 的任何 digest”视为泄漏而断言失败。反之，若实现按公式计算，静态审计可引用该句指控其“fingerprint”。
- **为什么有问题**: 安全要求应是“raw value 不落盘/不输出”，而不是“不得计算确定性 digest”。docs/14 line 253 明确：raw request ID 从不存储，只存 derived key。Plan 的同一句同时要求派生 digest 和禁止 fingerprint，语义冲突。
- **直接证据**: plan lines 30、32；`docs/14-production-data-model-and-flyway-schema-spec.md:253`。
- **影响**: 实现/测试歧义；security contract 表述不准确；审计争议。
- **建议改法和验证点**: 改为“raw value 从不持久化、记录、输出或作为独立标识；只允许计算并持久化 deterministic `admissionKey` 与 `requestKeyDigest`（小写 SHA-256），且任何日志/响应/事件不得含 raw value”。测试同时断言 raw 缺失与 digest 存在。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

### PA17-RR4-A-04-未修复-低-“verificationResult 仅在 API response”与 `share_admission.verification_result` 写入矛盾

- **位置**: §2.3 step 5 line 46；§3 line 79；V009 `sharing.share_admission`。
- **问题类型**: 持久化契约 / 措辞矛盾。
- **当前写法**: line 46 说“`verificationResult` remains in the API response only, never this durable payload or its fingerprint”。line 79 明确 V012 对 `sharing.share_admission` 的 column-level INSERT 包含 `verification_result`；V009 该列 `NOT NULL` 且有 `NOT_REQUIRED/VERIFIED` check。
- **反例/失败场景**: 实现 Agent 按“API response only”从 admission row 插入中省略 `verification_result`，触发 NOT NULL/check 失败；或在 review 中把该列的持久化误判为泄漏并在后续“修复”中删除。
- **为什么有问题**: fix-5 OQ-1 的准确要求是 `ADMISSION_GRANTED` event payload/fingerprint 不含 `verificationResult`，不是 admission row 不含；V009/V012 要求 admission row 持久化它。Plan 的 “API response only” 过宽，与自身 V012 ACL 文本冲突。
- **直接证据**: plan lines 46、79；`backend/src/main/resources/db/migration/V009__sharing.sql` 的 `share_admission` 定义（`verification_result text NOT NULL`，`ck_share_admission_result`/`ck_share_admission_result_shape`）。
- **影响**: 插入失败或错误删除 durability 字段；隐私语义误述；验收返工。
- **建议改法和验证点**: 改为“`verificationResult` 保留在 API response 和 immutable `share_admission` row；绝不出现在 `ADMISSION_GRANTED` payload 或 `payload_sha256`”。测试同时断言 row 值、event payload 无该 key、API response 有该字段。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

## 5. Open Questions

1. **Repository 方法清单是否足够**：§4 line 99 的 `ShareAdmissionRepository` 方法清单没有显式的 subject ownership / captured binding / current active binding 读取方法，也没有显式的 lifecycle advisory-lock 方法；§2.2/§2.3 要求这些读取和 ranks 7/8/9 advisory locks。请确认它们由 `findGrantByTokenDigest`/`readSubjectRisk` 或“dedicated repository lock operation”覆盖，否则实现 Agent 只能在 allowlisted repository 中新增未列名方法，或违反“SQL/locks only in repository”的边界。
2. **Replay 与 strict binder 的先后**：same-key replay 的 body 若 schema-invalid（例如 verification 分支非法），binder 会在 service 前返回 422，而不是“忽略 changed/unavailable proof”走 replay。请明确：仅 schema-valid 的 changed proof 被忽略；invalid body 始终 422。
3. **`admit` 的 no-throw 边界**：§4 line 96 说 service “does not throw before a denial transaction commits”，但 token constructor/binder 的 422 在事务前抛出。请明确 pre-transaction validation exception 与 committed denial outcome 的边界，避免实现把所有错误塞进事务或把验证错误误映射为 500。
4. **VERIFICATION_FAILED/EXPIRED fingerprint 字段**：plan 引用 docs/14，但 line 32 的“`requestKeyDigest` plus mode/result/reason”和 line 45 的“`{kind: EXPIRY, expiresAt}`”没有完整列出 docs/14 §2.12 的 canonical payload/actionFingerprint 输入（如 `shareGrantId`、`eventType`）。请确认以 docs/14 全文为准，并在测试中断言完整字段集。
5. **TICKET_ISSUED/TICKET_FAILED payload key set**：plan 只冻结 event ID 公式，没有冻结 redacted payload/fingerprint 的 exact keys。请确认这是有意留给实现（仅要求 deterministic/redacted），还是应像 `ADMISSION_GRANTED` 一样冻结；否则同一 ticket failure 重试可能因 payload 字段选择不同而冲突。
