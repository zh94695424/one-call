### F-PR7-01 (Low) — `A5_COUNT_ONLY_COVERAGE` declared but never emitted

**Trigger**: Plan line 921 claims: "any shortcut reading fixture count/coverage count directly setting true => `A5_COUNT_ONLY_COVERAGE`（代码级 fail-safe，不允许）". Reason code is declared in `acceptance/validate.mjs:145` and matrix `reasonRegistry` (`acceptance-matrix-v1.json:28074`).

**Actual path**: Grep across `acceptance/validate.mjs` finds `A5_COUNT_ONLY_COVERAGE` only in the `REASON_CODES` declaration (line 145). Zero `root()` or `report()` calls emit this code. Sibling codes `A5_LEGACY_REFERENCE_FORBIDDEN` (emitted at lines 1183, 1555, 2298) and `A5_PROHIBITED_READINESS_FLAG` (emitted at lines 1251, 2682) are properly emitted, confirming the gap is specific to this code.

**Expected**: A code path that detects a count-only shortcut and emits `A5_COUNT_ONLY_COVERAGE` as a fail-safe.

**Actual**: No emission path exists. Coverage completeness is derived indirectly (per-cell semantic checks + evidence/authority requirements for `productionAccepted`), but the named fail-safe is not implemented.

**Impact**: Plan documents a code-level fail-safe that does not exist. Documentation overstates enforcement. Core acceptance boundary (`authorityRegistry=[]` → `productionAccepted=false`) is separately and correctly enforced and is not compromised.

**Fix**: Either (a) implement an emission path that detects count-only shortcut patterns, or (b) correct plan/docs to remove the "code-level fail-safe" claim for this specific code and reclassify it as a declared-but-unimplemented reason code.

**Fix risk**: Low. Option (b) is documentation-only. Option (a) adds a new detection surface that must not false-positive on legitimate count assertions.

### F-PR7-02 (Low) — `A5_DETERMINISM_FAILURE` declared but never emitted; `deterministic=true` hardcoded

**Trigger**: Plan line 923 claims: "同一输入重复运行两次，canonical output 相同；否则 `A5_DETERMINISM_FAILURE`". Reason code declared in `validate.mjs:146` and matrix `reasonRegistry` (`acceptance-matrix-v1.json:28078`).

**Expected**: Validator either performs an internal determinism check and emits `A5_DETERMINISM_FAILURE` on mismatch, or reports determinism as externally verified/unverified rather than asserting `true`.

**Actual**: `deterministic=true` is asserted unconditionally without verification. The plan's double-run fail-safe is not implemented.

**Impact**: Validator output claims a property it does not verify. Empirically the property holds (controller ran S1/S2 twice with byte-identical SHA-256 `085752AE…1280` / `810029BE…BA9`), but the tool itself does not enforce it. This is a misleading claim in the tool's own output, not a production-readiness claim.

**Fix**: Either (a) implement actual determinism verification (e.g., hash canonical output, compare across runs, emit `A5_DETERMINISM_FAILURE` on mismatch), or (b) change line 3803 to report determinism as externally verified (`deterministic=external` or `deterministic=unverified`) rather than a hardcoded `true`.

**Fix risk**: Low. Option (b) is a one-line output correction. Option (a) adds runtime cost and must define what "same input" means precisely.
