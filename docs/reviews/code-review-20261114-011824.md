### PA32-CR-A-01 — Low — Employee-revocation IT exercises only one of the two plan-required serialization orders

- **Entry/branch**: PostgreSQL concurrent `operations_iam.employee_account` disable vs an Operations suspend/resume that has taken/locked current employee authority. Plan §8.6 test19 requires both serial orders: “a waiting disable cannot interleave with the held employee lock, and a committed disable before acquisition denies first/replay.”
- **Location**: `backend/src/test/java/com/onecall/archtests/container/OperationsSubjectLifecycleIT.java:111–116` (`employeeRevocationSerializesWithLockedCurrentAuthority`), against the plan text at `docs/gateflow/pa32-operations-subject-suspension-resume-lifecycle-plan.md:367`.
- **Expected**: two latch/barrier scenarios: (a) the disable holds the administrator advisory and employee row and commits before the operation acquires them → the operation denies; (b) the operation acquires/locks first and remains inside its transaction, a disable waits on the same locks, the operation commits, then the disable commits. Case (b) is the direct proof that the employee row/administrator locks are held through the owner-local writes, not released after the facts read.
- **Actual**: the test covers only case (a): the blocker holds `operations_iam.admin_mutation` + the employee row, then updates `status='DISABLED'` and commits before the pending request proceeds; it asserts 401 and zero effects. No statement captures a disable waiting behind a locked operations transaction, and no assertion proves the operation's employee lock survives its `advance`/transition/Outbox/audit writes.
- **Direct evidence**: the only disable/contention setup in the IT is the lines above; `grep` over the IT for `DISABLED`/`employee_account … FOR UPDATE`/`admin_mutation` returns only that method. The complementary tests (`locksFollow…:83–89`, `handoffUsesOneBackendPid…`) prove statement order and same-backend handoff but do not introduce a competing disable after the operation has acquired the locks.
- **Impact**: verification gap for a security-relevant lock-lifetime property. The current production code holds all row/advisory locks until the REQUIRES_NEW transaction commits (`DefaultOperationsSubjectLifecycleService.java:40–83`; no savepoints/early release), so I found no production defect; however, a future refactor that splits the employee read from the writes, or releases/commits early, could pass the current suite. The Controller's `70/70` evidence does not close this branch because no test executes it.
- **Actionable fix**: inside the existing test method only, add the reverse-order scenario with the existing fixture helpers/latches: let the suspend acquire the employee/admin locks and block after its employee read (an execute listener or test hook already used by the fixture can latch it), submit a disable that must wait, release the operation, assert the 200/committed transition+Outbox+audit, then commit the disable and assert the next same-key replay is 401 and unchanged facts. Preserve the method count/name and the 24-method IT inventory; no new file or test arithmetic.
- **Risk/severity**: Low verification risk; no production change is required. Controller owns whether this acceptance-evidence gap blocks the gate.

### PA32-CR-A-02 — Low — “Pool reuse cannot leak role” assertion does not force reuse of the connection that ran the failed restoration

- **Entry/branch**: PostgreSQL role restoration failure in the employee handoff / audit handoff, followed by pool reuse. Plan §8.7 test7 is named `failedRestorationRollsBackAndPoolReuseCannotLeakRole`.
- **Location**: `backend/src/test/java/com/onecall/archtests/container/OperationsSubjectLifecycleFixture.java:78` (`pool.setMaximumPoolSize(2)`) and `:203–207` (`cleanPool`), used by `OperationsLifecycleRoleLeastPrivilegeIT.java:56–76`.
- **Expected**: the post-failure check should deterministically acquire the same physical backend that executed the aborted handoff, or ensure only that backend can serve the check, and then assert `current_user`/`session_user`, transaction state, advisory locks and absence of a leaked role. With a two-connection pool, the clean backend can satisfy the assertion while the dirty backend is never inspected.
- **Actual**: after the failed transaction, `cleanPool` starts one ordinary transaction and `identity()` asserts `login|login|…`; Hikari may hand out either of the two backends. The test also checks no `idle in transaction`/advisory locks, but a leaked **idle** session role on the other backend would not appear in either query. The test can therefore pass non-deterministically and is not a proof of same-connection restoration for the failure path.
- **Direct evidence**: fixture line 78 sets the mutable pool to 2; `cleanPool` lines 203–207 run a single `transaction.execute` plus two catalog queries keyed only by `usename`, not by the failed PID. The first part of `failedRestoration…:57–60` uses a custom collaborator whose `finally` restoration fails; the second part injects a real abort listener at `:61–75`; neither part constrains the next borrow to the aborted PID. The production code uses transaction-local `SET LOCAL ROLE` with explicit restoration (`DefaultEmployeeAdministratorLock.java:40–63`; `JooqOperationsLifecycleRepository.java:69–82`), so rollback/commit already resets the role; this is a test-strength issue.
- **Impact**: verification gap for the role-leak backstop, not a production defect. A future change from `SET LOCAL ROLE` to session-level role switching, or a restoration bug on the committed path, could escape the current check because the identity probe may run on the clean connection.
- **Actionable fix**: in the fixture/failure test, force single-connection reuse for the clean check (temporarily `setMaximumPoolSize(1)` with all connections evicted/closed, or capture the aborted PID and assert the next borrowed PID equals it before running `identity()`), then restore pool size 2 for the concurrency tests. Keep the existing method names/counts.
- **Risk/severity**: Low verification risk; no production change is required.

If the frozen contract intends only visible-ASCII header values, this is a non-issue; if it intends arbitrary UTF-8, the HTTP boundary needs an explicit decision/test. The Controller/API owner should settle this; I did not attempt to run a container to prove the decode behavior.
