## Findings

### DR-01-已修复-[高]-多数受控动作仍把页面可读权限当成写权限
- **入口/函数**: `pageNumberDetail`、P1/P2 动作按钮、全局 click dispatcher、`executeCommand`
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:272`、`:452`、`:997`、`:1046`、`:1061`
- **输入场景**: 超级管理员进入商品、公证或权益页面后执行业务动作；或任意已登录角色向 DOM 注入 `open-command`、`product-publish`、`staff-disable` 等 action。
- **实际分支**: `canCommand` 只覆盖 4 个动作；其余 action handler 不校验角色，`open-command` 还接受任意命令和对象并最终调用 `executeCommand`。
- **预期行为**: 每个受控动作在按钮渲染和 handler 两处调用同一动作权限真源；超级管理员只拥有 IAM/策略能力，不因 `areas:['all']` 自动取得业务命令。
- **实际行为**: 能读取路由的角色或伪造 action 的角色可以推进业务状态；超级管理员可发布商品、重试存证、发放补偿等，违反批准角色矩阵。
- **直接证据**: `commandRoles` 仅注册订单补发、分享撤销、导出重申请、综合对账；`:997-1059` 的多数写 handler 直接写 `state`；`:1061-1068` 无命令权限校验。
- **影响**: 原型表达错误 RBAC 和受控命令契约，可能使评审批准生产权限提升。
- **建议改法和验证点**: 建立覆盖全部动作的权限矩阵；按钮和 dispatcher 双校验；移除超级管理员的业务命令权限；QA 对超级管理员和只读角色伪造动作做拒绝断言，并保留各领域允许路径。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-02-已修复-[高]-P0 第二条详情仍显示第一条对象事实并可能揭示错误身份
- **入口/函数**: `pageUserDetail`、`pageIdentityDetail`、`pageOrganizationDetail`、`pageTicketDetail`
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:406`、`:425`、`:437`、`:514`
- **输入场景**: 从列表打开 `USR-2189/USR-2271`、`IDC-3112`、`ORG-30027`、`TKT-10435/TKT-10438`，或对非首个用户签发临时身份访问。
- **实际分支**: 页面标题部分使用 URL ID，但正文、工单类型、组织主体、掩码和临时揭示值仍硬编码首条 fixture；用户查找失败还回退到 `users[0]`。
- **预期行为**: 可点击记录的标题、摘要、受控动作对象和敏感内容必须来自同一个 fixture；未知对象统一拒绝且不回退到其他真实对象。
- **实际行为**: 详情组合了不同对象的事实，`USR-2189` 的授权可能显示 `USR-2048` 对应的虚构完整姓名/证件/号码。
- **直接证据**: `pageUserDetail` 只对标题取 `u`，敏感值和掩码固定；三个其他详情 renderer 仅把 `id` 插入标题/ID 字段，其余内容固定为首行。
- **影响**: 对象身份错配、审计和业务判断绑定错误对象，高敏内容被展示在错误授权上下文。
- **建议改法和验证点**: 为所有可点击 P0 fixture 建立按 ID 取值的数据结构，移除首条 fallback；QA 遍历第二记录并断言对象身份、事实和敏感值一致。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-03-已修复-[高]-运营商角色可越过供应商对象范围并直接访问其他供应商
- **入口/函数**: `roleAllows`、`pageVendors`、`pageVendorDetail`
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:129`、`:257`、`:725`、`:734`
- **输入场景**: 使用范围为“渠道 A · 华东”的 `carrier` 角色进入供应商列表，或直接导航 `/vendors/VND-NOTARY-YZ`、`/vendors/VND-AI-CN`。
- **实际分支**: `roleAllows` 只比较 route area；供应商列表无范围过滤，动态详情接受任意 ID 并渲染对应供应商能力与健康事实。
- **预期行为**: 对象范围先于查询和详情加载；渠道 A 角色只能看到并访问 `VND-CARRIER-A`，越权详情进入统一拒绝页且不确认对象存在。
- **实际行为**: 渠道角色可查看公证和 AI 供应商元数据，并可创建绑定这些对象的升级工单。
- **直接证据**: `carrier.areas` 包含整个 `vendor` area；`roleAllows` 无路径 ID/对象范围输入；`pageVendors` 固定渲染三行。
- **影响**: 跨供应商数据范围泄漏和越权工单操作，违背登录页及计划中的对象级授权承诺。
- **建议改法和验证点**: 将供应商 fixture 与允许角色/范围绑定，在列表查询和直接路由两处使用同一对象范围规则；QA 增加 carrier 列表过滤、直接 URL 拒绝和伪造升级 action 拒绝。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
