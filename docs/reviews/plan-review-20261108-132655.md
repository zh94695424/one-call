## Findings

### 1-未修复-低-生产 provider 接线所需的模块边界修订前提未写入 §9 provider residual 行
- **状态**: `defer-candidate`
- **位置**: §9 residual table rows “Real credential provider …” and “Actual COS/KMS/Secret
  Manager access … inside a production provider”; §3 opening (“not a named interface and
  cannot be imported by other modules”); §7 method
  `playbackUsesOnlyNamedEvidenceReadAndPrivateTypedScope` (“no new named interface”);
  §9 closing “No residual authorizes additional work here.”
- **问题类型**: 架构边界 / residual 分类不完整（unclassified residual precondition）
- **当前写法**: §9 assigns production `MediaCredentialVerifier` / `ControlledMediaReader`
  providers to “Security + Platform + Sharing provider integration” / “Platform + Security +
  Evidence provider integration”, states defaults remain Unavailable, and asserts no residual
  authorizes additional work — without stating that wiring any cross-module production bean
  first requires an approved module-map / named-interface boundary revision.
- **反例/失败场景**: A later provider work unit implements the COS/KMS-backed
  `ControlledMediaReader` (or a signature-backed verifier) in an adapter/platform module and
  tries to declare `@Bean ControlledMediaReader`. Because the interface type lives in
  `com.onecall.core.sharing.internal.playback` with no `@NamedInterface`, the foreign module
  cannot reference the type; Modulith verification or compilation fails. The fallback attempt
  — implementing it inside sharing — collides with docs/12 §244 (“核心领域不能依赖 … 供应商
  SDK；具体实现只能出现在 adapter 层”) and with this slice’s frozen boundary test that forbids
  new named interfaces. An “Evidence provider integration” bean would additionally require an
  `evidence → sharing` edge, creating a cycle against the existing `sharing → evidence` edge.
- **为什么有问题**: PA0 (docs/gateflow/pa0-production-runtime-bootstrap-plan.md §6.2,
  line 425) already requires every future cross-cutting edge to explicitly revise the
  `allowedDependencies` table and re-review (“不得为了‘以后方便’预先放宽 allowedDependencies”),
  and adding a sharing named interface would also require the exact-four interface assertions
  in `SharingQueryBoundaryTests` to be revised. §9’s provider rows record *ownership* but omit
  this *precondition*, while the plan elsewhere is rigorous about recording equivalent
  constraints (e.g., V013’s PUBLIC-ACL rejection called out for future migrations). The
  assigned owners can therefore be misled into believing provider integration is ordinary
  implementation rather than a reviewed boundary-revision event.
- **直接证据**: Plan §3 line “They are not a named interface and cannot be imported by other
  modules”; §7 “no new named interface”; §9 provider rows and “No residual authorizes
  additional work here”; PA0 §6.2 line 425; docs/12 line 244;
  `SharingQueryBoundaryTests` exact four named interfaces;
  `ModuleBoundaryTests` exact sharing allowed-dependency row.
- **影响**: 后续 work unit 在实现阶段才发现需要边界修订 → 意外 stop/返工，或实现者为绕过
  限制而弱化本 slice 冻结的边界测试（真实安全风险，虽非本 slice 正确性缺陷）。
- **建议改法和验证点**: 在 §9 的两个 provider residual 行各加一句：生产 provider bean 若
  位于 sharing 之外，必须先按 PA0-R-09 修订 `allowedDependencies`/named-interface 映射并
  通过 `ModuleBoundaryTests`/`SharingQueryBoundaryTests` 的精确断言评审；若位于 sharing 之内，
  必须先裁决 docs/12 §244 adapter-layer 约束。验证点：未来 provider plan 的 residual/
  non-goals 必须引用该前置条件；本 slice 不需要任何代码改动。
- **修复风险（低）**: 低 — 纯文档/ residual 表一句话补充，不触碰本 slice 行为、测试或
  allowlist。
- **严重程度（低）**: 低 — 不威胁本 slice 的可实施性、正确性或验收；属于后续 provider

## Open Questions

1. **`VerifiedMediaClaim` 对象作用字段的独立来源（含自反性 SCOPE_MISMATCH 风险）** —
   §4 step 7 compares `claim.mediaObjectId` / `durationSeconds` against
   `EvidenceMediaObjectReader.resolve(claim.evidenceId)`, and §5 step 1 compares
   `claim.evidenceId` against the grant row. Evidence: PA18’s
   `MediaAuthorizationCredentialRequest` carries only
   `{shareGrantId, shareAdmissionId, purpose, eventType, requestKeyDigest, codeGeneration,
   revocationGeneration, three expiries, credentialExpiresAt, preProviderFingerprint, eventId}`
   — no evidenceId/mediaObjectId/duration/window; docs/14 §2.5 states the shareable projection
   and `content_snapshot` deliberately contain **no media-object id**; the witness payload is
   exactly the six (or eight) fixed keys; grant `GRANT_COLUMNS` has `evidence_id` but no
   media-object column; OpenAPI exposes only the opaque credential string. Therefore a
   production verifier can populate `mediaObjectId`/`durationSeconds`/`window` only from its
   own future enrichment/wire format — and if it uses the same evidence reader keyed by the
   same evidenceId, step 7’s object check compares one source against itself (media objects
   are append-only/immutable, so the check adds no independent assurance). The plan does
   classify “wire/enrichment and issued-claim provenance” as residual (§9 row 2), and tests
   inject claims directly, so this is not an in-slice defect; the Controller should confirm
   that row 2 adequately owns defining an **independent** object-scope source (e.g.,
   issuance-time embedding in the opaque credential) so that production SCOPE_MISMATCH is
   non-vacuous. Tracking: future Security/Platform provider work unit plan.
2. **§5 step 2 “Missing/inconsistent grant bounds => Unavailable” 未枚举** — The step orders
   `REVOKED → EXPIRED/status-or-now≥expiresAt → bounds → validFrom → ACTIVE/LOCKED` but never
   enumerates what “missing/inconsistent” includes (null `validFrom`/`expiresAt`,
   `validFrom >= expiresAt`, null after a non-EXPIRED status). A codegen agent will most
   likely infer exactly those cases, and the fallback is fail-closed Unavailable either way,
   but the plan’s otherwise-total precision makes the omission a small ambiguity worth one
   clarifying clause at implementation intake. Tracking: implementation-report questions or
   Controller clarification; not a plan re-write blocker.
