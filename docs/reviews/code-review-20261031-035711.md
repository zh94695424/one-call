## Findings

### 1-未修复-中-guard revision monotonicity is not behaviorally distinguished from "any revision change"

- **入口/函数**: `v008MediaRecordingShapeDefaultsAppendOnlyAndRollbackBackstops` / `v008CreationCycleBothOrdersAndTerminalLifecycleBackstops` → `guard_recording` / `guard_evidence_record` revision branch
- **文件(行号)**: `backend/src/main/resources/db/migration/V008__evidence_media.sql:341-342, 374-375` (guard predicate); `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:2714-2716, 2749-2752, 2884-2885, 2902-2905` (probes)
- **输入场景**: A legal status transition (e.g. `DECLARED → UPLOADED` or `PENDING → SOLIDIFIED`) submitted with `revision = OLD.revision + 2` or `revision = OLD.revision - 1`
- **实际分支**: The guard predicate is `IF NEW.revision <> OLD.revision + 1 THEN RAISE …_REVISION_INVALID` — correct strict +1. Tests probe (a) status change with unchanged revision → `*_REVISION_INVALID` and (b) same-state revision write (`revision = 7` / `revision = 9`) → success. No probe submits a legal status change with a non-+1 revision delta.
- **预期行为**: If the frozen contract is "status transition requires exactly `revision+1`" (plan §9 line 615: "allowed with revision+1"), the suite should also prove that `+2`/`-1` on a legal transition is rejected, so a weakened predicate (`<> OLD.revision`, `>= OLD.revision`) cannot pass.
- **实际行为**: Every current assertion is green under both the correct `+1` predicate and a weakened "any change" predicate. The migration itself is correct; the witness set cannot tell them apart.
- **直接证据**: SQL `V008__evidence_media.sql:341` `NEW.revision <> OLD.revision + 1`; test `PostgresContainerIT.java:2714` probes only the no-bump case; `:2749` proves same-state jump to 7 succeeds (outside the transition branch); no `RECORDING_REVISION_INVALID`/`EVIDENCE_RECORD_REVISION_INVALID` probe with `revision = old±k` on a status-changing UPDATE.
- **影响**: Test gap only — no production misbehavior in the shipped migration. A future guard edit that accepts non-+1 transition revisions would remain green.
- **建议改法和验证点**: Add two savepoint-isolated `expectSqlFailure(..., "P0001", "RECORDING_REVISION_INVALID", ...)` (and the evidence_record analogue) with `status` set to a legal next state and `revision = old + 2` / `revision = old - 1`. Classify as optional future test, not a gate blocker (see Residual Risk).
- **修复风险（低/中/高）**: 低 — additive probes inside existing savepoint blocks; no SQL change.
- **严重程度（低/中/高/严重）**: 中 (coverage of a core immutability/revision invariant)
