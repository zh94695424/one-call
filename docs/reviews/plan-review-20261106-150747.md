## Findings

### 1-未修复-[高]-未来测试算术错误：`9/172 = 275` 应为 `9/162 = 265`

- **位置**: §5 “Planned future inventory” (L147–154); §10 completion report (L291); implied CI/README targets (L154, L134–135)
- **问题类型**: 不可直接实施 / 契约缺失 / 测试缺口（exact source=CI=XML arithmetic）
- **当前写法**: “adds exactly three classes and **44 methods**, for **20 Surefire classes / 103 methods**, **9 Failsafe classes / 172 methods**, combined **275 methods**”; CI must assert `20/103`, `9/172`, `275`; completion report repeats `20/103 + 9/172 = 275` with “exactly 44 new methods”.
- **反例/失败场景**: Independent derivation from the plan’s own method lists and the verified baseline:
  - Baseline (source = CI = XML): Surefire `19/91`, Failsafe `7/130` (`64+10+10+8+12+18+8`), combined `221`.
  - Additions: `ShareAdmissionServiceTests` 12 (Surefire); `PublicShareAdmissionIT` 24 + `SharingAdmissionRoleLeastPrivilegeIT` 8 = 32 (Failsafe); total new = **44**.
  - Future: Surefire `20/103` (91+12); Failsafe `9/162` (130+32); combined **265** (221+44).
  - Plan’s `172` and `275` are each **+10** (172−162=10; 275−265=10) and are internally inconsistent with “44 new methods” (275−221=54≠44).
  - An implementation that updates CI/README to `172/275` fails exact inventory; an implementation that keeps true counts fails the plan’s stated CI assertions. Either way the plan is not code-generation-ready on the exact-inventory contract.
- **为什么有问题**: Goal Confirmation requires exact source=CI=XML arithmetic owned by the plan; the plan’s frozen numbers are arithmetically wrong against its own inventories and the live baseline. Controller intake already flagged this class of defect; independent derivation confirms it.
- **直接证据**: Plan L143 (baseline 91/130/221), L147–151 (12+24+8), L147/L154/L291 (172/275); source scan of all `@Test void` methods: 91+130=221; CI maps equal source sets; listed new method names = 44.
- **影响**: Implementation agent writes wrong CI totals and README; verification gate fails or agent illegally edits inventory; review cannot accept “exact arithmetic”; rework of CI/README/plan.
- **建议改法和验证点**: Replace every future total with `20/103`, `9/162`, `265`; keep `44` new methods; recompute any derived CI assert strings and README text from `baseline + listed methods` only; verification = `91+12=103`, `130+32=162`, `103+162=265`, `221+44=265`, and no remaining `172`/`275` in the plan.
- **修复风险（低）**
- **严重程度（高）**

### 3-未修复-[中]-ranks 7/8/9 “advisory/row locks” 与 V012 “No foreign locks” 及 docs14 owning-module 规则冲突

- **位置**: §2.2 (L34) vs §3 V012 cross-schema bullet (L80)
- **问题类型**: 架构边界 / 过度耦合 / 不可直接实施
- **当前写法**: §2.2 — “acquire organization, membership, and account lifecycle advisory/**row locks** in frozen ranks 7, 8, and 9”; §3 — “No cross-schema writes, **foreign locks**, …”.
- **反例/失败场景**: docs14 global lock order (§ around L2979): ranks 7/8/9 take lifecycle **advisories**, and row locks “only in the owning module.” Sharing is not the owner of `organization_access` / `customer_iam` tables. If the implementation follows §2.2 literally and runs `SELECT … FOR UPDATE` on foreign tables: (a) V012 grants only cross-schema `SELECT`, so PostgreSQL will refuse lock escalation / the V012 postcondition “no foreign locks” fails; (b) if V012 were widened to allow foreign `FOR UPDATE`, it would violate docs14 and least privilege. If the implementation follows V012 (advisory only), §2.2’s “row locks” text is wrong and invites a later “fix” that breaks ACL tests.
- **为什么有问题**: Two frozen statements in the same plan prescribe opposite lock privileges for the same ranks; neither the repository method list nor `JooqShareAdmissionRepository` text resolves which lock kind is legal.
- **直接证据**: Plan L34 (“advisory/row locks”), L80 (“No … foreign locks”); docs14 lock order text: “(7) organization lifecycle advisory and, **only in the owning module**, the organization row lock”; (8)/(9) same pattern; V010/V011 pattern of cross-schema SELECT-only for non-owners.
- **影响**: Runtime `42501`/failed lock, V012 postcondition failure, deadlock-avoidance contract break, or implementer rewrites mid-slice.
- **建议改法和验证点**: State explicitly: ranks 7/8/9 in the admission transaction acquire **lifecycle advisory locks only** (e.g. `pg_advisory_xact_lock` on the frozen namespaces), then non-locking (or owner-free) re-reads of the declared columns; row locks remain owner-module-only and are out of scope for PA17; V012 continues to deny foreign locks. Verification = plan contains no instruction to `FOR UPDATE` foreign tables; `SharingAdmissionRoleLeastPrivilegeIT` still denies foreign lock attempts.
- **修复风险（低）**
- **严重程度（中）**

### 4-未修复-[中]-`admissionKey` 长度写成 73，实际为 74

- **位置**: §2.2 (L31)
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: “Persist only this **73-character** derived key.”
- **反例/失败场景**: `"admission:"` is 10 code points; lowercase SHA-256 hex is 64; total = **74**. An implementer or unit test that asserts `length == 73` rejects the correct key or pads/truncates wrongly; a diagnostic that trusts the plan number mis-documents the idempotency identity. V009 `ck_share_admission_key` allows 1–128 so the DB will not catch the off-by-one.
- **为什么有问题**: The plan freezes a concrete length constant that does not match its own formula; code-generation-ready plans must not ship false constants on idempotency identities.
- **直接证据**: Plan L31 formula + “73-character”; `len("admission:")+64 == 74`; docs14 §2.12 defines `admission:` + SHA-256 without a 73-char claim; V009 check is 1–128.
- **影响**: Wrong test assertion, wrong validation, confusion in replay diagnostics; low runtime risk but material contract error.
- **建议改法和验证点**: Change to **74-character** (or drop the length and keep only the formula); verification = `10+64=74` and any length assertion in the new unit tests uses 74.
- **修复风险（低）**
- **严重程度（中）**

### 5-未修复-[中]-Replay 成功的 HTTP 状态未冻结；OpenAPI 仅定义 `201`

- **位置**: §2.4 (L54); OpenAPI `createPublicShareAdmission` responses
- **问题类型**: 契约缺失 / 测试缺口
- **当前写法**: “The HTTP status for a **first** successful admission is `201`.” Replay is described as returning the original admission and reissuing the ticket, but no status is stated for replay.
- **反例/失败场景**: OpenAPI success response is only `'201'` (description covers first admit **and** same-`admissionRequestId` replay). An implementation that returns `200` on replay produces an undocumented status; clients generated from OpenAPI only handle `201`; exact problem/status tests cannot pin replay. Goal Confirmation requires exact admission/session/ticket windows and exact Problem/status mappings.
- **为什么有问题**: The frozen public contract has a single success status; the plan freezes status only for the first admit, leaving replay under-specified for a deterministic implementation.
- **直接证据**: Plan L54; OpenAPI L3776–3781 (`'201'` only, description includes replay); no `'200'` on this operation.
- **影响**: Client/contract mismatch, test ambiguity, non-deterministic implementation choice.
- **建议改法和验证点**: Freeze replay success as **`201`** with the same `ShareAdmission` body (aligning with OpenAPI); add/assert in `PublicShareAdmissionIT` that same-key replay returns `201` and identical field set; verification = plan text and OpenAPI agree on the sole success status.
- **修复风险（低）**
- **严重程度（中）**

## Open questions

1. **Manifest hash algorithm**: B contains exactly 1,413 files and is content-identical to the peer freeze inputs (excluding the peer’s own artifact path). The declared manifest SHA `40086B50…` was not reproduced under path-only, path+content, `sha256sum`-style, or concatenated-digest schemes. Controller should record the canonical manifest recipe (or accept count+content-identity as sufficient for this gate).
2. **Optional bearer on POST/NONE**: Plan freezes 401 for missing session “where required” (`ORGANIZATION_MEMBER`) and preserves anonymous NONE/code/mobile, but does not fully freeze behavior when an **invalid** `Authorization` header is present on a non-member mode (current GET has `optionalBearerFailuresKeepFrozenPrecedence`). Recommend pinning to the existing public GET precedence before implementation.
3. **Grant `EXPIRED` transition columns**: V009 `guard_share_grant` requires `revocation_generation = OLD+1` and `revision = OLD+1` on status → `EXPIRED`. Plan §2.3.1 says “persist the frozen `EXPIRED` transition” without restating the generation bump. The trigger backstops it, but the plan could state the exact UPDATE column set for code-generation readiness.

## Conclusion

**Verdict: `fail`**

Material, evidence-based defects prevent safe handoff to an implementation agent under the binding exact-arithmetic and exact-allowlist requirements:

1. Future inventory arithmetic is wrong (`172/275` vs correct `162/265`) in three plan sites and would break the CI/README freeze.
2. Allowlist items 20–22 are optional/preferred, violating the exact-allowlist contract.

Additional medium findings (lock-kind contradiction, `admissionKey` length, replay status, event identities) should be corrected in the same plan-fix pass. The plan’s architecture direction, Goal Confirmation alignment, V009/V011 reuse, fail-closed provider seams, and verified 221 baseline are otherwise sound; this verdict is about code-generation readiness of frozen contracts, not a recommendation to redesign the slice.

No plan, Control, source, test, migration, OpenAPI, POM, CI, README, or evidence file was modified. Only this review artifact was written.
