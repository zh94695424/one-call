### B-01-未修复-低-§10 pair-map 序列化描述与固定摘要值只在“二进制摘要字节”读法下相符
- **位置**: 累积 plan §10 “Pair-map digest”（`docs/gateflow/pa35-operations-ivr-session-read-foundation-plan.md:1030-1031`）与 fix5 §4 pin（`…-plan-fix-5.md:141-142`）。
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: “over path-sorted UTF-8 path,NUL,raw digest bytes, canonical digest bytes per row (no row terminator)”，并把值钉为 `ed03b90f…`。同一 §10 表格表头把 64 位十六进制称为 “Current raw SHA-256”，因此 “digest bytes” 可被合理读成十六进制字符串字节。
- **反例/失败场景**: 实施 Agent 按字面把 26 行拼成 `path + NUL + 64-hex RAW + 64-hex LF`（或再加一个 NUL），得到 `98a11b26…` / `bd86ac42…`，与钉住的 `ed03b90f…` 不等；F8/G1 失败后，最省事的“修复”往往是把钉值改掉或删掉 pair-map 等式——正好削弱 REREVIEW3-02 要求保留的 frozen-byte proof。
- **为什么有问题**: 同一句里 “NUL” 只出现一次，而钉值要求“两个摘要各 32 二进制字节、彼此无分隔”，只有这种拼接可复现；把可复现公式留给读者猜，在一个以字节证明为核心验收项的 slice 里是不必要的实施风险。
- **直接证据**: 我的复现脚本：`sha256(Σ sorted(path_utf8 + b"\x00" + bytes.fromhex(raw) + bytes.fromhex(lf))) == ed03b90fe748039ca7d1d674c32cf0e0c56b828901116294a1ea5dd011954409`（True）；`hex` 读法 → `98a11b262fd351099474c13fde7e0636e71f70fd70bc8a18c7896e7588e93179`；`binary + 中间再加 NUL` → `65090d776ead05e271e3af467b5f4f24e5f31e126a4b31ec447619d69b677562`。另见 fix5:194 使用同族写法 “sorted UTF-8 path,NUL,raw digest bytes” 描述 2151 路径快照摘要。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 后续返工 / 削弱冻结字节证明（review 不可验收）。
- **建议改法和验证点**: 把该句改写为 “每行 = path UTF-8 字节 + 单个 0x00 + 32 字节二进制 raw 摘要 + 32 字节二进制 canonical-LF 摘要；行之间无分隔符、无行终止符；按 path 的 UTF-8 字节升序”，并在 F8/G1 里把“十六进制读法必须不等于钉值”作为负例（或直接断言总字节长度 == 26×(len(path)+1+64)）。验证点：在 LF 与 CRLF 两种 checkout 下 pair-map 摘要均等于钉值；改动任一表格 hash 后 F8/G1 失败。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
