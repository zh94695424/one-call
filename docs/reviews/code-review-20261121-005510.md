## Findings (fixed format)

### PA39-RR-A-01 — [Low] `sqlState()` can stop scanning before a nested SQLException state

- **Status:** open, non-blocking hardening observation (not a demonstrated runtime failure).
- **Location:** `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/DefaultOperationsCatalogDraftCommand.java:82-88`.
- **Evidence:** the corrected helper returns `""` immediately when a `DataAccessException` is encountered whose `sqlState()` is null (`return data.sqlState() == null ? "" : data.sqlState();`), instead of continuing to the cause chain. The pre-fix code continued when the state was null. If such a wrapper ever hides an inner SQLException carrying `23505`/`40001`/`55P02`/`55P03`, the owner would return 503 instead of recovery/409.
- **Impact:** low. On the tested jOOQ path `DataAccessException.sqlState()` derives from its SQLException cause (the existing recovery tests depend on it), so no current call path demonstrates the loss.
- **Recommendation:** when `sqlState()` is null, continue walking the cause chain (e.g., check `cause.getCause()`) before defaulting to the SQL-failure `""` sentinel; add one unit subcase for a state-less `DataAccessException` wrapping a stated `SQLException`.
