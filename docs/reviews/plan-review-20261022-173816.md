## Findings

### F-14-未修复-[中]-撤销场景把“确认先提交”写成 REJECT，和两序列化顺序规则及其测试互斥

- **位置**: Plan §10.1 transaction outcome contract line 600; illustrative scenarios line 609; section 11 tests lines 746 and 768; D45 line 209; fix-5 §1.3 and §4.3.
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 测试缺口 / 契约缺失.
- **当前写法**: Line 600 says an access revocation either commits before the confirmation acquires the locks (a phase-A/B rejection) or after the confirmation commits — “the claim/activation already won and the revocation governs later calls”. Line 609 instead says that in the second branch (“the confirmation commits first”) the activation/trial commit, the session stays `CONFIRMED`, and `ACTIVATION_NEXT_ACTION` is a stable `REJECT` with `TASK_ACCESS_REVOKED`/`ORGANIZATION_INACTIVE`/`ACCOUNT_DISABLED`, with no dial authorization. Tests 746/768 correctly say the first branch is “the confirmation/claim commits first and the revocation governs later calls”.
- **反例/失败场景**: A PENDING task passes phase A; the confirmation holds the canonical-caller, subject-lifecycle, access and task locks across both phases; the revocation writer commits only after the confirmation commits. At that point the confirmation cannot observe the later revocation. If all phase-B predicates passed, the frozen result is `DIAL_TASK_CALLEE` with a claim and reservation. Line 609 nevertheless asserts a `REJECT` caused by a revocation that committed later, which is impossible under the stated locks. A test written verbatim from line 609 cannot be satisfied: either the revocation is visible (so the first branch, not “confirmation commits first”, applies) or the confirmation won and may dial.
- **为什么有问题**: The entire point of the accepted F-13 serialization rule is that the winning confirmation/claim is durable and later revocation affects only later calls. Line 609 swaps the two order outcomes. It is not merely stylistic: it is in the normative scenario list that section 11 refers to for implementation assertions, and it can drive an implementation to add a post-commit revocation re-read (a TOCTOU) or to synthesize a rejection after a committed authorization, conflicting with frozen decisions, immutable `ivr_decision`, and the active-call/claim contract.
- **直接证据**: Line 600 (“the claim/activation already won and the revocation governs later calls”); line 609 (“the confirmation commits first … a stable REJECT … no dial authorization is produced”); line 746 (two serial orders; status change before lock acquisition or confirmation/claim first); line 768 (same, with “the revocation governs later calls”); line 209 (category 2 only after the shared selection observes the domain condition); fix-5 §1.3 claims the two orders but does not correct this scenario, and §4.3 scanned only for old rollback wording and `action = DIRECT_AUTHORIZATION`, not this contradiction.
- **影响**: Plan-level contradiction in the accepted F-09/F-13 area; unsatisfiable or misleading concurrency tests; possible implementation that denies a call already authorized at commit or attempts a post-commit state reversal; review cannot accept the scenario as code-generation-ready until it is corrected. It does not create a security bypass or data-loss path by itself.
- **建议改法和验证点**: Rewrite line 609 to mirror line 600 and tests 746/768. If the revocation commits before the confirmation acquires the locks, phase B observes it and returns a category-2 no-dial REJECT while the valid activation/trial and `CONFIRMED` session commit (no claim/reservation). If the confirmation/claim commits first, the frozen result may be `DIAL_TASK_CALLEE` with the claim/reservation (or another action legitimately observed at commit), and the later revocation governs later calls only; it cannot retroactively change the committed decision. Add an assertion that the winning branch may dial and the losing branch is the only one that returns the access REJECT; prohibit post-commit re-reads/rejections. Re-run the exact structural script and the focused revocation tests.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.
