### S1-01-已修复-[高]-IVR 授权只读取剩余秒数，没有原子预占，允许并发呼入重复消费同一试用余额
- **入口/函数**: “IVR 未注册用户开通、试用和录音”步骤 4—6及断网恢复规则。
- **文件(行号)**: `docs/12-technology-stack-and-system-architecture.md:285`
- **输入场景**: 同一 `BusinessSubject` 在剩余 300 秒时几乎同时建立两通 IVR 会话，或第一通已取得额度但结束事件尚未回传时第二通呼入。
- **实际分支**: 两通会话都读取“当前可用录音秒数”，FreeSWITCH 各自按返回值录音；文档只在通话结束时幂等扣量，没有在授权事务中占用余额。
- **预期行为**: 后台按 `callId` 在事务内原子预占可授权秒数，同一余额不能被多个活动会话重复承诺；结束时按权威时长结算并释放未使用部分，超时/孤儿预占可恢复。
- **实际行为**: 并发会话可分别得到相同余额；即使结束事件各自幂等，也无法弥补授权总量已经超发。
- **直接证据**: 步骤 4 只创建或复用 `TrialGrant`，步骤 5 直接返回“当前可用录音秒数”，步骤 6 才扣量；一致性章节仅描述共享额度需要并发保护，没有把它绑定到 IVR 授权路径。
- **影响**: 免费试用或付费录音权益可能被并发超额使用，断网缓冲会放大不可回收的录音成本和权益不一致。
- **建议改法和验证点**: 在步骤 4—6明确创建 `UsageReservation(callId, subjectId, authorizedSeconds, expiresAt)`；使用条件更新/行锁扣减可用余额，重复 `callId` 返回首次预占；结束事件结算实际秒数并释放差额；过期扫描只释放未结算预占且处理迟到结束事件。测试并发双呼、重复开始、重复结束、断网迟到和预占超时。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### S1-02-已修复-[中]-部署图允许 Core API 直接发布 RabbitMQ，与事务 Outbox 单一发布路径矛盾
- **入口/函数**: 部署与网络拓扑中的消息发布路径。
- **文件(行号)**: `docs/12-technology-stack-and-system-architecture.md:175`
- **输入场景**: 实现订单支付、证据固证或 IVR 完成事件时，工程师按部署图让 API 在数据库提交前后直接调用 RabbitMQ。
- **实际分支**: 图中存在 `API --> RMQ`，同时正文声明事务状态与 Outbox 同事务提交、RabbitMQ 不可用时在线事务仍成功，由 Worker 恢复投递。
- **预期行为**: Core API 与 Scheduler 只写 PostgreSQL/Outbox；Java Worker 的 Outbox Relay 是唯一业务事件发布者。直接发 MQ 只能是受控非事务遥测且不得用于业务事实。
- **实际行为**: 两个相互冲突的架构契约会形成直接发布、Outbox 发布或双发布三种实现，产生丢消息或重复副作用风险。
- **直接证据**: 部署图 `API --> RMQ`；逻辑图已删除 Core 到 MQ；第 10.2 节和 RabbitMQ 降级规则要求 PostgreSQL Outbox 后续投递。
- **影响**: 支付权益、证据处理和外部通知可能出现数据库成功但消息丢失，或直接消息与 Outbox 重复发布。
- **建议改法和验证点**: 删除 `API --> RMQ`，在图中标注 `DB/Outbox --> Java Worker --> RabbitMQ`；明确 Scheduler 同样写 Outbox。结构检查应断言不存在 Core API 到 MQ 的业务发布边。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S1-03-已修复-[中]-次数耗尽提升撤销世代，打断最后一个获准的收听会话
- **入口/函数**: 9.4 录音分享准入与媒体续签。
- **文件(行号)**: `docs/12-technology-stack-and-system-architecture.md:317`
- **输入场景**: 剩余一次成功访问时，接收方完成准入并开始播放，计数因此达到上限。
- **实际分支**: 初稿将次数耗尽与撤销/过期一起提升撤销世代，使该会话后续分片续签失败。
- **预期行为**: 上限仅阻止新准入，已经原子占用最后一次名额的会话可以继续播放；撤销、过期、换码仍约束该会话。
- **实际行为**: 最后一次有效访问尚未完成就被中断，与当前原型行为不一致。
- **直接证据**: 初稿 9.4 步骤 6；`web-prototype/preview.html:2310` 的 `shareBlockedState()` 明确放行已进入播放的耗尽会话。
- **影响**: 最后一个合法接收方无法完整收听，生产契约与已确认原型产生差异。
- **建议改法和验证点**: 分开准入名额与撤销世代；准入检查/计数/会话创建原子提交，验证失败不计数；展开最后名额、重复准入、会话过期、撤销和换码场景。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
