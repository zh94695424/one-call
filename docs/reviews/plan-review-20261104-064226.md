### PA14-B-01-未修复-严重-evidence共享投影在command role下不可读，create流程必然失败
- **位置**: `## Goal and success signal`、`### Create` step 2 (`docs/gateflow/pa14-sharing-command-service-foundation-plan.md:11`、`:109`)、`## Exact application and persistence interfaces` evidence collaborator bullet (`:89`)、IT `evidenceProjectionUsesCommandTransactionConnection` (`:151`)
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施
- **当前写法**: sharing 在 command 事务内先用 `SET LOCAL ROLE sharing_command_role` + 角色断言，再由 evidence-owner `ShareableEvidenceProjectionReader.readShareableProjection(DSLContext transactionDsl, ...)` 在“同一物理连接/同一事务”上读取 shareable projection，然后再比较 replay 指纹；同时 Non-goals 禁止 migration/grant，Stop 条件只允许“发现矛盾后停下”。
- **反例/失败场景**: 任一 create 请求：角色断言通过后，reader 必须取 §2.12 规定的 `{artifactRole, mediaSha256, mediaSizeBytes, mediaMimeType, validatedDurationSeconds}`，这些列只存在于 `evidence.media_object(sha256,size_bytes,mime_type)` 与 `evidence.recording(validated_duration)`。以 `sharing_command_role` 执行即得 `42501` → 事务回滚 → 每次 create 都 500/503；`evidenceProjectionUsesCommandTransactionConnection`、`createPersistsGrant...` 全部无法通过，slice 1 立刻命中 plan 自己的 stop 条件。
- **为什么有问题**: Goal Confirmation 明确要求“Creation must use the same-connection evidence-owner `read_shareable_projection`”，而 `docs/14` §2.12/§10.23 精确定义了该投影字段集合；V010 冻结的 command role 权限集不含这两张表。plan 声称 “No unresolved ... question remains”，但该矛盾可由冻结产物直接推出，属于 plan gate 必须解决而非 implementation 发现的问题。
- **直接证据**: `backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:114-116` 仅授予 `evidence.evidence_record`（10 列）与 `evidence.evidence_artifact`（`evidence_id, media_object_id, artifact_role`）；`:178` 断言 `command_column_select<>34` 为硬失败；`backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:4728-4736`（`V009_FOREIGN_COLUMNS` 8 张表 34 列，不含 media_object/recording）、`:5092-5103`（逐列 `hasColumn(... ### PA14-B-04-未修复-高-shareId/transition eventId被误定为UUID，与冻结API和数据模型身份冲突
- **位置**: `## Exact application and persistence interfaces`（`:83` `Create/Revoke/RotateCode` 的 `shareId`（`UUID`）、`:86` `lockAndReadGrant(UUID shareId, ...)`、`findCreateReplay(UUID shareId)`、`findTransition(UUID eventId)`）
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: 领域命令、仓库方法把 `shareId` 与 transition `eventId` 建模为 `UUID`。
- **反例/失败场景**: 客户端用真实 share 调 revoke：路径参数是 `share:<64hex>`（70 字符），控制器无法解析成 `UUID` → 全部 422/404；即使按 `share_id` 文本查得 grant，`findTransition(UUID eventId)` 也无法接收 `share-transition:<64hex>`（81 字符），实现只能临时改成字符串或错误地按 `id` 查事件，导致 replay-before-state 判定失效（重复撤销被当成新动作，可能二次 bump generation）。
- **为什么有问题**: 冻结契约明确这两类身份是文本协议身份而非 UUID：OpenAPI 路径参数 `shareId` 为 `type: string, minLength 1, maxLength 128`；`docs/14` §2.12 定义 `share_id = "share:" + lowercase SHA-256(...)`（70 字符）与 transition `event_id = "share-transition:" + SHA-256(...)`（81 字符），且 §2.12 声明 S3 协议身份“never natural keys”，`id` 才是 application-generated uuid。既有查询侧已把 `shareId` 建成 `String`（`ShareCursor` 第四分量），plan 的 `ShareCreated.shareId:String` 与自身命令侧 `UUID shareId` 也互相矛盾。
- **直接证据**: `api/openapi/onecall-v1.openapi.yaml:2842-2850`、`:2972-2980`、`:3049-3057`；`docs/14-production-data-model-and-flyway-schema-spec.md:252`、`:254`；`backend/src/test/java/com/onecall/archtests/architecture/SharingQueryBoundaryTests.java:37-38`；`backend/src/main/java/com/onecall/core/sharing/internal/persistence/V009` 侧 `share_id text` 见 `backend/src/main/resources/db/migration/V009__sharing.sql`（`ck_share_grant_share_id` 长度 1-128）。
- **影响**: 生成错误代码 / 三个 mutation 端到端不可用 / 幂等语义破坏（重复动作二次 bump generation）。
- **建议改法和验证点**: 在 plan 中把三类身份拆开命名：`shareId: String (share:<64hex>, 1-128)`、`grantId: UUID`、`transitionEventId: String (share-transition:<64hex>, 81)`，并把 `lockAndReadGrant/findCreateReplay/findTransition` 形参类型与 Outbox `aggregate_id uuid`、audit `object_id uuid` 的对应关系写死；验证点：新增 IT 断言“按 `share_id` 文本解析并可锁定 grant、按 81 字符 event id 命中 replay 且零写入”。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PA14-B-05-未修复-中-关键record/属性/事件字段未定义，implementation须自造契约

- **影响**: 生成错误代码 / 持久化事实不可迁移 / 测试无法证明目标行为。
- **建议改法和验证点**: 为每个被引用类型补 “字段名+类型+nullability” 闭集（或直接引用 `docs/14` 行号作为唯一真源），把 metadata 承载体声明为 `CustomerShareCommandResult` 的嵌套 record 以保持 5 导出类型；写出命令属性键名与 env 名并列入 `application-persistence.yml`；新增 IT/Surefire 断言：artifact 按 role rank 排序、`content_sha256 == §2.5 canonical(完整快照)`、同 `creationRequestId` + 相同不可变事实的重放返回 200 而非 409、`reason` 只进入 fingerprint/audit 的指定位置。

### PA14-B-06-未修复-中-create唯一冲突“同事务reread”在PostgreSQL中不可执行
- **位置**: `## Exact application and persistence interfaces` 仓库翻译规则（`:94`）、`### Create` step 4（`:111`）、IT `createConcurrentSameIdentityProducesOneGrantAndOneOutbox`（`:151`）
- **问题类型**: 并发恢复风险 / 契约缺失
- **当前写法**: “The repository performs no implicit retry. It translates only recognized SQLSTATE/constraint outcomes: ... recognized frozen deterministic uniqueness to replay reread”，且 `insertGrant(NewGrant grant): void`。
- **反例/失败场景**: 两个同 `creationRequestId` 并发 create（或 §9.0.1 rank 9 advisory 序列化之外的路径）：输家语句报 `23505` 后事务进入 aborted 状态，同事务内任何 “replay reread” 立即变成 `25P02 current transaction is aborted`，于是本应返回 200 metadata replay 的请求变成 500/503；而 `insertGrant(...): void` 也让实现无法观测 `ON CONFLICT DO NOTHING` 的 0 行分支。plan 又明令禁止 implicit retry，实现只剩自造 savepoint 或改事务结构两条路。
- **为什么有问题**: `docs/14` §9.29.4 要求“unique share_id/token-hash losers reread and return the existing grant only for the same creator/scope/fingerprint or a stable conflict”，plan 复述了该语义却没有给出在 PostgreSQL 中可执行的机制；这是并发/幂等契约缺口。
- **直接证据**: plan `:94`、`:111`、`:145`（“No automatic retry for 40001/40P01”）；`docs/14-production-data-model-and-flyway-schema-spec.md:3401`（§9.29 step 4）；`backend/src/main/resources/db/migration/V009__sharing.sql`（`uq` on `share_id`、`capability_token_hash`）。
- **影响**: 状态不一致 / 幂等语义破坏 / 实施 Agent 自造 savepoint 或重试框架（后者属被禁止的过度设计）。
- **建议改法和验证点**: 明确写死为 `INSERT ... ON CONFLICT (share_id) DO NOTHING RETURNING id`（或 `NOT EXISTS` 预读 + 唯一冲突仅映射为稳定冲突）并由 `insertGrant` 返回“是否新建 + 已存在行摘要”，禁止跨事务重试；验证点：`createConcurrentSameIdentityProducesOneGrantAndOneOutbox` 必须断言输家返回 200 metadata、grant/Outbox/audit 行数恒为 1、且无 `25P02`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PA14-B-07-未修复-中-revoke/rotate的状态与错误映射未收敛，可能产出未声明的Problem code
- **位置**: `### Code rotation`（`:125-127`）、`### HTTP/domain mapping`（`:133`）、`## Exact application and persistence interfaces`（`:91`）
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口
- **当前写法**: 全局映射写 “stale witness to 409 `SHARE_GENERATION_STALE`; revoked terminal to 410 `SHARE_REVOKED`”，rotation 只写 “Otherwise map to the frozen validation/state/gone errors”，并只用一句 “apply only on operations that declare the code” 兜底；eligible old status 集合与终态 `EXPIRED` 处理未出现。
- **反例/失败场景**: (1) rotate 带过期 `expectedCodeGeneration`：按 plan 的全局句应映射 `SHARE_GENERATION_STALE`，但 rotate 的冻结领域码集合恰为 `{NOT_FOUND, SHARE_TRANSITION_CONFLICT}` → 生成未声明 code，违反 `docs/15` §4 “多余/缺失的精确集合成员均使校验失败”；(2) 对 `EXPIRED` grant revoke：plan 只定义 “terminal revoked → SHARE_REVOKED”，实现需在 409 `SHARE_TRANSITION_CONFLICT` 与 410 `SHARE_REVOKED`（`ShareGone` 描述含 “revoked or expired”）之间自造选择，而 18 个 IT 名里没有任何过期/终态用例；(3) revoke 的 old status 允许集（§9.29.6：`LOCKED` 与 `ACTIVE` 均可）未写明，CAS 谓词 “exact old status” 无法确定。
- **为什么有问题**: 这三处都是用户可见映射，且 plan 把 “exact HTTP/domain mapping” 当作已收敛项。
- **直接证据**: `docs/15-production-openapi-surface-spec.md:214`、`:249`（逐操作精确集合）、`:231`（`SHARE_EXPIRED` 仅 public-share）；`api/openapi/onecall-v1.openapi.yaml:3039-3047`（rotate 错误码集合无 `SHARE_GENERATION_STALE`/`SHARE_REVOKED`）、`:4229-4234`（`ShareGone` 描述含 expired）；`docs/14-production-data-model-and-flyway-schema-spec.md:3403-3404`（§9.29.5-6：rotate 仅 `LOCKED → ACTIVE`；revoke 允许 `LOCKED`/`ACTIVE`；`EXPIRED`/`REVOKED` 终态）。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 违反冻结错误码集合 / 测试固化错误语义。
- **建议改法和验证点**: 在 plan 内给出三张“操作 × 领域码 × HTTP 状态”的封闭表（含 rotate 陈旧 witness → 409 `SHARE_TRANSITION_CONFLICT`、revoke 终态 `EXPIRED`/`REVOKED` → 410 `SHARE_REVOKED` 或明确排除并把 expiry observation 声明为 out-of-scope），并补对应 IT 名；验证点：新增断言 “每个 mutation 产生的 code 集合等于该操作 `x-onecall-error-codes` 领域子集”。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
