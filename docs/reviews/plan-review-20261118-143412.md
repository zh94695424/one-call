### 1-未修复-[中]-Canonical LF-projection gates are bound to a WSL-only `/tmp` root while the only recorded working launcher is Windows `cmd.exe`

- **位置**: Plan §11.0 setup and fallback (`:530-532`, `:575-583`), §11.1–§11.3 canonical commands (`:587-640`), §13 fix5 evidence requirements; fix5 §5 (`:78-110`) and §6.
- **问题类型**: 不可直接实施 / gate executability (unavailable gate).
- **当前写法**: `export PA38_VALIDATION_ROOT="$(mktemp -d /tmp/pa38-lf-validation.XXXXXX)"` hard-codes the LF projection under the WSL `/tmp` filesystem; all canonical regression/focused/Failsafe/full/oracle commands use `(cd "$PA38_VALIDATION_ROOT/backend" && ./mvnw …)` and require exit 0. The only host contingency says: “If the unchanged wrapper cannot launch on the host, record that and use the unchanged supported host launcher (e.g. `cmd.exe /c mvnw.cmd` from the same backend directory)”.
- **反例/失败场景**: On the recorded Windows/WSL host the repository’s `backend/mvnw` is a POSIX shell script **with CRLF line terminators**; `/bin/sh` cannot exec it (`#!/bin/sh\r`). Control `:121` records exactly this blocker (“the frozen CRLF `mvnw`”) and records the only verified launcher as `cmd.exe /c mvnw.cmd -v` in the **Windows** worktree (`/mnt/c/…`). The canonical projection is deliberately a Git-less copy under WSL `/tmp`, which Windows `cmd.exe` cannot use as a working directory (UNC CWD is unsupported and falls back to `C:\Windows`), so the prescribed “`cmd.exe /c mvnw.cmd` from the same backend directory” is not a working command there. An implementation agent then has three bad choices: run canonical gates in the primary checkout (which reproduces the raw `:207` failure and defeats the whole projection design), substitute an unbound launcher, or report an unavailable gate after a full implementation cycle.
- **为什么有问题**: fix5’s closure of RR4-03 is only meaningful if the canonical commands are actually executable on the same host that produced the raw failure. The plan binds the projection root and the candidate bytes but never binds or preflights a launcher compatible with that root, and the one evidence-backed launcher is evidence-backed only on a Windows path.
- **直接证据**: `file backend/mvnw` → “POSIX shell script, ASCII text executable, with CRLF line terminators”; `head -c` shows the CRLF shebang. `docs/gateflow/project-execution-control.md:121` (CRLF `mvnw` blocker; `cmd.exe /c mvnw.cmd -v` verified in the Windows worktree) and `:122` (the single `:207` failure). Plan `:531-532` (`/tmp`), `:581` (fallback “from the same backend directory”), `:583` (“all §11.1 … must run from this same LF projection”). `cmd.exe` exists in this host interop (`/mnt/c/WINDOWS/system32/cmd.exe`), confirming the recorded host shape.
- **影响**: Gate unavailable or false-red; an entire implementation cycle may be spent before discovering that the canonical contract cannot be executed as written; worst case, a raw-checkout run is mislabeled as canonical or the frozen `:207` assertion is “fixed” by weakening a test, both of which the plan explicitly forbids.
- **建议改法和验证点**: Bind the projection to a root the selected launcher can actually execute — for example `mktemp -d "$(dirname "$PA38_CANDIDATE_ROOT")/.pa38-lf-validation.XXXXXX"` (a Windows-visible sibling outside the candidate, still excluded from the inventory) — **or** pin and preflight a verified Linux Maven command (e.g. an installed `mvn` on `PATH` or an explicitly recorded `sh`-compatible launcher) in §11.0. Add a preflight assertion that runs the chosen launcher `-v` in `$PA38_VALIDATION_ROOT/backend` before any gate, and state that if no launcher can execute in the bound projection the gate stops for Controller rather than falling back to the primary checkout. Verification point: the recorded launcher runs `-v` in the bound projection, and every §11.1–§11.3 command is recorded with that launcher and a real exit 0.
