### F-01 — Low — Cross-module membership `FOR UPDATE` denial isolation — Final status: **已修复**

Accepted defect: the `customer_iam_role` membership row-lock probe projected ungranted `id` (so `42501` could arise at column `SELECT` before the row-lock check), and `subject_number_role` had no membership `FOR UPDATE` probe.

Direct evidence (current code):

- `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:1295-1298` (`customer_iam_role`) now runs `SELECT account_id FROM organization_access.organization_membership WHERE account_id = ? FOR UPDATE`; both projection and filter use the granted `account_id`.
- `PostgresContainerIT.java:1347-1350` (`subject_number_role`) runs the same granted-column probe.
- The non-locking equivalents succeed under the real roles in the same transaction: `PostgresContainerIT.java:1284-1287` (customer) and `:1332-1335` (subject) select the same granted columns with the same `WHERE account_id` and assert one row.
- `expectSqlQueryFailure` (`PostgresContainerIT.java:1758-1779`) sets a savepoint, executes via `executeQuery`, fails the test if the statement unexpectedly succeeds, asserts exact SQLSTATE equality, and always rolls back to the savepoint in `finally`; an `AssertionError` from `fail(...)` or the SQLSTATE assertion is not caught by the `SQLException` branch, so it propagates after the savepoint rollback.
- Frozen V002 (`V002__identity_organization_and_employee.sql:312-313`) grants only `SELECT (organization_id, account_id, role, status)` on `organization_access.organization_membership` to both cross roles; V002 grants no cross `UPDATE` on that table.

Independent disposable PostgreSQL 16.15 probe (actual V001+V002 applied with `psql -1`; container removed):

| Role | Catalog | Plain `SELECT account_id ... WHERE account_id = ?` | `... FOR UPDATE` |
| --- | --- | --- | --- |
| `customer_iam_role` | table `UPDATE=false`, `account_id` `UPDATE=false`, `account_id` `SELECT=true` | succeeds | `ERROR: 42501: permission denied for table organization_membership` at `aclcheck_error, aclchk.c:2812` |
| `subject_number_role` | table `UPDATE=false`, `account_id` `UPDATE=false`, `account_id` `SELECT=true` | succeeds | same exact `42501` |

Causality probes in the same disposable container: after `GRANT UPDATE (account_id)` to `customer_iam_role`, the `FOR UPDATE` statement succeeds (table-level `has_table_privilege('...','UPDATE')` remains `false`); after `GRANT UPDATE (status)` only to `subject_number_role`, the `FOR UPDATE(account_id)` statement succeeds. The `42501` in the frozen-grant state is therefore the row-lock/UPDATE authorization, not a missing SELECT projection/filter privilege.

Regression check: the customer plain undeclared-`id` denial remains at `PostgresContainerIT.java:1292-1294`, the subject plain undeclared-`id` denial remains at `:1344-1346`, and no S1/S2 assertion was changed. Focused method 1/1 and full suite 18/18 green.
