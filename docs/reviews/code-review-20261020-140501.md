## Findings

### CR-006-部分修复-[严重程度（中）]-事件结果可定位一个对象，但同一幂等身份仍可对应多个业务副作用对象

- **入口/函数**: `loadReviewSnapshot` → `validateState` / `validProcessedEvents` / `validEventRecord`; 导入后 `createOrder` 重放，以及两个订单分别进入 `applyPaymentResult` / `issueEntitlements`。
- **文件(行号)**: `shared/onecall-business.js:446`, `shared/onecall-business.js:484`, `shared/onecall-business.js:516`, `shared/onecall-business.js:659`, `shared/onecall-business.js:689`.
- **输入场景**: 从公开 `createOrder` 生成的合法状态出发，复制该订单为不同 `id`，但保留相同 `idempotencyKey='ONE-CHECKOUT'`、主体、账户、渠道和冻结快照；原 ORDER 事件记录保持不变并仍指向第一笔订单。通过 `snapshot` / `loadReviewSnapshot` 传递后，用原请求重放，再分别支付并发放两个订单。
- **实际分支**: `validateState` 只按 `orders[].id` 检查唯一性，没有检查 `idempotencyKey`。ORDER 域的 `validEventRecord` 通过 `frozenOrder` 按结果 `id` 找到第一笔订单，并验证该订单的 key 等于事件 ID；它没有证明这是状态中唯一拥有该订单幂等键的订单。因此事件结果本身合法时，第二个同 key 的订单不影响导入或重放。
- **预期行为**: 同一 ORDER 域幂等身份必须只对应一次订单创建副作用。导入与重放的共享 owner 不仅应找到结果对象，还应证明事件身份到业务结果的映射唯一；重复请求应返回原订单，不能让快照携带第二笔同 key 订单。跨动作域复用相同字符串仍应继续允许。
- **实际行为**: 定向只读探针得到 `snapshot=OK, load=OK, replay=DUPLICATE`，导入状态同时含 `ORDER-001001` 和 `ORDER-DUPLICATE`，二者 `idempotencyKey` 均为 `ONE-CHECKOUT`。进一步对两笔订单分别执行支付和发放，四个转换都返回 `OK`，最终为 `orders=2, entitlements=2, snapshot=OK`。相同缺口也可由两个不同 activation ID 共享同一动作域 `eventId` 复现，快照导入与原键重放均通过。
- **直接证据**: 446 行的集合唯一性只调用 `unique(candidate.orders)`；484–492 行验证订单引用和状态但不检查 `idempotencyKey`；659–661 行只将事件结果那一笔订单的 key 与 `record.eventId` 对齐；689–692 行的 `frozenOrder` 只按 `value.id` 查一个当前对象。批准计划 `docs/gateflow/cross-channel-alignment-plan.md:53` 明确 `DUPLICATE` 不创建第二个订单，55 行定义 `processedEvents` 是带 result identity 的幂等键映射，67 行把 `idempotencyKey` 定义为订单字段。Round-2 fix 又明确声称事件引用必须解析为“one compatible current object”，当前校验尚未覆盖事件身份的反向唯一性。
- **影响**: 一个跨端评审快照可把一次结账表示成两笔独立可支付、可发权益的订单，而所有共享校验仍显示有效。后续 S2/S3 无法把共享状态的 `DUPLICATE` 成功回包解释为“只存在原订单”，并可能展示或操作重复订单及重复权益。这是 S1 本地确定性契约问题，不依赖生产并发或外部攻击假设。
- **建议改法和验证点**: 至少在状态校验中要求 `orders[].idempotencyKey` 在 ORDER 域唯一，并让 ORDER 事件记录按该 key 解析到且仅解析到自己的结果订单。对其他带创建事件身份的对象按域检查相同的一对一关系，同时保留“相同字符串跨域可复用”，不要做全局 eventId 唯一。新增“两个订单同 key 不同 ID”和“同一动作域两个 activation 同 eventId”原子导入拒绝测试；断言修复后无法分别支付/发放。回归支付域多个不同事件合法推进同一订单、UNKNOWN→PAID、历史订单下架后履约，以及七域正常导入/重放，避免把事件对象关系误收紧为所有域都一对一。
- **修复风险（低/中/高）**: 中；需要按动作域定义唯一关系，不能破坏跨域同字符串复用，也不能阻止支付状态机对同一订单使用多个不同回调事件。
- **严重程度（低/中/高/严重）**: 中。
