### F-S2-R1-01

| 字段 | 值 |
| --- | --- |
| **ID** | `F-S2-R1-01` |
| **最终状态** | `未修复` |
| **严重度** | **High** |
| **Title** | IVR-outbox recovery 的“新鲜 timestamp/nonce + 同一 domain identity”仅由不等式判定，缺省/空值被当作新鲜，identity guard 在任一侧缺省时被跳过 |
| **Entry / function** | `security/validate.mjs` → `runStep()` → `case 'ivr-outbox'`（recovery 分支与 identity/payload guard） |
| **File and line** | `security/validate.mjs:1427`（identity guard）、`security/validate.mjs:1444-1445`（401/403 基线用 `??` 捕获）、`security/validate.mjs:1462-1466`（freshness 纯不等式）、`security/validate.mjs:1467-1480`（成功恢复不更新 `previousNonce`/`previousTimestamp`）；契约文本 `docs/17-production-security-design-spec.md:377`；fixture `security/v1/fixtures/sec-s2-09-ivr-outbox-auth-blocked.json`（无 omitted/null/empty 负例） |
| **Triggering input** | 对已 `securityBlocked` 的 outbox entry 发起 recovery step：`recoverySignal: "CREDENTIAL_ROTATED"`（或其余三个合法 signal），且 `transportNonce`/`transportTimestamp` 之一或全部**省略**（`undefined`）、置 `null`、或置空字符串 `""`；或 `domainIdentity` 省略 / 为 `null` / 含空字段；或后续 re-block 后再次以省略 transport 的 recovery 步骤重试 |
| **Actual branch** | 1) `freshTransport = step.transportNonce !== entry.previousNonce && step.transportTimestamp !== entry.previousTimestamp`（L1462-1463）。JS 语义下：`undefined !== null` → `true`；`null !== "1700000000"` → `true`；`"" !== "TEST_ONLY_…"` → `true`；`undefined !== "TEST_ONLY_…"` → `true`。两操作数只要不严格相等即判“新鲜”。2) identity guard 条件为 `step.mutateEventId === true \|\| (step.domainIdentity && entry.identity && !deepEqual(...))`（L1427）——任一侧为 falsy（省略、`null`、`""`）时整个子条件为假，**guard 被完全跳过**，不返回 `IDENTITY_MUTATION_FORBIDDEN`。3) 成功恢复（L1467-1480）只写 `entry.securityBlocked = false`，**不更新** `entry.previousNonce`/`entry.previousTimestamp`；且 401/403 捕获用 `??`（L1444-1445），省略字段保留旧基线。 |
| **Expected behavior** | `docs/17-production-security-design-spec.md:377`：「只有在收到显式 credential/key/certificate 或 service-authorization recovery signal 后才允许重试；重试使用同一 domain identity（`callId`/`eventId`/`recordingId`/`decisionId`）与 immutable payload，并**生成新的 timestamp/nonce**。」controller `project-execution-control.md` L195 要求独立验证「recovery truly requires the **same non-empty** domain identity and **fresh non-empty** timestamp/nonce rather than accepting omitted values by inequality alone」。实现报告 §4.8 亦声明「same domain identity and immutable payload plus a **fresh timestamp and nonce**」。即：identity 必须存在、非空、与 entry 相同；transport 必须存在、非空、格式合法、且不同于上一次使用值；三者缺一应拒绝。 |
| **Actual behavior** | 省略/null/空的 `transportNonce`/`transportTimestamp` 因不等式恒真而通过 `STALE_TRANSPORT` 检查，被判 `freshTransport: true` 并返回 `OK / RETRY_AFTER_RECOVERY / retried: true`；省略/null/空的 `domainIdentity`（或 entry 侧 identity 缺失）使 L1427 guard 短路，不拒绝身份核验；成功恢复不滚动 `previous*` 基线，配合 L1444-1445 的 `??` 语义，re-block 步骤若省略 transport 字段则基线不前移，**曾使用过的同一 nonce/timestamp 可在后续 recovery 中再次被判“新鲜”**。 |
| **Direct evidence** | 1) 代码：L1427、L1444-1445、L1462-1466、L1467-1480（见上引用）。2) 语义探针（jq 复刻同一 JS 关系，8 场景，临时文件已删除）：P1 省略 step transport vs 已存 nonce/timestamp → `fresh: true`；P2 `null` transport → `fresh: true`；P3 空字符串 transport → `fresh: true`；P4 transport 与 entry 全等（唯一真“stale”情形）→ `fresh: false`；P5 省略 step `domainIdentity` → identity guard 不触发；P6 entry `identity: null` → guard 不触发；P7 双方 identity 含空字段 → guard 不触发；P8 双方 identity 均存在且不等 → guard 触发（`IDENTITY_MUTATION_FORBIDDEN`）。**结论：不等式单独判定确实把缺省值当作新鲜；identity 核验在任一侧缺省时完全失效。**3) fixture 覆盖：`sec-s2-09` 仅在 `recovery-retry` 提供完整非空 transport+identity，在 `stale-transport-denied` 提供**与已存值全等**的 transport；**没有** omitted / null / empty / malformed 的 identity 或 transport 负例步骤。实现报告 §6 声称的 probe「stale transport made fresh」只覆盖全等情形，未覆盖缺省情形。 |
| **Impact** | 该 evaluator 是 S2 冻结契约的唯一可执行断言面。缺省值通过意味着：(a) 「fresh non-empty timestamp/nonce + same non-empty domain identity」这一被 controller 点名验证的契约未被机器强制，文档 §14 的“生成新的 timestamp/nonce”与“同一 domain identity”在缺省输入下落空；(b) 后续 S3/集成若以本 evaluator 结果为证据，会继承错误的“已验证 recovery 新鲜性”结论；(c) `previous*` 不滚动 + `??` 基线保留，使“同一 nonce 不得复用”的跨 recovery 周期保证也不存在。当前 15 个 fixture 全部通过不能反驳本缺陷——正例步骤总是提供完整非空字段，负例只测全等 stale，缺省路径无任何断言。 |
| **Concrete fix / verification** | 修复（evaluator 侧，不改契约文本）：1) recovery 分支要求 `typeof step.transportNonce === 'string' && step.transportNonce.length > 0` 且 `typeof step.transportTimestamp === 'string' && step.transportTimestamp.length > 0`（并沿用与 IVR 头一致的格式校验），缺失/空/错误类型直接 `STALE_TRANSPORT` 或新增 `TRANSPORT_MISSING` 403；2) 在已有不等式基础上叠加“非空”前置条件，禁止以 `undefined`/`null`/`""` 通过；3) identity：当 `entry.identity` 存在时要求 `step.domainIdentity` 存在且 `deepEqual`，任一侧缺失即 `IDENTITY_MUTATION_FORBIDDEN`（或 `IDENTITY_MISSING` 403）；4) 成功恢复时同步 `entry.previousNonce = step.transportNonce; entry.previousTimestamp = step.transportTimestamp`，并让 401/403 捕获仅在字段实际存在时写入（或与修复 1 合并为“非空才记录”）；5) 在 `sec-s2-09`（或新增 S2 负例步骤，仍属既有 fixture 内容演进，需 controller 授权）加入 omitted-transport、null-transport、empty-transport、omitted-identity、empty-identity 五个负例步骤，期望全部 403 DENIED。验证：`node security/validate.mjs --stage s2 …` 仍 15/15 通过；对临时副本注入上述五类缺省输入的 mutation 探针全部被拒；S1 stage 与历史 checkpoint 回归不变。 |
| **Fix risk** | Low–Medium。仅改 evaluator 判定与（若授权）fixture 负例步骤；现有正例步骤均提供完整非空字段，不应被新前置条件打破。风险点：若 controller 不允许改 fixture，则只能修 evaluator 并以临时探针留证，需在 fix 报告中明确。不触及 A0/A1/A2 契约、模型注册表或文档正文。 |
| **Severity rationale** | 绑定契约（文档 §14 L377 + controller L195）被点名要求“非空 + 同一 identity + 新鲜 transport”，而机器断言面对缺省输入失效，且无负例覆盖；这是可复现、同路径、同状态的契约执行缺口，非推测性偏好。 |

### F-S2-R1-02

| 字段 | 值 |
| --- | --- |
| **ID** | `F-S2-R1-02` |
| **最终状态** | `未修复` |
| **严重度** | **Medium** |
| **Title** | `signatureMode: 'invalid'` 的末字符替换在签名已以 `A` 结尾时是恒等变换，负例构造存在确定性无效化缺口 |
| **Entry / function** | `security/validate.mjs` → `runStep()` → `case 'ivr-request'`（header 构造段） |
| **File and line** | `security/validate.mjs:1203-1207`（关键行 `security/validate.mjs:1206`） |
| **Triggering input** | `action: "ivr-request"` 且 `signatureMode: "invalid"`，材料/`keyRef` 派生出的合法签名 `v1.<keyId>.<base64url…>` 的**最后一个字符恰为 `A`**（base64url 字符集 `A-Za-z0-9_-` 中 `A` 为合法末字符，出现概率约 1/64） |
| **Actual branch** | `headers['X-ONECALL-SIGNATURE'] = \`${headers['X-ONECALL-SIGNATURE'].slice(0, -1)}A\``。当原值 `s.endsWith('A')` 时，`s.slice(0,-1) + 'A' === s`，字符串恒等 → header 未被破坏 → 后续 `signatureFormatValid` 与常量时间比较按**有效签名**继续 → 步骤不因“坏签名”被拒（除非其他分支先拒）。 |
| **Expected behavior** | `signatureMode: 'invalid'` 应保证构造出的签名与任何合法 `K17` 派生签名都不相等，使 `sec-s2-04` 类负例稳定落在“签名校验失败 → 401 UNAUTHENTICATED”分支；实现报告 §4.4/§6 将 “bad signature / missing/bad signature made valid” 列为已覆盖的负例路径。 |
| **Actual behavior** | 负例构造依赖“改最后一个字符”，但目标字符集含 `A`，约 1/64 概率原样返回；此时 `signatureMode: 'invalid'` 无效化失败。对当前 `sec-s2-04`：报告称 fixture 通过（15/15），反推当前派生签名末字符不是 `A`，故**当前**负例恰好有效；但该机制对材料/时间戳/nonce 任何变化导致的末字符漂移不鲁棒，属确定性负例构造缺口。 |
| **Direct evidence** | 代码 L1203-1207（上引）。字符串恒等式：对任意以 `A` 结尾的 `s`，`${s.slice(0,-1)}A === s` 为真（纯 JS 语义，无需运行时）。当前 `sec-s2-04-ivr-signature-invalid.json` 依赖该模式（步骤含 `signatureMode: "invalid"` 类输入路径，fixture 完整读取确认为负例 `negative: true`，期望 `UNAUTHENTICATED`）。会话权限门禁止 `node`/`openssl` 执行，**未能实算**当前派生签名是否以 `A` 结尾——见 Open Questions。 |
| **Impact** | 负例路径的构造正确性不确定：若末字符为 `A`，坏签名负例会静默变成“有效签名路径”，期望 `DENIED/UNAUTHENTICATED` 与实际 `OK` 不匹配 → fixture 失败（响亮失败而非静默通过，故不构成假阳性放行），但会使 `--stage s2` 在材料扰动下不可复现，并削弱报告 §6「missing/bad signature」探针类别的可信度。属于任务第 7 项“deterministic validation gaps”。 |
| **Concrete fix / verification** | 将无效化改为保证不同的变换，例如翻转首字符（`'X' === s[0] ? 'Y' : 'X' + s.slice(1)`）或对固定位置做字符集内替换（`s[0] === 'v' ? 'w' : 'v' + s.slice(1)`），使结果恒不等于原签名；或直接对签名体做单字节非 base64url 字符注入后仍保持格式可解析。验证：临时副本上对同一 `signatureMode: "invalid"` 步骤，穷举/抽样多个 keyRef+timestamp+nonce 组合，断言破坏后签名 ≠ 原签名且步骤稳定 401；`--stage s2` 15/15 通过；S1 回归不变。 |
| **Fix risk** | Low。单行构造改动，仅影响 `signatureMode === 'invalid'` 路径；`missing` 与 `headersOverride` 路径不动。需回归 `sec-s2-04` 及任何使用该模式的探针。 |
| **Severity rationale** | 可在同一 entry/分支上证明的确定性缺口，影响负例构造的稳定性与报告证据强度；当前 fixture 未触发假通过，故低于 F-S2-R1-01，不列为 High。 |

## 2. Open Questions

1. **当前 `sec-s2-04` 派生签名是否以 `A` 结尾**：需执行 `node security/validate.mjs --stage s2 …` 或等价 HMAC 计算确认。本会话权限门拒绝一切 `node`/`openssl`/`python3` 执行（见 §4），未能实算。若以 `A` 结尾，则当前负例即已失效、fixture 应已失败——与报告 15/15 通过相矛盾，故推断不以 `A` 结尾，但属推断非实证。
2. **报告中的运行期 stdout 哈希**（S1 `3E991F1D…`、S2 `5BA15F81…`）与 A1 `check:s3`、A2 stage-S3 输出**未能独立复跑**（权限门）。本评审以静态逐行审读 + 哈希核对 + jq 语义探针替代；controller 若具备执行权限，应重跑 §4 命令表补全。
3. **修复 F-S2-R1-01 是否允许改动 `sec-s2-09` fixture**：任务规定评审期不得改 fixture；fix 阶段新增负例步骤需 controller 在 fix 授权中明确（或以临时探针留证、fixture 不动）。
4. **`entry.identity` 的写入时机**：`observe-401` 步骤提供 `domainIdentity` 后 entry 才有 identity；若首个 401 步骤本身省略 `domainIdentity`，则后续所有 recovery 的 identity guard 恒短路。当前 fixture 首步总是提供，故未在正例中暴露——是否需要“block 时必须已捕获 identity”前置，属契约解释问题，归入本 finding 修复时一并裁决。
