### PA36-PR-02 — 未修复 — 高 — The exact-three-role login is not demonstrated to coexist with the existing one-username Operations-read pool used by PA33/PA34

- **位置:** §4.1 identity decision (plan lines 147–163), §4.2 context and limits (plan lines 171–175), runbook wiring instruction (plan line 190), and the residual table's "three-edge LO" row (plan line 373).
- **问题类型:** Architecture boundary / overcoupling / false assumption / insufficient implementation sequencing.
- **当前写法:** The plan creates one dedicated login `LO` with exactly three `SET` edges—`operations_iam_role`, `ivr_role`, and `evidence_role`—and says it uses the existing shared Operations-read datasource properties with no new pool. It later says LO may be configured for the PA35 capability, while a wider identity decision returns to Controller if deployment wants one login to serve additional owner collaborators.
- **反例/失败场景:** The existing Operations persistence configuration constructs one Hikari pool from one datasource username/password (`backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/OperationsSubjectReadPersistenceConfiguration.java:67–82`) and one `OperationsReadContext` switches to the existing enum roles (`backend/src/main/java/com/onecall/core/operations_iam/subjectread/OperationsReadContext.java:13–15`, `:28–42`, `:46–57`). PA34 activation reads share that same context (`backend/src/main/java/com/onecall/core/operations_iam/internal/activationread/OperationsActivationReadConfiguration.java:19–29`), and the existing subject-read readers require `SUBJECT`, `ACTIVATION`, `TRIAL`, `EVIDENCE`, and `ORDER` in addition to `operations_iam_role` (`backend/src/main/java/com/onecall/core/subject_number/internal/operationsread/JooqOperationsSubjectReader.java:54,74`; analogous readers). If the single shared datasource is configured with LO, the first existing PA33 subject or PA34 activation request reaches `SET LOCAL ROLE subject_number_role`/`activation_consent_role` and fails because LO has only operations/ivr/evidence. If the datasource keeps an older union-role login, LO is not actually used for PA35 and the claimed three-role production boundary is not exercised.
- **为什么有问题:** A Hikari pool has one username for all connections; there is no per-request credential selection in the plan, and a new pool/datasource is explicitly non-goal. The plan's phrase "existing shared Operations-read datasource" therefore does not by itself identify a deployable topology. A test-only direct SQL probe of LO can pass while the existing Spring pool remains incompatible. The residual row acknowledges the danger but does not resolve the sequencing or make the PA36 success signal evaluable.
- **直接证据:** One shared `operationsSubjectReadDataSource` bean with a single username/password and one shared `OperationsReadContext`; existing subject/activation consumers use the same beans and require roles LO does not have. The plan itself says "No backward-compatible three-input success path" for PA25 but does not provide a versioned datasource transition; line 175 defers the wider identity decision instead of defining the coexistence path.
- **影响:** Enabling PA35 with LO can regress the already-existing PA33 subject-read and PA34 activation-read endpoints to sanitized 503/42501 failures, or force an unauthorized new pool/wider login. The plan may appear green in focused fixed-SQL tests while failing the shared Operations application boundary.
- **建议改法和验证点:** Choose one explicit option and encode it in the plan before implementation: (a) return to goal confirmation for a separate PA35 datasource/pool or a union-role shared credential; (b) keep LO only as a provisioning primitive and explicitly scope PA36 to identity-only, with PA35 deployment blocked until the Controller approves the coexistence decision; or (c) define a safe per-consumer credential/pool boundary. Add a test that starts the real shared Operations Spring context, configures the exact three-role LO, proves the intended PA35 role switches work, and proves existing PA33/PA34 endpoints either remain functional under the selected transition or are explicitly disabled. Update docs17/runbook and the success signal accordingly.
- **修复风险（低/中/高）:** Medium.
- **严重程度（低/中/高/严重）:** High.

## Open questions

1. **PA25 operational compatibility:** The plan intentionally removes the three-variable success path and requires `operations_login`. Existing runbook commands and any external automation using only `sharing_login`, `customer_login`, and `command_login` will fail closed at `PA25_INPUT_REJECTED`. Is that interface break explicitly owned by Controller/Platform, and will every caller be migrated in the same change window? The plan's fail-closed behavior is safer than silently accepting an incomplete topology, but it is still an operational compatibility change.
2. **Shared Operations coexistence:** Does PA35 intend to run with PA33/PA34 in the same application instance and with the same `onecall.operations-subject-read.datasource.*` properties? If yes, a three-role LO cannot be the sole username without a role-union or separate pool decision. This is the unresolved basis of Finding 2.
3. **Runtime proof:** The plan's replay matrix, PostgreSQL role-membership semantics, `SET LOCAL ROLE` restoration, and exact ACL tuples are statically coherent but were not executed in this review. The implementation evidence must include real PostgreSQL 16 positive/negative runs and must not substitute source inspection for those proofs.
4. **Historical-test treatment:** The omitted five tests should be corrected as current-inventory consumers of V018/docs17, not rewritten as if V017 were still the latest state. The implementation should preserve independent V001–V017 prefix assertions and add separate V018 coverage.

## Final conclusion

**Verdict:** `fail`

The ACL arithmetic, migration-history baseline, tuple topology, and test/CI/POM counts are largely well-grounded. The plan is not ready for implementation because its own exact path ownership is incomplete and its dedicated three-role login does not yet define a valid coexistence path for the existing shared Operations datasource. Both issues can produce concrete failures in the promised full green run or in live PA33/PA34 behavior, so they are not merely documentation nits.
