### 02-未修复-[低]-§10 对 F8/G1 要求磁盘字节严格等于 RAW 列，比它所继承的两个 frozen-input 测试更严，只在 CRLF checkout 下可满足，而两种自然修法都被计划自身禁止

- **位置**: §10 `:892-903`（"Resolve each path against `..`, hash exact on-disk bytes and require RAW
  equality; separately hash CRLF→LF-only bytes and require LF equality. Never accept the LF digest as a
  substitute for raw equality in this checkout or rewrite any frozen file."）；对照 §10 `:862-866`、
  §11 `:1007-1011`；继承基线 `OperationsActivationReadBoundaryTests.java:98`、
  `OperationsLifecycleBoundaryTests.java:82`。
- **问题类型**: 测试缺口 / 契约缺失（验证环境前置条件未声明）/ 其它（可移植性绑定）
- **当前写法**: F8 与 G1 都必须对 21 个冻结路径做**两次**严格相等：磁盘原始字节摘要 == RAW 列，
  且 CRLF→LF 后摘要 == LF 列；并明令 "Never accept the LF digest as a substitute for raw equality in
  this checkout or rewrite any frozen file"。
- **反例/失败场景**: 表中 21 行的 RAW 与 LF 摘要**两两互异**，因此两条等式只有在磁盘字节本身是 CRLF
  时才可能同时成立。本快照恰好满足（我实测 21 个文件全部每行以 `\r\n` 结束，42/42 摘要全中）。但在
  Linux 上以 `core.autocrlf=false`/`input` 新鲜 clone、或任何把 blob 规范化为 LF 的检出中，磁盘字节为
  LF，于是 raw 摘要 == LF 列 ≠ RAW 列，F8/G1 立即失败——**且失败与 PA35 的任何实现内容无关**。仓库没有
  `.gitattributes`（我已确认不存在），因此检出行尾完全由客户端配置与平台决定，不由仓库钉住。CI 的两个
  `runs-on` 都是 `ubuntu-latest`（`ci.yml:35`、`:2487`），这正是最可能产生 LF 检出的环境。
  而计划的两种自然修法都被自身封死：接受 `isIn(raw, lf)` 被 `:900-901` 明文禁止；把冻结文件改写成
  CRLF 被同一句 "or rewrite any frozen file" 与 §1 `:59` "V001–V017 remain byte-identical" 禁止。
- **为什么有问题**: 这不是继承来的约定，而是**比继承约定更严**。两个已有的 frozen-input 测试对同一批
  迁移文件都用 `.isIn((Object[]) …)` 接受 raw 或 lf 任一摘要

  两者都断言 `hasSize(21)` 与恰好 17 个迁移文件名）——即仓库既有约定本来就是表示法无关的。§10 在
  REREVIEW2-02 关闭时选择了继承"plan 文件解析机制"，却同时把**磁盘字节的判定**收紧到严格 RAW，
  于是同一次 F8/G1 运行里，plan 侧解析允许两种表示（其 hash 与 RAW 成员比对），磁盘侧却只允许一种。

  LF-equivalent projection for existing checker conventions, with source raw bytes unchanged; record that
  limitation" —— 说明作者知道行尾依环境而变，却没有把同样的处理带给 §10 的磁盘断言。更强的证据是本轮
