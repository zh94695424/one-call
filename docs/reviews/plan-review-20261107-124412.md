## 4. Focus-area verification

### 4.1 Step 8 generic conflict vs historical `FAILURE` retry

Plan step 8 (`:94`) now states the generic rule and the exception in the same paragraph:

- generic: a prior success **or failure** row with a different `purpose`/`eventType`, or same `purpose`/`eventType` with a different `preProviderFingerprint`, is a stable 409 `SHARE_GENERATION_STALE` with no provider call and no event;
- exception: "A historical `FAILURE` with the same purpose and fingerprint is not a request-key poison: it permits a fresh retry";
- replay: "A same-purpose success is a replay candidate and its durable credential/expiry is authoritative."

The exception is placed after the generic rule, is stated in imperative prose, and covers exactly the case where the historical row is `eventType=FAILURE` while the retry's identity uses the purpose-specific success event type. The failure payload (`:171-188`) carries the same `purpose`, `requestKeyDigest`, `preProviderFingerprint`; `§4.2` (`:110-129`) restricts the fingerprint's `eventType` to the three success event types, so a correct implementation computes the failure's fingerprint over the purpose-specific event type and the retry matches. Step 10 (`:96`) adds fresh-retry success, success-authoritative replay and identical-failure reuse. **The ambiguity reported in round 1 is resolved.** Residual wording precision is OQ-3.

### 4.2 Lazy resolver without controller-side mode knowledge

`plan:63-81` pins the service contract and the resolver; `plan:87-93` pins the order: (2) non-locking token/mode read, (3) invoke `callerResolver.resolve()` exactly once only for `ORGANIZATION_MEMBER`, before ranks 7/8/9 and before any authoritative sharing read/lock; non-member modes never invoke it. The controller only constructs a lazy resolver: absent bearer → `Optional.empty()` without context I/O; valid present bearer → principal-backed resolver performing at most one context lookup; invalid bearer remains a filter-boundary failure; the controller must not eagerly call context services. Tests assert invalid token + unavailable context → 404 with zero context lookup, non-member + absent bearer → zero context calls, member + absent caller → 401, member context unavailable → 503. This is consistent with the current controller's separation of optional bearer from member resolution (`PublicSharesController:58-84`) and with the module boundary (`SharingQueryBoundaryTests:80`). **Fixed.** One wording residual: `plan:79` says the controller constructs the resolver "after the non-locking mode discovery input is available", although the controller cannot know grant mode; the operational clauses and step 3 make the intended lazy design unambiguous. Recorded as OQ-2.

### 4.3 Concurrent first-request convergence

The offending round-1 design was `credentialExpiresAt = databaseNow + TTL` per caller, causing divergent post-provider payloads and a PA17-style `CONFLICT → 503`. Fixed design:

- `eventId` is the provider idempotency key; `preProviderFingerprint` is a consistency input; the expiry bound is `min(witness.sessionExpiresAt, witness.admissionExpiresAt, witness.grantExpiresAt)` — deterministic from the immutable PA17 witness (`plan:95,131-143`);
- concurrent first calls must receive the same provider credential and expiry (`plan:96`); the provider may be called twice but must be semantically idempotent;
- `insertAccessEvent` remains the sole conflict authority (`JooqShareAdmissionRepository:110-117`); identical payload → `REUSED_IDENTICAL` and both callers return the first durable expiry; same-event-ID different payload/provider mismatch → 503 with no success claim (`plan:96`);
- the named two-connection test proves both callers return the same credential/expiry, exactly one event, exactly one semantic credential, first durable expiry returned, and no transaction spans provider I/O (`plan:274-275`).

Both-callers-200 follows from identical payload reuse; the plan states the success response field set at `plan:297`. **Fixed.** Provider determinism remains a residual seam risk (§6).

### 4.4 Success replay during outage and repeated transient failures

`plan:96` and `:141-143` state: once a success exists, replay returns its first credential/expiry; provider outage during that replay returns `DEPENDENCY_UNAVAILABLE` without appending another `FAILURE`; a historical same-purpose same-fingerprint `FAILURE` may be retried; a retry may append the purpose-specific success; identical repeated failures are reused rather than duplicated. The failure payload/identity (`:169-192`) is deterministic and redacted; `result=FAILED` and both `FAILURE`/`FAILED` are legal V009 values (`V009:117-120`). The service and IT retry tests are named at `plan:240,251` and `:271,275`. **Fixed.**
