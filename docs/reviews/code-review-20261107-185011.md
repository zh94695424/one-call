### B-R-01 — Unreachable `SHARE_LOCKED` branch after witness already required

- **Entry/function:** `DefaultShareMediaAuthorizationService.authoritative`
- **File/line:** `backend/src/main/java/com/onecall/core/sharing/internal/admission/DefaultShareMediaAuthorizationService.java:155`

- **Actual branch:** `if ("LOCKED".equals(grant.status()) && repository.findAdmissionWitness(grant.id(), admissionId).isEmpty()) throw failure(SHARE_LOCKED);`
- **Expected/actual:** Plan §3 step 6 and OpenAPI state `SHARE_LOCKED` is intentionally absent for this operation and `LOCKED` is eligible only when already witnessed. Line 115 already does `findAdmissionWitness(...).orElseThrow(FORBIDDEN)`, so the second lookup at line 155 is always non-empty in the same transaction (V009 events are immutable). The branch is dead. If it were reachable it would return `SHARE_LOCKED` (409), which is **not** in this operation’s `x-onecall-error-codes`.
- **Direct evidence:** lines 114–115 (witness required → `FORBIDDEN` when missing) vs line 155; OpenAPI `api/openapi/onecall-v1.openapi.yaml:3816` (`SHARE_LOCKED` intentionally absent) and `:3842–:3857` (no `SHARE_LOCKED` in error list); IT `alreadyAdmittedLockedSessionAuthorizesAndShareLockedIsNotReturned` proves witnessed `LOCKED` authorizes and new admission after lock still gets PA17 `SHARE_LOCKED` (different operation).
- **Impact:** No reachable behavior change; dead defensive code that could confuse future edits into returning an unlisted status code.
- **Fix direction:** Delete line 155 (or assert impossibility), keeping witnessed-`LOCKED` eligibility solely via the earlier witness + `ACTIVE`/`LOCKED` status check.
- **Fix risk:** Low — removing an unreachable branch; no test asserts `SHARE_LOCKED` on the media path.
- **Severity:** Low

### B-R-02 — Terminal-status ordering depends on time-expiry and V009 trigger, not an explicit `EXPIRED` status check

- **Entry/function:** `DefaultShareMediaAuthorizationService.authoritative`
- **File/line:** `DefaultShareMediaAuthorizationService.java:112–113` vs `:135–136`; V009 trigger `V009__sharing.sql:226–236`
- **Trigger:** Grant `status='EXPIRED'`
- **Actual branch:** Only `REVOKED` is checked by status (line 112); `EXPIRED` is caught by `expires_at` time (line 113). Line 136 maps any remaining non-`ACTIVE`/non-`LOCKED` status to `SHARE_GENERATION_STALE` (409).
- **Expected/actual:** Accepted F-07 requires terminal `REVOKED`/`EXPIRED` status/time checks before generation so PA18 matches PA17/OpenAPI 410 mappings. PA17 explicitly checks `status.equals("EXPIRED")` before generation (`DefaultShareAdmissionService.java:141–143`). PA18 does not. This is safe in the frozen schema because V009 raises `SHARE_GRANT_EXPIRY_INVALID` when setting `EXPIRED` while `clock_timestamp() < expires_at`, and `EXPIRED` also forces `revocation_generation+1`. Therefore every durable `EXPIRED` row has past `expires_at` and line 113 fires first. IT `revokedExpiredGenerationStaleAndSessionExpiredMapExactly` scenarios `expired`/`time-expired` sleep past the 2s window before mutate and assert `SHARE_EXPIRED` 410.
- **Direct evidence:** service lines 112–113, 135–136; `V009__sharing.sql:234–236`; IT lines 682–688; OpenAPI 410 list includes `SHARE_EXPIRED`.
- **Impact:** No production-path defect under V009 constraints; residual coupling of precedence to schema trigger + time check rather than an explicit status predicate (PA17 parity gap).
- **Fix direction:** Optionally add `if ("EXPIRED".equals(grant.status())) throw failure(SHARE_EXPIRED);` immediately after the `REVOKED` check for PA17 predicate parity and defense-in-depth.
- **Fix risk:** Low — one-line addition; must not reorder past `REVOKED` or before malformed-grant handling.
- **Severity:** Low

### B-R-03 — Failure-append DB error can mask the intended durable `FAILURE` fact

- **Entry/function:** `DefaultShareMediaAuthorizationService.authorize` provider-outage path
- **File/line:** `DefaultShareMediaAuthorizationService.java:73–75`, `:81–82`, `:174–184`
- **Trigger:** Provider throws/`Unavailable`/`Malformed` **and** the subsequent `appendFailure` `writes.execute` itself throws a non-`ShareAdmissionException`
- **Actual branch:** Inner catch calls `appendFailure(...)` then `throw failure(DEPENDENCY_UNAVAILABLE)`. If `appendFailure` throws `RuntimeException`, control leaves via the outer `catch (RuntimeException)` → still `DEPENDENCY_UNAVAILABLE`, but no `FAILURE` row was written.
- **Expected/actual:** Plan §3 step 10 requires appending exactly one deterministic redacted `FAILURE` when a durable valid decision reached provider I/O. A simultaneous database failure makes that append impossible; the client still correctly receives 503 with no success claim, but the durable failure fact is absent (subsequent retry is a fresh first attempt, which is permitted).
- **Direct evidence:** lines 73–75, 98–99, 174–184; plan §3 step 10; no test forces DB-down during `appendFailure`.
- **Impact:** Fail-closed for the HTTP surface; event history may omit `FAILURE` only when the database is already unavailable. Not a success-claim bug.
- **Fix direction:** Accept as fail-closed residual, or catch append failures and rethrow `DEPENDENCY_UNAVAILABLE` while logging without leaking payload (no new schema).
- **Fix risk:** Low if left unchanged; any change must not swallow the original provider-outage mapping.
- **Severity:** Low

### 5. Same-purpose success replay & provider outage; fresh retry after FAILURE; no later FAILURE after success

Prior-event loop (`:163–171`):

1. `FAILURE`+`FAILED`+matching `preProviderFingerprint`+matching `purpose` → `continue` (fresh retry allowed).
2. Same `eventType`+`SUCCESS`+matching fingerprint → `Decision.priorSuccess = event` (replay candidate).
3. Else → 409 `SHARE_GENERATION_STALE` (cross-purpose / changed fingerprint), **no provider, no event**.

Provider paths (`:73–83`): on outage/malformed/invalid credential, `appendFailure` runs **only if `decision.priorSuccess() == null`**. So:
- First attempt outage → one `FAILURE`, then same-key retry succeeds (IT 912–924).
- Outage **after** success → `DEPENDENCY_UNAVAILABLE`, **no** second `FAILURE`, first success row unchanged (IT 926–934).
- Identical repeated failure reuses the deterministic ID via `ON CONFLICT DO NOTHING` + identity compare (`JooqShareAdmissionRepository.java:117–123`); IT asserts one `FAILURE` per key after two failed attempts (IT 881, 908).

Cross-purpose same key → 409 with zero second provider call/event (service line 375–380; IT 564–576).
