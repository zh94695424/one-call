## Findings

### OQ-1-未修复-[中]-Derived `purchaseConsentEventId` can exceed the 128-character consent `event_id`/`source_ref` limits for accepted 75..475-character order keys

- **入口/函数**: `catalog-order` order creation T-S2-07 (`§9.17` steps 2/4) calls `activation-consent.append_purchase_consent` (`§10.20`), which inserts `activation_consent.consent_record`; the purchase consent identity is defined by the OQ-1 derivation in `§10.17`.
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3235` (deterministic `purchase-consent:<canonical lowercase account UUID>:<client idempotency key>`), `:3227` (`PURCHASE` consent fingerprint includes `eventId`), `:1849`/`:1868` (`consent_record.event_id` and `ck_consent_event_id`, 1-128), `:1863` (`ck_consent_source_ref`, 1-128), `:2710`/`:2712` (order uses the stable `purchaseConsentEventId`), `:3374` (append service), `:1092`/`:1112` (client key 1-475) and `:3859` (T-S2-53 says a 475-character key creates the order).
- **输入场景**: A first order with a valid client idempotency key of length 75..475 (the order check accepts 1-475), no existing platform replay.
- **实际分支**: The default derivation is 17 characters (`purchase-consent:`) + 36-character canonical account UUID + 1 character (`:`) + the client key = 129..529 characters. The consent row uses that value as its `(PURCHASE, eventId)` identity (`:3235`), but `consent_record.event_id` is limited to 1-128 (`:1849`, `:1868`); `source_ref`, if set to the same stable reference, is also limited to 1-128 (`:1863`). A key longer than 74 characters therefore produces an over-length consent identity.
- **预期行为**: The derived identity must fit the persisted consent identity contract for the entire accepted client-key range, or the client key must be bounded before mutation with an aligned platform-key/test contract. A fixed-length deterministic encoding (for example `purchase-consent:` plus lowercase SHA-256 hex, 81 characters) is sufficient; same-key retry must still reproduce the same identity and fingerprint.
- **实际行为**: A 475-character client key produces a 529-character `purchaseConsentEventId`. The order path cannot insert the `PURCHASE` consent: the immediate CHECK rejects the row, the transaction follows category 3 and rolls back the `NEW` idempotency row, consent, order and Outbox with a raw constraint error rather than a stable typed order result, or an implementer invents an unspecified truncation/hash that is not the documented OQ-1 identity. T-S2-53's positive assertion that the 475-character key creates the order cannot hold.
- **直接证据**: The exact derivation at `:3235`; the 1-128 checks at `:1849`, `:1863`, `:1868`; the order/consent handoff at `:2710`, `:2712`, `:3374`; the accepted key range at `:1092`, `:1112`; the contradictory 475-key assertion at `:3859`. The 476-512 rejection path is reached only after the key is rejected, so it does not cover 75-475.
- **影响**: Order creation fails for a valid accepted key range and the OQ-1 deterministic retry identity cannot be persisted. The failure is fail-closed (no partial order/consent commit) but it is a code-generation contradiction and a real boundary defect, not a policy question. It also makes T-S2-53's 475-character positive test false.
- **建议改法和验证点**: Derive a fixed-length stable identity that fits `event_id`/`source_ref` (for example `purchase-consent:` + 64 lowercase hex SHA-256 of the canonical account/key input, or an equally exact fixed-length encoding), or reduce the client-key bound to 1-74 and update the platform-key boundary and T-S2-53. Validate before any order/consent/idempotency write. Add T-S2-53/T-S2-55 cases at 74/75/128/475 characters, assert the same identity on retry, and assert no raw CHECK/unique error is exposed as a protocol success. No new table/column/function is needed.
- **修复风险（低/中/高）**: 低 (derivation/validation text; no schema object).
- **严重程度（低/中/高/严重）**: 中.

2. **V006 function disabled recheck under OQ-6.** `§10.9` Errors (`:3008`) lists `TRIAL_POLICY_NOT_FOUND` for a "missing/disabled policy version", while the policy-selection paragraph (`:3015`) says the wrapper's authoritative enabled read is the linearization point and a disable after it does not revoke the selected grant. 5. **Call-event fingerprint/hash circularity.** `§9.24` step 4 (`:2790`) says `payload_redacted` stores the original semantic inputs and the fingerprint, while `§4.27` (`:1445`) defines `payload_sha256` as the SHA-256 of the canonical redacted payload and the fingerprint scope (`§10.17` `:3230`) includes `payloadSha256`. Confirm the hash is computed over the original redacted event fields before the fingerprint metadata is added (or store the fingerprint outside the hashed object); otherwise the stored object's hash and its fingerprint input are ambiguous. Owner: S2 author / IVR; destination: next bounded specification edit.
