## Material findings

### F-01-未修复-[低]-验证章节硬编码了错误的 worktree GIT_DIR
- **位置**: Plan §10 validation commands, lines 281-282.
- **问题类型**: 不可直接实施 / 验证证据风险
- **当前写法**: `GIT_DIR=/mnt/d/codex-call/.git/worktrees/codex-call15 GIT_WORK_TREE="$PWD" GIT_OPTIONAL_LOCKS=0 git diff --check` (and the same for `--name-only`).
- **反例/失败场景**: The active PA15 worktree recorded by Control is `C:\Users\Administrator\.codex\worktrees\pa15-sharing-public-share-read\codex-call` (WSL `/mnt/c/...`), not `/mnt/d/codex-call/.git/worktrees/codex-call15`. An implementation agent following this literally either fails, or—worse—points Git at another worktree and produces a diff that does not describe the PA15 candidate. The plan's protected-path/no-untracked-file claim would then be unsupported.
- **为什么有问题**: The validation command is meant to prove the implementation worktree has only the allowed changes; a stale `GIT_DIR` defeats that proof and may cross the isolation boundary into a sibling worktree.
- **直接证据**: Control line 19 records the PA15 worktree path; plan lines 281-282 hardcode a different `/mnt/d/...` worktree name. No path in this snapshot resolves to that Git dir.
- **影响**: Invalid "protected paths unchanged / no unexpected files" evidence; possible inspection of the wrong repository; implementation agent may waste a cycle diagnosing Git rather than product code.
- **建议改法和验证点**: Derive the repo from `$PWD` (for example `git rev-parse --show-toplevel`/`--git-dir`) or use `git -C "$PWD"` with `GIT_OPTIONAL_LOCKS=0`; never hardcode a worktree-specific `GIT_DIR`. Verify with a dry-run that `git status --porcelain` reports only the allowed candidate paths.
- **修复风险**: 低
- **严重程度**: 低

### F-02-未修复-[低]-member 判定额外加入 attested selected workspace 等值门槛，超出冻结契约文字
- **位置**: Plan §6 line 158 (and its relation to the state matrix row at line 150).
- **问题类型**: 目标边界 / 契约缺失（本地策略未经 Goal Confirmation 明确确认）
- **当前写法**: "An attested ORGANIZATION workspace, when present, must equal the grant tenant; a PERSONAL workspace is nonmatching for organization content." The state matrix separately says a "valid current matching member" is eligible for content.
- **反例/失败场景**: An authenticated account is a current ACTIVE member of the grant tenant organization B, but the session's attested selected workspace is PERSONAL or organization A. The plan returns metadata-only 200 even though account/organization/membership membership of B exists. The OpenAPI says content is projected only after the authenticated account/organization/membership matches the grant tenant (lines 3633-3638); the Goal Confirmation says strict current account/organization/membership matching (line 21). Neither names the selected-workspace attestation as an additional content gate.
- **为什么有问题**: This is a user-visible tightening not stated in the frozen contract. It may be the intended product behavior ("current organization" = selected workspace), but that interpretation is not confirmed by the Goal Confirmation or OpenAPI. An implementer can implement either reading, and the named member tests can silently encode the stricter one.
- **直接证据**: OpenAPI `getPublicShare` description lines 3633-3638; Goal Confirmation line 21; plan line 158 vs matrix line 150. `CustomerContextService` returns all ACTIVE memberships independent of `selectedWorkspace`; the workspace gate is an adapter-level addition.
- **影响**: A legitimate current member can be denied content; reviewer/implementation ambiguity in `memberSessionMatchAndNonmatchNeverLeakContent` and `organizationPageRechecksCurrentAccountTenantAndMembership`; possible product regression not required by the goal.
- **建议改法和验证点**: Confirm with the Goal Confirmation owner. If only current membership of the grant tenant is authoritative, remove the workspace-equality clause and test "valid member + different/PERSONAL selected workspace -> content". If the stricter rule is intended, record it as an explicit goal clarification and add the same test case as a frozen denial.
- **修复风险**: 低（删除严格门槛）／低（若确认保留则仅补测试与说明）
- **严重程度**: 低
