## 6. Findings

### PA17-RR6-A-01-未修复-[低]-Post-commit grant-terminal ticket branch has no frozen event behavior, and the seven `TICKET_FAILED` reasons cannot express it

- **位置**: Plan §9A L378; §2.4 L52, L54–L55; §5 L281 (`ticketFailureEventIsDeterministicRedactedAndSingle`, `revokedExpiredLockedAndStaleGenerationMapExactly`).
- **问题类型**: 契约缺失 / 可观测性 / 状态机.
- **当前写法**: §9A says: "Before ticket issue, map a current grant's applicable revoked/expired terminal outcome first; distinguish it from provider/Redis unavailability (503)." §2.4 L54 says any post-commit credential/ticket/Redis/event failure appends exactly one deterministic `TICKET_FAILED`; L55 freezes exactly seven reasons.
- **反例/失败场景**: An admission commits; before ticket issue a creator revoke or a time-based expiry lands. The terminal branch must return `SHARE_REVOKED`/`SHARE_EXPIRED` 410. The plan does not state whether a `TICKET_FAILED` event is appended. If appended, none of the seven reasons (`MEDIA_CREDENTIAL_UNAVAILABLE`, `MEDIA_CREDENTIAL_MALFORMED`, `TICKET_WRITE_UNAVAILABLE`, `TICKET_WRITE_MALFORMED`, `TICKET_WINDOW_EXPIRED`, `TICKET_EVENT_UNAVAILABLE`, `INTERNAL_FAILURE`) is a grant-terminal reason, so the implementation must invent a reason or mislabel it `INTERNAL_FAILURE`; if not appended, the literal "any post-commit failure appends exactly one" rule appears unsatisfied unless §9A's authority clause is read as exempting domain denials.
- **为什么有问题**: The event store is append-only and the event result/payload sets are frozen by §9A L377 and §2.4 L55. The implementation agent must make an unstated event-append choice; `ticketFailureEventIsDeterministicRedactedAndSingle` and the terminal/race methods can then disagree on event count or reason.
- **直接证据**: Plan §9A L378; §2.4 L52/L54/L55; §9A L377; V009 `share_access_event` `event_type`/`result` checks; docs/14 §9.31 L3422/L3424 (ticket/Redis failure appends `TICKET_FAILED`; a pre-reconstruction revoke/expiry governs).
- **影响**: Event/audit inconsistency and potential test churn after implementation; no security bypass and no admission-count change.
- **建议改法和验证点**: Add one sentence to §9A: the post-commit grant-terminal branch returns the frozen 410 outcome and appends **no** `TICKET_FAILED` event (`TICKET_FAILED` is reserved for the seven provider/Redis/window/event reasons); or, if audit requires an event, add a frozen terminal reason and map it. Assert the chosen behavior in existing `revokedExpiredLockedAndStaleGenerationMapExactly` / `admissionRaceWithRevokeOrRotateObservesCommittedWinner`.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### PA17-RR6-A-02-未修复-[低]-RR5-01 witness equality is not explicitly scoped to existing-witness replay; a literal read of the final-recheck branch can require a witness before a fresh member insert

- **位置**: Plan §9A L376; §2.2 L35/L37; §2.3 L44/L46/L47; §2.4 L56; §4 L131.
- **问题类型**: 状态机漏洞 / 不可直接实施 / 契约精度.
- **当前写法**: §9A applies the witness-recipient equality "In §2.2, both §2.3 replay/final-recheck transaction branches, and §2.4 reconstruction", and immediately says "Missing, malformed, or ambiguous witness fails closed as `DEPENDENCY_UNAVAILABLE` (503)." The final-recheck branch (§2.3 L46) also performs fresh inserts (§2.3 L47).
- **反例/失败场景**: A fresh `ORGANIZATION_MEMBER` admission has no `ADMISSION_GRANTED` witness yet; the witness is created by the fresh insert. An implementation agent that applies the authoritative §9A sentence literally to the final-recheck branch may look for a pre-insert witness, find it missing, and fail closed with 503 — blocking every new member admission. Conversely, the agent may resolve the ambiguity inconsistently across the replay and fresh-insert paths.
- **为什么有问题**: §2.3 L46–L47 and docs/14 L3414 make the intended split clear (replay compares the existing witness; a fresh insert writes the current trusted recipient as the witness), but §9A does not say "when an existing admission/witness is being resolved." Because §9A is declared authoritative over earlier wording, the unscoped sentence is the highest-priority text.
- **直接证据**: Plan §9A L376; §2.3 L46 ("If another request committed the key during proof, discard the precomputed proof and replay its witness. Only a still-missing active key ... may insert"); §2.3 L47 (fresh insert appends the witness with the original trusted recipient); §2.4 L56 (same-key retry re-reads the witness); docs/14 L3412/L3414/L3424.
- **影响**: Implementation agent could deny all fresh member admissions (503) or implement inconsistent witness checks; acceptance of `organizationMemberUsesCurrentAccountOrganizationMembership` and `noneAdmission...` member cases could fail.
- **建议改法和验证点**: Add "when resolving an existing admission/witness" to the §9A sentence, and state "a fresh insert writes the trusted current recipient as the new witness and performs no pre-insert witness-equality check." Extend the two named existing methods with the fresh-insert positive case and the different-account replay negative case; no new method.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.
