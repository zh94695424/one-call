## Findings

Production-code review found no high-severity correctness or security defect in the credential authority, codec, key handling, replay/reconstruction, event convergence, transaction boundaries, Spring wiring, or frozen boundaries. The findings below are test-strength/plan-conformance gaps and one cleanup item; they are evidence-based and non-disclosing.

### F-01 — **Medium** — The binding fail-closed evidence matrix and the production exactly-one evidence resolver are not covered

- **Plan requirement (binding):** plan §10.2 (line 284) requires `evidenceResolutionFailuresNeverInvokeProvider` to loop `Missing`, `Unavailable`, zero/multiple reader providers (including `@Primary`), null/throwing reader/result, and malformed facts (invalid UUID/object ID/hash/size/MIME, null/nonpositive duration, window overflow); with an otherwise authorized fresh request it must assert authoritative transactions have closed before resolution, exact `DEPENDENCY_UNAVAILABLE`, **0** media events, **0** insert attempts, **0** provider calls, unchanged admission/grant state; after recovery it must assert a fresh P3 request (`priorReplayAnchor == null`), the full 19-key fingerprint, provider-call count 1, insert attempts 1, exactly one 24-key success and zero failure; a repeated request must be byte-identical and leave provider-call count 2 with one unchanged event.
- **Actual:** `backend/src/test/java/com/onecall/archtests/sharing/ShareAdmissionServiceTests.java:737-746` loops only `NULL`, `MISSING`, `UNAVAILABLE`, `THROWN`, and `DURATION` (null validated duration). It asserts dependency/no event/no provider call, then one successful recovery and `priorReplayAnchor == null`. It does not exercise zero/multiple/`@Primary` readers, malformed fact metadata, transaction-closure at resolution, provider/insert counts, the 19/24-key shapes, or the required repeat replay. The fixture injects a single direct reader lambda; it never exercises the production resolving reader.
- **Production resolver has no test:** `backend/src/main/java/com/onecall/core/sharing/internal/persistence/ShareAdmissionPersistenceConfiguration.java:114-125` implements the `ObjectProvider<EvidenceMediaObjectReader>` exactly-one resolver (`size()!=1` → `Unavailable`; zero/multiple/throwing → `Unavailable`). `MediaPlaybackConfigurationTests.java:131-153` only obtains `shareMediaAuthorizationService` and reflects its `credentials` field; it never calls the service, so the zero/multiple/`@Primary`/throwing resolver behavior is untested. The playback configuration tests exercise the separate playback-service evidence resolver, not this admission resolver.
- **Impact:** this is the security-relevant outage path introduced by PA21: no access event of any type, no provider call, and no fingerprint fabrication when evidence is unavailable or ambiguous. A regression in the resolver's exactly-one check, `@Primary` concealment, malformed-fact rejection, or recovery replay identity would pass the focused suite. Production review of the resolver and the `AuthorizedMediaFacts` constructor found them consistent with the contract, so this is a coverage/conformance gap, not an observed production defect.
- **Recommendation:** extend the existing method (no new test path or method count change) to cover the missing rows and post-recovery/read-back assertions, and exercise the persistence resolver with a fake `ObjectProvider` (one/multiple/zero/throwing) inside an already-approved test method.

### F-02 — **Low** — The two named replay tests were not strengthened to pin the expanded 19-key fingerprint and 24-key success payload/hash

- **Plan requirement (binding):** plan §8.1 (lines 181-184) requires `ShareAdmissionServiceTests.sameAuthorizationRequestAndPurposeReplaysCredentialAndEvent` and `PublicShareAdmissionIT.mediaAuthorizationUsesExactRouteAndFrozenResponse` to preserve their exact names and use the normalized witness bound for the 19-key fingerprint, the returned provider expiry for the 24-key success payload/hash, and byte-identical replay, independently of the codec under test.
- **Actual:** `ShareAdmissionServiceTests.java:375-394` checks the response credential/expiry, event count/type/result, `credentialExpiresAt`, replay equality, and `INSERTED`→`REUSED_IDENTICAL`, but never asserts the 19-key fingerprint, the 24-key payload shape, or the full canonical payload hash. `PublicShareAdmissionIT.java:539-577` checks the frozen two-field response, route, event count/type, `credentialExpiresAt`, replay equality, provider calls, semantic credential, and `mediaWrites`, but likewise never calls `assertMediaSuccessFields`, `mediaFingerprint`, or recomputes the payload hash. The sub-microsecond synthetic-provider path is precisely the compatibility case the plan singled out, and it now lacks those independent payload assertions.
- **Impact:** a regression affecting the sub-micro/second synthetic replay path's event-key shape, fingerprint, or payload hash would not fail these named methods. Other tests (`resolvedMediaFactsBoundBeforeProviderAndCommittedExactly`, `twoConnection…`, `providerUnavailable…`, and the real-authority tests) do pin the shapes for their paths, substantially limiting the residual risk; this is therefore Low, not a product defect.
- **Recommendation:** add the independent 19/24-key and full-hash assertions inside the two existing methods; no new test method or path is needed.

### F-03 — **Low** — Authority metadata/identity negative loops omit several constructor-validated fields

- **Plan requirement:** plan §4.1 requires valid UUIDs, lowercase 64-hex hash/digests/fingerprint, nonblank event ID, positive size/duration, nonblank MIME, nonnegative generations, and exact purpose/event mapping; §10.2 names `authorizedFactsRequireFullWindowAndValidMetadata` and `purposeEventAndRequestIdentityValidationFailClosed`.
- **Actual:** `MediaPlaybackCredentialAuthorityTests.java:171-176` covers duration `0/-1`, arbitrary window start/end, and hash `null`/uppercase/short; it does not cover null evidence/object IDs, nonpositive `sizeBytes`, null/blank MIME, or a null facts object. `MediaPlaybackCredentialAuthorityTests.java:202-208` covers mismatched event type and invalid request digest; it does not cover null/unknown purpose, blank event ID, invalid/uppercase pre-provider fingerprint, negative generations, or null instants. The production `AuthorizedMediaFacts` and request-record constructors do enforce these, so no defect was observed.
- **Impact:** low regression protection around a trusted-fact boundary; not a current correctness/security failure.
- **Recommendation:** extend the existing loop tables in those two methods.

## Open Questions

1. **Concurrent same-request-key/different-purpose calls.** The success event identity at `DefaultShareMediaAuthorizationService.java:68` includes `eventType`, while `authoritative()` reads priors by request-key digest only (`:165-168`). Sequential cross-purpose reuse conflicts as tested (`ShareAdmissionServiceTests.java:396-400`), but two concurrent first calls with the same request key and different purposes can both see no prior events and insert distinct success events/credentials (distinct event IDs, no DB uniqueness on the request digest). This appears pre-existing in the unchanged event identity/formula and is not in the PA21 new-test list. Confirm whether it is an accepted residual (Sharing/Backend) or whether request-key serialization/uniqueness is required; changing it would be a plan/schema change outside these non-goals.
2. **Authority-level replay expiry trust.** `MediaPlaybackCredentialAuthority.issueOrReplay` trusts the caller-supplied `credentialExpiresAt` on replay and the test `MediaPlaybackCredentialAuthorityTests.java:161-169` shows a shortened expiry is accepted for the same anchor. The production service always passes the committed event expiry and validates it, so the current flow is safe; confirm the authority is intended to be used only behind that service contract.
3. **Evidence/frozen inputs not re-read in this session.** The authoritative patch, base snapshot, `.review-evidence`, and external `SKILL.md` were outside the workspace allowlist. The supplied SHA-256 values and Controller container/XML/Node evidence are therefore taken as supplied; V001/V008/OpenAPI/POM and the candidate file inventory were checked directly, but a full manifest re-hash was not performed here.
4. **`Malformed` result variants.** Both P2 and P3 result unions include `Malformed`; only P3 is used by the new authority. The architecture test pins the P3 set (including `Malformed`). If this variant is new rather than pre-existing, confirm it is part of the accepted carrier extension and not an unintended legacy P2 surface change.
