## 5. Material finding

### 01-未修复-[中]-ACTIVE→ACTIVE extraction-code rotation is presented as a legal owner action

- **位置**: Plan §4.1 lifecycle matrix, row `ACTIVE → ACTIVE | Extraction-code rotation`; §4.1 enforcement paragraph ("including same-state rotation"); §7.1 S2 method responsibility and §7.4 lifecycle assertions ("for each named legal change … success").
- **问题类型**: 契约缺失 / 设计真源冲突 / 目标漂移.
- **当前写法**: The plan lists `ACTIVE → ACTIVE` extraction-code rotation with `salt/hash` replaced, `code_generation +1`, `revocation_generation +1`, `revision +1` under "Legal mutation" in a matrix introduced as "Required named owner action/state witnesses … This matrix describes atomic owner actions". It also says same-state rotation is allowed structurally.
- **反例/失败场景**: An implementation agent writes the S2 oracle to commit/assert an `ACTIVE → ACTIVE` code rotation as an authorized owner action and to expose `code_generation`/`revocation_generation` mutation on an active grant. The frozen design describes code rotation as the explicit `LOCKED → ACTIVE` unlock path, not an active-state action. The S2 evidence would then encode an action the service surface does not authorize, and the concurrency rotation case would be ambiguous about which source status it assumes.
- **为什么有问题**: The plan is meant to be code-generation-ready for the frozen persistence contract. The matrix row is not just a structural shape: it is labelled a legal atomic owner action and feeds the "named legal change" assertions. That overstates the frozen transition set and can fossilize an unauthorized action in durable test evidence.
- **直接证据**:
  - doc-14 §4.44 (`:2324`): "Code rotation replaces `code_salt`/`code_hash`, increments `code_generation` and `revocation_generation` by one, sets a `LOCKED` grant back to `ACTIVE` …".
  - doc-14 §7.4 (`:2817`): "`LOCKED → ACTIVE` only by code rotation …"; the only `ACTIVE → ACTIVE` transition described is extension; no active-state rotation is listed.
  - doc-14 §10.23 (`:4064`): "`LOCKED → ACTIVE` only through code rotation".
  - docs/15 `:145` (`rotateCustomerShareCode`): "仅 `EXTRACTION_CODE` 模式；`LOCKED→ACTIVE` 且 `codeGeneration`/`revocationGeneration` +1".
  - Plan §4.1/§7.4 exactly as cited above.
- **影响**: The S2 lifecycle oracle and the admission-vs-rotation concurrency case may assert/assume an unauthorized active-rotation action; later sharing-service work could inherit the DB guard's active-rotation allowance as a supported path. No schema/ACL/DDL corruption is implied, but plan-level service semantics and test evidence would be wrong.
- **建议改法和验证点**: Either (a) remove `ACTIVE → ACTIVE` extraction-code rotation from the "legal mutation" matrix and keep only `LOCKED → ACTIVE` as the named rotation action, or (b) explicitly classify same-state rotation as structurally accepted but service-forbidden (like the same-state terminal and mixed-action probes), with a residual owner `Sharing/Backend` for the excluded service action. Keep the code-rotation coupling negatives (partial salt/hash, generation, revision) and state explicitly which source status the concurrency rotation case starts from. Re-run only the S2 lifecycle method and the source=CI=XML equality; no DDL/ACL/inventory change.
- **修复风险（低/中/高）**: 低 (a bounded matrix/test-oracle clarification; no DDL or schema change).
- **严重程度（低/中/高/严重）**: 中.
- **Status**: `accepted-candidate` (evidence-backed; controller adjudication required).

## 6. Open questions (not accepted as blocking findings)

- **Q1 — Targeted regression command scope.** §9 command 5 ("targeted cumulative fence regression before final") lists `v007ForeignKeyAndLateOrderConsentFkBackstops` and four V008 methods, but omits the two V006/V007 inventory methods and the V001–V003 inventory method whose helper bodies/call sites are changed. The final full run (§9 command 6) covers all 64, so this is a sequencing/detection-cost issue, not an acceptance gap. Recommend adding the three changed inventory methods to the targeted run or recording why the full run is the first check.
- **Q2 — "Append" wording vs sorted exact lists.** `assertFunctionsAndTrigger` uses `containsExactly` over `ORDER BY 1`; the sharing functions sort before `subject_number.*` and the sharing triggers sort between `sharing.*` and `subject_number.*`. The plan says "append" to the prior lists. An implementer must insert in sorted position, not literally at the end. The plan's "exact set, never count-only" intent makes the correct action derivable; this is a clarity risk.
- **Q3 — EXPIRED terminal fixture wording.** §7.4 line 371 says the terminal fixtures are "established through [their] named transition", while line 373 permits a method-local direct `INSERT` for a future-expiry `EXPIRED` fixture because a named expiry transition requires a reached expiry. The controller's fix-3 ruling permits the direct INSERT, so both routes are acceptable; the wording should say so explicitly to avoid an implementer trying to reach `EXPIRED` through a future-expiry named transition (which the guard correctly refuses).
- **Q4 — Live fence non-sharing retention detail.** The plan says the live fence keeps "all non-sharing evidence, function-wave and prior exact checks" and "cross-schema misplaced-name exclusions" are preserved in the staged helper. The final fence's concrete contents are not enumerated item-by-item. The requirement is clear at intent level but could be made an explicit checklist so the implementer does not drop the legacy IVR-name, consent-FK, exact IVR/entitlement/activation/evidence table and five-service checks when replacing the three absence calls.
