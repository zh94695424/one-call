## Findings

### F-PA4-S1-01 — V004 exact-ACL suite omits plan-mandated REFERENCES/TRIGGER, cross-module column-write and full role-denial surfaces

- **Entry/function**: `v004OwnerPublicRuntimeAndCrossModuleAclsAreExact` → `assertV004SchemaUsageMatrix`, `assertV004OwnedAndCrossModuleGrants`, `assertV004GuardFunctionExecuteBoundaries`; shared helper `assertTablePrivileges`.
- **File and exact line**: `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:1568-1575` (test entry); `:6693-6770` (schema matrix); `:6772-6943` (owned/cross-module grants); `:6991-7048` (function boundaries); `:8668-8682` (helper checking only SELECT/INSERT/UPDATE/DELETE/TRUNCATE).
- **Triggering input/scenario**: an accidental or future migration issues one of the privileges that the accepted plan's contract sections explicitly deny, for example `GRANT REFERENCES` or `GRANT TRIGGER` to `catalog_order_role`/another V004 role on a V004 table, `GRANT UPDATE(col)` to `catalog_order_role` or `entitlement_metering_role` on a cross-module table, `GRANT EXECUTE` on a guard function to any owner role other than `catalog_order_role`, or `GRANT USAGE`/`CREATE` on a schema to a role/schema pair not enumerated in the spot checks.
- **Actual branch**: the checked-in assertions query only the enumerated pairs and, through `assertTablePrivileges`, only five table privileges. The cross-module loops (`:6868-6886`, `:6902-6921`) assert table-level SELECT/UPDATE/INSERT/DELETE/TRUNCATE and exact column SELECT, but never column-level UPDATE or REFERENCES/TRIGGER. The guard-function loop (`:6998-7028`) checks 12 runtime roles and PUBLIC but no owner role. `assertV004SchemaUsageMatrix` checks selected USAGE/CREATE pairs, not every role/schema pair, and does not assert `catalog_order_role` has no CREATE on `activation_consent`/`entitlement_metering` or that owners lack CREATE on foreign schemas.
- **Expected behavior**: any privilege outside the accepted matrix must fail the suite closed, per plan §6.6.2 (`has_table_privilege(..., 'DELETE'|'TRUNCATE'|'REFERENCES'|'TRIGGER')` false for every runtime role), §6.6.3 ("No cross-module INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES or row-lock privilege"), §6.6.5 (all denials asserted, including all V004/S1 roles), and §8.3 ("assert every row in 6.6.1 ... and PUBLIC"; owners have CREATE only on their own schema).
- **Actual behavior**: the suite is green because those privilege surfaces are never inspected. The current V004 migration is clean (it grants only the accepted matrix), so this is an evidence-completeness defect rather than a live over-grant; however, the method's name and the S1 success signal claim exact ACL enforcement, and a future privilege escalation of these shapes would pass review and CI.
- **Direct evidence**: `assertTablePrivileges` (`:8668-8682`) checks exactly SELECT/INSERT/UPDATE/DELETE/TRUNCATE. Grep of the test class finds per-role REFERENCES/TRIGGER privilege assertions only in the V002 matrix (`:8576-8584`) and V003 matrix (`:7203-7214`); none exist for the eight V004 roles. The cross-module loops assert only table-level write privileges and column SELECT, never column UPDATE. The guard loop omits `catalog_order_owner`, `ivr_owner`, `entitlement_metering_owner`, `activation_consent_owner`, `platform_reliability_owner`, `audit_owner`, `customer_iam_owner`, `organization_access_owner`, `operations_iam_owner` and `subject_number_owner`. The V004 DDL that would be the target of such a regression is `backend/src/main/resources/db/migration/V004__catalog_order_and_payment.sql:408-453`.
- **Impact**: the fail-closed "exact least-privilege grants" evidence has a regression blind spot. A future `REFERENCES`, `TRIGGER`, foreign-column `UPDATE`, owner-role `EXECUTE`, or unlisted schema USAGE/CREATE grant would not fail the checked-in suite or the CI XML check, even though the plan explicitly forbids it. No current incorrect grant was found.
- **Concrete fix and validation**: extend the V004 ACL method to a complete matrix without adding test methods: (1) all eight V004 roles plus PUBLIC × the four S2 schemas and touched S1 schemas, asserting USAGE and CREATE exactly; (2) every non-owner V004/S1 role × all seven V004 tables and the five cross-module tables, asserting SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER exactly, with owner-inherent privileges modeled explicitly; (3) `has_column_privilege(..., 'UPDATE')` false for every cross-module column and for every non-granted V004 column; (4) guard-function EXECUTE false for every role except `catalog_order_role` (and owner-inherent `catalog_order_owner`), including all owner roles; (5) S1 table-privilege denials for `ivr_role` (all five touched S1 tables), `activation_consent_role` and `entitlement_metering_role`. Keep 27 methods, rerun `./mvnw -B -ntp validate`, `./mvnw -B -ntp clean verify`, `./mvnw -B -ntp -Pcontainer-smoke verify` (27/0/0/0), and optionally seed one rogue grant per new surface in a disposable PostgreSQL 16 database to prove each assertion fails, then revoke/roll back.
- **Fix risk**: Low. The assertions must distinguish table-level from column-level privileges (the suite already relies on `has_table_privilege` returning false when only column UPDATE exists) and must model owners' inherent privileges; otherwise the new matrix could produce false failures. No product SQL change is expected.
- **Severity**: Low.
