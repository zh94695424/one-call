### 1-未修复-[中]-只读 listing 耦合可变锁图且 DB 侧等待无上界
- **位置**: §5 "Transactions and role" (`docs/gateflow/pa10-sharing-application-service-plan.md:100`), §2 row "Active personal/organization context" (`:23`), §9 IT 10 (`:207`)
- **问题类型**: 过度耦合 / 并发恢复风险 / 契约缺失
- **当前写法**: 每次 listing 事务在 `SET LOCAL ROLE` 之后按 rank 7→8→9 取 `pg_advisory_xact_lock(hashtextextended(...,0))`，并在锁后重读 account/organization/membership；计划以 "This follows docs/14 §§9.0.2/10.21" 作为依据；同时明确 "no production pool-sizing or timeout/SLO policy is selected"，只在测试 fixture 里使用有界 statement/lock/future timeout。
- **反例/失败场景**: 未来的 grant 创建/admission/revoke（或任何 rank 9 owner 事务）持有 `customer_iam.account:<A>` 期间，A 反复打开分享列表。listing 在 `pg_advisory_xact_lock` 上无限等待；JVM 侧只有 Hikari `connectionTimeout` 约束取连接，不约束取锁。10 个池连接被 parked listing 占满后，同一 DataSource 上所有其它查询在 30s 取连接超时，一个只读元数据列表变成可用性放大器。IT 10 只用 fixture timeout 观测 `pg_stat_activity` 等待，即验证了 fixture 行为而不是产品行为。
- **为什么有问题**: 计划引用的 `docs/14:3018` §9.0.2 item 1 规范的是 share grant **创建/准入** 事务的锁序，而不是只读 listing；同一真源在 `docs/14:155`（"An unlocked read-only workspace projection is not authorization serialization and is rechecked per protected request"）和 `docs/14:2973`（"An unlocked read-only workspace listing (T-S1-04) is an advisory projection, not an authorization lease and not this lock contract"）明确把只读 listing 排除在锁契约之外。READ COMMITTED 下每条语句新快照，三把 xact 锁并不能给跨页 listing 任何一致性保证，只增加与写路径的耦合和无界阻塞面。
- **直接证据**: plan `:23`、`:100`、`:207`；`docs/14-production-data-model-and-flyway-schema-spec.md:155`、`:2973`、`:3018`；`V009__sharing.sql:338-351`（listing 只需 SELECT 权限，无需行锁）；`PostgresContainerIT.java:22753`（既有 xact 锁用法均在 owner 写路径）
- **影响**: 实施 Agent 按"规范已要求"实现读路径锁；生产 listing 可被写事务无限期 park，池耗尽外溢到其它共享该 DataSource 的读路径；review 无法从计划文本判断锁是必要还是过度设计；测试证明的是 fixture 超时而非产品上界
- **建议改法和验证点**: 二选一并写进 §5/§9。(A) 按 `docs/14:155/2973` 走已授权的 unlocked recheck：去掉 rank 7/8/9，只按精确列做 SELECT 并要求状态；IT 10 改为"并发 commit 的 disable/suspend 在同一页序列的后续 recheck 中可见"这一确定性断言。(B) 若坚持保留锁：在角色断言之后立即 `SET LOCAL lock_timeout = '<bounded value>'`（声明为事务控制上界，不是业务策略值），新增/改写 IT 断言第二连接持锁时 listing 在有界时间内以 sanitized `SERVICE_UNAVAILABLE` 失败（55P03 映射），且不得出现无界等待；同时在 §3 sources 行改正锁契约出处。验证点：存在一条"被阻塞的 listing 有界失败"的 IT；`grep` 计划文本不再引用 §9.0.2 作为读路径锁依据。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-[中]-keyset 顺序与锚点确定性的权威来源未定义且依赖环境
- **位置**: §6 bullets (`:108`, `:110`, `:112`), §2 row "Stable listing" (`:25`), §8 fixtures (`:166`), §9 IT 5 (`:202`)
- **问题类型**: 契约缺失 / 测试缺口 / 并发恢复风险
- **当前写法**: 排序/比较一律交给"the same database text collation"，禁止 Java 字典序、禁止引入 `COLLATE`/新归一化 ID/新索引；fixture 使用 tied microsecond timestamps 与 "lexical IDs (e.g. `s-2`, `s-10`, mixed case)"；IT 5 断言 "concatenated traversal equals expected scope order"。计划未定义 expected scope order 由谁产生，也未固定/声明 fixture 库的 collation，也未指定 11 列与锚点在 jOOQ 中的确切 `SQLDataType`/converter 与时区约束。
- **反例/失败场景**: (a) 实施 Agent 用 `String::compareTo` 在 Java 里排 expected 顺序：`C`/`POSIX` collation 下 `S-3` 排在 `s-10` 之前，而 glibc `en_US.utf8`（`PostgresContainerIT.java:878-882` 只设 `POSTGRES_USER/DB/PASSWORD`，未传 `POSTGRES_INITDB_ARGS`，因此 initdb locale 完全由镜像默认决定；本 review 环境无 Docker 权限，该 locale 未能实测，但"未被固定"这一事实已由源码证明）下主权重视大小写与标点为等值，比较落到 `s3` vs `s10`，顺序相反 → IT 在 CI 或换镜像/换 locale 时随机红；更坏的情形是 Agent 通过放宽断言（只断言无重复/无缺口）让 IT 变绿，而真正的排序语义没人证明。(b) 若 `valid_from` 经 `LocalDateTime`/会话时区相关路径绑定，`valid_from = :anchor` 可能整体偏移，导致跨页漏行/重行——这是用户可见的数据跳过，而现有 IT 只在单一 locale/TZ 组合下跑过。docs/14 与 docs/18 全文都没有 pin 生产 collation（`grep` 无命中），因此测试库与生产库的排序语义可能不同。
- **为什么有问题**: 目标要求 "Stable metadata order is valid_from DESC, share_id DESC" 且"分页确定性"是成功信号；把权威交给数据库 collation 是正确方向，但计划同时要求一个"expected 顺序"断言，却没有说明 expected 必须由数据库自身产生，也没有把 collation/时区作为可证明的环境事实固定下来。这使关键的正确性证明依赖未声明的环境假设。

- **影响**: 生成错误代码（Java 侧排序、放宽断言）；IT 在 CI/换镜像后 flaky；生产跨页漏行/重行只在上线后暴露；review 不可验收（无法判断"稳定顺序"是否被证明）
- **建议改法和验证点**: 在 §6/§9 明确三条：(1) IT 5/6 的 expected 顺序必须由同一 fixture 数据上的一次性 DB 基线查询（`ORDER BY valid_from DESC, share_id DESC`）产生，禁止在 Java 中重排；(2) IT 1 增加 `datcollate`/`datistemplate` 事实断言并显式声明 fixture 库 collation（要么以 `POSTGRES_INITDB_ARGS=--lc-collate=C` pin 住，要么把"顺序权威 = 该 collation"写为契约并记录生产 collation 为待确认输入）；(3) §5/§6 指名 jOOQ 类型（例如 `valid_from`/`expires_at` 用 `OFFSETDATETIME`+`Instant` 转换、`share_id` 用 `SQLDataType.VARCHAR`）并要求一条 JVM/session 时区偏移用例，证明锚点等值与 `<` 谓词在 TZ 不同结果集上一致。验证点：存在 TZ/顺序断言的 IT；不存在 Java 侧字典序 expected 构造。

- **严重程度（低/中/高/严重）**: 中

### 3-未修复-[中]-"secret-free projection" 证明机制与自身禁令冲突

- **当前写法**: 连接/角色/超时/迁移不可用一律映射为常量 sanitized `SERVICE_UNAVAILABLE`，非预期映射/不变量错误映射为 `INTERNAL`，公开文本不含请求值、数据库值和 raw SQL cause；并且明确要求避免记录 SQL 异常。计划没有任何"允许记录什么"的正面规定，也没有指标/结构化诊断要求。
- **反例/失败场景**: 部署后列表全部失败。可能是 42501（query login 不是 `sharing_role` 成员，Q17 provisioning 漂移）、57014（statement_timeout）、55P03（锁等待，见 F1）、08001（连接）、25006（只读事务写入）或 UUID/枚举映射缺陷。按 §5/§6 的字面要求，这些在线上表现为完全相同的常量消息且"不记录 SQL 异常"，运维无法区分，回滚/修复决策没有依据；本 slice 自己的 IT 9/10 也依赖 SQLSTATE 判别，说明信息存在且只是被禁了。
- **为什么有问题**: docs/17 的脱敏是 allow-list + deny-list 模型（`:524`），deny-list 针对的是 phone/token/hash/keyRef/objectKey 等值，并不禁止 SQLSTATE/errcode/异常类名这类非敏感事实；同一真源在失败出口要求"告警"（`:574`）。把"不泄漏"实现成"不记录"既不符合 best practice（observability），也不符合已冻结的脱敏契约，并把风险从数据泄漏换成了不可诊断的静默失败。
- **直接证据**: plan `:67`、`:88`、`:113`、`:205-207`；docs/17:524、`:574`、`:437`（允许 object identity digest/hash prefix 级日志字段）；docs/17:707 `R-A3-REDACTION-RUNTIME`（运行时出口不由 A3 证明，说明需要服务自证的可诊断出口）
- **影响**: 生产故障不可定位、MTTR 拉长；实施 Agent 可能反向选择"记录完整异常"从而破坏脱敏目标；后续 review 无法判断失败原因归属
- **建议改法和验证点**: 在 §6 增加"sanitized diagnostic record" 契约：固定 allow-list（operation 名、`ShareQueryException` code、`java.sql.SQLException` 简单类名、SQLSTATE 与 classcode、是否有/无当前角色，不含 bind 值、SQL 文本、账号/组织/证据 UUID、URL、用户名）；把 `causes` 保留在内部（不进入 public message）但允许该 allow-list 出口。IT 8 的日志 canary 断言扩展为"该诊断行存在且不含任何 canary 值"。验证点：至少两个不同 SQLSTATE（42501 与 25006）在日志里可区分，canary 断言仍为绿。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## 8. Conclusion

verdict: **pass-with-risks**

The plan is unusually well-grounded: every load-bearing factual claim I could test (BOM versions, Boot 4 auto-configuration surface, V009 column ACLs and mutation rights, V002 lifecycle states, docs/14 §9.0/§10.21/§10.23, docs/15 and the frozen OpenAPI listing contract, existing guard/CI counts, the baseline build) held up against the bytes at `add92fd2`, and the core security semantics — creator-only predicate in both branches, caller-supplied trusted context with no client-overridable scope, exact 11-field allow-list projection, transaction-local `sharing_role` with a separate query login, and refusal to invent auth/Q15/Q17/Q12/Q22 — are correct and non-negotiable in the right places.

Seven material findings remain, none of which is a structural safety blocker: the read path locks like a write path without a bounded wait and cites authority that exempts it (F1); keyset order/anchor determinism is delegated to an unpinned environment while the test's expected-order source is undefined (F2); the sole secret-leak proof conflicts with the plan's own logging prohibition (F3); fail-closed sanitization leaves no diagnostic exit (F4); the in-process migration runner pre-empts the deferred Q17 identity decision and is not mapped to any binding success signal (F5); the slice has no environment entry gate and no graded evidence split, so it cannot be validated in this environment at all (F6); and the future public application service is structurally buried in `internal` (F7). All seven are plan-text edits with low/low/low/low/low/medium/low fix risk and named verification points.

Before an accepted-plan entry, I recommend the controller require at minimum F1 (bounded or removed read-path locks with a deterministic bounded-failure IT), F2 (DB-derived expected order + pinned/declared collation + explicit jOOQ timestamp types and a timezone case), F3 (named capture mechanism), F4 (sanitized diagnostic allow-list) and F6 (pre-entry environment gate plus local/CI evidence split). F5 and F7 may be dispositioned as goal-confirmation amendments or explicit residual rows with owners, but not left silent.
