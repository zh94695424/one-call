## Findings

### PA12-ACL-01 — [High] Frozen `sharing_role` ACL exposes secret columns and contradicts the required 42501 test

- **Trigger:** Apply the frozen V001–V009 migrations, connect through the PA10 sharing query login, set `ROLE sharing_role`, and execute any direct column read or future query path against `sharing.evidence_share_grant`, for example `SELECT capability_token_hash FROM sharing.evidence_share_grant`.
- **Branch:** This is the database trust boundary beneath the GET endpoint. It is reachable independently of the controller’s safe field list; it also determines whether the promised SQL ACL/no-secret defense is true.
- **Expected:** The sharing query principal should be limited to the approved metadata projection. Secret columns (`capability_token_hash`, `code_salt`, `code_hash`, `content_snapshot`, `content_sha256`) should be denied with `42501`; the GET path should remain read-only and unable to perform writes.
- **Actual:** `backend/src/main/resources/db/migration/V009__sharing.sql:307-315` grants `SELECT, INSERT` on the entire `sharing.evidence_share_grant` table to `sharing_role`, and grants column-scoped `UPDATE` privileges for lifecycle fields. There is no later column-level `REVOKE` for the secret columns. In PostgreSQL, table-level `GRANT SELECT` includes all columns, so `sharing_role` has direct read privilege over the secret/hash/snapshot columns. The implementation’s query at `backend/src/main/java/com/onecall/core/sharing/internal/persistence/JooqShareQueryRepository.java:65-72` avoids selecting them, and the transaction is read-only, but that does not repair the underlying ACL.
- **Direct evidence:** `backend/src/test/java/com/onecall/archtests/container/CustomerSharesIT.java:217-232` explicitly expects `SELECT capability_token_hash FROM sharing.evidence_share_grant` to fail with `42501`. That assertion is incompatible with the frozen `GRANT SELECT` at `V009__sharing.sql:308`. The same test only proves endpoint transaction read-only (`25006`), not column-level privilege isolation; the role still has table-level `INSERT` and lifecycle `UPDATE` capability outside a read-only transaction.
- **Impact:** The stated SQL ACL/no-secret boundary is false. A compromised or accidentally broadened sharing query path, direct operational use of the query principal, or a future read-only-path regression can read capability hashes, code material, and content snapshots. The container test that is intended to protect this boundary should fail against the supplied migrations, so the advertised green CI/integration inventory is not independently credible from this snapshot. The HTTP response itself is currently metadata-only; this finding is the lower-level trust-boundary and acceptance failure.
- **Fix direction:** This cannot be corrected inside the PA12 candidate without violating the frozen V009 scope. The owning migration/DB gate must either introduce a dedicated least-privilege read role or view and grant only the approved columns, explicitly revoke table-wide `SELECT` before granting safe columns, and separate endpoint read privileges from create/revoke/rotate write privileges. Then run the PostgreSQL acceptance test and confirm the direct secret-column probes return `42501`; do not weaken the test to match the broad grant. Reconcile the non-goal write APIs through their own role rather than relying on `SET TRANSACTION READ ONLY` as the ACL boundary.
- **Risk:** High. This is a security boundary failure plus a likely guaranteed acceptance-test failure. No evidence shows the HTTP endpoint currently serializes secret fields, but the database principal has more authority than the PA12 contract allows.
- **Severity:** High / blocking for PA12 acceptance.
