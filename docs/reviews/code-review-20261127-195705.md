### 1-未修复-低-subjectId structured filter is never discriminated by any executable test
- **入口/函数**: `OperationsOrdersReadIT.structuredFiltersAndCursorPagingRemainStableAcrossLimitAndEmployeeChanges`.
- **文件(行号)**: `OperationsOrdersReadIT.java:136-141`; fixture `OperationsOrderReadFixture.java:205-209` (`order(...)` always inserts `subject`).
- **输入场景**: request `GET /api/v1/operations/orders?subjectId=<subject>`.
- **实际分支**: the IT asserts only `get("items").size()).isPositive()` for the subjectId filter; every seeded order shares the single `fixture.subject`, so the page is identical whether or not the predicate is applied. `DefaultOperationsOrderReadService` list-row filter check (`:66-67`) also cannot catch a dropped predicate because every returned row already matches.
- **预期行为**: the test claims to prove structured filtering; `paymentStatus` is discriminated (alternating UNKNOWN/UNPAID and the service defensive `require` turns a dropped predicate into 500), but `subjectId` is not.
- **实际行为**: a regression that removes `subjectId` from `JooqOperationsOrderReader` (`:49`) would still pass this IT and the reader unit test.
- **直接证据**: single `subject` inserted for all orders (`OperationsOrderReadFixture.java:207`); assertion is `isPositive()` only (`OperationsOrdersReadIT.java:140`).
- **影响**: false assurance on subjectId filtering; an over-broad listing regression would be undetected. Not an authorization boundary (operations employees may read all orders); production predicate is present and parameterized, so no live defect.
- **建议改法和验证点**: seed one order under a second subject and assert the `subjectId=<subject>` page excludes it (exact id set), not just `isPositive()`.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
