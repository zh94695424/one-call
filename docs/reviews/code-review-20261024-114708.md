### Adversarial assessment of adjacent array-admission bypasses

- **Own-property/boolean handling**: correct. `items: false` is accepted by own-property presence and treated as closed/nothing; `items: true` is rejected by the boolean-true invariant; `items: {}` is walked and fails object closure. Probe exits match exactly.
- **Invalid `items` values**: `items:` (null), `items: invalid-schema-string`, `items: 0`, and `items: []` all exit 1. For null/string/number the rejection is `struct` (`Expected type Schema (object) but got null`, etc.); `items: []` additionally triggers both custom messages because the walker treats the malformed array node as an untyped schema. Thus no invalid-`items` false acceptance exists at the lint gate (`obs-*` probes).
- **Invalid `type` values**: `type: any`, `type: 'array '` (trailing space), `type: [null]`, `type: [123]`, `type: {}`/non-string non-array forms and a duplicate `type` key all exit 1 (Redocly `struct`/parser), so the predicate cannot be bypassed by an unknown type string at the gate. A valid `type: ['object','null']` correctly excludes arrays and only requires object closure (`adv-type-list-object-needs-closure` exit 1 for closure, `adv-type-list-object-closed` exit 0).
- **Composition/ref forms**: untyped wrappers themselves must declare both closures (fail-closed); an array branch inside `allOf` is caught; 21-hop pure refs are resolved without a silent cutoff; external, impure or cyclic request-schema refs fail closed; legitimate recursive arrays terminate through the walker seen set.
- **Deferred keyword class**: `patternProperties`, `if`/`then`/`else`, `dependentSchemas`, `not`, `unevaluatedProperties`, and other non-enumerated applicators are still not traversed. This is explicitly outside fix 6. In particular `patternProperties` at a closed object can still re-open the object and can also host array subschemas that would otherwise need `items`; that is the same aggregate-review-owned residual previously recorded, not a new regression and not expanded here.

## Open Questions

- **Finding-ID traceability**: the controller records the accepted finding as R5-01 (`project-execution-control.md:241,254`), while the fix-6 artifact, implementation report and controller gate line use `R6-01` for the same rule (`fix-6.md:45`, implementation report §7/§12). The semantics are unambiguous and this is documentation-only; the controller should normalize the canonical ID when accepting the re-review. It does not affect correctness.
- **Custom-rule boundary for non-schema `items` values**: the onecall rule deliberately checks own-property presence and does not itself validate that an `items` value is a schema. At the delivered lint gate this is safe because Redocly `struct` rejects null/string/number forms (verified). If the plugin were ever used with those structural rules disabled, `items: null`/`0`/string would satisfy own-property presence; the accepted R5-01 wording does not require the custom rule to duplicate schema meta-validation, so this is recorded as a boundary rather than a defect.
- **Fail-closed false rejections**: semantically closed untyped/annotation-only/enum-only schemas and arrays closed only through a composition branch (for example `{type: array, allOf: [{items: false}]}`) are rejected because the rule requires a direct `type`/`items`/`additionalProperties` declaration. This is the disclosed fail-closed contract policy of F5-01/R5-01, not full JSON Schema satisfiability. No canonical shape is affected.
- **Scope of the re-review**: this review adjudicates only the R5-01/fix-6 delta and nonregression. It does not accept S1, select an aggregate-review keyword policy, or authorize S2.
