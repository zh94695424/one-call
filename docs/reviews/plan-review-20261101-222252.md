The fix was written against `1dd69ce`, whose control is `0022f000…`; the controller's own `7c67c7c` "record PA11 plan fix" commit changed it. The adjudication content at line 28 is unchanged. Also, the prompt/fix/control record original reviews under `docs/reviews/...`, while the matching bytes are under `docs/gateflow/...`.
- **Impact**: No effect on the plan's substantive authority or the reviewed behavior; the accepted-plan checkpoint would otherwise freeze the wrong control hash and a non-existent review path.
- **Recommendation**: At acceptance, record the actual control hash at the accepted-plan checkpoint (and reconcile the review paths), or label the plan's value as plan-fix-time input rather than "current". Owner: Controller.

### N-02 — Low — Two citation line anchors are imprecise

- **Observed**: V002 `:234` is `REVOKE ALL ON TABLE customer_iam.customer_account FROM PUBLIC;`; the relevant `GRANT USAGE ON SCHEMA customer_iam` is `:241` and the column grants are `:243–245`. The docs/14 personal-workspace derivation is at `:3066`; the plan cites `:3062` (T-S1-04 heading) and `:3064` (step 1).
- **Impact**: Cosmetic; the cited sections and substantive claims are correct. Could mislead a code generator reading specific lines.
- **Recommendation**: Correct at acceptance or rely explicitly on the plan's section-anchor disclaimer. Owner: Plan author/Controller.

### N-03 — Low — `CustomerProblemWriter` wiring (bean vs plain collaborator) is not named

- **Observed**: §3 lists `CustomerProblemWriter` as a file; the filter, controller `@ExceptionHandler`s and error controller all use it. §8's no-DB web test imports `CustomerWebConfiguration`, `CustomerMeController`, `CustomerApiErrorController` and the five test beans, but does not say whether `CustomerProblemWriter` is a separate container bean. If it is an unimported `@Component`, the test context would lack a dependency; if it is a plain/stateless class or defined by `CustomerWebConfiguration`, it is covered.
- **Impact**: Test-scaffolding ambiguity only; both lawful shapes are implementable without a bypass.
- **Recommendation**: State in §3/§8 that the writer is either a plain collaborator/utility or defined by the imported web configuration; keep the no-bypass rule. Owner: Backend/Implementation.

### N-04 — Low — Inactive-account mapping is stated in two places with different framing

- **Observed**: §8 application #3 says "empty/inactive repository projection -> 401"; application #4 says "bad status -> 500". The SQL filters `a.status = 'ACTIVE'` and the repository contract says an absent ACTIVE account is empty, so a valid `DISABLED` account should yield empty -> 401; an unknown/invalid status enum is a projection violation -> 500.
- **Impact**: A code generator could map a repository-returned valid `DISABLED` account inconsistently.
- **Recommendation**: Clarify that a valid `DISABLED` account is 401 and only an unknown/invalid status is 500; no test-count change. Owner: Backend/Implementation.

### N-05 — Low — Positive allowlist must be evaluated before the legacy substring firewall

- **Observed**: The current negative regex includes `spring-boot-starter-(?:jdbc|jooq|flyway|web|security|data-)`, which matches the approved `spring-boot-starter-webmvc` as a substring. The plan's rule "legacy substring bans remain effective for any coordinate outside the exact approved set" implies the exact positive set is allowed first and the legacy bans apply only to non-approved coordinates. The exact CI algorithm is not written out.
- **Impact**: A naive implementation that adds the starter to the approved set but keeps the negative regex applied to every JAR would reject the approved starter; a prefix-loosening workaround would weaken B-F7.
- **Recommendation**: In §8, state the ordering explicitly (exact frozen-set membership passes; negative regex applies only to non-members) and add a small CI probe/fixture proving `spring-boot-starter-webmvc` passes while `spring-boot-starter-web`, `spring-websocket`, `tomcat-embed-jasper` and `jakarta.servlet-api` fail. Owner: Backend/CI.

### N-06 — Low — Test-only ERROR-dispatch and dual-pool context mechanics are left to implementation

- **Observed**: §8 web #7 says the failing test dependency may call `sendError(...)` "via test-owned servlet request attributes"; §8 IT #9 says the dual-pool test starts both profiles with distinct logins. The exact test-context composition (e.g., `RequestContextHolder`/request attributes, imported test configurations, per-test properties) is not frozen.
- **Impact**: Implementation may invent ad-hoc test machinery; the plan already forbids an extra route/filter and a main-source bypass, so the risk is bounded.
- **Recommendation**: Freeze these mechanisms at the implementation entry gate and keep them test-owned. Owner: Backend/Implementation.

### N-07 — Low — Residual overlap between a few test methods

- **Observed**: `OneCallApplicationTests` extended absence assertions overlap `CustomerWebConfigurationTests` #1 default-runtime absence; web #4 reachable Problems overlap web #7's 401/503/500 assertions. The plan gives distinct inputs (DB-env profile activation; negotiation/ERROR dispatch) and the fix artifact justifies the current count, so this is not a count problem.
- **Impact**: Possible duplicate coverage/maintenance cost, not a correctness or security gap.
- **Recommendation**: Keep distinct inputs explicit in the method bodies; do not add methods solely to preserve counts. Owner: Backend/Implementation.

### N-08 — Low — Boot 3.x→4.1.2 stack drift is not repeated in the deviation line

- **Observed**: B-F4 required the Spring Security deviation and the Boot 3.x→4.1.2 drift to be recorded. §4/POM document Boot 4.1.2, but the §2/§9 deviation line names only Spring Security.
- **Impact**: The reconciliation ADR may omit the already-accepted Boot drift.
- **Recommendation**: Add one clause to the deviation/ADR destination. Owner: Backend/Architecture/Security.
