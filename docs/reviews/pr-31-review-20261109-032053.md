## Findings

### 1-未修复-低-`ReadSession.abort()` 的"close 后 no-op / 幂等"契约只存在于 plan 与测试，未落在发布的接口契约里

- **入口/函数**: `MediaGatewayFilter.transfer(...)` 的成功清理路径与失败清理路径；被 `ControlledMediaByteSource.ReadSession` 的实现方消费。
- **文件(行号)**: `backend/src/main/java/com/onecall/core/sharing/internal/gateway/MediaGatewayFilter.java:127-140`；`backend/src/main/java/com/onecall/core/evidence/mediaread/ControlledMediaByteSource.java:39-45`。
- **输入场景**: 字节已全部写出、`session.close()` 成功之后，`reply.flushBuffer()` 抛 `IllegalStateException`/`IOException`（客户端断开或容器 flush 失败）。
- **实际分支**: `closeAttempted = true; session.close(); reply.flushBuffer();` 成功 close 后 flush 失败 → 进入 `catch` → `session.abort()` 被对**已关闭**的 session 调用一次（`abort()` 异常被吞掉），随后 `if (!closeAttempted)` 为假，不再 close。
- **预期行为**: plan §5.1/§5.2 与 `MediaGatewayWebTests.abortCloseAndFlushFailuresPreserveCleanupCounts`、`ControlledMediaByteSourceTests.sessionsCloseAbortAndRejectReadsAfterTerminalState` 都要求"abort after close 是 no-op"，因此 filter 的调用顺序在测试实现下是安全的。
- **实际行为**: 这一"close 之后 abort 必须 no-op、close 必须幂等且即使抛异常也要释放资源"的硬性契约只写在 plan 与测试 fixture 中；`ControlledMediaByteSource.ReadSession`（发布接口，未来真实 provider 唯一需要实现的类型）没有任何 javadoc 声明该语义。当前生产中没有 `implements ControlledMediaByteSource`，只有测试 provider；未来真实 provider 若把 `abort()` 实现为非幂等/close 后重复释放内部句柄，filter 虽会吞掉其抛出的异常（HTTP 响应仍安全），但 provider 的内部资源状态可能被二次释放/破坏。
- **直接证据**: `MediaGatewayFilter.java:128-136`（成功 close 后 flush 失败仍调用 `session.abort()`）；`ControlledMediaByteSource.java:39-45`（`abort`/`close` 无任何幂等或顺序说明）；契约语义仅见 `docs/gateflow/…-plan.md` §5.1/§5.2 与测试。
- **影响**: 仅影响未来真实 provider 的正确性（当前为测试实现）；不会造成本次 PR 的 HTTP 错误或测试失败。属契约归属/可维护性缺口。
- **建议改法和验证点**: 在 `ReadSession.abort()`/`close()` 增加 javadoc，明确：`close()` 必须释放资源即使抛异常；`abort()`、`close()` 幂等；close 之后 `abort()` 为 no-op；read 在终态抛固定 safe `IOException`。可让 `ControlledMediaByteSourceTests` 的幂等断言继续作为可执行证据。
- **修复风险（低/中/高）**: 低（纯注释，无行为变更）。
- **严重程度（低/中/高/严重）**: 低。
