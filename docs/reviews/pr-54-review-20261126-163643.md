### F-02-未修复-低-row↔snapshot 的 hash 一致性断言是同义反复，其唯一负向锚点由 mock 伪造

- **入口/函数**: `CustomerOrderQueryService.getCustomerOrder` 的 row↔snapshot 一致性校验块；被校验值的产生方 `DefaultCustomerOrderSnapshotReader.read` / `CustomerOrderSemantics.projection`。
- **文件(行号)**: `backend/src/main/java/com/onecall/core/customer_iam/internal/application/CustomerOrderQueryService.java:86`、`:92`；`backend/src/main/java/com/onecall/core/catalog_order/internal/customerorder/DefaultCustomerOrderSnapshotReader.java:22`；`backend/src/main/java/com/onecall/core/catalog_order/internal/customerorder/CustomerOrderSemantics.java:195-202`（第 202 行 `benefits, hash)` 即 Snapshot 最后一个成分）；`backend/src/test/java/com/onecall/core/customer_iam/internal/application/CustomerOrderQueryServiceTests.java:94-122`。
- **输入场景**: detail 读命中一行订单，seam 返回一个 `snapshotSha256` 与行内 `row.snapshotSha256()` 不相等的 Snapshot（AGG-01 想防的"行与投影不同源"情形）。
- **实际分支**: 该分支在真实实现下不可达。`CustomerOrderQueryService.java:86` 以 `snapshots.read(row.snapshot(), row.snapshotSha256())` 调用 seam，`DefaultCustomerOrderSnapshotReader.java:22` 直接把同一个入参转交给 `CustomerOrderSemantics.projection(storedSnapshot, snapshotSha256)`，而 `projection` 的返回对象最后一个成分就是这个入参本身；因此只要 seam 正常返回，`Objects.equals(row.snapshotSha256(), snapshot.snapshotSha256())` 恒为 true。
- **预期行为**: 若 `:92` 要作为"行事实与快照投影同源"的守卫存在，它必须能被真实实现触发；否则该职责应显式声明为 seam 单点所有，并由 seam 内部（入参 hash 与 `sha(canonical(parse(stored)))` 的比较）单独守卫并测试。
- **实际行为**: `:92` 成为永假的装饰性条件，却被 AGG-01 的修复当作一项已验收的负向锚点来计数；实际唯一覆盖它的测试臂是 Mockito 造的、真实 seam 永远不可能产出的值。
- **直接证据**: 上述三处传递链为同一数据的直通（`CustomerOrderQueryService.java:86` → `DefaultCustomerOrderSnapshotReader.java:22` → `CustomerOrderSemantics.java:202`）；负向臂见 `CustomerOrderQueryServiceTests.java:104`（`..., agreed, "b".repeat(64)`）与 `:97`（`agreedHash = "a".repeat(64)"`）、`:111` 的 `verify(snapshots).read("stored", agreedHash)`；桩值来源见 `:45`（`detail()` 把行内 hash 固定为 `"a".repeat(64)`）。也就是说该臂断言的是"stub 返回了调用方没给过的值"，而不是"生产实现能发现不一致"。另证：`implements CustomerOrderSnapshotReader` 在 `src/main/java` 只有 `DefaultCustomerOrderSnapshotReader` 一处，不存在会返回不同 hash 的第二实现。
- **影响**: 测试保真度虚高（test-cemented assurance）：AGG-01 验收项中的"hash agreement"这一维并未被任何真实路径证明，未来若有人把 seam 改成自算 hash 或改 `projection` 的参数顺序，该断言与测试都不会失败，反而可能给出已覆盖的错觉。属 maintainability / semantic ownership 层面问题，不改变当前对外行为（同义反复的 `||` 项不会误拒、不会漏放合法数据，其余五个字段臂与 cursor/anchor 锚点是真实有效的）。
- **建议改法和验证点**: 二选一。要么删除 `:92` 这一同义反复项，并在 `CustomerOrderQueryServiceTests` 删除 `"b".repeat(64)` 臂，同时在 seam 侧（`CustomerOrderSnapshotReaderTests`）补一条"stored JSON 与入参 hash 不符 → `InvalidSnapshotException`"的真实实现断言（已有 `DefaultCustomerOrderSnapshotReader.java:17-21` 逻辑，只需钉住它作为 hash 绑定的唯一 owner）；要么让 seam 自己从 stored JSON 派生 hash（不再回显入参），使 `:92` 变成可触发的跨源比较。验证点：临时把 seam 改为回显常量 hash 时，测试必须失败（变异式检验），否则不得声称该维已覆盖。
- **修复风险（低/中/高）**: 低。删除项 + 测试重定向，或 seam 返回值语义收紧；不涉及 SQL、ACL、迁移或 OpenAPI。若选后者需同步核对 PA41 读回路径对 Snapshot 哈希的既有用法（`JooqCustomerOrderRepository` 侧）。
- **严重程度（低/中/高/严重）**: 低。
