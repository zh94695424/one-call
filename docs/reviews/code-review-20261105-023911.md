## Findings

### 1-未修复-中-组织 workspace 的成员查询可能选中 REVOKED 行并误拒 re-grant 后的有效成员
- **入口/函数**: `JooqSharingCommandRepository.readActiveCallerContext` (organization branch), reached from `DefaultCustomerShareCommandService.create` via `readCommandContext` for every organization-workspace create.
- **文件(行号)**: `backend/src/main/java/com/onecall/core/sharing/internal/persistence/JooqSharingCommandRepository.java:78-86`; schema evidence `backend/src/main/resources/db/migration/V002__identity_organization_and_employee.sql:113`; frozen rule `docs/14-production-data-model-and-flyway-schema-spec.md:2977`.
- **输入场景**: A trusted caller has an ACTIVE account and an ACTIVE membership row for the selected organization, while an older REVOKED membership row for the same `(organization_id, account_id)` still exists after a revoke-then-re-grant cycle (the frozen schema permits exactly this shape).
- **实际分支**: The SQL at lines 78-80 joins `organization_access.organization` to `organization_access.organization_membership` and filters only `o.id = ? AND m.account_id = ?`. It does not filter `m.status <> 'REVOKED'` and has no ordering/limit. When both rows exist, `fetchOne` returns the first row chosen by PostgreSQL. If that row is the REVOKED row, lines 81-82 return `Optional.empty()`, and the service maps the absent context to `FORBIDDEN` (403). If the ACTIVE row is chosen, the call proceeds normally.
- **预期行为**: `docs/14` §9.0 is explicit: “Under the pair advisory lock the reader queries the single non-revoked `organization_membership` row for the pair and requires `status = 'ACTIVE'`; absent, `SUSPENDED` or `REVOKED` fails closed.” After a re-grant, the single non-revoked row is the new ACTIVE row, so a valid member must pass.
- **实际行为**: The command can return a truthful 403 `FORBIDDEN` for a valid re-granted member depending on physical row selection. The same defect would affect every future organization-workspace transition that reuses this context reader. No privilege escalation occurs: a revoked-only member still fails the status check.
- **直接证据**: SQL/condition at `JooqSharingCommandRepository.java:78-82`; the partial unique index `uq_membership_live ... WHERE status <> 'REVOKED'` at `V002__identity_organization_and_employee.sql:113` proves that one ACTIVE and one REVOKED row can coexist; the frozen single-non-revoked rule at `docs/14...:2977`.
- **影响**: Correctness/availability defect in a core authorization-context read for a realistic lifecycle path (revocation followed by re-grant). Legitimate organization users can be denied create with no database facts, non-deterministically. It also violates the frozen lifecycle-read contract and could be misdiagnosed as risk/policy denial.
- **建议改法和验证点**: Filter the lifecycle read to the single non-revoked row, e.g. add `AND m.status <> 'REVOKED'` (the partial unique then guarantees at most one) before requiring `ACTIVE`, or otherwise make the selection deterministic and require `ACTIVE`. Extend the existing `CustomerShareCommandsIT` method (no new method is required by the plan) to seed a REVOKED row plus a new ACTIVE row for the same `(organization_id, account_id)`, run an organization create, and assert success and the ACTIVE role; also assert a revoked-only pair still fails. The command role already has SELECT on the required columns, so no grant change is needed.
