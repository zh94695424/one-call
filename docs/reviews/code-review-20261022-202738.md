### R-01-未修复-[高]-F-09 publication writes the new ACTIVE/enabled version before removing the old one, violating immediate partial unique indexes

- **Entry/function**: `catalog-order.publish_catalog_version` and `entitlement-metering.publish_trial_policy` in `§9.26`; the same ordering is repeated in the `§4.17` and `§4.29` revision/immutability text.
- **File (line)**: `docs/14-production-data-model-and-flyway-schema-spec.md:2816` (catalog publication step 3: set candidate `published_at`/`ACTIVE`, then set the previous `ACTIVE` version `OFFSALE`), `:2818` (trial-policy step 5: set the candidate `published_at`/`enabled = true`, then disable the previous enabled published version), `:985` and `:1564` (same order in the dictionaries), `:980` (`uq_catalog_version_active (product_id) WHERE sale_status = 'ACTIVE'`), `:1560` (`uq_trial_policy_enabled (campaign_key) WHERE enabled AND published_at IS NOT NULL`), `:208` (S2 has no deferrable FK/constraint).
- **Input scenario**: A second catalog version is published for a product that already has an `ACTIVE` version, or a second `FIRST-TRIAL` policy version is published while the previous published version is enabled.
- **Actual branch**: The transaction performs the new-version update first. At that statement the previous version is still `ACTIVE` (or enabled-and-published), so the immediate partial unique index sees two qualifying rows and raises a unique violation. The same order appears in the trial-policy path.
- **Expected behavior**: Under the owner publication advisory lock, first offsale the previous `ACTIVE` version (or disable the previous enabled published policy) with revision +1, then set the candidate `published_at`/`ACTIVE` or `published_at`/`enabled = true`; all in one transaction, with one winner and one current version/policy.
- **Actual behavior**: The normal second-publication path aborts the winner's transaction on its own unique index; the stable-loser branch is never reached because there is no committed winner. The claimed T-S2-57/T-S2-64 outcomes (one winner; stale loser returns a stable conflict/current state) cannot hold.
- **Direct evidence**: The step order at `:2816` and `:2818`; the partial unique predicates at `:980` and `:1560`; `§2.10`/`§2.11` (`:197-200`, `:208`) describe these as ordinary immediate controls, not deferrable; `§9.26` step 6 (`:2819`) claims one winner and no raw unique error.
- **Root cause**: The specification lists the new-current transition before the old-current removal. With an immediate partial unique index, the order of the two `UPDATE` statements is part of the correctness contract; the chosen order cannot commit.
- **Impact**: Catalog and trial-policy publication cannot succeed whenever an active/enabled version exists — the ordinary publication case. This is a transaction/specification blocker for F-09 and for the operations workflows, not a call to invent policy.
- **Suggested fix and verification**: In `§9.26` step 3 and step 5, and in the `§4.17`/`§4.29` prose, require: (1) previous current row → `OFFSALE`/`enabled = false` with revision +1; (2) candidate → `published_at` plus `ACTIVE`/`enabled = true` with revision +1; then audit/Outbox. Add a T-S2-57/T-S2-64 case with a pre-existing active/enabled version, asserting one winner, one current row, the previous row retired, no raw unique violation, and the stale loser returning the current state/conflict. The fix is a mechanical statement-order correction; no new table, function or policy is needed.
- **Fix risk (低/中/高)**: 低 (order correction in the existing transaction).
- **Severity (低/中/高/严重)**: 高.

### R-02-未修复-[高]-F-06 IVR confirmation requires a cross-owner `service_activation FOR UPDATE` that the IVR role cannot take

- **Entry/function**: `ivr` confirmation transaction T-S2-01 (`§9.11`) and its use of `activation-consent.record_activation_confirmation`.
- **File (line)**: `docs/14-production-data-model-and-flyway-schema-spec.md:2629` (step 1: "lock `inbound_session`, the current `call_record` and (when present) `service_activation` `FOR UPDATE`"), `:126`, `:2465`, `:2497` (cross-owner `FOR UPDATE`/`FOR SHARE` is prohibited; a row lock on a foreign row must be taken by the owning module's same-transaction collaborator), `:3078` (`ivr_role` has only `SELECT` of `service_activation.id, subject_id, status, revision`), `:3105` (`record_activation_confirmation` is called after replay and phase-A guards, i.e. step 6, not at step 1), `:3831` (T-S2-41: no S2 role takes a cross-owner `FOR UPDATE`).
- **Input scenario**: A fresh IVR confirmation for a subject with an existing `activation_consent.service_activation` row.
- **Actual branch**: The IVR transaction (running under `ivr_role`) attempts `SELECT ... FOR UPDATE` on `service_activation` at step 1. `ivr_role` has no `UPDATE` privilege on that table, and PostgreSQL requires an update-capable privilege for row locking; the enclosing cross-owner rule also forbids the lock. The statement fails with a permission error before the replay/confirmation/savepoint logic can complete.
- **Expected behavior**: Step 1 should lock only the IVR-owned `inbound_session` and `call_record`; the subject lifecycle advisory lock serializes the phase-A suspended/access gates, and the activation-consent owner service should take the `service_activation` row lock at step 6 (or a named owner-service lock collaborator at step 1) on the same connection. The organization/membership/account "advisory/row lock" phrases in `:2669`, `:2707` and `:2803` have the same issue: the S2 callers may take the advisory locks and re-read, but only the owner module may take the foreign row locks.
- **Actual behavior**: The specification simultaneously requires the IVR role to take a foreign row lock and states that no cross-module role may do so; the confirmation path is not executable as written. An implementer either gets a permission error or silently omits a stated lock, diverging from the contract.
- **Direct evidence**: The explicit `FOR UPDATE` at `:2629`; the exact `ivr_role` grant at `:3078`; the cross-owner rule at `:126`/`:2465`/`:2497`; the service call timing at `:3105`; the T-S2-41 assertion at `:3831`.
- **Root cause**: The confirmation sequence treats the activation row lock as an IVR-owned lock. It is a foreign-owned row; the general cross-owner contract requires either an advisory lock plus re-read or a named owner-service collaborator, and that collaborator is not invoked at the point the lock is asserted.
- **Impact**: The central IVR confirmation flow (and the task-backed/no-task access gates) cannot be implemented exactly as specified under the declared least-privilege roles; the spec is not code-generation-ready for this path. This is a privilege/sequence contradiction, not a runtime-test claim.
- **Suggested fix and verification**: Remove `service_activation` from the IVR step-1 `FOR UPDATE` list; state that the IVR locks only `inbound_session`/`call_record`, uses the subject lifecycle advisory lock and exact `SELECT` re-read for the activation/consent predicates, and that `record_activation_confirmation` takes the activation row lock when it writes at step 6. Replace every foreign "advisory/row lock" phrase with "advisory lock plus exact `SELECT` re-read; the owning module takes its row lock" (or name the owner collaborator). Add a T-S2-41/T-S2-51 forced privilege assertion proving `ivr_role` cannot take a cross-owner `FOR UPDATE` and that the confirmation still commits its intended outcome through the owner service.
- **Fix risk (低/中/高)**: 低/中 (wording plus one owner-service lock point; no schema change).
- **Severity (低/中/高/严重)**: 高.

### R-05-未修复-[中]-F-06 order creation takes the activation row lock after the idempotency row, contradicting the declared one-total-order

- **Entry/function**: `catalog-order` order creation T-S2-07 (`§9.17`) and its downstream call to `activation-consent.append_purchase_consent`.
- **File (line)**: `docs/14-production-data-model-and-flyway-schema-spec.md:2707` (step 1 acquires subject (3), organization (7), membership (8), account (9)), `:2708` (step 2 calls `platform.idempotency_begin` — global key 10), `:2710` (step 4 calls `append_purchase_consent`), `:3359` (the consent service's lock order is subject (3), `service_activation` row (4), organization (7), membership (8), account (9)), `:2476` ("one total order; no transaction takes an earlier key after a later key"), `:2487` (the idempotency row is acquired after locks 1-9 and before a tentative claim/reservation), `:2498` (the S2 savepoint/begin contract).

The subject advisory lock (3) happens to serialize the current paths so the specified interleavings do not deadlock, but the specification does not state that exception; an implementation that omits/relaxes subject (3), or a later caller that acquires 4 without it, can form a lock cycle. - **Suggested fix and verification**: Amend `§9.0.1`/`§9.17`/`§10.20` with the exact purchase-path order and exception, or restructure the call. Add a T-S2-63/T-S2-57 lock-order test with a concurrent confirmation/operations action and a forced lock-wait timeout; assert no deadlock and the expected winner/loser.
- **Fix risk (低/中/高)**: 中 (sequence/collaborator clarification; no schema change).
- **Severity (低/中/高/严重)**: 中.

### R-07-未修复-[中]-F-08/F-11 call-event conflict replay can lose the first outcome or regress an APPLIED event

- **Entry/function**: `ivr.process_call_event` duplicate/conflict branches and the `call_event` fingerprint/processing-status lifecycle.
- **File (line)**: `docs/14-production-data-model-and-flyway-schema-spec.md:2784-2787` (same-fingerprint duplicate returns the first outcome; a changed fingerprint "Mark/return `QUARANTINED`"; a sequence conflict persists the new event with `sequence_no = NULL` and reason `SEQUENCE_CONFLICT`), `:1472` (only `processing_status`, `reason_code` and `revision` may change; a duplicate same fingerprint returns the first outcome), `:3218` (the call-event fingerprint includes `callId, eventId, eventType, legId, payloadSha256, sequenceNo` with `sequenceNo` null-safe only when absent), `:3846` (T-S2-56).
- **Input scenario A (sequence replay)**: A first delivery of event E with `sequence_no=5` conflicts with an existing sequence and is stored `QUARANTINED` with `sequence_no = NULL`; the same event E is retried with the original sequence.
- **Input scenario B (changed re-delivery)**: Event E was already `APPLIED`; a later delivery of the same event ID with a changed payload/type is processed.
- **Actual branch**: Scenario A recomputes the fingerprint from the incoming `sequenceNo=5`, but the stored row has `sequence_no=NULL`; the fingerprints differ, so the service treats the retry as a changed-fingerprint/`EVENT_ID_CONFLICT` rather than returning the first `SEQUENCE_CONFLICT`/`QUARANTINED` outcome. Scenario B's "Mark/return `QUARANTINED`" can update the only mutable columns (`processing_status`, `reason_code`, `revision`) of the existing `APPLIED` row, because no second row can be inserted for the same `(IVR_EVENT,event_id)`. The spec does not state that the first `APPLIED` outcome is left unchanged.
- **Expected behavior**: A duplicate same event ID returns the stored first processing outcome (including a sequence-conflict quarantine) without changing it; a changed re-delivery is a stable conflict/audit fact that never downgrades an `APPLIED` event or its call/leg/settlement facts. The sequence-conflict normalization must preserve the fingerprint input needed for replay (or the replay comparison must use a stored normalization that equals the retry).
- **Actual behavior**: The sequence-conflict retry changes its outcome classification, and a conflicting re-delivery can change a previously applied event's processing status; the "first outcome" / "no terminal regression" guarantees are not preserved for these branches.
- **Direct evidence**: The nulling at `:2787`; the fingerprint field at `:3218`; the mutable status rule at `:1472`; the `Mark/return` wording at `:2785-2786`; T-S2-56's duplicate/changed expectations at `:3846`.

## Open Questions

1. **`purchaseConsentEventId` provenance and retry stability.** The `PURCHASE` order fingerprint includes `purchaseConsentEventId` (`:3215`), but `§9.17` does not state whether the client supplies it, the order service derives it, or how it is kept stable when the same order idempotency key is retried. If the server generates a fresh consent event ID on each attempt, the same-key/same-semantic order retry changes its fingerprint and conflicts instead of replaying. The spec should state the source and normalization, or exclude the transport event ID if a new consent event is not meant to be a semantic change. Owner: S2 author / catalog-order API contract; destination: next bounded specification edit or the order OpenAPI contract.
2. **Routing snapshot vs. reservation equality.** `§10.18` includes `balance.granted_units = grant.granted_units` in the eligible predicate, but the `ivr_role` grant on `entitlement_grant` (`:3081`) lacks `grant.granted_units`; the routing projection reads a subset and the reservation rechecks the equality. In valid data the equality is guaranteed by the copied/guarded value, and a corrupted balance is fail-closed at reservation, so this is not asserted as a defect. Confirm whether the routing read should include the grant units or whether the routing predicate should explicitly state the omitted equality as a routing-only relaxation.
3. **Other §3.2 read-only collaborators not matched by exact grants.** The matrix declares additional conceptual reads (for example `ivr` → `customer_order`, `usage_reservation`, `usage_fact`; `entitlement-metering` → `call_record`, `call_event`; `activation-consent` → `inbound_session`, `trial_policy_version`; `entitlement-metering` → catalog version/product/offer/benefit) that do not appear in `§10.12` and are contradicted by services that intentionally receive facts rather than read the owner's table (for example `§9.24` says the entitlement owner never reads IVR tables). Align the matrix with the actual read/write paths or mark these as conceptual/fact handoffs. Owner: S2 author; destination: next bounded specification edit.
4. **Catalog-offer withdrawal path.** `catalog_offer.offer_status` has `ACTIVE/WITHDRAWN` and a conditional revision, and the dictionary says a withdrawn offer blocks new orders, but `§9.26` covers catalog-version publication/offsale and trial-policy publication/disable, not an exact catalogue-offer withdrawal transaction, audit/Outbox or unique-loser behavior. Is offer withdrawal a separate operations action or is version offsale sufficient? Owner: S2 author / catalog-order operations; destination: F-09 follow-up if the offer lifecycle is intended to be independently operable.
5. **Trial-policy publisher identity.** `trial_policy_version.published_by_employee_id` is NOT NULL and immutable once published, while the INSERT is the only grant that supplies it and the UPDATE grant cannot change it. `§9.26` authenticates an operations employee for publication but does not require that employee to equal the draft's `published_by_employee_id`. If drafts may be created by a different employee, the recorded "publishing employee" is the draft creator. Clarify whether publication must be by the same employee or whether the column means "draft owner". Owner: S2 author / operations catalog; destination: next bounded specification edit.
6. **Trial-policy publication vs. in-flight issuance serialization.** `§9.26` uses the trial-policy advisory lock for publication/disable; `issueFirstTrial` "resolves the current enabled published policy under the entitlement owner's own read/serialization" (`§10.13`), while `§9.0.1` says publication keys "are not combined with the IVR call-path order" (`:2494`). State whether issuance takes the same trial-policy key and how that interacts with the IVR call-path lock order, or whether a confirmation may grant under the policy it read before a concurrent disable. Owner: entitlement-metering / IVR; destination: next bounded specification edit or the IVR protocol/acceptance work.
7. **Activation transition DB matrix vs. service-only rules.** `ck_activation_transition_matrix` (`:1944`) permits `ACTIVE → SUSPENDED` for any source domain and `INACTIVE → ACTIVE` for `OPERATIONS`, while the state machine/§4.37 says `ACTIVE → SUSPENDED` is operations-only and `INACTIVE → ACTIVE` is confirmation-driven. The service is the only writer, so this is not asserted as a current defect; confirm whether the DB check should be narrowed or the service-only rule is sufficient.
8. **Balance `EXHAUSTED` status at settlement.** `ck_entitlement_balance_status_shape` (`:1672`) requires `status = 'EXHAUSTED'` exactly when `consumed_units = granted_units`, while `§4.32` describes the status as "derived" and the settlement prose (`§9.15`) describes the unit updates but not the status update. Clarify that the settlement's single balance update sets `EXHAUSTED` in the same statement when consumption reaches the granted units (or otherwise satisfies the check).
