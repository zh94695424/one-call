## 3. Open questions

- **OQ-1 (PUBLIC TEMP scope/deployment)**: The global `REVOKE TEMPORARY ON DATABASE ... FROM PUBLIC` is the only PostgreSQL-supported way to deny TEMP to this role, and the repository has no temp-table dependency, so it is defensible under the goal's "no DDL" wording. However, it removes a default capability from **all** roles that rely on PUBLIC TEMP, and V011 cannot detect such external consumers; a successful migration can therefore break unrelated deployment jobs before the "fail-closed" review catches it. The plan classifies this as a Database/SRE residual and forbids restoring PUBLIC TEMP to make deployment pass. Please have the Controller/Database owner confirm whether a deployment preflight or an explicit consumer inventory is required before V011 is accepted; if not, the residual must remain owned and visible at deployment. Not classified as a finding because the plan explicitly discloses it and the goal arguably requires it.
- **OQ-2 (DDL negative-probe completeness)**: The plan probes `CREATE TABLE`, `CREATE SCHEMA`, `CREATE TEMP`, `ALTER TABLE`, `DROP TABLE`, `CREATE SEQUENCE`, `CREATE FUNCTION`, `SET ROLE`, `SET SESSION AUTHORIZATION`, `GRANT`, and `ALTER ROLE ... SUPERUSER`, but not `CREATE ROLE`, `CREATE DATABASE`, `CREATE VIEW`, `CREATE INDEX`, `MERGE`, or `COPY FROM`. The role attribute/effective ACL checks cover the missing privileges, but the plan claims exhaustive executable proof. Either add these probes or explicitly state that the attribute/effective-ACL checks are authoritative for them.
- **OQ-3 (properties test context composition)**: `PublicSharePersistenceConfigurationTests` is allowlisted for the new property-failure assertions, but the plan does not specify whether the failure contexts include `ShareProjectionReaderConfiguration`/the service bean. If they include the full public configuration without the reader, the context may fail for a missing reader rather than the intended credential error. Please pin the exact context composition and the deepest cause assertion.
- **OQ-4 (V011 existing-role password)**: The plan says a deployment-managed password must not be rejected, and the §9 catalog query does not select `rolpassword`; please keep the precondition and tests explicitly out of `rolpassword` so a legitimate existing credential does not fail the migration. (The plan's §3 wording already points this way; this is a precision confirmation.)
- **OQ-5 (public reader manager coupling)**: The evidence module's public bean names a sharing-module transaction manager by string. This follows the existing command-reader precedent, but there is no startup validation of that name. The executable proxy test is the only guard; keep it and assert the missing/ambient-manager failure explicitly.

## 5. Conclusion

**Verdict: `fail`.**

The plan is strong on the core ACL design: the role/24-column/70-denial arithmetic is exact, the V001–V010 byte manifest is correct, the 91/126/217 → 91/130/221 arithmetic is exact, the isolated pool/manager/DSL and evidence-owned MANDATORY adapter are directionally sound, and the negative-probe matrix is unusually thorough. However, the declared 17-path scope is not complete: a new production file under `sharing/internal/persistence` invalidates the protected `SharingQueryBoundaryTests` exact source inventory (F-01), and the second `ShareableEvidenceProjectionReader` bean makes the protected `CustomerShareCommandsIT` by-type lookups ambiguous (F-02). Both are concrete test failures within paths the plan explicitly protects, so the plan is not yet code-generation-ready. F-03 additionally weakens command-write evidence if the fixture DSL switch is implemented as written.

The Controller should require a plan fix that either adds the two protected test paths to the allowlist with exact edits (and updates the 17-path arithmetic) or changes the production design to avoid the new file/duplicate bean ambiguity, then re-freeze and re-review. No implementation should be authorized from this revision.
