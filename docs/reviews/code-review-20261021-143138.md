## Findings

### S1-01-已修复-[中]-管理列表继续把已到期或次数用尽的新分享显示为有效
- **入口/函数**: `sharesPage` 管理列表渲染；生命周期真源在 `shareBlockedState`。
- **文件(行号)**: `web-prototype/evidence-hub.html:2272`, `web-prototype/evidence-hub.html:2314`
- **输入场景**: 新建分享的 `expiresAt <= Date.now()`，或成功访问已达到 `visits` 上限，然后返回分享管理。
- **实际分支**: 接收页通过 `shareBlockedState` 判定 `expired/exhausted`，管理页却只读取未同步的 `item.status === '有效'`。
- **预期行为**: 同一记录在接收页与管理页展示一致生命周期；已过期/次数用尽不能继续显示为有效或提供有效态操作。
- **实际行为**: 接收页拒绝访问，但管理列表显示“有效”并继续提供撤销、换码/延期，形成用户可见的状态冲突。
- **直接证据**: 创建时 `status` 固定为“有效”；时间和次数只在 `shareBlockedState` 计算；`sharesPage` 的 badge 与 action 都由 `item.status` 驱动，未消费计算结果。QA 在访问次数达到 `1 / 1` 后只检查无换码，未断言状态。
- **影响**: 管理方会误认为链接仍可访问，且列表操作与接收结果不一致。
- **建议改法和验证点**: 抽取不含当前播放会话豁免的记录生命周期函数，同时供 `shareBlockedState` 和 `sharesPage` 使用；管理页显示“已过期/次数用尽”并关闭有效态操作。QA 分别断言次数用尽与动态过期后的管理状态。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

Re-review: `shareLifecycle` is now the shared record lifecycle source, while `shareBlockedState` only exempts the already admitted final session. Management derives badge/action availability from the same lifecycle. QA proves `次数用尽`, recipient rejection, and dynamic `已过期`; full Web QA passes. Finding final status: `已修复`.
