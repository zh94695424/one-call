### RB2-01-未修复-[高]-授权的 module-edge 计数编辑 `13 → 14` 与 Spring Modulith 行为不符，会使既有边界 oracle 变红

- **位置**: plan §10.2 `:323`（`ModuleBoundaryTests` 授权项 "the expected module-edge count `13 -> 14`"）、§3 `:86-88`、§4.2 `:116-117`
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施
- **当前写法**: §3 正确地把 command port 与 authority read port 放进 `operations_iam` named interfaces，由 `catalog_order` 实现/消费；§10.2 因此授权把 `ModuleBoundaryTests` 的期望模块边计数从 `13` 改成 `14`。
- **反例/失败场景**: PA38 新增的两条依赖都是 `catalog_order → operations_iam`（`::operations-catalog-sale-command`、`::employee-authority-read`）。而该模块对**今天已经存在**：`ModuleBoundaryTests.java:48` 声明 `catalog_order` 允许 `operations_iam::operations-subject-read`，且 `catalog_order/internal/operationsread/JooqOperationsCatalogProductReader.java` 实现的正是 `operations_iam.subjectread` 端口。`discoveredProductionEdgesStayInsideTheConfiguredMap` (`:98-115`) 先把每个模块的 `getDirectDependencies(modules).uniqueModules()` 收成 `Set<String>`，再 flatten 后 `containsExactlyInAnyOrder(13 项)`。由于 `uniqueModules()` 按 target **module** 去重，一个模块对同一目标模块使用第二个、第三个 named interface 不会新增一条边。实现者按 §10.2 把期望列表改成 14 项后，该断言必然失败；要"让它绿"，唯一途径要么新增一条 plan 明令禁止的边（例如 `operations_iam → catalog_order`），要么把 `containsExactlyInAnyOrder` 弱化成 `containsAll`/删掉 `.as("exactly thirteen production edges exist…")` —— 正是 `REV-01`/`REV-06` 要求保留的 oracle。
- **为什么有问题**: `REV-01` 的裁决目的（消除反向边、保留 `operations_iam → operations_audit`）与 `REV-06` 的"精确 lockstep 枚举"在这一点上互相矛盾：plan 声称已枚举的守卫编辑实际上是一个会破坏守卫的编辑。plan §10.2 同时要求"assertion text/diagnostic needed to preserve `operations_iam -> operations_audit`"，但 `operations_iam → operations_audit` 目前根本不是 discovered 边（它只出现在 `allowedDependencies`/`EXPECTED_ALLOWED`），因此该句也指错了对象。
- **直接证据**: `spring-modulith-core-2.1.2.jar` 常量池显示 `ApplicationModuleDependencies.uniqueModules()` = `uniqueStream(ApplicationModuleDependency::getTargetModule)` + `distinct`；`backend/src/test/java/com/onecall/archtests/architecture/ModuleBoundaryTests.java:40-55,98-115`（13 项 flatten 列表，含 6 个 `"operations_iam"`）；`backend/src/main/java/com/onecall/core/catalog_order/package-info.java:1`；`operations_iam/package-info.java:1`；本次按真实 import 图重算的 13 条模块对（`catalog_order→operations_iam` 在内）。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / review 不可验收（边界门禁红灯或被削弱）/ 后续返工
- **建议改法和验证点**: 把 §10.2 改成"discovered module-edge 计数保持 `13` 不变；`EXPECTED_ALLOWED` 中 `catalog_order` 从 3 项扩为 5 项（新增两个 `operations_iam::…`）"；如需要证明 named-interface 粒度新增，改用已有的 `getAllowedDependencies(modules)` tuple 断言范式（`ModuleBoundaryTests.java:121-134,222-235`），显式断言 `("catalog_order","operations-catalog-sale-command")`、`("catalog_order","employee-authority-read")`、并保留 `("operations_iam","operations_audit")` 与 `("catalog_order","operations-subject-read")`。验证点：`mvn -Dtest=ModuleBoundaryTests test` 9 个 `@Test` 全部不变且 `verifiesNoCyclesOrBoundaryViolations`/`discoveredProductionEdgesStayInsideTheConfiguredMap` 仍为 13。

- **严重程度（低/中/高/严重）**: 高

### RB2-02-未修复-[高]-authority 读取的事务传播自相矛盾：`REQUIRES_NEW` 不可能同时"same connection / no second transaction"
- **位置**: plan §3 `:96`、§6.1 `:172-187`、§4.1 条目 5/10 `:106,111`、§9.1 `isTransactionMandatory` `:277`
- **问题类型**: 架构边界 / 状态机漏洞 / 不可直接实施 / 目标漂移（相对 `REV-02` 已接受指令）
- **当前写法**: §3："The authority read transaction is **mandatory, `REQUIRES_NEW`**, `READ_COMMITTED`, and bound to the same physical datasource."；§6.1："The command transaction is `REQUIRES_NEW`, `READ_COMMITTED`, writable, and **mandatory**. The authority read is invoked inside that transaction and uses the **same connection; no nested pool or second transaction** is created."；§4.1 条目 10 又规定配置类 "**no resource construction**"。
- **反例/失败场景**: 若 authority port 真的用 `PROPAGATION_REQUIRES_NEW`（且按计划复用同一个 `operationsLifecycleTransactionTemplate` bean，§2.3/§6.1），Spring 会挂起外层命令事务并从同一 `HikariDataSource` 取**第二条物理连接**执行内层事务。后果是三重破坏：(1) `SET LOCAL ROLE operations_iam_role` 只作用于内层事务/内层连接，外层命令连接的 role 从未被见证，"same-connection ACTIVE/ADMIN witness" 变成假象；(2) 计划 §6.1 step 3 在同一条连接上继续 `SET LOCAL ROLE catalog_order_role` 的序列不再成立，role 切换/恢复断言（`setLocalRoleIsExactAndRestored`、`restoresRoleOnSuccessAndFailure`）测不到真实行为；(3) 每个命令占两条池连接，池耗尽与自我饥饿（PA32 fixture 的小池 + `CONNECTION LIMIT -1`）在并发测试里变成随机红灯。反过来，若用 `PROPAGATION_MANDATORY`（§9.1 测试名 `isTransactionMandatory` 显示这才是本意），则它与"`REQUIRES_NEW`"以及"reuse these exact beans / no resource construction"三句互相排斥——现有 bean 的传播行为硬编码为 `PROPAGATION_REQUIRES_NEW`（`OperationsLifecyclePersistenceConfiguration.java:45-51`），要得到 MANDATORY 必须**新建**一个 `TransactionTemplate`，正如 shipped 先例所做（`DefaultEmployeeAdministratorLock.java:24,28-29`：`mandatory = new TransactionTemplate(manager); mandatory.setPropagationBehavior(PROPAGATION_MANDATORY)`）。
- **为什么有问题**: 这不是措辞问题，而是本 slice 的安全前提：Goal Confirmation 的 binding runtime boundary（Control `:26`）与 `REV-02` 都要求"见证与变更发生在同一可写事务/同一物理连接"。plan 用两句互斥的传播描述同时声称满足了它们，并把唯一能同时满足两者、且 shipped 已验证的方案（同一 manager 上新建 MANDATORY template）用"no resource construction"预先禁掉。另外 `REV-02` 原文（Control `:45`）明确指示"Reuse the already-provisioned LO/operations-read datasource family **with a new writable transaction template bound to the same physical pool**"，plan §2.3/§6.1 改成了复用 `operationsLifecycle*` 且不新建 template，属于对已接受修复方向的静默偏离，fix1 矩阵却按 `REV-02` 全量关闭登记。
- **直接证据**: plan `:96` vs `:174` vs `:106,111`；`OperationsLifecyclePersistenceConfiguration.java:45-51`（唯一 writable template = `REQUIRES_NEW`/`READ_COMMITTED`/not read-only）；`DefaultEmployeeAdministratorLock.java:22-30,33-34`（MANDATORY template + `TransactionSynchronizationManager.isActualTransactionActive()` 断言，即 shipped 的"加入调用方事务"范式）；`DefaultOperationsSubjectLifecycleService.java:40-44`（外层用 REQUIRES_NEW template，并在其中断言活动事务与连接绑定）；`JooqOperationsLifecycleRepository.java:16-21,69-82`（`SET LOCAL ROLE` 的作用域是**当前事务**，故跨事务切换必然失效）。
- **影响**: 实施 Agent 跑偏 / 生成错误代码（写出跨连接的"见证"）/ 状态不一致 / 安全边界失效（权限见证与实际变更不在同一事务）/ 后续返工
- **建议改法和验证点**: 单一确定表述：外层命令事务 = 复用 `operationsLifecycleTransactionTemplate`（`REQUIRES_NEW`+`READ_COMMITTED`+writable）；authority port 与 catalog 内的 role 切换 = 在 `operationsLifecycleTransactionManager` 上构造的 **`PROPAGATION_MANDATORY`** template（明确授权这一处"resource construction"，并声明它不是第二个池/凭据族）；删除 §3 中给 authority 的 `REQUIRES_NEW`，删除 §6.1 "writable, and mandatory" 里的歧义。验证点：`isTransactionMandatory` 断言 `TransactionSynchronizationManager.isActualTransactionActive()` 且 `hasResource(manager.getDataSource())`；IT 侧新增/改写断言"见证 SELECT 与 catalog UPDATE/audit append 的 `pg_backend_pid()` 相同"（可复用 `OperationsReadContext.java:76-86` 的 backend-pid 身份断言范式）。

## 8. Planreview 专项 lens 结论

- **Goal-bound minimal design review**: 未发现目标扩张。两路由/一 slice、无新字段/表/角色/迁移、无 draft/product/offer-withdrawal/trial-policy/UI/read-model 工作，均与 Control `:20-32` 对齐；§12 残差全部有去向。`RB2-02/03` 是对**已接受指令**的偏离，而非新增目标。
- **Architecture boundary review**: 端口方向、named interface 归属、`operations_iam → operations_audit` 保留、controller 经 `ObjectProvider` 解析、catalog 不读 `employee_account` —— 结构判断成立；但 discovered-edge 计数被算错（RB2-01）、409 码缺少归属接缝（RB2-04）、web trace 缺少跨端口承载（RB2-05）。
- **Best-practice review**: 与 shipped 先例对齐度高（`subjectlifecycle`/`operations-subject-read` 端口范式、`SET LOCAL ROLE` 断言、`failAfter` 式故障注入、canonical UUID/严格 JSON binder）；偏离点是未复用 `OperationsReadContext` 既有的角色切换/复位/身份断言范式（RB2-08），以及把 fixture 承载强行塞进 IT 文件。
- **Optimal-solution review**: `REV-02` 已经给出被现有代码证明可行的路径（LO 物理池 + 新写 template，同连接双角色已被 `OperationsReadContext` 断言验证）；plan 选择的路径需要额外未证明前提且传播语义自相矛盾（RB2-02/03），因此不是可信备选中的最优解。
- **Overengineering review**: 未见为未来 slice 预埋的抽象；`CatalogSaleLifecycleSemantics`/`Repository`/`Configuration` 三分类与 `activation_consent` 侧同构，规模恰当。唯一"过聪明"处是同时定义 stale 与 conflict 两套分类表（受 `REV-03` 驱动），但缺优先级使其变为不可判定（RB2-07）。
- **Overcoupling review**: 本项目的 CI/POM/guard/digest 锁步本质上是强耦合，plan 只在 §10 做了部分枚举（RB2-06/01）；另一处耦合风险是 audit/Outbox 的 append-only 事实一旦被 §9.2 的"exact arguments"测试写死，就把 RB2-05 的留白固化为契约。建议把该耦合显式化为一张"字面量-旧值-新值-理由"表（§10.2 已对守卫提出，CI 侧对称即可）。

**`fail`**

1. **安全接缝未被证明且自相矛盾**：authority 见证的传播语义在 §3 与 §6.1 互斥（`REQUIRES_NEW` 与"same connection / no second transaction"不可同真，RB2-02），而"该可写身份能进入 `catalog_order_role`"这一 Goal Confirmation 前提被读族 LO 的证据替代、无法在本 slice 内证明（RB2-03）。§13"Blocking open questions: none"因此不成立。
