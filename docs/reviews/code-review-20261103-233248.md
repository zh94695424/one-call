## Findings

### F-01 High: A pre-existing compatible command role can retain elevated attributes, memberships, and grant options

`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:22` accepts an existing `sharing_command_role` after checking only the five tuple values `rolcanlogin`, `rolsuper`, `rolcreatedb`, `rolcreaterole`, and `rolinherit`. It does not reject `rolreplication`, `rolbypassrls`, an unexpected password, unexpected role owners, or any role membership. The role is therefore not required to match the exact attribute/unwired state claimed by the plan. A stale role with `BYPASSRLS` or a login member survives the migration; explicit `SET ROLE` remains possible for a member.

The same gap exists on replay for schema grant options. Line `:44` revokes only `CREATE` on `sharing`, then line `:45` grants `USAGE` without first revoking an existing `USAGE WITH GRANT OPTION`. A compatible pre-existing role can therefore retain the ability to grant sharing-schema usage onward. The migration ends at `:100` without the required role-membership/attribute/ACL postcondition.

The standalone test at `backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:102` exercises only the freshly created role. It does not seed an existing role or run V010 against a stale cluster state, so the new high-risk path is untested.

### F-02 High: Relation-level and PUBLIC ACL residue on cross-module tables survives V010

The only relation-wide `REVOKE ALL ON TABLE` is for the three sharing tables at `backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:39`. For `evidence`, `customer_iam`, `organization_access`, and `subject_number`, V010 revokes schema privileges and then only the named column privileges (`:52`, `:53`, `:54`, `:62`, `:69`, `:70`, `:79`, `:80`, `:81`). `platform` and `audit` receive schema/function revokes only (`:89`, `:90`, `:96`, `:97`).

Those column revokes do not remove an independent table-level ACL. For example, a pre-existing `GRANT SELECT ON evidence.evidence_record TO sharing_role` makes every evidence column readable; the specific column `REVOKE` at `:53` leaves the relation ACL intact. The same construction applies to `customer_account`, organization/membership, subject tables, and any stale PUBLIC/table grant. Third-party grantors can also survive an owner-context revoke. This contradicts the required exact end state and the explicit stale-role/PUBLIC adversarial requirement.

No closing catalog assertion exists after the final `RESET ROLE` at `:100`; successful command execution therefore does not prove that the exact query/command matrices are the only role-effective privileges.

### F-03 Medium: The “exact catalog” evidence was diluted and does not prove grantor, PUBLIC, or complete matrices

The replacement ACL queries in `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5107` join `pg_roles` on the grantee and filter to the two sharing roles. They do not select grantor, and grantee OID 0 (`PUBLIC`) cannot satisfy that join. The previous explicit closed-world check for PUBLIC, grant options, and undeclared grantees was removed (`pa13-implementation.diff:346`), as were the sharing-owner and unrelated-role table/column assertions (`pa13-implementation.diff:449`). The method name still claims owner/PUBLIC exactness, but those properties are no longer directly asserted.

The new standalone tests are much narrower than their names and the accepted contract. `backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:128` and `:139` each execute one row of effective privilege booleans; they do not enumerate namespace, relation, attribute, or procedure ACLs, do not check grantor/grantee/PUBLIC, and do not assert the full 13 query columns, 34 command foreign columns, eight UPDATE columns, or the two-function allow-list. The behavior tests at `:151` and `:163` cover only a small subset of the plan’s required INSERT, lifecycle-update, cross-module, trigger, function, and sequence witnesses.

Existing `PostgresContainerIT` behavior tests still cover much of the positive command lifecycle, so the fresh schema is not wholly untested. However, the required independent exact catalog proof is absent, which is why the stale-state failures in F-01/F-02 remain green under the recorded runtime evidence.
