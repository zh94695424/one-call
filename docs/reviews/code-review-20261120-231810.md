## Findings

### PA39-CR-B-01 — Medium — authority-layer SQLSTATE is reclassified as a terminal domain conflict

- **Entry point / function:** `POST /api/v1/operations/catalog/versions` and
  `PUT /api/v1/operations/catalog/versions/{versionId}/draft` →
  `DefaultOperationsCatalogDraftCommand.execute(Caller, Supplier, Supplier)` and
  `DefaultOperationsCatalogDraftCommand.recover(...)`; root cause is the missing normalization in
  `DefaultOperationsCatalogDraftCommand.attempt(...)`.
- **Exact lines:**
  `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/DefaultOperationsCatalogDraftCommand.java:33`
  (and the identical guard at `:43`), combined with `:50-52` (authority read precedes any catalog lock) and
  `:75` (SQLSTATE is deliberately harvested from `EmployeeAuthorityReadPort.Failure`).
- **Triggering input / scenario:** the runtime login is an ordinary (non-superuser) role and
  `operations_iam.employee_account` is momentarily shielded by an `ACCESS EXCLUSIVE` holder — a maintenance
  `ALTER TABLE`, `TRUNCATE`, `VACUUM FULL`/`CLUSTER`, or a mis-scoped lock. `begin()` has already set
  `lock_timeout = 250ms`
  (`backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/JooqCatalogDraftRepository.java:42`),
  so the authority SELECT at
  `backend/src/main/java/com/onecall/core/operations_iam/internal/employeeauthority/DefaultEmployeeAuthorityReadPort.java:30`
  fails with SQLSTATE `55P03`; `:39-40` rethrows it as
  `EmployeeAuthorityReadPort.Failure(SERVICE_UNAVAILABLE, "55P03")` (the `[0-9A-Z]{5}` shape filter at
  `EmployeeAuthorityReadPort.java:14` accepts it).
- **Actual branch:** `attempt` rethrows the port failure → `execute:32` resolves `state = "55P03"` via
  `:75` → `:33` throws `Failure(CATALOG_DRAFT_CONFLICT)` → `OperationsProblemWriter.write:13-14` → HTTP
  `409` with `code: "CATALOG_DRAFT_CONFLICT"`, title "Catalog draft conflict". For `55P02`/`40001`-class
  authority states, `:34` instead opens a whole second recovery transaction that immediately repeats the
  same failing authority read during the contention window.
- **Expected behaviour:** plan §4.1 step 6 and §6.1 require *unavailable authority* to be sanitized
  `503 SERVICE_UNAVAILABLE`; docs15:205 defines 503 as "a dependency, capacity or **maintenance**
  condition"; docs15:246 pins `create`'s domain set to exactly `NOT_FOUND` + `CATALOG_DRAFT_CONFLICT`, so a
  dependency outage must never be expressed as a catalog conflict. The shipped PA38 owner command already
  implements this barrier explicitly at
  `backend/src/main/java/com/onecall/core/catalog_order/internal/operationscommand/DefaultOperationsCatalogSaleCommand.java:62`
  (`if (failure instanceof EmployeeAuthorityReadPort.Failure) throw new Failure(Code.SERVICE_UNAVAILABLE);`)
  and additionally evaluates `55P02/55P03` **after** typed failures (`:33`), which PA39 inverted.
- **Direct evidence:** the three-file comparison above; `sqlState` walks the cause chain and returns the
  port's state before any `instanceof Failure` test; the plan text itself is self-conflicting (§4.1 step 6
  vs §6.4 "For both commands, SQLSTATE 55P02 or 55P03 … maps to stable CATALOG_DRAFT_CONFLICT"), and §6.4's
  enumeration of the recovery order shows that sentence is about *reacquiring the product advisory lock*,
  not about the authority read. No test exercises an authority-layer `55P02`/`55P03`;
  `DefaultOperationsCatalogDraftCommandTests.recoveryReauthenticatesOnceAndNeverRetriesWrites` only injects
  those states from `repository.create`/`repository.recoverCreate`.
- **Impact:** during routine maintenance DDL on the employee table, a client receives a semantically wrong,
  apparently-terminal `409 CATALOG_DRAFT_CONFLICT` — the response that legitimately means "your content or
  state is not admissible" — instead of a retryable `503`. Operators retry/dedupe on `Problem.code`
  (docs15 §4: `Problem.code` is the only machine branch), so automated callers can abandon valid drafts and
  support can chase a non-existent content conflict. It also inflates load by starting a doomed recovery
  transaction, and breaks the documented PA38 owner-command invariant that authority unavailability never
  crosses the port as a domain code.
- **Safe fix direction:** mirror PA38 — inside `attempt`'s catch, before rethrowing, normalize
  `EmployeeAuthorityReadPort.Failure` to `Failure(Code.SERVICE_UNAVAILABLE)` (or restrict `sqlState` to
  causes produced by repository-executed SQL so port states never reach `execute`). Optionally reorder
  `:33-35` to test `instanceof Failure` first, as PA38 does.
- **Fix risk:** Low. One guard in one file; both shipped commands keep every current mapping because
  domain `Failure` carries no cause (`OperationsCatalogDraftCommand.java:41` passes `null`), so no existing
  409/503/409-stale classification changes. Add one unit case asserting 503 for an authority `55P03`.

- **Entry point / function:** both routes → `DefaultOperationsCatalogDraftCommand.execute` / `.recover`.

- **Direct evidence:** lines above; `grep` confirms no `Logger`/`System.err` in any Operations web class, and

### PA39-CR-B-04 — Low — exact-integer canonical JSON diverges from the frozen docs14 §2.5 number rule on an irreversible stored digest

- **Entry point / function:** both routes → `CatalogDraftSemantics.projection` / `.canonical` →
  `snapshot_sha256`.
- **Exact lines:** `.../CatalogDraftSemantics.java:61` (`MAPPER.writeValueAsString(TreeMap)` holding
  `Long`/`Integer`), `.../CatalogDraftSemantics.java:73` (`node.bigIntegerValue()`), consumed at
  `.../JooqCatalogDraftRepository.java:134`, `:168` and `.../CatalogDraftSemantics.java:113`.
- **Triggering input / scenario:** `priceCents` or a benefit `quantity` above 2^53, e.g.
  `"priceCents":9007199254740993` or `9223372036854775807` (both exercised by
  `OperationsCatalogDraftLifecycleIT.allCommercialMatrixVariantsRoundTripExactly`).
- **Actual branch:** emits exact base-10 JSON (`"priceCents":9007199254740993`) and hashes those bytes.
- **Expected behaviour:** the frozen `docs/14-production-data-model-and-flyway-schema-spec.md:270` defines
  canonical JSON as "RFC 8785-compatible … **ECMAScript-compatible shortest round-trip number
  formatting**", and requires `snapshot_sha256` to be the digest of exactly that canonical form. Strict
  RFC 8785 serialises those two inputs as `9007199254740992` and `9223372036854775808`, i.e. **different
  bytes and therefore different digests** for the same logical projection.
- **Direct evidence:** I independently reproduced the implementation's exact-integer goldens
  (`9007199254740993` → 253 bytes / `685316f46127d05a7feb1bbe2a71b72a89f2d1831749c0379c8364e2df9194cc`;
  `9223372036854775807` → 256 bytes / `7f2381e49689bb4f9fa57035224b302e378b8491d689fe78d1f3b333f93f674b`) confirming the encoder is lossless-integer, not IEEE-754. The deviation is deliberate and
  authorized by plan §5.1 ("the RFC-compatible rule here is sorted-key, shortest exact integer JSON, not
  lossy IEEE-754 coercion"), and traces to the accepted plan-review closure `PA39-PLAN-REV-B-03`
  (`docs/gateflow/project-execution-control.md:39`). docs14 itself was not amended because it is frozen.
- **Impact:** none at runtime today. Because `snapshot_sha256` is permanent and a mismatch is a permanent
  `503` (`.../CatalogDraftSemantics.java:113`), any *future* component that canonicalises the same eleven
  members under the literal docs14 rule (export, cross-check, reconciliation job, the trial-policy analogue)
  will compute a different digest for every large-integer draft and reject it as corrupt data.
- **Safe fix direction:** route to the docs/Architecture owner to record the exact-base-10 bigint exception
  in docs14 §2.5 (or a catalog-specific note) and cross-reference it from `CatalogDraftSemantics`, so the
  irreversible digest has one written authority. Do not change the encoder or the stored hashes.
- **Fix risk:** documentation-only, zero runtime risk; changing the encoder instead would corrupt every
  already-committed `snapshot_sha256` and must not be done.

## Adversarial scenarios executed (all correct as shipped)

- **JSON strictness:** duplicate keys at root/benefit depth, missing fields, unknown fields, non-object root,
  `{} {}` and `<json> true` trailing tokens, `{`, empty body, UTF-8 BOM by first byte, malformed UTF-8
  (`C3 28`), 8193-byte and truncated bodies, string/float/exponent/boolean numerics, uppercase/braced/spaced
  UUIDs, `null` except `priceCents`, every schema-external replace member — all 422 before provider and
  authority (`OperationsCatalogDraftWebTests.structuralValidationPrecedesProviderAndAuthority`,
  `OperationsCatalogDraftLifecycleIT` line 63 asserts zero `employee_account` reads). Nesting bombs are
  bounded by the 8192-byte cap plus Jackson's default depth limit. A BOM after leading whitespace survives
  the first-byte guard but fails the strict UTF-8 tokenizer path.
- **Precedence:** concealment → 401 → media grammar → grammar 422 → provider 503 → owner matrix 422 →
  authority 403/503 → 404 → persistence shape 503 → non-DRAFT 409 → legacy member set 409 → recognized
  corruption/bad hash 503 → WITHDRAWN 409 → revision decisions. Each boundary has at least one assertion, and
  `validateStored`'s `VALIDATION_FAILED → 503` conversion (`.../CatalogDraftSemantics.java:116`) prevents
  owner-internal grammar faults from leaking as client 422.
- **Canonical ordering:** UTF-16 root order `audience, benefitLines, billingCycle, channels, currency,
  grantIntervalMonths, installments, offerType, priceCents, productId, versionNo` and benefit order
  `entitlementType, grantIntervalMonths, quantity, validityDays` verified independently; request-array
  reordering and physical row order (SQL `COLLATE "C"`) canonicalise equal, duplicates are invalid not equal.
- **Exact integers:** `9007199254740993` and `Long.MAX_VALUE` survive binder → `Long` → bigint → jsonb
  `numeric` → response and produce distinct adjacent hashes; `positiveLong`/`nonNegativeLong` reject
  `2^63` and negatives via `bitLength` bounds, and replay-successor comparison is widened
  (`.../JooqCatalogDraftRepository.java:163`) so `expectedRevision = Integer.MAX_VALUE` cannot overflow.
- **Create replay/conflict:** equal never-published draft at any positive revision → 200 with byte-identical
  body, zero DML/audit/token change; changed projection, ACTIVE/OFFSALE/published, or legacy snapshot → 409
  with zero writes; zero-row insert → exactly one bounded locked reread (200/409/503), never a second INSERT.
- **Replace applied replay / stale / conflict:** `r == e+1` with exact `P_requested` → 200 and no UPDATE;
  `r == e+1` unequal, `r > e+1`, `r < e` → 409 `CATALOG_DRAFT_STALE_VIEW`; non-DRAFT precedes both; recovery
  at `r == e` → 503, never a fabricated 200 or a second application.
- **Immutable benefits/channels:** no INSERT/UPDATE/DELETE on `catalog_benefit_line` and no offer

  duplicate snapshot channels, malformed offer token, non-microsecond `created_at`, row/snapshot disagreement

- **Same-connection role switching:** `assertIdentity` re-checks login, expected role, backend PID,
  `txid_current()` and `transaction_read_only = off` on every transition, plus physical-connection identity

  audits an obsolete snapshot; `55P03` → 409 with rollback and no retry.

## Open Questions

1. Should the authority layer be exempt from §6.4's blanket `55P02/55P03 → 409` sentence (PA39-CR-B-01)?
   The plan supports both readings and PA38 chose 503; Controller ratification of one reading would let the
   code and text converge.
2. `docs/15:240` requires every operation to expose `RATE_LIMITED` (429) and the frozen OpenAPI documents it
   at 2326/2406, yet the pinned eight-value `Code` enum has no `RATE_LIMITED` while the sibling PA38 port
   does. Was 429 intended to stay reserved for a future platform limiter rather than this port, as the
   `OperationsCatalogDraftWebTests`/`BoundaryTests` assertions imply?
3. `Products` have no foreign key from `catalog_order.catalog_version.product_id`, so `readProduct` is the
   only existence guarantee and `recoverCreate` deliberately omits it. Is the absence of an FK (and the
   resulting orphan-row possibility from non-cooperating writers) an accepted A0 design fact for this slice?
4. `snapshot` has no `updated_at`/lineage column, so a row rewritten by a future non-cooperating writer
   keeps only its digest for detection. Is digest-plus-row-agreement considered the complete forensic record
   for `snapshot_sha256`, or does an owner want provenance beyond `created_by_employee_id`?

## Residual Risk

- **Test gap (specific, evidence-backed):** `OperationsCatalogDraftWebTests:69` probes the PUT-shaped
  concealment paths (`BASE + "/x/draft/"`, `BASE + "/x;bad/draft"`, `BASE + "/x%2f/draft"`,
  `BASE + "/x/other"`) with **POST** requests. Those probes therefore 404 through the POST equality branch
  and would stay green even if the PUT regex `[^/;%]+/draft` were accidentally widened. The CI JAR smoke
  covers only `…/draft/extra` for PUT. Recommend re-issuing those four paths with PUT in the same method.
- `GET/PATCH/DELETE/HEAD/OPTIONS` are asserted only against the collection path; the
  `…/{versionId}/draft` template's non-PUT concealment is not directly asserted (traced safe: `draft`
  requires `PUT` and `read` never lists this template).
- `validateCommercial`'s matrix sweep always uses `installments = 1`, so a `SUBSCRIPTION` with a
  non-positive installments value is only covered by the binder's grammar guard, not by an owner-level
  negative case; `validateStored`'s `VALIDATION_FAILED → 503` conversion is covered only indirectly.
- `hashtextextended` single-key advisory locking is inherited from PA39 plan §6.2 and PA38; a 64-bit hash
  collision between two product keys would serialize unrelated products, and the lock is cooperative only
  (non-cooperating direct writers can interleave). Accepted pre-existing design; no PA39 change.
- Commit-time connection loss after a durable create/replace yields 503 although the facts committed; the
  natural-key/successor replay paths make the client retry safe, but the observable status is ambiguous.
- No component in the product logs sanitized fault causes, so an owner-side defect is invisible beyond its
  HTTP status and `traceId` (see PA39-CR-B-02).
- The feature stays fail-closed unless `persistence` plus `onecall.operations-subject-read.enabled=true`
  plus the missing production employee-verifier/credential adapters are all supplied; only MockMvc, JAR-smoke
  401/503/404 and PostgreSQL container tests prove the end-to-end path, never a production deployment.
- Runtime evidence reproduces the plan's numbers but remains a single-host PostgreSQL 16.16 container on
