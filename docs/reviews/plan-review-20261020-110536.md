# Plan Review — cross-channel-alignment

## Reviewed target and scope

- Target: `docs/gateflow/cross-channel-alignment-plan.md`, baseline `f6ea510bb23c98fa04aee91acbdb3200dc3f70f4`.
- Binding Goal Confirmation: `docs/gateflow/cross-channel-alignment-control.md`; design source: `docs/09-business-activation-and-lean-admin.md`.
- Review gate only. Inspected the three prototype sources, their QA scripts/runners and READMEs, plus the installed miniapp renderer's srcdoc/CSP behavior. No implementation, QA runner, generator, commit, push or PR action was performed.
- Scope tested: rule-first sequencing, three-slice/gate cost, standalone packaging, shared ownership and coupling, demo employee semantics, catalog version invariants, claim/evidence privacy, trial idempotency, payment/entitlement separation, offline support and regression preservation.

## Assumptions tested

| Assumption / lens | Adversarial result |
| --- | --- |
| Goal-bound minimal design | The plan maps to the confirmed order and does not revive real backend, payment, IVR, finance workflow or production IAM work. Six admin entries and demo-only credential behavior are bounded prototype decisions, not claims of production security. |
| Architecture boundary | One narrow executable contract is justified by three conflicting local catalogs and state vocabularies. Employee/session authority and existing evidence-preservation statuses remain outside that commerce contract. |
| Best practice / state machine | Trial uniqueness, append-only claim, immutable capture identity and paid-versus-issued transitions are mostly explicit, but the trial-consumption API does not bind the confirmed session to the supplied subject; see PR-001. |
| Optimal solution / overengineering | A generated inline module is more machinery than static fixtures, but it addresses observed drift while preserving `file://` operation. The miniapp renderer embeds the fragment into sandboxed srcdoc and its CSP permits inline script but not a reliable relative `file:` dependency, so direct shared script loading is not a credible alternative. |
| Overcoupling | The generator changes only bounded markers and each UI keeps an independent in-memory clone. Cross-surface snapshots are QA transport, not live synchronization. This is acceptable provided the hooks remain explicitly demo/review-only and loaders enforce structural and referential validation. |
| Slice/gate sequencing | S1 rules/package, S2 admin, S3 clients+IVR followed by cross-surface validation follows the user-confirmed sequence and stays at three behavior slices. S3 is large, but its ordered checkpoints avoid another full gate; no fourth slice is required by current evidence. |
| Standalone packaging | The miniapp source is a fragment rendered into `sandbox="allow-scripts"` srcdoc; inserting the module before its application script is feasible and remains comfortably below the renderer's 1 MB fragment limit. Generated preview equality must be checked by module version/hash or evaluated value, not raw byte equality against escaped srcdoc. |
| Catalog/version invariants | Draft uniqueness, immutable published content, stale fingerprint rejection, retirement of prior ACTIVE version and frozen order snapshots are specified. Demo prices are clearly non-production and historical samples remain snapshots. |
| Claim/evidence/privacy | Pre-verification history remains hidden; conflict/recycled-number paths block association; claim does not set identity or rewrite evidence. The remaining cross-subject session gap is material because it can defeat those otherwise-correct invariants. |
| Trial/payment idempotency | Subject+campaign trial uniqueness and repeat-event no-ops are explicit. UNKNOWN/PAID/CLOSED and PENDING/FAILED/ISSUED are separate, and IVR cannot create orders. |
| Offline support | `configured:false` and null contact prevent invented phone/mail/WeChat details, receipts, SLA or guaranteed eligibility. Existing online invoice/consultation submission is expressly removed. |
| Regression/QA feasibility | Keeping old UI assertions during S1 is feasible because S1 only injects an unused module. However the current Web runner masks a failing Node QA process, so S1 cannot use that runner as pass evidence until the runner is fixed; see PR-002. |

## Findings

### PR-001-未修复-[高]-取证扣量未约束会话主体与额度主体一致
- **状态候选**: `accepted-candidate`
- **位置**: §3.2 `consumeTrial` contract、§3.3 transition 6、S1 assertions、S3 IVR failure assertions
- **问题类型**: 状态机漏洞 / 契约缺失 / 数据一致性与隐私风险
- **当前写法**: `consumeTrial({subjectId,sessionId,eventId,seconds},now)` 同时接受 `subjectId` 与 `sessionId`，要求正整数、剩余额度、未过期、未暂停和已确认会话，但没有要求 `session.subjectId === subjectId`，也没有规定从已确认会话派生唯一主体。现有测试清单同样没有跨主体错配用例。
- **反例/失败场景**: 会话 `S-A` 已为主体 A 按键确认；主体 B 恰好有可用试用额度。调用方把 `sessionId=S-A` 与 `subjectId=B` 组合提交。按当前契约，实施可合法地用会话 A 通过“已确认”校验、用主体 B 通过额度校验，继而扣减 B 并生成 `subjectId=B, sessionId=S-A` 的证据元数据。
- **为什么有问题**: Goal Confirmation 和设计真源要求证据持续绑定产生时的稳定业务主体、会话与实际采集事实，认领也不得改写归属。该错配会同时破坏试用唯一性、证据归属和后续认领隔离，且属于生成实现时无法靠 UI 约定补足的领域约束。
- **直接证据**: Plan §3.2 把 `subjectId`、`sessionId` 都列为输入；§3.3(6) 只列出额度/状态/数值校验；S1 与 S3 仅覆盖重复、过期、耗尽、暂停、未确认等失败路径。`09` §3.3 明确证据始终引用产生时的 `subjectId`、会话、主叫、授权快照与实际采集事实。
- **影响**: 试用额度误扣、跨主体证据元数据污染、认领后错误展示历史记录，导致状态不可置信并形成隐私边界破坏。
- **建议改法和验证点**: 优先从已确认 `IVRSession` 派生 subject，移除调用方可独立指定的 `subjectId`；如保留该参数，必须在任何写入前强校验已解析的 `session.subjectId` 与输入完全一致。同步要求 evidence→session→subject 引用一致，并在 loader 中检查。增加 A 会话+B 主体、未解析会话和被替换主体三类测试，断言 grant usage、evidence、sequence、processedEvents 均不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-[中]-S1 使用会吞掉失败退出码的 Web QA runner 作为验收证据
- **状态候选**: `accepted-candidate`
- **位置**: S1 Validation（plan line 159）、S3 Validation（line 181）、`web-prototype/qa/run.ps1`
- **问题类型**: 测试缺口 / 不安全 sequencing / review 不可验收
- **当前写法**: S1 要求运行三个现有 QA runner，并以它们证明生成模块没有引入 CSP/page error；但当前 Web runner 最后一条命令只是 `node qa.js`，没有检查 `$LASTEXITCODE`。计划直到 S3 才要求 Web runner 对非零 QA 退出抛错。
- **反例/失败场景**: S1 注入的模块导致 Web 页面解析或运行错误，`qa.js` 捕获后设置非零退出码；`run.ps1` 仍正常结束，外层 `powershell -File` 报告成功，于是 S1 被错误验收并进入后台迁移。
- **为什么有问题**: S1 正是首次改动三个源文件和构建路径的阶段，不能把其 Web 回归保障延迟到 S3。旧断言本身可以继续运行，问题是 runner 不能可靠传播结果。
- **直接证据**: `web-prototype/qa/qa.js` 末尾以 `process.exitCode = 1` 报告失败；`web-prototype/qa/run.ps1` 在 Node 调用后没有 `$LASTEXITCODE` 检查。只读 shell 探针显示子 Node `exit(7)` 时，当前 Windows PowerShell 包装进程退出码仍为 `0`。Plan S3 已承认需要补上该检查，但 S1 先依赖了旧 runner。
- **影响**: S1 可在 Web 实际损坏时产生假绿，后续 S2/S3 建立在未经验证的生成基线上，review 证据失真并增加返工。
- **建议改法和验证点**: 把 Web runner 的非零传播修复纳入 S1 允许改动和完成条件，行为与另外两个 runner 对齐；或在 S1 gate 直接执行 `node web-prototype/qa/qa.js` 并检查退出码。保留旧行为断言不变，另用可控非零命令验证包装层确实失败。S3 只保留回归检查，不再把这一基础修复延后。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- `loadReviewSnapshot` 的“checks known IDs/references”应明确为“校验导入快照内部的结构、枚举和引用完整性”，还是“只允许预置 fixture ID”。S3 会导入刚发布的版本、动态主体、订单和权益；若解释为固定 ID allowlist，计划中的跨端序列将被自身 loader 拒绝。该问题可在修订契约时澄清，不要求扩展生产安全目标。
- `businessSnapshot()` / `loadReviewSnapshot()` 应继续只存在于明确标注的本地 demo/review 构建中。当前仓库没有生产构建，因此不是本 work unit 的 blocker；若这些 HTML 后续被复用为发布物，需单独决定移除或构建时关闭 hooks。

## Residual risks and suggested tracking destination

- `assigned to later work unit`: 真实员工鉴权、凭据投递、后端权限和安全审计；owner 为 backend/security。原型必须持续标注 DEMO，不以本地六位码证明安全性。
- `assigned to later work unit`: 可信主叫、号码回收裁决、认领凭证和历史证据访问策略；owner 为 product/security/backend。
- `assigned to later work unit`: 并发试用预占、持久化唯一键、可靠录音时长、挂断、支付回调与权益事务；owner 为 IVR/payment/backend。
- `requiring explicit user decision`: 正式价格/权益、续购叠加、退款资格/SLA、真实客服联系方式与工作时间；继续在 `docs/10` 标记待确认，原型不填造数据。
- `fixed in current slice (planned)`: 生成模块漂移由 bounded markers、`--check` 和 hash/version 校验覆盖。Miniapp preview 中 srcdoc 会 HTML 转义，不能把原始文件字节相等误当验收条件。
- `covered by later approved slice`: S1 后旧 UI 仍展示旧语义是明确过渡状态，分别由 S2/S3 迁移；控制文档不得提前把 G1/G3/G4/G5 标为全端完成。
- `existing external-state blocker`: 仓库无 Git remote；本地实现/审查可继续，但不能宣称 push、PR 或 final closeout 通过。
