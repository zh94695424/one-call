### 04-未修复-中-cursor 把 32-byte filter digest 放进明文 header，而仓库里已有把同一 digest 放进密文、语义完全等价的 baseline
- **位置**: §6（envelope binary grammar 与 AAD 定义）；影响 §8 B1–B12、G11/G16
- **问题类型**: 非最优方案 / 最佳实践偏离（minimization）
- **当前写法**: envelope = version, key-id length, ASCII key-id, **32-byte filter digest**, nonce,
  28-byte anchor ciphertext, tag；AAD = length-prefixed purpose + endpoint + sort + 整个 header
  （含 digest）；并规定「changed header → CURSOR_INVALID，valid envelope + different filters →
  CURSOR_FILTER_MISMATCH」。
- **反例/失败场景**: 已有的 PA33 baseline `OperationsSubjectCursorCodec.java:15–23,52–62,66–68` 把
  digest 放在**明文密文内部**（60-byte plaintext payload = 28-byte anchor + 32-byte digest），header 只含
  version/key-id，并且得到与计划要求的完全相同的两种分类：篡改 header/key-id/密文 → GCM 失败 →
  400 CURSOR_INVALID；合法 envelope 换 filter → 解密成功后 constant-time 比较失败 → 400
  CURSOR_FILTER_MISMATCH；ring 缺失 → 503。也就是说计划的「不要把 request digest 当 AAD，否则把 changed
  filters 误判为 tamper」这个约束，baseline 早已用另一种形式满足，而不需要把 digest 暴露成明文字段。
  代价面：cursor 一旦进入访问日志、代理、浏览器历史或 IT 工件，明文 digest 就承诺了
  subjectId/callId/taskId/status 的 **presence 组合**，并对可猜测值域（例如 1–64 字符、来自小集合的
  public `taskId`，或已知 subject 的情形）提供离线确认 oracle。同时它引入了第三种 envelope 形状
  （subject：密文内含 digest；activation：无 digest；ivr：header 内 digest），为任何后续 Operations cursor
  工作增加第三种心智模型。
- **为什么有问题**: 与计划 §1 自己的「Reuse beats a second pool, alternate ring, generic query abstraction
  or extra named interface」和 §6「no plaintext … enumerable identity」精神相悖；docs/17:7/11/58 的
  minimization 与 cursor 先例都不要求把承诺暴露到明文；这是一个没有当前收益的暴露面扩张。
- **直接证据**: 计划 §6；`backend/src/main/java/com/onecall/core/operations_iam/internal/subjectread/
  OperationsSubjectCursorCodec.java:15–23,52–62,66–68`；`internal/activationread/
  OperationsActivationCursorCodec.java:22,80–92`；`docs/17-production-security-design-spec.md:11,58`。
- **影响**: 数据最小化回退 / 与冻结安全文档先例偏离 / 后续 cursor 工作的格式碎片化 / review 需要额外论证。
- **建议改法和验证点**: 采用 baseline 形状——payload 明文 = anchor(28) + digest(32)，整体 AES-GCM 加密；
  AAD = purpose + endpoint + sort + header(version, key-id)；digest 校验仍用 constant-time 比较。§6 文本、
  B1–B12、G11/G16 的**语义**不变（invalid / mismatch / 503 三类），只需把「digest 在 header」改为「digest
  在密文内」，并新增一条断言：游标明文部分不含任何 filter 承诺字节。若坚持 header digest，则必须在 §6
  说明为何放弃既有 baseline 以及暴露 32-byte 承诺的可接受性。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 05-未修复-中-无索引谓词与 PA33/PA34 共用 4 连接池的可用性耦合被 residual 错标成「child chains」
- **位置**: §5.1（index expectations）、§5.2（decision/evidence OR 谓词的 index 说明）、§12 residual 第 5 行「Large child chains / five-second read budget」
- **问题类型**: 过度耦合 / 并发恢复风险（availability coupling）
- **当前写法**: 计划诚实地说明「No frozen index guarantees a global (created_at DESC,id DESC) seek or
  status-only lookup」与「There is no dedicated decision or evidence session_id index; the OR predicates can
  scan」，但把容量风险作为 residual 时只写成「Large child chains / five-second read budget」，并禁止任何新索引。
- **反例/失败场景**: 冻结 schema 确实如此：`V005:147–152`（inbound 只有
  `(caller_number_hmac,status,created_at DESC)` 与 `(subject_id,created_at DESC)`，都不含 `id` 决胜）、
  `V005:386` `ix_ivr_decision_call_time = (call_id, decided_at)`、`V008:173–179`
  `(subject_id,created_at)/(call_id)/(status,created_at)`——`ivr_decision.session_id` 与
  `evidence_record.session_id` 无索引。于是每次 detail 至少包含一次针对两个 append-only 表的
  session-side 扫描/OR 合并，每次无 subjectId 的 list 需要全表 top-N 排序。而这些查询跑在 PA33 建立的同一个
  池上：`maximumPoolSize(4)`、`connectionTimeout(3000)`、`statement_timeout 2000ms`、tx timeout 5s。
  四个并发 PA35 慢读就能让**已上线**的 `listOperationsSubjects` / `listOperationsActivations` 在 checkout
  3s 后失败——即 PA35 的一条慢查询把回归投射到 PA33/PA34 的用户可见行为上，而 §12 的 residual 措辞（child
  chains）不会让容量 owner 识别出真实成本来源与共享池耦合。
- **为什么有问题**: Control 要求复用现有 pool/context（计划也正确禁止第二池和第二 DSL），因此这个耦合是计划的
  既定结果而非可回避实现细节；plan §5.1 只要求「Record representative EXPLAIN evidence … without asserting
  a planner-specific index choice」，这不能证明共享池下的排队影响。风险本身成立，但当前写法把它错误归类，
  等于 review 后没人跟踪真正的问题。
- **直接证据**: `backend/src/main/resources/db/migration/V005__ivr_task_session_call.sql:147–152,386`；
  `V008__evidence_media.sql:173–179`；`OperationsSubjectReadPersistenceConfiguration`
  （`setMaximumPoolSize(4)`, `setConnectionTimeout(3000)`）；`OperationsReadContext.enter()`
  （`statement_timeout 2000ms`, `idle_in_transaction_session_timeout 5000ms`）；计划 §5.1/§5.2/§12。
- **影响**: 后续返工 / 已上线 surfaces 的用户可见降级 / 风险后移且跟踪目标错位。
- **建议改法和验证点**: 在 §12 增加独立一行：「无索引 session-side OR 谓词 + 全局 `(created_at,id DESC)` 排序
  与 PA33/PA34 共享 4 连接池 / 2s statement / 5s tx」，owner = Backend/Database + Capacity，destination =
  `docs/18-production-capacity-and-deployment-spec.md` 的 `DailyVolume`/rowsPerDay 模型，并要求 implementation
  report 的 EXPLAIN 附录写明所假设的 `inbound_session`/`ivr_decision`/`evidence_record` 行数与实际执行计划；
  明确「超限即 sanitized503、绝不部分返回」是可观测降级路径，同时保持「不加索引/不加 V018/不改池参数」。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
