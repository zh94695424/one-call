- **入口/函数**: 普通短信绑定页 `phoneSms` → `data-phone-submit` click handler → `B.activateService` → `provisioningHtml` → `trialHomeHtml`。
- **文件(行号)**: `prototype/onecall-miniapp-pages.html:4024-4025,4163-4165,4379-4381,4441,4904-4914`；共享契约 `shared/onecall-business.js:204-222`。

- **实际分支**: 提交只把 `data-binding-mask` 记入 `pendingBinding`。开通对象由 `purchaseSubject()` 选择，既未使用已验证号码查找/创建对应主体，也未把 `review.subjectId` 更新到开通成功的主体；调用返回值未检查，随后无条件 `show()` 成功页。结果页使用 `purchaseSubject()`，试用页另用 `currentSubject()`。
- **预期行为**: 验证号码、同意记录、activation、首次 trial 和开通结果必须关联同一当前账户主体；后续试用页继续显示该主体。仅在共享 helper 成功后进入成功页，失败应保留可操作的错误状态。
- **实际行为**: 页面宣称 `186 **** 4471` 已完成验证、同意和开通，显示 `05:00`；canonical state 却新增 `ACT-001001` 和 `TRIAL-001002` 到 `MINI-ACCOUNT-001`（`138 **** 6208`），没有 4471 主体。继续后页面显示未实名、剩余 `04:00`、已用 `01:00`、原发放 `05:00`，来自仍被选中的未认领 IVR 主体 `SUBJ-REPEAT-001`（`139 **** 7712`）。
- **直接证据**: 初始 `review.subjectId` 指向 `SUBJ-REPEAT-001`；`purchaseSubject()` 在其不属于当前账户时 fallback 到本账户非 IVR seed（4024-4025）。4441 的表单和按钮指定 4471；4908-4909 却仅传 `purchaseSubject().id`，没有消费验证号码，也丢弃 helper 返回值。4380-4381 与 4164 分别从两个主体选择函数读 trial。独立浏览器操作与导出的 canonical IDs/号码/额度逐项一致。

### S3-02-未修复-[中]-个人权益与账户计数读取全局集合，包含其他账户事实

- **入口/函数**: Web 个人“套餐与权益” `rightsPage`；Mini“我的” `profileHtml`。
- **文件(行号)**: `web-prototype/evidence-hub.html:2110`；`prototype/onecall-miniapp-pages.html:4388`。正确账户过滤对照：Web `:2193`、Mini `:4385`；canonical entitlement owner：`shared/onecall-business.js:404`。
- **输入场景**: 使用合法 canonical business snapshot，其中当前账户仍为 `ACCOUNT-DEMO-001`，但另一个已验证/开通主体属于 `ACCOUNT-OTHER`。通过共享 `createOrder`、PAID payment callback 和 `issueEntitlements` 为后者生成一笔个人进阶版年付权益，再经公开 local review hook 正常导入两端。
- **实际分支**: Web 个人权益直接显示 `business.entitlements.length` 并 map 全集合；Mini profile 直接显示 `business.orders.length` 和 `business.entitlements.length`。两者均未应用已有的 `accountId/ownerAccountId` ownership。
- **预期行为**: 当前账户的付费权益明细和订单/权益计数从同一账户范围的集合派生；同一账户多号码应按既有 account ownership 汇总，其他账户记录不计入。

- **直接证据**: Web 2110 的 length/map、Mini 4388 的两个 length 均直接作用于全局数组；Web 2193 和 Mini 4385 同一状态下的订单读取按当前 `accountId` 过滤。共享 helper 404 明确写入 `ownerAccountId:order.accountId`，完整订单/权益关联通过 snapshot validator，故不是依靠非法记录触发。
- **影响**: 合法多账户 handoff 下个人读模型错误展示其他账户的套餐事实并夸大自己的订单/权益，且列表与概览互相矛盾。此 finding 限于当前本地原型的业务归属展示，不将 review hook 或其全局 snapshot 当成生产鉴权漏洞，也未声称泄露原始录音。

- **修复风险（低/中/高）**: 低；局部读模型过滤，重点防止误按单一 subject 过滤而丢失同账户其他号码的权益。

### S3-03-未修复-[中]-Web 季付/年付缺少每期额度、发放间隔和期数的购买展示

- **入口/函数**: Web 套餐目录 `plansPage` → `checkoutPage` → `orderDetailPage`，共用 `offerRights`。
- **文件(行号)**: `web-prototype/evidence-hub.html:1626,2171,2173-2176,2195`；catalog `shared/onecall-business.js:98-99`；规则 `docs/10-cross-channel-rules.md:51-52`；已接受 plan `docs/gateflow/cross-channel-alignment-plan.md:87`。
- **输入场景**: 当前个人账户在 Web 选择基础版季付或年付，并阅读确认订单及创建后的历史订单详情。
- **实际分支**: `offerRights` 只输出 `rights` 原始四项数值；目录、确认、冻结快照和历史详情均复用此 renderer，未读取 `installments` 或 `grantIntervalMonths`。目录的自由文本 description 笼统提到按月，确认和历史详情则连该描述也没有。
- **预期行为**: 按共享当前/冻结商品显示每期额度、发放间隔及总期数。季付 3 期、年付 12 期，每 1 个月发放一次；用户确认及之后复核时能辨认 60 分钟等是每期额度。该展示契约不要求在本 slice 实现生产 recurring fulfillment scheduler。
- **实际行为**: 独立打开年付确认页，只显示 `PERSONAL_BASIC_ANNUAL-V1`、365 天、¥390.00 和“录音 60 分钟 / AI 60 分钟 / 存证 20 项 / 存储 5 GB”；全页没有每期、按月或 12 期说明。季付目录和确认同样没有 3 期说明，历史详情继续使用同一个丢失 schedule 的 renderer。
- **直接证据**: catalog 98-99 分别提供 `installments:3/12`、`grantIntervalMonths:1` 和同一 60/60/20/5 rights；docs10 51-52 定义为按月分期权益，plan87 将这两个字段纳入共享商品 schema。Web 1626 只消费 `rights`；2175-2176 和2195未显示 schedule。Mini 的 `grantText`（`prototype/onecall-miniapp-pages.html:4248`）至少显示按月和总期数，进一步确认当前两端展示已发生差异。浏览器可见文案和人工打开的套餐截图印证遗漏。
- **影响**: 购买确认与历史购买快照没有完整表达分期权益，用户无法区分全年总量与每期额度；共享字段虽已冻结，展示契约仍发生语义丢失。
- **建议改法和验证点**: 让 Web 从所选 offer 或历史 `order.snapshot` 渲染每期 rights、`grantIntervalMonths` 和 `installments`，单次商品使用相应单次语义；不要把可配置 interval 硬编码为“每月”。增加季付、年付及非默认 interval 的目录→确认→历史详情断言；修改 live catalog 后历史订单仍展示旧 schedule。现有 Web QA 399-422 覆盖季付价格/版本/支付，但没有 schedule 断言，也未覆盖年付此语义。
- **修复风险（低/中/高）**: 低；展示修复，需统一当前商品与冻结历史快照的来源。
- **严重程度（低/中/高/严重）**: 中。
