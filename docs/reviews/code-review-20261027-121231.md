Adversarial passes performed and not converted into findings:

- V001 function/constraint tracing: every S2 assertion was walked against the real SQL. `idempotency_begin` (`V001` L100-171) produces exactly `NEW` (insert, revision 1, null results), `REPLAY` (COMPLETED + matching fingerprint, stored fields, revision 2), `CONFLICT` (COMPLETED + changed fingerprint, all-null row, no write), and raises `IDEMPOTENCY_INCOMPLETE` for a committed `NEW` row (L169). `idempotency_complete` (L173-283) produces `COMPLETED` once, `ALREADY_COMPLETED` on same hash, and `IDEMPOTENCY_CONFLICT` on hash mismatch or revision mismatch; the denylist (L200-227) and argument guards raise `IDEMPOTENCY_ARGUMENT_INVALID`. `outbox_append` (L285-373) returns the original id on same domain/dedupe/hash, raises `OUTBOX_DEDUPE_CONFLICT` on hash mismatch and `OUTBOX_PAYLOAD_INVALID` for missing payload, bad envelope and protected plaintext. All test expectations match these branches; no test asserts a behavior V001 does not implement.
- False-positive assertions: result-snapshot equality (`PostgresContainerIT.java` L275, L296-298, L311, L321-323, L475-477, L547) compares full record snapshots read by fresh superuser connections after conflict probes; the snapshots include all 12/14 columns including timestamps, so a hidden write would break equality. `expectFailure` (L840-857) asserts SQLSTATE `P0001` plus the stable error-code substring and always rolls back in `finally`, so aborted-transaction state cannot leak into later statements.
- Transactional state after failures: every failure probe runs inside a dedicated connection/transaction that is rolled back before close; every success path commits explicitly only where the contract requires durability (first result, alertable `NEW`, replayable Outbox). The stale-revision probe (L325-340) and both rollback probes (L396-424) assert zero method-local rows afterward.
- Row-key isolation in the shared container: all keys are UUID-suffixed and every count/read is scoped to `(scope, idempotency_key)` or `(event_domain, dedupe_key)`. The intentionally committed alertable `NEW` row and replayable Outbox row cannot satisfy or break another method's scoped assertions; no append-only table is truncated; the S1 inventory test does not assert global row absence.
- Lock-wait race determinism: in both races the winner holds an uncommitted unique-key row; the loser's `INSERT ... ON CONFLICT DO NOTHING` parks on the in-flight speculative entry (`wait_event_type = 'Lock'`). The main thread does not proceed on sleep alone: `awaitBlockedBackend` (L626-643) requires an observed blocked backend (`application_name` + `state='active'` + `wait_event_type='Lock'`) within 15 s and fails the test otherwise. Bounds are layered: loser `statement_timeout` 20 s > 15 s detection; future timeout 30 s > 20 s statement timeout, so a stall fails closed with first-failure evidence instead of hanging. Winner commit yields loser `REPLAY` (revision 2, winner result fields); winner rollback yields loser `NEW` (revision 1), both with exactly one final method-local row. `enable_seqscan = off` + `EXPLAIN (FORMAT JSON)` in `assertAlertIndexUsed` (L814-831) is necessary (a tiny test table would otherwise seqscan and the plan assertion would be vacuous or flaky) and robust enough (substring check on the plan JSON, not an exact deparse string; the partial index is the only path satisfying the `status='NEW'` filter plus `created_at` ordering once seqscan is disabled).
- Exceptional future paths: on any failure between `executor.submit` and `awaitFuture` (lock-detection failure, assertion failure, commit failure), the `finally` blocks call `executor.shutdownNow()` and try-with-resources closes both connections; closing the loser connection terminates its backend even if the future thread is mid-query, and the loser's `statement_timeout` bounds the wait. This is a failing-test path only and is bounded; it cannot hang the suite or leak a live backend past JVM exit. No happy-path leak exists: both futures complete and both connections are committed/closed deterministically.
- Connection and executor closure: every helper opens connections via try-with-resources or explicit close in `finally`; each race uses one single-thread executor created per race and shut down in `finally`.
