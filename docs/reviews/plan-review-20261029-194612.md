### PR-002-未修复-[高]-V004 孤立 consent 成功探针仍被安排在 latest migration 之后执行
- **位置**: Revised plan `§7.1` step 2 and `§7.2` renamed-method instruction (`docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:442-455`)
- **问题类型**: 不可直接实施 / 测试缺口 / 状态机漏洞
- **当前写法**: While at target 004, run the transactional orphan-`purchase_consent_id` insert “in the renamed `v004ForeignKeyAndStagedConsentFkBackstops` method”; only then migrate to 005. The method itself is a JUnit `@Test` method.
- **反例/失败场景**: In the actual test lifecycle, `@BeforeAll startContainerAndMigrate()` stages a migration prefix and then migrates latest before JUnit invokes any `@Test` method. If the implementation follows the plan literally, the renamed test runs against V007 with the FK already installed, so the random missing consent reference is rejected and the required V004-success assertion fails. If the implementation instead silently omits or relocates the operation, the suite passes without proving the accepted V004 behavior.
- **为什么有问题**: The accepted finding specifically requires preserving V004's executable behavior at the prefix where no consent FK exists, with rollback before advancing. The wording names the wrong execution phase and leaves the implementation agent to redesign lifecycle orchestration; it does not establish the needed evidence. The fix artifact's “已修复” claim is therefore not borne out by the revised plan.
- **直接证据**: Plan `§7.1` lines 444-447 and `§7.2` lines 453-454 place the action in a renamed test method while describing it as occurring before V005. Current `PostgresContainerIT.java:873-920` marks setup `@BeforeAll`, migrates the staged prefix, then calls unrestricted `flyway.migrate()` to latest; the existing `@Test` starts at line 927. Controller re-review instruction in `project-execution-control.md:30-34` expressly requires a staged setup helper/result before V005. V004 has no consent FK before V007 (existing absence assertion in current test around lines 7213-7218; V004 migration header and schema ordering).
- **影响**: The V004 prefix behavior test is impossible as described, causing a failing test if followed literally or a silent loss of required regression coverage if improvised. The plan is not yet code-generation-ready for the staged lifecycle.
- **建议改法和验证点**: Keep the count-neutral renamed `@Test` as the later assertion/reporting method, but specify an executable staged helper invoked by `@BeforeAll` immediately after migration to target 004 and before retargeting to 005. That helper must insert the minimal valid parents/order with a random non-null orphan consent ID in a transaction, assert insert success, roll back, and capture a static result/flag (or equivalent durable in-memory evidence) which the renamed `@Test` asserts. State ordering explicitly: migrate V001–V004 → invoke helper and rollback → capture success → migrate V005 → V006 → V007/latest → JUnit tests assert captured V004 proof. Alternatively specify an equally concrete lifecycle-correct hook. Retain the final-V007 valid-parent success case and orphan rejection by SQLSTATE `23503` and exact `fk_customer_order_consent`.
