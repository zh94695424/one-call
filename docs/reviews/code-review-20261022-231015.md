### OQ-2/OQ-6-部分修复-[中]-Approved expiry inputs are excluded from the new creation and action fingerprints, so changed expiry or extension content can replay instead of conflicting

- **入口/函数**: `sharing.create_share_grant` creation-fingerprint comparison; `sharing.apply_share_transition` EXTEND event-identity and fingerprint resolution; `sharing.issue_or_reconstruct_ticket` only consumes the resulting grant state.

Author claims: `docs/gateflow/a0-production-data-model-and-flyway-schema-spec-s3-fix-1.md:50` and `:54`.
- **输入场景**: (a) Same trusted creator account and same stable `creationRequestId` as an existing grant, same organization/evidence/verification/download/admission options, but a changed approved `expiresAt`; (b) same stable EXTEND `actionRequestId` on an existing `ACTIVE` grant, but a changed `newExpiresAt`.
- **实际分支**: `share_id` is derived only from `{creatorAccountId, creationRequestId}` (`:250`), and the EXTEND event ID is derived from `{shareGrantId, actionType, sourceIdentity: REQUEST, actionRequestId}` (`:248`), so the existing grant/event is found. The service then recomputes only the creation/action fingerprint (`:3365`, `:3369`). The fingerprint field lists explicitly include `expiresAt (RFC 3339 UTC)` and `newExpiresAt (EXTEND only)`, but the same clauses then exclude `timestamps` (`:250`) and `all timestamps` (`:248`). Under that literal exclusion the approved expiry input is removed from the hash, so the recomputed value equals the frozen value and the service returns existing metadata or the first recorded outcome as a replay.
- **预期行为**: The controller OQ-2 requires the canonical creation fingerprint to include scope and initial request parameters, with same identity and changed content conflicting; OQ-6 requires changed action content to conflict and the same action retry to be resolved before mutable state checks. `T-S3-15` (`:4675`) requires a changed scope to return `SHARE_CREATION_CONFLICT`; `T-S3-16` (`:4676`) requires a retry with changed action content to conflict. Only generated/observed network timestamps should be excluded, not approved input facts such as the requested validity end or extension target.
- **实际行为**: A changed creation expiry or a changed EXTEND target can be silently treated as a successful replay. No second grant or extension is created, so the first frozen value remains authoritative, but no conflict is reported and the changed input is not applied. The specification does not let a code generator determine the exact hash input unambiguously.
- **直接证据**: The explicit inclusion of `expiresAt`/`newExpiresAt` followed by the `timestamps`/`all timestamps` exclusion at `:250` and `:248`; the service comparison at `:3365`/`:3369`; the conflicting test requirements at `:4675`/`:4676`; the controller clarifications at control `:601`/`:605`; the author claims at fix artifact `:50`/`:54`. The S2 registry at `:3783` narrows its own excluded timestamps to network timestamps, but S3 does not adopt or cross-reference that narrowing.
- **影响**: This is an idempotency and conflict-contract defect, not an authorization bypass. The first grant or extension remains authoritative and no second capability or admission is created. However, two of the six accepted OQ clarifications are not exact for code generation, and a changed validity/extension request can be reported as a successful replay. The affected test assertions cannot pass if the literal exclusion is implemented.
- **建议改法和验证点**: Replace `timestamps`/`all timestamps` with `generated or observed network timestamps (created_at, occurred_at, admitted_at, decided_at and equivalent server times)` and explicitly state that the approved input facts `expiresAt` and `newExpiresAt` are included in `creationFingerprint`/`actionFingerprint`, or compare the full typed creation object in addition to the fingerprint. Add `T-S3-15` and `T-S3-16` cases for a changed expiry and a changed extension target and assert `SHARE_CREATION_CONFLICT`/stable conflict with no mutation. No table, column, function, action or wire change is needed.
