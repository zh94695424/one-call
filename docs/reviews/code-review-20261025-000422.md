### F1 — Hardcoded `'s1'` slice argument in fixture runner breaks S2/S3 stage extension

| Field | Value |
| --- | --- |
| Entry / function | fixture loop → `validateFixture` (`protocol/ivr/validate.mjs`) |
| File / line | `protocol/ivr/validate.mjs:1926-1928` |
| Input scenario | Future S2 (or S3) stage run that includes cumulative fixtures with `"slice": "s2"` / `"s3"` while sharing the same fixture directory walk |
| Actual branch | `validateFixture(entry.fixture, 's1', counters, issues)` always passes the literal `'s1'`; inside `validateFixture`, `fixture.slice !== expectedSlice` increments `stage_field_invalid` |
| Expected behavior | Stage-driven slice name from `config` / CLI `--stage`, so cumulative s2/s3 fixtures validate under their own slice |
| Actual behavior | Any s2/s3 fixture would be rejected as wrong-slice at S2/S3 validation time even if IDs are listed in `STAGE_CONFIG` |
| Direct evidence | Lines 1926–1928 call site; `STAGE_CONFIG.s2`/`s3` already list cumulative `fixtureIds` (`s1-*` plus `s2-*` / `s3-*`) and slice order, but the call site does not use stage |
| Impact | S2/S3 will fail closed until the call site is changed; not an S1 correctness defect (S1 only has s1 fixtures). Concrete stage-extensibility debt owned by the shared validator file |
| Fix / verification | Pass the resolved stage/slice into `validateFixture`; run `--stage s2` / `s3` once those fixtures exist |
| Fix risk | Low — local parameter change; S1 behavior unchanged if `'s1'` remains the S1 stage value |
| Severity | **low** (maintainability / next-slice blocker, not S1 functional bug) |

### F2 — Forbidden Problem-code check is conditional and cannot fail alone

| Field | Value |
| --- | --- |
| Entry / function | A1 drift scan of domain-vs-Problem token overlap (`protocol/ivr/validate.mjs`) |
| File / line | `protocol/ivr/validate.mjs:1607-1614` |
| Input scenario | A1 `ProblemCode` enum gains `TASK_CONFLICT` / `CALL_IN_PROGRESS` / `CONFIRMATION_NOT_ALLOWED` while the model also keeps those strings only as `decisionReasons` (not as problem codes) |
| Actual branch | Loop flags drift only when `reasonTokens.has(forbidden) && problemCodeEnum.includes(forbidden)` — i.e. only if the token appears in both model reasons and A1 ProblemCode enum |
| Expected behavior | Domain decision reasons must never become A1 Problem codes; a dedicated negative should fail if A1 promotes those domain tokens |
| Actual behavior | If A1 adds the token to ProblemCode but the model removes it from `decisionReasons`, this check is silent. Per-operation error-array `deepEqual` and problemCode↔HTTP maps still catch most real drifts, so this is defense-in-depth only |
| Direct evidence | Lines 1609–1613; primary protections at 1615–1624 (`deepEqual` of exact per-op arrays) and model `errors.problemCodes` vs A1 ProblemCode enum |
| Impact | Weak secondary guard; primary A1 error mapping still precise. Risk is a false sense of a dedicated forbidden-code negative rather than a missing primary comparison |
| Fix / verification | Assert the three tokens are absent from A1 `ProblemCode.enum` unconditionally (or assert model reason set ∩ ProblemCode enum is empty for that deny list) |
| Fix risk | Low — pure validator assertion tighten |
| Severity | **low** |
