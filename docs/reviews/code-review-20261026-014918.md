### F-AGG-02 (Low) — IVR canonical string is self-signing; its frozen content is not pinned by any fixture

- Triggering input: a symmetric mutation of the canonical composition (CRLF instead of LF, appended query string, reordered lines, non-uppercased method, URL-decoded path) applied to both signing and verification.
- Actual branch: sign and verify share one function, so any symmetric bug round-trips and every existing `sec-s2-04`/`sec-s2-05`/`sec-s2-07` signature step still passes. Expected: INV-A3-09 and the design freeze the exact six-line `\n`-joined canonical string (`docs/17-production-security-design-spec.md:349-355`; model `signatureProfiles["ivr-request-v1"].canonicalStringLines`/`canonicalStringSeparator`), and a composition bug should be discriminated.
- Impact: a codegen-critical contract (exact bytes covered by the HMAC) is verified only by static code review, not by fixture discrimination.
- Concrete fix: add one step (in `sec-s2-04` or a dedicated s2 step) that pins the canonical string — or its lowercase hex SHA-256 — for a fully specified input (fixed method/path/timestamp/nonce/body), computed independently of `signatureFor`.
- Fix risk: Low — one additive fixture step; no model/spec/registry change.

### F-AGG-03 (Low) — `sec-s2-04` cannot discriminate timestamp-window vs signature-verify order swaps

- Locations: `security/v1/fixtures/sec-s2-04-ivr-signature-invalid.json` (each denial step isolates a single failure: missing/revoked mTLS, missing/invalid signature with in-window timestamp, out-of-window timestamp with valid signature, unknown keyId, malformed nonce, disallowed identity); machine verification order at `security/validate.mjs:1619-1701` (mTLS → headers → timestamp → signature → nonce); frozen order at `docs/17-production-security-design-spec.md:356` and model `signatureProfiles["ivr-request-v1"].verificationOrder`.
- Triggering input: a step combining an out-of-window timestamp with an invalid signature (or a malformed nonce with an invalid signature).
- Actual branch: with only single-failure steps, swapping the timestamp and signature checks produces identical outcomes for every existing step (out-of-window step yields `TIMESTAMP_OUT_OF_WINDOW` under either order once the other check passes; bad-signature step likewise). Expected: INV-A3-09 freezes the order; the fixture set should fail on an order inversion. Actual: order inversion false-passes.
- Impact: the frozen verification-order invariant is under-tested at the aggregate fixture level; every combination still denies, so this is order/reason-code fidelity, not an authorization hole.
- Concrete fix: add one step to `sec-s2-04` with an invalid signature AND an out-of-window timestamp, expecting `TIMESTAMP_OUT_OF_WINDOW` (timestamp checked before signature per the frozen order); optionally a second step with malformed nonce AND bad signature expecting `HEADER_INVALID`.
- Fix risk: Low — additive fixture step; no contract change.

### F-AGG-04 (Low) — Provider `verificationOrder` list conflicts with the conflict-prose ordering (codegen precision)

- Locations: `security/v1/security-design-v1.json`, `signatureProfiles["provider-callback-v1"]` — `verificationOrder` lists `"event identity and payload fingerprint"` BEFORE `"nonce SET NX for a new event or changed payload"`, while the same profile's `conflict` field states `"same event with a different payload returns 409 PAYMENT_EVENT_CONFLICT after the nonce check"`. Human spec mirrors the tension: `docs/17-production-security-design-spec.md:367` lists fingerprint (annotated with the 409) before nonce, while `:368` states changed payload "必须先通过 nonce 检查". The machine and fixtures pin the prose reading: `security/v1/fixtures/sec-s2-06-provider-signature-replay.json` step `changed-payload-after-nonce-replay` expects `401` / `NONCE_REPLAY` (not `409`) when a changed payload arrives with a replayed nonce.
- Triggering input: a code-generation implementer coding strictly against the ordered list, performing the changed-payload conflict check before `SET NX`.
- Actual branch (list-faithful implementation): replayed-nonce + changed payload returns `409 PAYMENT_EVENT_CONFLICT`. Expected (frozen executable semantics per `conflict` field, spec `:368`, and fixture): `401 CALLBACK_SIGNATURE_INVALID` / `NONCE_REPLAY`.
- Impact: the binding goal is a code-generation-ready spec; the two authoritative statements inside the same model object prescribe different placement for the conflict check, creating a real implementer-divergence risk from the pinned fixture semantics. Duplicate-before-nonce and conflict-after-nonce are individually unambiguous; only the combined ordered list is imprecise.
- Concrete fix: amend `verificationOrder` in both `security/v1/security-design-v1.json` and `docs/17-production-security-design-spec.md:367` to split the step — e.g. `"exact-duplicate event fingerprint check (200 early exit, no nonce consumption)"` before nonce, and `"changed-payload conflict (409) after nonce SET NX"` after nonce — leaving the `conflict` field, fixtures, and machine unchanged.
- Fix risk: Low — wording-only clarification of an already-pinned executable order; no counter/registry/invariant/stage change.
