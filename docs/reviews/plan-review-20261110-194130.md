## Findings

### 1-未修复-中-Existing compatible but unrelated login can be adopted instead of rejected; adoption/replay/collision boundary is undefined

- **位置**: Plan §4.1 (line 86, "collisions, managed/system names"), §4.2 step 4 (line 97, "For already-compatible existing external logins, `apply` reaffirms... Add absent approved edges"), §4.3 (line 115, "Missing roles/edges are classified separately from incompatible existing state"), tests #10 and #18 (§6.2, lines 180 and 188).
- **问题类型**: 契约缺失 / 状态机漏洞 / fail-closed 不完整
- **当前写法**: `apply` treats any pre-existing role whose name equals the externally chosen `sharing_login`/`customer_login`/`command_login` and whose attributes are "already-compatible" as the intended external login: it reaffirms `LOGIN NOINHERIT`/safe flags/connection limit and adds any missing approved edge. `check` rejects only incompatible attributes, wrong edges, extra edges and drift. The only rejection language is an undefined "collisions, managed/system names" rule in §4.1; the plan does not define how the script proves that an existing compatible role is the intended external login rather than an unrelated pre-existing login.
- **反例/失败场景**: A target cluster already contains another service's least-privilege login, e.g. `app_reporting_login` with `LOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS CONNECTION LIMIT -1`, NULL validity, no memberships and no ACL entries. Platform chooses `sharing_login=app_reporting_login` (a name collision not in the migration-created/managed-name set). `apply` sees a compatible existing login, adds `GRANT sharing_role TO app_reporting_login WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`, and commits. The exact postcondition then passes, a subsequent `check` returns `PA25_CHECK_OK` for the structurally valid graph, and the unrelated application credential now has `sharing_role` access. No test covers this case: test #10 covers missing *edges* and old names that still hold a membership, and test #18 covers "colliding" names against managed names, but neither defines or exercises an unrelated compatible pre-existing login.
- **为什么有问题**: The Goal Confirmation requires malformed/stale/ambiguous role state to fail closed (Control line 22) and success to prove every login enters only its intended effective role. A compatible but unrelated pre-existing role is ambiguous role state; adopting it silently violates the "no unrelated memberships" and least-privilege boundary. The plan also says an "existing stale login name/password distribution is not guessed, renamed, dropped or aliased" (§4.3), but the current `apply` path guesses in the opposite direction by adopting it. The implementation agent must invent a provenance rule that the plan does not supply, so this is also a code-generation-readiness gap.
- **直接证据**: Plan §4.1 line 86 lists "collisions" without defining the collision set; §4.2 step 4 line 97 explicitly adopts "already-compatible existing external logins"; §4.3 line 115 classifies only incompatible state and says stale names are not guessed; test #10 line 180 requires repair of a missing edge without defining how the owning role is identified; test #18 line 188 covers unsafe/colliding names but not a compatible unrelated role. Control line 22 makes fail-closed ambiguous state a binding requirement.
- **影响**: Unintended privilege binding/cross-service access; an unrelated production credential may need emergency rotation or retirement; `check` cannot detect the mistake because the resulting graph is structurally valid; implementation may be forced to redesign the collision/adoption rule after plan acceptance.
- **建议改法和验证点**: Define the adoption rule explicitly. A bounded option: `apply` may adopt a pre-existing role only when it already has the exact approved four-edge graph compatible with that login; an existing chosen-name role with compatible attributes but missing edges is rejected unless the operator supplies an explicit nonsecret adoption/repair attestation (or the plan adds a checked nonsecret `COMMENT ON ROLE` marker, if comments are acceptable in the frozen model). Reject any chosen name that exists with compatible attributes but no approved provenance. Add a negative test in the class with a pre-existing compatible unrelated login (no edges) to `invalidInputsHistoryAndAuthorityRejectAtomically` and/or `missingAndStaleMembershipsFailCheckAndOnlyAbsentEdgesAreReconciled`, asserting no edge is added and no rollback mutation remains.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## Open questions

1. **OQ-1 (adoption/collision rule)**: If finding 1 is accepted, which nonsecret signal distinguishes a legitimate replayed external login from an unrelated compatible pre-existing role? The answer must not introduce a persistent helper object/schema/table unless separately authorized, and must preserve test #10's missing-edge repair.
2. **OQ-2 (strict environment prerequisites)**: The plan rejects any `pg_db_role_setting` row touching a managed node and any current-database `setrole=0` database-wide settings (§5.1), and requires NULL validity for the three external logins (§4.3). Platform/Database must confirm these are acceptable on the target managed PostgreSQL 16 service; a normal `ALTER DATABASE ... SET` or a Security `VALID UNTIL` rotation policy would otherwise block provisioning. The plan surfaces this as external disposition, but a pre-implementation confirmation would reduce rework.
3. **OQ-3 (independent ACL oracle)**: The plan hardcodes the 300 expected tuples in the delivered SQL script and says the IT independently checks equality to frozen source-derived sets. The implementation should state whether the IT derives its expected set from the frozen migrations (independent) or copies the script's table (not independent); the plan's wording is compatible with both.
4. **OQ-4 (CI cost)**: The new IT starts a fresh migrated container per method in a CI job with `timeout-minutes: 30`. The plan requires recording elapsed time but does not establish that 20 fresh containers fit; measure before/after and preserve the no-parallel/fresh-contamination requirement.

## Conclusion

`pass-with-risks`

The plan's central factual contract is evidence-backed: the six-login/seven-role/four-edge graph, the frozen ACL model (300 tuples), V001–V013 byte identity, the 309/234/543 inventory arithmetic, the six-path allowlist and external ownership boundaries all check out. The plan is generally code-generation-ready. One Medium fail-closed gap remains: `apply` can adopt a compatible but unrelated pre-existing login, and the plan does not define how replay, repair and collision are distinguished. The remaining items are open questions or owner-routed residual risks, not plan blockers.
