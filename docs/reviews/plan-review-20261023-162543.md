## Findings

### F-01-未修复-[中]-Support-entry operations have no A0 model while the binding success signal and mapping rule require one per operation

- **位置**: Plan §1.3 item 8 at L58; §5.1 C19 at L350; §5.2 O18 at L373; §5.6 `SupportEntry` at L436; §7.1 `SupportEntry` mapping at L503; §9.3 rule 1 at L642; §9.2 `check-doc-map` at L626; §10.3 final-report item 3 at L698-699.
- **问题类型**: 契约完整性 / A0 映射 / 校验不可实施 / 公开信任面边界.
- **当前写法**: The binding success signal says “每个 operation 的 `x-onecall-a0-models` 至少一个 A0 表名” (L58). The final-report requirement repeats “每个 operation 至少一个表/事务” (L699). C19 and O18 are explicitly “无业务表；docs/10 §6 配置边界” (L350, L373), and §7.1 records `SupportEntry | 无 A0 表` (L503). The custom metadata rule requires `x-onecall-a0-models` on every operation (L642), and `check-doc-map` is specified to require every model table to exist in docs/14 (L626). No exception is defined for C19/O18.
- **反例/失败场景**: An implementer follows the success signal literally and must either leave `x-onecall-a0-models: []` (violating L58/L699) or attach an unrelated A0 table to satisfy the validator (contradicting the A0 truth and docs/15). If the check only verifies that the extension exists, the plan ships two operations with no executable mapping while the S1/S2 reports claim every operation has one. A future agent cannot tell whether the support entry is a business operation or a UI/config projection.
- **为什么有问题**: The success signal and docs/15 mapping are binding acceptance criteria; A0 is the accepted persistence truth. Support entry is a display/config requirement, not an A0-owned business fact. The plan may keep the endpoints, but it cannot simultaneously claim a per-operation A0 table and declare both endpoints tableless without an explicit, approved exception.
- **直接证据**: Plan L58/L699 require a table/transaction per operation; L350/L373/L503 declare no A0 table; L642/L626 are the enforcing rules. docs 12 L26 says the system provides a unified offline-support entry, contact and handling instructions; docs 10 L73 says the three ends show `mode=OFFLINE`, `configured=false` and no online submission. Neither source defines C19/O18 as A0 operations.
- **影响**: The plan’s own completion report and doc-map check cannot be satisfied consistently; the 47-operation count contains two operations whose A0 mapping is undefined; an implementation agent must invent either a fake mapping or an undocumented exception. The anonymous C19 endpoint’s trust boundary also remains weakly grounded.
- **建议改法和验证点**: Decide and document one bounded outcome before implementation: (a) retain C19/O18 with `x-onecall-no-a0-model: true`, a controller-approved exception to success signal #8, a docs/15 owner/destination row, and a specific `no-a0-model` rule that asserts no customer/business data; or (b) remove C19/O18 from the 47 and expose the offline config in UI/docs only, reducing the count and updating slice counts. If retained, require C19 to be explicitly `x-onecall-anonymous-read: true` and prove its schema contains only `mode`, `configured`, `contactChannels` and `instructions`. Add a negative test that any new operation without an A0 table is rejected unless the exception is specifically allowed.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-02-未修复-[中]-A0 model references are non-canonical shorthand or wildcards and will not pass the proposed exact catalog check

- **位置**: Plan §5.1 C10 at L341 (`catalog_*`); C5 at L336 (`trial_grant`, `entitlement_grant`, `entitlement_balance`); I1 at L379 (`usage_reservation`, `service_activation`, `entitlement_balance`); P2 at L391 and P3 at L392 (`share_access_event`, `evidence_share_grant`, `subject_risk_state`); K1 at L403 (`payment_order`, `customer_order`); §7.1 rows at L489-505 also mix qualified and unqualified names; §1.3 item 8 at L58; §9.2 doc-map at L626.
- **问题类型**: A0 映射 / 校验可复现性 / 不可直接实施.
- **当前写法**: The proposed rule says A0 table names must exist in the accepted 44-table catalog and `check-doc-map` must assert each `x-onecall-a0-models` table against docs/14 (L58, L626, L642). docs/14’s catalog names are schema-qualified, e.g. `catalog_order.catalog_offer`, `entitlement_metering.usage_reservation`, `subject_number.caller_number_binding`, `sharing.share_access_event` (docs/14 L356-403). The plan’s §5 tables frequently use short names, `catalog_*`, or omit the schema; §7.1 does the same in several rows.
- **反例/失败场景**: The implementer copies the §5 summary into the OpenAPI extension. `check-doc-map` treats `catalog_*`, `usage_reservation`, `share_access_event` and `entitlement_grant` as absent from the 44-table catalog, so the check fails; or the implementer adds undocumented suffix matching/normalization that lets a typo or wrong-schema name pass. docs/15 may use a third naming form, making the three-way mapping non-comparable.
- **为什么有问题**: The plan’s key success signal is a direct, static A0 mapping. If the canonical form is not fixed, the validator is either too strict (false failures) or too permissive (false coverage), and a code-generation-ready contract cannot state which table an operation actually maps to.
- **直接证据**: docs/14 L356-403 lists the exact qualified names; plan L341 uses `catalog_*`; L379 uses `usage_reservation`; L391/L392 use `share_access_event` and `subject_risk_state`; L403 uses `payment_order`/`customer_order`. Plan L58/L626 does not specify a normalization rule.
- **影响**: The central static validation is not reproducible, docs/15 and OpenAPI can disagree, and implementation can claim A0 coverage without exact table identity. This directly undermines the “code-generation-ready” success signal.
- **建议改法和验证点**: Declare a single canonical representation for `x-onecall-a0-models`: fully qualified names exactly matching docs/14, with `catalog_*` expanded to `catalog_order.catalog_product`, `catalog_order.catalog_version`, `catalog_order.catalog_offer` and `catalog_order.catalog_benefit_line`. Mark the §5 A0 column as non-normative summary or update it. Make `check-doc-map` exact-match against the catalog block and add fixtures for an unqualified name, a wildcard and a wrong-schema name, all of which must fail.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-03-未修复-[中]-Code rotation reuses `ShareCreated`, whose one-time `capabilityToken` contradicts A0’s no-token-reissuance rule

- **位置**: Plan C18 at L349; §5.4 fixed request fields at L398; §5.6 `ShareCreated` at L421; §4.7 share creation/rotation at L268-270; §4.9 one-time return at L290; A0 T-S3-03 steps 4 and 6 at L3386/L3388; A0 state machine at L2808.
- **问题类型**: 公共契约安全 / A0 矛盾 / 生成类型错误.
- **当前写法**: C18 `rotateCustomerShareCode` returns `200 ShareCreated（新 code 仅本次）` (L349). The `ShareCreated` component is defined as `ShareGrant` fields + `capabilityToken` (only at creation) + `extractionCode?` (only code mode) (L421). A0 T-S3-03 step 4 says the plaintext capability token is returned only at first creation; “There is no token reissuance/reconstruction action” (L3386). Step 6 says code rotation replaces salt/hash, increments `code_generation` and `revocation_generation`, clears `LOCKED` to `ACTIVE` only as the explicit code-rotation unlock path, and appends `CODE_ROTATED`; it does not reissue a capability token (L3388).
- **反例/失败场景**: The generated TypeScript type for C18 is `ShareCreated`, which includes `capabilityToken`. An implementation that follows the schema may return a fresh capability token on rotation, creating a second usable link and violating the one-time token rule; a client may persist it and a later response/log may expose it. If the implementation omits the field, it violates the response schema’s requiredness as written. The same ambiguity affects the client-compat fixture, which may assert the wrong response type.
- **为什么有问题**: Code rotation is an owner transition on an existing grant, not a new creation. A0 explicitly separates token issuance from code rotation and forbids token reissuance. Reusing the creation response conflates two security events and gives generated clients a token-shaped object where none is permitted.
- **直接证据**: Plan L349/L421 vs docs/14 L3386 (“no token reissuance/reconstruction”) and L3388 (rotation semantics); plan §4.9 L290 says later reads must not return the token.
- **影响**: A security-sensitive response can leak or reissue a capability token; generated types encode the wrong contract; the C18 operation cannot be implemented consistently with both the plan and A0.
- **建议改法和验证点**: Introduce a distinct `ShareCodeRotation` response containing `shareId`, `verificationMode`, `codeGeneration`, `revocationGeneration`, `status` and the one-time `extractionCode` only; keep `ShareCreated` exclusively for C15. Add a generated-type assertion that `rotateCustomerShareCode`’s response has no `capabilityToken`, and a test that rotation never returns or logs a token.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-04-未修复-[中]-I1/I3 map frozen IVR decision outcomes (`TASK_CONFLICT`, `CALL_IN_PROGRESS`) to HTTP 409 instead of a 200 `IvrDecision`

- **位置**: Plan I1 at L379; I3 at L381; §4.6 problem-vs-decision policy at L217; §6.1 action list at L445-450; §6.2 decision table at L463; §6.3 failure/expiry at L472-477; A0 T-S2-03 at L3191; A0 T-S2-04 at L3203-3205; docs 13 §6.3 action table at L212-222.
- **问题类型**: HTTP/action 映射 / 状态机 / 契约缺失 / 不可直接实施.
- **当前写法**: I1 lists `409 SESSION_IDENTITY_MISMATCH/TASK_CONFLICT/CALL_IN_PROGRESS` among “特有错误” (L379); I3 lists `409 CONFIRMATION_NOT_ALLOWED/CALL_IN_PROGRESS` (L381). But A0 T-S2-03 step 5 returns the frozen action `REJECT_CALL_IN_PROGRESS` with a terminal `REJECTED` current call record and no claim/reservation (L3191); A0 T-S2-04 step 3 does the same for direct authorization (L3203). The plan’s own decision table says a competing call maps to `REJECT_CALL_IN_PROGRESS` and task data anomaly/multiple candidates maps to `REJECT` (`TASK_CONFLICT`) (L463). §4.6 explicitly says A0 IVR reason/action values belong in `reasonCode`/`action`, while `Problem.code` is for request failure and must not copy every decision reason (L217).
- **反例/失败场景**: A caller with an active call or a corrupt/multiple task reaches I1. If the endpoint returns 409 `CALL_IN_PROGRESS`/`TASK_CONFLICT`, the IVR receives no `IvrDecision`, cannot play the frozen rejection prompt, and may retry or create a second call record. If the endpoint returns 200 as required, the plan’s error table and Problem registry are wrong. `TASK_CONFLICT`/`CALL_IN_PROGRESS` are not in the representative Problem registry table (L223-253) and are A0 decision reason/action values, not transport errors.
- **为什么有问题**: The IVR contract is action-driven; the backend owns routing and the IVR must not infer or retry from HTTP errors for business refusals. A0 freezes these outcomes in `ivr_decision` and requires a terminal decision/call record. Mapping them to 409 breaks the stable action contract, the replay/idempotency model and the code-generation-ready status mapping.
- **直接证据**: Plan L379/L381 vs L217 and L463; docs/14 L3191 and L3203-3205; docs/13 L212-222 lists `REJECT_CALL_IN_PROGRESS` as an action and says IVR only executes the response action.
- **影响**: IVR behavior diverges on exactly the concurrency and data-integrity paths A0 makes deterministic; automatic outbound calls can be retried or misrouted; a generated client cannot tell whether 409 is a retryable transport error or a frozen decision; the Problem registry becomes inconsistent.
- **建议改法和验证点**: Return `200 IvrDecision` for every normal domain result, including `REJECT_CALL_IN_PROGRESS` and `REJECT` with `reasonCode=TASK_CONFLICT`; only authentication, invalid argument, session/fingerprint conflict that prevents a decision, and technical unavailability should use Problem. Remove `TASK_CONFLICT`/`CALL_IN_PROGRESS` from the I1/I3 409 lists and the Problem registry; add examples and tests for competing active call, multiple task candidates, and direct-path competing call. If a technical precondition (e.g. current `UNKNOWN` call with inconsistent line state) is intended, define a distinct stable Problem code and explain why no decision can be frozen.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-05-未修复-[中]-C10 order creation omits the current active service-activation predicate required by the business source and A0

- **位置**: Plan C10 at L341; §1.3 item 3 at L53; §4.3 authorization examples at L174-182; docs 12 §9.4 at L325; A0 T-S2-07 step 1 at L3236; docs 13 client task rules at L138 (secondary C6 concern).
- **问题类型**: 权限边界 / 业务规则缺失 / 不可直接实施.
- **当前写法**: C10’s server inputs are “session account/workspace；subject access；实名（普通客户）；当前 ACTIVE offer/versionToken；服务端金额；购买同意” (L341). A0 T-S2-07 step 1 requires the order service to verify “current active service activation” in addition to subject access, real-name, active offer/version token, consent and workspace authority (L3236). docs 12 §9.4 lists “当前业务开通状态” as a mandatory order-creation check (L325). The plan’s C3/C5 distinguish subject access from activation, so “subject access” cannot be read as covering activation without an explicit statement.
- **反例/失败场景**: A subject is `SUSPENDED` or `INACTIVE` but still has a valid offer/version token and real-name. C10 authorizes an order because the listed predicates do not include current `service_activation = ACTIVE`; the user can pay for a service that is not active, and the entitlement issuance/payment path proceeds on an invalid order. A future implementation may add the check, but the contract’s server-derived authorization boundary is incomplete.
- **为什么有问题**: The binding constraints require server-derived authorization for every write and direct mapping to A0 state/transactions. A0 explicitly makes activation status a precondition of order creation; docs 12 makes it a business rule. Omitting it from the C10 authorization description is a security/business gap, not a deferred policy value.
- **直接证据**: Plan L341; docs 12 L325 (“创建订单时服务端重新校验账户、工作空间与主体访问权、普通客户端的实名条件、明确购买同意、当前业务开通状态及精确在售版本/渠道”); docs/14 L3236 (“Verify subject access, ordinary-client real-name, current active service activation and the current ACTIVE offer/version token”). The plan’s C6 server inputs also omit an explicit activation/active-call statement while listing only caller binding and unique task (L337; docs/13 L138 requires activation and active-call checks).
- **影响**: A suspended/inactive subject can create a payable order; the contract does not encode the A0 transaction’s authorization predicate; implementation agents must guess the missing denial code and status.
- **建议改法和验证点**: Add `current service_activation.status = ACTIVE` (with current subject/workspace authority) to C10’s server inputs and `x-onecall-authorization`, and define the stable denial (`FORBIDDEN` or a specific activation code) and tests for `INACTIVE`/`SUSPENDED`. Review C6 similarly and state whether task creation requires activation and no other `ACTIVE/UNKNOWN` call; if it does not, explain why A0 T-S2-02’s active-call guard is still applied.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-06-未修复-[中]-The operations surface publishes catalog/trial-policy candidates but has no approved way to create the DRAFT/never-published rows, and no recorded deferral

- **位置**: Plan §1.4 L69 and §1.5 L80 (exclude catalog draft editing); §5.2 O8/O9 at L363-364 (read-only); O10 at L365 and O13 at L368 (publish existing version/policy IDs); §8.3 S2 stop condition at L579-580 (“需要选择的目录草稿创建”); §7.2 open inputs at L507-529 (no draft-creation row); docs 09 §5 at L103-104; A0 T-S2-14 steps 3 and 5 at L3347/L3349.
- **问题类型**: 目标完整性 / A0 事务前置 / 开放输入缺失 / 不可直接实施.
- **当前写法**: The plan explicitly excludes catalog draft editing and does not define creation of `catalog_version` DRAFT or `trial_policy_version` rows. O10 takes `{versionId}` and publishes a candidate DRAFT/never-published version; O13 takes `{policyVersionId}` and publishes a never-published trial policy. A0 T-S2-14 requires the candidate to already exist as `DRAFT` with `published_at IS NULL` (L3347) or never-published (L3349). docs 09’s approved operations scope includes “套餐设置 | 编辑新版本草稿、确认发布、上下架” and “试用规则 | 额度、有效天数、启用” (L103-104). The only handling in the plan is an implementation stop condition, not an owner/destination deferral.
- **反例/失败场景**: A fresh production deployment has no DRAFT catalog version or trial policy version. O10/O13 cannot be used; an operator would have to seed rows by direct SQL or an unspecified tool, bypassing the A1 authorization, validation, audit and idempotency contract. Alternatively, an implementation agent invents create/edit endpoints despite the plan’s exclusion, expanding scope and violating the “47 operations” claim.
- **为什么有问题**: The plan claims 47 first-release operations from approved sources and calls S2 the catalog/trial control slice. The publication operations are not end-to-end without a candidate-creation path. A0’s publication transaction is only the activation step; docs 09’s draft-edit capability is a separate approved operations function. If it is intentionally excluded, the plan must record that as a deferred open input with owner/destination, not only a stop condition.
- **直接证据**: Plan L365/L368 require existing candidate IDs; L579 admits the draft-creation decision is unresolved; L69/L80 exclude it; docs 09 L103-104 approve draft editing and trial-rule editing; docs/14 L3347/L3349 require a pre-existing candidate. The plan’s §7.2 table lists Q1/Q6/etc. but no “catalog/trial-policy candidate creation” row (L507-529).
- **影响**: The S2 operations surface cannot be exercised on a fresh system; manual database seeding is an unowned authorization bypass; the 47-operation completeness claim is overstated; the implementation agent faces a scope decision at S2 stop.
- **建议改法和验证点**: Choose a bounded resolution before S2: (a) add minimal approved create/edit operations for a new version/policy candidate if the A0 transaction set supports them, or (b) explicitly defer them in §7.2 with owner Product/Operations/catalog-order, destination the catalog operations OpenAPI work, and state that O10/O13 accept only pre-seeded candidates with server-validated immutable content. Do not leave this only in a stop condition. Update the 47-operation count and slice reports if operations are added or removed.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-07-未修复-[低]-C9 customer catalog list has no stable sort/cursor binding while every other resource list is specified

- **位置**: Plan C9 at L340; §4.8 cursor/stable sort at L275-283; §1.3 item 7 at L57; docs 12 §8 at L283.

Keep the open question about page-size defaults separate.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### F-08-未修复-[中]-P3 maps `SHARE_LOCKED` to an error for media authorization, contradicting A0’s allowance of an already-admitted session under LOCKED

- **位置**: Plan P3 at L392; P2 at L391; §4.9 public-share verification at L290-292; A0 §7.4 share state machine at L2808-2809; A0 T-S3-05 step 3/4 at L3407-3408; A0 S3 transition rules at L2817.
- **问题类型**: 公共分享状态机 / 权限边界 / 契约矛盾.
- **当前写法**: P3 returns `409 SHARE_GENERATION_STALE/SHARE_LOCKED` among its errors (L392). A0 §7.4 says a `LOCKED` grant still permits an existing admitted session’s replay/reconstruction while blocking a new admission (L2809); T-S3-05 step 3 requires the current status to be `ACTIVE` or, for an already-admitted session, `LOCKED`, then reissues the same derived ticket (L3407); step 4 requires media playback/seek/renewal to recheck the current grant status/time/generation (L3408). The plan itself uses `SHARE_LOCKED` correctly for P2 new admissions (L391).
- **反例/失败场景**: A share is `LOCKED` after an approved verification-failure/lock policy. The last admitted user calls P3 `PLAYBACK/SEEK/RENEW` within the recorded admission/session/grant validity. If P3 follows the error table, it returns 409 `SHARE_LOCKED` and stops an already-authorized playback, even though A0 says only new admissions are blocked. The user loses the last session; the implementation may also mark the lock as a revocation despite A0’s no generation increment.
- **为什么有问题**: A0 distinguishes new admission from existing-session continuation. `LOCKED` blocks new verification/admission but does not invalidate an already-admitted session and does not bump `revocation_generation` (A0 L2808-2809/L2817). P3 is media authorization for an existing admission, not a new admission; returning `SHARE_LOCKED` conflates the two paths.
- **直接证据**: Plan L392 vs L391 (correct P2 usage); A0 L2809 (“`LOCKED` still permits that existing replay/reconstruction while blocking a new admission”) and L3407/L3408; A0 L2817 (“Reaching the admission limit is not revocation... the last admitted session keeps its valid session/grant window”).
- **影响**: The contract denies a behavior the approved share state machine explicitly permits; a generated client cannot distinguish `LOCKED` new-admission denial from existing-session continuation; implementation may propagate a false lock/revocation to media.
- **建议改法和验证点**: Remove `SHARE_LOCKED` from P3’s error set; require P3 to allow an existing admitted session through `ACTIVE` or `LOCKED` with current generation/expiry checks; keep `SHARE_LOCKED` only for P2 new admission. Add tests for `P2 new key under LOCKED -> 409 SHARE_LOCKED` and `P3 existing admission under LOCKED -> 200/reissued MediaAuthorization`. If a technical ticket failure occurs, use `DEPENDENCY_UNAVAILABLE`/the approved stable code and leave the admission count unchanged.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

## Special review lenses

- **Goal-bound minimal design:** The contract is bounded to the five approved surfaces, uses one canonical source, and excludes generic CRUD, payment initiation, employee authentication, online workflows, vendor payloads and recording playback. The two support-entry operations are a minor scope expansion and the missing draft-creation prerequisite is an under-coverage gap; neither justifies a new workflow, service or fourth slice. One-time token typing and A0-name canonicalization are minimal corrections, not redesign.
- **Architecture boundary:** Customer, employee, IVR, public-capability and provider-callback identities remain separate; operations does not inherit customer sessions; IVR keeps outbound/media facts and the backend keeps task/entitlement/decision truth; public sharing uses path capability plus server verification; callbacks remain a signed opaque adapter boundary. C10’s missing activation predicate is the only material authorization-boundary gap in an otherwise sound model.
- **Best practice:** RFC 9457 Problem, stable business codes, cursor pagination, `Idempotency-Key`/event identity, server-derived amounts/status, no provider/internal leakage and append-only/share state semantics are used correctly. The IVR HTTP/action separation (F-04), code-rotation response (F-03) and LOCKED session behavior (F-08) are the places where best practice and the accepted state contracts diverge.
- **Optimal solution:** A single canonical OpenAPI source plus focused custom rules, one mapping document, one strict TypeScript compatibility fixture and three behaviorally bounded slices is the right solution shape. The alternative of five surface files or hand-written clients would duplicate shared rules; no better smaller architecture was evidenced.
- **Overengineering:** No material overengineering. The ten custom rules, two Node scripts, fixture, docs/15 and generated-output directory each address a binding success signal or an A0/Problem/cursor check. The plan avoids an unnecessary service, database, workflow engine, login stack or generated client. The residual is parser/lockfile maintenance, not excess architecture.
- **Overcoupling:** The OpenAPI lint/doc-map intentionally reads docs/14 and docs/15 to prevent drift; that is acceptable validation coupling, not runtime coupling. The validation layer should not become the only source of A0 names; the plan should make the canonical qualified names explicit (F-02). No cross-module runtime ownership or microservice coupling is introduced.
