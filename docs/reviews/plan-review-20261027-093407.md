## 5. Material findings

Finding format: `ID [severity] status: open|accepted-risk|fixed` — problem, evidence, impact, required action, owner/destination.

### F-PA1-PR-01 [medium] status: open

**Broken-migration failure test is not fully isolated from the shared Flyway history and risks a false positive.**

- Problem: §5.8/§7.1 place `brokenMigrationFailsVisibly` in the same `PostgresContainerIT` that has already migrated V001 into the shared container, using a second Flyway instance with `locations("classpath:db/migration-broken")`, “a separate schema”, and a test-only `V001__broken.sql`. The plan does not specify a **separate history table/schema** (e.g. Flyway `schemas`/`defaultSchema`/`table` isolation) for that second instance.
- Evidence: shared `@BeforeAll` runs `Flyway` on `classpath:db/migration` and stores the result; default history is `public.flyway_schema_history` (§5.1, §5.8). A second Flyway instance with default configuration on the same database will read/validate the same history. A broken script also named `V001__…` collides on version, so the instance may raise `FlywayException` during validate/repair/version-resolution **before any broken DDL executes**, and the assertions “first valid DDL is rolled back” / “no successful applied row” become vacuously true or unproven. A real partial-DDL rollback is only proven if the broken migration actually starts executing.
- Impact: false-positive S1 evidence that “migration failure is visible rather than silently skipped” for the wrong reason; residual risk that a silently-skipped or partially-applied broken script would not be detected; cross-test pollution of `public.flyway_schema_history` if a broken applied row is ever written.
- Required action (before or during S1, no design change): give the broken-migration Flyway instance an isolated history location (dedicated schema and/or distinct history table name) and/or a non-colliding version prefix; assert that the broken script’s first valid statement actually ran and was rolled back (e.g. object absence with explicit pre-existence proof), not merely that some `FlywayException` occurred. Keep the fixture under `src/test/resources` and off the production classpath.
- Owner/destination: Backend (S1 implementation); controller verifies in S1 checkpoint evidence.

### F-PA1-PR-02 [low] status: open

**Surefire `classpathDependencyExcludes` is the sole mechanism keeping `BootstrapDependencyBoundaryTests` green; the plan treats it as free but it is a single-point classpath assumption.**

- Problem: §3.1/§5.8 assert Flyway test-scope + Enforcer compile/runtime excludes + Surefire `classpathDependencyExcludes` leave the existing bootstrap test “byte-for-byte valid and unchanged.” The test checks `ClassUtils.isPresent("org.flywaydb.core.Flyway", …)` on the **surefire** classloader only.
- Evidence: `BootstrapDependencyBoundaryTests.java:11-24` loads Flyway by class name; `backend/pom.xml:95-106` currently bans `org.flywaydb:*` at all scopes; plan narrows bans to `compile`/`runtime` and excludes the two Flyway artifacts from surefire. If the exclusion coordinates do not match resolved artifacts (e.g. optional classifier/packaging, or a future transitive path), the unit suite fails or, worse, a future edit reintroduces Flyway onto the bootstrap classpath without any production-jar signal until CI’s fat-jar grep.
- Impact: low probability of S1 friction or of a weakened firewall narrative; CI fat-jar check remains the authoritative production firewall, so no production-runtime regression is claimed.
- Required action: keep the existing test unchanged as planned; in S1 record the surefire-classpath proof (test green **and** a negative probe that a temporary surefire-visible Flyway type would fail the test) in the completion report; do not replace the test with a scope-qualified Enforcer-only claim.
- Owner/destination: Backend/Platform; S1 completion-report firewall evidence section.

### F-PA1-PR-03 [low] status: accepted-risk (plan already discloses; verify in S1)

**Shared-container, order-sensitive IT methods rely on discipline rather than enforced isolation.**

- Problem: all 12 methods share one migrated container; several mutate non-append-only catalog state (decoy schema, broken-migration schema, `SET ROLE`, committed `NEW` idempotency rows). The plan’s implementation rules (unique keys, never truncate append-only tables, drop decoy/broken schemas) are correct but not mechanically enforced by the test harness design described.
- Evidence: §7.1 shared `@BeforeAll` migration; `hostileSearchPathCannotRedirectFunctionEffects` creates and drops a decoy schema; `brokenMigrationFailsVisibly` leaves isolation to F-PA1-PR-01’s fix; `committedNewIdempotencyRowIsAlertable…` intentionally leaves a committed `NEW` row that must not break other methods’ exact-row assertions.
- Impact: false failures or order-dependent flakes (R-12 already covers concurrency flakiness); false positives if a method asserts global counts that include rows/schemas created by an earlier method.
- Required action: keep unique-key discipline; scope row-count assertions to method-local keys; assert schema/role/object inventories with explicit “business objects only” filters that exclude `public.flyway_schema_history` and system schemas; drop temporary schemas in `finally`-equivalent paths.
- Owner/destination: Backend/QA; S2/S3 test review.
