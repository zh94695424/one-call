### F-01 `[高]` C10 cannot express the explicit current purchase consent that A0 requires

- **入口/位置**: `createCustomerOrder` (`POST /api/v1/customer/orders`) at `api/openapi/onecall-v1.openapi.yaml:589-679`; request schema `OrderCreateRequest` at `:3693-3712`; `client-compat.ts:149-165`; `docs/15-production-openapi-surface-spec.md:100,196,200`.
- **输入场景**: An authenticated customer submits `Idempotency-Key` (1-475) plus `{subjectId, catalogOfferId, channel[, expectedVersionToken]}`. The customer must be able to accept or decline the current PURCHASE prompt/policy, and a stale/declined decision must produce the declared errors.
- **实际分支**: The request has no purchase-consent decision, policy code/version, prompt version, or content hash. The contract instead says consent is server-derived, and the only consent-writing operation in S1/S2 is C5 `createCustomerSubjectActivation`, which is a SERVICE_ACTIVATION path (A0 T-S2-13), not PURCHASE. No operation can create or decline a PURCHASE consent before C10; A0 only appends it inside T-S2-07.
- **期望**: Plan §8.3 requires “购买同意是显式且当前 policy”; plan §5.1 C10 lists purchase consent as a server-authoritative input; architecture §9.4 step 2 requires “明确购买同意”; A0 T-S2-07 step 4 / §10.20 requires `append_purchase_consent` with the current prompt/policy version/key/content, explicit `ACCEPT` only, and no consent inference; missing/stale/declined consent is a typed denial. The purchase-consent event identity (81-char `purchase-consent:` + SHA-256 of `{accountId, clientIdempotencyKey}`) must remain server-derived.
- **实际**: `OrderCreateRequest.required` is exactly `[subjectId, catalogOfferId, channel]` and its only optional field is `expectedVersionToken`. `client-compat.ts` explicitly asserts `purchaseConsentEventId` is absent. `docs/15` §6 says “金额、同意、activation、支付与 issuance 全部服务端派生”. `PURCHASE_CONSENT_DECLINED` is declared in the exact C10 error set but cannot be requested through any operation.
- **直接证据**: YAML `:3697-3712`; A0 `docs/14:3239` (“does not infer consent”, explicit `ACCEPT` only), A0 `:3965` (“current prompt/policy version/key/content, explicit `ACCEPT` only” and typed denial), plan `:637`, architecture `:325`; docs/15 `:100,196,200`.
- **影响**: C10 cannot implement T-S2-07 as accepted. The server would have to infer an explicit purchase consent from the order request, which A0 forbids; `PURCHASE_CONSENT_DECLINED`/`PURCHASE_CONSENT_STALE` are unreachable, and a generated client cannot supply the facts needed to satisfy or decline the current PURCHASE policy. This is a core S2 business-flow and error-matrix defect, not a later-slice concern.
- **修复**: Add a bounded purchase-consent input block to `OrderCreateRequest` (for example `decision: ACCEPT|DECLINE`, `policyCode`, `policyVersion`, `promptVersion`, `contentSha256`), mirroring the accepted C5 explicit-consent shape; keep `purchaseConsentEventId` server-derived and absent from the request; map `DECLINE` to `409 PURCHASE_CONSENT_DECLINED`, current-policy mismatch to `409 PURCHASE_CONSENT_STALE`, and absent/invalid consent to `409 PURCHASE_CONSENT_REQUIRED`. Update docs/15 §3.2/§6, `client-compat.ts`, and the trusted-fact/negative rules together.
- **验证/修复风险**: Low mechanical risk (additive C10-only fields; no S1 request change), but it is a public contract change requiring regeneration and the full `check:s2` plus controller negative probes. The fix must not add a client-chosen purchase-consent event ID, price, payment, or entitlement facts. If the controller has a documented out-of-band consent flow outside A1, it must state where DECLINE/STALE can be produced; none exists in the accepted S1/S2 operation set.
- **严重度/建议分类**: 高；建议 `accepted` (or `needs-more-evidence` only if such an out-of-band flow is documented).

### F-02 `[中]` `TrialPolicyDraft.enabled` is `null`, not `false`

- **入口/位置**: `createOperationsTrialPolicyDraft` / `replaceOperationsTrialPolicyDraft` responses, `api/openapi/onecall-v1.openapi.yaml:4478-4513` (`TrialPolicyDraft.enabled`, required); generated `tmp/openapi-client/onecall-v1.d.ts:1626`; `client-compat.ts:254-255,407`.
- **输入场景**: Successful 201 first create, 200 same-projection replay, or 200 applied replace of a never-published FIRST-TRIAL draft.
- **实际分支**: The response schema requires `enabled` and sets `type: 'null'`; the generated type is `enabled: null`; the compile-time fixture asserts `AssertTrialDraftEnabledNull`.
- **期望**: Plan §5.2 O20 and §5.6 `TrialPolicyDraft` require `enabled: false`; S2 report §4 also states “`enabled=false`、`publishedAt=null`”. A0 `trial_policy_version.enabled` is `boolean NOT NULL` (default `true` at the column level, but a draft must be explicitly never-enabled), so `null` is not a valid persisted state.
- **实际**: `enabled: null`.
- **直接证据**: YAML `:4508-4510`; generated declaration `:1626`; `client-compat.ts:254-255`; plan `:404,477`; S2 report `§4`; A0 `docs/14:1605`.
- **影响**: The public response and generated client model the wrong type; clients cannot rely on the promised `false`; the contract diverges from the binding plan and from the persisted boolean domain. The compile-time assertion locks in the divergent truth.
- **修复**: Change `enabled` to `boolean` with `const: false` (OpenAPI 3.1) or `enum: [false]`; change the client-compat assertion to `false`; keep `publishedAt: null`; update docs/15 if it states the response value.
- **验证/修复风险**: Low; regenerate and run `check:s2`; no S1 impact.
- **严重度/建议分类**: 中；建议 `accepted`.

### F-03 `[中]` O10/O13 omit the required nullable expected-current-version input

- **入口/位置**: `publishOperationsCatalogVersion` request `CatalogVersionPublicationRequest` at `api/openapi/onecall-v1.openapi.yaml:4057-4070`; `publishOperationsTrialPolicy` request `TrialPolicyPublicationRequest` at `:4180-4193`; operation descriptions `:1581-1590,1867-1875`; generated `tmp/openapi-client/onecall-v1.d.ts:1462-1466,1509-1513`.
- **输入场景**: An ADMIN publishes a DRAFT catalog version or trial policy while supplying the expected current active/enabled version (nullable when none) plus `expectedRevision`.
- **实际分支**: `expectedActiveVersionId` and `expectedEnabledPolicyVersionId` are nullable but **optional** (`?` in the generated type); only `expectedRevision` is in `required`. The rules do not assert presence of either expected-version field or even `expectedRevision` for these publication operations.
- **期望**: Plan §4.7 and §5.2 define the state-conditional identity as `expectedActiveVersionId` / `expectedEnabledPolicyVersionId` (nullable) **plus** `expectedRevision`; the operation descriptions themselves say the caller supplies the expected version. “Nullable” means the field must be present and may be `null` for “none”, not that it may be omitted.
- **实际**: A caller can publish with only `expectedRevision`. This weakens T-S2-14 stale/concurrent-publication detection: the server cannot distinguish “no current version expected” from “expectation omitted”.
- **直接证据**: YAML `:4061-4069` (`required: [expectedRevision]`, `expectedActiveVersionId` optional); YAML `:4184-4192`; generated declaration `:1464` and `:1511` (`?: string | null`); plan `:280,394,397`; docs/15 `:105,109`.
- **影响**: Two of the four state-conditional publication operations have an under-specified concurrency guard. A generated client type makes the expected version optional, so an accidental omission compiles and can defeat the stale-view semantics the plan requires.
- **修复**: Add both fields to the request `required` arrays (still nullable); add client-compat assertions that they are required and nullable; add a static rule that the four publication/disable operations declare `expectedRevision` and the correct expected-version field (nullability/requiredness). Update docs/15 wording.
- **验证/修复风险**: Low; clients must send `null` when there is no current version. This is a stricter contract, but it is the plan's accepted state-conditional identity.
- **严重度/建议分类**: 中；建议 `accepted`.

### F-04 `[中]` `AuditFact` snapshots are open objects and bypass the S1 schema-closure rule

- **入口/位置**: `listOperationsAuditFacts` response `AuditFact` at `api/openapi/onecall-v1.openapi.yaml:4248-4259`; generated `tmp/openapi-client/onecall-v1.d.ts:1533-1539`; closure rule `api/openapi/contract-rules.mjs:1027-1031`.
- **输入场景**: An ADMIN/OPS employee reads `GET /api/v1/operations/audit`; `beforeSnapshot`/`afterSnapshot` are returned as redacted audit projections.
- **实际分支**: Both fields are `type: [object, 'null']` with `additionalProperties: true`. The generated type is `{ [key: string]: unknown } | null`. `validateSensitiveFields` checks closure only when `node.type === 'object'`; for a type array containing `object` the check is skipped.
- **期望**: Plan §4.11 says object schemas default to `additionalProperties: false`; §4.12 permits open objects only for `OpaqueProviderPayload` and the delayed IVR event `payload`. Audit snapshots are neither; §5.6 requires redacted snapshots, not an open object. The cumulative S1 closure invariant must not be weakened by S2.
- **实际**: The only open object in the S2/cumulative schemas is this audit snapshot pair; the static closure rule does not flag it, and the client-compat only checks top-level forbidden property names, not snapshot contents.
- **直接证据**: YAML `:4249-4258`; generated declaration `:1533-1539`; rule `:1029-1031`; plan `:338,347-352`; docs/15 `:113,188`.
- **影响**: The public contract permits arbitrary, potentially unredacted audit data to be modeled and generated into client types; the plan's redaction and opaque-boundary budget is violated; the same type-array escape can hide future sensitive fields from the closure rule. This is a current S2 contract defect and a validation regression, not merely a runtime risk.
- **修复**: Replace the open snapshots with a closed `RedactedAuditSnapshot` schema containing only the approved redacted fields (or explicitly record an approved opaque boundary with owner/destination, which the plan does not currently allow). Update the closure rule to treat a type array containing `object` as object-admitting and require `additionalProperties: false`; add a negative fixture with `beforeSnapshot.additionalProperties: true`.
- **验证/修复风险**: Medium design choice (the exact redacted snapshot fields need an owner decision), but the closure portion is mechanical. A closed schema may expose fewer fields than the runtime stores; that is the intended redacted projection.
- **严重度/建议分类**: 中；建议 `accepted`.

### F-05 `[中低]` S2 trusted-fact validation still false-accepts plan-forbidden C10/O18-O21 fields

- **入口/位置**: `api/openapi/contract-rules.mjs:107-124` (`TRUSTED_REQUEST_FACT_NAMES`), `:1092-1095` (draft price exception), `:1115-1127` (walker); `client-compat.ts:149-165`; plan §4.3 `:188-192`; docs/15 §6 `:194-195`.
- **输入场景**: An adversarial request-schema drift adds a trusted/server-derived field to a request:
  - `OrderCreateRequest.currency` or `OrderCreateRequest.paidAt`;
  - `TrialPolicyDraftCreateRequest.priceCents`, `snapshotSha256`, or `purchaseConsentId`;
  - `CatalogVersionDraftCreateRequest.snapshotSha256`, `versionToken`, or `issuanceStatus`.
- **实际分支**: `currency` and `paidAt` are in the plan's forbidden request-fact list but are not in `TRUSTED_REQUEST_FACT_NAMES`; `snapshotSha256`, `versionToken`, `purchaseConsentId`, and `issuanceStatus` are server-derived but are not in either the trusted set or a draft forbidden set. `draftPriceAllowed` is true for all four `DRAFT_OPERATION_IDS`, so a `priceCents` added to O20/O21 would pass even though docs/15 §6 allows draft commercial `priceCents` only on O18/O19. The client-compat `ForbiddenOrderCreateKey` does not assert `currency`, `paidAt`, `snapshotSha256`, `purchaseConsentId`, or `issuanceStatus` absent.
- **期望**: Plan §4.3 forbids client-supplied `currency`/`paidAt` and the other listed server facts; docs/15 §6 scopes the draft price exception to O18/O19; plan success signal #3 and the S2 verification requirement require negative probes to reject these drifts.
- **实际**: The current canonical `OrderCreateRequest`, `CatalogVersionDraftCreateRequest`, and `TrialPolicyDraftCreateRequest` are clean, so this is not a current wire-contract violation. The static rules and compile-time assertions would accept the adversarial additions described above; the draft exception is broader than the plan.
- **直接证据**: rule `:107-124` vs plan `:188-192`; rule `:1095,1121`; client-compat `:149-165`; docs/15 `:194-195,124`.
- **影响**: The plan's trusted-fact boundary and negative-probe acceptance evidence are incomplete. A future schema edit could expose `currency`, `paidAt`, server snapshot/payment/issuance facts, or a trial-draft `priceCents` without any gate failure, and the generated client would model the fact as client-supplied.
- **修复**: Extend the trusted-fact set with the full plan §4.3 names; scope the `priceCents` (and, if added, `currency`) exception to O18/O19 only; explicitly ban server-generated snapshot/purchase/issuance names on all request bodies; add client-compat `Extract` assertions for the C10/O20/O21 absent fields; add `/tmp` negative fixtures for each. Keep legitimate O18/O19 draft commercial fields passing.
- **验证/修复风险**: Low-medium; must avoid globally banning `currency`/`priceCents` on O18/O19. This is a validation-author change, but it is required by the S2 plan's negative-probe and trusted-input requirements.
- **严重度/建议分类**: 中低；建议 `accepted` (bounded S2 validation hardening) or `deferred-with-owner` to A1 validation author if the controller explicitly treats current-clean-body-only as sufficient.

## Open Questions

1. **CNY vs ISO-4217 currency**: A0 constrains `catalog_version.currency`, `customer_order.currency`, and `payment_order.currency` with `^[A-Z]{3}$` (ISO-4217), while plan §4.10 and docs/15 §5 describe `Money` as `{amountCents, currency: 'CNY'}`. The contract defines an unused `Money` with `currency: CNY` but uses the ISO pattern for order/catalog currency, and `client-compat.ts:229-230` asserts `Order.currency` is `string`. Decide whether the public v1 contract freezes CNY-only or follows the accepted A0 ISO domain; if CNY-only, narrow the schemas and generated assertions; if ISO, clarify docs/15 §5 and the plan wording. Owner: Product/Finance/catalog-order; destination: docs/15 and the contract.
2. **O19 channel `version_token` update**: Plan §5.2 O19 says the replace updates the version mutable content and existing channel `version_token`; the request forbids `channels` and the response exposes only one optional version-level `versionToken`, not per-channel tokens. Confirm that channel tokens are regenerated server-side and that clients do not need to observe them. Owner: catalog-order / A1 contract; destination: docs/15 §3.3 and O19 description if clarification is needed.
3. **Unknown idempotency-scope extension guard**: The contract contains no `CATALOG_DRAFT`/`TRIAL_POLICY_DRAFT` scope, no `platform.idempotency_record` mapping on O18-O21, and no invented scope in the sanctioned fields. The rules reject these values in `x-onecall-a0-models`, `x-onecall-a0-contracts`, and `x-onecall-idempotency`, but there is no dedicated whitelist for an arbitrary unknown `x-onecall-*scope*` extension. If the plan's “any new scope must be statically rejected” is intended to cover unknown extension keys, add that check; otherwise record it as a residual.
4. **O18 duplicate channel/benefit entries**: A0 has `uq_catalog_offer_version_channel` and `uq_catalog_benefit_line_version_entitlement`; the O18 request arrays do not set `uniqueItems` and do not enforce unique `entitlementType`. Runtime/A0 conflict is available, but decide whether the static contract should reject duplicates as `VALIDATION_FAILED`/`CATALOG_DRAFT_CONFLICT` before the database. Owner: catalog-order / A1 validation.
5. **S2 dynamic evidence in this session**: The required Node/npm harness could not be executed here (see limitations). The controller's green baseline is not independently re-run by this review; it should re-run it before accepting or rejecting any finding.
