# IVR 呼入自动外呼设计修订 Plan Review

## Reviewed target and scope

- Target: `docs/gateflow/ivr-call-task-auto-dial-plan.md` (scope amendment review).
- Scope: synchronize the self-built IVR task path across the authoritative design, architecture summary, current business summaries and acceptance entry points. The task path consumes one eligible pending task on inbound resolution, automatically dials its frozen callee, and bridges/records the A/B call through the existing IVR media plane. Direct no-task IVR input and activation/trial flows remain independent.
- Binding goal: remove only the task-path callee-number confirmation. Do not implement production runtime, alter recording notice/consent requirements, or invent a task token, PIN, queue or carrier feature.

## Assumptions tested

- A/B dial, bridge, recording, call facts, duration and uploads are existing self-built IVR capabilities; the business backend owns task, access and entitlement facts.
- The IVR obtains `callId` at inbound and the telephone network does not carry the miniapp `taskId`; caller-only lookup cannot distinguish every delayed old inbound from a replacement task.
- `resolve` can atomically persist the claim, reservation and frozen authorization before returning `DIAL_TASK_CALLEE`; an API retry with the same `callId` returns that decision.
- Exactly-once external dialing cannot be guaranteed by backend idempotency alone. The plan explicitly assigns durable `callId` idempotency to the IVR outbound operation and requires a new task after a terminal outbound failure.
- Recording notice/consent and direct-entry caller confirmation are distinct from task callee-number confirmation.

## Findings

No blocking findings. The plan keeps the change narrow, identifies the current contradictory summaries, preserves the existing IVR/media ownership boundary, and specifies task claim plus quota reservation as one transaction. It also covers response-loss retry, single B-leg idempotency, failed/unanswered call settlement, unknown outcomes and non-claim behavior when eligibility fails.

## Open questions

- Before production launch, confirm whether the existing IVR can durably deduplicate outbound operations by `callId`, including restart and response-loss recovery. If not, automatic retries could place duplicate calls; this is an implementation readiness condition, not a reason to add callee confirmation back into the product flow.
- Product/legal must finalize recording notice and consent wording/timing independently of callee confirmation.

## Residual risks and tracking

- Caller-only correlation remains ambiguous: after a task is replaced, a delayed inbound may claim the current replacement task and automatically dial its callee. Owner: product/telephony/backend; destination: IVR integration and launch-readiness decision. No task code or line routing identifier is assumed by this plan.
- No runtime, database, IVR idempotency, real-line, recording-consent or performance behavior is validated in this documentation work unit; owner: backend/IVR/security/product.

## Lenses applied

- Goal-bound minimal design: each affected file synchronizes the confirmed auto-dial flow; unrelated activation, purchase, entitlement and direct-entry behavior remains unchanged.
- Architecture boundary: backend authorizes and freezes task/entitlement; IVR performs A/B dialing, bridge, recording and authoritative call reporting.
- Best practice / optimal path: one transaction avoids a claimed task without a reservation; IVR-side durable operation identity handles uncertain API delivery without duplicate B legs.
- Overengineering / overcoupling: no new service, media engine, task-code flow or multi-task queue is introduced.
- State / recovery / test coverage: the plan includes expiry, eligibility failures, same-`callId` replay, outbound terminal failure, no-answer, bridge failure, lost responses and authoritative reconciliation.

## Conclusion

`pass-with-risks`. The revised scope is suitable for the documentation implementation slice. Caller-only late-inbound misbinding, durable IVR outbound idempotency and recording-consent policy remain explicit pre-launch risks with owners; this review does not treat them as solved.
