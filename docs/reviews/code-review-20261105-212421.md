### 1-未修复-低-计划 §8.3 要求 rotation 全部八个 error-code 映射，web owner 测试 rotate 循环仅覆盖七个（缺 UNAUTHENTICATED/401）

- **入口/函数**: `CustomerSharesCommandWebTests.revokeAndRotateMapClosedResponseUnions` 中的 rotate 错误码循环（非 revoke 循环）。
- **文件(行号)**:
  - `backend/src/test/java/com/onecall/archtests/CustomerSharesCommandWebTests.java:176-183`（实际只遍历 7 个 code）
  - 对照：同文件 `:132-140` revoke 循环含 `UNAUTHENTICATED → 401`
  - 对照：同文件 `:268-269` 仅对 `.../revocations` 做 401 探测
  - 对照：同文件 `:393-396` `Fixture.rotate()` 恒带 `Authorization: Bearer test`，verifier lambda `:366-368` 恒成功 → 本方法内 rotate 不可达 401
  - 对照：同文件 `:341` `problem()` 在 `status == 401` 时已断言 `WWW-Authenticate: Bearer`（补一行即可免费覆盖）
  - 计划：`docs/gateflow/pa14-sharing-command-code-rotation-plan.md:214` §8.3 行
  - 合同：`api/openapi/onecall-v1.openapi.yaml:3012+` POST `/api/v1/customer/shares/{shareId}/code-rotations` 的 `x-onecall-error-codes` 恰为八项：`UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, VALIDATION_FAILED, SHARE_TRANSITION_CONFLICT, RATE_LIMITED, SERVICE_UNAVAILABLE, INTERNAL`
- **输入场景**: 对 rotate 路由执行计划 §8.3 规定的 “all eight rotation error-code mappings” 断言；即对 `POST .../code-rotations` 逐一注入 `ShareCommandException` / 触发 filter 401，断言 Problem 响应。
- **实际分支**: 循环 `Map.of(FORBIDDEN 403, NOT_FOUND 404, SHARE_TRANSITION_CONFLICT 409, VALIDATION_FAILED 422, RATE_LIMITED 429, SERVICE_UNAVAILABLE 503, INTERNAL 500)` —— 七项，**无 `UNAUTHENTICATED / 401`**。
- **预期行为**: 计划 §8.3 明确要求 “all eight rotation error-code mappings, no revoke-only stale/410 leakage”。八个 code 与冻结 OpenAPI `x-onecall-error-codes` 一一对应；401 应在 rotate 路由上被 web 层 owner 测试直接断言（含 `WWW-Authenticate: Bearer`）。
- **实际行为**: rotate 路由在 owner web 测试中**从未**返回/断言 401；全仓 grep 显示 401 探测仅存在于 `revocations` 路径（`:268-269`）与 GET-list bearer 探测（`CustomerSharesWebTests.java:276-293`）。`CustomerSharesWebTests` 的 suffix 循环（`:500-535`）对 `code-rotations` 使用已认证 `Bearer personal`，得到 503/404，不覆盖 401。
- **直接证据**:
  1. `CustomerSharesCommandWebTests.java:176-183` — rotate 循环 7 键（见上）。
  2. `CustomerSharesCommandWebTests.java:132-140` — revoke 循环 11 键，含 `UNAUTHENTICATED, 401`。
  3. `CustomerSharesCommandWebTests.java:268-269` — 唯一 401 探测 URL 为 `PATH + "/share:fixture/revocations"`。
  4. `CustomerSharesCommandWebTests.java:393-396` — `rotate()` 恒发 `Bearer test`；`:366-368` verifier 恒返回 session。
  5. 计划 `:214` 原文：`... all eight rotation error-code mappings, no revoke-only stale/410 leakage; retain revoke and shared writer/query mappings.`
  6. OpenAPI `:3012+` `x-onecall-error-codes` 八项列表（见上）。
  7. 生产路径存在且在兄弟路由已验证：`CustomerBoundaryFilter.java:65` authenticate → `:108-112` catch → `CustomerProblemWriter`；`problem()` `:341` 已支持 401 断言。
- **影响**: **计划符合性 / 测试充分性缺口，非生产缺陷**。401 生产路径由共享 filter/handler 承担，并在 revoke 路由与 GET-list 上被直接证明；rotate 路由复用同一 filter 段。风险是：若未来有人改动 filter 中 rotate 的 route 分支或 auth 顺序，owner web 测试不会因 rotate 缺 401 而失败。同时削弱计划 §8.3 作为验收契约的字面满足度。
- **次要附注（并入本 finding，不另计）**: “no revoke-only stale/410 leakage” 在本 owner 方法中**没有显式 web 级否定断言**（rotate 循环 simply 不含 410/`SHARE_REVOKED`/`SHARE_GENERATION_STALE`），但已由 IT/服务层强证明：`CustomerShareCommandsIT.java:1446` 将一切非成功 rotate（含 `REVOKED` 状态）映射为 `SHARE_TRANSITION_CONFLICT`，永不 410；`DefaultCustomerShareCommandService.rotate()` 路径只抛 `SHARE_TRANSITION_CONFLICT`。故不升格为独立 finding。
- **建议改法和验证点**:
  1. 在 `:176-183` 的 `Map.of` 中增加 `ShareCommandException.Code.UNAUTHENTICATED → 401`（或等价地增加一次对 `PATH + "/share:fixture/code-rotations"` 缺/坏 bearer 的 `problem(..., 401, "UNAUTHENTICATED")` 探测，仿 `:268-269`）。
  2. 验证点：`mvn -Dtest=CustomerSharesCommandWebTests test` 仍零失败；`problem()` 已断言 401 的 `WWW-Authenticate: Bearer` 与 5 字段 Problem；`verifyNoInteractions(commands, query)` 仍成立。
  3. 若补“410 不泄漏”显式断言，可在同方法对 rotate 注入 `ShareCommandException.Code.SHARE_REVOKED` 并断言**不**按 410 呈现（当前生产根本不抛该 code，预期走 500/INTERNAL 或保持缺省）——可选，非阻断。
- **修复风险**: 低。仅扩展现有 owner 方法内的既有循环/探测，不改生产、不改 CI 清单、不新增测试方法（若仅加 Map 键，Surefire 计数不变）。
- **严重程度**: **低**。
