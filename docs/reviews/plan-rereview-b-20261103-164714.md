### R-04 — Medium: the plan never states the `25006`/`42501` precedence, and its instruction for the two existing read-only write probes is ambiguous and probably wrong in place

**Scenario.** Implementer applies plan `:71` ("Replace the claim that the query role has an authorized write blocked by read-only mode with ACL denial"; "Query role unauthorized writes/foreign reads produce `42501`") by editing the two existing assertions in place, keeping the surrounding read-only transaction.

**Evidence.** Both existing probes are authorized-then-read-only proofs executed inside a **read-only** transaction: `SharingQueryFixture.java:267-270` runs `UPDATE sharing.evidence_share_grant SET revision = revision + 1` on the pooled connection inside the Spring read-only/REQUIRES_NEW transaction (read-only asserted at `SharingQueryServiceIT.java:325`/`:414` and `CustomerSharesIT.java:262-263`), recorded as `fixture.writeState` and asserted `"25006"` at `SharingQueryServiceIT.java:319`; `CustomerSharesFixture.java:328-341` does the same with `connection.setReadOnly(true)` + `SET LOCAL ROLE sharing_role` + `transaction_read_only = 'on'` and asserts SQLSTATE `25006`. In PostgreSQL, a DML statement in a read-only transaction is rejected when the executor starts (`ExecCheckXactReadOnly`, `SQLSTATE 25006`) *before* the range-table permission census (`ExecCheckRTPerms`, `42501`) that the same start path performs afterwards. The plan itself relies on exactly that ordering for the new IT ("All expected `42501` attempts occur in **writable** transactions, each isolated by a savepoint"; "`25006` … an **otherwise-authorized** UPDATE … in an actually read-only transaction"), but never states the rule, and its existing-site instruction implies the opposite for those two probes.

**Impact.** Two ways to lose: (a) the in-place edit yields `25006` where the plan demands `42501` → red build; (b) leaving both probes untouched keeps them green but *vacuous*, because a `25006` from a read-only transaction says nothing about whether the write was authorized — which is precisely the evidential claim the goal asks PA13 to replace. The plan's own `CustomerMeIT.java:198` contrast is right: there the write is authorized for `customer_iam_role`, so `25006` is genuine evidence, and V010 does not touch that principal.

**Correction.** State the precedence rule once as a plan-level fact; then pin the two sites: either keep each read-only `25006` probe **and** add, in the same test, a writable-transaction `42501` probe for the same UPDATE (preferred — it preserves the pool/read-only evidence the goal requires while adding the missing ACL evidence), or convert the probe and say so explicitly, naming the file, the helper (`assertSharingReadOnlyWriteDenied`) and both expected SQLSTATEs.

This is the last genuinely unpin-able catalog value in the plan.

**Correction.** Pin, per statement, which role context performs each revoke, and prefer the migration-superuser context (or superuser-then-owner belt-and-braces) for the three `V009:5-7` items; then either (a) require grantor comparison only for ACL items V010 itself creates (owner-recorded, deterministic), or (b) state the expected grantor rule as "the recorded grantor must be the object owner or the bootstrap identity actually used, asserted as a per-fixture set", so the two fixture identities do not force two different expectations.
