### N-01-未修复-高-spool 无快照时点契约，drain 与 peakOccupancy 在任一单一快照下必有一错

- **位置**: §4.2 Spool 输入表（lines 206-213）、§4.3 F-SPOOL-01/02/03（lines 262-264）、§4.5 Spool bullet（line 292）、§6.3 `s1-04`（line 360）。
- **问题类型**: 契约缺失 / 恢复语义欠定义 / 不可直接实施。
- **当前写法**: `used=disk−free`，`peakOccupancy=used+SPOOL_NEW_PEAK_BYTES_PS×outage`（F-SPOOL-01）；free"已排除"existing、"existing 只参与 drain 与一致性"；`existing=0 => drain 0`，否则 `drain=existing/(recoveryTotal−continuing)`（F-SPOOL-03）。所有 spool 标量无任何 as-of/时点标注（全文 asOf 仅 backupRecovery 必需）。
- **反例/失败场景**: 快照=中断开始（对投影公式的自然读法）：pre-outage backlog=0、new=10 MB/s、outage=3600 s → peakOccupancy=used+36 GB（正确投影），但 F-SPOOL-03 drain=0——恢复期必须上传的 36 GB 无任何排空时间指标；controller 反例 2 精确成立。快照=中断结束：used/existing 已含中断产量 → drain 正确，但 peakOccupancy 二次计入 → 假 overflow、freeAfter 偏小。
- **为什么有问题**: 同一组单值输入无法同时服务两个公式要求的不同时点；`s1-04` 的"零 backlog => 0 drain"断言会在投影语义下把恢复时间空洞固化进 validator。
- **直接证据**: plan lines 206-213、262-264、292；line 98/219（asOf 仅 backup）；无"快照/snapshot"语义（grep 仅命中 §3 无关"registry 快照"）。
- **影响**: 实施 agent 必须自行猜测时点 → 恢复核心场景输出系统性失真（drain=0 或假 overflow）；后续实现/联调按错误排空时间做缓冲决策的风险。
- **建议改法和验证点**: 声明单一快照契约（建议：disk/free/existing/new/outage 全部 as-of 恢复开始；existing 显式含或将中断产量单列为 `PROJECTED_OUTAGE_BACKLOG_BYTES`，drain=(existing+projected)/net 且 peakOccupancy 不再重复加成）；`s1-04` 增加 existing=0+正中断产量场景，断言 drain/overflow 与契约一致且无二次计入。
- **修复风险（低）**: 纯 plan 措辞+一个输入字段/一条公式的局部调整，不新增 slice、不触碰上游契约。
- **严重程度（高）**: 恢复中心公式在核心场景二选一必错，属直接可证的语义矛盾。
