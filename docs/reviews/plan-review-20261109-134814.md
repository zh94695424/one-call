## Findings

### 01-未修复-中-Replay expiry-equality rule contradicts the existing sub-microsecond replay tolerance tests and the plan's "preserve all replay assertions" instruction

- **Status**: accepted-candidate
- **位置**: Plan §4.2 line 57 ("Replay takes expiry from the validated committed event, requires equality to the current normalized bound, and never extends it"); Plan §8.1 line 187 ("Preserve all replay/event/transaction/redaction assertions"); Plan §10.2 line 281/line 284; existing `ShareAdmissionServiceTests.sameAuthorizationRequestAndPurposeReplaysCredentialAndEvent` and `PublicShareAdmissionIT.mediaAuthorizationUsesExactRouteAndFrozenResponse`.
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口 / 不可直接实施
- **当前写法**: The plan makes the real authority's expiry the normalized witness bound (correct), and separately says replay "requires equality to the current normalized bound". It also says the existing replay assertions must be preserved and does not name or reconcile the two sub-microsecond replay tests.
- **反例/失败场景**: The existing tests deliberately return a provider expiry of `sessionExpiresAt().minusNanos(1)` (truncated to microseconds = one microsecond before the bound). The first call is accepted; the event payload stores the sub-bound `credentialExpiresAt`; the second (replay) call must return the identical result and write `REUSED_IDENTICAL`, with one durable event and two provider calls. If the implementation applies "committed expiry == current normalized bound" literally to replay, the second call rejects with `DEPENDENCY_UNAVAILABLE`/conflict and both tests go red. If the implementation preserves the existing `providerExpiry <= bound` tolerance, it does not implement the plan's stated replay equality invariant. The plan does not say which is intended, nor does it name either test in §8.1.
- **为什么有问题**: The two assertions are mutually exclusive for a synthetic/legacy event whose committed provider expiry is strictly below the bound. The existing `EventWriteStatus` and `validCredential` contract (`expiry <= bound`, after now) intentionally allow sub-bound expiries; the new sentence appears to tighten replay to exact equality without an explicit behavior change, expected error code, or test update. This is a security-adjacent replay/acceptance contract, not a style issue.
- **直接证据**:
  - `backend/src/test/java/com/onecall/archtests/sharing/ShareAdmissionServiceTests.java:375-393`: `for (boolean subMicrosecond : List.of(false, true))`; provider result `new Issued("credential-private", f.witness.sessionExpiresAt().minusNanos(1))`; `expectedExpiry = Instant.parse("2026-01-01T00:07:59.999999Z")`; `second == first`; `eventWrites == [INSERTED, REUSED_IDENTICAL]`; `issued.hasSize(2)`.
  - `backend/src/test/java/com/onecall/archtests/container/PublicShareAdmissionIT.java:495-531`: `mediaProviderMode="SUB_MICROSECOND"`; `expectedExpiry = mediaBoundText(...).minusNanos(1).truncatedTo(MICROS)`; first response 200; replay body equal; one `PLAYBACK_AUTHORIZED`; zero `FAILURE`; `credentialCalls=2`; `semanticCredentials=1`.
  - `backend/src/main/java/com/onecall/core/sharing/internal/admission/DefaultShareMediaAuthorizationService.java:78-81,96-100,208-212`: the service persists the provider expiry and validates `expiry <= bound` (not equality).
  - Plan §4.2 line 57; §8.1 line 187.
- **影响**: A codegen agent can either break existing replay/event assertions or silently skip the new equality invariant; the plan's "byte-identical replay" proof and "preserve all replay assertions" claim cannot both be verified. Review cannot accept the replay expiry contract as code-generation-ready.
- **建议改法和验证点**: State the exact rule: the real authority always issues and commits exactly the normalized bound, while the service preserves its existing `providerExpiry <= bound` tolerance for synthetic/legacy providers (then keep both tests unchanged); or explicitly change both sub-microsecond tests to the new expected mapping (for example, exact-bound success or deterministic conflict) and name them in §8.1. Pin the expected result/error for a committed sub-bound expiry on replay. Verification: run both named tests plus the new `issuanceUsesOnlyWitnessExpiryBound` and `advancingClockReplayReturnsFirstCredential`.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
