## Material Findings

### PR-001-未修复-[中]-S1 静态验证命令与 48 方法检查点矛盾且迁移数量检查不闭合
- **位置**: `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:556`, `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:624`, `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:632`, `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:654`
- **问题类型**: 不可直接实施 / 测试缺口 / 契约缺失
- **当前写法**: S1 completion requires exactly 48 methods, but the only static method-count command executes `test "$(wc -l ...)" -eq 51`. The same block labels the migration listing as “Exactly one new migration and no V008+ migration” but only prints `find ... | sort`; it never asserts the exact seven-name set or absence of V008+.
- **反例/失败场景**: A correct S1 implementation with 48 methods fails the prescribed static command before it can satisfy the S1 completion report. Conversely, a workspace containing V001-V008 merely prints eight filenames and can continue, so the command can be cited without having enforced the stated V007-only boundary.
- **为什么有问题**: The plan claims code-generation readiness and exact per-slice validation. A guaranteed false S1 assertion forces the implementation agent to improvise or silently edit the command, while the non-asserting migration listing does not fail closed on future-slice leakage.
- **直接证据**: S1 states “CI expected set/count 48” and “exactly 48 named container tests” at plan lines 560 and 575. The command at line 636 hardcodes `51`. The comment at line 629 claims an exact migration boundary, but lines 629-630 contain no `test`, comparison or expected-name set.
- **影响**: S1 cannot be completed using the plan verbatim; validation results become non-reproducible, and an accidental V008+ migration can escape the static gate.
- **建议改法和验证点**: Define an explicit per-slice value such as `EXPECTED_METHODS=48` for S1 and `EXPECTED_METHODS=51` for S2, and use it in both source and XML checks. Replace the migration print-only command with an exact comparison against the sorted V001-V007 filename list and an explicit count of 7. Verify both variants by running the static block once at the S1 checkpoint and once at S2 without manual command rewriting.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-002-未修复-[高]-现有 V004 孤立 purchase_consent_id 成功行为会被替换而非分阶段保留
- **位置**: `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:440`, `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:451`, `docs/gateflow/pa7-v007-activation-consent-foundation-plan.md:467`, `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:15790`
- **问题类型**: 测试缺口 / 切片过粗 / 不可直接实施
- **当前写法**: The plan stages catalog absence at V004/V006 and changes every final-database valid order insert to use a real consent parent. It promises to preserve every V001-V006 behavior assertion, but it does not specify how to retain the current executable assertion that a fully valid V004 order with a random orphan `purchase_consent_id` succeeds before V007.
- **反例/失败场景**: An implementer follows section 7.3 and replaces the random UUID in `v004OrderPaymentLifecycleAndAppendOnlyBackstops` with a real consent fixture. The final suite passes, but the prior executable proof that V004 intentionally accepts a non-null orphan consent ID is gone. Merely querying that the FK is absent does not execute the insert path and cannot detect an unintended V004 insert trigger or other referential backstop.
- **为什么有问题**: V004 deliberately introduced a non-null column without an FK until V007. The plan itself says prior behavior assertions must not be weakened and that absence evidence should move to the prefix where it remains true. The staged plan records FK/catalog absence but omits this concrete behavior assertion, so the cumulative evidence contract is incomplete.
- **直接证据**: Current code at `PostgresContainerIT.java:15790` states “Valid order insert with a random purchase_consent_id (no parent) succeeds” and executes that insert. Plan section 7.1 stages only migration counts/object/grant/FK absence. Plan section 7.3 requires all final valid inserts to use real consent parents. Plan section 7.2 simultaneously requires preservation of every V001-V006 behavior assertion.
- **影响**: Accepted V004 evidence is weakened during a cumulative migration change, a regression in the intended late-FK timing can become unobservable, and review cannot prove that V007—rather than an earlier wave—first closes the referential boundary.
- **建议改法和验证点**: Add an explicit staged-V004 transactional probe before migrating to V005: create the minimal valid V004 parents and catalog rows, insert one customer order with a random non-null orphan `purchase_consent_id`, assert success, and roll the transaction back so V007 migration is not blocked. Record the result and assert it in the renamed cumulative V004 method. Keep the final-database version of the order lifecycle test on a real consent parent and separately prove final orphan failure with exact `fk_customer_order_consent` `23503` evidence. This can remain count-neutral and does not require a seventh test method.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
