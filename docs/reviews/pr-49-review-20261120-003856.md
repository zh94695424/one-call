### PA38-PRR-B-02 — High — CRLF line endings break the CI entry point this PR depends on; the residual label "hygiene" understates it

**Reproduced in this workspace**
- 2,237 of 2,343 files contain CRLF (474 of them under `backend/`, one being `.github/workflows/ci.yml`), and **there is no `.gitattributes` anywhere in the tree**, so nothing normalizes line endings at checkout.
- `file backend/mvnw` → "POSIX shell script, ASCII text executable, **with CRLF line terminators**"; the first bytes are `#!/bin/sh\r\n`. Executing it: `./mvnw: /bin/sh^M: bad interpreter: No such file or directory`. Deleting only the CRs makes the script run (it then correctly reports the missing `./.mvn/wrapper/maven-wrapper.properties` because I ran it from the wrong directory) — so CR is the sole blocker, not a missing wrapper jar. `ci.yml` invokes `./mvnw` four times (`:53`, `:54`, `:59`, `:2556`) with `defaults.run.working-directory: backend` (`:38-39`) on `ubuntu-latest`.
- `backend/.java-version` is `21.0.13+9\r`. `ci.yml:50` runs `grep -Fx '21.0.13+9' .java-version`: exit status **1** on the shipped bytes, **0** on the CR-stripped copy (both demonstrated here). Since `-x` requires a whole-line match and the line retains its `\r`, the very first CI step fails before Maven is ever invoked.
- All five `.pa5-*.sh` launcher scripts at the repo root have the same `SHEBANG-CRLF` defect, so the local gate drivers are affected on any POSIX host too.

**Why 18 review rounds missed it** — The ledger was deliberately made CRLF-tolerant while the runner was not. `EvidenceRoleIvrAssociationAclBoundaryTests.java:99` asserts `hash(raw) ∈ {crlfDigest, lfDigest}` but `hash(lf(bytes))` must equal the pinned value, and the manifest is built from `hash(lf(...))`. So `310 / 1e0a68c8…` and `32 / 572,661 / 8b6ac652…` reproduce identically either way (I confirmed both), and the `@Test` line scan is `\r\n`-agnostic. Nothing in the chain executes a file.

**Honest limit** — This workspace is a file copy with no `.git` (confirmed: `fatal: not a git repository`), so I cannot inspect the committed blob directly. The blobs may be LF if the contributor's Windows checkout applied `core.autocrlf=true` — but there is no `.gitattributes` to make that deterministic for a fresh Linux runner, so the risk is live and unresolved regardless.

**Smallest remediation** — Add `.gitattributes` with `* text=auto eol=lf` plus explicit `*.sh text eol=lf`, `mvnw text eol=lf`, `.java-version text eol=lf`, renormalize (`git add --renormalize .`), and prove it with one Actions run. Reassign this item from "hygiene" to a merge blocker owned by Backend/CI in the current-status file.

### PA38-PRR-B-05 — Low — `EmployeeAuthorityReadPort.Failure.sqlState` is recorded but cannot reach any decision, so the "alive transaction" cleanup branch is taken on provably aborted transactions

The port builds its failure with a null cause — `super("Employee authority unavailable", null, false, false)` (`EmployeeAuthorityReadPort.java:14`) — and stores the state only in a private field with a getter (`:16`). The command classifies by walking the *cause chain* for `SQLException`/`DataAccessException` (`DefaultOperationsCatalogSaleCommand.java:67-72`), so for any port failure `sqlState(failure) == null` and the guard at `:58` concludes the transaction is still usable and calls `repository.restore(witness)` (`:59`). If the port failed because of an SQL error (`42501`, `40001`, …) PostgreSQL has already aborted the transaction, so `SET LOCAL ROLE NONE` inside `restore()` fails with `25P02`, `restore()` rewrites it to `unavailable()` (`JooqCatalogSaleLifecycleRepository.java:66`) and the catch at `:60` discards the real diagnostic in favour of a generic 503. The outcome is fail-safe — rollback still runs via `status.setRollbackOnly()` at `:57`, and the role can never survive into a pooled connection — so this is a wasted round trip plus a lost cause chain, not a leak. The only assertion touching the field, `DefaultOperationsCatalogSaleCommandTests.java:61` (`assertThat(authorityFailure.sqlState()).isEqualTo("42501")`), reads back the value the test itself just constructed. Suggest either having `sqlState()` consult the port failure first, or dropping the field and letting the command rely on `holder.setRollbackOnly()` already performed at `DefaultEmployeeAuthorityReadPort.java:38`.

### PA38-PRR-B-08 — Low — Catalog lifecycle vocabulary now lives in `operations_iam`, and the operations route allowlist is duplicated as regex text in two filters

Two related coupling costs of this slice, both defensible and both real:

## 4. Adversarial review — attacks that the implementation survives

I tried to break the slice in the areas the task named and could not. Recording these as tested rather than assumed:

- **Auth/error precedence.** `OperationsCatalogVersionController.java:38/:44` resolve `caller(request)` *before* `body(request)`, so 401 precedes 400; `structuralValidationPrecedesAuthorityWitness` and `authenticationPrecedesStructuralParsing` pin it; and inside the transaction the authority check (`DefaultOperationsCatalogSaleCommand.java:48-51`) precedes the lock, the reads and the existence check, so a non-ADMIN never learns whether `versionId` exists (`missingAuthorityMapsToServiceUnavailable` verifies `repository.catalogRole` is not even reached). Missing/non-admin authority fails closed to 503 rather than 403, which is the conservative direction.
- **Bounded bodies.** `readNBytes(8193)` (`:49`) plus the `length > 8192` rejection (`:69`) bound memory regardless of `Content-Length`, and `CatalogVersionRequestBinderTests`/`OperationsCatalogVersionWebTests.java:161-177` measure exactly 8,192 and 8,193 bytes consumed for both declared-length and chunked 2 MB inputs. Malformed UTF-8, duplicate keys, trailing tokens, non-canonical UUIDs, `2147483648`, quoted and fractional numbers, unknown fields (`reason`, `idempotencyKey`, …) and `null`/`[]`/`{}` bodies all reach 422 before any DB touch.
- **PostgreSQL lifecycle and concurrency.** `begin()` (`:35-54`) clears the bound connection, installs three `SET LOCAL` limits, requires `session_user == current_user` on entry, captures login/PID/xid, and re-reads the settings to prove `2s`/`250ms`/`5s`; `assertIdentity` (`:89-95`) re-proves identity *and* the same `Connection` object on every hop, including the `pg_stat_activity`-observable advisory-lock wait; `connection()` (`:76-83`) rejects autoCommit, read-only, non-`READ_COMMITTED` and out-of-transaction execution. `REQUIRES_NEW`/`READ_COMMITTED`/timeout 5/not-readOnly is asserted at bean-creation time (`CatalogSaleLifecycleConfiguration.java:20-21`), so a mis-wired template fails startup rather than silently joining an outer transaction.
- **Replay.** `recover()` (`:146-155`) is reachable and correctly conservative: a `40001` injected before the transition read (`SERIALIZATION_AT_READ`) replays to 200 with zero new facts, while `23505`/`SERIALIZATION_AT_ACTIVATION` lose to a competitor and resolve to 409. `recoveryWitness` (`OperationsCatalogVersionLifecycleFixture.java:134-148`) proves the recovery transaction is a fresh xid, enters and exits `catalog_order_role` exactly once, and performs no authority read, no `UPDATE`, no advisory lock and no appends — so the recovery path cannot write.
- **Audit/Outbox atomicity.** `auditFailureRollsBackLifecycle` (including the `STATEMENT_TIMEOUT`/`57014` variant) and `outboxFailureRollsBackLifecycle` (all three outbox stages) each assert the full `catalog_version` table is byte-identical afterwards with `facts(0, 0)`. Retirement-before-activation ordering is enforced twice — textually (`OperationsCatalogVersionBoundaryTests.java:17`) and behaviourally (`retirementStatementPrecedesActivation`) — matching `docs/14` §9.26 step 3, which also sanctions one audit fact with two Outbox identities for a displacement (`publicationWithOldActiveHasOneAuditAndTwoOutboxes`, and `oneActiveInvariantHoldsAfterEveryCommit` expecting `facts(4, 7)` across four publishes). The audit fact and the candidate Outbox event share a dedupe key, so they are correlatable after the fact.
- **Role restoration.** Only `SET LOCAL` is used, so abort, rollback and commit all discard it; `restore()` (`:62-68`) asserts the effective user is back to the original login and clears the binding in a `finally`; the failure branch rolls back rather than trusting a partial cleanup (`DefaultOperationsCatalogSaleCommand.java:56-64`, per the plan's "SQL-aborted transactions roll back before any further query"); and the pool independently refuses to reuse a connection whose `session_user != current_user` or whose three timeouts drifted (`GuardedReadDataSource.session()`), setting `cleanupFailure` under the physical connection, which the template's `finally` promotes to a 503 that overrides even a prospective success or 409. `TERMINATE_BEFORE_ROLE_RESTORE` proves the eviction. I could not construct a sequence that commits, or returns to the pool, with a role other than the login.
- **No-new-privilege check for "no V019".** I verified the claim instead of accepting it: `catalog_order_role` already holds column-level UPDATE on exactly `sale_status, published_at, revision` (`V004:426-428`), EXECUTE on `platform.outbox_append` (`V004:34-35`) and `audit.append_fact` (`V004:43-44`), SELECT on `catalog_benefit_line` (`V004:432`), and `operations_iam_role` holds SELECT on `operations_iam.employee_account` (`V002:347`).
