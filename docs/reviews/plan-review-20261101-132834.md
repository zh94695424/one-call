- **影响**: Review acceptance is not attributable to a frozen target; implementation may be authorized against a different plan/contract package; peer independence and later re-review reconciliation are compromised; the gate cannot be closed on this artifact set even if the plan content otherwise passes.

### 02-未修复-中-blocking lifecycle locks and table scans have no production timeout despite a timeout-to-503 claim

- **位置**: `docs/gateflow/pa10-sharing-application-service-plan.md:90,96-100,113,152,207,255`; runtime configuration contract and §9 test `lifecycleChecksSerializeAndTechnicalFailureRollsBack`.
- **问题类型**: 并发恢复风险 / 测试缺口 / 契约缺失
- **当前写法**: The service takes blocking `pg_catalog.pg_advisory_xact_lock` calls for account/organization/membership lifecycle checks, uses a fresh read-only transaction, and maps connection/role/timeout/migration availability failure to sanitized `SERVICE_UNAVAILABLE`. The plan also says there is intentionally no production pool sizing or timeout/SLO policy and that only integration-test statement/lock/future timeouts are bounded.
- **反例/失败场景**: An organization-status, membership, or account owner transaction holds one of ranks 7/8/9 while waiting on another operation; a listing blocked on the advisory lock, or a listing scan blocked by a long-running transaction, waits indefinitely. Requests consume Hikari connections until the pool is exhausted, so no `SERVICE_UNAVAILABLE` result is produced and unrelated callers are starved. The test-side timeout does not prove the production service path ever times out.
- **为什么有问题**: The plan names timeout behavior as part of the sanitized failure contract but deliberately selects no production bound that can produce it. The query has no index for the planned creator/workspace/order predicate, so a full scan can itself be unbounded as the table grows. A plan that claims fail-closed availability without a trigger for that failure is not code-generation-ready.
- **直接证据**: The plan requires blocking `pg_advisory_xact_lock` at lines 100 and a production transaction at lines 96-98, but its exact configuration keys at line 90 contain only URL/user/password/migration values and explicitly exclude production pool sizing and timeouts. Line 113 maps timeout to `SERVICE_UNAVAILABLE`; line 207 only promises bounded fixture timeouts; line 255 tracks real PostgreSQL behavior but not a query/lock timeout owner. `backend/src/main/resources/application.yml` contains no persistence timeout configuration, and the current POM has no new runtime dependency yet.
- **影响**: A single stuck lifecycle lock or slow scan can hang all share listing and exhaust the query pool. The implementation can satisfy the happy-path tests and still fail the service’s stated availability and failure-path contract. The test matrix would not catch the gap.
- **建议改法和验证点**: Define a bounded production query/lock/connection behavior, either through a minimal approved `statement_timeout`/`lock_timeout`/Hikari acquisition setting or an explicit non-blocking/controlled refusal path, and map the exact PostgreSQL timeout SQLSTATEs (for example cancellation `57014`) to sanitized `SERVICE_UNAVAILABLE`. Add a bounded integration test with a held rank-7/8/9 lock and an exhausted/slow query path that proves the caller returns the sanitized failure within a finite deadline, releases the role/transaction, and leaves the pool reusable. If production timeout values are intentionally out of scope, remove the unproven timeout-to-503 claim and record the unbounded wait as an explicit residual risk with an owner and destination before accepting the plan.
- **修复风险（低/中/高）**: medium
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-migration and query target equality is asserted but has no executable check

- **位置**: `docs/gateflow/pa10-sharing-application-service-plan.md:90,92`; configuration keys and Flyway startup contract; `SharingPersistenceConfigurationTests`/runtime startup tests at `docs/gateflow/pa10-sharing-application-service-plan.md:187-190,198`.
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: When migration is enabled, the plan requires a separate migration URL/user/password, “same database target,” and a different user from the query login, but it does not specify how the two independently configured targets are compared or what happens when a JDBC URL has aliases, parameters, or different host spellings.
- **反例/失败场景**: Migration URL points at database `dbA` and query URL at `dbB`; Flyway successfully upgrades `dbA`, the query Hikari source starts on `dbB`, and the service returns empty or internal failures because the expected schema is absent or different. A textual URL comparison can also reject valid configurations such as `localhost` versus `127.0.0.1` or different query parameters for the same database.
- **为什么有问题**: “Same database target” is a safety invariant for the separate-credential model, not an implementation detail. Without a concrete validation method, an implementation agent must invent a check and may choose a URL-string comparison that is either bypassable or over-restrictive. The proposed unit test covers missing/separate credentials but not target identity.
- **直接证据**: Plan line 90 defines only `url`, credentials, and migration credentials; line 92 states the same-target requirement. The test inventory at lines 187-190 tests missing and distinct credentials, and the runtime test at line 198 verifies separate identities, but no test asserts that the two connections resolve to the same database. The plan provides no database identity key, metadata comparison, or negative same-target test.
- **影响**: A valid separate-credential deployment can silently query the wrong cluster/database, or a safe configuration can be refused as if it were unsafe. Both violate the stated runtime foundation and can turn a migration-success run into an unavailable or wrong-data service.
- **建议改法和验证点**: Specify the exact comparison using actual connections, for example canonical database identity plus server/database name (and, where relevant, server address/port), not raw JDBC string equality. Require both connections to be open and the migration history/schema version to be visible from the migration target before the query service is built. Add positive and negative tests for same database with differing URL spellings, different databases, different users, and missing migration credentials. If no implementable comparison is intended, remove the requirement and state the target-selection risk explicitly.
- **修复风险（低/中/高）**: medium
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-中-the migration-disabled runtime query path is claimed but not named in the test matrix

- **位置**: `docs/gateflow/pa10-sharing-application-service-plan.md:92,158,187-207`.
- **问题类型**: 测试缺口 / 过度验收标准未落地
- **当前写法**: The plan says an existing provisioned schema can be queried with `migration.enabled=false`, but the exact Surefire inventory only tests missing/separate migration properties at the configuration level, and the named runtime startup test uses migration enabled. No listed test starts the actual service against externally migrated V001-V009 with the application migration path disabled.
- **反例/失败场景**: The implementation accidentally makes the query service depend on the Flyway bean, or rejects a pre-provisioned schema when migration is disabled. All current named tests can remain green because no test exercises that supported mode; the first such deployment fails at startup or on first listing.
- **为什么有问题**: This is not merely an optional extra test: the plan states migration-disabled operation as a supported behavior and the profile is intentionally opt-in. The test matrix must prove both startup modes rather than infer one from property validation.
- **直接证据**: Plan line 92 states the supported mode. The `SharingPersistenceConfigurationTests` entry at lines 189-190 checks missing/separate properties, while the only named runtime startup test at line 198 is explicitly “credential/migration” enabled. The ten IT method set at lines 198-207 contains no migration-disabled query case. The plan’s expected counts (21/74) are exact, so this omission cannot be left to an unnamed extra test.
- **影响**: An implementation can pass the stated test inventory and still fail a supported deployment mode; the completion report’s claim that default/preprovisioned startup is verified would be false; the error is likely to surface only after handoff.
- **建议改法和验证点**: Add a named integration method that applies V001-V009 through the fixture/admin connection, starts the actual persistence context with `migration.enabled=false`, and executes personal and organization listings. Keep the exact method/XML/CI inventories synchronized; if the 10-method budget is fixed, replace or fold an existing method rather than silently adding an uncounted test.
- **修复风险（低/中/高）**: low
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. Which snapshot is authoritative: the supplied frozen hash manifest or the current detached checkout? The current checkout’s control and six supporting artifacts do not match the supplied hashes, so a fresh manifest is required before this plan can be gate-accepted.
2. What exact production timeout/connection-acquisition behavior is intended for the blocking lifecycle locks and the unindexed listing scan? If no production bound is intended, is unbounded waiting acceptable for this slice, and who owns the operational follow-up?
3. Which concrete database/schema identity check will enforce migration/query same-target equality, and is that check intended to reject differing JDBC URL syntax for the same database?
4. Is migration-disabled querying against an externally provisioned schema part of the acceptance signal for PA10, or should that claim be removed from this slice? If it is part of acceptance, what named test proves it?
5. Are unknown/inconsistent enum or nullable database values possible through any supported migration/provisioning path? If yes, which named negative test proves the plan’s stated sanitized `INTERNAL` behavior? If schema constraints make them impossible, this can remain a residual integrity risk rather than a new test requirement.
6. Q15 wire cursor serialization, Q17/Q23 production login/role provisioning, customer authentication, HTTP mapping, and policy values remain deferred. The plan should continue to state that the application service cannot be called from an external client in this slice.

## Plan Review Conclusion

**Verdict: fail.**

The plan is materially aligned with the binding goal: the personal and organization predicates are correct, the creator-only invariant is explicit, the eleven-field projection matches the frozen OpenAPI shape, V009 grants the needed reads, the default profile remains database-free, and the proposed source/test inventories are coherent. The baseline Maven suite passed.

It cannot be accepted in its current review package. The frozen input manifest does not match seven of the eight supplied artifacts. Independently of that integrity failure, the plan does not define a production bound for its blocking advisory-lock/table-scan path while claiming timeout-to-`SERVICE_UNAVAILABLE`, does not specify an executable check for migration/query same-target identity, and does not name a test for the stated migration-disabled runtime mode. These are material availability, implementability, and verification gaps, not stylistic concerns.
