## Findings

### R-A18-01 — Grants legitimately captured without `bindingId` (`CURRENT` resolution) are rejected with 503 `DEPENDENCY_UNAVAILABLE`; the frozen contract requires the captured/current binding projection and 403 `SHARE_RISK_BLOCKED` for an unresolvable projection (High, material; contract/availability)

- Entry/function: `DefaultShareMediaAuthorizationService.authoritative` (`backend/src/main/java/com/onecall/core/sharing/internal/admission/DefaultShareMediaAuthorizationService.java:144`, with `:150-154`).
- Trigger: an existing PA17 admission whose `evidence.evidence_record.identity_at_capture` has no `bindingId`, i.e. a share created with the supported `CURRENT` binding resolution and a single active verified binding. `JooqShareAdmissionRepository.grant` maps this to `capturedBindingId == null` and `identityAtCaptureMalformed == false` (`JooqShareAdmissionRepository.java:49-50`).
- Actual branch: line 144 executes `if (grant.capturedBindingId() == null || grant.identityAtCaptureMalformed()) throw failure(DEPENDENCY_UNAVAILABLE);` before any current-binding read (lines 150-152 are only reached with a non-null captured id). The endpoint therefore always returns HTTP 503 `DEPENDENCY_UNAVAILABLE` for this state; no credential is issued and no event is appended.
- Expected: the plan §1/§3 step 6 require validating the “captured/current binding”; docs/14 §9.31.4 (`docs/14-production-data-model-and-flyway-schema-spec.md:3425`) requires rechecking the “exact captured/current binding plus `subject_risk_state` projection” and maps an absent/unresolvable binding/risk projection to `SHARE_RISK_BLOCKED`; T-S3-26 (`:4763`) repeats that mapping. PA17 admission already supports the `CURRENT` case: `DefaultShareAdmissionService.facts` selects `readCurrentBindings(...)` when `capturedBindingId == null` and accepts exactly one current active verified binding (`DefaultShareAdmissionService.java:193-197`). Share creation itself explicitly accepts `resolution == "CURRENT"` (`DefaultCustomerShareCommandService.java:172-174`), and the evidence contract says the capture object carries a binding reference only “if applicable” (`docs/14:2156,2198`). The service should mirror PA17: use the captured binding when present; otherwise resolve the unique current active binding; if neither resolves uniquely, return `SHARE_RISK_BLOCKED` (403), not a retryable 503.
- Direct evidence: the line-144 null check; PA17 `facts` fallback; the creation-path `CURRENT` acceptance; docs/14 `:3425,:4763`; and the new IT case `capturedAndCurrentBindingAndOpenOrMissingRiskDenyWithoutEvent` which corrupts `identity_at_capture` to `{}` and **expects `DEPENDENCY_UNAVAILABLE`** (`PublicShareAdmissionIT.java:645-649`), i.e. the test enshrines the non-contract behavior instead of proving the current-binding path.
- Impact: any PA17 admission created under the supported `CURRENT` resolution cannot obtain a media credential; the endpoint fails 503 on a legitimate, non-malformed durable state, and the frozen error surface (403 `SHARE_RISK_BLOCKED`) is not delivered. Clients will retry a state that the contract treats as a risk denial. This is a functional contract violation in the core authorization path, not merely a test gap.
- Fix direction: replace the unconditional rejection with PA17-equivalent binding selection: if `capturedBindingId == null`, load `readCurrentBindings(subjectId)` and require exactly one active verified binding; otherwise use the captured binding. If the captured binding is absent and the current set is empty or ambiguous, return `SHARE_RISK_BLOCKED` (403). Evaluate `readSubjectRisk` over the same resolved binding set. Update the `missing-binding-id` IT expectation and add a DB-backed `CURRENT`-resolution success and an absent/ambiguous-current denial.
- Fix risk: Medium. It touches the binding/risk block and the `missing-captured`/`missing-binding-id` test matrix; the captured-binding path must remain unchanged and the existing risk, `different-current`, `disabled`/`retired`/`unverified` and `OPEN` denials must remain green. No schema/ACL/OpenAPI change is needed.
- Severity: **High**; material, gate-blocking.

### R-A18-06 — Residual concurrency: a concurrent first-call pair can persist both a SUCCESS and a later FAILURE for one request key (Residual; within the accepted concurrency residual unless the Controller narrows it)

- Two callers can both pass the authoritative pre-provider lookup before either success event is durable (the grant lock serializes the read/lock transaction, but provider I/O is outside it by design). If one provider call succeeds and the other returns `Unavailable`/`Malformed`/throws, the first appends SUCCESS and the second appends FAILURE under different event IDs; PostgreSQL cannot make the two event identities mutually exclusive. The service's `priorSuccess` suppression (`:74,:81`) only sees a success that was durable in the caller's authoritative snapshot.
- The plan accepts concurrent provider I/O and database-only event conflict authority (§8 residual), and the named two-connection test uses a deterministic successful provider for both callers, so this interleaving is not exercised. The durable stream can still contradict “no later FAILURE after a success” under a partial outage.
- Impact: audit semantics under concurrent partial provider failure; no credential/success is falsely claimed (the failing caller gets 503). Fix direction (if the Controller wants strict exclusivity): re-check for a durable success inside the failure-append transaction before inserting, or define the accepted residual explicitly. Fix risk: Medium (a full guarantee needs a shared serialization point; a re-check narrows but does not eliminate the race without an event-identity change that the plan forbids).
- Severity: **Residual**; recorded, not the primary blocker.

## Open Questions

1. **OQ-1 (`CURRENT` resolution):** Should a grant whose `identity_at_capture` has no `bindingId` resolve the unique current active binding (PA17 `facts`, docs §9.31.4/T-S3-26), or is it intentionally `DEPENDENCY_UNAVAILABLE`? The plan and design contract point to resolving; the code and the `missing-binding-id` IT point to 503. The Controller should pin this before closing; this review treats the code as a material contract deviation.
2. **OQ-2 (`SHARE_SESSION_POLICY_UNAVAILABLE`):** Should absent/malformed/non-positive witness bounds map to `SHARE_SESSION_POLICY_UNAVAILABLE` (plan step 9) or `DEPENDENCY_UNAVAILABLE` (plan step 4)? Both are 503, but the frozen code and evidence text must agree.
3. **OQ-3 (existing admission, missing witness):** Should it be 403 `FORBIDDEN` (this code) or 503 `DEPENDENCY_UNAVAILABLE` (PA17 `existing.isPresent() && witness == null`)? The plan step 4 phrase “missing/mismatched admission/witness is a denied result” is ambiguous against “malformed/unreadable projection is 503”.
4. **OQ-4 (replay after credential expiry):** May a same request/purpose replay return the first (now expired) credential/expiry, or must it fail closed 503? The plan step 10 says replay returns the first credential but also requires the provider expiry to be strictly after the decision time.
5. **OQ-5 (concurrency):** Is the concurrent success+failure event pair for one request key accepted under the plan's “concurrent provider I/O / DB conflict authority” residual, or must the service add a success re-check before appending FAILURE?
