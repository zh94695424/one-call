# Plan review: account identity and workspaces

## Reviewed target and scope

- Target: `docs/gateflow/account-identity-workspaces-plan.md`.
- Binding scope: `docs/gateflow/account-identity-workspaces-control.md`.
- Evidence checked: Web login/workspace/session-expiry paths, shared business snapshot allowlist, existing Mini/Web QA and cross-channel authorization tests.

## Assumptions tested

- Account directory can remain outside `createDemoState` and snapshot/import: supported by the exact `BUSINESS_FIELDS` allowlist and forbidden auth/session keys.
- Enterprise permissions can be derived from selected membership: supported, but only if every login/restore/switch path validates that membership.
- Business-subject owner migration can retain authorization revoke semantics: supported because revoke targets the authorization record's canonical `subjectId`, not the current account ID.
- Raw provider subjects can be kept out of UI-facing lookup results while still resolving demo login: underspecified in the plan.

### PR-01-已修复 [高]-会话恢复可能继承前一账户的工作空间与角色
- **位置**: Slice S2 / Web changes / login and workspace state machine
- **问题类型**: auth / tenant isolation / 状态机漏洞
- **当前写法**: 计划要求正常选择工作空间时校验 membership，但没有覆盖 `finishLogin()` 的 `returnRoute` 分支。
- **反例/失败场景**: 管理员会话过期后，评审者改用普通成员手机号重新登录；现有 `returnRoute` 分支直接把 `session` 设为 signed-in 并恢复路由，旧的 `workspace='enterprise'` 与 `enterpriseRole='admin'` 可能继续生效。
- **为什么有问题**: 身份已经变化，授权上下文却来自旧会话；这会让“角色只来自当前账户有效成员关系”的核心成功信号失效。
- **直接证据**: `web-prototype/evidence-hub.html` 当前 `finishLogin()` 的 `returnRoute` 分支不调用 `enterWorkspace()`，直接恢复 `state.route`；`state.workspace` 和 `state.enterpriseRole` 是长期 UI state。
- **影响**: 原型可演示跨账户角色继承，属于明显提权回归，且普通 happy-path QA 不易发现。
- **建议改法和验证点**: 计划明确所有登录完成路径都先绑定新 `accountId`；恢复路由前，以 `currentWorkspaceId` 调用 `workspacesForAccount` 复核。不存在则进入工作空间选择页并丢弃旧授权上下文。新增“管理员过期 -> 普通成员重新登录”回归测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
- **复审证据**: 计划已要求每个登录成功路径先清除旧授权上下文，并只在新账户仍拥有同一 workspace membership 时恢复路由；新增管理员过期后以普通成员重登录的负向验收。

### PR-02-已修复 [中]-账号目录的公开面与脱敏承诺相互矛盾
- **位置**: Shared account contract / `demoAccounts`, `validateAccountDirectory`, lookup returns
- **问题类型**: 公共契约缺失 / 测试缺口
- **当前写法**: 计划同时提出 deep-frozen `demoAccounts`、用候选目录测试重复 identity，并承诺返回对象不暴露未脱敏 credential；但未定义目录是否导出、验证测试如何取得候选副本，以及 validator 如何识别一个格式合法但仅作业务绑定的手机号。
- **反例/失败场景**: 若公开导出含 `providerSubject='13800006208'` 的目录，任意浏览器代码均可读取原始演示号码；若完全不导出，duplicate candidate 测试没有稳定基线；若 validator 硬编码业务号码黑名单，账号层反向依赖业务主体样例。
- **为什么有问题**: 实现者必须自行选择一个互相冲突的公共接口，容易造成敏感字段泄漏或账号/业务层过度耦合。
- **直接证据**: plan 的 `demoAccounts` identity schema 使用 providerSubject 做解析，同时要求 `validateAccountDirectory(candidate)` 和“business-only phone rejected”；现有 business snapshot 没有未脱敏号码可供可靠交叉验证。
- **影响**: 公共契约不可直接实现，测试可能验证实现细节而非“业务绑定不授予登录”的真实规则。
- **建议改法和验证点**: 明确原始 provider subject 仅存在于未导出的私有常量；导出一个去敏的 `demoAccountDirectory` 视图和独立 fixture factory/validator 测试入口，或明确演示原始值可公开且查询结果必须去敏。不要让 validator 识别“业务用途”；改为测试默认登录目录不含业务号码，且业务绑定/快照导入前后登录目录完全不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
- **复审证据**: 计划现明确私有原始目录、公开脱敏 projection 与只供测试/原型的 fixture factory；validator 不再反向依赖业务号码，改由目录不包含业务号码及业务变更不影响身份目录来验收。
