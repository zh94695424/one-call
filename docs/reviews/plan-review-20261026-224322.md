### F-PA0-PR-01 — Frozen `allowedDependencies` table is not executable-asserted

- Severity: Medium
- Status: unresolved
- Plan location: §6.2 table (lines 390–405); §6.4 `discoversExactlyTheFrozenModuleSet` (lines 448–461); S1 invariant “allowedDependencies 与 §6.2 表一致” (line 953); completion-report field `allowedDependencies table hash` (line 1150).
- Problem type: contract not enforced by planned verification.
- Current plan behavior: the only positive assertions are exact module *names* and `@ApplicationModule` *presence*. `verify()` runs on an empty production edge graph, so it cannot distinguish a correct §6.2 allow-list from a widened or emptied allow-list.
- Counterexample: implement `ivr` as `@ApplicationModule(allowedDependencies = {"customer_iam", "catalog_order", …})` (or omit attribute entirely if that means unrestricted). `EXPECTED` set still matches; annotation is present; `verify()` still passes because no cross-module types exist yet. S1 reports success while the frozen architecture cap is wrong.
- Repository evidence: plan lines cited; `docs/12` §6 lines 224–238 is the prose source the plan claims to freeze; no other executable source exists in-repo.
- Impact: the goal signal “executable and non-trivial module dependency verification” is only partially met. The first domain work unit can land illegal edges that PA0 never noticed, or PA0’s frozen table can silently diverge from `docs/12` without a failing test.
- Bounded fix: in `ModuleBoundaryTests`, read each production `package-info`’s `@ApplicationModule.allowedDependencies()` (or the Modulith `Module` API for allowed deps) and assert exact set equality against a single in-test map that mirrors §6.2 (including empty sets). Keep the annotation-presence and exact-name checks. Do not rely on a hash in the human report alone.
- Verification point: mutate one module’s `allowedDependencies` in a throwaway branch (e.g. add `catalog_order` to `ivr`) and require `ModuleBoundaryTests` to fail; restore and require green.
- Fix risk: low. Test-only; no product rule change.

### F-PA0-PR-02 — Empty `allowedDependencies` may not mean strict none; leaf firewall and forbidden fixture may be fictional or deadlocked

- Severity: Medium
- Status: unresolved
- Plan location: §6.2 “无 outgoing edge 的模块写 `@ApplicationModule`（空 allowedDependencies）” (line 422); empty `{}` rows for `customer_iam` / `subject_number` / `operations_audit` / `platform_reliability` (lines 392–405); §6.5 forbidden fixture “strict none” (line 478) and contingency (line 490); stop condition (line 1128).
- Problem type: framework-semantics gap / false architecture guarantee.
- Current plan behavior: leaf modules and the forbidden fixture are specified as deny-all via empty `allowedDependencies`, with a vague fallback to “框架文档化的 strict 形式.” No concrete strict encoding is named.
- Counterexample: Spring Modulith’s widely documented behavior is that an empty/omitted `allowedDependencies` does **not** restrict outgoing dependencies (empty ⇒ no allow-list limit), while a *non-empty* list is restrictive. Under that semantics:
  1. bare `@ApplicationModule` on `customer_iam` permits a future `customer_iam → ivr` edge without `Violations`;
  2. the forbidden fixture with consumer `strict none` = empty annotation + reference to `provider.Provider` does **not** throw, so the “must fail” test fails as a test (expected exception missing) **or** the implementer deletes it, which the plan forbids — landing on the §13.5 stop condition with no coded recovery.
- Repository evidence: plan lines cited; plan itself admits empty may not be strict (lines 409, 490, 1128) but still instructs empty as the primary encoding for production leaf modules and the forbidden fixture. No in-repo Modulith version proof exists to resolve the semantic (network-gated in this session).
- Impact: either false confidence that Phase A leaf modules are closed, or S1 blocked on an avoidable encoding choice. Non-empty rows (`organization_access`, `ivr`, …) are likely enforced; empty rows are the hole.
- Bounded fix (choose and freeze in the plan before S1):
  (a) if Modulith 1.4.14 documents a real deny-all/strict form, name the exact annotation/attribute and use it for all empty §6.2 rows **and** the forbidden fixture; or
  (b) if none exists, keep Modulith for cycle/non-empty allow-lists/internal packages, and add a small complementary check (annotation-value equality from `F-PA0-PR-01` plus an ArchUnit or classfile scan rule that no `com.onecall.core.<module>.**` type references types under other root modules when the map says `{}`), and rewrite the forbidden fixture to exercise that complementary rule;
  keep the fail-closed stop only for “cannot encode deny-all with *any* approved mechanism,” not for “empty might be wrong.”
- Verification point: in S1 preflight, run the forbidden fixture and a temporary leaf-module illegal edge under the chosen encoding; both must fail the build before S1 can be reported complete.
- Fix risk: low–medium. May add one test dependency (ArchUnit) — that is still inside module-boundary enforcement, not goal drift; if ArchUnit is rejected, option (a) must be proven instead.

### F-PA0-PR-03 — Java toolchain is not exact-pinned despite confirmed pin success signal

- Severity: Medium
- Status: unresolved
- Plan location: §4.1 Java row (line 194); §9.3 `actions/setup-java` `java-version: '21'` (lines 786–790); residual `PA0-R-10` (line 1105); goal success “pin Java/Maven/Node 22” and scope “Exact patch versions must be backed by authoritative compatibility evidence and may not be guessed” (`docs/gateflow/project-execution-control.md` lines 41–42).
- Problem type: incomplete toolchain pin / reproducibility gap.
- Current plan behavior: Maven is wrapper+SHA pinned; Node is exact `22.23.4`; Java is major-only via floating Temurin `21` resolution at CI time. Patch proof is deferred as residual rather than planned as a pin.
- Counterexample: two CI runs on different days resolve different Temurin 21.0.x builds. A bytecode/toolchain-only failure is attributed to application code; S1 local Java `21.0.12.1` (controller-observed) no longer matches CI. The confirmed goal treats supported pinning as a success signal equal to Maven/Node, not optional hardening.
- Repository evidence: plan and control-doc lines cited; `docs/12` line 68 requires fixed reviewed patch versions at implementation time for version families.
- Impact: success signal incompleteness; non-reproducible CI green; weaker “repeatable runtime” claim than the goal contract.
- Bounded fix: choose one exact Temurin 21 patch (e.g. `21.0.x+Y` distribution coordinate) with the same preflight evidence discipline as Boot/Maven (controller metadata + S1 `java -version` assertion), set `java-version` to that exact string, and tighten Enforcer/`assert toolchains` greps to the patch. If evidence cannot be obtained in-session, keep a fail-closed S1 preflight for the *exact* patch rather than leaving major-only as the designed end state. Update/remove `PA0-R-10` accordingly.
- Verification point: `java -version` in S1 report and CI `assert toolchains` both show the frozen patch; changing the pin fails the plan-conformance check.
- Fix risk: low. Pin string + assertion only.

### F-PA0-PR-04 — S2 completion requires Docker-capable execution while also allowing `NOT RUN`, conflicting with Gateflow pre-push reality

- Severity: Medium
- Status: unresolved
- Plan location: §1.3 success signal local/CI policy (lines 51–52); §7.4 local skip policy (lines 618–621); §9.6 CI evidence boundary (lines 896–900); §11.2 error handling `NOT RUN` (lines 1027, 1043) vs completion “在 Docker-capable 环境执行 container smoke … 未满足时 S2 不完成” (line 1045).
- Problem type: slice acceptance predicate self-contradiction / Gateflow sequencing gap.
- Current plan behavior: mechanism says local absence is legal and CI must not skip; completion text says S2 is incomplete until a Docker-capable run is recorded; another clause says missing CI/Docker may be reported `NOT RUN` and handed to controller/PR.
- Counterexample: author environment has no Docker daemon; controller facts record Docker CLI present but daemon not running and permission-gated `docker` for author. Under “未满足时 S2 不完成,” S2 cannot finish inside Gateflow before push. Under the `NOT RUN` clauses, S2 “completes” with the primary behavioral success of S2 (real PostgreSQL smoke) unproven, and implementation review/deepreview inherit an unresolved primary invariant.
- Repository evidence: plan lines cited; control-doc direct evidence line 44 (no running Docker daemon); goal line 41 explicitly allows honest local absence but still lists Testcontainers smoke as a success signal.
- Impact: reviewers/controllers cannot tell whether S2 is allowed to checkpoint with Docker `NOT RUN`, or must block the work unit until GitHub Actions (post-push) — an implicit dependency on PR timing the plan does not bind.
- Bounded fix: split the predicates explicitly in §11.2:
  (1) **author S2 code-complete**: workflow+IT+profile+A1–A5 local (Node-permitting) present; container smoke either executed **or** recorded `NOT RUN` with exact denial — completion allowed;
  (2) **S2 evidence-complete / work-unit success**: requires at least one external Docker-capable execution (controller-provided environment **or** first GitHub Actions run) with failsafe XML `tests=1 skipped=0 failures=0 errors=0`; this gate may be satisfied only by controller/PR evidence, never by author claim.
  State that Gateflow may accept author S2 code-complete while keeping work-unit success pending on (2). Align stop conditions and the completion report template with the split.
- Verification point: S2 report has distinct fields `author_container_smoke=PASS|NOT RUN (reason)` and `controller_or_ci_container_smoke=PASS|FAIL|PENDING`; work-unit closeout requires the second to be PASS.
- Fix risk: low. Wording and report schema only; CI mechanism unchanged.
