## 5. Findings (all low severity, non-blocking)

**F1 - LOW (coverage): no executed foreign row-lock denial probe.**
The controller brief requires proof of "no foreign write or row-lock privilege" for
`activation_consent_role`. The test proves absence of table-level and column-level UPDATE
privileges on the four foreign read targets (test 8399-8418, 8465-8526), which entails denial of
`SELECT ... FOR UPDATE`/`FOR SHARE` (PostgreSQL requires UPDATE privilege for row locking), and it
executes foreign write denials for `ivr_role`/`catalog_order_role` (8666-8676). It does not
execute a `SELECT ... FOR UPDATE` as `activation_consent_role` against those four tables.
Trigger/path: `v007OwnerPublicRuntimeAndCrossModuleAclsAreExact` ->
`assertV007SchemaUsageMatrix`/`assertV007RuntimeDenialsAndLegalUpdateControl`. Impact: the
denial is asserted at the privilege layer, not observed at runtime. Fix: add one bounded
`expectSqlQueryFailure(..., "42501", "SELECT id FROM subject_number.business_subject WHERE id = ?
FOR UPDATE")` under `activation_consent_role` (rolled back) in the existing ACL method, or cover it
in S2.

**F2 - LOW (coverage): partial trigger event-bit assertion.**
`assertV007FunctionsAndTriggersExact` verifies relation, function, BEFORE, ROW, UPDATE and the
expected DELETE presence, but does not assert the absence of INSERT/TRUNCATE/INSTEAD-OF bits
(test 7970-7994). The frozen migration is correct (BEFORE UPDATE OR DELETE / BEFORE UPDATE,
lines 189-199), so this is proof-strength only. Fix: assert the full expected `tgtype` value (or
explicitly assert `tgtype & 4 = 0` and `tgtype & 32 = 0`).

**F3 - LOW (test robustness): parent-delete RESTRICT expectation is coupled to RI trigger order.**
The representative parent delete (test 8205-8223) deletes a `customer_account` that is referenced
by both `fk_consent_account` and `fk_activation_transition_actor_account`, then asserts the error
names exactly `fk_consent_account`. PostgreSQL reports one violated FK at a time; the observed name
depends on RI trigger firing order. It passes on the controller's PostgreSQL 16.15 run, but the
assertion could become brittle across catalog/OID or engine changes. Fix: leave
`actor_account_id` NULL (or point it at a different account) so only `fk_consent_account`
references the deleted parent, or accept either exact constraint.

**F4 - LOW (coverage): head-guard behavioral probe covers one of three immutable columns.**
The owner `P0001` probe changes only `subject_id` (test 8660-8665); `id` and `created_at` are not
behaviorally probed in S1. The function checks all three with `IS DISTINCT FROM`
(migration 180-183), and the plan assigns broader head immutability to S2. No change required for
S1; note for S2.

**F5 - INFO (process, not code): stale hash table in the frozen implementation artifact.**
`s1-implementation.md` section 2 records the pre-fix test SHA `64820b93...` / 21,358 lines,
whereas the final frozen test is `79717037...` / 21,812 lines. The artifact is explicitly
historical ("blocked runtime report ... remains untouched") and
`s1-validation-fixes.md` records the correct final SHA; readers should treat the supplement as
authoritative. No action on code.
