## 3. Findings

Severity: **H** = must be resolved in the plan before an accepted-plan checkpoint; **M** = must be resolved before/at code generation; **L** = tighten wording/labelling.

### F-1 (H) `/error` replacement omits the condition that makes it work
`internal/web/CustomerApiErrorController.java` is described as "Replace Boot default `/error` JSON/HTML" without stating the mechanism. Boot 4.1.2 bytecode (`spring-boot-webmvc-4.1.2.jar`) shows `ErrorMvcAutoConfiguration$BasicErrorControllerConfiguration.basicErrorController` is `@ConditionalOnMissingBean(value = org.springframework.boot.webmvc.error.ErrorController.class, search = CURRENT)`, and `BasicErrorController` maps `${server.error.path:/error}` with an unconstrained `@RequestMapping`. Consequences if the plan is implemented literally:
- not implementing `ErrorController` leaves `BasicErrorController` registered and competing for `/error` — either ambiguous handler resolution on `Accept: */*` or, worse, the default `{timestamp,status,error,message,path}` map / whitelabel HTML the plan explicitly forbids;
- implementing it requires the **Boot 4 relocated** FQN `org.springframework.boot.webmvc.error.ErrorController` (Boot 3's `org.springframework.boot.web.servlet.error.ErrorController` does not exist here) plus `getErrorPath()` semantics.
Required plan change: one sentence pinning the interface, its Boot 4 package, and an assertion in `CustomerWebConfigurationTests` or `CustomerApiBoundaryTests` that `BasicErrorController` is absent and that no response ever contains `timestamp`/`path`/`exception` keys or `<!DOCTYPE html`.

### F-2 (H) Transport- and negotiation-originated failures have no frozen mapping and no test
The §7 table covers only conditions the application itself produces. Real HTTP traffic on this route can also fail *before* the handler: Tomcat's `maxHttpHeaderSize` (a long opaque bearer plus cookies), malformed request target/authority, and content negotiation (`Accept: text/html` on the success path raises `HttpMediaTypeNotAcceptableException`, which Boot normally answers 406 via `BasicErrorController.mediaTypeNotAcceptable`). Grep confirms the plan contains no `400`, no `406`, no `Accept` handling and no negotiation discussion, and neither `allFrozenProblemMappingsAreClosedAndSanitized` nor `otherPathsMethodsAndAliasesAreNotCustomerOperations` covers them. This is the exact class of path where an unspecified default reintroduces Boot's error map or an HTML body, and `Problem.status` must equal the HTTP status (`docs/15-production-openapi-surface-spec.md` §4) while `getCustomerMe` allows only six codes (`api/openapi/onecall-v1.openapi.yaml:307`) — none of which is 400/406.
Required plan change, separating the two mechanisms:
- Application-reachable failures (Spring's `DefaultHandlerExceptionResolver` calls `sendError`, which does reach the container error dispatch): pin a mapping so every such failure on this route emits a canonical Problem — hostile `Accept` must not become 406 (`CustomerMeController` declares its produced media type explicitly), and any internal ERROR dispatch whose container status is outside `{401,403,404,422,429,500,503}` is emitted as one pinned code rather than a non-canonical 400/406.
- Connector-decode failures that never reach the application (Tomcat rejects an oversized/malformed request head at the processor and answers its own 400), which in-process code cannot sanitize at all. The plan's §7 claim to "write `application/problem+json` consistently" is therefore over-absolute and must be scoped, and the header-size limit must be named either as a deliberate `server.max-http-request-header-size` decision or as a transport boundary owned by the edge (§7 already treats TLS/WAF and downstream log policy that way). Add one named test method to `CustomerMeWebTests` for the app-reachable cases and one CI smoke assertion that no response body ever contains Boot's `timestamp`/`path`/`error` map or HTML; the connector-level case belongs in the residual ledger, not in an unachievable test.

### F-3 (H) The frozen denial-audit obligation is silently inverted and missing from the residual ledger
`docs/17-production-security-design-spec.md:455`-`:456` freezes `SECURITY_AUTH_DENIED` ("会话/凭据无效") and `SECURITY_AUDIENCE_MISMATCH` ("跨域 token/credential") with persistence `append_fact`, and `acceptance/v1/acceptance-matrix-v1.json` scenario `A5-IDENT-PERMISSION_DENIED-01` expects exactly one `A3:AUDIT:SECURITY_AUTH_DENIED` audit row for a `getCustomerMe` denial (its `expectedDelta.audit` is `mode: EXACT, value: 1`), with `A1:OP:getCustomerMe` also cited by `A5-IDENT-NORMAL-01`, `A5-IDENT-TIMEOUT-01`, `A5-IDENT-OUT_OF_ORDER-01`, `A5-IDENT-RECOVERY-01`. `customer_iam_role` already has `EXECUTE ON FUNCTION audit.append_fact` (`backend/src/main/resources/db/migration/V001__platform_schemas_roles_idempotency_outbox_audit.sql:534`) and `audit.append_fact` permits `p_actor_type='SYSTEM'` with a NULL actor (`backend/src/main/resources/db/migration/V001__platform_schemas_roles_idempotency_outbox_audit.sql:460`-`:462`), so denial auditing is technically in-scope today without any ACL widening. The plan instead asserts the opposite as a success invariant (§6 "no … audit/outbox emission"; §8 `CustomerMeIT` #8 compares audit rows before/after and requires no change) and never mentions `append_fact`, `SECURITY_AUTH_DENIED`, `SECURITY_AUDIENCE_MISMATCH`, docs/17 §17 or A5. Grep confirms zero occurrences.
This is not automatically a defect — the binding goal says "no hidden writes" and "no other … services" — but a review cannot accept an unstated inversion of a frozen security obligation that this very endpoint is named in. Required plan change: add an explicit §2 evidence line and an §11 residual row ("denial security-audit `append_fact` for `SECURITY_AUTH_DENIED`/`SECURITY_AUDIENCE_MISMATCH` → owner Identity/Backend/Security; destination: authentication-integration or audit work unit; PA11 therefore does **not** absorb `A5-IDENT-PERMISSION_DENIED-01`"), and reword §6/§8 so "no writes" is scoped to "PA11 scope writes nothing", not "denials need no audit". If the controller instead wants denial auditing now, that is a second write transaction and must be re-scoped, which conflicts with the confirmed goal.

### F-4 (M) "No Spring Security" contradicts the canonical stack row and is not labelled as a deviation
`docs/12-technology-stack-and-system-architecture.md:55` lists the core server stack as "Java 21 LTS、Spring Boot 3.x、Spring Modulith、**Spring Security**、Bean Validation". The plan's judgment ("Spring Security is not necessary") is sound and the ban is pre-existing (`backend/pom.xml:130`, `backend/pom.xml:135`), but §2's docs/12 evidence row cites only lines 222/248/280/348/460 and never confronts line 55; the plan therefore presents a stack deviation as if the canonical document were silent. Note also that the same row names Bean Validation, which is likewise absent from the classpath — consistent with the plan's correct refusal to invent a validation stack merely to give `422 VALIDATION_FAILED` a producer. Required plan change: one line in §2/§9 recording that the accepted goal's explicit verifier-port decision (`docs/gateflow/project-execution-control.md:24`) plus the pre-existing enforcer ban supersedes the `docs/12:55` stack row for this slice, with `Boot 3.x → 4.1.2` noted as an already-accepted drift, and the reconciliation destination named (docs/12 amendment or controller deviation register) since PA11 may not edit `docs/12`.

### F-5 (M) PERSONAL derivation vs the presented SQL — `NULLS FIRST` is vacuous and invites a wrong mapping
§6's projection is `customer_account LEFT JOIN (ACTIVE memberships × ACTIVE organizations)` with `ORDER BY w.organization_id ASC NULLS FIRST`, and §5 requires "exactly one PERSONAL first, then ORGANIZATION rows". With that SQL shape a NULL-`organization_id` row exists **only when the account has zero usable organization memberships** — in which case it is the single row and `NULLS FIRST` cannot matter. Whenever ≥1 organization row exists, no NULL row exists, so the PERSONAL workspace must be **synthesized from the account row** (exactly as `docs/11-account-identity-and-workspaces.md:30`/`:36` and `docs/14-production-data-model-and-flyway-schema-spec.md:3066` state: "个人空间由客户账户派生", "The personal workspace is derived from the active account"). An implementer reading the SQL literally will map `NULL organization_id → PERSONAL` and return a context with no PERSONAL workspace for every account that has an organization — failing §8's own `workspaceOrderingIsUuidDeterministicAndPersonalFirst` and `inactiveAccountReturns401AndInactiveWorkspacesAreAbsent` assertions.
Required plan change: state that PERSONAL is derived in the repository mapper from the account row (never from a NULL joined row), drop or justify `NULLS FIRST`, and make the "exactly one PERSONAL" invariant a mapper-level guarantee with the DB supplying only organization rows.

### F-6 (M) Ordering invariant-check comparison semantics are unspecified — real risk of spurious 500
§5 correctly forbids re-sorting with `UUID.compareTo` (Java compares `mostSignificantBits` as **signed** longs; PostgreSQL `uuid_cmp` is a big-endian unsigned byte compare, so ~50% of random UUIDs order differently). But §8 also requires the service to reject "bad … order" with 500, and the plan never says with which comparator. A validator using `UUID.compareTo` on PostgreSQL-ordered rows will fail closed on legitimate data whenever the fixture set mixes MSB sign boundaries — i.e. the very fixture the plan asks for in `CustomerMeIT` #4.
Required plan change: pin the validator as either "preserve the repository-returned sequence exactly (no re-derivation)" or an explicit unsigned comparison (`Long.compareUnsigned` on MSB then LSB, equivalent to `uuid_cmp`), and require `CustomerMeIT` #4 to assert the validator agrees with the database for both sign classes.

### F-7 (M) The CI JAR-firewall carve-out must be exact-coordinate, not prefix deletion
The current negative regex (`.github/workflows/ci.yml:266`) bans substrings `spring-web`, `tomcat`, `jakarta.servlet`, `spring-boot-…web…`, which today also incidentally reject `spring-websocket`, `tomcat-embed-jasper`, `spring-boot-starter-web`, `spring-boot-starter-websocket` and `jakarta.servlet-api`. `spring-boot-starter-webmvc` is nearly identical in graph to the legacy `spring-boot-starter-web` (verified against both starter POMs on Central), so a prefix-based loosening would make an accidental swap invisible in `BOOT-INF/lib`. The plan's direction is right ("allow only the explicit resolved MVC/Tomcat/Jackson family", "no speculative wildcard"), but it must be made a hard rule: positive enumeration of the 18 coordinates from the entry-gate manifest, one-to-one presence/version/no-duplicate against `BOOT-INF/lib`, with the substring bans retained for everything not in that list (including `spring-websocket`, `tomcat-embed-jasper`, `spring-boot-starter-web`, `spring-boot-starter-webflux`, `jakarta.servlet-api`, and Jackson 2 `…databind`/`…core`).

### F-8 (M) Null-omission is contract-critical but is delegated to a global profile property
`spring.jackson.default-property-inclusion` is confirmed present in Boot 4.1.2 (`spring-boot-jackson-4.1.2.jar` → `META-INF/spring-configuration-metadata.json`, type `JsonInclude$Include`), so the plan's property is valid. Still, omission is the *only* thing keeping PERSONAL workspaces schema-valid (`WorkspaceSummary.organizationId/role` are non-nullable `string` in `api/openapi/onecall-v1.openapi.yaml:4390`-`:4409`), and the mechanism chosen is global and profile-scoped. Recommend pinning omission on the payload types themselves (`@JsonInclude(JsonInclude.Include.NON_NULL)`; `com.fasterxml.jackson.core:jackson-annotations:2.21` is on the graph) and keeping the profile property only as defence in depth, so the wire contract cannot regress if a later profile, test slice or future endpoint changes the global setting. Keep the existing actual-HTTP JSON assertion as the proof.

### F-9 (L) "Indistinguishable" claims are status/body-level, not timing-level
§7/§8 claim invalid/revoked/disabled/wrong-audience denials are indistinguishable, and separately that a verifier rejection must not touch the pool while a missing/DISABLED account denial is produced *after* a pool checkout and query. Those two 401 paths therefore differ in observable latency and connection-pool state. No listed test produces timing evidence, and the difference is inherent to the (correct) fail-closed design. Fix: scope the claim to "identical status, code, title and body shape" and add the latency side channel as a named bounded residual (owner Security; destination: authentication-integration, together with Q1/Q19). Do not "fix" it by issuing a DB read on every rejection.

### F-10 (L) New wire-text decisions are not labelled as new decisions
`type: "about:blank"`, the seven fixed titles (`Authentication required`, `Access denied`, `Request validation failed`, `Too many requests`, `Service unavailable`, `Internal error`, `Not found`), the bare `WWW-Authenticate: Bearer`, and the `Cache-Control: no-store` / `Pragma: no-cache` / `X-Content-Type-Options: nosniff` set appear nowhere in `docs/15`, the OpenAPI document or the A1/A3 validators (verified by grep). The plan is careful to label the workspace ordering as "not a pre-existing frozen ordering claim" but silent on these, even though they are equally client-visible. Fix: mark them as PA11-owned implementation contract that later surfaces must inherit, and name the destination for centralising the Problem-title convention (A1 or a shared convention note) so a later slice does not re-invent titles for the same codes.

### F-13 (L) "No invented capacity values" leaves Hikari defaults silently in force
PA11's customer pool sets no sizing/timeouts (consistent with `SharingPersistenceConfiguration.java:29`-`:36`, which sets none either), so Hikari defaults (10 max, 30 s connection timeout) become the production-shaped behaviour, and a DB outage surfaces as ~30 s request stalls behind the 503. ### F-14 (L) Three of the six error codes are unreachable in this slice
`FORBIDDEN`, `VALIDATION_FAILED` and `RATE_LIMITED` have no producer (no role gate, no validation stack, no limiter) yet live in `CustomerContextException.Code` and in `allFrozenProblemMappingsAreClosedAndSanitized`. ### F-15 (L) Bearer material lifetime and header removal
`OpaqueCustomerBearer` is a String-backed wrapper with a redacted `toString`, which is the right minimum; the wrapper overrides `getUserPrincipal()`/`getRemoteUser()` but does not remove `Authorization` from the underlying request, so any future filter or component can still read it. That is fine for PA11, but §7 should phrase the canonical rule (`docs/17-production-security-design-spec.md:325`: "bearer and Authorization header always removed") as "never logged, never serialized, never retained in the principal or any request attribute by PA11 code" rather than implying header stripping, which the slice does not do.
