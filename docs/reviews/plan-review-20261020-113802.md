## Assumptions tested

| Lens / assumption | Result |
| --- | --- |
| Goal-bound minimal design | All three fixes protect confirmed trial/evidence correctness or trustworthy validation. They do not add production IAM, backend persistence, telephony, payment or finance workflow goals. |
| Architecture boundary | The exact business snapshot owns IVR sessions and excludes employee/customer authentication and UI state. Employee login-session state remains admin-local; business sessions remain cross-surface evidence context. The similarly named concepts no longer leak across the boundary. |
| Best practice / state machine | Consumption validates references before grant lookup/write; invalid snapshot candidates are fully validated/deep-cloned before a single replacement; rejection leaves the existing business snapshot unchanged. Claim cannot alter frozen IVR-session links or evidence records. |
| Optimal solution | Exact top-level keys and internal referential validation allow dynamic demo objects without a seed-ID allowlist, while refusing mixed authority/UI state. This is simpler and safer than silent field stripping or duplicating per-surface validators. |
| Overengineering | The shared module remains narrow, in memory and dependency-free. Runner failure testing and snapshot validation are bounded to observed risks; no new framework, persistence layer, production build or fourth behavior slice is introduced. |
| Overcoupling | UIs keep independent state clones, and review hooks transfer only the exact business snapshot. Generated inline packaging solves the miniapp srcdoc/file constraint without runtime service coupling. Existing evidence-preservation and employee authority remain separate owners. |
| Slice sequencing / feasibility | S1 establishes rules, packaging and reliable QA; S2 migrates admin employee/catalog behavior; S3 migrates clients/IVR and runs cross-surface verification last. This matches the user-confirmed order and stays within three behavior slices. |
| Catalog and commerce invariants | Draft/version/history, stale confirmation, immutable order snapshots, trial/paid ledger separation and PAID-versus-ISSUED states remain explicit. Formal prices, stacking and renewal are still identified as demo or undecided. |
| Claim/privacy | Conflict and recycled-number paths reveal no history; claim does not establish identity, regrant trial or rewrite capture facts. Snapshot reference checks preserve evidence→IVR session→subject linkage. |
| Offline support / production claims | Null contact remains non-actionable; no receipt, SLA or eligibility is invented. Hooks and credential codes are explicitly local demo/review mechanisms, with removal required before any future production reuse. |
