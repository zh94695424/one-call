## Findings

### F-09-部分修复-[中]-激活后 DIAL 分支未把权益、任务授权、工作区权限和风险状态作为完整前提

- **位置**: Plan §10 activation-confirmation state machine and sequence 1 at line 425; `ivr.record_activation_next_action` contract at lines 488-490; S2 completion assertion at line 759; tests at lines 510-514.
- **问题类型**: 契约缺失 / 状态机漏洞 / 权限边界 / 并发恢复风险 / 测试缺口 / 不可直接实施.
- **当前写法**: After activation and first-trial processing, the plan rechecks the session/caller, active activation and consent, an unexpired task, and available entitlement, then selects `DIAL_TASK_CALLEE` “when a valid task exists”. It does not define current creator/workspace authorization, subject/caller access or risk checks, nor does it require the expiry predicate again in the atomic claim `UPDATE`.
- **反例/失败场景**: A task remains `PENDING` but the organization membership or creator permission is revoked during the IVR prompt. An `OPEN` caller risk appears after the initial resolve. A task expires between the recheck and the claim update. A task exists while the trial/paid balance has reached zero. The implementation can authorize an unfunded or unauthorized dial, or fail with a low-level reservation/unique error instead of returning the deterministic purchase/rejection action.
- **为什么有问题**: `docs/13` §6.3 requires current workspace permission, valid task and available entitlement; no available seconds maps to `GUIDE_PURCHASE`, not dial. `docs/12` §9.1 requires post-activation revalidation before reservation. `docs/10` says an open risk blocks claims, and `docs/11` makes server-side membership/resource authorization the security boundary. The plan’s resolve path names these checks, but the activation-confirmation path does not carry them through.
- **直接证据**: Plan line 425 says “DIAL_TASK_CALLEE when a valid task exists”; line 488 says the service claims the task but does not enumerate authorization/risk predicates; line 759 only claims rechecking task expiry and entitlement. Source `docs/13` lines 208, 218-224 and `docs/12` lines 295-296 require the stronger conditions.
- **影响**: Unauthorized or unfunded calls, inconsistent user-visible actions, opaque rollback failures and implementation-agent invention in the primary IVR path.
- **建议改法和验证点**: Make `DIAL_TASK_CALLEE` conditional on `PENDING`, caller/subject binding, current creator/workspace access, no blocking risk, `expires_at > clock_timestamp()` in the claim `UPDATE`, and positive available entitlement. Reuse the exact claim predicates from resolve. Return `GUIDE_PURCHASE` for zero entitlement and `ENTER_CALLEE` only when no valid task remains and balance is positive. Define stable non-dial outcomes for replacement/cancellation/expiry/access/risk changes and reservation competition. Add tests for each race and rollback path.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-10-未修复-[中]-同一 call 的不同 eventId 重复确认与 call/purpose 唯一约束冲突

- **位置**: Plan `ivr.ivr_decision` catalog row at line 225; activation-confirmation state machine at line 407; sequence 1 at line 425; published service at lines 488-490; S2 tests/completion at lines 511-514 and 759.
- **问题类型**: 幂等性 / 状态机漏洞 / 契约缺失 / 测试缺口 / 不可直接实施.
- **当前写法**: `platform.idempotency_begin('IVR_CONFIRM', eventId, requestFingerprint)` keys the request by event ID, while `ivr.ivr_decision` permits only one `(call_id, ACTIVATION_NEXT_ACTION)`. The prose says repeated confirmation returns the stored decision, but does not define how a new event ID looks up that decision before consent/trial/task side effects.
- **反例/失败场景**: IVR retries with a regenerated event ID. `begin` returns `NEW`; consent and first-trial services run; the next-action service attempts a second call/purpose row and hits a unique violation. If the subject became suspended, naive code may also try `CONFIRMED → REJECTED`, which is not an allowed session transition. The caller receives an opaque failure and the new idempotency record may be left without a stable result.
- **为什么有问题**: `docs/13` §6.5 defines confirmation identity as event ID plus request fingerprint, while §6.3 requires the same call to return its first frozen action. `docs/10` requires identical input to return the first immutable result and changed input to be rejected atomically. The current plan defines both uniqueness rules but not their precedence or interaction.
- **直接证据**: Plan line 225 declares unique `(call_id, purpose)` and a fingerprint conflict; line 425 calls `begin` before side effects but has no existing-decision lookup; line 490 only states that a repeated confirmation returns the stored result. The existing tests cover same-event replay and an already-active repeat, not a different event ID.
- **影响**: Repeat confirmations can fail with an implementation-level constraint error, loop indefinitely, duplicate consent attempts, or produce an invalid rejected session. This blocks a code-generation-ready idempotency contract.
- **建议改法和验证点**: Under canonical-caller/call serialization, first read `(call_id, ACTIVATION_NEXT_ACTION)`. If it exists and the canonical request fingerprint matches, return its frozen decision/action and complete the new event ID’s idempotency row with that same decision ID. If the fingerprint differs, return a stable conflict with no side effects. Check this before the `SUSPENDED` branch; apply `REJECT_SUSPENDED` only to a not-yet-confirmed session and never insert a second decision or transition a confirmed session to rejected. Test same fingerprint/new event ID, changed fingerprint/new event ID, same event ID replay, and a new event ID after operations suspension.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-11-未修复-[中]-激活确认未定义活动/未知通话竞争的稳定动作，可能依赖唯一约束报错

- **位置**: Plan sequence 1 at line 425; `ivr.record_activation_next_action` service row at line 488; IVR decision action catalog at line 225; INV-11 and INV-13 at lines 369-373.
- **问题类型**: 并发恢复风险 / 状态机漏洞 / 契约缺失 / 测试缺口.
- **当前写法**: The plan claims the post-activation service can create or bind an active `call_record` for `DIAL_TASK_CALLEE`, but the sequence does not explicitly recheck an existing `ACTIVE/UNKNOWN` call for the canonical caller or map that condition to `REJECT_CALL_IN_PROGRESS`. The action enum contains `REJECT_CALL_IN_PROGRESS`, and the direct-authorization sequence does explicitly check it, but activation confirmation does not.
- **反例/失败场景**: A direct authorization or another IVR node creates an active/unknown call after the initial resolve and before activation confirmation claims the task. The active-call partial unique index may reject the insert and roll back the entire activation confirmation, or an implementation may choose the task path and return a second dial authorization. Neither behavior satisfies the stable action contract.
- **为什么有问题**: `docs/13` §6.3 lists `REJECT_CALL_IN_PROGRESS` as the explicit action for an existing activity and §7/§10 requires one active/unknown call per canonical caller. The plan has the necessary index and direct-path check, but a code-generation-ready activation path must state the same guard and outcome before task claim/reservation.
- **直接证据**: Plan line 225 includes `REJECT_CALL_IN_PROGRESS`; line 425 lists rechecks without active/unknown call; line 428 explicitly checks active/unknown call only for direct DTMF. Source `docs/13` lines 208, 218, 310-316 define the stable action and single-call invariant.
- **影响**: Low-level unique violations, whole-confirmation rollback after a valid activation, or duplicate/competing B-leg authorization. The behavior is hard to observe and makes retry semantics ambiguous.
- **建议改法和验证点**: Add the active/unknown-call guard to the activation-confirmation recheck and to the transaction-level decision service. Return and persist `REJECT_CALL_IN_PROGRESS` with a stable reason/result snapshot; do not claim the task or create a reservation. Add races between activation confirmation and direct authorization, duplicate IVR nodes and an `UNKNOWN` call reconciliation case. Preserve the partial unique index as a backstop, not as the primary user-visible branch.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-12-未修复-[低]-DIAL_TASK_CALLEE 的冻结授权响应字段没有在计划中逐项定义

- **位置**: Plan `ivr.ivr_decision` catalog row at line 225; `ivr.record_activation_next_action` return contract at line 488; sequence 1 at line 425.
- **问题类型**: 公共契约缺失 / 不可直接实施 / 测试缺口.
- **当前写法**: The service returns a “frozen response snapshot”, and the decision table has a generic `response_snapshot` plus `reservation_id`, but the plan does not enumerate the required action-specific fields or their source and immutability rules.
- **反例/失败场景**: An implementation returns only `availableRecordingSeconds` or a reservation ID and omits `authorizedRecordingSeconds` or `authorizationExpiresAt`. IVR may start a B-leg after the authorization window, use a live balance instead of the frozen reservation, or fail to recover a lost response after a timeout. Different implementations can also expose the callee number in logs or omit the internal-only boundary.
- **为什么有问题**: `docs/13` §6.2 explicitly requires `reservationId`, `authorizedRecordingSeconds` and `authorizationExpiresAt` for `DIAL_TASK_CALLEE`, and says available seconds are only a routing snapshot. §6.3/§7 further require `callId`-based B-leg recovery and cutoff behavior. “Frozen snapshot” is not enough for a code-generation-ready public contract.
- **直接证据**: Source `docs/13` lines 200-201 names the exact fields and semantics. Plan lines 225, 425 and 488 use generic snapshot language and do not define a field schema, reason-code enum, or prohibited exposure for the action response.
- **影响**: IVR and backend can disagree on authorization expiry, recording limit and recovery; this creates call timing, quota and privacy bugs. The implementation agent must invent public response fields and tests.
- **建议改法和验证点**: Define an action-specific immutable snapshot contract: `action`, `callerState`, `taskMatch`, `taskId`/masked callee boundary, `reservationId`, `authorizedRecordingSeconds`, `authorizationExpiresAt`, `availableRecordingSeconds` as routing-only, `reasonCode`, and the source request/decision identity. State that full `calleeNumber` is IVR-internal only, never ordinary logs or client responses, and that authorization fields come from the committed reservation. Add response replay, cutoff, lost-response and redaction tests.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

## What is already strong

- The modular-monolith/PostgreSQL boundary is appropriate for the current five-person team and the confirmed business scope; it avoids premature service splitting.
- Identity, organization membership, business subject/number, employee account and login identity are correctly separated.
- The plan correctly models one non-terminal task per canonical caller, a 30-second database-time TTL, canonical-caller serialization, frozen task details, explicit call/leg/reservation/evidence links and no “latest callee” lookup.
- Trial issuance, per-order/per-installment issuance, payment state and entitlement state are separated and replayable.
- The SUSPENDED path is fail-closed in the plan: no accepted consent/trial/reservation/success Outbox, stable `REJECT_SUSPENDED`, lifecycle locking and no trial reissue on operations resume.
- The evidence record/event cycle, Outbox, append-only audit, restricted cross-schema writes, sensitive-field representation and migration-wave validation are unusually explicit for a planning artifact.
- The three-slice dependency order is credible. S2 is large, but splitting its activation/entitlement transaction across more slices would make the primary correctness boundary harder to test.

## Open questions

- The exact subject-risk lookup and lock key must be named: the plan has `subject_risk_state` keyed through caller binding, while F-09 requires the current subject/caller/workspace authorization view. The final specification must state the authoritative read and serialization order.
- The stable `reasonCode`/`taskMatch` values for authorization revocation, risk blocking, task replacement/cancellation, zero entitlement and call-in-progress are not enumerated in the plan.
- The subject lifecycle advisory-lock namespace and collision-safe key derivation remain unspecified; this is acceptable as a final-spec/implementation detail only if the lock-order and collision tests are made explicit.
- The `platform.idempotency_begin` contract says a committed `NEW` row raises and emits an alert, but a transaction rollback cannot durably emit an in-transaction alert. The final specification must state whether alerting is application-caught, an external metric/notification, or a separate durable recovery path.
- Evidence deferred-trigger privilege/search-path details and the trial subject-lock mechanism still require implementation-level PostgreSQL tests.

## Special review lenses

### Goal-bound minimal design

Passes on scope. The 44-table model, three slices and cross-schema service boundaries map to the confirmed production data-model goal. F-09 through F-12 are not scope expansion; they are missing correctness and public-contract details inside the confirmed IVR activation/task/reservation behavior.

### Architecture boundary

Passes with targeted corrections. IVR owns `ivr_decision`; activation-consent and entitlement-metering are called through mandatory published services; PostgreSQL remains truth. The recommended fix is to complete the existing IVR-owned orchestration contract, not to add a fourth slice or split another service.

### Best practice

Mostly strong. Partial unique indexes, immutable snapshots, conditional revisions, idempotent Outbox, restricted privileges and reconciliation are appropriate. The main best-practice failures are using a database uniqueness error as an implicit business response (F-11), and leaving an action-specific authorization response as an untyped JSON snapshot (F-12).

### Optimal solution

The direction is close to optimal for this team and phase: a modular monolith with one PostgreSQL transaction at the IVR boundary is simpler and safer than distributed transactions or a queue-only claim model. It is not yet the optimal executable plan because the activation confirmation path duplicates the resolve decision logic without a single explicit action-selection/claim predicate contract. The better alternative is a shared, IVR-owned `resolveNextAction` decision routine used by both resolve and post-confirmation flows, with the same ordered checks and a transaction-local reservation result. This reduces drift without changing ownership or adding a slice.

### Overengineering

No material overengineering finding. The evidence-cycle constraints, durable issuance state and function-wave checks are justified by the confirmed integrity requirements. Do not add a generic workflow engine, microservice split or extra event-sourcing layer to address these findings.

### Overcoupling

The cross-owner calls in one local transaction are justified by the requirement that consent, activation, first trial, task claim and reservation commit atomically. The avoidable coupling is behavioral duplication between resolve and activation confirmation. Consolidating their action-selection predicates behind an IVR-owned routine/protocol reduces the chance that one path gains a permission/risk check while the other does not.

## Recommended implementation-ready shape

1. Keep the current 44-table, 40-invariant, 9-wave, three-slice model and PostgreSQL ownership boundaries.
2. In S2, define one canonical action-selection contract with ordered checks: existing call/purpose decision, caller/session identity, active/unknown call guard, current subject/activation/consent, current workspace/creator authorization and risk, task `PENDING`/binding/expiry, and positive entitlement before claim/reservation.
3. Reuse the exact conditional claim predicate for resolve and activation confirmation. A failed claim must map to a frozen non-dial action, not a raw constraint exception.
4. Define the per-call decision/fingerprint lookup before all side effects, including different-event-ID retries and the SUSPENDED-after-confirmed case.
5. Define the action response snapshot and reason codes explicitly, including the three frozen authorization fields required by the IVR protocol.
6. Add the race and recovery tests listed under F-09 through F-12, then rerun the structural script and perform an independent re-review. Do not start implementation before those steps pass.

## Final conclusion

**fail**

The plan is directionally strong and its core architecture is likely the right solution for the current scope. It is not yet a complete or optimal code-generation-ready delivery plan. F-09 and F-10 remain material blockers already identified by the prior review; this independent review adds F-11 (missing stable active-call concurrency outcome) and F-12 (underspecified frozen authorization response). The optimal path is a targeted fix round that completes the existing S2 IVR orchestration contract and reuses one action-selection/claim predicate across resolve and activation confirmation. No implementation, migration or fourth slice should begin before those corrections are documented and independently re-reviewed.

Final plan review conclusion: `fail`.
