## 3. Findings

### PA39-CR-A-01 — Medium — Unexpected command-internal runtime exceptions are remapped to 503 instead of the frozen 500

- **Entry point / function**: `POST /api/v1/operations/catalog/versions` and `PUT /api/v1/operations/catalog/versions/{versionId}/draft` → `OperationsCatalogDraftController` → `DefaultOperationsCatalogDraftCommand.execute` (used by both `create` and `replace` and by recovery).
- **Exact file lines**: `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/DefaultOperationsCatalogDraftCommand.java:29-37` (`execute` catch) and `:39-46` (`recover` catch) map every non-typed, non-23505/40001, non-55P02/55P03 `RuntimeException` to `new Failure(Code.SERVICE_UNAVAILABLE)`. The controller then maps `SERVICE_UNAVAILABLE` to 503 at `backend/src/main/java/com/onecall/core/operations_iam/internal/web/OperationsCatalogDraftController.java:71-74`.
- **Triggering input/scenario**: a grammar-valid, authenticated ACTIVE-ADMIN request that reaches the owner command, and any unexpected non-SQL `RuntimeException` is raised inside `repository.create/replace`, `CatalogDraftSemantics`, `appendAudit`, or connection logic (e.g., a future refactor `NullPointerException`, `ClassCastException`, `IllegalStateException`, or a capability adapter throwing a plain runtime exception).
- **Actual branch**: `attempt` catches, marks rollback-only and restores; `execute` sees `sqlState == null`, not 23505/40001, not a typed `Failure`, and throws `Failure(SERVICE_UNAVAILABLE)`; the controller writes a sanitized 503 `SERVICE_UNAVAILABLE` problem.
- **Expected vs actual**: plan §6.4 (`docs/gateflow/pa39-operations-catalog-draft-write-foundation-plan.md:267`) says "Unexpected application serialization/programming failure → sanitized500", and §6.5 (`:302`) says "Unexpected controller/application exception | 500 INTERNAL". Actual is 503, so the frozen error contract and precedence are not met for command-internal programming failures.
- **Direct evidence**: the two catch blocks are total over `RuntimeException` with a terminal 503 `Failure`; the only 500 test (`backend/src/test/java/com/onecall/archtests/OperationsCatalogDraftWebTests.java:82`) injects a **mock command** that throws, so it never exercises the real `DefaultOperationsCatalogDraftCommand`'s catch. The unit test at `backend/src/test/java/com/onecall/core/catalog_order/internal/operationsdraft/DefaultOperationsCatalogDraftCommandTests.java:50` actively asserts `SERVICE_UNAVAILABLE` for an `IllegalStateException` thrown by `repository.create`, demonstrating the composition actually produces 503 and that the suite enshrines it.
- **Impact**: an internal defect/regression is reported as transient dependency unavailability rather than internal error. This breaks the declared 500 contract, can trigger client retry/backoff on a non-retryable bug, misleads 5xx monitoring/alerting, and makes the sanitized `INTERNAL` branch effectively unreachable for any programming failure thrown inside the command.
- **Safe fix direction**: in `execute` and `recover`, preserve typed `Failure` and SQL classifications (23505/40001 recovery, 55P02/55P03 409, known SQL/dependency states 503); map only unrecognized **non-SQL** `RuntimeException`s to `Failure(Code.INTERNAL)` (or let them propagate to the controller's `unexpected` handler). Ensure capability adapters emit typed `Failure(SERVICE_UNAVAILABLE)` or SQL exceptions for genuine unavailability. Update the command unit expectation and add an end-to-end real-command 500 test.
- **Fix risk**: Medium — the current fixtures use plain `IllegalStateException` to simulate audit/child/dependency faults and assert 503; those fixtures and expectations would need to inject typed dependency failures/SQLExceptions for the 503 cases. If the Controller instead intends all command-internal runtime exceptions to fail closed as 503, the plan lines 267/302 and the web 500 test wording must be corrected; the current code and contract text cannot both be right.
- **Severity**: Medium.

### PA39-CR-A-02 — Low — A zero-row version UPDATE skips the plan-mandated bounded locked reread

- **Entry point / function**: replace path → `JooqCatalogDraftRepository.updateDraft`, called from `replace`.
- **Exact file lines**: `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/JooqCatalogDraftRepository.java:197-200` executes the conditional version UPDATE through `exactlyOne(...)`; `:210` makes any non-one row count `unavailable()` (503). Plan §6.3 requires the reread at `docs/gateflow/pa39-operations-catalog-draft-write-foundation-plan.md:257`.
- **Triggering input/scenario**: a replace request whose conditional `UPDATE ... WHERE id=? AND product_id=? AND sale_status='DRAFT' AND published_at IS NULL AND revision=?` affects zero rows despite the preceding target `SELECT ... FOR UPDATE` — for example a future BEFORE UPDATE trigger returning `NULL` (suppresses the row without error), a fault-injection/zero-row adapter, or a non-cooperating direct writer that bypasses the advisory lock.
- **Actual branch**: `exactlyOne(0)` throws `Failure(SERVICE_UNAVAILABLE)`, the attempt rolls back, and `execute` returns 503; there is no second locked read and no state/revision/projection matrix decision.
- **Expected vs actual**: the plan requires one bounded locked reread under the already held advisory lock, then the matrix (unchanged DRAFT `r=e` remains the anomalous 503; vanished/mutated state would use 404/409/503 as applicable). Actual is an immediate 503.
- **Direct evidence**: `:197-200`/`:210`; plan line 257 explicitly says "bounded locked reread once and use state/revision/projection matrix".
- **Impact**: only observable when a row lock can be bypassed or an UPDATE is silently suppressed; in that case a state that should be classified as conflict/stale (or still 503 for the unchanged `r=e` anomaly) may be reported as 503. Under PostgreSQL row locking and the frozen V004 triggers the branch is effectively unreachable, so this is a defence-in-depth/plan-conformance gap rather than a known exploitable defect.
- **Safe fix direction**: on a zero row count, perform exactly one locked `readDraft` under the still-held advisory lock, re-run the §6.3 matrix without issuing a second UPDATE, and only then return 503 for the confirmed unchanged `r=e` anomaly.
- **Fix risk**: Low–Medium — adds a locked reread and a matrix branch; must not write a second time and must preserve rollback/503 on cleanup.
- **Severity**: Low.

### PA39-CR-A-03 — Low — The audit append does not assert that exactly one audit row was produced

- **Entry point / function**: create/replace → `JooqCatalogDraftRepository.appendAudit`.
- **Exact file lines**: `backend/src/main/java/com/onecall/core/catalog_order/internal/operationsdraft/JooqCatalogDraftRepository.java:205-209` executes `SELECT audit.append_fact(...)` through `dsl.fetch(...)` and discards the result. Plan §6.4 requires exactly one audit per actual create/replace (`docs/gateflow/pa39-operations-catalog-draft-write-foundation-plan.md:263`; create wording also at `:242`).
- **Triggering input/scenario**: `audit.append_fact` runs without raising but returns zero rows — e.g., a future replacement/overload of the function, a tampered function body, or a rule/trigger suppressing the insert. The frozen V001 function and grants make this unreachable in the current schema.
- **Actual branch**: no row count is checked; the version/child/token mutation and transaction commit proceed as if the audit succeeded.
- **Expected vs actual**: exactly one audit fact must be atomically present with the mutation; a silent zero-row append should roll back and be sanitized 503. Actual can commit a mutation with no audit.
- **Direct evidence**: `:205-209` uses `fetch` and ignores the result; the live tests count audit rows for normal paths but do not simulate a silent zero-return function.
- **Impact**: defence-in-depth/maintainability. Under the frozen V001 function it is not reachable; under a future function change or privilege/trigger manipulation it could allow an unaudited owner mutation, which is a material audit-integrity property.
- **Safe fix direction**: use a form that exposes the inserted row or count (`SELECT count(*) FROM audit.append_fact(...)` or `fetchSingle` plus a non-null/one-row assertion) and throw `unavailable()` (503) otherwise.
- **Fix risk**: Low — verify the function's return shape and the create `NULL` before-snapshot; add a unit/live negative probe.
- **Severity**: Low.
