## Findings

### A1-未修复-严重-详情 `snapshot` 被声明为“原样存储 JSON”，与冻结 `OrderSnapshotProjection` 不一致

- **位置**: 计划 §2:27（“use them directly”）、§3 详情 44-46（“`snapshot` is the stored immutable JSON value”）、§5:68（详情单条 SELECT）、§7 路径 3/5/6。
- **问题类型**: 契约缺失 / 投影语义 / 不可直接实施。
- **当前写法**: 详情接口把数据库 `catalog_order.customer_order.snapshot` 原值直接作为 API `snapshot` 返回，并只额外返回列 `snapshot_sha256`；没有描述任何“存储快照 → API 投影”的映射。
- **反例/失败场景**: PA41 存储的完整快照键为 `{schemaVersion, catalogVersionId, catalogOfferId, channel, versionToken, productCode, versionNo, offerType, audience, priceCents, currency, billingCycle, installments, benefitLines[lineKey,schedule,...], terms}`；OpenAPI `Order.snapshot` 引用 `OrderSnapshotProjection`，其 `additionalProperties: false` 且要求在对象内包含 `amountCents` 与 `snapshotSha256`，只允许 `benefitLines` 的 4 个字段，且没有 `versionNo`/`priceCents`/`terms`。原样返回会同时产生“多余键”（`versionNo`、`priceCents`、`terms`、`lineKey`、`schedule`）与“缺失必需键”（`amountCents`、嵌入的 `snapshotSha256`），违反冻结 schema；S3/契约校验或 `exactGetRoutesAndFrozenJsonShape` 会拒绝，或实现者被迫放宽断言。
- **为什么有问题**: 计划把“历史事实来自存储快照”错误等同于“响应体等于存储快照”。冻结 API 投影是一个**派生/收窄**视图（`priceCents→amountCents`、去 `versionNo/terms`、benefitLines 收窄、并入 `snapshotSha256`），不是数据库列值。当前 PA41 写路径本身就区分两者。
- **直接证据**: `CustomerOrderSemantics.snapshot(...)` 生成完整存储值（`CustomerOrderSemantics.java:97-148`）；`CustomerOrderSemantics.projection(full, hash)` 生成 API `Snapshot`（`:195-202`）；`JooqCustomerOrderRepository.java:108` 使用 projection 组装响应；`CustomerOrderSemanticsTests.java:95` 明确断言 `sha(canonical(projection(full,hash))) != hash`（即投影字节 ≠ 存储字节）；`CustomerOrderCreationService.Snapshot`（`CustomerOrderCreationService.java:18-23`）与 OpenAPI `OrderSnapshotProjection`（`onecall-v1.openapi.yaml:5411-5461`）、`CatalogBenefitLine`（`:5274-5290`）一致，而与存储形状不一致。且 `CustomerOrderSemantics` 为 package-private（`catalog_order.internal.customerorder`），新读取端口位于 `catalog_order.internal.customerquery`，无法直接复用该映射。
- **影响**: 生成违反冻结 OpenAPI 的响应；快照字段不可信；实现者需自行发明映射并可能改弱契约测试；后续 SDK/契约校验返工。
- **建议改法和验证点**: 在计划中显式定义详情 `snapshot` 的 `OrderSnapshotProjection` 映射（`priceCents→amountCents`、丢弃 `versionNo/terms`、benefitLines 仅保留 `entitlementType/quantity/validityDays/grantIntervalMonths`、对象内写入列 `snapshot_sha256`），并说明复用/上移现有 PA41 投影逻辑（例如提供共享 mapper，或授权移动/公开该逻辑）以获得实现路径；新增“存储字节 ≠ 投影字节”以及“原样存储值不可直接通过 schema”的测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 严重

### A2-未修复-严重-V020 破坏 PA25 冻结 oracle 与 19-migration 断言，且计划禁止必要的 PA25 编辑

- **位置**: 计划 §7:107（“V001–V019 and PA25 … not edit”）、§8:118（“migration/PA25 verification remain green”）、§9:140-143、§10:155（“no changes to … PA25”）、§11:163（“no … PA25 edits”）。
- **问题类型**: 迁移风险 / 验收标准矛盾 / 切片遗漏（跨切片耦合）。
- **当前写法**: 只新增 V020，声明 V001–V019 与 PA25 不可修改，同时要求既有 regression 和 PA25 验证保持绿色。

- **直接证据**: 上列 PA25 行号；`CustomerOrdersFixture.java:61`；`CustomerOrderRoleLeastPrivilegeIT.java:26-31,160-176`；`SharingQueryFixture.java:66-72`；PA40A `CustomerCatalogOfferReadPrivilegesIT.java:65-115,411-429`（重建 V018 历史 PA25 脚本、断言 432/19）在 PA25 前移后也需同步调整。
- **影响**: 直接破坏已提交的 PA41/PA25 回归；PA42 验收命令无法全绿；PA25 运维契约失效；需要跨切片会签。
- **建议改法和验证点**: 在计划中显式授权并枚举以下改动（并取消“no PA25 edits”）：(a) `backend/ops/postgresql/pa25-runtime-identities.sql` 的 `$frozen$` 追加 17 个 tuple（14 customer_order + 2 issuance + 1 schema USAGE；432→449）、`$history$` 追加 V020（19→20），同步 4022/4117-4118/4148 的计数；(b) PA41 `CustomerOrderRoleLeastPrivilegeIT`（19→20、PA25 check 语义）；(c) PA40A `CustomerCatalogOfferReadPrivilegesIT` 的历史脚本重建与 oracle；(d) 所有固定 `hasSize(19)`/`migrationsExecuted == 19` 的 fixture/IT——逐文件列出。若控制器坚持 PA25 冻结，则必须把该结论作为显式 residual/blocker 并修改“regressions remain green”的成功信号。

- **严重程度（低/中/高/严重）**: 严重

### A3-未修复-高-授权缺少 ACTIVE 账户/工作空间/成员关系的每次请求复核，ORGANIZATION 作用域信任会话工作空间

- **位置**: 计划 §3 详情 47、§5:64-67、§7 路径 4。
- **问题类型**: 授权/permissions/租户隔离。
- **当前写法**: “Validate trusted caller and selected workspace as the create path does: account/channel/workspace type non-null; PERSONAL iff organization ID is null. Invalid internal context fails closed…”，并且 ORGANIZATION 谓词为 `o.account_id = :trustedAccountId AND o.owner_organization_id = :trustedOrganizationId`；“there is no extra subject-ownership check”。
- **反例/失败场景**: `CustomerBearerAuthenticator` 直接用已验证会话内的 `selectedWorkspace` 构造 `TrustedCustomerCaller`，不重新读库（`CustomerBearerAuthenticator.java:49`）。若账户被 DISABLED，或组织成员关系被移除/停用，只要旧会话仍有效：列表会返回该账户订单；ORGANIZATION 列表会凭会话中的 `owner_organization_id` 返回该组织的订单，而不确认当前成员关系——即**成员被撤销后仍可读取组织订单**的授权泄漏。现有所有客户读取路径都显式执行 `repository.requireActiveContext(scope)`（账户 ACTIVE；ORG：组织 ACTIVE + 成员关系 ACTIVE + 角色 ∈ ADMINISTRATOR/MEMBER/EVIDENCE_MANAGER/AUDITOR，失败 403）。
- **为什么有问题**: Goal Confirmation 要求“cross-workspace resources … excluded”，而计划仅做形态校验，把工作空间可信度完全交给会话快照，未达到仓库既有读路径的授权基线。
- **直接证据**: `JooqCustomerBusinessNumberAccessRepository.java:12-26`；`CustomerCatalogOfferQueryService.java:82`；`CustomerBusinessNumberQueryService.java:63,82-90`；`CustomerBearerAuthenticator.java:20-50`。
- **影响**: 账户停用/组织成员撤销后仍可读订单，组织订单越权暴露；违反最小权限与既有读取约定。
- **建议改法和验证点**: 在 `SET LOCAL ROLE customer_iam_role` 之后、查询订单之前，显式执行与既有读路径等价的 ACTIVE 复核（账户 ACTIVE；ORG 时组织 ACTIVE + 成员关系 ACTIVE + 允许角色），失败映射为 403（与 `FORBIDDEN` 契约一致），PERSONAL/ORG 均适用；新增“账户 DISABLED → 403”“成员关系撤销/停用 → 403”“组织停用 → 403”的列表与详情测试；明确该复核发生在读事务内、零写入。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### A5-未修复-中-计划给出的列表 SQL 无法产生 `hasMore`（额外候选被 `page` 丢弃且无标志返回）

- **位置**: 计划 §3 列表 40、§5:68。
- **问题类型**: SQL 不完整 / 契约缺失。
- **当前写法**: `candidates` 以 `LIMIT :limit_plus_one` 取 `limit+1`，`page` 再以 `LIMIT :limit` 截断，外层只 `SELECT … FROM page p LEFT JOIN LATERAL … ORDER BY …`；随后文字称“Use the extra candidate solely to derive `hasMore`”。
- **反例/失败场景**: `page` CTE 已丢弃第 `limit+1` 行；外层结果最多 `limit` 行，既没有额外行也没有计数/标志列，应用层无从得知 `hasMore`。这与“用额外候选推导 hasMore”的文字自相矛盾；实现者必须自行发明机制（返回 `limit+1` 行并在应用层截断，或增加 `count/flag` 列）。
- **为什么有问题**: `OrderPage.hasMore` 是冻结必填字段（OpenAPI `OrderPage` 5589-5605）；计划既要求“一条语句”，又给出无法产出 `hasMore` 的 SQL，未达到“可直接实施”。
- **直接证据**: 计划 §5:68 的 CTE 文本；OpenAPI `OrderPage` required `[items,nextCursor,hasMore]`。
- **影响**: `hasMore` 计算不一致或为占位；分页边界测试无法据计划编写；可能出现多取一行却对多取行也做 issuance join 的性能偏差。
- **建议改法和验证点**: 明确单一语句方案：例如外层返回 `limit+1` 行（含 issuance 聚合）后由应用截断并据行数得 `hasMore`；或增加 `(SELECT count(*) FROM candidates) > :limit AS has_more`（或窗口计数）。新增空页、恰好 `limit`、`limit+1`、`limit=1`、`limit=100` 的边界测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### A6-未修复-中-V020 的 GRANT 语句未指定 `SET LOCAL ROLE <owner>`，grantor 与计划的归一化/断言不一致

- **位置**: 计划 §9:125-136（GRANT 块）与 §9:141-143（归一化含 grantor）。
- **问题类型**: ACL 语义缺失 / 不可直接实施。
- **当前写法**: 仅给出 `GRANT USAGE ON SCHEMA entitlement_metering …`、`GRANT SELECT (...) ON TABLE catalog_order.customer_order …`、`GRANT SELECT (order_id,status) ON TABLE entitlement_metering.entitlement_issuance …`，并称归一化“`grantor` is the actual migration owner”。
- **反例/失败场景**: Flyway 以超级用户执行 V020；若未 `SET LOCAL ROLE catalog_order_owner` / `entitlement_metering_owner` 再 GRANT，PostgreSQL 记录的 grantor 是迁移超级用户，而非 catalog_order_owner / entitlement_metering_owner。计划的 17-tuple 归一化与计划新增的 `v020HasOnlyExactSeventeenTupleDelta`（§8:115）都包含 grantor；PA25 oracle 亦记录 grantor。结果：要么实际 grantor 与断言不符，要么实现者按计划文本执行而测试按另一假设编写。
- **为什么有问题**: 既有权限迁移显式以 owner 身份授权并恢复（V016:1497-1509 动态 `SET LOCAL ROLE <grantor>`；V019:1922-1934 `SET LOCAL ROLE catalog_order_owner`；V004 以各 owner 授权）。计划省略了该关键语义，且其“grantor 为实际迁移 owner”的陈述与裸 GRANT 自相矛盾。
- **直接证据**: 上列迁移行号；计划 §9:141 的归一化字段；`CustomerCatalogOfferReadPrivilegesIT` 的 delta oracle 使用 `|catalog_order_owner|false`。
- **影响**: 生成错误 grantor 的 ACL；差异测试波动；后续 PA25/权限审计返工。
- **建议改法和验证点**: 在 V020 中明确：`SET LOCAL ROLE catalog_order_owner` 后授予 customer_order 14 列并恢复；`SET LOCAL ROLE entitlement_metering_owner` 后授予 schema USAGE 与 issuance 2 列并恢复；逐 tuple 说明预期 grantor；测试断言 `(grantee, object, privilege, grantable, grantor, column)` 精确匹配。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### A7-未修复-中-`issuanceStatus` 投影与 docs14 §4.20 的 grant-join R-04 投影未对账，`(order_id,status)` 授权依据不足

- **位置**: 计划 §2:28、§5:68、§6、§9:134-135。
- **问题类型**: 状态机/投影语义 / 设计源不一致 / open question 未收敛。
- **当前写法**: 仅授予并读取 `entitlement_metering.entitlement_issuance(order_id,status)`，按状态集合聚合出 `NONE/PENDING/ISSUED/FAILED/MIXED`，并声明“Do not … entitlement grant contents”。
- **反例/失败场景**: docs14 §4.20:1265 定义的“order-level entitlement projection”输入包括 `installment_no`、`entitlement_type`、`grant_id`、`issued_at`、`last_error_code`，且需 join `entitlement_metering.entitlement_grant`（`id, subject_id, entitlement_type, granted_units, valid_from, expires_at`），由 `catalog_order_role` 读取（docs14:3794）。docs15:271 与 OpenAPI 只定义 5 值 `issuanceStatus` 枚举，仅需 `status`。计划采用 docs15 的窄语义，却引用 docs14 且未解释为何不需要 grant/expiry/quantity；实现者若按 docs14 增加 grant join，则会因未授权而受阻，或对 `MIXED`/过期语义产生错误理解。
- **为什么有问题**: 两个设计真源描述的“order-level issuance projection”粒度不同；计划未显式收敛到“API `issuanceStatus` = docs15 状态集合投影，不含 grant/expiry”，也未说明 docs14 R-04 投影不属于本 API 字段。授权面与 SQL 因而缺少明确依据。
- **直接证据**: docs14:1265、docs14:3794（catalog_order_role 的 issuance 列）、docs15:271；计划 §6 映射表与 §9:134。
- **影响**: 投影定义歧义；授权面可能被扩到 grant 表或漏掉设计意图；`MIXED` 语义测试可能弱化。
- **建议改法和验证点**: 在计划中显式声明：客户 API `issuanceStatus` 仅由 `entitlement_issuance.status` 状态集合派生（`NONE/PENDING/ISSUED/FAILED/MIXED`），不 join grant、不使用 `valid_from/expires_at/granted_units`；docs14 §4.20 R-04 的 grant-join 投影不属于该字段，作为后续/内部投影处理；据此说明 `(order_id,status)` 授权充分。新增状态集合与非法/NULL 状态 fail-closed 的精确测试。
- **修复风险（低/中/高）**: 低-中
- **严重程度（低/中/高/严重）**: 中

## Open questions

1. **a0-models 与 V020 授权对账**: OpenAPI `x-onecall-a0-models` 为 list 声明 `catalog_order.payment_order`，为 detail 声明 `catalog_order.payment_order`、`activation_consent.consent_record`（`onecall-v1.openapi.yaml:814-817,871-874`；docs15:56-57），而计划明确不授权也不读取这两表，只读订单行上的 `paid_at/closed_at/payment_status/purchase_consent_id`。请在计划中说明 a0-models 是描述性元数据、`paymentStatus` 的权威源就是 `customer_order.payment_status`（V004 已用 `ck_customer_order_payment_shape` 绑定），以免实现者或评审误读为必须读 `payment_order`。
2. **Cursor 明文排序键与 docs15 §5:260**: docs15 明文要求 cursor 绑定排序键/最后记录内部排序值/过滤摘要，但“不得是 offset、SQL key、HMAC、时间戳或可枚举 ID 明文”。计划携带明文 epoch/纳秒与 order UUID（base64url+HMAC 包裹），并自述“opaque by contract, not confidential”。PA40B 的 catalog-offer codec 已采用同一模式，故可视为项目先例；但计划应显式对账该设计语句，或说明为何“base64url+HMAC 封装”满足“opaque”要求。
3. **ORGANIZATION 可见范围语义**: 计划 ORGANIZATION 谓词要求 `o.account_id = trustedAccountId AND o.owner_organization_id = trustedOrg`。若未来组织订单由组织所有、购买账户为组织主账户或其他成员，则“同组织其他成员只读可见”与“仅购买账户可见”存在产品歧义；PA41 仅创建 PERSONAL 订单，无法用现有请求构造验证。请明确组织读是“账户+工作空间”还是“工作空间内全员”，并据此定义 fixture/IT 的种子数据。
4. **Filter digest 措辞不一致**: §3:37 称“canonical empty-filter digest”，§4:59 又称其“canonically includes absent `subjectId=ALL` and `paymentStatus=ALL`”。同时 docs15:264 的 `subjectId/paymentStatus` digest 表述指向 O15 运营列表。请统一客户列表的 filter digest 定义（无过滤参数时是否为常量摘要、是否包含这两个 ALL 占位）。
5. **`amount_cents` 读取防御**: PA41 创建时以 `MAX_INTEGER = 9007199254740991` 约束，但 DB check 只要求 `>= 0`。当前读取计划未在读取侧校验 `amount_cents <= 2^53-1`；对历史/外部写入的异常值，JSON number 可能失真。请决定读取侧是否 fail-closed。

## Conclusion

`fail`

The overall direction (one read-only slice, narrow V020, HMAC keyset cursor, status-set issuance projection) is sound and largely maps to the Goal Confirmation without feature scope creep. However, the plan is **not implementation-ready**: it would return an API-invalid `snapshot` (A1), provably break the committed PA41/PA25 regression contract while forbidding the required PA25/oracle edits (A2), omit the ACTIVE account/workspace authorization re-check that every existing customer read performs (A3), and cannot be wired/tested within its own allowlist or against any real cursor key source (A4). The list SQL does not produce `hasMore` (A5), the V020 grantor semantics are unspecified (A6), and the issuance projection is not reconciled with docs14 §4.20 (A7). These are evidence-backed, actionable defects, not style issues. A bounded plan revision that fixes A1–A7 and closes the open questions is required before implementation.
