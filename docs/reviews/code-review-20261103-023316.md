- **Precedence.** Filter: authentication (401/503) then PA11 Accept negotiation (500); controller:

## Findings

### F1 - Test-strength gap: combined invalid limit+cursor precedence and valid-cursor/changed-limit are not exercised

- **Severity:** Low (test strength, no current behavior defect)
- **Trigger/branch:** `GET /api/v1/customer/shares?limit=0&cursor=<invalid>`; also a valid cursor replayed
  with a different `limit`.
- **Expected:** Plan section 5 order makes limit validation win (422) when both are invalid, and section
  4.1/8.2 allows changing page size with an otherwise valid cursor.
- **Actual:** The implementation is correct by construction: `parseLimit` is called before `parseCursor`
  (`CustomerSharesController.java:48-49`). However, `CustomerSharesWebTests.limitAndCursorValidationHaveDeterministicPrecedence`
  (`CustomerSharesWebTests.java:355-377`) tests invalid limit and invalid cursor only in separate requests,
  and never replays a valid cursor while changing `limit`. `CustomerShareCursorCodecTests.cursorBindingRejectsOtherAccountsAndWorkspaces`
  (`CustomerShareCursorCodecTests.java:39-53`) likewise does not include the plan's "same scope/different
  limit succeeds" case.
- **Impact:** A future reordering of validation would not be caught by a test even though the plan fixes
  the precedence; low regression risk.
- **Fix direction:** Add the combined-invalid request (assert 422) and a valid cursor + different-limit
  request (assert 200) to the existing methods; do not add classes/methods that change the frozen
  67/92/159 inventory without an accepted inventory change.
- **Risk:** Low.

### F2 - Test-strength gap: the DB-backed HTTP IT asserts only `shareId`, not the full eleven-field projection from real rows

- **Severity:** Low (test strength)
- **Trigger/branch:** Real PostgreSQL-backed `GET /api/v1/customer/shares` response mapping.
- **Expected:** Creator-context rows expose exactly the eleven accepted metadata fields and values from the
  fixture.
- **Actual:** `CustomerSharesIT.authenticatedHttpListsPersonalAndOrganizationCreatorMetadata`
  (`CustomerSharesIT.java:44-62`) asserts only the ordered `shareId` values via `itemIds(...)`. The full
  wire field set and nullable `maxAdmissions` are proven with a synthetic `ShareSummary` in
  `CustomerShareCursorCodecTests.wirePageHasOnlyFrozenFieldsAndNullableCursor`, and the repository mapping
  is covered by the frozen PA10 `SharingQueryServiceIT`, but no PA12 IT asserts the real-row values
  (`evidenceId`, mode/status, timestamps, `maxAdmissions`, `downloadAllowed`, generations) end-to-end.
- **Impact:** A regression in column-to-record mapping during adapter integration could be reported only by
  the older PA10 layer rather than by this slice's own HTTP IT; low regression isolation risk.
- **Fix direction:** Extend the existing IT method (without renaming it) to assert the full JSON object for
  at least one seeded personal row and one organization row; keep the eight-method inventory unchanged.
- **Risk:** Low.

### F4 - Non-blocking codec observation: decoded-length lower bound is looser than the legal minimum

- **Severity:** Info
- **Trigger/branch:** `CustomerShareCursorCodec.decode` on a short, well-formed-header payload.
- **Expected/Actual:** The minimum legal payload for a one-scalar share ID is 49 bytes; the code checks
  `bytes.length < 47` (`CustomerShareCursorCodec.java:55`) and relies on the exact-length formula
  (`bytes.length != 46 + (21*length+7)/8`) to reject 47/48-byte payloads. No invalid value is accepted:
  every such value is rejected immediately after by the length formula. The check is therefore a harmless
  dead/loose bound, not a defect.
- **Impact:** None observed; optional cleanup only.
- **Fix direction:** Change the constant to 49 or remove the redundant lower-bound check.
- **Risk:** Info.

## Explicitly considered and rejected as PA12 findings

- **`Accept: application/json;q=0, */*;q=1` returns 500.** The filter sorts by specificity before quality
  (`CustomerBoundaryFilter.java:57-67`), so a q=0 specific type can win over a q=1 wildcard. This is
  inherited PA11 behavior, and the PA12 plan explicitly freezes "authenticated unacceptable/malformed/q=0
  Accept retains PA11 mapping". It is not a regression introduced by this slice; recorded as an
  interoperability residual, not a finding.
- **Unkeyed cursor binding.** The SHA-256 binding is a normalized-filter fingerprint, not a secret or
  signature. A client can recompute it for its own account/workspace, but the repository always applies
  mandatory creator/workspace predicates, so an arbitrary anchor cannot widen visibility. The plan accepts
  this by design.
- **No list index, rate limiting, production verifier, session store or TTL.** All are explicit non-goals or
  deferred residuals owned by other roles, not PA12 defects.
