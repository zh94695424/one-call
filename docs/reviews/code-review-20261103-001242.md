## Residual Risk

1. **No supporting index for the listing query (capacity, pre-existing, now customer-reachable).** `sharing.evidence_share_grant` carries only `ix_share_grant_evidence (evidence_id, status)` and `ix_share_grant_expiry (status, expires_at)` (`V009__sharing.sql:71-72`) plus the PK and two UNIQUE constraints; **no index in any migration contains `created_by_account_id`** (the only `owner_organization_id` index is on `subject_number.business_subject`). The PA12 predicate `created_by_account_id = ? AND owner_organization_id {= ? | IS NULL}` with `ORDER BY valid_from DESC, share_id DESC LIMIT ?` therefore plans as a sequential scan plus sort over an append-only table on every page request. `JooqShareQueryRepository.java` is byte-identical to base, so this is inherited PA10/V009 shape — but PA12 is what exposes it on a customer-facing HTTP route, and `limit ≤ 100` bounds the returned rows without bounding the scan. Direction: a future migration adding `(created_by_account_id, owner_organization_id, valid_from DESC, share_id DESC)` (PostgreSQL b-trees index NULLs, so one index serves both the PERSONAL `IS NULL` and ORGANIZATION `=` branches). Owner: Platform/Database. Not fixable inside PA12's frozen scope.
2. **Cursor is scope-bound but not keyed.** `binding()` is `SHA-256(PREFIX + accountId + "\n" + scope)` with `PREFIX` a source-visible constant, not an HMAC over a server secret, so a legitimate owner can compute valid bindings and forge anchors. Impact is bounded and non-confidential: scope always derives from the trusted caller, a cursor can only narrow it, and all values are bound parameters under jOOQ `ParamType.INDEXED` + `PREPARED_STATEMENT`, so forgery yields at worst an arbitrary restart/skip within the caller's own data — never another creator's or workspace's rows, and never SQL injection. The delivered property (cursors do not cross surfaces, accounts or workspaces) is the one the tests assert and the one the API needs. Matches the primary judge's “unkeyed scope/filter-bound continuation value, not an authentication token”.
3. **Successful-response buffering is unbounded in principle.** `CustomerBoundaryFilter.BufferedResponse` accumulates the full body in a `ByteArrayOutputStream` before writing. Bounded in practice by `limit ≤ 100` and the frozen 11-field row (~tens of KB), but the mechanism itself has no cap and applies to every admitted response.
4. **No production verifier exists.** Any syntactically valid bearer yields a fixed 503, so `/shares` is inert until a separately approved adapter lands. Fail-closed and documented; it also means the end-to-end authenticated path is exercised only by test-owned verifiers.
5. **Route admission is a manual allowlist.** `CustomerBoundaryFilter.java:47-52` enumerates the two exact paths; a future customer route 404s until explicitly added. Safe by default, but it is a recurring edit site and a place where a later PA could regress `/me`.
6. **Keyset tie-breaking depends on collation.** `ORDER BY … share_id DESC` and the `share_id < ?` predicate share the database collation, so they are self-consistent, and `CustomerSharesIT` exercises equal-`valid_from` ties with non-ASCII ids against a real PostgreSQL ordered baseline. A non-deterministic collation would still need separate review; provisioning/collation is declared a Platform/Database concern.
7. **Reproduction limits bound my confidence.** With Docker, TCP bind and JVM agent attach all denied here, the 92 Failsafe methods, both JAR smokes, the 82 firewall probes, hosted CI and 35 of 67 Surefire methods are not independently reproduced. My positive runtime conclusions rest on 32 executed-green Surefire methods (including every architecture/boundary class and all 6 codec tests), the offline compile, and exhaustive static reading. Two independent reviewers hitting the identical 28/49-and-21-blocked split on the same focused subset is corroborating, not confirming, evidence for the socket/agent-dependent cases.
8. **Both findings are documentation-class and controller-owned.** Neither B2-01 nor B2-02 blocks this code-review gate on behaviour grounds; both do slightly weaken the re-verifiability of the paper trail for this candidate.
