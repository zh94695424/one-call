### C-02-部分修复-中-企业授权撤销通过展示列表解析而错误拒绝有效主体

- **入口/函数**: Web 企业管理员的“协议与授权 → 查看快照 → 撤销后续授权 → 确认撤销”，进入 `agreement-revoke`。
- **文件(行号)**: `web-prototype/evidence-hub.html:2627-2632`；同链路的展示列表与 canonical resolver 位于 `:2146-2173`，可见性与操作入口位于 `:2319-2341`。
- **输入场景**: Fresh Web 登录后切到企业空间、管理员角色；分别撤销有效的 `auth-6688`、`auth-9056`、`auth-3360`，以及先重新确认 `auth-7812` 再撤销其新版本。每次使用独立 fresh 页面，目标均有唯一同账户、同号码 canonical subject，初始状态为 `ACTIVE`、revision 为 `2`。
- **实际分支**: handler 先通过 `numberRecords().find(item=>item.number===record?.number)` 反查展示卡片，再交给 `setNumberActivation`。Fresh 企业管理员没有 added numbers 时，`:2150` 的条件为 false，紧随其后的 `else if(isEnterprise())` 在 `:2151` 把管理员卡片替换为仅有 `member-phone / 138 **** 6208` 的列表。四个授权号码均查不到卡片，`resolveNumberSubject(undefined)` 在 `:2155` 直接返回 `NOT_FOUND`，未查询已经存在的 canonical subjects。
- **预期行为**: 对当前角色可见且可撤销的有效授权，按授权记录的账户和号码唯一解析 canonical subject，经 shared `setActivationStatus` 提交 `ACTIVE → SUSPENDED`、revision、transition/event，并形成引用真实迁移的撤销记录；缺失或歧义主体才原子拒绝。
- **实际行为**: 四次均显示 `撤销失败：NOT_FOUND`；完整 canonical snapshot 与 `#content` 在点击确认前后完全相同，transition 增量为 `0`。有效授权无法撤销，主体仍为 `ACTIVE`，确认面板也没有收敛为撤销完成。
- **直接证据**: `:1700-1710` 已创建并激活对应 subjects，`:1734-1740` 的授权记录含相同号码及 subjectId；`:2319-2322` 允许管理员看到这些记录，`:2340-2341` 暴露撤销按钮；`:2629` 却把 canonical mutation 的入口参数限定为展示列表查找结果。`:2154-2158` 的唯一账户/号码 resolver 本身可以处理授权记录，当前 handler 没有把该记录传入。下表是本轮独立可见操作复现，不是从 handoff 推断。
- **影响**: 已修复的个人手机、个人固话及导入 Mini 固话路径可以提交规范迁移，但企业管理员对四条有效授权的后续服务停止操作全部失效。生命周期语义仍错误依赖展示列表；这属于 C-02 的剩余可操作授权路径，不单独扩大为企业号码管理功能 finding。
- **建议改法和验证点**: 保持现有授权可见性及角色检查，直接以被授权记录通过唯一 canonical resolver 解析并调用 shared owner，避免以 `numberRecords()` 是否展示该号码决定 canonical 对象是否存在。补充企业管理员上述四条授权的实际确认撤销回归，断言状态、revision、WEB transition/event ownership、撤销记录引用、无试用重发和跨端导入；继续覆盖缺失/歧义时 UI 与 canonical 原子不变。

- **严重程度（低/中/高/严重）**: 中。
