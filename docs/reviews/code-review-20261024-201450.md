### R-01 `[中高]` The generated discriminated unions for `ShareCodeRotation` (and P2 `verification`) are uninhabitable and use schema-name literals instead of the canonical wire values

- **Entry point / location**: `ShareCodeRotation` wrapper (`api/openapi/onecall-v1.openapi.yaml:6490-6534`), with wrapper `result` enum `ROTATED|REPLAYED` (`:6501-6503`) and branch consts `ROTATED` (`:6541-6543`) / `REPLAYED` (`:6576-6578`); P2 `ShareAdmissionRequest.verification` (`:7102-7123`), wrapper `mode` enum (`:7105-7107`) and branch consts `NONE`/`EXTRACTION_CODE`/`DESIGNATED_MOBILE`/`ORGANIZATION_MEMBER` (`:7124-7159`). Generated declaration: `tmp/openapi-client/onecall-v1.d.ts:2315-2363` (C18) and `:2543-2581` (P2).
- **Input scenario**: A generated TypeScript client receives the C18 `200 ShareCodeRotation` first/replay response, or constructs the P2 `ShareAdmissionRequest.verification` request for any of the four modes.
- **Actual branch**: Without a `discriminator.mapping`, `openapi-typescript 7.8.0` replaces each branch discriminator value with the component schema name (`api/openapi/node_modules/openapi-typescript/dist/lib/utils.mjs:17-38, 126-153, 163-213`). The generated wrapper therefore declares:
  - C18: `result: "ROTATED" | "REPLAYED"` intersected with `"ShareCodeRotationRotated" | "ShareCodeRotationReplayed"`, so the effective `result` type is `never`; no wire response can satisfy it. The wrapper's optional `extractionCode` is also intersected into the REPLAYED member (`d.ts:2325`), so the generated REPLAYED type still permits an extraction code even though the canonical branch and docs/15 §3.3 forbid it.
  - P2: `mode?: "NONE" | "EXTRACTION_CODE" | "DESIGNATED_MOBILE" | "ORGANIZATION_MEMBER"` intersected with `"ShareVerificationNone" | "ShareVerificationExtractionCode" | ...`, so the effective `mode` type is `never`; a generated client cannot construct `{ mode: "NONE" }`, `{ mode: "EXTRACTION_CODE", code: "..." }`, or any other real request.
- **Expected**: The generated client must represent the canonical wire values (`result: ROTATED|REPLAYED`; `mode: NONE|EXTRACTION_CODE|DESIGNATED_MOBILE|ORGANIZATION_MEMBER`) and must exclude `extractionCode` from the REPLAYED response. Plan §4.11:341 and §9.2:695-696 require generated-type assertions; docs/15 §3.3:145 and §6:280 claim the discriminated rotation contract and generated assertions.
- **Actual**: `check:s3`/strict tsc pass because `client-compat.ts` deliberately avoids literal discriminator assertions (`client-compat.ts:326-333` says “avoid literal const values due to possible discriminator renaming”; the branch assertions at `:330-333` inspect only the standalone branch components, and `AssertShareVerificationExtractionCodeKeys` at `:395-397` checks only the branch key set). No assertion checks `ShareCodeRotation['result']`, the wrapper's effective `extractionCode`, or `ShareAdmissionRequest['verification']['mode']`.
- **Direct evidence**: `tmp/openapi-client/onecall-v1.d.ts:2315-2328` (`ShareCodeRotation` wrapper including the optional `extractionCode`), `:2330-2363` (branch `result: "ShareCodeRotationRotated"` / `"ShareCodeRotationReplayed"`), `:2543-2581` (P2 wrapper and branch `mode: "ShareVerification..."`); `openapi-typescript/dist/lib/utils.mjs:17-38` (`parseRef(path).pointer.pop()` supplies the schema name when no mapping exists), `:126-153` and `:163-213` (branch enum patching); `client-compat.ts:310-333, 395-397`; plan §4.11:341, §9.2:695-696; docs/15:145,280.
- **Impact**: The generated client cannot represent the only success response of `rotateCustomerShareCode` or any `createPublicShareAdmission` verification request. This defeats the “code-generation-ready / generated TypeScript-client compatibility” success signal and the F-03 generated-compatibility correction; the green `tsc` result is a coverage gap, not evidence of compatibility.
- **Suggested correction**: Add a `discriminator.mapping` for both unions (for example `ROTATED: '#/components/schemas/ShareCodeRotationRotated'`, `REPLAYED: '#/components/schemas/ShareCodeRotationReplayed'`, and the four P2 mode mappings), or remove the duplicate wrapper discriminator property/union shape and generate from the branch consts; then add literal `Equal` assertions for the wrapper `result`/`mode` and for the replay `extractionCode` exclusion.
- **Verification / fix risk**: Low-medium; this is a generator-metadata/type-shape correction, not a wire-schema change. It must regenerate `onecall-v1.d.ts` and update `client-compat.ts`; the canonical JSON Schema satisfaction already passes.
- **Severity / classification**: 中高；`accepted`.

### R-02 `[中高]` The two approved opaque payloads generate as `Record<string, never>`, so I4 and K1 request bodies cannot carry a non-empty payload

- **Entry point / location**: `IvrEventPayload` (`api/openapi/onecall-v1.openapi.yaml:6904-6907`) referenced by `IvrCallEventRequest.payload` (`:6902-6903`); `OpaqueProviderPayload` (`:7242-7245`) referenced by `PaymentProviderCallbackRequest.payload` (`:7246-7248`). Generated declaration: `tmp/openapi-client/onecall-v1.d.ts:2464-2467` and `:2621-2625`.
- **Input scenario**: The IVR sends one real event payload on I4, or the payment provider sends one real normalized provider payload on K1.
- **Actual branch**: The canonical schemas are open by JSON Schema 2020-12 default (`type: object`, no `additionalProperties: false`), and they are intentionally exempted from the request closure walker as the two named opaque boundaries. However, `openapi-typescript 7.8.0` maps a bare object with no properties/additionalProperties to `Record<string, never>` unless `emptyObjectsUnknown` is enabled (`api/openapi/node_modules/openapi-typescript/dist/transform/schema-object.mjs:142-147`); the `generate` script has no such flag (`api/openapi/package.json:13`). The generated `IvrEventPayload` and `OpaqueProviderPayload` are therefore `Record<string, never>`.
- **Expected**: The generated client should expose the two approved opaque boundaries as open payloads (for example `Record<string, unknown>` or an equivalent), consistent with the canonical open object and plan §4.12 / docs/15 §6. The canonical contract itself already uses the right JSON Schema semantics.
- **Actual**: A generated client cannot type a non-empty I4 event payload or K1 provider payload; only `{}` is assignable. `AssertPaymentCallbackPayloadOpaque` (`client-compat.ts:439-446`) only checks that `PaymentProviderCallbackRequest` has the key `payload`, not that the payload is open, so the regression is invisible to the generated compatibility suite.
- **Direct evidence**: YAML `:6904-6907, 7242-7245`; `d.ts:2467` (`IvrEventPayload: Record<string, never>`), `:2621` (`OpaqueProviderPayload: Record<string, never>`), `:2464`, `:2624`; `openapi-typescript/dist/transform/schema-object.mjs:142-147`; `api/openapi/package.json:13`; `client-compat.ts:439-446`; plan §4.12:345-352; docs/15:283,355-356.
- **Impact**: I4 (call-event ingestion) and K1 (provider callback) generated request types are unusable for real payloads, directly weakening the two opaque trust boundaries and the generated-client compatibility claim. The canonical JSON Schema is not the defect; the generated projection is.
- **Suggested correction**: Declare `additionalProperties: true` (or an empty `{}` schema) on `IvrEventPayload`/`OpaqueProviderPayload` so the generated type is open, and add a generated assertion that `IvrCallEventRequest['payload']` / `PaymentProviderCallbackRequest['payload']` is not `Record<string, never>`; alternatively enable the generator's `emptyObjectsUnknown` option in a separately authorized config change.
- **Verification / fix risk**: Low; it changes generated types and may require a regenerated fixture, but it does not relax the two named opaque boundaries or any request closure rule. The current walker exemptions remain correct.
- **Severity / classification**: 中高；`accepted`.

### R-03 `[低]` `ShareCodeRotation.rotatedAt` is an optional response timestamp with no plan component or A0 grant-column ownership

- **Entry point / location**: `ShareCodeRotationRotated.rotatedAt` (`api/openapi/onecall-v1.openapi.yaml:6567-6569`) and `ShareCodeRotationReplayed.rotatedAt` (`:6595-6597`), with the wrapper also declaring the property (`:6527-6529`).
- **Input scenario**: A client reads a C18 first/replay response.
- **Actual branch**: The field is optional and is not in the plan's `ShareCodeRotation` component dictionary (`docs/gateflow/a1-production-openapi-surfaces-spec-plan.md` §5.6:467) or docs/15 §3.3:145. A0 §4.44 `sharing.evidence_share_grant` has no `rotated_at` column (`docs/14:2259-2280`); the only plausible source is `sharing.share_access_event.occurred_at` on the `CODE_ROTATED` event (`docs/14:2368`), but no mapping is declared.
- **Expected**: Every public response fact should map to an approved plan field or an explicitly documented A0 source; the prior F-04 correction removed an invented share `createdAt` on the same principle.
- **Actual**: An optional timestamp is exposed in both branches without a plan/A0 mapping. Because it is optional, no required response is unsatisfiable, and the value is derivable from the rotation event if that is the owner's intent; the issue is ownership/documentation, not schema satisfiability.
- **Direct evidence**: YAML `:6527-6529, 6567-6569, 6595-6597`; plan §5.6:467; docs/15:145; A0 §4.44:2259-2280 and §4.46:2368; the shared `occurred_at` column exists but is not cited.
- **Impact**: Potential semantic ownership drift in the public rotation response; a future implementation could synthesize or omit the value without an owner decision.
- **Suggested correction**: Either remove `rotatedAt`, or document that it is the `CODE_ROTATED` share access event's `occurred_at` and add it to the plan/docs/15 component ownership; add a generated assertion only if it remains.
- **Verification / fix risk**: Very low; optional field.
- **Severity / classification**: 低；`needs-more-evidence` (controller/plan/A0 owner decision).

## Open Questions

1. **Generated-client scope (R-01/R-02).** If the controller classifies the generated declaration as non-normative tooling output, both findings become residuals rather than contract defects; however, the accepted plan's success signal and §4.11/§9.2 explicitly require generated TypeScript-client compatibility, and the controller's own validation treats strict `tsc` as evidence. The controller should state whether generated wire values and open payloads are in scope.
2. **`rotatedAt` ownership (R-03).** Is the intended source the `CODE_ROTATED` share access event's `occurred_at`, or should the field be removed? No plan/A0 mapping currently exists.
3. **F-01 validator coverage.** The YAML itself is correct at every external occurrence, but `validateS3FixShapes` checks only operation-level path parameters and an 11-entry component list; it does not check query parameters `callId`/`taskId` (`YAML:1466-1481`), `IvrInboundResolveRequest.callId` (`:6806`), `IvrSessionSummary.callId` (`:4988`), `IvrSessionDetail.callId` (`:5198`), or `ShareCreated.shareId` (`:6439`). The F-01 positive/negative probes are literal-length checks (`contract-rules.mjs:2190-2217`), not schema-driven. A future regression on those occurrences would pass `check:s3`. This is a validation-coverage residual, not a current wire defect.
4. **F-10 fixture intent.** `validateS3FixProbes` contains a synthetic inline-opaque fixture whose body is comment-only (`contract-rules.mjs:2266-2273`) and a tautological broken-ShareCreated fixture (`:2220-2245`). The real fail-closed checks are in `validateSensitiveFields`/`walkRequestSchema`, but the claimed “negative fixtures” are partly documentation rather than executable assertions. T-S/uq/ck anchors also remain globally extracted rather than per-operation owned.
5. **C15 mode conditional.** `ShareCreated.extractionCode` is optional with a description that it is returned only for `EXTRACTION_CODE` (`YAML:6482-6489`); the schema does not enforce that conditional. Plan §5.6 specifies `extractionCode?`, so this is not raised as a material finding, but the server could return a code in another mode and still validate.
6. **A0 §10.14 `task.taskId = uuid`.** Still an A0/IVR documentation residual; the A1 contract deliberately exposes the opaque `outbound_call_task.task_id` under controller adjudication.
