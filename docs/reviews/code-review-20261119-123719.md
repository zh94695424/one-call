### F1 — 新-[低]-new catalog POSTs buffer an unbounded request body before the 8 KiB check (authenticated availability hardening)

- **Entry/function**: `OperationsCatalogVersionController.publishOperationsCatalogVersion` / `offsaleOperationsCatalogVersion`.
- **Files (lines)**: `backend/src/main/java/com/onecall/core/operations_iam/internal/web/OperationsCatalogVersionController.java:38`, `:44` (`@RequestBody byte[] body`) and `:66` (`body.length > 8192` → `422`).
- **Input scenario**: an authenticated employee session (any server-derived status/role; authority is evaluated later) POSTs `application/json` with a body far larger than 8 KiB, including chunked transfer.
- **Actual branch**: Spring MVC's `ByteArrayHttpMessageConverter` materializes the entire request body into a `byte[]` before the controller method runs. `parse(...)` only then rejects `body.length > 8192`. No servlet/Spring limit is configured in this repository (`backend/src/main/resources/application-web.yml` sets only web type/access-log/logging; no `maxPostSize`, `max-http-form-post-size`, `max-swallow-size` or equivalent; the only request-size handling under `backend/src` is `parse`'s own check).
- **Expected**: bounded ingestion at the HTTP seam, as the shipped Operations sibling already does: `OperationsSubjectsController.java:40` reads `request.getInputStream().readNBytes(8193)` and `CustomerSubjectActivationsController.java:43` reads `MAX_BODY_BYTES + 1`, both rejecting over-size input without materializing the whole entity.
- **Direct evidence**: controller signature/`@RequestBody` at `:38`/`:44`; post-materialization check at `:66`; sibling bounded read at `OperationsSubjectsController.java:40`; `CatalogVersionRequestBinderTests.rejectsInvalidUtf8AndOversizedBody` (`:96-101`) invokes `parse` reflectively and therefore does not exercise container ingestion.
- **Impact**: an authenticated employee can force heap allocation proportional to an arbitrarily large request body (OOM / service-wide availability loss). It is authentication-gated and this class of body-size residual is already owner-classified across the platform to Platform/Security edge bounding, so the incremental risk is Low; it is nevertheless a local deviation from the shipped bounded-read pattern on a newly exposed route.
- **Fix direction**: change the two method signatures to `HttpServletRequest` and read `request.getInputStream().readNBytes(8193)` (or add a container/edge request-size limit), preserving the exact `422 VALIDATION_FAILED`, headers, content length and every `@Test` identity. If deferred, record it with the existing Platform/Security body-size owner.
- **Fix risk**: Low. **Severity**: Low (new; Controller may elevate or defer).
