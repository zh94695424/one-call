### 03-未修复-中-Service 的 channel/audience 权威来源在 §5.4 中仍然歧义

- **Status**: needs-evidence
- **位置**: plan §4.1、§5.4（`Request(..., String channel, String audience, ...)` 与 step 1「derive audience from workspace type」）、§5.5 controller conflict 处理
- **问题类型**: 契约缺失 / auth authority 边界
- **当前写法**: `Request` 携带 `channel`/`audience`；controller 负责把 query 参数与可信值比对并在不同时 403；service step 1 声称「derive audience from workspace type」，但 step 2 又写成 `reader.fetchOffers(new Scope(channel, audience, offerType), ...)`，没有明确这里的 `channel`/`audience` 是 `caller.channel()`/derived audience 还是 `Request.channel()`/`Request.audience()`。
- **反例/失败场景**: 若实现者按字面把 `Request.audience()` 直接传给 reader，则任何绕过 controller 的调用（新单测、未来 controller、内部复用）都可以把 PERSONAL 会话的 audience 改成 ENTERPRISE，从而把 ENTERPRISE/QUOTE offer 投影给错误上下文；这违反 binding goal「account/workspace/session channel 是唯一权威，query 参数只能收敛」。同样，`Request.channel()` 若未被校验，可能过滤到其他渠道。
- **为什么有问题**: 该 slice 的核心安全不变量是「service 用可信 caller 派生 channel/audience」；§5.4 的写法把权威值和请求参数混在同一个 `Scope` 构造里，测试 oracle 也不明确（`activeChannelAudienceAndOfferTypeNarrowingReachTheOwnerReader` 可能把错误契约固化）。
- **直接证据**: §4.1 的「Session channel … and selected workspace are the only authority」；§5.4 的 `Request` 字段与 `new Scope(channel, audience, offerType)`；`TrustedCustomerCaller.Channel`/`SelectedCustomerWorkspace` 是可信值；controller 在 §5.5/§4.1 做 403 归一。
- **影响**: 潜在 authority-trust bug / 单测契约错误 / 后续调用者误用；review 无法确认「query 永不选择另一 channel/audience」在 service 层被强制。
- **建议改法和验证点**: 明确 service 只用 `caller.channel().name()` 与 `caller.selectedWorkspace().workspaceType()` 派生 channel/audience；`Request` 只携带 `offerType`（以及 anchor/limit），或由 service 显式校验 `Request.channel/audience` 等于可信值并在不等时拒绝；新增负向单测：Request 携带错误 audience/channel 时不得到达 reader。验证：service 单测 + WebTests 403/422 边界。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-低-cursor payload 的 base64url 最大长度写成 244，实际为 243

- **Status**: accepted-candidate
- **位置**: plan §4.6（cursor payload 长度说明）
- **问题类型**: 契约缺失 / 算术
- **当前写法**: 「Total 118+codeLength bytes (120–182), base64url without padding (160–244 chars), max 512」。
- **反例/失败场景**: `product_code` 约束 `^[A-Z][A-Z0-9_-]{1,63}$` 给出 codeLength ∈ [2,64]，总字节 ∈ [120,182]；base64url no-padding 长度 = ceil(4N/3)，N=182 时为 **243**（182 = 3·60 + 2 → 60·4 + 3），不是 244。若 codec 测试按 plan 的 244 写边界断言，会与真实编码器不一致。
- **为什么有问题**: 这是 plan 自身给出的精确范围，测试方法 `payloadVersionLengthDomainAndAnchorAreExact` 可能照抄错误上界。
- **直接证据**: plan §4.6；OpenAPI `Cursor` maxLength 512（外部无冲突）；V004 `ck_catalog_product_code`。
- **影响**: 低——最多导致测试边界断言偏一；不影响 512 上限与安全性。
- **建议改法和验证点**: 改为 160–243，或删除精确长度断言，改为「解码字节长度 == 118+codeLength 且 re-encode 等于输入」。验证：codec 单测对 2/64 字节 productCode 的最短/最长样例。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
