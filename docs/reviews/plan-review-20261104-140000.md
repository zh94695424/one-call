### F-01 — High — Canonical creation digests are defined over serialized strings, not the persisted JSON object graph

**Type:** canonical-data contradiction / unreachable contract

**Direct evidence**

- Plan `:138` states:
  - `content = canonicalJson(contentObject)`
  - `verification = canonicalJson(verificationObject)`
  - `scopeDigest = SHA-256(canonicalJson({content,verification}))`
  - persisted `content_sha256 = SHA-256(canonicalJson({content,verification,creation}))`
- `docs/14-production-data-model-and-flyway-schema-spec.md:255` defines `scopeDigest` as the section 2.5 canonical JSON of `{content, verification}` and `content_sha256` as the canonical JSON of the complete `content_snapshot` `{content, verification, creation}`.
- V009 `:55`–`:56` requires `content_snapshot->'content'`, `->'verification'`, and `->'creation'` to be JSON objects, not strings.
- V009 `:61`–`:62` only validates that `content_sha256` is lowercase 64-hex; it does not prove the value was computed from the persisted object nodes.
- Plan `:322` assigns a canonical-digest assertion to the evidence-projection IT, but does not remove the contradictory serialization instruction.

**Failure scenario**

If the implementation follows plan `:138` literally, the persisted snapshot contains string nodes:

`{"content":"{...}","verification":"{...}","creation":{...}}`

Then `content_snapshot->'content'` is `jsonb` type `string`, so `ck_share_grant_snapshot_shape` fails on INSERT. If the implementation instead stores object nodes and only uses serialized strings to compute the hashes, the hash is over JSON strings containing JSON, not over the persisted `{content,verification}` or `{content,verification,creation}` objects. The persisted digest is then silently wrong, because V009 does not recompute it. The two instructions cannot both be satisfied.

**Why it blocks code generation**

The plan calls the snapshot immutable and requires byte-for-byte reproducibility from the evidence projection and creation semantics. It does not define which representation is persisted or which representation is hashed. The implementation agent must invent a representation, and either choice violates part of the frozen plan or docs/14. Existing tests may repeat the plan’s own serialization and therefore fail to notice the mismatch.

**Fix criteria**

Define the persisted JSON nodes explicitly: `contentObject`, `verificationObject`, and `creationObject`. Persist those object nodes in `content_snapshot`; compute `scopeDigest` over the canonical JSON of `{contentObject, verificationObject}` and `content_sha256` over the canonical JSON of `{contentObject, verificationObject, creationObject}`. Do not serialize the nodes to strings before hashing. Add a test that reads `content_snapshot` back from PostgreSQL, asserts `jsonb_typeof` for all three nodes, and recomputes both digests from those objects using the docs/14 §2.5 canonicalization. No schema, OpenAPI, or docs/14 edit is permitted by this plan.

**Owner / destination**

Backend/Sharing with test evidence in `CustomerShareCommandServiceTests` and `CustomerShareCommandsIT`; canonicalization helper in the sharing command service.

### F-02 — High — The create insert conflict target and token-hash collision outcome are undecided

**Type:** persistence contract / hidden choice / incomplete error mapping

**Direct evidence**

- Plan `:117`: `insertGrantReturning` returns empty on zero-row conflict.
- Plan `:126`: a zero-row insert performs exactly one same-transaction `findCreationIdentity` reselect to classify replay versus changed-fingerprint conflict.
- V009 has two independent unique constraints: `uq_share_grant_share_id` at `:33` and `uq_share_grant_token_hash` at `:34`.
- `docs/14-production-data-model-and-flyway-schema-spec.md:3404` explicitly names both `share_id` and token-hash losers, but the plan does not translate that into SQL behavior or an error branch.
- Plan `:335` assigns “insertion/collision/append/commit rollback and sanitized internal errors” to IT 8, but no exact token-collision outcome, SQLSTATE, or response is stated.

**Failure scenario**

There are two incompatible implementations:

- `INSERT ... ON CONFLICT (share_id) DO NOTHING RETURNING ...` handles the replay race, but a token-hash collision raises `23505` on `uq_share_grant_token_hash`, aborts the transaction, and has no declared mapping.
- Bare `ON CONFLICT DO NOTHING RETURNING ...` swallows both conflicts, returns zero rows for a token collision, and then `findCreationIdentity(shareId)` returns empty because the colliding token belongs to a different share identity. The plan gives no branch that distinguishes this from a new identity or maps it to a sanitized response.

The first behavior can leak a raw constraint path to the generic exception handler; the second can leave an unclassified zero-row result. The prior accepted behavior was a sanitized `INTERNAL`/500 with no persisted facts for a token-hash collision, but the current plan never freezes that behavior.

**Why it blocks code generation**

The plan claims an exact create identity and atomic replay/conflict contract. The implementation agent must choose the conflict target and invent the token-collision branch, and IT 8 can pass with either an unintended 500 or an incomplete retry interpretation.

**Fix criteria**

Freeze the exact SQL and branch table:

- Use `ON CONFLICT (share_id) DO NOTHING RETURNING`, reselect by `share_id`, and handle exact replay versus changed fingerprint; or use bare `ON CONFLICT DO NOTHING RETURNING` and define the empty-reselect token-collision branch.
- Specify that `uq_share_grant_token_hash` collision is a sanitized `INTERNAL`/500 with rollback and no grant, Outbox, audit, access event, or returned secret, unless the frozen OpenAPI contract authorizes another code.
- Assign the exact assertion to IT 8 and add a service-level test for the zero-row/no-existing-share branch.
- Do not catch a raw `23505` and continue in the same aborted transaction without a savepoint or an explicit new transaction protocol.

**Owner / destination**

Backend/Database; `JooqSharingCommandRepository`, `CustomerShareCommandServiceTests`, and `CustomerShareCommandsIT` IT 8.

### F-03 — High — `TransitionResult.NotUpdated` after an access-event insert has no rollback rule

**Type:** transaction semantics / durable-fact integrity / hidden choice

**Direct evidence**

- Plan `:66` fixes the transition order as: append access event → conditional grant update → Outbox → audit.
- Plan `:122` allows `transitionGrant` to return `TransitionResult.NotUpdated`.
- Plan `:130` permits one bounded same-transaction reread for classification and expressly permits `NotUpdated`.
- Plan `:335` assigns transition context/lock/state and append/commit rollback branches to IT 12/17 and IT 13/18, but no rule says what happens to the already-inserted access event when the conditional update returns zero rows.
- `docs/14-production-data-model-and-flyway-schema-spec.md:3028` confirms the accepted owner-row order is grant lock, access-event insert, then conditional grant update/revision.
- `docs/14-production-data-model-and-flyway-schema-spec.md:3406` requires status, event, and audit to roll back together.

**Failure scenario**

The service appends the access event, calls `transitionGrant`, and receives `NotUpdated`. If the service returns a current-state 200 or a stable conflict response without aborting the transaction, the access event remains committed even though the grant was not transitioned. If it throws a conflict, the transaction likely rolls back, but the plan never states that rule. The implementation can pass the named “one conditional winner” test while leaving an orphaned access event on a forced zero-row path.

**Why it blocks code generation**

A transaction-shaped repository API is not enough; the service must know whether `NotUpdated` is a rollback-only outcome or a normal response. The access event is deliberately inserted before the conditional update, so this is not a generic commit-failure case. The plan’s “any append or commit failure” sentence does not cover a zero-row update that returns normally.

**Fix criteria**

State that any zero-row conditional update is a rollback-required outcome for the entire command transaction, including the already-inserted access event. Either make `NotUpdated` throw a stable conflict/current-state exception that is marked rollback-only, or return a result whose service path explicitly rolls back before responding. Add assertions to IT 12/17 and IT 13/18 that a losing or stale conditional update leaves no access event, Outbox, audit, state, generation, or revision change. Do not change the accepted event-before-update order without a separate authority decision.

**Owner / destination**

Backend/Database; `JooqSharingCommandRepository`, command service, and `CustomerShareCommandsIT`.
