### F-09-部分修复-[中]-任务领取的“当前 workspace/creator access”没有落成组织/账户生命周期状态谓词和锁

- **位置**: Plan §10.1 step 4 lines 488-494; shared read/lock order line 459; D43 line 204; table rows for `customer_iam.customer_account` (line 218) and `organization_access.organization` (line 221); `ivr.outbound_call_task` line 235; source `docs/12` §7.2 line 265; `docs/13` lines 44-46 and 208; `docs/11` lines 36-37.
- **问题类型**: 权限边界 / 契约缺失 / 并发恢复风险 / 不可直接实施.
- **当前写法**: The task path checks “personal owner/account or organization membership and the task creator's current task access” and reads/`FOR SHARE`s “personal account or organization membership” (lines 459, 491-494). D43 says blocking comes from “revoked workspace/membership or creator task access”. It does not name `organization.status = ACTIVE` for an organization workspace, does not name `customer_account.status = ACTIVE` for the creator/owner, and does not lock/serialize an organization-status change.
- **反例/失败场景**: A task is PENDING in an organization workspace. Operations sets `organization.status = SUSPENDED` or `DISABLED` while the membership row remains `ACTIVE`; the task creator account may also be disabled while the membership row remains. The claim reads binding, membership and subject, sees an unexpired PENDING task and positive entitlement, and claims/dials. The organization/creator account status was never a predicate under the written contract, and the organization row was not locked, so a concurrent status change can race the check.
- **为什么有问题**: The binding source `docs/12` §7.2 requires enterprise access to check organization *and* member status, role and resource ownership; `docs/13` §3/§6.3 requires the task creator's current workspace access to be revalidated before reservation; `docs/11` §1/§3 says a disabled account cannot log in and access is derived from valid membership/organization state. The plan's high-level phrase “current workspace access” does not make these facts code-generation-ready, and its lock order only names membership, not the organization or creator-account lifecycle row.
- **直接证据**: Plan lines 459 (locks “personal account or organization membership”), 491-494 (checks binding/membership/creator task access), 204 (D43 “revoked workspace/membership” but no organization-status predicate), 218 (account status `ACTIVE/DISABLED` exists), 221 (organization status `ACTIVE/SUSPENDED/DISABLED` exists); source `docs/12` line 265; `docs/13` lines 44-46/208; `docs/11` lines 36-37/69.
- **影响**: A call can be authorized after the owning/creator organization or account has been suspended/disabled, violating current-access and tenant/workspace security. A code-generation agent must invent which status fields are authoritative and which rows must be locked; the F-09 claim of complete task authorization is not fully supported.
- **建议改法和验证点**: Add explicit predicates to §10.1 step 4 and D43: `organization.status = 'ACTIVE'` for an organization workspace; `customer_account.status = 'ACTIVE'` for the owner and creator; `organization_membership.status = 'ACTIVE'` and the current role/task-access check. Lock or `FOR SHARE` the organization row and creator/owner account row in the shared read/lock order; require organization/account disable or suspension writers to take the corresponding row lock or subject lifecycle lock before commit. Add tests for organization suspension/disable and creator-account disable during the prompt and between check and claim. If the exact role matrix remains deferred (Q27), keep the status predicates mandatory and defer only the role mapping.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-12-部分修复-[中]-`DIRECT_AUTHORIZATION` 是 purpose，却被当作 action 使用，直接授权响应无法同时满足七动作枚举与 reservation/callee 规则

- **位置**: Plan §8 `ivr.ivr_decision` row line 240; §10.1 entry/direct rows lines 442-446 and write set line 557; §11 typed response table lines 654-673; source `docs/13` §6.2 lines 204-210 and §6.4 lines 226-232.
- **问题类型**: 公共契约缺失 / 状态机漏洞 / 不可直接实施 / 最佳实践偏离.
- **当前写法**: `purpose` is `INBOUND_RESOLVE / ACTIVATION_NEXT_ACTION / DIRECT_AUTHORIZATION`, while `action` is explicitly limited to seven values: `GUIDE_ACTIVATION`, `DIAL_TASK_CALLEE`, `ENTER_CALLEE`, `GUIDE_PURCHASE`, `REJECT`, `REJECT_SUSPENDED`, `REJECT_CALL_IN_PROGRESS` (lines 240, 654-655). Yet the write-set table names `DIRECT_AUTHORIZATION` in its “Action” column (line 557), `reservationId` is “NOT NULL iff `action = DIAL_TASK_CALLEE` or `DIRECT_AUTHORIZATION`” (line 665), `task.calleeNumber` is null in the redacted snapshot and non-null only for `action = DIAL_TASK_CALLEE` (line 663), and the action-specific rule says `DIRECT_AUTHORIZATION` has null task but non-null reservation fields and an encrypted confirmed callee (line 673).
- **反例/失败场景**: A direct DTMF authorization creates a decision with `purpose = DIRECT_AUTHORIZATION`. The contract requires `reservationId`/`authorizedRecordingSeconds`/`authorizationExpiresAt` and an encrypted callee. No seven-value action can satisfy the written rules: `DIAL_TASK_CALLEE` requires `taskMatch = CLAIMED` and a task; `ENTER_CALLEE` is declared to have null reservation fields; the rejection/guide actions have null reservation fields. The implementation agent must either add an eighth action (outside the stated enum and controller-preserving action set) or violate the nullability/callee rules. Client, audit and replay consumers then disagree about the action of the direct authorization response.
- **为什么有问题**: `docs/13` §6.2 fixes `action` to the seven table actions and says unknown enum values fail closed; §6.4 requires the direct outbound-authorization endpoint to return `reservationId`, `authorizedRecordingSeconds` and the cutoff after a confirmed entered callee. The plan has not defined how the direct response represents that authorization within the seven-action contract. The prior F-12 typed-response fix covered the DIAL_TASK_CALLEE fields but did not resolve this direct-purpose/action collision.
- **直接证据**: Plan line 240 (seven actions; purposes include direct); line 446 (direct purpose); line 557 (write-set row `DIRECT_AUTHORIZATION`); lines 654-655 (purpose enum vs seven actions); lines 663/665 (callee and reservation nullability keyed to an action that cannot be `DIRECT_AUTHORIZATION`); line 673 (direct action-specific rule); source `docs/13` lines 204 and 226-232.
- **影响**: The direct-authorization response is not code-generation-ready: the action value, task/callee boundary and reservation nullability cannot be implemented consistently, and tests can pass only by inventing an unapproved eighth action or by violating the seven-action enum. Replay/frozen-snapshot consumers may expose or omit the callee incorrectly.
- **建议改法和验证点**: Keep the seven-action enum. Treat `DIRECT_AUTHORIZATION` strictly as a decision purpose. Define the direct response action explicitly (for example, retain `ENTER_CALLEE` for the no-task direct path and carry the authorization in a purpose-scoped `authorization` object, or otherwise choose one of the seven actions) and make `taskMatch`, task fields, reservation fields, callee payload and nullability rules purpose-aware. Update the `ivr_decision` catalog, §10.1 write set, §11 typed table, action-specific rules and tests. If an eighth action is truly intended, require explicit controller/goal approval and update the enum, counts and every dependent assertion; do not leave the contract as an implicit eighth action. Add direct-response replay, nullability and callee-redaction tests.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### F-13-未修复-[高]-激活成功后的呼叫拒绝与“任何失败谓词回滚 consent/activation/trial”互相矛盾

- **位置**: Plan D45 line 206; §10.1 rollback line 559; sequence 1 line 578; scenario line 568; INV-08 line 381; source `docs/12` §9.1 lines 295-298; `docs/13` §6.3 line 224.
- **问题类型**: 状态机漏洞 / 事务边界 / 契约缺失 / 并发恢复风险 / 不可直接实施.
- **当前写法**: D45 and INV-08 say that once consent, activation and trial are validly established, a later task-access, binding, risk-policy or active-call failure is persisted as a call decision (`REJECT`/`REJECT_CALL_IN_PROGRESS`), the session remains `CONFIRMED`, and the activation/trial commit. Scenario 568 repeats the membership-revocation case: consent/activation/trial commit and the session stays `CONFIRMED`. The §10.1 rollback paragraph says “any failed predicate, conditional claim, reservation, decision insert or completion ... rolls back the whole local transaction, including a `NEW` idempotency row and any call/task/reservation/decision/Outbox writes from this attempt.” Sequence 1 contains both “any failure before commit rolls back ... consent, activation, transition, entitlement, claim and reservation facts together” and the later sentence that “the activation/trial commit” when a later call condition blocks dialing.
- **反例/失败场景**: A membership or task-access authorization is revoked after a valid confirmation has established consent/activation/trial but before the post-activation task claim. The shared predicate returns `REJECT` with `TASK_ACCESS_REVOKED`. If the implementation follows the blanket rollback text, the accepted consent, activation transition, trial, grant and balance are rolled back; if it follows D45/scenario 568, they commit while the rollback contract says they must not. The same ambiguity applies to a competing active call before the post-activation claim and to a technical failure after the first-trial write. The idempotency completion, session status and retry behavior therefore differ depending on which sentence the implementation agent follows.
- **为什么有问题**: `docs/12` §9.1 requires consent, activation and first trial to be one transaction and requires post-confirmation rechecks before reservation; `docs/13` §6.3 requires activation success to return a next action without skipping current state validation. A domain refusal due to a later call-level condition is not the same as a technical failure that prevents the transaction from committing. The plan must state which facts are durable for each category. Promising both full activation rollback and valid activation/trial commit for the same later-rejection branch makes the primary S2 transaction undecidable.
- **直接证据**: Plan D45 line 206; scenario line 568; INV-08 line 381; rollback line 559 (“any failed predicate ... rolls back ... consent, activation, transition, entitlement ...”); sequence 1 line 578 contains both the blanket rollback sentence and the later activation/trial commit sentence; source `docs/12` lines 295-298 and `docs/13` line 224.
- **影响**: A valid activation/trial can be lost on a call-only authorization change, or a call-only rejection can commit while the written rollback rule says it cannot. The first-result/idempotency row, `inbound_session` status, trial uniqueness and retry behavior become implementation-dependent. This is a material correctness and auditability blocker for the confirmation transaction.
- **建议改法和验证点**: Split the contract into two explicit categories. (1) **Technical transaction failure** at any lock/read/claim/reservation/decision/completion/Outbox step: roll back every write in the local transaction, including a `NEW` idempotency row, consent, activation, transition, trial/grant/balance, claim and reservation; return a retryable failure; commit no decision. (2) **Domain refusal** after consent/activation/trial were validly established (revoked task/workspace/binding access, competing call, no positive entitlement where the result is `GUIDE_PURCHASE`): commit consent/activation/trial, the one frozen no-dial decision and its idempotency completion; create no claim/reservation; keep the session `CONFIRMED`; do not roll activation/trial back. (3) A refusal before activation/trial (fresh `SUSPENDED`, `CONFIRMATION_NOT_ALLOWED`, pre-confirmation active-call guard) writes no accepted consent/trial and follows the specified rejected-decision/completion path. Replace “any failed predicate” and “any failure before commit” with these categories. Add forced technical-failure tests after each write, and post-activation revocation/active-call/zero-balance tests that assert the exact committed facts.
- **修复风险（低/中/高）**: 中 (requires careful transaction/test wording, not a schema redesign).
- **严重程度（低/中/高/严重）**: 高.
