## 7. Material findings

### RR-01-未修复-高-mixed-action structural-success contradicts grant-guard ACTIVE extension predicate

- **位置**: Plan §4.1 enforcement paragraph (`SHARE_GRANT_EXTENSION_INVALID`) versus §4.1 mixed-action classification and §7.4 mixed-action probe “Expected: structural success”; design §10.22 / §4.44 / §7.4
- **问题类型**: 状态机漏洞 / 测试缺口 / 契约缺失 / 其它 (internal contradiction in the B/02 repair)
- **当前写法**: The grant guard is specified to raise `SHARE_GRANT_EXTENSION_INVALID` when expiry increases unless the grant “requires ACTIVE and old expiry still future”. The same section requires an `ACTIVE → LOCKED` UPDATE that also strictly increases `expires_at` to be **structurally accepted**, with an S2 witness asserting success and classifying the write service-forbidden.
- **反例/失败场景**: Implementation agent writes `IF NEW.expires_at > OLD.expires_at AND NEW.status <> 'ACTIVE' THEN RAISE SHARE_GRANT_EXTENSION_INVALID`. The S2 mixed probe then fails (P0001, zero structural success). Stop condition “failing cumulative evidence” fires. The agent may then (a) weaken the guard by dropping the ACTIVE check without authority, (b) weaken/reverse the probe expectation, or (c) stop for plan clarification — all of which are avoidable if the predicate referent is stated.
- **为什么有问题**: Design §10.22 only rejects expiry *decrease*. Extension-on-ACTIVE is a named service action (`ACTIVE → ACTIVE` in §7.4), not a frozen trigger ban on expiry increases whenever `NEW.status` is not ACTIVE. The fix’s core B/02 claim (“structurally possible”) is not guaranteed by the plan’s own guard rules. This is a new contradiction in the repair text, not a pre-existing design conflict.
- **直接证据**:
  - Plan §4.1: “Increasing expiry requires ACTIVE and old expiry still future (`SHARE_GRANT_EXTENSION_INVALID`)” listed under “Enforce … at the grant guard”.
  - Plan §4.1: “an `ACTIVE → LOCKED` update may also strictly increase `expires_at` while the old expiry is future” / “structurally possible”.
  - Plan §7.4 mixed probe `SET status = 'LOCKED', expires_at = expires_at + interval '1 hour' ...` “Expect structural success”.
  - Design §10.22 `trg_share_grant_guard`: “reject a decrease of `expires_at`” only; no NEW.status=ACTIVE gate on increases.
  - Design §7.4: extension is `ACTIVE → ACTIVE` named action, not a mixed lock+extension action.
- **影响**: Implementation agent generates a guard or S2 witness that cannot both match the plan; S2 fails or an unauthorized predicate weakening is used to force green; B/02 acceptance is not testable as written; later service “one named action per update” residual is muddied by an accidental structural mixed-ban.
- **建议改法和验证点**:
  1. Disambiguate the guard sentence: either “Increasing expiry requires `OLD.status = 'ACTIVE'` and `clock_timestamp() < OLD.expires_at` (`SHARE_GRANT_EXTENSION_INVALID`)”, or “Structural guard only rejects expiry decrease (and optionally persist-before-expiry for the EXPIRED edge); ACTIVE+future is the *service* precondition of the named extension action, not a `NEW.status` trigger gate.”
  2. Keep the mixed probe’s expected structural success only under that disambiguation; if the project instead wants a structural mixed-ban, then B/02 must be reclassified (not service-forbidden-but-structurally-accepted) and the fix narrative updated — do not leave both claims live.
  3. Verification: one S2 case proves lock-only (expiry unchanged) succeeds; one S2 case proves pure extension on ACTIVE succeeds; the mixed probe either structurally succeeds with the OLD.status reading, or is explicitly a negative `SHARE_GRANT_EXTENSION_INVALID` witness if that is the chosen contract.
- **修复风险（低/中/高）**: 低 (bounded wording/contract clarification; no DDL/object expansion)
- **严重程度（低/中/高/严重）**: 高

### RR-02-未修复-中-generation-change authorization sentence may over-ban the same-state probes

- **位置**: Plan §4.1 “Revoke/expiry generation +1 and lock generation unchanged are checked with their status edges” versus §4.1 same-state classification and §7.4 same-state probes
- **问题类型**: 状态机漏洞 / 测试缺口
- **当前写法**: Generation deltas are described as “checked with their status edges”, while the later explicit paragraph says the guard “does not ban same-state terminal generation increases” and §7.4 requires those increases to structurally succeed.
- **反例/失败场景**: Implementation agent treats generation changes as legal *only* on revoke/expiry/rotation edges and raises `SHARE_GRANT_GENERATION_INVALID` otherwise. Same-state EXPIRED/REVOKED probes then fail despite the explicit success expectation.
- **为什么有问题**: Same class of enforcement-sentence vs witness contradiction as RR-01, but here a later explicit sentence already asserts the desired semantics; the earlier sentence is merely easy to over-read. Less severe than RR-01 because the override exists.
- **直接证据**: Plan §4.1 enforcement sentence vs “it does not ban same-state terminal generation increases”; §7.4 same-state probe “Expect structural success”; design §10.22 only bans generation *decrease*.
- **影响**: S2 same-state witnesses fail or guard is accidentally hardened into a terminal-row prohibition the plan forbids.
- **建议改法和验证点**: One sentence: “Generation *decreases* are forbidden; generation increases are not limited to the named revoke/expiry/rotation edges in the structural guard (service exactly-once remains excluded).” Keep §7.4 probes as-is. Verification: same-state +1/+1 succeeds; generation decrease still `SHARE_GRANT_GENERATION_INVALID`.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
