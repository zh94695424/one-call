## Findings

### F-PA17-01 — Post-commit reconstruction recheck omits persisted session/admission expiry, changing the frozen 410 outcome in a narrow replay race (Medium)

- **Entry/function:** `DefaultShareAdmissionService.ticketContext` (`backend/src/main/java/com/onecall/core/sharing/internal/admission/DefaultShareAdmissionService.java:257-267`) calls only `predicates(...)`; `predicates` (`.../DefaultShareAdmissionService.java:136-158`) has no session/admission-expiry check. The check exists only in the earlier authoritative branch (`.../DefaultShareAdmissionService.java:97-101`). `issue` (`.../DefaultShareAdmissionService.java:269-275`) maps a nonpositive ticket window to `ticketFailed(..., "TICKET_WINDOW_EXPIRED", SHARE_SESSION_EXPIRED)` (`.../DefaultShareAdmissionService.java:301-311`).
- **Triggering input:** a same-key replay whose persisted `sessionExpiresAt`/`admissionExpiresAt` is still in the future when the authoritative replay transaction commits, but elapses before the post-commit `ticketContext` transaction samples its facts/clock (short approved TTL plus a slow post-commit lock/facts acquisition). The plan requires the reconstruction read to require `clock_timestamp() < sessionExpiresAt` and `< admissionExpiresAt` before reissue (plan §2.3 step 2, §9.31 step 3; docs/14 §9.31 step 3).
- **Expected behavior:** the session-expired replay is stopped by the current-state recheck with `410 SHARE_SESSION_EXPIRED`, before any ticket-policy lookup, provider, Redis/media I/O, or event append; the plan/§6 method `ticketPolicyUnavailableBeforeAdmissionLeavesNoRows` states a denied replay/current-state wins before policy with zero policy calls.
- **Actual behavior:** in that race the post-commit `predicates` passes. If the post-commit replay ticket policy is available, `issue` sees a nonpositive minimum window and appends a `TICKET_FAILED` (`TICKET_WINDOW_EXPIRED`) before returning 410; if the post-commit replay policy is unavailable, `admit` returns `503 SHARE_SESSION_POLICY_UNAVAILABLE` (`.../DefaultShareAdmissionService.java:77`, `199-207`) instead of 410. No admission/count/revision damage and no ticket/credential is issued either way.
- **Impact:** narrow but real error-precedence/side-effect defect: the wrong HTTP status when policy is unavailable during the race, and an extra policy call plus a durable `TICKET_FAILED` on a replay that the frozen order says must be a pre-policy session-expiry denial. The existing `sessionExpiryReturnsGoneWithoutRenewal` test (`PublicShareAdmissionIT.java:158-163`) only covers expiry before the authoritative transaction, so this interleaving is untested.
- **Concrete fix + validation:** move the existing-admission session/admission-expiry predicate into the shared predicate helper used by `ticketContext` (or add an explicit check there before the replay policy lookup). Add a deterministic unit/IT test with a clock seam or a blocking post-commit hook proving session expiry between transactions returns 410 with zero policy calls, no `TICKET_FAILED`, and no provider calls. Preserve the current authoritative check and the fresh-admission path.
- **Fix risk:** Low. One predicate move plus one race test; no schema, payload, event-identity, or count change.

### F-PA17-02 — Personal-share subject ownership and non-object captured identity are weaker than the frozen S3 projection (Low)

- **Entry/function:** `DefaultShareAdmissionService.facts` (`backend/src/main/java/com/onecall/core/sharing/internal/admission/DefaultShareAdmissionService.java:189-196`) re-reads `business_subject.owner_account_id`/`owner_organization_id` but only compares `ownerOrganizationId` with `grant.ownerOrganizationId()`. The personal owner account is never compared with the grant creator. `JooqShareAdmissionRepository.grant` (`.../JooqShareAdmissionRepository.java:42-50`) reads `identity_at_capture` and treats any node without a `bindingId` as "no captured binding"; it does not reject a non-object `identity_at_capture`. `GrantSnapshot` (`.../ShareAdmissionRepository.java:31-36`) and `GRANT_COLUMNS` (`.../JooqShareAdmissionRepository.java:19-22`) do not carry `created_by_account_id`, although V012 grants that column.
- **Frozen rule:** the existing S3 ownership rule for a personal creator is `subjectOwnerOrganizationId` empty AND `ownerAccountId == creator account`; for an organization creator it is `organizationId == subjectOwnerOrganizationId` (`DefaultCustomerShareCommandService.java:175-178`, `JooqSharingCommandRepository.java:108-143`). Plan §2.2 requires the exact subject-ownership/captured-binding/risk recheck; docs/14 §10.21 grants `owner_account_id` and `created_by_account_id` for that projection.
- **Triggering input:** a personal share whose subject-owner account differs from the grant creator (or an `identity_at_capture` value that is not an object) presented through a schema-valid admission. The subject-ownership guard currently makes a set owner immutable (docs/14 INV-05/owner guard; no transfer), which sharply limits exploitability; this is a defense-in-depth/contract-completeness gap rather than a demonstrated live bypass.
- **Expected behavior:** for a personal grant, the current subject owner account must equal the grant creator (`created_by_account_id`); an organization grant must match the subject owner organization; a malformed/unresolvable `identity_at_capture` must fail closed as unresolved rather than silently selecting the current active binding.
- **Actual behavior:** only the organization equality is checked; a personal subject owner account mismatch is accepted; a non-object `identity_at_capture` is interpreted as "no captured binding". The existing tests do not cover either case (`wrongTenantAccountOrMembershipFailsClosed` covers member tenant/membership; `openRisk...` covers risk).
- **Impact:** the admission recheck does not implement the exact frozen S3 ownership projection for personal shares, and the captured-identity fallback is more permissive than the existing command-side `isObject()` fail-closed rule. No test or runtime witness exercises the gap.
- **Concrete fix + validation:** add `createdByAccountId` to `GrantSnapshot` and `GRANT_COLUMNS`, compare it with the personal subject owner account (organization equality remains), and reject a non-object `identity_at_capture` as `DEPENDENCY_UNAVAILABLE`. Extend existing member/ownership tests without adding methods; verify no raw identifiers appear in diagnostics.
- **Fix risk:** Low-to-Medium. Small repository/service/test change, no schema or migration change; V012 already grants the needed column.
