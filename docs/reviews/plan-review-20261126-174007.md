## 5. Open questions

1. §4 privilege table cites `V006:649–651` for the entitlement owner's own-table `SELECT` "with own-schema USAGE"; the schema `USAGE` itself is `V004:492–493`. The no-V021 conclusion is unaffected (both grants exist and `catalog_order_role` also has the narrow `V006:671–672` issuance `SELECT`), but Controller may want the citation made exact in a future doc-only pass.
2. §6 describes the filter digest semantically (length-prefixed, ordered presence, canonical UUID/ASCII bytes) rather than byte-for-byte. This is sufficient for an opaque, single-implementation cursor, but a short compatibility note would reduce future rotation/rollout ambiguity.
3. §5/§9 says to extend the ERROR-dispatch TRACE handling "if needed". The new order IT's real-HTTP TRACE=404 probe will force the correct implementation; the conditional phrasing is not a blocker because the existing IvrSession IT keeps its own TRACE=500 behavior and §5 says "preserve other routes".
4. The README edit must retain the PA36/PA42 current-section markers asserted by `CustomerCatalogOfferReadAclBoundaryTests:118–122` and `EvidenceRoleIvrAssociationAclBoundaryTests:127–133`. §9/§11's "retain all assertions"/"assertion strength retained" covers this, but spelling out those markers in the README step would make the constraint unmistakable.
5. §5 says limit parsing uses the "current bounded decimal parser (including numerically valid leading zeros)". The existing parser is `[0-9]{1,3}` + range 1..100 (e.g. `001` accepted, `0001` rejected); tests should lock that exact behavior rather than arbitrary-length leading zeros.
6. Control line 33's "OPENAPI-required authenticated-but-wrong supported employee role as 403 only where representable/mocked" is interpreted by §5.3 as "no representable third role, so no mock-403 canary". This is deterministic and matches the DB CHECK; Controller may want to confirm no mock-403 canary is expected.
