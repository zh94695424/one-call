### F-01 `[高]` S3 narrows A0 opaque protocol identifiers to UUID, so valid `taskId`/`callId`/`recordingId`/`shareId` values are unrepresentable

- **入口/位置**: `OutboundCallTask.taskId` (`api/openapi/onecall-v1.openapi.yaml:6267-6269`), C7/C8 path `{taskId}` (`:2689-2695`, `:2752-2758`); `IvrDecision.callId` (`:6553-6555`) and `IvrDecision.task.taskId` (`:6619-6621`); `CallEventReceipt.callId` (`:6767-6768`); `RecordingDeclarationRequest.recordingId` (`:6789-6791`), `RecordingDeclaration.recordingId` (`:6811-6813`), I6 path `{recordingId}` (`:3563-3569`); `ShareState.shareId` (`:6336-6338`), `ShareSummary.shareId` (`:6377-6379`), `ShareCodeRotation.shareId` (`:6444-6446`), C17/C18 path `{shareId}` (`:2970-2976`, `:3046-3052`).
- **输入场景**: A customer creates a task and reads/cancels it by `taskId`; the IVR resolves a call and then calls I2-I6 using the returned `callId`/`recordingId`; a customer creates a share and later revokes/rotates by `shareId`. The design examples are opaque values such as `CALL-20261021-001` and `CT-01J...` (`docs/13:181-192`).
- **实际分支**: Each of these fields/path parameters declares `format: uuid`. A value accepted on one hop (I1 request `callId` is `1-128` text at `:6673-6676`) may be rejected on the next hop (`{callId}` is `uuid`). The deterministic `share_id` is a text identity in A0 but the public `shareId` is modeled as the internal `id` UUID.
- **期望**: Plan §4.10 (`:329`) assigns `taskId` 1-64, `callId` 1-128, `recordingId` 1-128 and `shareId` 1-128 as opaque strings. A0 confirms `ivr.outbound_call_task.task_id` is `text` 1-64 (`docs/14:1273,1298`), `ivr.inbound_session.call_id` and `ivr.call_record.call_id` are `text` 1-128 (`docs/14:1343,1362,1398,1422`), `evidence.recording.recording_id` is `text` 1-128 (`docs/14:2088,2104`), and `sharing.evidence_share_grant.share_id` is `text` 1-128 (`docs/14:2262,2284`).
- **实际**: UUID-only formats on all four identities; the generated client types still project `string`, but any schema-validating runtime/edge rejects the design's opaque values, and the A0 `share_id` text identity is not represented by `ShareState.shareId`.
- **直接证据**: YAML lines above; A0 §4.23/§4.24/§4.25/§4.40/§4.44; plan §4.10; `docs/13:181-192,228-232`.
- **影响**: Real IVR/customer values can fail the contract at a trust boundary; C15's deterministic `share_id`/creation identity is conflated with a different (UUID) A0 column; generated clients and docs encode the wrong identifier domain. A0 §10.14 itself says `task.taskId` is `uuid` (`docs/14:3738`), so the task identity needs an explicit owner decision rather than a silent schema choice.
- **修复**: Use `type: string` with the A0 lengths (`taskId` 1-64, `callId` 1-128, `recordingId` 1-128, `shareId` 1-128) for every path/body/response occurrence, and decide explicitly whether `task.taskId` exposes `outbound_call_task.task_id` (text) or `id` (uuid). Map `shareId` to `sharing.evidence_share_grant.share_id`, not the internal UUID PK. Regenerate types and add negative/positive fixtures for a non-UUID opaque value.
- **验证/修复风险**: Medium: changing formats can break generated-client assumptions and any saved fixtures; the A0 §10.14/task-table identity conflict must be resolved by A1/A0 owners. No runtime behavior is claimed either way.
- **严重度/建议分类**: 高；建议 `accepted`.

### F-02 `[高]` `ShareCreated`'s `allOf` plus `additionalProperties: false` is unsatisfiable, and it disables the ShareCreated one-time-secret assertion

- **入口/位置**: `ShareCreated` (`api/openapi/onecall-v1.openapi.yaml:6414-6437`; the second branch closes at `:6418`), used by C15 201/200 (`:2842-2853`); generated `tmp/openapi-client/onecall-v1.d.ts:2293-2295`; rule `api/openapi/contract-rules.mjs:1347-1354`; `api/openapi/client-compat.ts:310-326`.
- **输入场景**: A successful first share creation (201) or same-fingerprint replay (200) returns `ShareCreated`, which must contain the required `ShareState` fields (`shareId`, `verificationMode`, `status`, `validFrom`, `expiresAt`, `admissionsUsed`, `downloadAllowed`, `revocationGeneration`) plus optional one-time secrets.
- **实际分支**: Under JSON Schema 2020-12, the second `allOf` branch declares `additionalProperties: false` but only lists `capabilityToken`, `extractionCode` and `createdAt` in its own `properties`. Every `ShareState` field is therefore “additional” against that branch and rejects the instance. No non-empty `ShareCreated` instance can satisfy the schema.
- **期望**: The plan requires a valid `ShareCreated` response with one-time secrets (`plan §5.6:466`, §4.11:341, §9.2:696) and default closed objects only where the same schema declares the fields (`§4.11:338`).
- **实际**: The YAML is syntactically valid and the generated type is an intersection, so lint/tsc pass, but schema-validating servers/gateways cannot accept a real 201/200 body. In addition, `validateSecretDirection` reads `schemas.ShareCreated.properties` directly; because the fields live under `allOf`, that check is dead. `client-compat.ts` has no assertion that `ShareCreated` contains `capabilityToken`/`extractionCode`, although the plan requires that generated-type assertion.
- **直接证据**: YAML `:6415-6418`; generated declaration `:2293-2295`; rule `:1347-1354`; client-compat `:310-326` (rotation/request negatives only); plan §4.11:341 and §9.2:696.
- **影响**: The first-response secret delivery is not statically proven; a future removal of `readOnly`/`x-onecall-return-once` would pass `check:s3`; an OpenAPI validator rejects the only success response. This is a core C15 contract defect.
- **修复**: Flatten `ShareCreated` (all `ShareState` properties plus the secret fields) or place `additionalProperties`/`unevaluatedProperties: false` on a wrapper that can see all properties; make the secret-direction rule resolve allOf branches/schema refs; add a `client-compat` assertion that `capabilityToken` and `extractionCode` exist on `ShareCreated` and carry the expected optional/read-only response shape. Add a negative rule fixture for a missing annotation.
- **验证/修复风险**: Low mechanical risk, but the schema shape and generated type must be regenerated; keep the rotation schema separate and keep request-body secrets rejected.
- **严重度/建议分类**: 高；建议 `accepted`.

### F-03 `[中高]` C15/C18 replay paths cannot carry one-time secrets correctly; they either re-expose a capability token/code or cannot satisfy the required response

- **入口/位置**: `createCustomerShare` 200 replay (`api/openapi/onecall-v1.openapi.yaml:2848-2853`; description `:2804-2809`), 201 first response (`:2842-2847`); `rotateCustomerShareCode` 200 (`:3060-3066`) and `ShareCodeRotation` (`:6438-6468`, required `extractionCode` at `:6442,6459-6465`); docs/15 `:142,145,280`.
- **输入场景**: The customer retries the same `creationRequestId` after losing the first response, or retries the same code-rotation action identity after losing the first response.
- **实际分支**: The C15 200 response is the same `ShareCreated` schema and its description says it “returns the original ShareCreated projection once more”, while the plan says a replay returns existing grant metadata and does **not** reissue the token/code (`plan §4.7:286`, §4.9:317; A0 T-S3-03 §9.29:3381,3386, and §4.44:2313 “metadata only”; “lost creation response returns metadata only”). The C18 200 response **requires** `extractionCode` even on replay, but A0 stores only a salted KDF digest and never the plaintext code, so a replay cannot reproduce it without violating “new code only once”. The current 201 `ShareCreated` also makes both secret fields optional, so even the first response cannot guarantee delivery.
- **期望**: First creation returns the one-time token/code; replay returns safe metadata only, with no new token/code/event. Code rotation’s first response returns the new code once; a same-action replay returns the first recorded transition metadata without reconstructing the code.
- **实际**: `ShareCreated` is reused for 200 and 201 with optional secrets; `ShareCodeRotation.extractionCode` is required for every 200. The generated client cannot distinguish a first response from a replay, and the contract either authorizes secret re-issuance or declares an unsatisfiable replay.
- **直接证据**: YAML `:2848-2853`, `:2804-2809`, `:3060-3066`, `:6442-6465`; A0 `docs/14:2313,3381-3386`; plan §4.7:286-288 and §4.9:317-321; docs/15 `:142,145,280`.
- **影响**: A capability token or extraction code can be re-emitted on replay (secret exposure), or the replay response cannot be produced at all (client failure). This is a secret-direction and idempotency-replay contract defect.
- **修复**: Make the first-creation schema require `capabilityToken` (and `extractionCode` only in code mode); use a metadata-only replay schema/response (for example `ShareState` or a dedicated `ShareCreationReplay`) that has no `capabilityToken`/`extractionCode`. For rotation, split first-response and replay semantics or make `extractionCode` optional with an explicit first/replay marker; never reconstruct the token. Update docs/15 and compile-time assertions.
- **验证/修复风险**: Medium because the same 200 status currently covers two different shapes; splitting schemas is additive but affects generated clients and docs. Runtime still cannot prove the secret was never logged; the contract can only constrain the response.
- **严重度/建议分类**: 中高；建议 `accepted`.

### F-06 `[中]` I1/I4 and task response bounds/requiredness drift from the binding plan and A0

- **入口/位置**: `IvrInboundResolveRequest.protocolVersion` (`api/openapi/onecall-v1.openapi.yaml:6680-6683`; operation description says node/protocol are server-derived at `:3091-3093`); `IvrCallEventRequest.sequenceNo`/`payload`/`legId` (`:6734-6755`); `OutboundCallTask.expiresAt` (`:6288-6295`).
- **输入场景**: The IVR resolves a call with a protocol version; it reports a call event with or without a sequence number/payload; the customer reads a task.
- **实际分支**: `protocolVersion` is optional and allows 1-64 characters; A0 `ivr.inbound_session.protocol_version` is `NOT NULL` 1-32 (`docs/14:1351`), and plan §4.1 says the independent input is 1-32. The operation description simultaneously says protocol is server-derived. I4 requires `sequenceNo` with `minimum: 0`, while A0 `ivr.call_event.sequence_no` is nullable and, when present, `>= 1` (`docs/14:1505,1520`); `payload` is optional while A0 `payload_ciphertext` is `NOT NULL` (`docs/14:1509`); `legId` allows 128 characters while A0 `call_leg.leg_id` is 1-64 (`docs/14:1476`). `OutboundCallTask.expiresAt` is nullable although A0 `outbound_call_task.expires_at` is `NOT NULL` (`docs/14:1286`).
- **期望**: Request/response bounds and requiredness should map exactly to the plan/A0 column domains; server-derived fields should not be accepted from the client.
- **实际**: The contract accepts values A0 cannot store (protocol >32, sequence 0, oversized leg id), rejects/omits values A0 requires (protocol absent, payload absent), and permits a null expiry for a non-null A0 fact.
- **直接证据**: YAML lines above; A0 §4.24, §4.27, §4.23; plan §4.1:157 and §4.10:329.
- **影响**: A schema-valid IVR request can fail at the A0 boundary; a valid A0 event without a sequence number cannot be represented; the "server-derived protocol" claim contradicts the request field.
- **修复**: Align `protocolVersion` to 1-32 and decide whether it is required input or server-derived (remove it from the body if derived); make I4 `sequenceNo` optional/nullable with minimum 1, `payload` required (or document an approved server default), `legId` 1-64; make `expiresAt` non-nullable. Update docs/15 and generated assertions.
- **验证/修复风险**: Low-medium; making fields required is a contract change, and the protocol-version source decision belongs to IVR/A0 owners.
- **严重度/建议分类**: 中；建议 `accepted`.

### F-08 `[中低]` `IvrDecision` makes A0 NOT NULL / reservation-conditional fields optional instead of required-nullable

- **验证/修复风险**: Low; generated type becomes stricter and more faithful. The action-specific reservation shape remains a runtime predicate.
- **严重度/建议分类**: 中低；建议 `accepted`.

### F-09 `[中]` I2/I3 confirmation inputs cannot express the A0 confirmation fingerprint (`decision` optional; I3 lacks prompt version and key/content)

- **入口/位置**: `IvrActivationConfirmRequest` (`api/openapi/onecall-v1.openapi.yaml:6688-6715`; `decision` optional at `:6713-6715`); `IvrDirectAuthorizationRequest` (`:6716-6729`); operation descriptions `:3170-3186,3258-3271`.
- **输入场景**: The IVR confirms activation with key 1 for a prior `GUIDE_ACTIVATION`, or confirms the direct DTMF callee for a prior `ENTER_CALLEE`.
- **实际分支**: I2 accepts a request without `decision`; the plan says the confirmation is an explicit key `1` (`plan §5.3:412,513`), and A0 T-S2-01's canonical fingerprint includes prompt/consent fields and confirmation key/content (`docs/14:3152`). I3 has only `eventId` + `callee`; A0 T-S2-04 includes prompt version and confirmation key/content in the direct fingerprint (`docs/14:3198`), and `docs/13:228` says the direct request carries callId, confirmation event ID, prompt version, key press and final callee.
- **期望**: The request must carry enough semantic confirmation fields to compute the frozen fingerprint and to reject same-event/different-confirmation content; explicit acceptance/key input must be required where the plan/A0 require it.
- **实际**: I2's acceptance is optional; I3's prompt version/key/content are absent, so a same-event different-prompt/different-key confirmation cannot be represented or distinguished. The server can only derive some of these values from the session, and the contract does not say so.
- **直接证据**: YAML lines above; A0 §9.11 `:3152`, §9.14 `:3198`; `docs/13:228-232`; plan §5.3:412, §6.2:513.
- **影响**: The IVR confirmation fingerprint and conflict semantics are under-specified; a generated client cannot prove which prompt/key was confirmed. The plan and A0 need reconciliation for I3.
- **修复**: Make I2's explicit acceptance required (or add a required key/decision field); add the required prompt version and confirmation key/content (or an approved opaque confirmation envelope) to I3 so the A0 fingerprint fields are representable. If the controller intentionally keeps the plan's minimal I3 body, record the A0-fingerprint gap as an explicit residual/owner and do not claim the full A0 fingerprint is frozen.
- **验证/修复风险**: Medium; this is a public IVR request change and may require a plan/A0 clarification. It does not affect customer/operations surfaces.
- **严重度/建议分类**: 中；建议 `needs-more-evidence` (controller/plan/A0 reconciliation), with the I2 required-decision part safely `accepted`.

### F-10 `[中低]` S3 broadens A0 anchor validation and keeps an annotation-based request-closure bypass
