## Findings

### 01-未修复-中-Pre-resolution evidence failure has no pinned event/fingerprint semantics and can poison retries

- **位置**: Plan §4.2 line 55 (“For a failure after valid fact resolution … 20 total … pre-resolution failure must not invent facts or append a success”) and §4.3 line 61; `DefaultShareMediaAuthorizationService.java:75,84,94-100,171-192`.
- **问题类型**: 状态机漏洞 / 契约缺失 / 并发恢复风险 / 不可直接实施
- **当前写法**: Post-resolution failures get a 20-key failure payload with the expanded 19-key fingerprint. The plan says pre-resolution failure must not invent facts or append a success, but does not say whether it appends a failure event, and if so what `preProviderFingerprint`/event shape it carries. It also forbids “an old-fingerprint comparison in one branch and an expanded one in another.”
- **反例/失败场景**: Evidence resolution returns `Missing`/`Unavailable`. The service throws `DEPENDENCY_UNAVAILABLE` after appending a 12-key failure event using the existing 10-key `decision.preProviderFingerprint()`. On retry after evidence recovers, the comparison now uses the expanded 19-key fingerprint; the stored 10-key failure does not match, so the retry is treated as a conflict (`SHARE_GENERATION_STALE`) instead of retrying the provider. Alternatively the implementation adds a special pre-resolution fingerprint branch, contradicting the plan’s “same expanded fingerprint” rule.
- **为什么有问题**: The event/fingerprint design is the core of the replay/concurrency contract. A factless failure event cannot carry the 19-key fingerprint; the plan does not define how such a prior event is recognized without an old-fingerprint branch. The existing `appendFailure` only covers provider failures, which are post-resolution after this change, so the new pre-resolution path has no explicit precedent.
- **直接证据**: Plan §4.2 line 55, §4.3 line 61; `DefaultShareMediaAuthorizationService.java:75` (provider-stage failure appends), `:84` (malformed provider result appends), `:171-178` (prior-event fingerprint loop), `:182-191` (12-key failure payload). New test name in §10.2 is only `evidenceResolutionFailuresNeverInvokeProvider`; no event-count/payload assertion is pinned.
- **影响**: A transient evidence outage can permanently poison the authorization request identity or force implementation inventiveness in the failure branch; the “same expanded fingerprint for success and failure retries” guarantee is not executable for the pre-resolution case.
- **建议改法和验证点**: Pin one rule, e.g. “evidence-resolution failure throws `DEPENDENCY_UNAVAILABLE` without appending an access event” (consistent with authoritative-stage failures), or define an explicit factless failure marker and comparison rule. Add the exact event-count/payload assertion to `evidenceResolutionFailuresNeverInvokeProvider` and a retry-after-recovery test.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-New 24/20-key payload conflicts with existing container redaction/payload helpers the plan does not name

- **位置**: Plan §4.2 line 55 (24-key success, 20-key failure), §4.3 line 65, §8 line 164; `PublicShareAdmissionIT.java:347,1201-1209,1219-1223`.
- **问题类型**: 测试缺口 / 契约缺失 / 不可直接实施
- **当前写法**: The plan names `PublicShareAdmissionIT.mediaFingerprint` and `assertMediaSuccessFields`, and says to update “both unit/container fixture payload/hash assertions”. It does not name `assertMediaFailureFields` (currently exactly 12 keys) or `assertNoMediaPayloadIdentityFacts` (currently forbids `BASE.evidence`).
- **反例/失败场景**: The plan’s success/failure payloads include the eight facts, including `evidenceId = decision.grant().evidenceId() = BASE.evidence` (`PublicShareAdmissionIT.java:347`). Every call to `assertNoMediaPayloadIdentityFacts` (`:931,990,1074,1079,1090`) will fail because the payload now contains `BASE.evidence`. `assertMediaFailureFields` will fail because the failure payload is 20 keys, not 12. A codegen agent may “fix” this by deleting the evidence/subject/binding assertions, weakening a redaction test.
- **为什么有问题**: The plan’s own Controller precision requires persisting the resolved evidence/object/duration/window facts in the success payload. The existing test helper treats `evidenceId` as a forbidden identity fact. The plan must state that `evidenceId`/`mediaObjectId` are now permitted nonsecret facts while `subject`/`binding` remain forbidden, and must update `assertMediaFailureFields` to 20 keys.
- **直接证据**: Plan §4.2 line 55, §4.3 line 65; `PublicShareAdmissionIT.java:347` (`evidenceId=BASE.evidence`), `:1201-1204` (13-key success helper), `:1206-1209` (12-key failure helper), `:1219-1223` (forbids `BASE.evidence`, `fixture.subject`, `fixture.binding`); plan §8 line 164 (“exact payload assertions without weakening tests”).
- **影响**: Red tests at first implementation run or a weakened redaction assertion; the plan’s “exact payload assertions” claim is not complete.
- **建议改法和验证点**: Explicitly update `assertMediaFailureFields` to 20 keys and `assertNoMediaPayloadIdentityFacts` to allow `evidenceId`/`mediaObjectId`/`sha256`/MIME/size/duration/window while continuing to forbid subject/binding; add the exact 24-key/20-key property-name pin in `realAuthoritySuccessStoresOnlyExactNonsecretMetadata`.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-Invalid-vs-Unavailable precedence for structurally malformed tokens under zero/ambiguous key providers is not pinned

- **位置**: Plan §5 line 94 (“Structural … failures map to `Invalid`; a truly absent/disabled/invalid key provider maps to `Unavailable`”), §6 line 132 (“zero/multiple providers … return `Unavailable`; structurally malformed tokens return `Invalid`”), §7 line 154 (“Preserve the unchanged … `MediaGatewayConfigurationTests`”).
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: The plan gives both mappings but not the precedence. The existing unallowlisted `MediaGatewayConfigurationTests` registers the unconditional authority with **zero** key providers and sends `POSITIVE_HTTP_BEARER = "pa20-positive-playback-token"` (`MediaGatewayTestProviders.java:21`), which is structurally malformed under `ocmp1.<kid>.<payload>.<mac>`. It expects `503` and `MediaPlaybackService.Result.Unavailable` in web/default contexts.
- **反例/失败场景**: An implementation that parses the token before resolving key providers returns `Invalid` for `pa20-positive-playback-token`, the service returns `Denied(INVALID_CREDENTIAL)`, and `MediaGatewayConfigurationTests.webGatewayPrecedesCustomerBoundaryAndDefaultBearerIsUnavailable` / `nonWebProfilesDoNotRegisterGatewayOrActivateProviders` get `403` / `Denied` instead of the frozen `503` / `Unavailable`. The unallowlisted test cannot be edited under the 18-path allowlist.
- **为什么有问题**: The precedence determines public 403-vs-503 behavior and the preserved unallowlisted context tests. The plan’s two sentences can be read in opposite orders; “zero/multiple providers … return Unavailable” (provider resolution first) is the only reading compatible with the preserved tests, but it is not stated as an ordering rule.
- **直接证据**: Plan §5 line 94, §6 line 132, §7 line 154; `MediaGatewayTestProviders.java:21`; `MediaGatewayConfigurationTests.java` `webGatewayPrecedesCustomerBoundaryAndDefaultBearerIsUnavailable` (`503`) and `nonWebProfilesDoNotRegisterGatewayOrActivateProviders` (`Unavailable`); `MediaPlaybackConfigurationTests.java:29-30` (“fixture” → `Unavailable`).
- **影响**: Implementation inventiveness; possible break of the frozen unallowlisted gateway/config tests; public status mapping differs by implementation.
- **建议改法和验证点**: Pin the order: each `verify` resolves the provider count first; zero/multiple → `Unavailable` (no token parse); with exactly one provider, parse the token; structural/malformed → `Invalid`; then `currentKeys()`; snapshot `Unavailable` → `Unavailable`; unknown kid in a valid available snapshot → `Invalid`. Add the same precedence to authority test 13 and to the `MediaGatewayConfigurationTests` preservation statement.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

These are bounded plan-text corrections, not a structural redesign; after they are pinned (and the gateway-mode/`calls` open questions are closed), the plan should be re-reviewed for a `pass`/`pass-with-risks` verdict.
