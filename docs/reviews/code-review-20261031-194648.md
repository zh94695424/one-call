### F1-unfixed-低-v009S3Admit replay 探测不检查 grant status
- **入口/函数**: `v009S3Admit` 的 replay 探测在 `replay` 非空时无条件返回 `REPLAY`
- **文件(行号)**: `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:3674-3681`
- **输入场景**: 同一 `admission_key` 的 replay 探测在 grant 已经 LOCKED 或 REVOKED 后仍直接返回 REPLAY
- **实际分支**: `replay` 非空即返回 `V009S3Admission("REPLAY",...)`，无论 grant 状态是否为 ACTIVE
- **预期行为**: 如果生产 sharing service 语义要求 LOCKED/REVOKED 状态下 same-key replay 变为 DENIED，则该 oracle 反映简化语义
- **实际行为**: LOCKED/REVOKED 状态下同 key 仍返回 REPLAY 而不是 DENIED
- **直接证据**: `v009S3AdmissionRace` 和 `v009S3LifecycleRace` 的 replay 探测在进入 limit/status 检查之前返回；`v009S3AdmissionRace` :3444-3448 对 LOCKED 状态做 replay 断言 `REPLAY` 通过
- **影响**: 这是测试 helper 行为，不是迁移 bug。`guard_share_admission` 本身只在 INSERT 前拒绝新 admission，不阻挡 SELECT replay 探测。如果 replay 是 service-level 语义，此处覆盖与实现一致但需 owner 确认。
- **建议改法和验证点**: 由 sharing service owner 澄清 LOCKED/REVOKED 状态下 same-key replay 的最终语义并在文档/测试中明确。
- **修复风险（低/中/高）**: 低
