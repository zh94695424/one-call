## Material findings

### F-01-未修复-低-comma-containing Idempotency-Key behavior is not bound to a named test

- **位置**: Plan §3.1 header rules (lines 46–49) and §8.1/§8.2 test ownership (lines 228, 240).
- **问题类型**: 测试缺口.
- **当前写法**: §3.1 states: "Preserve valid comma-containing single values as a single value, not an invented comma-splitting policy." The §8.1/§8.2 header matrix names missing, blank, 128-vs-129 code points, identical/distinct duplicates, case-insensitive header name, raw whitespace and Unicode identity, but does not name a comma-containing single value. The Surefire test says exact raw-key bytes are preserved, but no named assertion uses a key with a comma.
- **反例/失败场景**: A filter implementation uses `getHeader` plus a comma split, or flattens header values, and treats one header line `a,b` as two values (or uses only `a`). The valid key is rejected 422 or derives a different `actionRequestDigest`/event ID. The plan's listed tests still pass because none sends a comma.
- **为什么有问题**: The filter is the only layer where comma handling can happen. The plan makes an explicit identity-preservation contract, but the test map cannot distinguish the required behavior from a comma-splitting implementation. This is exactly the kind of client-visible identity divergence the slice is meant to prevent.
- **直接证据**: Plan §3.1 line 46 ("Preserve valid comma-containing single values as a single value, not an invented comma-splitting policy"); §8.1 `invalidCommandAndMissingServiceMapToProblemResponses` and §8.2 header cases (lines 240); existing `CustomerBoundaryFilter` already uses `java.util.Collections.list(...)` for Content-Type (lines 60–62), making a similar header-list treatment plausible.
- **影响**: A valid key containing a comma can be rejected or produce a different deterministic identity/replay outcome; the test suite would miss the regression. No authorization or data-loss risk, but a contract and replay-correctness gap.
- **建议改法和验证点**: Add one assertion inside an existing named web method (no new method): send a single `Idempotency-Key` value containing a comma, assert the command's `actionRequestId` is the exact comma-containing string, and assert the computed digest/event identity or a replay uses that exact value. A direct-command assertion can supplement it, but the filter-level case is the key one.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

## Open questions

1. **Controller access to the validated key.** Plan §3.1 allows "a filter-owned request attribute/accessor for controller use, or re-enumerate identically." The unchanged `CustomerApiBoundaryTests.customerDependenciesAndReadOnlySqlStayInsideBoundary` asserts `CustomerSharesController` source does **not** contain `getAttribute(`. Implementation must use a filter accessor or controller re-enumeration; direct `request.getAttribute(...)` in the controller would fail an unchanged protected scan. This is an implementation constraint, not a blocker, but it should be explicit.
2. **Malformed/inconsistent persisted transition facts.** §5 says `findTransition` must verify type/action/result/payload and fail closed, not treat malformed facts as a replay miss. §8.1's `revokeChangedReasonTerminalExpiryAndStaleWitnessConflict` includes "SQL/decode context/lock failure -> 503"; confirm an injected malformed/inconsistent event row is actually exercised there and maps to a controlled 503, not a replay miss or an unclassified 500. If the existing method has no room, add the assertion in place (no method/count change).
3. **Later-time replay and expiry boundary.** The plan's `revokeExactReplayAddsNoFactsOrRevision` needs a "later sampled time past expiry" case. V009 prevents decreasing a REVOKED grant's `expires_at`, so ordinary grant mutation cannot produce that state; confirm the IT uses the controlled repository clock seam (as §8.1 already requires for the equality boundary) rather than sleeps or a DB tamper.
4. **`SELECT ... FOR UPDATE` under column-level UPDATE.** Prior PA2 project evidence reports a disposable PostgreSQL 16 probe where table SELECT plus column-level UPDATE allowed `SELECT ... FOR UPDATE` (`FOR_UPDATE_OK`). The revoke IT must reassert this under the actual V010 `sharing_command_role` as part of `lockGrant`; if a target PostgreSQL 16 denies it, stop and escalate the frozen ACL conflict rather than widening grants.
5. **Environment.** The future focused/full runs depend on loopback and Docker/PostgreSQL 16. If the execution environment rejects loopback or Docker, report the exact failure and unexecuted proof, and do not claim a green checkpoint.
