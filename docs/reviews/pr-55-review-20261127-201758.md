- **输入场景**: 任一订单的 issuance 行集合（空、单一状态、多状态）。customer order read（PA42）与 operations order read（PA43）都需产出同一 `issuanceStatus` 枚举（OpenAPI 共享 `Order.issuanceStatus`；`OperationsOrderReadBoundaryTests` 在 `:662-688` 把 operations 记录绑定到该 OpenAPI schema）。
- **实际分支**: 两条读服务各自执行同一字面量 `Set.of("PENDING", "ISSUED", "FAILED")` 校验，并各自执行同一表达式 `values.isEmpty() ? "NONE" : values.size() == 1 ? values.iterator().next() : "MIXED"`；两个 reader 各自拼出等价 SQL `SELECT order_id, status FROM entitlement_metering.entitlement_issuance WHERE order_id IN (CAST(? AS uuid),…)`，并各自重复同一批入参约束（null/空/>100/重复/含 null）。
- **预期行为**: `issuanceStatus` 的业务裁决与取值域属于 issuance 域（owner 为 `entitlement_metering`）或共享读契约；正确 owner 应产生/承诺该语义，两个消费方复用，而非各自重新实现。
- **实际行为**: 本次 change 在既有 customer 实现之外新增第二份完全相同的状态域、聚合与 SQL。PA43 内部仅对 `PAYMENT_STATUSES`（`OperationsOrderReadPorts.java:11`）和 `validInstant`（`:12-16`）做了 single-truth + 守卫，却未同样收束 issuance 状态集；`paymentStatusSingleTruth`/`instantRangeSingleTruth` 守卫刻意不覆盖 issuance 域。
- **直接证据**: 上述四处代码段的字面量与 SQL 逐字相同；`OperationsOrderReadBoundaryTests.paymentStatusSingleTruth`（`:601-624`）与 `instantRangeSingleTruth`（`:625-657`）只钉 payment/instant 两类真源，未钉 `PENDING/ISSUED/FAILED`/`NONE/MIXED`；plan §3 把 `CustomerOrderQueryService` 明列为“precedent”，故这是被复制的既有模式，但该 PR 将它扩散成第二处事实。
- **影响**: 属语义/所有权漂移风险而非当前行为错误。若 issuance 状态枚举或聚合规则演进（新增状态、调整 MIXED 定义、改为按 installment 判定），customer 与 operations 必须同步修改且无共享契约强制一致，存在两读端对同一 OpenAPI 字段给出不同答案的静默分歧风险。
- **建议改法和验证点**: 由 `entitlement_metering` 读契约（或共享读模型）拥有 `issuanceStatus` 取值域 + 聚合，两读端消费之；本切片内 customer 源码被冻结，最小做法是把该重复登记为显式残余并由 Backend/Architecture 拥有，或至少给 operations 侧 issuance 状态集/聚合加 single-truth 守卫。验证点：把状态集或聚合在任一读端改动后，另一读端与 OpenAPI 绑定测试应能失败。
