### Adversarial opaque-forgery analytical proof (substitute for blocked `/tmp` mutations)

The following proofs are derived directly from the walker source and are sufficient to decide the controller's question; the controller's executable probes at `contract-rules.mjs:2353-2427` restate the same cases and will fail `check:s3` if any regresses.

1. **Annotation-only forgery fails.** `walkRequestSchema` exempts a node only via `node === opaqueComponentSchemas.OpaqueProviderPayload || node === opaqueComponentSchemas.IvrEventPayload` (`:1156-1158`). A different node that merely carries `x-onecall-opaque: true` hits the annotation-rejection branch (`:1159-1163`) **and**, independently, the closure branch (`:1168-1172`), because the exemption boolean is false. Two independent problems fire; the attempt cannot pass.
2. **Copied-object forgery fails.** Identity comparison is reference equality on the live component nodes loaded from the parsed document. A structurally identical object literal (same properties, same `additionalProperties: true`, same annotation) is a different reference, so `opaqueRequestException` is false and both rejections apply. There is no structural or name-based fallback path.
3. **Ordinary open object remains rejected.** An unannotated `{type: 'object'}` without `additionalProperties: false` fails the closure rule (`:1168-1172`). The dedicated probe at `:2392-2404` asserts this.
4. **Direct boolean `true` remains rejected.** `schema === true` is rejected at walker entry (`:1110-1113`) and again post-`$ref` resolution (`:1127-1130`). The dedicated probe at `:2405-2411` asserts this. The fix-4 `approvedOpaqueOpen` guard (`:1226-1229`) only skips the child-object walk when the node is identity-exempt **and** `additionalProperties === true` exactly; it does not open a path for boolean `true` or for ordinary objects.
5. **Approved nodes pass with zero problems.** The probe at `:2412-2427` runs the real `walkRequestSchema` against the live `OpaqueProviderPayload` and `IvrEventPayload` component nodes and asserts the problem list is empty. Combined with the identity check, this is the controller's fix-4 acceptance condition, satisfied in source.
6. **True-schema rejection remains live.** The synthetic inline unapproved-opaque node (`:2378-2391`), the synthetic unapproved component (`:2363-2377`), the ordinary open object (`:2392-2404`), and the direct boolean true (`:2405-2411`) are all executable negatives wired into the `sensitive-fields` rule (`:2494-2524`), which `check:s3` runs.
