### F-10-未修复-高-Membership lifecycle advisory-lock key is not discoverable under the declared cross-module SELECT grant, so the required claim/revocation serialization cannot be implemented as written

- **Entry/function**: `T-S1-06` subject claim, step 2 organization/membership/account lock acquisition; the same rule is stated globally in section 9.0.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1207` (claim must acquire the membership lifecycle advisory lock); `:1141` (namespace is `organization_access.membership:<membership_id>`); `:1437` (the claim role's `subject_number_role` cross-module membership SELECT grant is `organization_id, account_id, role, status`, with no `id`); `:1147` (cross-module readers must take the same advisory lock and re-read); `:1206` (claim inputs do not include a membership ID); `:590`, `:596`, `:1269` (membership partial unique, revocation/new-row rule, writer lock).
- **Input scenario**: An organization-scoped claim (fresh, replay or same-account duplicate) with an active membership at read time; concurrently the membership is revoked, or revoked and re-granted as a new row with a new membership ID. The claim is required to serialize with the membership writer on the membership lifecycle key.
- **Actual branch**: Step 2 orders the claim to acquire `organization_access.membership:<membership_id>`, but the claim role can only read `organization_id, account_id, role, status`; it cannot select the membership primary key. The claim inputs contain no membership ID. A re-granted membership has a new ID, so even a previously discovered ID is stale. The specification says to re-read predicates after the locks but does not define how the lock key is discovered or refreshed.
- **Expected behavior**: Grant the narrow `id` column (or define a concrete organization-access same-transaction collaborator that takes the membership lock and returns the exact status), query the current non-revoked `(organization_id, account_id)` membership, acquire that row's lifecycle advisory lock, re-read after the lock, return `CLAIM_MEMBERSHIP_INACTIVE` for an absent/revoked row, and lock/re-discover the new row for a re-grant. Assert the two serial orders and the absent/new/re-granted cases.
- **Actual behavior**: The implementer must either add an undeclared cross-module grant/query or silently skip the membership lock. With the lock skipped, a membership revocation or re-grant can commit between the claim's membership read and its completion; the current-access conjunction for an existing accepted organization-scoped claim (steps 5/6) can be satisfied from a stale membership. The fresh organization-scoped path still refuses for ownership policy, so no owner change occurs there, but the stated current-access and revocation-serialization contract is not enforceable.
- **Direct evidence**: `:1207` mandates the membership advisory lock; `:1141` keys it by `membership_id`; `:1437` omits `id`; `:1147` requires the same owner advisory key; `:1206` lists no membership ID input. The writer at `:1269` uses the membership ID. This is a concrete missing grant/lock-key path, not an assertion that SELECT alone is sufficient.
- **Impact**: least-privilege and cross-module serialization cannot both be satisfied as specified; a code generator must invent a privilege/query or drop the lock. An existing accepted organization-scoped claim can be returned after a revocation/re-grant that was not serialized.
- **Suggested fix and validation**: Add `id` to `subject_number_role`'s `organization_access.organization_membership` SELECT grant and define the bounded discovery/lock/re-read loop, including absent, revoked and re-granted rows; alternatively specify a concrete same-connection organization-access collaborator. Add privilege tests (read only the declared columns), two-order revocation tests and a re-grant/lock-key test. Do not add cross-module DML or a new SQL function.
- **Fix risk (低/中/高)**: 低. This is a narrow column-grant/lock-discovery correction.
- **Severity (低/中/高/严重)**: 高.

### F-11-未修复-中-Unknown target-subject or organization context is classified as a rejection-row outcome whose foreign keys cannot exist, producing a raw FK failure rather than a stable claim result

- **Entry/function**: `T-S1-06` fresh claim, steps 1-3 and the stable claim-code table.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1206` (target subject and optional organization inputs); `:1207` (subject row lock with no not-found branch); `:1208` (predicate failures append one `REJECTED` row when binding/reference resolve); `:1223-1238` (stable-code table: `CLAIM_SUBJECT_BINDING_MISMATCH` and `CLAIM_ORGANIZATION_INACTIVE` both map to `REJECTED`); `:750-752` (`fk_claim_subject`, `fk_claim_account`, `fk_claim_organization`).
- **Input scenario**: A fresh claim supplies a syntactically valid target `subject_id` that does not exist while the binding and verification reference resolve to another real subject, or supplies a non-null `organization_id` that does not exist.
- **Actual branch**: For a missing target subject, step 3 sees `binding.subject_id <> target subject_id` and follows the `CLAIM_SUBJECT_BINDING_MISMATCH` -> `REJECTED` row path. For a missing organization, step 3 sees a non-active/nonexistent organization and follows `CLAIM_ORGANIZATION_INACTIVE` -> `REJECTED`. In both cases the `REJECTED` row carries the unknown subject/organization ID, so `fk_claim_subject`/`fk_claim_organization` fails. The transaction aborts with a raw foreign-key error; no stable `CLAIM_*` code is returned. Step 2 locks the subject `FOR UPDATE` but defines no zero-row outcome.
- **Expected behavior**: Validate the target subject, authenticated account and any supplied organization before deciding an append-only outcome; return a stable not-found/invalid-context code with no claim row when the referenced identity does not exist, or append a row only when all of its foreign keys exist. Add explicit tests for unknown subject and organization IDs.
- **Actual behavior**: Stable rejection is replaced by a database error/aborted transaction for these boundary inputs. No accepted claim or owner change occurs, so the safety direction is correct, but the stable-outcome contract is broken.
- **Direct evidence**: `:1206` accepts the target subject and optional organization; `:1208` mandates the `REJECTED` row on the two predicate failures; the stable table at `:1224`/`:1228` maps both to `REJECTED`; the FK catalog at `:750-752` requires the referenced rows. The specification defines no `CLAIM_SUBJECT_NOT_FOUND`/`CLAIM_ORGANIZATION_NOT_FOUND`/no-row branch.
- **Impact**: API-level stable rejection fails for adversarial/invalid IDs; a raw foreign-key error can leak database detail and violates the claim outcome contract. Append-only claim history is not written for these requests.
- **Suggested fix and validation**: Define existence validation and stable not-found codes/no-row outcomes for the target subject and supplied organization (and the authenticated account, defensively), or restrict the rejection-row append to cases where every FK exists. Test unknown subject, unknown organization, and valid subject + unknown organization.
- **Fix risk (低/中/高)**: 低.
- **Severity (低/中/高/严重)**: 中.

### F-12-未修复-中-Create for a same-subject DISABLED binding has no defined stable outcome and can fall through to the raw unique or a misleading "idempotent" success

- **Entry/function**: `T-S1-07` create operation for an already-existing same-subject DISABLED binding; the destination check and unique-loser mapping.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1243` (step 2 says a same-subject historical `DISABLED` row is a re-enable candidate, not a new create); `:1244` (step 3 proceeds to insert and maps a unique loser only to "same-subject idempotent result or `BINDING_ACTIVE_CONFLICT`"); `:707-708` (unique `(subject_id, number_hmac)` and partial active-number unique); `:1242-1248` (stable binding outcomes).
- **Input scenario**: Create an `ACTIVE` binding for subject `S` on number `N` when `S` already has a `DISABLED` binding row for `N`.
- **Actual branch**: Step 2 identifies the row as a re-enable candidate but does not branch the create. Step 3 inserts the new `ACTIVE` binding; the unique `(subject_id, number_hmac)` conflicts. The loser mapping has no disabled/candidate outcome: the existing row is neither a same-subject active idempotent success nor another subject's active `BINDING_ACTIVE_CONFLICT`. The implementation can therefore emit a raw unique violation or return the DISABLED row as if the create succeeded.
- **Expected behavior**: Define a stable `BINDING_DISABLED_CONFLICT`/current-state result with no mutation, or route the create to the dedicated re-enable operation using the existing binding ID; keep the old row unchanged. Assert create-versus-disabled and create-versus-re-enable races.
- **Actual behavior**: Unstable create outcome: raw unique error or a misleading success for a binding that is still `DISABLED`; the caller cannot tell that an explicit re-enable is required.
- **Direct evidence**: `:1243` states the re-enable candidate rule but `:1244` has only the active/idempotent and `BINDING_ACTIVE_CONFLICT` mappings; `:707` makes the insert conflict unavoidable; `:1246` defines re-enable as a separate operation. The stable outcome list at `:1242-1248` has no disabled destination code.
- **Impact**: A normal create/retry case produces an unstable/raw error or a false active success; the binding row itself is not corrupted, and the old DISABLED row remains, but the S1 contract is not code-generation-ready.
- **Suggested fix and validation**: Add the stable disabled-destination outcome or an explicit create->re-enable handoff; add create-vs-disabled and create-vs-re-enable serial-order assertions and a no-raw-unique check.
- **Fix risk (低/中/高)**: 低.
- **Severity (低/中/高/严重)**: 中.

## Open Questions

- **OQ-1 — Same-account duplicate verification method.** Section 9.6 step 5 compares `verification_method` for a `request_id` replay, but step 6 compares null-safe organization and decrypted binding/number/proof without explicitly comparing the stored method, while the fix artifact claims method is part of replay identity. Because `proofRef` is server-generated and method-specific, this may be immaterial; the controller should decide whether step 6 must compare it.
- **OQ-2 — Request-ID loser mechanism.** Step 8 says to "roll back the attempt, reread by `request_id`" after a concurrent request-ID race. A PostgreSQL unique violation aborts the transaction, so the implementation must use a savepoint or a whole-transaction retry; the specification does not state which. The stable outcome is defined; the mechanism should be made explicit for code generation.
- **OQ-3 — Workspace-read lifecycle locking.** Section 9.0 broadly states that cross-module lifecycle/access readers take the owner advisory lock and re-read. `T-S1-04` performs a plain SELECT of organization/membership/account status and does not take those locks; its membership grant also lacks `id`. If the controller intends the general rule to cover workspace/login resolution, F-10 extends to `customer_iam_role`; if the read model is intentionally non-locking and rechecked per request, the specification should say so.
- **OQ-4 — S2 canonical-number lock placement.** The accepted plan's shared IVR order starts with the canonical-caller and subject lifecycle locks and does not list the canonical-number lock; the S1 global order places the canonical-number advisory before the subject lifecycle. The S2 author must acquire any canonical-number lock before the subject/session/call/activation keys, or use the subject-number collaborator without it. This is a handoff integration question, not an S1 transaction to author now.
- **OQ-5 — Organization-owned subject creation.** `subject_number_role` has INSERT on `owner_account_id` and `owner_organization_id` (`:1450`), and `guard_subject_owner` allows setting either from null (`:1474`), while the S1 text only defines personal owner setting through a claim and refuses fresh organization claims. Should the S1 create path force both owner columns null (leaving organization ownership to the deferred business-subject policy), or is an explicit operations-created organization-owned subject authorized? Owner: Product/Subject-number; the enterprise policy remains deferred.
- **OQ-6 — Claim timestamp semantics.** `verified_at` must be non-null for `ACCEPTED` and must be greater than or equal to `risk_checked_at` (`:741`, `:732`). The specification does not say whether `verified_at` is the original verification-attempt time or the claim-acceptance time; using the earlier attempt time can violate the check. Define the semantics.
- **OQ-7 — Null-owner accepted claim plus a different account's fresh claim.** The deterministic assertion says a null-owner accepted claim fails closed and is never silently repaired (`:1291`); step 5 handles a replay of that claim, but a fresh personal claim by a different account checks only the current owner columns and could set the owner when the subject owner is null, while an active accepted claim for another account exists. This requires pre-existing corrupted state; the controller should decide whether step 7 must query any accepted claim for the subject and return `CLAIM_DATA_INTEGRITY`.
- **OQ-8 — Non-material `docs/12` citation.** The normative content correctly refuses ambiguous ownership and matches the authoritative `docs/12` section 7.2 line 265, but `docs/14` line 1806 and the fix artifact line 59 still cite section 8.3. The controller stated this is a historical navigation error, not a new material behavior defect; correct it on the next documentation edit.
- **OQ-9 — Organization claim reuse role set.** Step 7 treats a membership role in the accepted four-role set as part of current approved access. The exact role-to-claim permission is not defined; Q27 covers task access, not claim reuse. Since reuse creates no new claim or owner and is restricted to the same account/explicit owner, this review does not treat it as a defect, but the controller may wish to name a narrower role.
