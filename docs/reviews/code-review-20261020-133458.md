### CR-005-未修复-[严重程度（中）]-新的交易谓词遗漏在售状态，草稿和下架版本可创建新订单

- **入口/函数**: `createOrder` → `transactionalOffer` → mutation commit.
- **文件(行号)**: `shared/onecall-business.js:364`, `shared/onecall-business.js:636`.
- **输入场景**: 已关联账户、已实名、未停用的主体，对一个其他字段合法但 `saleStatus=DRAFT` 或 `OFFSALE` 的个人版本，提交当前 `offerVersionToken`、明确购买同意及新的幂等键。
- **实际分支**: `createOrder` 在目录验证后只用 `transactionalOffer(selected, channel)` 判断可购买性；该谓词检查个人/非 QUOTE、金额、企业权益和渠道，却不检查 `saleStatus`。新 token 校验通过后直接创建订单。
- **预期行为**: 新下单只接受当前精确的 `ACTIVE` 版本。草稿、已下架或变更后的选择应原子返回 `NOT_SELLABLE` / `STALE_VERSION`，要求重新选择；历史订单仍按其已冻结的快照处理。
- **实际行为**: 两个独立只读探针均得到 `before snapshot=OK, visible=false, createOrder=OK, orders=1, after snapshot=OK`；新订单的快照分别保留 `DRAFT` 和 `OFFSALE`。因此可见性与实际下单裁决不一致，并且提交后完整校验也不阻止该订单。
- **直接证据**: 新订单入口的 364 行只调用 636–638 行的通用交易快照谓词，365 行仅比较 token，366–368 行创建订单并写事件。`visibleOffers` 在 189–196 行按 `ACTIVE` 过滤，但该结果不是下单的前置条件。批准计划 §3.3(7)（`docs/gateflow/cross-channel-alignment-plan.md:80`）明确要求 still-sellable，并要求 off-sale 拒绝；§4 的草稿/发布语义位于 101–103 行。16 项现有测试中没有草稿/下架新下单反例。
- **影响**: 后续后台套餐管理即使正确保存草稿或执行下架，客户适配器只要提交该版本及其公开 token，仍能购买未发布或已停止销售的内容；共享规则没有独立承担可售裁决。问题来自把“可作为历史个人交易快照”与“此刻允许创建新订单”复用为同一谓词。
- **建议改法和验证点**: 在 `createOrder` 的新订单路径显式要求 `selected.saleStatus === 'ACTIVE'`，或增加由共享模块所有的当前可售谓词。不要直接把 ACTIVE 限制加到历史快照通用谓词，否则可能误伤旧订单导入及套餐下架后的支付/权益发放。对 DRAFT/OFFSALE + 当前 token、旧 token、ACTIVE 正常下单分别测试；拒绝时比较完整状态不变，并回归历史订单在当前目录下架/换版后仍可合法履约。
- **修复风险（低/中/高）**: 低；若误改历史快照通用谓词则升为中。
- **严重程度（低/中/高/严重）**: 中。

### CR-006-未修复-[严重程度（中）]-快照接受无业务结构和引用约束的幂等结果，重放可成功返回幽灵订单

- **入口/函数**: `loadReviewSnapshot` → `validateState` → `validProcessedEvents`；导入后 `createOrder` → `replayEvent`。
- **文件(行号)**: `shared/onecall-business.js:508`, `shared/onecall-business.js:516`, `shared/onecall-business.js:604`.
- **输入场景**: 从合法已创建订单的快照开始，保留 ORDER 域的事件键、eventId 和原输入指纹，只把该事件的 `result` 替换为 `{id:'ORDER-GHOST', subjectId:'SUBJ-GHOST', accountId:'ACCOUNT-GHOST', payment:'PAID', entitlement:'ISSUED'}`；其余真实业务集合不变。该结果既缺少 Order 必填字段，也引用不存在的对象。
- **实际分支**: `validProcessedEvents` 只证明结果是安全 JSON 数据，不检查动作域对应的结果结构、输入/结果身份或其业务引用。导入被接受。原下单输入再次到达时，`replayEvent` 校验原指纹后直接把该结果包装为成功 `DUPLICATE`；`mutate` 对 DUPLICATE 提前返回，不进行完整校验。
- **预期行为**: 新增的不可变首次结果也是业务快照的一部分，必须遵守动作域结构及稳定身份/引用契约。缺字段、跨主体或不存在对象的结果应导致整个导入原子拒绝。合法历史结果中的可变状态（例如早先 UNKNOWN、较早的 usedSeconds）可以与当前状态不同，不能因此破坏正确重放。
- **实际行为**: 只读 Node 探针结果为 `first=OK, load=OK, replay=DUPLICATE`，回包是 `ORDER-GHOST/SUBJ-GHOST/PAID/ISSUED`；真正存在的订单仍为 `ORDER-001001/UNPAID`。这不是实际付费或越权的证明，而是本地评审快照中可确定复现的成功返回值与业务状态不一致。
- **直接证据**: 516 行唯一的结果约束为 `safeData(record.result)`；`safeData`（678–689 行）只验证 plain JSON 和安全键，连 null/boolean 也可作为 result。428–434 行因此接受并替换状态；610–611 行同样只检查 safeData 后返回该数据，577 行吸收 DUPLICATE。计划 §3.2（55 行）把事件映射定义为带 result identity 的业务状态；§7（147–149 行）要求完整结构/引用验证，未授予事件结果豁免。当前动态快照测试（`shared/qa/business.test.js:270`）只改顶层禁用字段，没有检查新事件记录内部的结果身份。
- **影响**: 后续跨端 fixture handoff 可能把不属于任何真实业务对象的成功结果带到另一端；公开转换不会自行纠正或拒绝，适配器可能据此展示不存在的订单、错误支付/权益或错误主体。若下游自行补验或回查修正，业务结构和引用语义会再次漂移出共享模块所有者。
- **建议改法和验证点**: 为各域定义明确的首次结果结构与稳定身份/引用校验，并校验输入指纹中的对象身份与结果一致。只对 immutable identity、冻结快照和引用做一致性约束，保留 mutable historical facts 的合法差异。导入及必要的重放防线复用同一公共契约所有者内的校验。增加 null/缺字段结果、幽灵/跨主体对象、错误动作域结果的原子导入拒绝测试；同时保留支付 UNKNOWN→PAID 后重放 UNKNOWN、试用后续扣量后重放原 usedSeconds 的通过测试。调整任何变更业务 ID 的测试 fixture 时，也应同步维护事件引用，而非为测试放松 validator。
- **修复风险（低/中/高）**: 中；需区分首次历史值与仍必须成立的稳定身份，避免把历史结果强行等同于当前可变对象。
- **严重程度（低/中/高/严重）**: 中。

### CR-007-未修复-[严重程度（中）]-试用事件重放优先于冻结会话校验，篡改主体上下文仍返回成功

- **入口/函数**: `consumeTrial` → `replayEvent` → `mutate` DUPLICATE early return.
- **文件(行号)**: `shared/onecall-business.js:321`, `shared/onecall-business.js:323`, `shared/onecall-business.js:577`.
- **输入场景**: 已确认的 IVR 会话成功消费一次后，把会话主体改向另一主体、置空冻结关联，或移除/替换/复制原主体；再以原 `sessionId/eventId/seconds` 重放。同样的篡改状态在计划和现有测试中属于必须拒绝的状态输入。
- **实际分支**: 321–322 行在检查唯一会话、CONFIRMED 状态、冻结 ID 相等、唯一主体及证据引用（323–330 行）之前读取并返回事件快照。随后 DUPLICATE 分支绕过 mutation 的完整状态校验。
- **预期行为**: 批准计划 §3.3(6) 明确规定，在查找 `processedEvents` 前先证明会话/主体关联；任何 unresolved/missing/duplicated/altered/cross-subject 关联均应 `INVALID_TRANSITION` 且无 mutation。通过结构检查的正常重放仍应返回首次结果，且不因后来额度耗尽而再次扣量或拒绝。
- **实际行为**: 五种只读探针（crossSubject、unresolved、removed、replaced、duplicated）全部出现 `snapshot=INVALID_TRANSITION, original-key replay=DUPLICATE, fresh-key call=INVALID_TRANSITION`，且完整状态不变。没有重复扣量，但相同无效上下文会因是否存在缓存事件而得到相反的成功/失败裁决。
- **直接证据**: 事件读取与返回位于 321–322 行，结构校验位于其后 323–330 行，577 行不再兜底检查 DUPLICATE。`docs/gateflow/cross-channel-alignment-plan.md:79` 明确给出前置顺序和拒绝结果；S1 completion（165 行）把 subject/IVR/evidence reference mismatch 列为阻塞条件。现有 tamper 回归（`shared/qa/business.test.js:241`）只使用新事件键 `EVT-TAMPER-*`，未复用此前已成功的 `EVT-REFERENCE`，所以未执行这一分支。
- **影响**: 无效或跨主体会话状态可被成功回包掩盖，调用方不能依赖 `consumeTrial` 成功证明其证据上下文符合共享契约。该问题不产生新的证据副作用，但仍违反已接受 PR-001 修复的明确不变量与错误语义。
- **建议改法和验证点**: 把唯一会话、冻结关联、唯一主体和已有证据引用校验移动到事件重放之前；保留 quota/expiry/exhaustion 等会随时间变化的消耗限制在合法重放之后。扩展现有五种 tamper 测试，分别用已处理原键和新键验证 `INVALID_TRANSITION` 及完整状态不变；正常原键在后续额度耗尽/过期后仍返回首次结果且不重复扣量。
- **修复风险（低/中/高）**: 低至中；必须只前移结构不变量，不能让实时额度状态破坏正确幂等重放。
- **严重程度（低/中/高/严重）**: 中。
