## Direct verification by review axis

### 1. Correctness and exact `/me` contract

- The route is exactly `GET /api/v1/customer/me`; the controller mapping declares `produces="application/json"` (`CustomerMeController.java:31-35`). OpenAPI freezes the same operation `getCustomerMe` with the opaque `customerSession` bearer and the `CustomerContext` 200 schema (`api/openapi/onecall-v1.openapi.yaml:285-333`).
- Success JSON is exactly `account`, `workspaces`, `channel`; account is `accountId,displayName,status=ACTIVE`; PERSONAL emits only `workspaceType,status`; ORGANIZATION emits `workspaceType,organizationId,organizationDisplayName,role,status=ACTIVE`. The targeted `@JsonInclude(NON_NULL)` is only on `WorkspaceSummary` and the nested Problem record (`CustomerContext.java:15-22`; `CustomerProblemWriter.java:13-14`), matching plan §5 and the OpenAPI schemas (`:4375-4424`).
- Problem JSON is exactly `type="about:blank"`, fixed `title`, integer `status`, enum `code`, nonempty server UUID `traceId`; no `detail`, `instance`, `errors`, Boot error map, HTML, URI/query/header echo or stack text (`CustomerProblemWriter.java:30-58`). OpenAPI requires exactly those five fields (`:4242-4270`).
- The status/title mapping is `401/UNAUTHENTICATED`, `403/FORBIDDEN`, `404/NOT_FOUND`, `422/VALIDATION_FAILED`, `429/RATE_LIMITED`, `503/SERVICE_UNAVAILABLE`, default `500/INTERNAL`; `WWW-Authenticate: Bearer` is emitted only for 401. 403/422/429 are writer-only vocabulary with no HTTP producer, as the accepted plan requires.
- Authentication precedes negotiation. A missing/malformed/duplicate bearer is 401 without verifier or DB access; an authenticated incompatible/malformed/`q=0` Accept normalizes to 500 INTERNAL, which is the accepted PA11 decision (plan §7 "Application versus connector boundary") rather than a wire 406/HTML response. The controller-recorded web tests exercise this matrix.
- Container ERROR dispatch maps 401/404/503 to the corresponding frozen Problem and normalizes every other status (including 400/403/405/406/415/422/429/500) to 500 INTERNAL (`CustomerApiErrorController.java:23-36`). Direct `/error` requests are denied with 404 by the boundary filter. Both mappings are exercised by the committed tests.
- No response body is written before success; success bytes are buffered and flushed only after the chain returns (`CustomerBoundaryFilter.java:71-80,83-124`). On failure the writer resets an uncommitted response and writes one sanitized Problem; a committed response is not appended to, as documented.

### 2. Security and ACL isolation

- The bearer parser accepts exactly one nonempty `Authorization` value matching case-insensitive `Bearer` + one or more ASCII spaces + RFC 6750 b64token syntax; tabs, embedded commas/spaces, duplicate headers, Basic credentials, query/cookie-only bearers and trailing text are rejected before the verifier (`CustomerBearerAuthenticator.java:12-25,43-49`). A JWT-shaped string remains opaque bytes.
- Exactly one verifier is required: zero or multiple candidates produce 503; provider acquisition/creation failure and verifier infrastructure failures produce 503; verifier `UNAUTHENTICATED` produces 401; wrong audience produces 401; null/malformed results produce 503. The fixed audience `onecall:customer-session:v1` is always supplied (`CustomerBearerAuthenticator.java:26-49`).
- The session result carries only account UUID, `MINIAPP|WEB` channel and audience; no token, provider subject, HMAC, identity document or organization secret. The principal exposes only `accountId.toString()`; the opaque bearer has a redacted `toString()` and no JSON getter binding (`VerifiedCustomerSession.java:6`; `CustomerRequestPrincipal.java:6-9`; `OpaqueCustomerBearer.java:3-12`).
- The request wrapper overrides `getUserPrincipal()`/`getRemoteUser()` with the trusted principal; incoming/container principals and forwarded identity headers are never reused. No `ThreadLocal`, HTTP session, cookie or cross-request authentication cache exists in production (`CustomerBoundaryFilter.java:65-70`).
- Client query/body/cookie/selector headers cannot select account, organization, role or channel: the controller accepts only servlet-derived `Principal`; the filter does not bind parameters or a body; the repository binds exactly the authenticated caller UUID plus fixed `ACTIVE` literals. Both the no-DB HTTP tests and the PostgreSQL IT exercise this.
- The service enters one `REQUIRES_NEW`, `READ_COMMITTED`, read-only transaction, issues fixed `SET LOCAL ROLE customer_iam_role`, asserts `select current_user`, and only then calls the repository (`CustomerContextService.java:34-44`; `CustomerPersistenceConfiguration.java:47-56`).
- The query selects only V002-granted columns: account `id,display_name,status`; organization `id,display_name,status`; membership `organization_id,account_id,role,status`. It is a single prepared SELECT with four binds (`"ACTIVE","ACTIVE",accountId,"ACTIVE"`), no `SELECT *`, no joins to identity/profile/auth tables, no locks, no DML, no audit/outbox/idempotency write and no function call (`JooqCustomerContextRepository.java:18-48`; V002 grants at `:241-245,303-313`).
- Isolation is server-fact based: the SQL ANDs `a.id = :authenticatedAccountId` and `a.status='ACTIVE'`, and membership/organization joins require both statuses `ACTIVE`. An empty result is 401, not an empty successful account. Only the caller's own active memberships are projected; other-account memberships are excluded.
- The service validates shape and provenance: ACTIVE account, non-null display name, caller account equality, caller channel equality, nonempty workspaces, PERSONAL exactly first with no organization fields, subsequent ORGANIZATION entries with non-null id/name/role and unique organization ids. DISABLED account is 401 before the remaining shape checks; any invalid ACTIVE projection is 500, never a partial or broadened success (`CustomerContextService.java:55-82`).
- The no-write guarantee is proven by the read-only transaction plus the test-owned deliberate write probe returning SQLSTATE `25006`, with before/after snapshots of account/identity/profile/organization/membership/idempotency/outbox/audit rows unchanged (`CustomerMeIT.java:181-212`; `CustomerMeFixture.java:208-221,276-280`). Note that `customer_iam_role` already has V002 own-schema INSERT/UPDATE grants for future writes; the `/me` path never uses them and its read-only transaction is the enforcement. This is a defense-in-depth boundary, not an ACL claim that the role is globally read-only.
