## Findings

### 1-未修复-[高]-证据创建身份由可变事实派生，改变同意版本或链路时无法冲突并产生重复证据

- **入口/函数**: `evidence.create_and_solidify` and the `EVIDENCE_CREATED` source identity used by `evidence.evidence_record` and `evidence.evidence_event`.
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3367`, `:3371`, `:4071`, `:2173`, `:2139`; accepted plan `docs/gateflow/a0-production-data-model-schema-spec-plan.md:633`.
- **输入场景**: The first evidence creation for recording `R` uses capture facts with `consentVersion = C1` (and optional `sessionId`/`reservationId`). A retry or duplicate completion for the same recording presents an otherwise identical capture with `consentVersion = C2` (or a changed optional link), which is exactly the "conflicting fact" the specification says must conflict.
- **实际分支**: Step 1 reads `evidence_record` by `(source_event_domain='EVIDENCE', source_event_id)`. Step 5 computes `source_event_id` as `evidence-created:` + SHA-256 of `{recordingId, callId, subjectId, sessionId, reservationId, consentVersion}`. A changed `consentVersion` changes the derived identity, so the read finds no prior row; the only uniqueness is `uq_evidence_source_event (source_event_domain, source_event_id)` and there is no unique constraint on `source_ref_id`/recording. The service proceeds to insert a second `evidence_record`, a second `EVIDENCE_CREATED` event and a second `ORIGINAL` artifact.
- **预期行为**: The accepted plan defines `source_event_id = eventId` for the validated source event and requires exactly one matching creation event. Under a stable source identity, the same recording with changed semantic facts must return `EVIDENCE_SOURCE_CONFLICT` and create no second record, creation event or artifact; the specification's own step 1 says exactly this.
- **实际行为**: A changed semantic fact becomes a *new* identity, not a conflict. The `EVIDENCE_SOURCE_CONFLICT` branch is unreachable for the fields included in the derived identity, and there is no database uniqueness preventing two evidence records for one recording. The plan's stable `eventId` contract is replaced by a hash of the facts that are supposed to conflict.
- **直接证据**: `:3367` states the read by `(source_event_domain, source_event_id)` and the conflict claim; `:3371` says "compute the record's `source_event_id` as the §10.24 `evidence-created:` identity"; `:4071` gives the exact input set including `consentVersion`, `sessionId` and `reservationId`; `:2173` shows the only unique key is `(source_event_domain, source_event_id)`; `:2139` defines `source_ref_id` as the recording reference with no unique constraint; accepted plan line 633 says `source_event_id = eventId`.
- **影响**: Duplicate immutable evidence facts, duplicate creation events/artifacts and divergent share-content projections for one recording. The "exactly one `EVIDENCE_CREATED` event owns each evidence record" shape still holds per row, but the same recording can acquire multiple evidence records, so share replay, audit and historical-evidence integrity can diverge. This is a current-scope idempotency and plan-alignment defect, not a deferred provider or retention input.
- **建议改法和验证点**: Restore the accepted stable `eventId` as `source_event_id`, or make a stable source key (for example `source_type + source_ref_id`) unique and compare all semantic facts under it. Do not include the facts that must conflict in the lookup identity; compare them and return `EVIDENCE_SOURCE_CONFLICT`. Add an executable assertion: same recording, changed `consentVersion`/link -> one record/creation event/artifact and a conflict; exact replay -> first result; no second Outbox fact. Any new unique constraint or column requires controller approval because the frozen catalog currently has no such key.
- **修复风险（低/中/高）**: 中; the fix changes the creation identity and may require a unique index or service lookup, not just prose.
- **严重程度（低/中/高/严重）**: 高.
- **建议裁决**: accepted.

### 2-未修复-[中]-证据 artifact 数组顺序自相矛盾，content/creation 摘要不可确定

- **入口/函数**: `evidence.read_shareable_projection` and `sharing.create_share_grant` when constructing `content_snapshot.content`, `scopeDigest`, `content_sha256` and `creationFingerprint`.
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:253` (same rule at `:4050`).
- **输入场景**: An evidence record has both an `ORIGINAL` and a `DERIVED` artifact, or multiple artifacts whose order matters. One implementation sorts `artifactRole` lexicographically ascending (`DERIVED` before `ORIGINAL`); another follows the parenthetical "ORIGINAL before DERIVED".
- **实际分支**: `:253` says both "sorted by `artifactRole` ascending" and "(`ORIGINAL` before `DERIVED`)"; `:4050` repeats "ordered by `artifactRole` ... ascending" without an explicit role rank. The artifact-role registry at `:246` is exactly `ORIGINAL` and `DERIVED`.
- **预期行为**: One deterministic order. A fixed role rank (for example `ORIGINAL = 0`, `DERIVED = 1`) applied before the `mediaSha256`/`mediaSizeBytes`/`mediaMimeType` tie-breakers, or an explicit statement that role order is `ORIGINAL` then `DERIVED` and is not lexical.
- **实际行为**: The two readings produce different `artifacts[]` arrays for the same evidence. Because `scopeDigest` and `content_sha256` are hashes of canonical JSON containing that array, and `creationFingerprint` includes the frozen content/scope, the same evidence can yield different digests across conforming implementations; a same-`creationRequestId` replay can then return a false `SHARE_CREATION_CONFLICT` or fail to reproduce the frozen content. The "byte-for-byte reproducible" claim at `:253` is not met.
- **直接证据**: `:253` explicitly combines "ascending" with "ORIGINAL before DERIVED"; UTF-16/lexical ascending places `DERIVED` before `ORIGINAL`, so the parenthetical and the adverb conflict. `:4050` omits the parenthetical and repeats the ascending wording. `:246` confirms the only role values.
- **影响**: Non-deterministic sharing content/scope/creation hashes and unreliable OQ-R1/F-08 replay/conflict behavior; a share grant can be duplicated, falsely conflicted or frozen with a content digest that another implementation cannot reproduce.
- **建议改法和验证点**: Define the role rank once and use "ascending by role rank" or "role order ORIGINAL, DERIVED (not lexical)" in `:253`, `:4050`, `§4.44` and `T-S3-15`; add a two-artifact replay assertion that computes the same `content_sha256`/`creationFingerprint` from both orderings. No table, column or function change.
- **修复风险（低/中/高）**: 低 (text and test clarification only).
- **严重程度（低/中/高/严重）**: 中.
- **建议裁决**: accepted.
