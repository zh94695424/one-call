## 3. Findings

### F-01-未修复-[高]-playback-credential-has-no-client-transport-path

- 状态候选: `accepted-candidate`
- 位置: plan §4.9 Playback (L419–425), §5.4 C10 (L550), §6.5 (L700), §9.2 `R-A3-A1-UPLOAD-CREDENTIAL-SHAPE` adjacent residual (L964–965); OpenAPI `MediaAuthorization.credential` (L7224–7229); `docs/15` L154, L284
- 问题类型: missing fail-closed transport contract / unclassified residual risk
- 当前写法: C10 is "opaque media-gateway token `v1.<keyId>.<base64url(HMAC-SHA-256(...))`" (§4.9 L423) that "media gateway 校验签名/audience/expiry/generation/object scope 后用自己的 CAM 身份读取 COS". A1 `MediaAuthorization.credential` is a readOnly field on an operations/public-share response, "validated by the media gateway" (`docs/15` L154, OpenAPI L7221). A1 exposes **no playback endpoint** (`docs/15` L284). The plan §1.4 (L73) forbids new endpoints; §4.9 forbids returning COS URLs; §9.2 records `R-A3-A1-SUPPORT-VIEW` (no operations playback) but never records a client→gateway transport residual.
- 反例失败场景: An S3 implementation Agent is asked to make C10 usable. A1 provides no host, path, header or query parameter through which a client (share recipient browser/app) presents C10 to the media gateway. COS cannot natively validate a custom HMAC bearer token with audience/generation/object scope — COS presigned URLs carry only COS-enforced conditions and would leak object key/bucket (forbidden by §4.9 L423, L433 and A1 schema). The implementer must therefore invent either (a) a new gateway endpoint (violating §1.4 no-new-endpoint and the binding goal's "不新增 endpoint") or (b) a URL-shaped credential that embeds COS signing (violating §4.9 L423 "不向客户端返回 COS URL" and the plan's own `R-A3-A1-UPLOAD-CREDENTIAL-SHAPE` stop rule). Either path silently expands the A1 wire or leaves playback non-functional.
- 为什么有问题: The plan freezes the token *format* and the gateway's *verification logic* but not the *transport surface* on which the token is presented. A1 froze the credential as a response field on authorization responses (P2→P3 handoff), not as a request credential on any client-callable operation. Without a typed deferred input (e.g., "gateway ingest host/path/header") or an explicit statement that the transport is runtime-deployment configuration outside the A1 wire (and therefore a classified residual with owner), the S3 slice cannot be code-generated without guessing. The plan's own no-hidden-risk principle (§9 residuals list) fails to classify this gap.
- 直接证据: OpenAPI `MediaAuthorization` schema description (L7221): "validated by the media gateway"; `docs/15` L154 same; `docs/15` L284 "no operations playback endpoint"; plan §1.4 L73 "不做…运营播放 endpoint"; plan §4.9 L423-425 (gateway validates, no COS URL returned, no transport specified); plan §5.4 C10 audience `onecall:media-playback:v1` with no transport row; plan §6.5 L700 "签发 C10 → media gateway 校验 → 读取 COS" (skips client→gateway hop).
- 影响: S3 implementation blocker. Either a non-goal violation (new endpoint) or an unimplementable playback path. Unclassified residual risk violates the binding goal's fail-closed/every-credential-has-owner requirement.
- 建议改法和验证点: (1) Add to §4.9/§5.4 an explicit statement that the client→media-gateway transport is a deployment-time configuration owned by Infrastructure/Security, recorded as a typed deferred input (new CV or a sub-row of Q11) or as a named residual `R-A3-A1-MEDIA-GATEWAY-TRANSPORT` with owner Infrastructure/Security and destination "media gateway deployment / storage capacity", stating that A3 freezes only the token format + verification contract + redaction, not the wire path; OR (2) if the controller determines the transport must be in the A1 wire, classify it as an unavoidable A1 gap and stop. Validation: the plan text must contain the residual/deferred row; S3 fixtures must assert only token-format/scope/deny semantics, never a transport URL; the S3 completion report must list the residual.
- 修复风险: Low — pure documentation/residual classification, no A0/A1/A2 change.
- 严重程度: 高（S3 code-generation blocker；unclassified residual）

### F-02-未修复-[中]-action-derived-reason-and-ui-confirmation-require-controller-adjudication

- 状态候选: `needs-evidence`
- 位置: plan §4.10 (L435–443), §5.9 (L620–639), §6.6 (L703–711), §9.2 `R-A3-A1-EMPLOYEE-REASON-PROJECTION` (L963); `docs/14` §9.3 (L3051), §10.6 (L3504); `docs/12` §11.1 (L389 操作理由); OpenAPI ADMIN publish/draft request schemas (all `additionalProperties:false`, no reasonCode)
- 问题类型: semantic contract degradation not adjudicated; non-goal-mandated control frozen without authority
- 当前写法: §5.9 freezes ACTION_DERIVED reason source for 8 ADMIN mutations (L626–633) via the residual `R-A3-A1-EMPLOYEE-REASON-PROJECTION`. §4.10 L441 mandates "运营 UI 必须以当前 operation/status/revision 展示确认" and §6.6 L707 step 3 repeats it. §1.4 L73 lists "UI/prototype 修改" as a non-goal. §25 (L25) states the three projection boundaries are non-blocking and that "若 plan review/controller 判定任一为不可避免的 accepted-contract 矛盾，实施必须停止并报告".

An action-derived constant (e.g., `CATALOG_VERSION_PUBLISH`) satisfies the A0 syntactic CHECK but carries zero operator motive — a compliance auditor reading the audit fact cannot distinguish "published because launch approved" from "published by mistake". The plan freezes ACTION_DERIVED into §5.9 without the controller explicitly accepting this semantic degradation; a later controller may reject it after S3 has already frozen the registry, forcing a gate regression. But it freezes both ACTION_DERIVED *and* UI 二次确认 as if both were fully authorized, while §25 itself says the controller must adjudicate projection boundaries before implementation. Freezing a semantically degraded reason source and a non-goal-mandated control into the S3 registry without explicit controller sign-off is premature freeze of an unresolved adjudication. The validator will happily assert `reasonSource=ACTION_DERIVED` and `二次确认=要求` without proving either is acceptable.

Validation: the plan must contain the two residuals with owners; §5.9 二次确认 column must not be a validator-assertable field, or must be labeled "runtime-not-static"; S3 fixtures must assert only role/state/reasonSource/audit-failure-rollback, never UI.
- 修复风险: Low-Medium — documentation + registry column change; no A0/A1 change; must not accidentally drop the A0 reason CHECK.
- 严重程度: 中（needs controller adjudication before S3 freeze）

### F-03-未修复-[中]-upload-credential-dual-shape-incoherent

- 状态候选: `accepted-candidate`
- 位置: plan §4.9 Upload (L411–417), §5.4 C09 (L549), §5.10 CV-4 (L666), §9.2 `R-A3-A1-UPLOAD-CREDENTIAL-SHAPE` (L964)
- 问题类型: incoherent dual-shape credential / missing enforcement branch
- 当前写法: §4.9 L414 binds C09 to `(callId,recordingId,objectIdentityDigest,purpose=UPLOAD)`; §4.9 L415 says "形态：opaque 短时授权字符串（可能为 COS presigned URL 或等价凭证）"; §5.4 C09 audience `onecall:evidence-upload:v1`; §6.5 L699 "签发 C09 → IVR 受控直传". CV-4 defers COS presign capability.
- 反例失败场景: A COS presigned PUT URL carries COS-enforced conditions (method, key, content-length-range, expiry) but cannot carry an application-level audience claim (`onecall:evidence-upload:v1`), cannot enforce `purpose=UPLOAD` as an A3 semantic (COS only sees the HTTP method + object key), and cannot enforce `objectIdentityDigest` as a COS condition (the digest is an application-layer identity, not a COS policy attribute). Conversely, a custom HMAC token (`v1.<keyId>.<base64url(...)>`) can carry audience/scope but cannot be validated by COS natively — it must be validated by an IVR/API-side issuer or a gateway that then uses COS signing. The plan does not branch the two shapes into distinct enforcement matrices: which checks are COS-enforceable (PUT-only, size, key, expiry) versus which are application-enforceable at complete time (purpose, callId/recordingId binding, objectIdentityDigest re-hash). An S3 implementer must invent the split, risking either an unenforceable audience claim on a presigned URL or a custom token that IVR cannot present to COS without a signing oracle.
- 为什么有问题: "可能为…或等价凭证" defers the shape decision to implementation, but the same section freezes scope bindings that are only enforceable under one of the two shapes. The audience claim and the COS-presigned shape are mutually incompatible enforcement models; freezing both simultaneously is incoherent without an explicit branch and a rule for which layer enforces which property. The residual `R-A3-A1-UPLOAD-CREDENTIAL-SHAPE` classifies the leak risk but not the enforcement incoherence.
- 直接证据: Plan §4.9 L414-416 (scope + dual shape + IVR direct-upload path); plan §5.4 C09 (L549) audience + storage "COS/SM signing K19"; plan §5.10 CV-4 (L666) defers presign; residual L964 (leak classification only).
- 影响: S3 implementation ambiguity; possible unenforceable scope claims or a need for a signing gateway not specified in the plan (same class as F-01 but for upload).
- 建议改法和验证点: (1) Branch §4.9 Upload into two named shapes: `U1a-COS-presigned` (COS-enforceable: PUT-only, object key, size-range, expiry at `uploadExpiresAt`; application-enforced at complete: purpose/callId/recordingId/objectIdentityDigest re-hash — audience claim NOT carried on the URL, enforced server-side at issuance) and `U1b-custom-HMAC` (application-enforced at a signing/verification point, then translated to COS signing — requires a defined verifier, same transport question as F-01); (2) freeze which shape is the primary and which is the deferred alternative under CV-4, or freeze "presigned + complete-time server checks" as the primary with audience as an issuance-side registry key, not a URL claim; (3) update C09/§5.7 U1 accordingly. Validation: the plan must contain the branch and the complete-time vs COS-enforceable split; `sec-s3-01` fixture must assert the complete-time digest re-hash path regardless of shape.
- 修复风险: Low — design clarification, no A0/A1 change (A1 field remains opaque 1-2048 string).
- 严重程度: 中（S3 design incoherence）

### F-04-未修复-[中]-a2-outbox-401-403-handling-unspecified

- 状态候选: `accepted-candidate`
- 位置: plan §4.7 (L379–397), §4.12 exactly-once rules 3/6 (L480, L483), §9.2 `R-A3-A2-AUTH-OUTBOX` (L965); `docs/16` outbox classification (L326)
- 问题类型: missing fail-closed behavior in an A2-adjacent state machine
- 当前写法: §4.7 L394 maps auth failures to `401 UNAUTHENTICATED` / `403 FORBIDDEN` / `503 SERVICE_UNAVAILABLE`. §4.7 L396 and §4.12 rule 3 (L480) state: IVR outbox retransmission keeps `eventId`/payload, updates only timestamp/nonce; must not change eventId, redial or re-resolve due to 401/403. §4.12 rule 6 (L483): after credential/nonce fix, A2 first-result still returned by original identity. The residual `R-A3-A2-AUTH-OUTBOX` (L965) records: "A2 outbox 未命名 401/403；认证失败在 A2 前；同 identity 重试".
- 反例失败场景: A2 L326 classifies outbox permanent codes (EVENT_ID_CONFLICT/SESSION_IDENTITY_MISMATCH/CALL_UNKNOWN/IVR_ARGUMENT_INVALID/VALIDATION_FAILED) and retryable codes (RATE_LIMITED/SERVICE_UNAVAILABLE/INTERNAL/5xx/network). `401 UNAUTHENTICATED` and `403 FORBIDDEN` are in **neither** set. When the IVR outbox delivers a `call-event.request` and the backend returns 401 (bad signature, expired nonce, rotated key) or 403 (service identity not allowed), the outbox state machine has no frozen transition: is 401 retryable (wait for credential fix, same eventId) or permanent (mark PERMANENT_FAILURE)? The plan says "同 identity 重试" after fix, implying retryable, but also forbids modifying A2 classification. An S3/S2 implementer must invent the outbox state for 401: if they treat it as retryable forever with no backoff cap, the outbox never converges; if they treat it as permanent, they contradict §4.12 rule 6's "修复后重试" implication. The A2 outbox machine (ACKED / PENDING / PERMANENT_FAILURE) has no frozen rule for "401 received".
- 为什么有问题: The residual records the *gap* but the plan does not freeze the *resolution*. "认证失败在 A2 前" is true for synchronous request handling (§4.7 zero-side-effect L395), but the IVR outbox is a **client-side retry machine** that observes the HTTP status after the request has left the IVR — the "before A2" framing does not tell the outbox what to do. Distinguishing transport replay (new nonce, same eventId) from domain replay (A2 idempotency) is correct (§4.7 L376), but the outbox classification for an auth-rejection status is a third category the plan leaves open. This is exactly the class of "missing fail-closed behavior" the binding goal forbids.
- 直接证据: `docs/16` L326 outbox permanent/retryable sets (no 401/403); plan §4.7 L394-396; plan §4.12 L480, L483; residual L965.
- 影响: S2/S3 implementation ambiguity in the outbox state machine; possible non-convergent outbox or incorrect PERMANENT_FAILURE on a recoverable credential error; risk of either stuck retries or silent message loss.
- 建议改法和验证点: (1) Freeze in §4.7/§4.12: `401` on an outbox delivery is **retryable with the same eventId** (credential/key/nonce may be fixable), subject to the existing outbox retry policy under Q8/Q13 (no new numeric cap); `403` (service identity not allowed) is **permanent** for that delivery (identity misconfiguration is not fixed by retransmission) — OR explicitly classify both under a named deferred input with owner Telephony/IVR + Backend, if the controller prefers not to freeze without runtime evidence; (2) state that this classification is an IVR-local outbox policy, not a change to A2's server-side classification (preserving the "A3 不修改 A2 digest/classification" rule); (3) add an S2 fixture (`sec-s2-*`) asserting: 401 → outbox stays PENDING/retryable with same eventId, no redial, no second reservation; 403 → PERMANENT_FAILURE with same eventId, no redial. Validation: fixture assertions + no change to A2 event registry digest.
- 修复风险: Low — IVR-local policy only; must not touch A2 server-side classification or digest.
- 严重程度: 中（S2 outbox state-machine gap）

### F-05-未修复-[中]-deferred-registry-contradicts-no-new-row-claim

- 状态候选: `accepted-candidate`
- 位置: plan §5.10 (L641–667), §9.3 (L984), §0 L24; `docs/14` §14 (L4774–4805, 28 Q-rows)
- 问题类型: internal contradiction / citation overclaim
- 当前写法: §5.10 (L641) titled "Deferred inputs 与 capability verification（23）" and lists Q1/Q3/Q6/Q7/Q8/Q10/Q11/Q12/Q13/Q14/Q17/Q18/Q19/Q22/Q23/Q25/Q27/Q28 (18 rows from A0) **plus** CV-1..CV-5 (5 new rows, L663–667, IDs `CV-*`, not `Q-*`, not present in A0 §14). §9.3 (L984) states: "见 §5.10 的 23 行：…+ CV-1..CV-5。所有 owner/destination 保持 `docs/14` §14 原值；**A3 不新增 open-input row**". §0 L24: "Q1/Q3/…/Q28 与 5 个云能力验证输入保持 typed deferred，owner/destination 不变；Q2 的逻辑算法/密钥层级由 A3 关闭".
- 反例失败场景: A validator or S1 implementation Agent reads §9.3 "A3 不新增 open-input row" and compares the 23-row deferred map against A0 §14's 28 rows. It finds 5 rows (CV-1..CV-5) that do not exist in A0 §14 and are therefore "new". Either the validator is written to ignore CV-* (overfitting to the implementation's own naming) or it fails the plan's own drift check. Alternatively, the validator is written to accept them because §5.10 lists them — but then §9.3's "不新增" claim is simply false, and a later controller reading only §9.3 would believe no new rows exist. The "23" count itself is a hybrid (18 A0 Q-subset + 5 A3 CV) presented under a heading that implies it is all A0 deferred inputs.
- 为什么有问题: The plan simultaneously (a) adds 5 new typed rows not in A0 §14, (b) claims it added none, and (c) freezes a count (23) that is the sum of a subset and the additions. This is a direct internal contradiction and a citation overclaim against A0 §14. The binding goal requires deferred values to have owner/destination without invention — CV-1..CV-5 do have owners/destinations (Infrastructure/Security) and are legitimate capability-verification inputs, but they are A3-originated, not A0-originated. The fix is to state this explicitly, not to hide it behind "不新增".
