## 4. Material findings

### 1-未修复-中-Post-commit guarded cleanup failure is described as a rollback, but it occurs after commit

- **位置**: Plan §2.1 ("existing guarded template performs its existing clean-connection check after completion"), §3.1 step 8 (cleanup failure -> 503), §5 step 10 ("cleanup failure ... rolls back everything"), §8.2 failure/restoration tests, §10.2 lost-201 residual.
- **问题类型**: 并发恢复风险 / 回滚语义不一致 / 残差分类错误.
- **当前写法**: The plan reuses `operationsSubjectReadCatalogSaleTransactionTemplate` and states that any cleanup failure escapes the transaction and rolls back everything, while also stating that the template's clean-connection check runs after completion.
- **反例/失败场景**: The order, consent, idempotency completion and both Outbox/audit facts commit in `super.execute(action)`. If the guarded connection close/`assertClean` then detects a baseline mismatch or close failure, `assertClean()` throws `SERVICE_UNAVAILABLE` after the commit. The caller receives 503 even though the complete effect bundle is durable. This is not a partial write, but it contradicts the plan's "cleanup failure rolls back everything" and is not covered by the zero-delta fault loops that stop "before restore" or by the in-transaction rollback cases.
- **为什么有问题**: The plan's own code fact (`OperationsSubjectReadPersistenceConfiguration.java:99-111,128-140`: `finally { guarded.assertClean(); }` after `super.execute`) makes a post-commit 503 possible, while §5 step 10 promises rollback of that failure class. An implementation agent following the text could write an unreachable rollback assumption, omit the post-commit test, or mishandle the client's retry. The accepted lost-201 limitation is the right family of behavior, but the plan currently classifies the cleanup failure as rollback rather than as an ambiguous committed outcome.
- **直接证据**: `OperationsSubjectReadPersistenceConfiguration.java:99-111` and `:128-140` wrap `super.execute` in `try/finally` and call `assertClean()` afterwards; `:186-220` sets `cleanupFailure` and throws `Failure(SERVICE_UNAVAILABLE)` from `assertClean()`. The plan §2.1 acknowledges the check is after completion; §5 step 10 still says cleanup failure rolls back everything.
- **影响**: A 503 with a committed order/consent/idempotency/Outbox/audit bundle is unaccounted for; retry/recovery semantics and the completion report may be wrong. This is not data corruption and the same-key retry can recover, so it is not a blocker, but it is a real rollback/error-classification gap.
- **建议改法和验证点**: Reclassify post-commit guarded cleanup/connection-close failure as an accepted lost-201/ambiguous-committed outcome, not a rollback. Add a subcase inside an existing test identity (for example `roleHandoffsRestoreOnSuccessReplayAndTypedDenial` or `injectedFailureAtEveryWriteStageLeavesZeroPartialRows`) that simulates a close/`assertClean` failure after commit, asserts exactly one committed bundle, no partial rows, and an explicit same-key retry returning 200 when authority/catalog eligibility still passes (or the documented 403/422/409 otherwise). Update the §10.2 lost-201 row to include this failure class. Do not weaken the pre-commit restoration/42501/55P03 rollback tests.
- **修复风险（低/中/高）**: Low.
- **严重程度（低/中/高/严重）**: 中.
