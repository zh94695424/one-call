### 1-未修复-高-ModuleBoundaryTests 精确七边多重集断言未被 plan 指定更新，按 plan 字面实施必然失败

- **位置**:
  - Plan §3（activation_consent 允许依赖追加 `operations_iam::subject-lifecycle-command`、`operations_iam::employee-administrator-lock`）
  - Plan §4 / §8（`ModuleBoundaryTests` 变更描述：“Dependency-map value only; method names/count unchanged.”）
  - Code: `backend/src/test/java/com/onecall/archtests/architecture/ModuleBoundaryTests.java` `discoveredProductionEdgesStayInsideTheConfiguredMap`（约 98–115 行）
- **问题类型**: 不可直接实施 / 测试缺口 / 契约缺失（架构边界测试与 plan 切片不同步）
- **当前写法**:
  - Plan 要求仅扩展 `EXPECTED_ALLOWED` 中 `activation_consent` 的 allowedDependencies 值，并写明方法名与断言数量不变。
  - 同一测试方法内另有生产边发现结果的**精确多重集**断言：

```java
assertThat(discovered.values().stream().flatMap(Set::stream))
    .as("exactly seven production edges exist: customer query owners, sharing -> evidence and activation_consent -> entitlement_metering")
    .containsExactlyInAnyOrder(
        "sharing", "evidence", "subject_number",
        "activation_consent", "evidence",
        "catalog_order", "entitlement_metering");
```

- **反例/失败场景**:
  1. Implementation agent 按 plan 只改 `EXPECTED_ALLOWED` 的 `activation_consent` 集合（加入两个 `operations_iam::…` named edges），不改七边多重集。
  2. `discoveredProductionEdgesStayInsideTheConfiguredMap` 运行时：`activation_consent` 的 discovered direct dependencies 新增 `operations_iam`。
  3. `flatMap` 多重集从 7 个元素变为 8 个（多出 `"operations_iam"`），`containsExactlyInAnyOrder` 失败。
  4. 同 PR 的模块边界套件变红；若 agent “修测试以变绿”却未理解边语义，可能错误地放宽为 `containsAll` 或删断言，破坏 plan 自己依赖的“恰好七条生产边”冻结事实。
- **为什么有问题**:
  - Goal Confirmation 要求 plan 达到 code-generation-ready；冻结架构测试的**精确期望值**与新切片边不一致，且 plan 的变更说明主动把实现者引离该断言（“method names/count unchanged” 只覆盖方法签名与用例数，未覆盖该方法内期望多重集）。
  - 该断言的 message 文本写死 “exactly seven production edges”，与新增边后的事实矛盾——即使 agent 改了期望数组，不同步改 message 也会留下错误文档性断言。
  - 与 Modulith `allowedDependencies` 追加边后的真实 discovered graph 必然冲突：不是 speculative risk，是确定性测试失败。
- **直接证据**:
  - `ModuleBoundaryTests.java` 112–114 行精确 `containsExactlyInAnyOrder` 七元素多重集及 “exactly seven” message。
  - Plan 对 `ModuleBoundaryTests` 的修改范围表述为 Dependency-map value only / method names/count unchanged，未要求更新该多重集或 message。
  - Plan §3 明确 `activation_consent` 将新增指向 `operations_iam` 的两条 named 依赖 → Modulith discovered edge 必含 `operations_iam`。
- **影响**:
  - 实施 Agent 按字面 plan 交付 → CI/本地架构测试失败，slice 无法验收。
  - 次生风险：agent 为消红弱化精确边断言，削弱 plan 依赖的模块边界回归网。
  - Review 不可验收：计划声称的测试面与真实失败面不一致。
- **建议改法和验证点**:
  1. Plan §4（或 §8 测试清单）显式写明：在 `discoveredProductionEdgesStayInsideTheConfiguredMap` 中将期望多重集更新为**八条**边：原七条 + `"operations_iam"`，并更新 `.as(...)` message（例如 “exactly eight production edges … activation_consent -> operations_iam”）。
  2. 保持 `containsExactlyInAnyOrder` 精确性，禁止改为 `contains` / `containsAll`。
  3. 验证点（实现后）：`ModuleBoundaryTests.discoveredProductionEdgesStayInsideTheConfiguredMap` 通过；`modules.verify()` 通过；`EXPECTED_ALLOWED` 中 `activation_consent` 含两条 `operations_iam::…` 且无 `OPEN_TOKEN`。
  4. 对照检查 `assertsExactAllowedDependencyMapFromPlan62` 与 `verifiesNoCyclesOrBoundaryViolations` 中与 `customer_iam` `hasSize(12)` 相关的断言——**不受**本边影响，勿误改。
- **修复风险（低）**: 仅改已 allowlist 的测试文件内一处期望多重集 + message；不触碰生产模块声明逻辑。
- **严重程度（高）**: 冻结架构测试确定性失败；plan 变更说明误导实现；直接阻断 code-generation-ready 交接。
