## 4. Findings

### 1-未修复-中-exact-delta 守卫未指定语句边界,分号切片可让新守卫静默失守
- **位置**: §10 "Symmetric operations-filter source-delta acceptance …" 第 1-3 条 (plan 行 274-276);§10 customer-regression 条 (行 270);§9 modified production 第 1 条 (行 210)
- **问题类型**: 测试缺口 / 契约缺失(守卫算法未钉死)
- **当前写法**: 要求 "Extract the complete `boolean read = ...;` expression from OperationsBoundaryFilter and assert equality to the exact expected GET-only expression (normalizing whitespace only)",并声明该等式必须能发现 "added tenth route / widened method / regrouping that bypasses GET"。plan 只规定了比较对象与期望内容,没有规定**如何确定被抽取文本的边界**;customer 侧同样只写 "exact two-alternative source delta"。
- **反例/失败场景**: 授权字面量自身含分号:`OperationsBoundaryFilter.java:43` 即 `path.matches("/api/v1/operations/catalog/products/[^/;%]+")`。若实施 Agent 按 "`...;"` 的字面提示以 `indexOf(';')` 类"到第一个分号为止"的抽取,结果在第 43 行**中途截断**,只剩 4 个 equals 分支,全部 `path.matches` 分支以及追加在联合末尾的两条 order 分支(以及任何第十条分支)都落在抽取范围之外。此时期望串若由同一截断函数生成,断言**全绿却什么都没钉**——正是 B F1 要消除的"加宽无人捕获"失效模式;若期望串按 §10 完整枚举,则测试首跑变红,而最省力的变绿路径正是缩短期望串(同样静默丢掉尾部)。同一缺陷适用于 customer 过滤器 GET 联合(`CustomerBoundaryFilter.java:71` 首个分号就在 `[^/;%]` 内)与 §10 行 276 的 ERROR 分支断言(其 detail 模板同样含 `[^/;%]+`)。
- **为什么有问题**: 该守卫是这条权限边界上唯一机器可检查的约束(既有 `contains`/`doesNotContain` 守卫 `OperationsLifecycleBoundaryTests.java:53`、`OperationsActivationReadBoundaryTests.java:104`、`OperationsIvrSessionReadBoundaryTests.java:60` 只能发现删除,不能发现新增);仓库里的源码抽取先例全部是 marker→marker(`CustomerCatalogOfferBoundaryTests.java:73`、`EvidenceRoleIvrAssociationAclBoundaryTests.java:121`、`OperationsLifecycleBoundaryTests.java:90`),没有任何"到分号为止"的先例可援引,而 plan 不给边界规则,等于把最容易踩空的实现方式留作默认。
- **直接证据**: 在本 worktree 上实跑两种抽取:从 `boolean read =` 到首个 `;` 的结果止于第 43 行、可见 4 个 route 字面量、不含任何 orders 分支;完整语句(到 `boolean catalog`)含全部 7 个分支。customer GET 块首个 `;` 出现在第 71 行的 `[^/;%]` 内部。plan 文本见 §10 行 274-276、行 270。
- **影响**: 实施 Agent 跑偏 / 生成错误代码(守卫退化为自指字符串)/ 权限边界加宽不被捕获 / review 无法以测试证明"只加了两条" / 后续返工
- **建议改法和验证点**: 在 §10 该段补三条可机械检查的要求:(a) 钉死抽取边界——被抽取文本必须是从 `boolean read =` 起、以括号配平(或到下一语句标记 `boolean catalog =`)结束的**完整语句**,并明确禁止以 `indexOf(';')` 结束抽取,理由写明 `[^/;%]` 字符类内含分号;(b) 追加截断哨兵——除等式外,必须断言抽取结果中确实包含授权的 `"/api/v1/operations/orders".equals(path)` 与 `path.matches("/api/v1/operations/orders/[^/;%]+")` 两条完整字面量,且抽取结果内 `/api/v1/operations` 分支计数恰为 9(作为等式之外的第二重检查,不替代等式);(c) 追加整文件普查——该文件中全部 `/api/v1/operations/...` route 字面量集合必须等于 {9 条 `read` 分支} ∪ {既有 catalog/subject/draft 命令准入} ∪ {探针决定后的 ERROR 联合},使"在 `read` 之外另加一条"也无法隐藏。对 customer 过滤器的两分支 delta 守卫与 §10 行 276 的 ERROR 分支断言施加同样的边界+哨兵规则。验证点:实施后故意在 `read` 末尾追加第十条 `path.matches("/api/v1/operations/orders/[^/;%]+/extra")` 或放宽 `"GET"`,守卫必须变红;把抽取改成 `indexOf(';')` 风格时截断哨兵必须立刻变红。
