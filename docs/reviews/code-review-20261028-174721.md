### F-PA5-S1-01-未修复-[中]-冻结 `ck_ivr_decision_source`/`ck_ivr_decision_shape` 因 NULL 三值逻辑放过禁止的 decision 形状

- **入口/函数**: `V005__ivr_task_session_call.sql` 中 `ivr.ivr_decision` 的 INSERT 约束求值（`ck_ivr_decision_source`、`ck_ivr_decision_shape`，并由 `ck_ivr_decision_direct_reason` 配合放行）。
- **文件(行号)**: `backend/src/main/resources/db/migration/V005__ivr_task_session_call.sql:339-342`（source）、`:351-353`（shape）；冻结文本 `docs/14-production-data-model-and-flyway-schema-spec.md:1570`、`:1575`；冲突的语义契约 `docs/14:3746`（`reservationId` NOT NULL iff `action = DIAL_TASK_CALLEE` 或 `purpose = DIRECT_AUTHORIZATION and action is NULL`）。
- **输入场景**: 以 owner/migration 身份直接 INSERT `ivr.ivr_decision`：
  (a) `purpose='DIRECT_AUTHORIZATION'`, `action=NULL`, `reason_code='DIRECT_AUTHORIZED'`, `source_event_domain='IVR_DIRECT_AUTH'`, `source_event_id='evt-d'`, `reservation_id=NULL`；
  (b) `purpose='ACTIVATION_NEXT_ACTION'`, `source_event_domain='IVR_CONFIRM'`, `source_event_id=NULL`, `action='GUIDE_PURCHASE'`, `reservation_id=NULL`；
  (c) 同 (b) 但 `source_event_domain=NULL`、`source_event_id=NULL`。
- **实际分支**: (a) `ck_ivr_decision_shape` 第二支中 `action IN (...)` 在 `action IS NULL` 时求值为 `NULL`，`NULL AND (reservation_id IS NULL)` = `NULL`，整个 OR 为 `NULL`；PostgreSQL CHECK 仅在 `FALSE` 时拒绝，`NULL` 通过。`ck_ivr_decision_direct_reason` 的 `(action IS NULL) = (reason_code='DIRECT_AUTHORIZED')` 为真，故三条 check 全部放行。(b)/(c) `length(source_event_id) BETWEEN 1 AND 128`、`source_event_domain = 'IVR_CONFIRM'` 在 NULL 时均为 `NULL`，OR 链结果为 `NULL`，`ck_ivr_decision_source` 通过；`ck_ivr_decision_shape` 对该 action 与 reservation 组合为真。
- **预期行为**: 按 `docs/14` §4.28，`ACTIVATION_NEXT_ACTION` 必须 `source_event_domain='IVR_CONFIRM'` 且 `source_event_id` 为非空 1–128；`DIRECT_AUTHORIZATION` 必须 `source_event_domain='IVR_DIRECT_AUTH'` 且 `source_event_id` 非空。按 §10.14，成功 direct authorization（`action IS NULL`）的 `reservationId` 必须非空。上述行应以 `23514` 拒绝。
- **实际行为**: 独立 disposable PostgreSQL 16.15 容器中三条 INSERT 均返回 `INSERT 0 1`（事务内 `ROLLBACK` 复验；非事务应用容器中 (a) 实际持久化 `count=1`）。即不存在 reservation 的 “成功 DIRECT_AUTHORIZATION” 与无 source event identity 的 ACTIVATION/DIRECT decision 均可落库。
- **直接证据**: V005 冻结谓词逐字对应 `docs/14:1570`/`1575`；probe：`purpose='DIRECT_AUTHORIZATION', action=NULL, reservation_id=NULL` → `INSERT 0 1`；`purpose='ACTIVATION_NEXT_ACTION', source_event_domain='IVR_CONFIRM', source_event_id=NULL` → `INSERT 0 1`；`source_event_domain=NULL, source_event_id=NULL` → `INSERT 0 1`。该结果是 SQL 三值逻辑直接可推导的，不依赖测试或猜测。
- **影响**: 数据库 backstop 未按文档 fail-closed：可持久化“无 reservation 的 direct 成功 decision”与“无 source event identity 的事件型 decision”。后续 replay 会按 `(call_id,purpose)` 冻结并返回该行；若消费方/结算按 `action IS NULL + DIRECT_AUTHORIZED` 视为已授权的 direct success，将出现无 committed reservation 的授权语义。`uq_ivr_decision_source` 是 `WHERE source_event_id IS NOT NULL` 的部分唯一索引，NULL identity 同时绕过该 replay 身份 backstop。S1 无 service，故为潜在而非当前线上可利用；但这是 architecture-sensitive 的冻结 decision 契约缺口。
- **建议改法和验证点**: 这是 frozen predicate 自身的缺陷，S1 实现与 accepted plan 逐字一致，**不应在 S1 无授权改动**。若 schema authority 决定修正，建议 bounded errata：(1) `ck_ivr_decision_source` 的非 INBOUND 分支显式要求 `source_event_domain IS NOT NULL AND source_event_id IS NOT NULL`（或先 `source_event_id IS NOT NULL` 再长度/btrim）；(2) `ck_ivr_decision_shape` 的 DIRECT 分支对四个非 dial action 加 `action IS NOT NULL AND`，或增加 `AND NOT (purpose='DIRECT_AUTHORIZATION' AND action IS NULL AND reservation_id IS NULL)`；同步修 `docs/14`/plan/`V005_CHECK_DEF_MAP`，计数（73）不变。验证点：上述三条 INSERT 均 `23514` + 精确 check 名，合法 direct-success（有 reservation）与合法无 reservation refusal 仍成功。

- **严重程度（低/中/高/严重）**: 中

### F-PA5-S1-02-未修复-[低]-冻结 `ck_call_event_payload_redacted` 因 NULL/jsonb 三值逻辑接受 `receipt.payloadSha256 = null` 与 `source.payload = null`

- **入口/函数**: `ivr.call_event` INSERT 的 `ck_call_event_payload_redacted` 约束求值。
- **文件(行号)**: `backend/src/main/resources/db/migration/V005__ivr_task_session_call.sql:286-298`；冻结文本 `docs/14-production-data-model-and-flyway-schema-spec.md:1526`；语义要求 `docs/14:1513-1514`、`:1541`；测试期望 `PostgresContainerIT` V005_CHECK_DEF_MAP（`ck_call_event_payload_redacted` 项）。
- **输入场景**: INSERT `ivr.call_event`，`payload_redacted = {"source":{"eventType":"SESSION_START","legId":"leg-1","sequenceNo":9,"payload":null},"receipt":{"payloadSha256":null,"eventFingerprint":"<64hex>"}}`，或 `receipt.payloadSha256` 为 JSON null 而 `payload_sha256` 为合法 64-hex。
- **实际分支**: `payload_redacted ? 'payload'` / `? 'payloadSha256'` 只判断 key 存在；key 存在但值为 JSON null 时为真。`receipt->>'payloadSha256'` 对 JSON null 返回 SQL NULL，`NULL = payload_sha256` 为 `NULL`，整条 AND 链为 `NULL` → CHECK 通过。对 `source.payload` 没有 `jsonb_typeof(...)= 'object'` 判断，JSON null 通过。
- **预期行为**: `docs/14` §4.27：`payload_redacted` 恰好 `source`（含对象型 `payload`）+ `receipt`；`payload_sha256` 是 `source.payload` canonical JSON 的 SHA-256，`receipt.payloadSha256` 必须等于 `payload_sha256`。上述形状应以 `23514` 拒绝。
- **实际行为**: 两类 malformed 行均 `INSERT 0 1`（事务内 `ROLLBACK` 复验）。
- **直接证据**: V005 谓词逐字对应 `docs/14:1526`（仅授权 JSONB 括号分组）；probe 输出 `INSERT 0 1`。NULL 传播路径见上。
- **影响**: 低。`receipt` 由 service 生成、永不接受客户端输入（§4.27），正常路径不会写入坏值；但数据库 shape backstop 比文档弱，owner/异常写入可持久化非对象 payload 或 null receipt hash，破坏 §4.27 的“first stored payload 吸收 + hash 等式”防御层。
- **建议改法和验证点**: 与 F-PA5-S1-01 同属 frozen predicate errata 类，需 schema authority 授权；建议加 `jsonb_typeof(payload_redacted->'source'->'payload') = 'object'` 与 `jsonb_typeof(payload_redacted->'receipt'->'payloadSha256') = 'string'`（或 `IS NOT NULL`）。验证：上述 malformed 形状 `23514`，现有 S1 smoke 与 S2 合法 event 形状仍通过。
- **修复风险（低/中/高）**: 低（同上，需授权与 deparse 期望同步；计数/列不变）。
- **严重程度（低/中/高/严重）**: 低
