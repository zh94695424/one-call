## 3. Findings

### B1-未修复-高-步骤9的 replay/conflict 指纹在 provider I/O 之前不可计算，credential 过期时间推导未冻结，核心 replay 承诺可能被错误实现为 409

- **位置**: Plan §2.2 step 9–10；§3.1 成功事件 payload（含 `credentialExpiresAt`、`credentialDigest`）与 "`payload_sha256` … `insertAccessEvent` result is authoritative"；§3.2 provider 请求 "…and the credential expiry"；§7.1 test `sameAuthorizationRequestAndPurposeReplaysCredentialAndEvent`。
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施（code-generation-ready 缺口）。
- **当前写法**: Step 9 要求在任何 provider I/O **之前** "check the durable event"，并把 "same event identity with a different event fingerprint" 判为 409 冲突；但同一 §3.1 把事件 payload 定义为包含 `credentialExpiresAt` 与 `credentialDigest`——这两个字段只有 provider 返回后才存在；§3.2 又把 "the credential expiry" 列为 provider **请求**输入。
- **反例/失败场景**:
  1. 实现者在 step 9 试图重算完整 `payload_sha256` → 无法计算（缺 credential 字段）→ 只能跳过或发明字段子集，计划未规定子集；
  2. 实现者把 `credentialExpiresAt` 推导为 `now() + TTL`（"short-lived credential" 的自然读法）→ 同一 `authorizationRequestId`+purpose 的重试得到不同 `credentialExpiresAt` → `insertAccessEvent` 判 `CONFLICT` → 目标要求的 replay 返回 **409 而不是第一个 credential**，且单元/集成测试在毫秒级时间窗内**测不出**该漂移；
  3. provider 请求携带调用方新鲜计算的 expiry → "same canonical request identity" 输入却不同 → provider 无法收敛到同一 credential，与 §3.2 "return the same opaque credential and expiry for the same … fingerprint" 自相矛盾。
- **为什么有问题**: Goal Confirmation 的成功信号之一是 "deterministic replay"（control:21–22）。replay/conflict 是本 slice 的核心语义；计划在此处留下一个三向歧义（pre-provider 比对字段集、`credentialExpiresAt` 的确定性推导、provider 请求指纹是否含 post-issuance 字段），实现 Agent 必须自行重新设计，违反 "code-generation-ready" 交付标准，并且现有测试设计无法捕获最危险的错误分支。
- **直接证据**: plan:54（step 9 fingerprint conflict before provider I/O）、plan:105–110（payload 含 `credentialExpiresAt`/`credentialDigest`；`payload_sha256` 定义）、plan:116（provider 请求含 "the credential expiry"）、`JooqShareAdmissionRepository.java:115`（insert 时全量 hash 比对）、OpenAPI `:3883`（replay 是本 operation 的 200 契约语义）。
- **影响**: 实现跑偏 → 合法重试被误判 409（goal 失败）；或 step 9 语义被静默忽略、冲突延迟到 provider 之后（多一次无谓 credential 签发、并发下行为漂移）；review 无法验收 "same request and purpose replays" 断言是否真正成立。
- **建议改法和验证点**: 明文冻结三件事：(a) step-9 的 pre-provider 比对字段集 = payload 中除 `credentialDigest`/`credentialExpiresAt` 外的全部字段（或明确 step 9 只做 identity 存在性判定、fingerprint 冲突以 `insertAccessEvent` 为唯一权威——二选一，禁止含糊）；(b) `credentialExpiresAt` 必须由 witness/frozen expiry bounds 确定性推导（或直接取自已存事件的 replay 路径），禁止新鲜 wall-clock 参与 replay 路径的 payload 构成；(c) provider 请求指纹不得包含调用方无法复现的 post-issuance 字段。验证点：新增/强化 `sameAuthorizationRequestAndPurposeReplaysCredentialAndEvent` 必须在（测试可控的）时间推进或 expiry-bound 变化下仍返回同一 credential 与 `REUSED_IDENTICAL`，`changedSemanticReplayConflictsWithoutSecondEventOrCredential` 必须在 pre-provider 或 insert 时按冻结的字段集触发且无 provider 二次签发。
- **修复风险（低）**: 仅改 plan 文本与测试措辞，不改 scope。
- **严重程度（高）**。

### B2-未修复-高-provider seam 的 "extend the request/result seam" 未钉死为 additive 扩展，按字面实现将迫使 allowlist 外的 `DefaultShareAdmissionService` 修改
