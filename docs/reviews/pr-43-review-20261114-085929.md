## Open Questions

- `OperationsBoundaryFilter` maps an unacceptable `Accept` (for example `text/html`) to `INTERNAL`/500, and the frozen tests assert that. `docs/15` does not freeze a 406 code and the OpenAPI default response is `Internal`, so this is contract-consistent, but it is semantically a client negotiation error rather than a server failure. Confirm the frozen default is intentional (no change required for this review).
- `OperationsSubjectsController` parses `subjectId` with `UUID.fromString` and then requires `subject.toString().equals(subjectId)`, so an uppercase-but-valid UUID is rejected with `422 VALIDATION_FAILED`, while the existing customer activation path accepts `UUID.fromString` without canonical lowercase enforcement. The OpenAPI path parameter only says `format: uuid`. Confirm the stricter canonical lowercase rule is intended.
- `OperationsLifecycleSemantics.validateTransition` enforces the narrow matrix for OPERATIONS rows but, for non-OPERATIONS rows, only rejects `SUSPENDED` sources; a persisted non-OPERATIONS `ACTIVE → SUSPENDED` row would pass the witness/replay validator even though `docs/14` §4.38 says the broad DB check cannot distinguish and the owner service enforces the narrow matrix. No current writer can produce such a row (customer path never writes `ACTIVE → SUSPENDED`; IVR is not implemented), so this is defense-in-depth only. Confirm whether hardening is desired.
