## 2. Findings

### F1-未修复-[高]- `ORGANIZATION_MEMBER` caller handoff after non-locking mode discovery is undefined, and the media-authorization service contract is unshaped

- **位置**: Plan §3 step 3 (`:69`), §5 items 2 and 5 (`:178`, `:181`), §6.1 caller tests (`:228`); current `PublicSharesController.java:43-50,52-92`; `SharingQueryBoundaryTests.java:80`.
- **问题类型**: 契约缺失 / 不可直接实施 / 架构边界 / 状态机漏洞 / open question 未收敛.
- **当前写法**: The service performs a non-locking token-digest read to discover grant mode; for `ORGANIZATION_MEMBER` it "requires a trusted caller and current active account/workspace context" (`:69`). The controller "add[s] ... trusted member caller handling" (`:178`). `ShareMediaAuthorizationService` is specified only as a "new named public-admission interface returning the existing nested response record/outcomes" (`:181`); no method signature, parameter types, outcome union, or caller-resolution mechanism is pinned.
- **反例/失败场景**:
  1. The PA18 request body has only `authorizationRequestId` and `purpose` (`api/openapi/onecall-v1.openapi.yaml:7205-7217`); the verification mode lives in the grant. The controller therefore cannot know before the service call whether to resolve an `ORGANIZATION_MEMBER` caller.
  2. If the controller eagerly resolves `getCustomerMe` whenever any `Principal` is present (the PA17 pattern at `PublicSharesController.java:59-79`), an invalid token with an expired/ambiguous customer session can yield 401 or 503 from the context call before the service's `SHARE_TOKEN_INVALID` 404. This contradicts plan step 2 ("missing/invalid token ... 404") and step 6 (`:72`).
  3. If the controller passes a raw `Principal`/session verifier into `sharing`, it violates the Modulith boundary and `SharingQueryBoundaryTests.java:80` (`assertThat(source).doesNotContain("com.onecall.core.customer_iam")` for admission files).
  4. If the controller resolves the member caller only for a `CustomerRequestPrincipal`, non-member shares carrying an invalid/expired optional bearer may still be rejected at the filter/controller before token processing, violating the "no customer session required" branch (`:69`).
  5. The only viable design is a lazy resolver (e.g., `Supplier<Optional<TrustedShareAdmissionCaller>>`) invoked by the service after mode discovery, but the plan never states it, never defines when the supplier runs, and never defines what the supplier does when the session is missing versus invalid versus unavailable.
- **为什么有问题**: This is the exact fix-1 intake question at Control `:35`; the plan's controller/service plumbing is the trust boundary for member re-authentication and the 401/404 precedence. Leaving it to the implementation agent forces it to redesign the authentication order and makes the planned `organizationMemberMediaAuthorizationRequiresTrustedCurrentSession` test incapable of pinning the required behavior.
- **直接证据**: plan `:69`, `:72`, `:178`, `:181`, `:228`; `openapi/onecall-v1.openapi.yaml:7205-7217`; `PublicSharesController.java:43-50,52-92`; `SharingQueryBoundaryTests.java:80`; `DefaultShareAdmissionService.java:53-65` (PA17 preliminary-read precedent).
- **影响**: Implementation may produce 401/503 where 404 is frozen; may reject valid no-session non-member links; may cross the module boundary; review cannot prove re-authentication precedes the authoritative read.
- **建议改法和验证点**: Pin the exact service method (e.g., `MediaAuthorizationOutcome authorize(ShareAdmissionCapabilityToken token, UUID admissionId, MediaAuthorizationRequest request, Supplier<Optional<TrustedShareAdmissionCaller>> caller, Optional<Principal> principal)` or an equivalent resolver contract), the exact outcome union, and the controller's lazy-resolution rule: absent bearer → empty caller and no context call; present caller → resolve only after the service reports `ORGANIZATION_MEMBER`; context `UNAUTHENTICATED` → 401; context unavailable → 503; invalid token → 404 regardless. Add assertions for invalid token + invalid session → 404, non-member + absent bearer → no context call, member + absent caller → 401.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F2-未修复-[高]- Concurrent first requests still diverge on `credentialExpiresAt`; there is no mechanism to converge on one effective credential and one event

- **位置**: Plan §3 step 10 (`:76`), §4.3 (`:113-122`), §4.4 credential request (`:137-143`), §8 residual row (`:294`).
- **问题类型**: 并发恢复风险 / 状态机漏洞 / 不可直接实施 / open question 未收敛.
- **当前写法**: After the authoritative lock transaction, each request samples `databaseNow` and computes `credentialExpiresAt = min(grantExpiresAt, admissionExpiresAt, sessionExpiresAt, databaseNow + approvedQ22MediaCredentialTtl)` (`:116-118`). The provider request carries `credentialExpiresAt` (`:141`). The post-provider durable payload contains `credentialExpiresAt` and is hashed by `postProviderFingerprint`; `insertAccessEvent` compares the full `payload_sha256` (`JooqShareAdmissionRepository.java:110-117`). The plan's residual says both requests "can both reach provider I/O" and relies on "DB append is sole conflict authority; deterministic provider request/event identity" (`:294`).
- **反例/失败场景**:
  1. T1 and T2 serialize on the grant lock. Both perform the pre-provider lookup before either provider returns; both see no event. `databaseNow1 != databaseNow2` (millisecond `clock_timestamp()`), so the two provider requests carry different `credentialExpiresAt` values.
  2. If the provider honors `credentialExpiresAt`, it issues two different credentials; when the second provider call succeeds, its first event insert conflicts on the same `event_id` with a different `payload_sha256` → `EventWriteStatus.CONFLICT`; the plan never says whether this maps to `SHARE_GENERATION_STALE` 409, `DEPENDENCY_UNAVAILABLE` 503, or a reuse of the first event. The second effective credential already exists even if it is not returned.
  3. If the provider keys on `eventId` and ignores `credentialExpiresAt`, the two provider outputs may still differ from the first durable `credentialExpiresAt`; the plan says "provider output must match the stored event facts" but gives no convergence rule, and the second insert still conflicts.
  4. A two-connection test using a deterministic fake that keys only on `eventId` can pass while the real provider issues two credentials; the plan's named two-connection test does not require independently sampled DB time or assert the second request's expiry equals the first durable expiry.
- **为什么有问题**: The Goal Confirmation success signal requires deterministic replay; the fix-1 intake (`control:35`) explicitly requires "concurrent first requests whose independently sampled `credentialExpiresAt` values must still converge on one provider credential/event without a second effective credential." The plan records this as a residual rather than answering it.
- **直接证据**: plan `:74`, `:76`, `:113-122`, `:137-143`, `:294`; `JooqShareAdmissionRepository.java:110-117,131`; `DefaultShareAdmissionService.java:97,285-295`; `ShareMediaCredentialProvider.java:6-21`.
- **影响**: A valid concurrent client can receive a 409/503 instead of the first credential, or the provider can mint a second effective credential; the deterministic-replay success signal is unproven; tests can be false-green.
- **建议改法和验证点**: Pin one convergent rule, e.g. (a) derive `credentialExpiresAt` from a stable witness fact such as the admission-time `sessionExpiresAt`/`admissionExpiresAt` rather than a fresh `databaseNow`, or (b) require the provider to key deterministic replay on `eventId` + `preProviderFingerprint` and to return the first credential/expiry, and require the second request to re-read the first durable event after provider I/O and return its stored expiry; pin the `CONFLICT` mapping and require a two-connection test with independent DB-time samples that asserts one credential, one event, and equal expiry. If neither is possible within the allowlist, stop for renewed confirmation.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F3-未修复-[高]- A durable `FAILURE` followed by a same-key retry has no single frozen outcome; step 8 and step 10 conflict

- **位置**: Plan §3 step 8 (`:74`), step 10 (`:76`), §4.5 (`:148-169`), §6.1/§6.2 tests (`:207-250`).
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口 / 并发恢复风险.
- **当前写法**: The pre-provider lookup treats "a prior success or failure row with a different `purpose` or event type" as a stable 409 conflict, and "a same purpose/event type and same semantic fingerprint" as a replay candidate (`:74`). On provider failure after a durable valid decision, the plan appends one `FAILURE`/`FAILED` event and says "Reuse the first identical failure; a changed failure fingerprint conflicts without a second row" (`:76`).
- **反例/失败场景**:
  1. First attempt fails: a `FAILURE` event exists under the same `requestKeyDigest` with `eventType=FAILURE`. A same-key, same-purpose retry's success identity uses `eventType=PLAYBACK_AUTHORIZED|SEEK_AUTHORIZED|RENEWED`; the event type differs, so healthy step 8 returns 409 `SHARE_GENERATION_STALE` before any provider call. The "reuse the first identical failure" path is therefore unreachable on a normal retry, and the request key is permanently poisoned by one transient provider failure.
  2. If the implementation special-cases a `FAILURE` row as replayable, the plan does not say whether the retry returns the first 503 failure code, performs a fresh success decision, or refuses; if it performs a fresh decision, the new success event and the old `FAILURE` event coexist for one `requestKeyDigest`, and the next retry's step-8 lookup sees both rows and has no deterministic winner.
  3. If a replay of a previously successful request reaches a provider outage, step 10's "append exactly one FAILURE event" can append a failure for a request that already has a success event, contradicting the first durable fact.
  4. No test method covers a `FAILURE` then same-key success retry; `providerFailureAppendsOnlyDeterministicFailureWithoutSuccess` only covers the first failure.
- **为什么有问题**: Control `:35` explicitly requires re-review to verify one frozen outcome and unambiguous tests/event identities. The plan's text yields either permanent 409 or contradictory events depending on implementation, and the two event types live under different identities so the ambiguity is invisible to the current tests.
- **直接证据**: plan `:74`, `:76`, `:148-169`; docs/14 `:251` (identity includes `eventType`; same identity + changed fingerprint = stable conflict); V009 `:118` (`FAILURE` is a registered event type); `JooqShareAdmissionRepository.java:110-117` (full payload hash comparison); `:6.1`/`:6.2` method lists.
- **影响**: Idempotency is ambiguous; a transient provider failure can permanently deny a valid request key; contradictory durable facts are possible; tests cannot prove one outcome.
- **建议改法和验证点**: Pin one behavior in the plan: (a) **terminal first-failure replay** — a same-key same-purpose retry finds the `FAILURE` row, returns the first bounded failure code (e.g., 503 `DEPENDENCY_UNAVAILABLE`) and never calls the provider, with a test; or (b) **fresh retry** — explicitly exempt same-purpose `FAILURE` rows from the step-8 cross-event-type conflict, define how success and failure rows coexist, and define the pre-provider fingerprint's `eventType` field for failure; or (c) another frozen outcome. In all cases pin the failure fingerprint input, event identity, response code, and add a same-key FAILURE→retry test plus a success-replay-during-provider-outage test.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
