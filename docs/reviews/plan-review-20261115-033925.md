## 3. Findings

### 01-未修复-低-“legal” transition 组合采用 V007 broad CHECK 的九种而非 docs/14 owner-service 的五种

- **位置**: plan §3 “Exact result mapping” line `:86`; plan §6 E `allPersistableStatusChannelAndDomainCombinationsProjectExactly` (`:326`); plan §6 G `allNinePersistableTransitionCombinationsReturnAllEnums` (`:362`); plan §6 fixture seeding `:390`.
- **问题类型**: 状态机漏洞 / 契约缺失（frozen design-source 语义与 test oracle 未收敛）。
- **当前写法**: plan 将九种组合称为 “legal combinations”：`INACTIVE→ACTIVE` 和 `ACTIVE→SUSPENDED` 各配 `MINIAPP/ACTIVATION`、`WEB/ACTIVATION`、`IVR/IVR_CONFIRM`、`OPERATIONS/OPERATIONS`，加 `SUSPENDED→ACTIVE`/`OPERATIONS/OPERATIONS`。测试名为 “allPersistable…” 并计划 seed 所有九种组合。
- **反例/失败场景**: docs/14 §4.38 `:2134` 明确说 “The sole owner service enforces the narrower matrix: `INACTIVE→ACTIVE` only for `IVR_CONFIRM` or `ACTIVATION`; `ACTIVE→SUSPENDED` only for `OPERATIONS`; `SUSPENDED→ACTIVE` only for `OPERATIONS` resume” 并且 “A non-OPERATIONS `ACTIVE→SUSPENDED`, an OPERATIONS `INACTIVE→ACTIVE` … are rejected by the service before insert even where the broad check would accept the row shape (OQ-7).” V007 `:127–141` 的 `ck_activation_transition_matrix` + `ck_activation_transition_channel_shape` 允许九种 shape，但只有五种是域内合法。若 fixture 直接以 admin 写入九种，测试会构造 domain-impossible 的 consent/IVR 或 OPERATIONS-first-activation facts，并把它们当作合法历史；页面 validator 也会接受这些行。若真实生命周期 bug 或直写产生这类行，read path 会正常返回而非 fail closed，从而掩盖完整性事件。
- **为什么有问题**: docs/14 是 frozen design source，plan 也把它列为 evidence；plan 只引用了表级 CHECK，遗漏了同节 owner-service 的窄矩阵。page validator 是该端点投影的最后一道完整性检查；如果计划声称验证 “legal status pair and channel/domain pairing”，就应明确采用哪一层的 legality。当前写法把 “V007-persistable” 与 “domain-legal” 混在一起，test oracle 的语义不明确。
- **直接证据**: `docs/14-production-data-model-and-flyway-schema-spec.md:2107–2119`（DB CHECK 与 channel shape）；同文件 `:2134`（owner-service 五种窄矩阵及四种拒绝）；`V007__activation_and_consent.sql:127–141`（broad CHECK）；plan `:86, :326, :362, :390`。
- **影响**: 实现 Agent 可能把 domain-impossible 的九种组合写成测试 fixture 和页面合法值，弱化完整性验证和 review oracle；不是越权、数据写入或用户可见的立即故障，但会掩盖真实生命周期异常并使测试语义与 frozen docs/14 冲突。
- **建议改法和验证点**: 二选一并写死：① page validator 采用 docs/14 的五种域内合法组合，fixture 只 seed 这五种，unit E 与 IT G 的断言改为五种；或 ② 明确声明该 read path 只验证 V007 的 DB CHECK shape，把九种称为 “DB-persistable”（而非 “legal”），并在实现报告中把四种 service-impossible 组合列为 residual/observation，且增加一个负例说明其返回行为。无论哪种，都应增加一条直接验证：对 domain-impossible 行，端点要么 503（域内严格）要么明确按 DB 事实返回（DB-only），不能既不说明又当合法。

## 4. Open questions

1. **Cursor vs frozen docs/15 §5 “normalized filter digest”.** Plan §4.2 deliberately omits a filter digest because this operation has no legal filters. `docs/15:260` states the general cursor convention “bound to stable sort, last internal sort value and normalized filter digest”; the shared OpenAPI `CursorParam` description also mentions a filter digest. Since any unknown/filter query name is 422, a digest would be constant and no `CURSOR_FILTER_MISMATCH` is observable. Please confirm the Control’s “bound to endpoint and stable sort anchor” interpretation; if the frozen prose is read literally, add a constant empty-filter digest to the AEAD payload/AAD (still without emitting `CURSOR_FILTER_MISMATCH`) or record the interpretation in the implementation report. No blocker observed.
2. **Owner port returns the API record `ActivationSummary` across the module boundary.** Existing PA33 ports return port-local `Candidate`/`DetailFacts` records and the service maps them to API DTOs. The plan’s one-record choice is simpler but makes `activation_consent` depend on the exact API serialization record. Confirm this is intentional; if not, use a port-local `TransitionFacts` record and service mapping. No current correctness failure; both are pinned by the proposed architecture test.
3. **Exact `int` vs `Integer` public record component types for `fromRevision`/`toRevision`.** The plan table says “int/Integer while mapping”; the JSON number contract is unaffected, but the code-generation-ready public record should pin one type (prefer `int` with boxed mapping/validation) before implementation.
4. **Snapshot establishment without a clock query.** The plan says “no clock query is needed”; the current context’s identity probe is the first RR statement and therefore establishes the snapshot. The proposed test `singleReadOnlyRepeatableReadTransactionEnclosesAllWork` should assert authority/fetch share the same `txid_current_snapshot()` observation, as the PA33 role test pattern does, so the “authority precedes fetch on one snapshot” claim is proven rather than assumed.
