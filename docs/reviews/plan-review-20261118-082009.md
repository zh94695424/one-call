### F-01-未修复-高-幂等 replay 谓词未定义且在自身顺序下不可达

- **位置**: plan §8.2 `:313-316`（publication replay）、§8.3 `:341-346`（offsale replay）、§4 success signal `:145`、§9.2 `matchingOffsaleReplayIsCurrentStateOnly`
- **问题类型**: 状态机漏洞 / 契约缺失 / 不可直接实施
- **当前写法**: publication "A candidate already `ACTIVE` is a current-state replay only when the request can be **proven to describe** that candidate/current state"; offsale "A **matching** already-`OFFSALE` row is an idempotent current-state read"。未给出任何可判定谓词、判定顺序或该分支的写入/返回集合。
- **反例/失败场景**: 客户端发出 `POST …/V/publications {"expectedActiveVersionId":P,"expectedRevision":r}`，服务端成功提交（P→OFFSALE r+1，V→ACTIVE）。同一请求重试时当前 ACTIVE 已是 V，于是 §8.2 `:308-311` 的期望比较（"Compare both caller expectations to the locked reread … A mismatch is … with no writes"）先行命中 stale，replay 分支永不进入 → 幂等重试得到 409 而非 200。offsale 同理：真实转换后 revision 变为 r+1，同体重试按 §8.3 `:345` "A stale revision … is `CATALOG_PUBLICATION_CONFLICT`" 必然 409；而对一个本来就 OFFSALE 的历史行首次调用也带 r，与上面的重试在数据库层面完全同形，无法区分。
- **为什么有问题**: Goal Confirmation `control.md:23-24` 与 OpenAPI `:1754`、`:1830`（200 = "after publication/offsale **or an already-ACTIVE/OFFSALE idempotent replay**"）把 replay 当作必须可判定的公开契约；`docs14:3451` 只写 "An already-`ACTIVE` candidate **with the same expected state** returns the current immutable state"，plan 把 "same expected state" 弱化成 "proven to describe"，反而丢掉了唯一可操作的字面线索，并把判定顺序留空。implementation agent 只能自行发明"匹配"的定义，且必然在两种错误答案（永不 replay / 把首次调用误判为 replay）之间二选一。
- **直接证据**: plan `:306`（候选必须 `DRAFT` 且 `published_at IS NULL`）、`:308-311`（两条期望先比较，mismatch 即 stale 且不写）、`:313-316`、`:341-342`（"supplied revision must match the locked reread"）、`:344-346`；`control.md:23-24`; `api/openapi/onecall-v1.openapi.yaml:1754,1830`; `docs/14…:3451-3452`;  shipped 写路径的 replay 依据是 Idempotency-Key 命中历史 transition（`DefaultOperationsSubjectLifecycleService.java:64-65` `previous.isPresent()`），PA38 明令无 `Idempotency-Key`（plan `:254`），因此无现成范式可套用。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 状态不一致（幂等重试被公开契约定为失败）/ 不可恢复（错误的 audit/Outbox 事实一旦写入无法删除，见 R-5）
- **建议改法和验证点**: 为两个命令各给一条**有序、可判定**的分类式，例如 publication：(1) 取锁重读后，若候选 `sale_status='ACTIVE'` 且 `expectedActiveVersionId = candidate.currentActiveOfProduct` 且 `expectedRevision = candidate.revision - 1` ⇒ 视为 replay（零写、零事实、返回当前 `CatalogVersionState`）；否则 (2) 期望与重读不匹配 ⇒ `PUBLICATION_STALE_VIEW`；否则 (3) ⇒ `CATALOG_PUBLICATION_CONFLICT`。offsale 用 `expectedRevision = row.revision - 1` 且 `published_at` 未变作为"matching"的充要条件。把每条分支的 writes/facts/返回码/HTTP 状态写成表；补 `matchingPublicationReplayIsCurrentStateOnly` 与 `firstOffsaleOfHistoricalOffsaleRowIsNotReplay`（或明确的相反结论），并在 `matchingOffsaleReplayIsCurrentStateOnly` 中断言"零 revision 变化 + 零新增 audit/Outbox 行"。
- **修复风险（低/中/高）**: 中（需回到 Goal Confirmation 的 owner 裁决 replay 判据；文本改动小）
- **严重程度（低/中/高/严重）**: 高

## 6. Planreview 专项 lens 结论

- **Goal-bound minimal design**：切片形状合格。§4 的一个切片、§11 的"不改文档"、§1 的"仅两路由"都能直接映射到 `control.md:20-31`；没有额外路由、字段、缓存、读模型或 future-slice 代码。唯一实质漂移是 §7.1:244-247 自造的 authority-before-input 验收标准（F-10）；另一处"目标有、验证无"的反向漂移是 F-12。
- **Architecture boundary**：两处真实越界——端口方向造成模块双向依赖（F-04），员工权限事实被推给 `catalog_order` 而没有受控端口与权限路径（F-06）；另有跨模块具体 bean/前缀共用与无主的重读上下文（F-07、F-14）。§6.2 "allow only" 的字面写法还会顺手删掉 `operations_audit` 声明。
- **Best practice**：正面证据同样明确——§10.17 payload/dedupe/reason、V004 约束名、advisory key 形状、T-S2-14 步骤顺序的引用全部逐字可核（本审查逐条比对通过）；缺陷集中在"可判定谓词"和"清单完备性"，不在方向。反面偏离是放弃 shipped 的 `clock_timestamp()` 与 11 参显式 audit 先例（F-11、F-14）。
- **Optimal solution**：V004 基座 + 产品级 advisory lock + 先退役后激活 + 单事务事实，是可信且最小的路线，未发现更简单的替代。但在端口归属上存在**严格更优且 plan 未讨论**的选择（`subject-lifecycle-command` 模式：零新增边方向、零循环风险、符合两条既有先例），故该项判为非最优（F-04）。
- **Overengineering**：未发现。8 个生产类与 Semantics/Configuration 的切分对应 shipped 同构文件；无新抽象层、无通用框架、无未来切片代码。
- **Overcoupling**：三处——过滤器把 `Idempotency-Key` 与 Content-Type/Accept 绑成同一分支，使一个契约变更必然牵动另一个（F-09）；写路径正确性与未声明的既有测试字面量绑死（F-05/F-08）；catalog 发布与员工生命周期共用连接池/配置前缀（R-3，目标强制，接受但须记账）。

## 7. Final verdict

**`fail`**

理由（四条支柱，均可由上文直接证据复核）：
