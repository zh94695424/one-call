## Findings

### P0-01-未修复-[高]-客服可从用户或工单详情完成完整身份临时访问
- **入口/函数**: `pageUserDetail`、`pageTicketDetail`、全局 `request-access` click handler
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:365`、`:471`、`:625`
- **输入场景**: 以 `support` 客服角色登录，进入其允许访问的 `/users/:id` 或 `/tickets/:id`，点击“申请查看完整身份/临时访问”。
- **实际分支**: 页面无条件渲染申请按钮；click handler 无内容类型/角色权限判断，直接创建 access modal，随后可模拟审批、二次验证并签发会话。
- **预期行为**: 权限矩阵中客服对完整证件原值为 `-`，应在展示层隐藏/禁用入口，并在事件处理层再次拒绝伪造触发。
- **实际行为**: 客服可看到虚构的完整姓名、证件和号码，原型表达了错误的权限契约。
- **直接证据**: 角色只有路由级 `areas`；敏感访问没有独立 `canSensitiveAccess(kind)` 判定，`request-access` handler 直接写入 `state.modal`。
- **影响**: 权限提升；评审人员可能批准错误的生产 RBAC 和敏感数据访问链路。
- **建议改法和验证点**: 建立按内容类型的允许角色集合；渲染按钮和 handler 都调用同一判定。Playwright 增加客服在允许访问的用户/工单详情看不到入口，并用脚本伪造 action 仍被拒绝和审计的断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### P0-02-未修复-[高]-浏览器 hash 历史导航不会清除临时访问会话
- **入口/函数**: `go` 与 `render`/`hashchange`
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:259`、`:576`
- **输入场景**: 风控人员在用户详情取得临时身份访问后，直接修改 hash、使用浏览器后退/前进或从历史记录导航离开，再返回原详情页。
- **实际分支**: 只有应用按钮调用的 `go(path)` 在路径变化时清除 `state.accessGrant`；原生 `hashchange` 直接调用 `render()`，后者不检查 grant 的绑定路由。
- **预期行为**: 任何离开授权页面的导航方式都立即清除会话，返回时必须重新申请。
- **实际行为**: grant 保留在内存中，回到相同对象详情会再次渲染完整敏感值。
- **直接证据**: `go` 第 260 行包含清理，`render` 没有等价检查；`window.addEventListener('hashchange',render)` 绕过 `go`。
- **影响**: 临时授权在用户已离开受控上下文后继续有效，违背计划的会话生命周期和审计承诺。
- **建议改法和验证点**: 在统一 `render`/route transition 入口按 grant.route 与解析后的实际路径比较并清理；保留 `go` 清理作为即时路径或移除重复真源。Playwright 使用原生 `location.hash` 离开/返回验证敏感 DOM 不再出现。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
