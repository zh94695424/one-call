## Non-blocking observations

- **O-1 (Low) — PA11 now owns the `Accept` quality policy.** `web/CustomerBoundaryFilter.java:49`–`:59` pre-decides compatibility (specificity then `q`) and maps an incompatible best match, including any `q=0` best match, to 500 INTERNAL before MVC runs. Reviewer probe 7 shows Spring MVC alone would return 200 for `application/json;q=0`, so the filter branch is genuinely required to satisfy accepted-plan §7; but the mixed form `application/json;q=0, */*` is not enumerated in the plan and the filter still returns 500 (pinned by `CustomerMeWebTests.java:312`). Impact: a duplicate negotiation policy exists next to MVC's, and one legitimate client expression is answered with a server-error code. Not a security issue and defensible under RFC 9110 §12.5.2 specificity. Recommendation: when the shared API Problem/negotiation convention is consolidated, state the `q=0` rule once and note that this slice intentionally overrides MVC's leniency. Owner: Backend/Architecture with API/Security (docs/15 + A1 reconciliation).
- **O-2 (Low) — Adapter-thrown application exceptions collapse to 503.** `security/CustomerBearerAuthenticator.java:35` catches `RuntimeException` and emits `SERVICE_UNAVAILABLE`; because the `candidates.size() != 1` throw at `:29` sits inside the same `try`, a `CustomerContextException` raised by a verifier (the exact case pinned at `CustomerSessionBoundaryTests.java:92`) is also reported as 503, not as its intended code. Both paths are fail-closed denials that establish no identity, and the plan mandates 503 for unexpected adapter failures, so behaviour is correct; the self-catch at `:29` is nonetheless redundant. Recommendation: move `:29` out of the guarded region, or add a comment marking the port contract as "signal 401 only via `CustomerSessionVerificationException`". Owner: Backend/Identity (future adapter work unit).
- **O-3 (Low) — `default -> 500` branches are unreachable-by-type but type-loose.** `web/CustomerProblemWriter.java:32` and `:41` switch on a `String`, with `default` producing `500 / Internal error`. Today the only callers pass `CustomerContextException.Code` (six values) or the literal `NOT_FOUND`, so no reserved code can be forged and no unknown code can leak text. Recommendation: switch on the enum plus an explicit `NOT_FOUND` sentinel so a future caller cannot silently land in `INTERNAL`. Owner: Backend/Security (Problem convention owner).
- **O-4 (Low) — `BufferedResponse` implements only part of the `HttpServletResponse` contract.** `web/CustomerBoundaryFilter.java:78`–`:119` routes `getWriter()` and `getOutputStream()` into one `ByteArrayOutputStream` without ordering guarantees, `flushBuffer()` (`:101`) flushes only the writer, `resetBuffer()` (`:103`) does not delegate, `setWriteListener` always throws (`:88`), and `reset()` (`:105`) also zeroes `errorStatus`. All of this is currently unreachable in a harmful way: Boot's JSON converter uses only the byte stream, and reviewer probe 6 shows the `errorStatus` guard survives precisely because `isCommitted()` becomes true after `sendError`, so the writer never reaches `reset()` on that path. Impact is latent fragility, not a defect. Recommendation: either buffer through a single stream façade or add a comment recording the `isCommitted()`-after-`sendError` dependency so a future Tomcat upgrade cannot silently reintroduce a double body. Owner: Backend/Web.
- **O-5 (Low) — the role-mismatch-by-value branch has no test.** `application/CustomerContextService.java:36`–`:40` rejects a `current_user` that is a non-null but different role, yet `CustomerContextServiceTests.java:131` only exercises `fetchOne("select current_user")` returning `null`, and `CustomerMeWebTests` stubs only the matching value. PostgreSQL always returns exactly one row, so the null case is the unrealistic one and the realistic `42501`-style mismatch witness is only covered indirectly by `CustomerMeIT.webRuntimeReadsMigratedDatabaseUnderCustomerRole`/`verifierOutageAndDatabaseFailureExposeNoSecrets` (denied-login context → 503). Recommendation: add a stubbed mismatched role name to `roleAssertionPrecedesRepositoryAndTransactionIsReadOnly` and assert 503 plus `verifyNoInteractions(repository)`; the method set and 49/84/133 counts stay identical. Owner: Backend/QA.
- **O-6 (Low) — qualifier assertion is prefix-based, not exact.** `CustomerWebConfigurationTests.java:121` asserts each `@Qualifier` value merely `startsWith("customer")`/`startsWith("sharing")`, while accepted plan §4 freezes the exact bean names. Exact names are present in `persistence/CustomerPersistenceConfiguration.java:30`–`:78` as required. Recommendation: assert `containsExactly`-style equality against the eight literal bean names. Owner: Backend/QA.
