## 2. Material findings

### F-01-未修复-中-docs/15 is classified as a frozen contract input but is absent from the raw/LF hash baseline and A06 oracle

- **位置**: Plan §1 "Frozen contract inputs"; §2 hash table; §10.3 baseline hash script and `git.exe diff --exit-code` command; §11 completion report ("frozen raw/LF hashes").
- **问题类型**: 不可验证行为 / 验收证据缺口.
- **当前写法**: §1 states that frozen contract inputs include the current OpenAPI, `docs/14`, **`docs/15`**, V001–V017 and current source/tests. §2 provides raw/LF hashes for exactly four paths: OpenAPI, `docs/14`, `V003` and `project-execution-control.md`. §10.3 says "At implementation entry capture a private baseline of the four frozen inputs plus all17 migrations", but its Python script lists three non-migration files plus the 17 `V*.sql` files and asserts `len(names) == 20`; `docs/15` is not in the list. The completion-report template still says "frozen raw/LF hashes".
- **反例/失败场景**: The implementation agent or a later closeout edits `docs/15` (for example to "clarify" the claim problem mapping or to normalize line endings). The §10.3 hash script does not hash `docs/15`, and the §9.1 A06 test is described as "Raw+LF hashes; V001–V017" without a `docs/15` oracle. The only remaining protection is the manual `git.exe diff --exit-code` command, which the plan itself records as unavailable in its Windows/WSL environment and which is not an executable test. The completion report can then truthfully claim "frozen raw/LF hashes" while `docs/15` has drifted.
- **为什么有问题**: The confirmed goal and the plan's own §1 bind `docs/15` as a frozen contract input. `docs/15:238–241` is the source of the exact claim 409 set and the "invalid proof is 422" rule used by the plan. A content change there can silently change the public contract that the implementation and review are validating against. The plan's "four frozen inputs" arithmetic is also internally inconsistent: `V003` is one of the four §2 rows and one of the 17 migrations, so "four inputs plus all 17 migrations" cannot be 20 without either double-counting `V003` or omitting `docs/15`.
- **直接证据**: Plan §1 line 20; plan §2 hash table lines 17–22 (OpenAPI, docs/14, V003, Control only); plan §10.3 lines 576–580 (`names` = three non-migration paths + 17 migrations) and line 580 (`assert len(names) == 20`); plan §10.3 lines 561–565 (the diff command does include `docs/15`); at review time `docs/15` raw SHA-256 is `db2f9b5a548288b71be4566ce1b820b9a9ffd0118978c24f92bdcc69d6aab5a0` and LF-canonical SHA-256 is `0b3b996e3e4a4acc3cb38211290be5ae874d66e7c63d670958b8bc23f67b9b02`, but neither value appears in the plan.
- **影响**: The frozen-input evidence for one of the five binding contract sources is weaker than the plan claims. A `docs/15` edit can pass the hash/A06 checks and be caught only by a manual diff or not at all, causing contract drift, inconsistent implementation, and a false "frozen hashes" completion claim.
- **建议改法和验证点**: Add `docs/15` raw and LF-canonical hashes to §2 and to the A06 oracle, and add `docs/15` to the §10.3 `names` list (which then becomes 21: four non-migration frozen inputs plus 17 migrations, with `V003` counted once in the migrations). Alternatively, explicitly scope the 20-file script to "three non-migration frozen inputs plus all 17 migrations" and state that `docs/15` is protected only by the diff; even then, add a `docs/15` hash assertion because one of its lines is directly used by the plan. Correct the "four frozen inputs plus all17 migrations" wording to remove the `V003` double count.

### F-02-未修复-中-The two-phase preparation transaction and PreparationChanged restart are future-KMS-driven overdesign for an S1 goal that explicitly has no external calls

- **位置**: Plan §6.3 "Keeping providers outside locks without a framework"; §7.4 retry implementation; §9.1 U06; §9.2 I02/I24; §10.1 validation counts.
- **问题类型**: 过度设计 / 非最优方案 / 范围漂移风险.
- **当前写法**: The plan splits every attempt into (1) an unlocked, role-asserted SELECT-only preparation transaction that resolves the binding identity, reads the current request/accepted rows, verifies/seals/opens the input reference and opens stored references, then closes its connection before any SPI call; and (2) an authoritative locked transaction that rereads everything. It adds a private `PreparationChanged` signal to roll back and restart preparation within a three-attempt budget. It justifies this with "The small prepare phase is necessary because later KMS-backed opening must not hold PG locks".
- **反例/失败场景**: The confirmed PA30 goal explicitly says no production proof verifier or KMS/encryption implementation exists; the work unit may define only the minimum narrow proof/reference SPI with production-default fail-closed behavior and controlled fakes, and real provider/KMS integration is a later owner/destination. `docs/14` §9.0 states "No lock is held across an external network call. S1 has no external calls." The two-phase structure therefore exists only for a future collaborator that is out of scope. The extra preparation transaction, staged decoded-payload map by claim ID and `PreparationChanged` restart add a second transaction and a second state machine per attempt. A subtle implementation error — for example, reusing a prepared decoded payload for a row that was not reread under the authoritative lock, or failing to re-prepare after a newly visible row — can produce an incorrect replay/context decision or a misleading 503. The extra U06/I02/I24 and U17/U18 test paths increase the gate cost for behavior that S1 does not need.
- **为什么有问题**: The confirmed goal is a goal-bound minimal slice. The plan's corrected re-read and rollback semantics are good, but the two-phase preparation is not required to satisfy T-S1-06 for S1's local fail-closed fakes. It couples the slice to a future KMS/provider design and makes the transaction/retry state harder to review and test than necessary. The plan's own §6.3 acknowledges the future motivation ("later KMS-backed opening"), which is exactly the kind of future-slice work the goal's non-goals exclude.
- **直接证据**: `docs/gateflow/project-execution-control.md` PA30 bullet "Binding proof boundary" (lines 22, 26) excludes real SMS/WeChat/caller challenge/manual review/KMS and limits this work unit to the minimum SPI plus controlled fakes; `docs/14-production-data-model-and-flyway-schema-spec.md` §9.0 ("No lock is held across an external network call. S1 has no external calls."); plan §6.3 lines 218–225 (two phases; "later KMS-backed opening"); plan §7.4 lines 332–336 (whole-attempt retry); plan §9.1 U06 and §9.2 I02/I24.
- **影响**: Overdesign/overcoupling: more production code, more transaction/retry states, more tests and a higher chance of a subtle stale-preparation defect or an unnecessary 503 for a future concern that the goal already defers. It also makes the "one behaviorally coherent slice" materially larger than the goal requires.
- **建议改法和验证点**: For S1, keep the two SPI contracts but perform the local proof verification, seal/open and stored-reference open **before or inside the single authoritative transaction** (S1 has no external calls; the authoritative transaction already holds the locks). Reuse the existing `TransactionTemplate` once per attempt, keep the current reread/lock/owner/audit order, and remove the separate preparation transaction, the staged-by-claim-ID map and the `PreparationChanged` restart. If the Controller instead wants the future-KMS seam, record it as a separate confirmed requirement and add the corresponding proof-consumption/expiry policy and tests; do not present it as necessary for the current S1 foundation. Validation: a simplified test inventory should still cover U06's "no provider call under lock" by construction (no provider call exists in S1) and the existing U17/U18 unique/rollback scenarios without the preparation-restart branch.
- **修复风险（低/中/高）**: 中 (plan revision; implementation has not started).
- **严重程度（低/中/高/严重）**: 中.

### F-03-未修复-中-The container fixture description omits the `persistence` profile needed to load the owner service and SPI beans

- **位置**: Plan §7.1 (`SubjectClaimPersistenceConfiguration` is `@Profile("persistence")` plus the enabled property); §9.2 `CustomerSubjectClaimFixture` description; §10.1 container commands.
- **问题类型**: 测试缺口 / 不可直接实施.
- **当前写法**: §9.2 says `CustomerSubjectClaimFixture` "composes `CustomerBusinessNumbersFixture.start(null)` for the accepted migration/provisioning baseline, but builds its own web context containing `OneCallApplication`, existing test session configuration and controlled proof/cipher beans plus explicit command properties." It does not state the Spring profile set. The existing base fixture's `web()` starts with `.profiles("web")` only; `CustomerWebConfiguration` is `@Profile("web")`, while the new `SubjectClaimPersistenceConfiguration` is `@Profile("persistence")` and `@ConditionalOnProperty` on `onecall.subject-claim-command.enabled=true`.
- **反例/失败场景**: An implementation agent follows the base fixture's `.profiles("web")` pattern, sets the command properties, and starts the claim web context. The controller and composer load, but the owner service, repository, dedicated pool and default/controlled SPI beans do not, because the `persistence` profile is absent. Every claim request returns 503 (owner service unavailable); I01–I24 and L01–L10 fail or must be reworked. The plan's container tests would not be executable as written.
- **为什么有问题**: The slice/test inventory is supposed to be code-generation-ready. The profile boundary is a real dependency: `@Profile("persistence")` is the activation condition for the dedicated pool and SPIs, and the base fixture deliberately uses only `web`. The plan also needs the customer query properties because `CustomerPersistenceConfiguration` is `@Profile("web")` and will load in the same context and requires its own credentials. Leaving both unstated invites a fixture that cannot produce the claimed I/L evidence.
- **直接证据**: Plan §7.1 lines 231–249; plan §9.2 lines 486–488; `backend/src/test/java/com/onecall/archtests/container/CustomerBusinessNumbersFixture.java` `web()` (`.profiles("web")` and `onecall.customer.persistence.*` properties); `backend/src/main/java/com/onecall/core/customer_iam/internal/persistence/CustomerPersistenceConfiguration.java` (`@Profile("web")`); plan §7.1 says `SubjectClaimPersistenceConfiguration` is `@Profile("persistence")` and only enabled by the explicit property.
- **影响**: The fixture can be implemented in a way that passes compilation but cannot exercise the real HTTP endpoint/owner transaction, causing failed container tests, rework and unverified I24/L10 behavior.
- **建议改法和验证点**: Specify the exact fixture startup: profiles `web,persistence`; `onecall.subject-claim-command.enabled=true`; the dedicated command datasource URL/username/password for the synthetic login; and the customer query datasource/cursor properties needed by the existing web-profile configurations. Add a fixture self-check that the qualified owner service and both SPI beans are present; the I01 test should assert the effective command role/PID before the first claim.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

## 3. Open questions

- **OQ-1 (audit reason/outcome mapping)**: Plan §7.3 names only `CLAIM_ACCEPTED`, `CLAIM_REPLAYED` and `CLAIM_DUPLICATE` as audit reasons, while the 5.3 matrix defines several denial paths (`CLAIM_RISK_BLOCKED`, `CLAIM_REPLAY_CONFLICT`, `CLAIM_CONTEXT_CONFLICT`, `CLAIM_OWNER_CONFLICT`, predicate/binding/account failures, `CLAIM_DATA_INTEGRITY`, retry exhaustion). The audit snapshot enum includes both `REJECTED` and `DENIED`. Should the plan provide an exact reason/outcome table for every locked decision so I23/U18 can assert stable audit facts rather than only "safe fields"? This is not a blocker because the matrix supplies internal reasons, but the mapping should be explicit before implementation.
- **OQ-2 (docs/15 evidence)**: Should the Controller require a raw/LF hash for `docs/15` (F-01), or is the diff-only protection acceptable? The former is stronger and matches the "frozen contract input" label.
- **OQ-3 (future preparation seam)**: If the two-phase preparation is retained (F-02), should the Controller explicitly confirm it as a current S1 requirement rather than a future-KMS convenience? Retaining it without that confirmation is a goal-bound design risk.
- **OQ-4 (sensitive type list)**: Should `SubjectClaimVerificationReference.Payload`, `SubjectClaimProofVerifier.ProofRequest` and `ApprovedProof` be explicitly added to the constant-redacted `toString()` list? The plan's R08/W11 assertions can cover them, but the types contain `numberHmac`, `proofRef` and `verificationProofId` and are exactly the kind of record whose auto-generated `toString()` is easy to leak.
- **OQ-5 (missing account public mapping)**: `CLAIM_ACCOUNT_NOT_FOUND` is mapped to 403 FORBIDDEN. The Control lists "inactive account" as FORBIDDEN but does not name the missing-account case; `docs/14` gives the internal code with no claim row. Is 403 the Controller-approved public mapping for a verified session whose account row is absent? It is a defensible boundary, but it is not written in the frozen public matrix.
