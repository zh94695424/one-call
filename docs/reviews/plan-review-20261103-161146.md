## 4. Findings

### B-01 — High (blocking): V010 forces edits to exact inventories that the plan's own ownership rule forbids

**Scenario.** Implement V010 exactly as planned. `./mvnw -B -ntp -Pcontainer-smoke verify` and CI go red immediately, because V010 changes observable catalog state that existing tests pin byte-exactly.
**Evidence.**
- `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5039-5135` `assertV009AclCatalog` asserts the *complete current* `sharing_role` ACL set: 7 schema USAGE rows, 6 table privileges (`SELECT`/`INSERT` × 3 sharing tables), 42 column rows (`expectedColumnAcls).hasSize(42)`), 5 function EXECUTE rows, plus `pg_auth_members` count `isZero()`. Called from CI-pinned `v009OwnerPublicRuntimeAndCrossModuleAclsAreExact` (`:3060`) and `concurrentV009AdmissionIdentityLimitAndLifecycleHasOneWinner` (`:3562`).
- `PostgresContainerIT.java:8430-8449` `assertSchemasAndRoles` asserts the whole-database role set with `containsExactlyElementsOf`, ending at `sharing_owner`/`sharing_role`; adding `sharing_command_role` fails it (same `:3562` caller).
- Flyway census is pinned at nine: `PostgresContainerIT.java:1285-1369` walks `flyway_schema_history` row-by-row and closes with `assertThat(resultSet.next()).isFalse()` after `009|V009__sharing.sql`; `:10735-10756` `containsExactly` nine history rows **and** nine `flyway.info().all()` scripts; `SharingQueryFixture.java:70-72`, `CustomerMeFixture.java:87-89` and `SharingQueryServiceIT.java:36` assert `migrationsExecuted == 9` / `applied().hasSize(9)`.
- `.github/workflows/ci.yml:147` hard-fails unless `PostgresContainerIT` has **exactly 64** `@Test` methods with **exactly** the pinned name set (`:79-144`), `:317` fixes the Failsafe aggregate at `92`, `:318` prints `64+10+10+8=92; combined 159`, and `:309`-`:314` reject any source test class absent from `container_expected`.
- The plan says the opposite: `docs/gateflow/pa13-sharing-role-least-privilege-plan.md:45` "retain login configuration and query assertions, **changing only** explicit future-write behavior principals"; `:48` "PA12 `/shares` … remain covered **unchanged**"; `:59` "Do not weaken assertions by changing exception types".
**Impact.** The instruction set is unsatisfiable: green CI requires editing `assertV009AclCatalog`, `assertSchemasAndRoles`, the two Flyway history inventories, four migration-count assertions, `container_expected`, the `92`/`159` totals and the printed summary — none of which is "a future-write behavior principal". ### B-02 — High (blocking): the validation contract cannot run the integration tests it cites as evidence

**Scenario.** An implementer runs validation steps 2 and 3 verbatim. Step 2 either dies in Surefire or "passes"; step 3 "passes". Neither executes a single container IT.
**Evidence.** `maven-failsafe-plugin`, its four `<includes>` and `failIfNoTests=true` are bound **only** inside the `container-smoke` profile — `backend/pom.xml:169-193` (profile id `:170`, plugin `:175`, includes `:177-182`). ### B-03 — High (blocking): the command-role column set is derived by a rule that provably breaks frozen behavior

**Scenario.** The implementer follows plan `:29` ("SELECT the command workflow's lookup/guard/read columns") and `:31` ("do not grant SELECT absent a frozen workflow read"), grants a subset, and every frozen V009 admission/lifecycle probe fails with `42501` instead of its expected `P0001`/`23514`/row assertion — or the future admission semantics become impossible without a further migration, which the plan itself forbids.
**Evidence.**
- `V009__sharing.sql:262-266`: the `BEFORE INSERT` guard `sharing.guard_share_admission()` is `SECURITY INVOKER` and executes `SELECT * INTO parent_grant FROM sharing.evidence_share_grant` against a `%ROWTYPE` of all 20 columns. Column-level `SELECT` on a subset makes an expanding `SELECT *` an authorization failure, so **any** role that inserts an admission needs `SELECT` on all 20 grant columns. V009 satisfied this with table-wide `SELECT` (`:308`).
- `PostgresContainerIT.java:4138-4161`: `v009S2Clone` emits `INSERT INTO sharing.<table> (<all columns>) SELECT <all columns> FROM sharing.<table> WHERE id = ?` for `evidence_share_grant`, `share_admission` **and** `share_access_event` — i.e. full-column reads of `capability_token_hash`, `code_salt`, `code_hash`, `content_snapshot`, `content_sha256`, `payload_redacted`, `payload_sha256`.
- `PostgresContainerIT.java:4570-4580` reads `id`, `revision`, `status` and `SELECT … FOR UPDATE` under the role; `:3482`, `:3707-3710`, `:3733-3738`, `:3888` and 34 sites in total `SELECT` from `share_admission`/`share_access_event`, which plan `:31` proposes to leave INSERT-only.
- Plan `:35` moves exactly these probes to `sharing_command_role` and `:59` demands their assertions stay intact.
**Impact.** The plan's derivation source ("docs/14 §10.21 and the V009-behavior fixture SQL") cannot produce a consistent command grant list without the reviewer-visible insight above; the frozen admission guard and the frozen S2/S3 corpus both require full-column reads of all three sharing tables. This is a redesign decision, not an implementation detail.
**Correction.** State in the plan, as the determined answer: `sharing_command_role` receives table-level `SELECT` on all three `sharing.*` tables (plus `INSERT` per plan, `UPDATE` on the eight V009 lifecycle columns at `V009__sharing.sql:313-315`, and no `DELETE`/`TRUNCATE`/`REFERENCES`/`TRIGGER`), justified explicitly by `guard_share_admission`'s `SELECT *` and by `v009S2Clone`; or, if narrowing is desired, enumerate the complete 20/14/11-column sets and prove each probe against them. Record that the command role — not the query role — is the only principal that can read secrets, and keep the query role's denial probes unchanged.

### B-04 — High: `organization_membership.role` is removed from both roles while the frozen ORGANIZATION_MEMBER predicate still needs it

**Scenario.** V010 grants membership `role` to nobody. The future recipient-admission check for `ORGANIZATION_MEMBER` then has no legal way to evaluate the documented predicate, and the next work unit must reopen ACLs the plan declared frozen.
**Evidence.** Plan `:23` (query set omits `role`) and `:33` (command cross-module read list repeats the same three-column tuple, omitting `role`). `V009__sharing.sql:349` grants `SELECT (organization_id, account_id, role, status)`; `PostgresContainerIT.java:4722-4727` `V009_FOREIGN_COLUMNS` includes `role` in the pinned 42-row inventory. docs/14 `:4021` documents the rationale verbatim: "`organization_id`, `account_id`, `role`, `status` | Creator/recipient membership **and role** under the logical pair lock"; docs/14 `:285` and `:4262` restate it as the durable sharing contract. It also contradicts the plan's own `:27` promise to "preserve only the frozen future … semantics in docs/14 and V009", because docs/14 preserves `role` as frozen sharing surface.

### B-05 — High: after V010 the "read-only-but-otherwise-authorized write fails `25006`" witness has no authorized write left for `sharing_role`

**Scenario.** Plan `:25`/`:35`/`:59` require the existing read-only proofs to survive unchanged: "retain a separate read-only proof that an otherwise authorized write is blocked by transaction mode" and "Do not weaken assertions by changing exception types". Once V010 removes every write privilege from `sharing_role`, no statement is "otherwise authorized" for that principal, so the proof's subject is gone.
**Evidence.** Both current `25006` witnesses depend on V009's column `UPDATE` grant: `SharingQueryFixture.java:267-271` executes `UPDATE sharing.evidence_share_grant SET revision = revision + 1` as `sharing_role` inside the production read-only pool and `SharingQueryServiceIT.java:319` asserts `writeState == "25006"`; `CustomerSharesFixture.java:328-340` does the same on the `sharingLogin` and asserts `"25006"`, called by CI-pinned `CustomerSharesIT.java:237-239`. `V009__sharing.sql:313-315` is what makes `revision` writable today; docs/14 and the control (`docs/gateflow/project-execution-control.md:22-23`, `:26`) both cite this `25006` proof as retained evidence.
**Impact.** The implementer must either (a) let the probe become a `42501`-or-`25006` test of an unauthorized statement — which no longer separates transaction mode from authorization and silently changes the meaning of two CI-pinned assertions — or (b) redesign the witness under `sharing_command_role`. The plan forbids (a) and does not mention (b), so this is unresolved and lands on the implementer. Which check PostgreSQL raises first for a DML statement that is both unauthorized and inside a read-only transaction is **not settled by this review** (no Docker socket, no network); the plan must not leave that ordering implicit either way.
**Correction.** Specify the post-V010 `25006` witness explicitly: run an *authorized* command-role mutation (per B-03's grant set) in a read-only session to prove `25006`, keep the query-role probes in read-write sessions to prove `42501`, and state which existing assertions change and why that is not a weakening. If ordering cannot be assumed, derive it in the IT with two separately-labelled statements rather than reusing the current one.

### B-07 — Medium: V010's execution identity and the REVOKE/GRANT mechanics are left as "derive later"

**Scenario.** The implementer writes V010 as one flat block under the Flyway identity, and `REVOKE`/`GRANT` fails, or succeeds for tables but leaves V009's cross-module column ACLs in place so `sharing_role` still reads evidence/subject columns and the negative probes fail.
**Evidence.** Plan `:13` says "Revoke ALL on both roles for all V009 table grants, schema/function ACLs currently given to `sharing_role`", "`SET LOCAL ROLE` only if needed to own role/ACL statements" and "the migration identity must already have role administration rights" — without saying who that identity is or per-object grantor. V009 itself demonstrates the required shape: `V009__sharing.sql:9,138,168,326,336,344,354,366,373` `SET LOCAL ROLE` into `sharing_owner`, `evidence_owner`, `customer_iam_owner`, `organization_access_owner`, `subject_number_owner`, `platform_reliability_owner`, `audit_owner` — seven owning roles, because GRANT/REVOKE on an object requires that object's owner (or its owner-role member), not merely role administration. The privileges to be removed are heterogeneous: 6 relation-level (`:308-315`), 42 attribute-level `pg_attribute.attacl` entries (`:329-363`), 5 `pg_proc.proacl` entries (`:317-322`, `:369`, `:376`) and 7 `pg_namespace.nspacl` entries (`:6-7,328,338,346,356,368,375`). Column-level ACLs are stored per attribute, so the plan must say whether a relation-level `REVOKE ALL` is expected to clear them or whether per-column `REVOKE (…)` statements are required. `:89` lists this as an assumption "to verify", which is a redesign input, not an assumption.
**Impact.** Ambiguity here decides whether V010 is a 20-line or a 60-line migration and whether the "no residual cross-module SELECT" guarantee is real; it is exactly the "derive before implementation" class that must be closed at the plan gate.
**Correction.** Name the migration identity and the per-object `SET LOCAL ROLE x_owner` sequence (mirroring V009's seven blocks), give the ordered statement list `REVOKE ALL … FROM <role>` → per-attribute revoke → re-grant, and state the expected `pg_class.relacl` / `pg_attribute.attacl` / `pg_proc.proacl` / `pg_namespace.nspacl` end state for both roles.

### B-08 — Medium: catalog-evidence design mixes a membership-filtered view with role-name functions, allowing vacuous denials

**Scenario.** The new IT "proves" the command role has no unexpected grants because the query it used returned zero rows for a role the current user cannot see.
**Evidence.** Plan `:20` lists `has_schema_privilege`, `has_table_privilege`, `has_column_privilege`, `has_function_privilege` (all take an explicit role name and are reliable) **and** `information_schema.role_table_grants`/`column_privileges`, which in PostgreSQL expose only privileges available to the currently enabled role(s); under `SET LOCAL ROLE sharing_role` they contain no rows about `sharing_command_role`, and under the superuser they contain everything. Plan `:23` also demands "Assert exact allowed function set is empty" with no scope predicate — application functions all start with `PUBLIC` EXECUTE from `acldefault('f', owner)` (which is why V009 revokes at `:317-322`), while `pg_catalog`/`information_schema` functions are always PUBLIC-executable and cannot be narrowed.
**Impact.** A denial assertion can pass because of visibility rather than privileges, and an unscaled "no function EXECUTE anywhere" assertion is unsatisfiable — the opposite of the "not a list of GRANTs" standard plan `:90` sets for itself.
**Correction.** Make `aclexplode(coalesce(acl, acldefault(…)))` over `pg_class`/`pg_attribute`/`pg_proc`/`pg_namespace` plus `has_*_privilege('<role>', …)` authoritative (the pattern already proven at `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5039-5135`), demote the `information_schema` views to supplemental, and bound every empty-set assertion to the application namespaces (`PostgresContainerIT.java:5074` for the namespace exclusion and `PostgresContainerIT.java:5122` for the extension-owned-function exclusion via `pg_depend`).
