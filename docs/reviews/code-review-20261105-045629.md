## Findings

### 1-未修复-中-createCustomerShare 无界 readAllBytes 请求体读取可由已认证客户触发进程级 OOM

- **入口/函数**: `CustomerSharesController.createCustomerShare`（`POST /api/v1/customer/shares` 控制器方法）；边界过滤器完成认证与 Content-Type 校验之后、binder 解析之前的原始 body 读取。
- **文件(行号)**: `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerSharesController.java:59`
- **输入场景**: 任意持有有效 `customerSession` 的客户端向 `POST /api/v1/customer/shares` 发送任意大（GB 级）请求体；可带任意大 `Content-Length`，也可用 chunked 编码不带该头；body 内容无需是合法 JSON（无需通过任何前置结构校验）。
- **实际分支**: `CustomerBoundaryFilter` 只校验方法/路径/认证/`Content-Type`，不读取 body；控制器第 57 行 workspace-shape 校验通过后，第 59 行 `binder.create(request.getInputStream().readAllBytes())` 将整个请求体一次性缓冲进 `byte[]`，之后才进入 `CustomerShareCommandJsonBinder` 的封闭 schema 422 校验。`backend/src/main` 全树仅此一处 body 读取，且无任何大小上限（无 `readNBytes`、无 `Content-Length` 检查、无 `maxPostSize`/`max-http*` 配置；Tomcat `maxPostSize` 仅作用于表单解析，不覆盖该裸读取）。
- **预期行为**: `docs/15` 与 `ShareCreateRequest` 封闭 schema（`creationRequestId` 1–128、`designatedMobile` 1–32、UUID/enum/固定字段）决定合法 body 仅数百字节量级；超长 body 应在全量缓冲之前被结构性上限拒绝并映射既有 422 `VALIDATION_FAILED`（或等价受控 4xx），与 binder 的严格封闭校验语义一致，同时保持计划规定的“Content-Type 门后单次读取原始 body”契约。
- **实际行为**: 无上限全量读入堆内存；单个已认证请求即可耗尽堆并触发 OOM，导致同 JVM 内全部会话/请求不可用且无法自愈；binder 的 422 校验与服务调用永远不会执行到。
- **直接证据**:
  1. `CustomerSharesController.java:59` — `try { body = binder.create(request.getInputStream().readAllBytes()); }`；
  2. `grep -rn "readAllBytes|getInputStream|Content-Length|readNBytes|maxBody|maxPostSize|max-http" backend/src/main` 仅命中该一行；`application.yml`/`application-web.yml` 无请求体大小配置；
  3. 基线 `259aeb45` 的同名控制器仅含 `@GetMapping`；PA14 区间 `git diff --stat` 对该文件为 +49 行引入 POST —— 该读取为 PA14 新增，非既有模式；
  4. 测试面无覆盖：`CustomerSharesCommandWebTests`/`CustomerSharesWebTests` 的 body 负例矩阵（空/截断/类型/枚举/精度/重复键/超长字段）全部经小体积字符串构造，无超限 body、无 413/422-over-cap 用例。
- **影响**: 可用性 —— 进程级 OOM 波及全部租户会话，非单请求失败；无数据损坏或机密泄露。触发前提为有效客户会话（过滤器先认证），非匿名攻击面。
- **建议改法和验证点**: 将第 59 行替换为带上限的单次读取（如 `InputStream.readNBytes(cap + 1)`，超限即 `throw new ShareCommandException(Code.VALIDATION_FAILED)` 走既有 422 Problem 路径），`cap` 从 `ShareCreateRequest` 封闭 schema 字段最大长度推导为结构性常量（数百字节～数 KB 量级），不引入策略类可配置值；对存在 `Content-Length` 的请求在读取前先行同样拒绝，chunked 无头场景由 `readNBytes` 上限兜底。验证点：新增 web 用例分别以超上限 `Content-Length` 与 chunked 超限 body 发起 POST，断言 422 `VALIDATION_FAILED`、`commands.execute` 零调用、响应无内部细节泄漏；既有 201/200/422 正负用例与路由矩阵全部保持通过。
- **修复风险**: 低。合法请求体远低于任何合理结构上限；改动局限于单一读取语句与一个受控异常分支，不触及指纹、事务、路由与响应语义；需确认上限同时覆盖 chunked 编码路径。
- **严重程度**: 中。
