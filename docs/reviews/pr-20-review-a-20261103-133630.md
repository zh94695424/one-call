## Findings

### F-A-01 — [High] `sharing_role` table-wide privileges permit direct secret-column reads (PA12-ACL-01) — confirmed, deferred, **not fixed by PA12**

- **Entry/function:** database trust boundary beneath `GET /api/v1/customer/shares`; the
  PA10 query principal `sharing_role`.
- **File/line:** `backend/src/main/resources/db/migration/V009__sharing.sql:308`
  (`GRANT SELECT, INSERT ON TABLE sharing.evidence_share_grant TO sharing_role;`) and
  `:313-315` (lifecycle-column `UPDATE`). Secret columns at V009:14 (`capability_token_hash`),
  `:19` (`code_salt`), `:20` (`code_hash`), `:27` (`content_snapshot`),
  `:28` (`content_sha256`).
- **Trigger:** connect through the sharing query login, `SET ROLE sharing_role`, and read
  any secret column directly.
- **Branch:** the ACL applies to the role used by the application query transaction; the
  application's safe 11-column `SELECT` does not remove the role's broader privilege.
- **Expected:** the query principal should be limited to the approved metadata projection;
  direct secret-column reads should be denied, and role-effective denial should be
  tested.
- **Actual:** table-wide `SELECT`/`INSERT` plus lifecycle `UPDATE` are granted; secret
  columns are readable after `SET ROLE sharing_role`. The PA12 `42501` probes use a fresh
  NOINHERIT direct login **without** `SET ROLE`, so they are not role-effective evidence.
- **Direct evidence:** the migration lines above; my disposable PostgreSQL 16.15
  reproduction (secret-column `SELECT LIMIT 0` succeeds under `SET ROLE sharing_role`;
  direct login without role fails 42501); `CustomerSharesIT.java:240-256` explicitly
  labels the direct-login probe "not role-effective ACL evidence"; `README.md:15`, the
  plan (`:9,17,154,255`) and the aggregate-fix record (`:6,11,53`) state the deferral.
- **Impact:** a compromised or broadened query path, direct operational use of the
  sharing login, or a future read-path regression can read capability hashes, code
  material, and content snapshots. The HTTP response itself is metadata-only today.
  This is a **pre-production security blocker**.
- **Fix direction (outside PA12 scope):** the separate Backend/Database/Security work
  unit must introduce a least-privilege role/view or column-scoped grants (and separate
  endpoint read privileges from create/revoke/rotate write privileges), then add a
  role-effective negative test that asserts secret-column denial under `SET ROLE`.
  V009 is frozen and must not be weakened or silently rewritten.
- **Fix risk:** high only if attempted inside PA12 (would violate the frozen migration
  scope); low as a separately authorized migration/role work unit.
- **Severity:** High.
- **Status / owner / destination:** `deferred-with-owner`, **not fixed**; owner =
  separate Backend/Database/Security work unit; destination must be identified before
  production rollout. This is exactly the disposition recorded in
  `docs/gateflow/project-execution-control.md:91-112` (PA12-ACL-01 at `:93,:99,:102,:107`).
