### S3-01-未修复-[高]-Same-key admission replay is denied once `max_admissions` is reached
- **入口/函数**: `sharing.admit_share` / T-S3-04 share admission, same-`admission_key` retry path.
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3374-3375`; related `:2344`, `:2802`, `:4673`, `:4675`, `:4676`; accepted plan `docs/gateflow/a0-production-data-model-schema-spec-plan.md:193,261`; design truth `docs/12-technology-stack-and-system-architecture.md:335,337`.
- **输入场景**: A grant reaches its limit (for example `max_admissions=1`, `admissions_used=1`), the first admission is committed, the creation/playback response or the Redis ticket/cache is lost, and the client retries the same capability-token request with the same stable `admissionRequestId`/`admission_key` inside `sessionExpiresAt`.
- **实际分支**: T-S3-04 executes step 4 before step 5. Step 4 (`:3374`) checks `max_admissions IS NOT NULL AND admissions_used >= max_admissions` and denies with `SHARE_ADMISSION_LIMIT_REACHED`; step 5 (`:3375`), which contains the same-key witness lookup, session-validity check and ticket reissue, is never reached.
- **预期行为**: The accepted plan D29 and `share_admission` row (`plan:193,261`) say the same admission key returns the existing admission and reissues the derived ticket without incrementing. `§4.45:2344` and `§7.4:2802` repeat that rule. `docs/12 §9.5` items 3 and 5 (`:335,:337`) say a repeated submission of the same admission returns the original session, and reaching the limit blocks only new admissions while the last admitted session may still play, seek and renew. T-S3-18 (`:4673`) and T-S3-21 (`:4676`) require the same-key reissue before `sessionExpiresAt`.
- **实际行为**: At the limit, the same-key retry is denied as a new admission. The durable admission and session are not reconstructed, even though the session is still valid and the count must not change. The same-key path is unreachable exactly when the last admitted session is the only one that may still be active.
- **直接证据**: The ordered steps at `:3374` and `:3375`; the unconditional limit denial at `:3374`; the same-key replay contract at `:2344`, `:2802`, `:4673`, `:4676`; the accepted-plan rows at `plan:193,261`; the design-truth wording at `docs/12:337`. The test matrix covers same-key retry without a limit (T-S3-18) and limit reached with a last session/new recipient (T-S3-20) but not the combined limit-plus-lost-response/replay case.
- **影响**: A legitimate last admitted recipient cannot recover a lost response, lost Redis ticket or cache loss once the grant limit is reached. The result is a false limit denial and a failure of the advertised reconstruction/count-once recovery path; no double count is created, but the recovery contract is broken. Because the limit is the normal end state of a bounded share, this is not an edge-only path.
- **建议改法和验证点**: Reorder the transaction: (1) perform the revoke/expiry/status/generation checks; (2) look up the existing admission by `(share_grant_id, admission_key)` and handle the valid, expired-session and generation-mismatch cases; (3) only when no admission exists, apply the `max_admissions` limit check; (4) insert the new admission and count. Keep the same-key path unable to increment. Add a test that reaches the limit, loses the response/ticket/cache, retries the same key before and after `sessionExpiresAt`, and asserts one admission, one count, ticket reissue before expiry, `SHARE_SESSION_EXPIRED` after expiry, and no generation change. Verify `SHARE_ADMISSION_LIMIT_REACHED` still applies to a new key at the limit.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### S3-02-未修复-[高]-Ticket reconstruction does not re-check the current recipient membership/tenant despite claiming wrong-tenant protection
- **入口/函数**: `sharing.issue_or_reconstruct_ticket` and `sharing.authorize_media_request` / T-S3-05 reconstruction and media renewal; ORGANIZATION_MEMBER admission.
- **文件(行号)**: `docs/14-production-data-model-and-flyway-schema-spec.md:3383` (reconstruction), `:3373` (admission-time membership check), `:2306` (ORGANIZATION_MEMBER contract), `:2318-2326` (`share_admission` columns), `:2376` (`ADMISSION_GRANTED` witness keys), `:4026-4027` (service contracts).
- **输入场景**: An `ORGANIZATION_MEMBER` recipient is successfully admitted. The recipient's membership is then revoked or suspended, the account is disabled, or the recipient is otherwise in a different tenant/account. Redis or the response is lost, so the client asks for ticket reconstruction/renewal with the same capability token and admission within `sessionExpiresAt`.
- **实际分支**: T-S3-05 step 3 re-reads the admission, the `ADMISSION_GRANTED` witness, the current grant, revocation/code generation, time and subject risk. It requires current status `ACTIVE` or `LOCKED`, matching generations, and unexpired admission/session/grant. It does not acquire S1 ranks 7/8/9, does not re-read `customer_account`, `organization` or `organization_membership`, and does not re-check the recipient's current membership or tenant. The `share_admission` row and the witness carry no recipient/member reference; the witness keys are only generations and expiry. The text nevertheless concludes at `:3383` that a stale admission "cannot bypass ... the wrong-tenant check," but no wrong-tenant check exists in this path.
- **预期行为**: The required contract says current member policy must be validated on renewal/reconstruction; ORGANIZATION_MEMBER requires the authenticated recipient's current active membership (`:2306`). The admission-time wrong-tenant check at `:3373` is not a substitute for a current reconstruction/renewal check. A revoked/suspended membership or a different tenant must fail closed.
- **实际行为**: Within the recorded session window, a previously admitted recipient can reconstruct and renew after losing current membership or moving tenant. The admission-time generation witness cannot detect membership changes because membership is not part of the witness. The claimed wrong-tenant protection is therefore false for reconstruction/renewal.
- **直接证据**: The reconstruction predicate list at `:3383`; the admission-time-only membership check at `:3373`; the ORGANIZATION_MEMBER requirement at `:2306`; the absence of any recipient/member column in `share_admission` at `:2318-2326`; the witness key list at `:2376`; the service descriptions at `:4026-4027`; the unauthorized/no-membership failure codes at `:3373` (`SHARE_WRONG_TENANT`).
- **影响**: A removed organization member retains historical-evidence access until the bounded session expires, and a different tenant can use a reconstructed ticket without a current membership check. This is a security/authorization drift, not merely a documentation wording issue. The TTL bounds the exposure but does not implement the stated policy.
- **建议改法和验证点**: On reconstruction and renewal for `ORGANIZATION_MEMBER`, re-authenticate the recipient and re-read the exact current account/organization/membership predicates under the S1 ranks 7/8/9 advisory locks, exactly as admission does; deny with `SHARE_WRONG_TENANT` or the approved membership code on inactive/suspended/revoked/mismatched facts. If the product deliberately makes an admitted session bearer-only for its short TTL, state that bounded exception and its owner explicitly instead of claiming a wrong-tenant check. Add tests for revocation/suspension/tenant change before reconstruction and before renewal, including lost Redis/cache.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### S3-04-未修复-[中]-A conflicting late recording callback after `VALIDATED` has no possible state transition, contradicting "quarantine"

- **输入场景**: A recording is already terminal `VALIDATED` with its first server facts and original media object. A late/duplicate callback presents the same `recording_id` with a different object version, hash, size, MIME or duration.
- **实际分支**: `§4.40` and `§7.4` say a different object fact "transitions once to `QUARANTINED`" and a conflicting retry "quarantines," but also say `VALIDATED` and `QUARANTINED` are terminal. The guard at `:4001` explicitly rejects a terminal `VALIDATED`/`QUARANTINED` to any other status. Once `VALIDATED`, the proposed transition cannot execute. Step 7 says the conflicting callback is "quarantined and alertable," but there is no recording/event row contract for that post-terminal conflict; recording has no event table, and evidence/Outbox is not specified for this case.
- **预期行为**: The first terminal server facts and original object must remain unchanged, and the late conflict must converge deterministically without fabricating a new recording or overwriting the original. An implementer following the guard will reject the update but has no specified place to persist the conflict; an implementer following the literal quarantine text will violate the terminal rule. The "exact outcome after already VALIDATED conflict" is undefined.
- **直接证据**: Terminal statements and the quarantine sentence at `:2119` and `:2798`; the conflicting instructions at `:3338` and `:3342`; the guard at `:4001`; the evidence-record late-result wording at `:2176`.

- **建议改法和验证点**: Scope the "different facts -> `QUARANTINED`" rule to non-terminal `DECLARED`/`UPLOADED`; state that after `VALIDATED`/`QUARANTINED` a conflicting callback is refused with the stable `RECORDING_IDENTITY_CONFLICT`/`MEDIA_VALIDATION_FAILED` outcome and one durable redacted conflict fact (access/audit/Outbox as appropriate) without changing the recording, media object or original version. Add a positive test for a conflicting callback before terminal and a post-`VALIDATED` test asserting no status/media/version change plus the conflict fact. Do not add a column/table.

## Open Questions

1. **`admissionExpiresAt` has no normative derivation.** The `ADMISSION_GRANTED` witness must contain `admissionExpiresAt` and `sessionExpiresAt` (`:248`, `:2376`, `:3375`), and reconstruction checks both it and the current grant expiry (`:3383`). Only `sessionExpiresAt = min(admitted_at + approved Q22 TTL, grant.expires_at)` is defined. Is `admissionExpiresAt` the grant expiry captured at admission, the same as `sessionExpiresAt`, or a separate approved admission TTL? The answer determines whether reconstruction has a duplicate check or a new approved input. Owner: Security/Sharing; destination: S3 bounded fix and Q22/sharing policy.
2. **Share-creation changed-scope conflict is not detectable from the specified key.** `§2.12` says the same creation action reproduces `share_id` and "a changed scope conflicts" (`:249`), but `share_id` is derived from `{creatorAccountId, ownerOrganizationId, evidenceId, creationRequestId}` and the raw request ID is not stored (`:249`, `:2255`). A retry with the same creation request ID and a changed scope therefore derives a different `share_id`, has no unique loser, and appears to create a second grant. Is a changed scope intended to be a distinct creation (documentation should say so) or a conflict (the derivation/lookup must change)? Owner: Sharing/Backend; destination: S3 fix and Q15/wire contract.
3. **DESIGNATED_MOBILE verification is HMAC comparison only; proof of possession is not defined.** `§2.12`/`§4.44` store only a keyed HMAC of the normalized designated number (`:246`, `:2289`, `:2306`) and T-S3-04 step 2 compares the HMAC (`:3372`). A person who knows the designated number can satisfy this; no OTP or independently verified channel is required. Is knowledge of the designated number sufficient, or must the flow prove possession/verification of that number? Owner: Security/Product/Sharing; destination: Q12/sharing access policy and S3 fix.
4. **`LOCKED` has no recovery/revocation path for non-code verification modes.** `§4.44`/`§7.4` allow `LOCKED → ACTIVE` only through code rotation (`:2308`, `:2801`), which is meaningful only for `EXTRACTION_CODE`; there is no `LOCKED → REVOKED`/`EXPIRED` transition. For `NONE`, `DESIGNATED_MOBILE` and `ORGANIZATION_MEMBER`, a locked grant appears permanently locked and cannot be revoked or persisted expired. Is that intended fail-closed behavior, or is an owner revoke/expiry path required? Owner: Security/Sharing; destination: Q12/sharing policy and S3 state-machine fix.
5. **A lost share-creation response cannot recover the same capability link.** `§2.12` returns the plaintext capability token only once and stores only its digest (`:249`, `:2932`, `:2938`); a retry reproduces `share_id` and returns metadata without the token. Is the intended recovery to create a new grant with a new creation request (and new token), or is a controlled re-issuance policy required? Owner: Product/Security/Sharing; destination: sharing policy/Q22 and S3/API contract.
6. **Transition access-event IDs (`REVOKED`, `CODE_ROTATED`, `EXPIRED`, `EXTENDED`, `LOCKED`) have no exact derivation.** `§2.12` gives exact identities for admission, ticket and playback/seek/renewal/failure (`:247`); `§9.29` only says the transition identity is "derived from the action and grant" (`:3365`). Is that sufficient for same-action replay/conflict determinism, or should the spec fix the exact canonical field set/formula? Owner: Sharing/Backend; destination: S3 fix and Q15.
