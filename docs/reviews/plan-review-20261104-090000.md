### PA14-R4-A-01-未修复-高-Evidence projection reader's `Optional` return cannot carry the required typed unavailable outcome

- **位置**: `docs/gateflow/pa14-sharing-command-service-foundation-plan.md:36` (reader signature and missing-row rule), `:54` (create fail-closed mapping), `:93` (evidence/risk test); `docs/14-production-data-model-and-flyway-schema-spec.md:255` (owner contract).
- **问题类型**: 契约缺失 / 不可直接实施 / 状态机漏洞
- **当前写法**: `ShareableEvidenceProjectionReader.readShareableProjection(DSLContext, UUID)` returns `Optional<ShareableEvidenceProjection>`. The plan assigns `Optional.empty()` to a missing row and simultaneously requires SQL, decoding, or ambiguous-projection failure to be a “typed unavailable result, never empty and never an uncaught 500.”
- **反例/失败场景**: The evidence owner query succeeds but artifact decoding fails, or the result contains an ambiguous duplicate. There are only two `Optional` states. If the implementation returns `empty`, create treats a real dependency failure as a missing row and may return the wrong 403/`FORBIDDEN` outcome; if it throws an ordinary exception, the command boundary can turn it into an undeclared 500; if it invents a third exception type, it is implementing a contract the plan did not name. The same ambiguity occurs when deciding whether the create operation should use 403 `SHARE_ACCESS_POLICY_UNAVAILABLE` or the evidence-specific fail-closed code.
- **为什么有问题**: The plan explicitly separates “missing” from “unavailable,” but the only named API cannot represent both. This is not a naming preference: it decides the operation's public response and whether a dependency fault is retried, disclosed, or logged. The test inventory names “absent/unresolvable reader” but has no assertion for a SQL/decoding/ambiguous failure distinct from missing.
- **直接证据**: Plan lines 36 and 54; `docs/14-production-data-model-and-flyway-schema-spec.md:255` says a missing/not-`SOLIDIFIED` projection fails closed through the owner contract; the frozen create response set has 403, 409, 422, 503, and 500 but no separate evidence-failure code. `CustomerProblemWriter.java` has no typed evidence-reader branch.
- **影响**: Implementation agents must invent the failure channel; a production SQL/decoding failure can become an undeclared 500 or be silently treated as a missing resource, and the 403 mapping cannot be reviewed or tested exactly.
- **建议改法和验证点**: Replace the `Optional` return with an explicit sealed read result such as `Found(ShareableEvidenceProjection)`, `Missing()`, and `Unavailable(ShareCommandException.Code)` (or name a typed unchecked exception with an exact handler), and freeze which result maps to create 403/503/500. Add a `CustomerShareCommandsIT` assertion for a valid row with a decoding/SQL/ambiguous failure, proving it is not empty and not an uncaught 500.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PA14-R4-A-02-未修复-高-The access-event and Outbox `event_type` registries are not separated, and V009 rejects the only named `SHARE_*` values

- **位置**: `docs/gateflow/pa14-sharing-command-service-foundation-plan.md:16` (registry/event types), `:62` (“registered event types … exactly as above”), `:91` and `:97`; `backend/src/main/resources/db/migration/V009__sharing.sql:117-118`; `docs/14-production-data-model-and-flyway-schema-spec.md:251` and `:2394`.
- **问题类型**: 契约缺失 / 数据模型冲突 / 不可直接实施
- **当前写法**: The sharing registry names `SHARE_CREATED`, `SHARE_REVOKED`, and `SHARE_CODE_ROTATED`. The later access-event paragraph says to keep the “registered event types … exactly as above” but never gives a separate `share_access_event.event_type` value. The plan also says create has no access event and that revoke/rotate append one.
- **反例/失败场景**: An implementation follows the only named registry for the revoke access-event row and inserts `event_type = 'SHARE_REVOKED'` or `'SHARE_CODE_ROTATED'`. V009's check allows only `REVOKED` and `CODE_ROTATED` (plus the other public-share event types), so the transition fails at the database constraint and rolls back instead of producing the required event. V009 is frozen and the plan forbids a migration/grant change, so a guessed value is not recoverable at implementation time.
- **直接证据**: Plan lines 16 and 62; V009 lines 117–118; docs/14 §2.12 line 251 and §4.46 line 2394 list access types `REVOKED` and `CODE_ROTATED`, while the user-confirmed Outbox registry uses `SHARE_CREATED`/`SHARE_REVOKED`/`SHARE_CODE_ROTATED`.
- **影响**: A required transition can fail on every call with a check-constraint error, or implementation can silently use one registry for the wrong table; this is a direct data-model compatibility failure, not a test-style issue.
- **建议改法和验证点**: State two explicit registries: Outbox `event_type` = `SHARE_CREATED`, `SHARE_REVOKED`, `SHARE_CODE_ROTATED`; access-event `event_type` = `REVOKED` for revoke and `CODE_ROTATED` for rotate (and no create access event). Add assertions to `revokeWrites...` and `rotateWrites...` for the exact access-event `event_type`, `event_domain = SHARE_ACCESS`, and Outbox event type/dedupe values.
