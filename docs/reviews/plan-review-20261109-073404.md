## Findings

### 01-未修复-严重-Replay cannot return the first credential under PA18/PA19 semantics

- **位置**: Plan §7 ("same authorization request replay returns repository's first committed credential, not a new token/event"), §10 ("same request replay returns byte-identical first credential", "no second signer invocation on replay if repository replay path returns stored credential"), §1 success signal; Control:23; public-share OpenAPI 200 description.
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施 / 测试缺口
- **当前写法**: "The provider must be deterministic for identical request+key+clock claim inputs; same authorization request replay returns repository's first committed credential, not a new token/event." The plan treats the repository replay path as if it returned a stored credential and only hedges with "if".
- **反例/失败场景**: First call at T1 issues token T1 with `issuedAt=notBefore=T1`; the access event is inserted with `credentialExpiresAt` but no credential. Second call at T2 re-runs `authoritative`, gets the prior SUCCESS event, then unconditionally calls `issueOrReplay` again. The authority signs a fresh payload with `issuedAt=notBefore=T2`; the token bytes differ. The event insert returns `REUSED_IDENTICAL` if the expiry/fingerprint are unchanged, and the service returns the **new** token with the **old** durable expiry. A frozen-clock test or a fixture cache can hide this; production cannot. Restart makes an in-memory cache useless. If the implementation instead stores the credential in the access event to make replay byte-identical, it violates the existing "credential never enters event" invariant and the plan's own no-secret rule.
- **为什么有问题**: PA18's durable record does not contain the credential, and the plan explicitly preserves that ordering/transaction boundary. The `MediaAuthorizationCredentialRequest` has no prior-credential field, and `insertAccessEvent` returns an `AccessEventRow`, not an `Issued`. "Deterministic for identical request+key+clock claim inputs" is not the same as production determinism because the clock is an input that advances. The public OpenAPI says "replays the first issued credential", so returning a new token violates a frozen contract. The goal's "first committed credential result" (Control:23) is therefore not achievable with the proposed design.
- **直接证据**:
  - `DefaultShareMediaAuthorizationService.java:69-76` calls `credentials.issueOrReplay(...)` on every authorization, including the replay branch.
  - `DefaultShareMediaAuthorizationService.java:94-100` inserts the event and returns `issued.credential()`; the durable payload (`87-93`) contains `credentialExpiresAt`, not the credential.
  - `DefaultShareMediaAuthorizationService.java:171-179` returns a `Decision` carrying `priorSuccess` (`AccessEventRow`), but the provider call is not skipped.
  - `ShareAdmissionRepository.java:60-64` defines `AccessEventRow`/`AccessEventInsert` with no credential field.
  - `JooqShareAdmissionRepository.java:135-142` inserts `payload_redacted`/`payload_sha256` and returns the first row; no credential.
  - `ShareAdmissionServiceTests.java:501-535` asserts the provider is invoked twice (`f.issued.hasSize(2)`) and the event payload `doesNotContain("credential-private")`; `388-392` asserts `second == first` only because the fixture provider returns a constant/`computeIfAbsent` value (`654-697`).
  - Public contract: `api/openapi/onecall-v1.openapi.yaml:3880-3892` ("same authorizationRequestId with the same purpose replays the first issued credential").
- **影响**: The implementation agent cannot satisfy both the goal and the existing durable/no-secret invariants. It must either violate the public replay contract, add a forbidden credential store, or rely on a frozen clock/test fixture that masks production behavior. Reviewers cannot accept a green replay test as proof.
- **建议改法和验证点**: Choose and state one of: (a) re-confirm the goal/OpenAPI wording to "replay returns the same durable access fact; a fresh but equivalent credential may be issued" and stop claiming byte-identical replay (requires owner/contract change, outside this plan's write scope); (b) authorize a durable, non-secret replay anchor (e.g., a credential store) — forbidden by the current no-schema/no-secret boundary; or (c) define deterministic issuance from a stable request value with no TTL/Q22 invention and explicitly accept the semantics. In all cases add a replay test with an **advancing** clock (not only a fixed-clock repeatability test), and assert the event count, provider invocation count, and returned-token equality separately.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 严重

### 02-未修复-严重-No authoritative playback window exists; the plan's facts bridge and fallback are not implementable

- **位置**: Plan §3 (line 40: "already-authorized valid window"), §7 ("Derive the authorized window from the existing authoritative admission/share snapshot already returned in `Decision`"; "call ... `decision.witness().evidenceId()`"), §12 blocking open question; Control:21-24,29; `MediaAuthorizationRequest.java`; `ShareAdmissionRepository.java`; `V009__sharing.sql`; `MediaGatewayFilter.java`.
- **问题类型**: 契约缺失 / 动机不成立 / 目标漂移 / open question 未收敛 / 不可直接实施
- **当前写法**: The plan asserts the window is an already-authorized sharing fact and instructs the implementation to "trace its existing field/source"; if absent, "extend only the relevant internal witness/snapshot construction" and "if no authoritative existing window fact can be located, stop implementation and ask the owner". It also writes `decision.witness().evidenceId()`, which does not exist.
- **反例/失败场景**: An implementation agent follows §7 literally: `decision.witness().evidenceId()` does not compile. It then searches the witness payload, grant snapshot and schema and finds no window. It tries the fallback: the `AdmissionWitness` record is in `ShareAdmissionRepository.java` and the witness payload is built/validated in `DefaultShareAdmissionService.java`/`expectedWitnessKeys`; neither file is in the 13-path allowlist. Adding a window key would change the witness payload shape/hash and the exact-key validation for existing admission rows. The only usable duration/object facts are in `ResolvedMediaObject`, and the only window the data plane supports is the full object `[0, duration]` because the gateway rejects any other window.
- **为什么有问题**: The plan's core "authorized facts" are not present in the named sources, and the Control says "No blocking open question remains" (Control:29) while the plan §12 declares one. The fallback cannot be executed within the allowlist and would cross the sharing/evidence ownership boundary by reconstructing a window from evidence metadata rather than an authorization fact. The plan is therefore not a code-generation-ready handoff; it requires an owner decision it has not obtained.
- **直接证据**:
  - `MediaAuthorizationRequest.java:3-8`: record contains only `authorizationRequestId` and `purpose`; no window/duration.
  - `ShareAdmissionRepository.java:55-59`: `AdmissionWitness` contains `eventId, payload, payloadSha256, verificationMode, codeGeneration, revocationGeneration, grantExpiresAt, admissionExpiresAt, sessionExpiresAt, recipientAccountId, recipientOrganizationId`; no `evidenceId` and no window.
  - `DefaultShareMediaAuthorizationService.java:124-136`: witness payload keys are an exact set (`verificationMode`, generations, three expiries, optional recipient IDs); no window.
  - `ShareAdmissionRepository.java:34-40`: `GrantSnapshot` has `evidenceId` and `contentSnapshot`, but no playback window.
  - `V009__sharing.sql` `evidence_share_grant` columns: no window/start/end column; `content_snapshot` shape checks only `content`, `verification`, `creation`.
  - `MediaGatewayFilter.java:78-81`: the gateway accepts only `startInclusive == Duration.ZERO` and `endExclusive == Duration.ofSeconds(media.durationSeconds())`; this is the effective window authority.
  - `ShareableEvidenceProjection.java:20-21` exposes `validatedDurationSeconds`, not a window.
  - Control:29: "No blocking open question remains"; plan §12: "Blocking open question for implementation".
- **影响**: Implementation must invent a window (goal drift/security risk) or stop (no code). If it derives `[0, duration]` from evidence, that is a different authorization claim than the plan describes and must be stated as the sharing-owned policy; if it adds a witness/snapshot field, it exceeds the allowlist and changes hashed admission facts. The plan cannot be accepted as codegen-ready.
- **建议改法和验证点**: Use the evidence-owned duration and `GrantSnapshot.evidenceId()` to define the full-object window `[Duration.ZERO, Duration.ofSeconds(resolved.durationSeconds()))`, require a `Found` result with non-null positive duration, and cite `MediaGatewayFilter` as the reason only the full window is valid. Remove the false `witness().evidenceId()` step and the unverified "sharing snapshot window" claim. If a sub-window is genuinely required, stop and request a new goal confirmation plus the necessary witness/schema changes (outside this allowlist). Update §12 to resolve the question explicitly, not defer a Control-closed question.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 严重

### 05-未修复-高-Binary profile is not code-generation-ready at the byte level

- **位置**: Plan §4 (wire form, payload field order, length prefixes, timestamp precision, parser bounds, error mapping); §10 "canonical known-answer bytes/MAC".
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: "Payload is a canonical binary sequence ... then fixed-order fields, each length-prefixed by unsigned 16-bit big-endian byte length (UUIDs and integer/time values have their specified fixed binary width and are not variable text) ... issuedAt, notBefore, expiresAt signed 64-bit epoch microseconds UTC ... Reject values not exactly representable at the encoded precision; do not silently truncate." The plan does not state whether the u16 prefix applies to every field or only text fields, nor the UUID byte order.
- **反例/失败场景**: Agent A writes `0x0010 + uuid16` for a grant UUID; Agent B writes raw 16 bytes. Both "follow" the plan but produce different known-answer vectors. A `Clock.systemUTC()` `Instant` has nanosecond precision while the encoding is microseconds; literal "reject non-representable" makes every normal issuance fail, while "truncate" is not stated. `repository.now()`/`bound()` are PostgreSQL microsecond values, but `issuedAt`/`notBefore` come from the injected `Clock`; the verifier reconstructs micros and the PA19 claim equality (`ShareAdmissionServiceTests` style) can differ at the nanosecond. The `Duration` window is nanoseconds while `durationSeconds` is integer seconds; the plan's "end ≤ duration" must be checked after the nanos/seconds conversion. The parser's maximum payload/structure bound is only implied by the 2048-character credential bound; the plan does not pin field-length overflow, truncated UUIDs, duplicate length prefixes, or trailing bytes as explicit `Invalid` cases.
- **为什么有问题**: The token is the security boundary; an ambiguous encoding cannot be independently implemented or reviewed. A "known-answer" test authored by the same agent that chose the encoding proves circularity, not interoperability. The timestamp precision mismatch is a concrete fail-closed risk: the plan says reject, while the existing PA18 code truncates provider expiry to `MICROS` (`DefaultShareMediaAuthorizationService.java:79`) and the verifier/clock can produce nanos.
- **直接证据**: Plan §4 text; `MediaPlaybackService.validShape` (duration/window comparisons, `:77-88`); `DefaultShareMediaAuthorizationService.java:79` (`truncatedTo(ChronoUnit.MICROS)`); `MediaPlaybackConfiguration.java:24` (`Clock.systemUTC()`); `VerifiedMediaClaim` record types; `ResolvedMediaObject.durationSeconds` is `Integer`.
- **影响**: Implementation inventiveness; a micro/nano mismatch can make valid issuance unavailable or valid tokens invalid; the known-answer vector and the review of the wire profile are not independently reproducible; parser edge cases may be missed.
- **建议改法和验证点**: Pin all of: whether every field has the u16 prefix; UUID encoding (e.g., most-significant then least-significant 64-bit big-endian, with `16` length if prefixed); fixed-width int/long/time fields with no prefix; exact instant normalization (truncate to microseconds at issuance and verification, or reject with a defined error and a test); field maximum lengths/payload maximum; exact handling of trailing bytes, truncated fixed-width fields, zero-length text, duplicate/invalid UTF-8 and unknown enum; and a fully independent hex known-answer vector not derived from the implementation.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 06-未修复-中-Legacy `issue(MediaCredentialRequest)` is ignored, but the same bean must implement it

- **位置**: Plan §3/§6 ("Add `HmacMediaPlaybackCredentialAuthority` implementing existing `ShareMediaCredentialProvider`"; "its issue path signs the authorized claim input"), §10 tests; `ShareMediaCredentialProvider.java`; `DefaultShareAdmissionService.java`.

- **当前写法**: The plan focuses on `issueOrReplay` and the verifier, describing "two independently invoked public seams", but `ShareMediaCredentialProvider` is a functional interface whose abstract method is `issue(MediaCredentialRequest)`; the authority must implement it.

The legacy method's request shape makes a valid C10 claim impossible; ignoring it leaves either a silent admission regression or a security-relevant claim-less token. The existing `DefaultShareAdmissionService` is not in the allowlist, so any behavior change there is out of scope.
- **直接证据**: `ShareMediaCredentialProvider.java:7-18` (abstract `issue`; `MediaCredentialRequest` fields); `DefaultShareAdmissionService.java:289-302` (calls `issue`, validates the credential, writes the ticket/view); `ShareAdmissionPersistenceConfiguration.java:100-101` (current fallback only implements `issue`); plan §6.
- **影响**: Implementation ambiguity; possible invalid token issuance or admission path failure; the integration test plan does not cover the legacy path; a future operator may enable a bean that unexpectedly changes admission behavior.
- **建议改法和验证点**: Explicitly define `issue` as `Unavailable` (preserve today's default-deny admission ticket behavior) and test that a valid key provider does not change the admission ticket path, or implement `issue` only after extending its request with the same authorized facts and proving the claim through PA19. State that the 13-path allowlist cannot change `DefaultShareAdmissionService`; if the admission ticket path is out of scope, say so.

- **严重程度（低/中/高/严重）**: 中

### 07-未修复-中-PA19 window enforcement is overstated and the real-authority PA19/PA20 path is untested

- **位置**: Plan §1/§8 ("PA19 still independently checks ... requested window"; "compares evidence ID/object ID/duration/window against existing evidence resolver and request"), §10 (`MediaPlaybackServiceTests` "changed window ... deny with zero opens"; "end-to-end issuer→verifier→PA19/PA20 success"); `MediaPlaybackService.java`; `MediaGatewayFilter.java`; `MediaPlaybackIT.java`.
- **问题类型**: 测试缺口 / 不可直接实施 / 状态机漏洞
- **当前写法**: The plan claims PA19 compares the window against the request and that a changed-window credential reaches zero opens in `MediaPlaybackServiceTests`, and claims an end-to-end issuer→verifier→PA19/PA20 proof.
- **反例/失败场景**: The P3 request has no window. `MediaPlaybackService.validShape` accepts any `0 <= start < end <= duration`; a correctly signed claim with window `[1,2]` passes PA19 shape, audience, purpose, time, state, evidence/object/duration checks and calls `ControlledMediaReader.open` with `[1,2]`. Only `MediaGatewayFilter` rejects `start != 0` or `end != duration` (403) before `transfer`. Therefore a "changed window" that remains inside the duration does **not** deny with zero opens at PA19; the planned `MediaPlaybackServiceTests` assertion is false for that case. The real authority is never wired into `MediaPlaybackService`/`MediaPlaybackIT` in the listed tests: `MediaPlaybackIT` uses a fixture verifier and `MediaPlaybackServiceTests` uses a lambda verifier, while the authority tests only round-trip the authority. The gateway IT is not in the allowlist.
- **为什么有问题**: The plan's security claim conflates MAC binding with authorization enforcement. The full-window rule lives in the gateway (PA20), not PA19, and the plan's test file ownership does not include a gateway test. The newly built authority could be green in isolation while never being exercised by PA19/PA20. A sub-window token could be issued and then 403 at the gateway, which is an avoidable mismatch.
- **直接证据**: `MediaPlaybackService.java:44-66` (checks and `reader.open(scope)`), `:77-88` (`validShape` allows sub-windows); `MediaGatewayFilter.java:78-81` (full window only); `MediaPlaybackIT.java:444-455` (fixture `ShareMediaCredentialProvider`, fixture verifier at `:511-516`); `MediaPlaybackServiceTests` lambda verifier; plan §10 list does not add a real-authority PA19/PA20 test.

## Final conclusion

**fail**

The plan is detailed, the crypto direction (HMAC-SHA-256/256-bit, active/verify-only overlap, constant-time compare, 1-2048 bounds, redaction) is plausible, and it does not add COS/KMS/Q22 work. However, it is not code-generation-ready and is not internally consistent with the existing PA18/PA19/PA20 source and gates:

- The replay success signal contradicts PA18's durable (credential-free) event semantics and the public OpenAPI replay wording; the plan's own fresh-clock determinism makes the first credential unreproducible.
- The "authoritative playback window" does not exist in the P3 request, admission witness, grant snapshot or schema; the plan cites a non-existent `witness().evidenceId()` and its fallback requires files outside the allowlist, while the Control says no blocking open question remains.
- The new production/test files collide with exact-file architecture tests and the CI's hardcoded source=CI=XML inventory, both of which the plan forbids editing.
- The exact binary profile and the key-provider/authority wiring are under-specified, forcing implementation inventiveness in the security-critical path.

Required before a plan `pass`: resolve findings 01 and 02 with the owner, update the replay/public-contract position, fix the fact accessor and window source, add the architecture and CI paths to scope (or relocate types and re-scope the success signal), pin the wire profile and parser bounds with independent vectors, and state the legacy `issue` behavior and the exact Spring visibility/ambiguity mapping.
