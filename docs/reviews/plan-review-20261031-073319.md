## Material Findings

### 01-未修复-中-same-state 终态 generation 变更的测试预期未分类

- **位置**: plan §4.1 lifecycle/action matrix (lines 222–236) and §7.4 lifecycle method (line 362: "same-state cases are classified by action/no-op"); design §4.44 line 2324 ("increments `revocation_generation` by one exactly once when observed/persisted") and §7.4 line 2817; design §10.22 line 4045 structural guard.
- **问题类型**: 契约缺失 / 测试缺口 / 状态机漏洞
- **当前写法**: Plan requires the S2 lifecycle method to iterate all 16 status pairs, classify same-state cases "by action/no-op", and separately document same-state revision-only behavior (`revision>=1`) without confusing it with action revision rules. Named actions cover ACTIVE→ACTIVE count/extension/rotation, ACTIVE→LOCKED, revoke, expiry persist and LOCKED→ACTIVE rotation. Plan §4.1 also says: do not invent a blanket ban on same-status no-op/revision-only writes; terminality means no change to another status, not a forbidden-terminal-row-shape check; revoke/expiry generation +1 is "checked with their status edges".
- **反例/失败场景**: After a grant is already `EXPIRED`, an owner UPDATE sets `revocation_generation = old+1`, `revision = old+1`, status unchanged. This is not a named action and not a pure no-op (a generation actually changes). The structural guard as specified (immutable columns unchanged, generation not decreased, terminal status not changed to another status, revision +1 when generations change) **accepts** this row. An implementer writing `v009GrantLifecycleRevisionMatrixAndImmutabilityBackstops` must choose an expected outcome: (a) assert success and treat generation inflation as structurally-legal/service-forbidden, or (b) assert `P0001` — which requires inventing a terminal-row-shape rule the plan explicitly forbids. The phrase "classified by action/no-op" does not cover this third class.
- **为什么有问题**: Design prose says expiry increments `revocation_generation` "exactly once when observed/persisted", which reads as forbidding a second increment on the same already-persisted expiry. The structural guard (design §10.22 and plan §4.1) does not implement that once-only semantic; it only forbids decreases and terminal→other status. The test oracle is therefore underspecified exactly where design prose and structural DDL diverge. An implementation agent cannot write the required S2 witness without either inventing a rule or silently blessing generation inflation.
- **直接证据**:
  - plan `:236` "Do not invent a blanket ban on same-status no-op/revision-only writes… Terminality means no change to another status, not a new forbidden-terminal-row-shape check."
  - plan `:229` expiry action: "revocation_generation +1 once; revision +1" — once, on the directed edge only.
  - plan `:234` "Revoke/expiry generation +1 and lock generation unchanged are checked with their status edges."
  - plan `:362` "same-state cases are classified by action/no-op… Same-state revision-only behavior and revision>=1 check are separately documented, not confused with action revision rules."
  - design `:2324` "Expiry sets `EXPIRED` and increments `revocation_generation` by one exactly once when observed/persisted."
  - design `:4045` guard rejects generation **decrease** and terminal→other status; it does not reject generation increase on a same-state terminal write.
- **影响**: Implementation agent runs off / generates a wrong test oracle; S2 either invents a DDL rule outside the frozen contract or asserts that terminal generation inflation is legal, contradicting design prose; later service implementers inherit an ambiguous DB contract; review cannot accept S2 evidence without knowing which classification was intended.
- **建议改法和验证点**: Before S2 implementation, controller/design owner must pin one explicit classification for same-state writes that change generation (and similarly for mixed-field mutations, Finding 2). Recommended: treat same-state generation-changing writes as structurally-legal but not owner actions — the S2 method asserts the structural success **and** documents the once-only service contract as residual, matching plan §4.1's refusal to invent a terminal-row-shape ban. Alternative: design owner amends §10.22/§4.1 with an explicit "generation increments only on named directed edges" predicate and plan adds the matching negative witness. Verification: S2 method name/fixture states the chosen expected SQLSTATE/success for `EXPIRED→EXPIRED + revocation_generation+1 + revision+1` and for `REVOKED→REVOKED + revocation_generation+1 + revision+1`.
- **修复风险（低/中/高）**: 低 — no DDL/security/migration change if the structural-legal/service-forbidden reading is adopted; only test-oracle wording and one classified witness.
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-低-单条 UPDATE 混合多个 owner action 时 guard 分类未写明

- **位置**: plan §4.1 action matrix (lines 222–234) "Required action/state witnesses"; design §10.22 structural guard; design §7.4 "Every transition is a conditional revision update".
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: The matrix lists atomic owner actions (count update, extension, rotation, lock, revoke, expiry persist). Guard rules are structural: immutable columns, non-decreasing expiry/generation, legal status edges, revision +1 when mutable fields change, rotation salt/hash coupling, extension only while ACTIVE and old expiry future.
- **反例/失败场景**: A single UPDATE on an ACTIVE grant simultaneously increases `expires_at` and sets `status='LOCKED'` (or sets `status='REVOKED'` and increases `revocation_generation` and also rotates salt/hash). The action matrix says lock leaves expiry unchanged and revoke does not extend expiry; the structural guard as written does not obviously freeze "other action fields" when a status edge fires. Depending on whether the implementer reads "checked with their status edges" as also freezing the non-actor fields, the mixed mutation may pass. Tests that only witness the named atomic actions will not notice.
- **为什么有问题**: The plan positions the guard as a structural backstop and the action matrix as required witnesses, not an exhaustive mutation classifier. That is design-aligned (§10.22 is structural), but the S2 method claims "All legal/illegal edges, action deltas" — an implementer may either over-enforce (invent mixed-action bans) or under-test (skip the case). Combined with Finding 1, the same-state/mixed space of legal UPDATE shapes is not closed.
- **直接证据**:
  - plan `:222–230` action matrix rows freeze specific fields per action (e.g. lock: "generations/count/expiry unchanged").
  - plan `:234` "Enforce revision +1 when expiry, code values/generations or admissions_used actually change, as mutable owner transitions require."
  - design `:4045` lists structural restraints only; no "single action per UPDATE" rule.
  - design `:2817` describes transitions as service-level actions, not SQL-statement shape constraints.
- **影响**: S2 witness set may miss a mixed UPDATE that the structural guard accepts; later services could accidentally combine transitions in one statement; review of S2 evidence cannot tell whether the omission was intentional.
- **建议改法和验证点**: Either (a) add one S2 probe that submits a mixed extension+lock (and/or revoke+rotation) UPDATE and states the chosen outcome (structural accept documented as service-forbidden, or explicit rejection if design owner adds a predicate), or (b) explicitly record in plan §7.4 that mixed-action single-statement shapes are residual service discipline and are not DB-enforced. Verification: the chosen outcome appears in the S2 method or in the residual-risk table with owner = sharing service.
- **修复风险（低/中/高）**: 低 — test wording plus at most one probe; no DDL change under option (a-accept) or (b).
- **严重程度（低/中/高/严重）**: 低

## Non-Blocking Observations / Open Questions

1. **Admission guard does not recheck code/revocation generation.** Design §10.22 and plan §4.2 match: the BEFORE INSERT guard checks existence/mode/ACTIVE/window/limit/next-number only. Plan §7.5 case 4 correctly notes "guard alone cannot know stale verified input" and requires the SQL harness to refuse a pre-rotation expected generation before insert. Residual service responsibility, already classified in plan §10. Not a plan defect.
2. **Event/admission grant-FK pair consistency.** Two independent nullable/non-null ID FKs do not prove that an admission belongs to the event's grant. Plan §1 item 5 and §10 residual row 1 classify this as later service/typed semantic validation. Design-aligned. Not a plan defect.
3. **CHECK UNKNOWN / JSON presence-only.** Plan §7.3 explicitly preserves UNKNOWN witnesses (missing nested evidence/creator/mode/hash; ADMISSION_GRANTED presence-only generations) and forbids DDL strengthening in this gate. Correct scope fence.
4. **PostgreSQL deparse spelling.** Plan requires a focused PG16 run to freeze literal deparse strings before the map is asserted. Honest about not guessing deparse online. Residual risk already owned by Backend/Database/QA (plan §10).
5. **Controller dirty state / Windows `.git` pointer diagnostics.** Already recorded in Goal Confirmation lines 26–27. Not introduced by this plan.
6. **Prior PA8 same-state revision policy.** Existing V008 tests accept same-state revision-only writes (e.g. recording `revision=7`, evidence `revision=9`). PA9 plan deliberately retains that baseline for the grant. Consistent; Finding 1 is only about generation-changing same-state writes on terminal grants.

## Final Plan Review Conclusion
