## Adversarial trace of the four methods

### 1. `mutableHeadsEnforceLifecycleRevisionAndNamedChecks` (`:1086`)

- **Lifecycle/defaults.** `assertSixTableDefaultsAndConditionalRevisions` seeds one
  method-local row per table with generated UUIDs, commits the parent
  `customer_account`/`organization` via the owning runtime role, then for every child
  asserts the column defaults (`status`, `revision`, `created_at`, `updated_at`, …)
  materialize exactly as frozen in V002 and as counted by the S1 inventory
  (`4/2/2/4/2/2 = 16`). A valid `revision = revision + 1` UPDATE through the granted
  column set succeeds; a stale `revision` produces a zero-row update, which is asserted
  rather than ignored. No method key is shared across tests, so container-level
  pollution cannot satisfy or defeat these counts.
- **34 CHECK probes.** Three lists (`customerProbes` `:1955`, `organizationProbes`
  `:2014`, `employeeProbes` `:2040`) contain 18 + 8 + 8 = 34 `CheckProbe` records.
  Completeness is asserted with
  `hasSize(34).containsExactlyInAnyOrderElementsOf(expectedConstraints)` where
  `expectedConstraints` is derived from the S1-frozen `V002_CHECK_DEF_MAP` keys
  (`:2098-2103`). Each probe is a single-violation insert/update (I re-derived every
  probe against V002's predicate conjunctions; none double-violates a second named
  check on the same statement), executed under the owning runtime role through
  `expectSqlFailure`, which asserts SQLSTATE `23514` and the exact constraint name
  substring. This closes the S1 plan-review residual F-PA2-PR-01's behavioral half:
  the S1 inventory freezes the exact `pg_get_constraintdef` text of all 34, and this
  method proves each named check actually fires on a live catalog.
- **FK.** Missing-parent inserts into `auth_identity`, `identity_profile`,
  `organization_membership` and parent `DELETE`s are each asserted to raise `23503`
  with the exact FK constraint name; parent rows are method-local and are removed in
  FK-safe order.
- **No id defaults/sequences.** `assertNoIdDefaultsOrSequences` queries
  `pg_attrdef`/`pg_get_serial_sequence` for all six `id` columns and asserts empty.

### 2. `localImmutabilityGuardsRejectRelationAndRotationChanges` (`:1094`)

- Under `customer_iam_owner` / `organization_access_owner` / `operations_iam_owner`,
  every immutability-guarded column (`id`, `created_at`, `account_id`, `provider`,
  `provider_scope`, `organization_id`, `login_name_hmac`, `auth_issuer`,
  `auth_subject_hmac`) is UPDATEd and asserted to raise `P0001` with the stable
  per-table code (`CUSTOMER_ACCOUNT_IMMUTABLE`, `AUTH_IDENTITY_IMMUTABLE`,
  `IDENTITY_PROFILE_IMMUTABLE`, `ORGANIZATION_IMMUTABLE`, `MEMBERSHIP_IMMUTABLE`,
  `EMPLOYEE_ACCOUNT_IMMUTABLE`). These codes and the guard predicates
  (`V002:177-205, 268-286, 328-333`) match.
- Auth rotation is tested against the exact V002 guard conjunction
  (`V002:196-204`): a ciphertext-only or hmac-only change is rejected; a simultaneous
  ciphertext+hmac change with `key_version = OLD.key_version + 1` is accepted; a
  simultaneous change with a non-incrementing `key_version` is rejected. This is the
  precise production predicate, not a simplified approximation.
- Runtime-role `42501` probes UPDATE exactly the guarded columns that V002 does **not**
  grant (`V002:244, 248, 251-252, 311, 348`) and are asserted denied; a sibling UPDATE
  of a granted mutable column (`display_name`, `status`, `revision`, `updated_at`,
  …) is asserted to succeed. The pair proves column-level (not merely table-level)
  denial. `switchLocalRole` (`:1611`) does `RESET ROLE` then `SET LOCAL ROLE`, so the
  role GUC is transaction-scoped and cannot leak past the enclosing savepoint/rollback
  even on an exception path; every helper that switches roles either resets inside the
  same savepoint or is followed by an explicit reset before the next probe.

### 3. `identityCollisionAndMembershipRevokeRegrantSemantics` (`:1099`)

- Same `(provider, provider_scope, provider_subject_hmac)` under the same
  `account_id` inserts as `IDEMPOTENT` (read-after-failure classification via
  `classifyIdentityInsert`); the same tuple under a different `account_id` is
  `IDENTITY_CONFLICT`. `identity_profile.account_id` and
  `employee_account.login_name_hmac` / `(auth_issuer, auth_subject_hmac)` uniqueness
  are each probed with a second conflicting insert and asserted `23505` on the exact
  unique index/constraint name.
- Membership: a second live row for the same `(organization_id, account_id)` while
  `status <> 'REVOKED'` is rejected by the partial unique index
  `uq_membership_live` (`V002:113`); revoking the first row and inserting a new
  `ACTIVE` row succeeds (regrant); re-activating the revoked row while a live row
  exists is rejected (revival conflict); multiple revoked rows for the same pair are
  allowed. This matches the frozen partial-index semantics and the plan §8.3
  revoke-regrant requirements, and correctly treats `uq_membership_live` as a
  `CREATE UNIQUE INDEX ... WHERE status <> 'REVOKED'` (not a table constraint),
  consistent with the S1 evidence correction.

### 4. `concurrentIdentityAndMembershipLiveCollisionsHaveOneWinner` (`:1104`)

Four sub-scenarios (identity commit-race, identity rollback-race, membership
commit-race, membership rollback-race), each on two independent JDBC connections:

- `configureBlockedWriter` (`:2659`) sets `SET LOCAL statement_timeout = 20000`,
  an `application_name`, then `SET LOCAL ROLE` — bounded liveness and identifiable
  backends.
- `awaitBlockedBackend` (`:1275`) polls `pg_stat_activity` for
  `state = 'active' AND wait_event_type = 'Lock'` under the scenario's
  `application_name` for at most 15 s and fails closed (does not sleep past the bound
  or assert on a bare sleep). The blocked writer is waiting on the same unique key's
  speculative-insert lock, which is exactly the contention the contract cares about.
- Commit-race: the winner commits first; the loser's insert surfaces `23505` on the
  exact unique name; the loser rolls back to a savepoint and reads the surviving row,
  asserting exactly one committed row and the winner's identity.
- Rollback-race: the winner rolls back; the loser then succeeds; exactly one row
  remains and it is the loser's.
- `Future.get` is bounded by `awaitFuture` (30 s); statement_timeout is 20 s; the
  `pg_stat_activity` wait is 15 s. No scenario can hang the suite past a hard bound.
- `cleanupCommittedRaceRows` (`:2700`) runs from every race's `finally` in FK-safe
  order (membership → auth_identity → identity_profile → employee → organization →
  customer_account), each DELETE followed by a zero-residue `count(*) = 0` assertion
  for that method's UUIDs. An exception anywhere (including a mid-race assertion
  failure) still executes the cleanup; a failure to clean is itself a test failure, so
  orphan committed rows cannot silently pollute later methods.

## Special-focus decision: savepoint-scoped constraint isolation

### The author's reported behavior

During the first internal container calibration the author observed PostgreSQL
reporting `ck_identity_profile_state_shape` (not `ck_identity_profile_status`) for an
insert with `real_name_status = 'BAD'`. The helper
`expectProfileStatusViolationWithIsolatedConstraint` (`:2121-2150`) therefore:

1. opens a savepoint;
2. `switchLocalRole` to `customer_iam_owner`;
3. `ALTER TABLE customer_iam.identity_profile DROP CONSTRAINT ck_identity_profile_state_shape`;
4. executes the probe insert with `real_name_status = 'BAD'`;
5. asserts SQLSTATE `23514` and the message contains `ck_identity_profile_status`;
6. in `finally`, `connection.rollback(savepoint)`;
7. after the savepoint, asserts `pg_constraint` still contains
   `ck_identity_profile_status` and `ck_identity_profile_state_shape` (count = 2);
8. `switchLocalRole` back to `customer_iam_role`.

The evidence artifact discloses this as deviation #1 and the controller's `S2
implementation` control row explicitly requires this review to decide, from first
principles, whether it is valid behavior evidence or test manipulation.

### First-principles and live-catalog resolution

I treated "a passing test on an altered catalog is not automatically acceptable" as
the governing standard and tested the alternative explanations rather than accepting
the author's framing.

1. **The author's empirical premise is true.** On the unmodified live V002 catalog
   (disposable container `s2-review-probe`, PostgreSQL 16.15, since removed), an
   insert of `real_name_status = 'BAD'` raises `23514` with the message naming
   `ck_identity_profile_state_shape`, not `ck_identity_profile_status`. `pg_constraint`
   shows `ck_identity_profile_status` has the lower OID (16526 vs 16531), so this is
   **not** a creation-order artifact that would flip under a different migration
   ordering; it is PostgreSQL 16's CHECK evaluation/report order for this table.
2. **The exact name is mathematically unreachable on the unmodified catalog.**
   `ck_identity_profile_status` is `real_name_status IN ('UNVERIFIED','VERIFIED')`
   (`V002:63`). `ck_identity_profile_state_shape` (`V002:68-74`) is a disjunction
   whose two branches both require `real_name_status IN ('UNVERIFIED','VERIFIED')`.
   Therefore **every** value that violates the status check also falsifies
   state_shape's guard, and PostgreSQL 16.15 reports state_shape first. No insert
   value can produce the exact `ck_identity_profile_status` message without first
   removing state_shape. This subsumption is inherent in the frozen `docs/14` §4.8
   predicates, not something the test invented.
3. **The probe remains sensitive to the production constraint.** Dropping
   state_shape only *unmasks* status. If `ck_identity_profile_status` were absent,
   misspelled, or had a wrong predicate on the production catalog, the unmasked insert
   would succeed and the helper's explicit
   `fail("expected SQL failure 23514 for ck_identity_profile_status but the statement succeeded")`
   would fire. The test therefore fails closed against exactly the drift it claims to
   detect. It does not assert a vacuous property.
4. **The isolation is transactional and self-restoring.** PostgreSQL DDL is
   transactional. `ROLLBACK TO SAVEPOINT` in the `finally` restores both constraints.
   I verified this live: after the drop/rollback cycle, `pg_constraint` again contains
   both named checks (count = 2) and the role GUC has returned to
   `customer_iam_role` because the role was set with `SET LOCAL ROLE` inside the same
   savepoint. The explicit `switchLocalRole` afterward is redundant-but-safe.
5. **There is no commit path that could persist the drop.** The helper never calls
   `commit()`. The enclosing test never commits. Connection close rolls back. Even a
   `fail(...)` inside the `try` is caught as the `SQLException` path or aborts the
   test method with the transaction still open, so the DROP cannot be committed to the
   shared container.
6. **The untouched-catalog truth is independently frozen.** The S1 inventory method
   `v001AndV002InventoryMatchesTheFrozenContract` asserts the exact normalized
   `pg_get_constraintdef` of all 34 checks, including both profile checks, against the
   `docs/14`-derived map, on a catalog that this S2 helper never commits a change to.
   The S2 probe and the S1 inventory are complementary, not redundant: S1 proves the
   definitions exist and match the frozen spec; S2 proves each definition *fires*.

### Decision

**Valid bounded test-only isolation. Not a material test-manipulation defect.**

A material test-manipulation defect would require one of: (a) the isolation persisting
beyond the probe (it cannot — savepoint rollback, no commit, role is `SET LOCAL`);
(b) the assertion becoming vacuous (it cannot — an absent/malformed status check makes
the insert succeed and `fail`); (c) the production catalog being modified for other
tests (it cannot — the drop is rolled back before any subsequent probe, and count = 2
is re-asserted); or (d) the frozen contract being reinterpreted to fit the workaround
(it is not — both predicates are exactly `docs/14` §4.8 / V002, and S1 already froze
their definitions). None of (a)–(d) holds.

This is recorded as a **residual hardening item**, not a finding: see Residual Risk
R-1 and R-2. A future aggregate-review owner or S3 slice may prefer an additional
direct unmodified-catalog probe (e.g. asserting the observed state_shape-first report
as its own explicit expectation, so the subsumption is itself a first-class assertion
rather than an implicit precondition). That is an improvement, not a correction of a
defect.

  `expectSqlFailure`, which fails the test if the statement *succeeds*; every
  expected-success path asserts affected-row counts or a read-back value, not merely
  the absence of an exception. The 34-probe completeness assertion fails closed if a
  probe list and the S1-frozen map diverge. The concurrency helpers fail closed on a
  missed `pg_stat_activity` wait rather than proceeding with a false "one winner".
- **Transaction-aborted / savepoint / role leaks.** `expectSqlFailure` and
  `classifyIdentityInsert` each open a savepoint and always `rollback(savepoint)` in
  `finally`, so an aborted subtransaction cannot poison the enclosing test
  transaction. `switchLocalRole` uses `SET LOCAL ROLE` after `RESET ROLE`, scoping the
  GUC to the transaction; the special-focus helper additionally re-asserts both
  constraints exist after rollback. No `SET ROLE` (session-scoped) is used on a path
  that outlives its savepoint.
- **Cleanup gaps / orphan rows / pollution.** Every race commits rows only through
  method-local UUIDs and removes them in FK-safe order in `finally`, asserting
  zero residue. Lifecycle, collision, immutability and FK probes likewise use
  method-local UUIDs and roll back or explicitly delete. No `truncate` is used on any
  V002 table. A later method cannot observe an earlier method's rows.
- **Wrong SQLSTATE / constraint extraction.** Expected SQLSTATEs are the canonical
  PostgreSQL codes: `23514` check, `23503` FK, `23505` unique, `42501` privilege,
  `P0001` raise. Constraint/index names are asserted as substrings of the driver
  message, which is the names PostgreSQL embeds for these error classes; the S1
  inventory independently freezes the catalog-side names so a renamed object would
  fail both halves.
- **Concurrency liveness / idempotency / ordering.** Bounded 15 s wait detection,
  20 s `statement_timeout`, 30 s future timeout. Contention is on the same unique key
  (same identity tuple / same live membership pair), not on unrelated rows. Loser
  classification reads committed state after the loser's own failure, which is the
  only point at which the winner's row is guaranteed visible. Rollback-race asserts
  the loser *succeeds*, not merely that it does not hang. No test relies on bare
  `sleep` for its assertion.
- **Hidden skips / parallelism.** No `@Disabled`, `Assumptions`, or conditional
  environment gate exists in the IT. Failsafe is bound only under `container-smoke`
  with `failIfNoTests=true`. No JUnit parallel-execution configuration is present, so
  the 16 methods run sequentially in one JVM and the shared-container assumptions
  (method-local UUIDs, no inter-method coupling) hold.
- **Scope drift.** The numstat and Windows `git status` show exactly the four
  author-writable paths plus the controller-owned control row. V001, V002, pom,
  Bootstrap, and all of `backend/src/main/**` are CR-normalized-identical to HEAD.
  The single deletion is the harmless `awaitFuture` genericization.
- **Overcoupling.** The four methods add no new production object, no new migration,
  no new role, and no cross-test shared fixture. The 34-probe map is derived from the
  already-frozen S1 `V002_CHECK_DEF_MAP`, not re-declared, so it cannot silently
  self-approve a wrong predicate. Concurrency helpers reuse the existing
  two-connection / `pg_stat_activity` pattern already used by the S1
  `concurrentIdempotencyRetryObservesOneWinner` method rather than introducing a new
  test framework.
- **Semantic ownership.** Evidence attributes each behavior to V002 DDL, `docs/14`
  predicates, and live PostgreSQL 16.15 observation. It does not claim the test derives
  the contract from itself, does not invent a new contract for the isolated status
  probe, and explicitly labels the deviation as a test-only isolation with residual
  risk. CI/README changes describe exactly what the workflow and methods do.
