### 1-未修复-低-请求体读取的传输层IOException被归类为422客户端校验失败
- **位置**: `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerOrdersController.java:35-37`（`CustomerOrderDtos.OrderRequest` 绑定块）；契约来源 `docs/gateflow/pa41-customer-order-creation-foundation-plan.md:72`（§3.1 第8步）。
- **问题类型**: 契约缺失 / 错误分类（failure handling）
- **当前写法（实际分支）**: `catch (IOException | IllegalArgumentException invalid) { throw new OrderCreationException(Code.VALIDATION_FAILED); }` — 任何来自 `request.getInputStream().readNBytes(8193)` 的 `IOException`（客户端中断、容器读超时、连接被 reset、servlet 层流故障）与 JSON 绑定器的 `IllegalArgumentException` 走同一分支，最终经 `CustomerOrdersController.java:44` → `CustomerProblemWriter.java:111` 输出 `422 VALIDATION_FAILED`。
- **触发输入**: 已通过 401/503/422 前置校验、Content-Type 合法的请求，在 body 流式读取期间断开（或容器 `connectionTimeout`/`maxSwallowSize` 触发读取异常）。异常发生在 `DefaultCustomerOrderCreationService.java:22` 事务开启之前，因此无任何写入。
- **预期 vs 实际**: 预期 §3.1 第8步 “Dependency/connection/timeouts/… failures → 503 SERVICE_UNAVAILABLE”（同一文档 §3.1 第1步把 dependency/connection 失败明确放在 503 族，把结构体校验放在 422 族）；实际该子分支把服务器侧 I/O 依赖失败报告为客户端校验失败 422。
- **直接证据**: 源码 `CustomerOrdersController.java:36-37`；同一 catch 形状存在于已接受的既有控制器 `CustomerSubjectActivationsController.java:46` 与 `CustomerSubjectClaimsController.java:41`（house pattern）；`backend/src/test/java/com/onecall/archtests/CustomerOrdersWebTests.java:84-85,117-120` 覆盖 malformed UTF-8/超限 body/owner 不可用，但没有任何用例让 body 流抛出 `IOException`，因此该分支的错误类别未被测试固定；plan `:72` 的 503 族清单包含 connection/timeout 失败。
- **影响**: 仅错误分类与可观测性：状态码族被误归（真实 503 族故障计入 422 客户端错误），运维排障与 SLO/告警（4xx vs 5xx）会把容器/网络故障误读为客户端滥用；无数据面影响（发生在事务前，零写入、零 Outbox/audit/idempotency 事实，重放语义与 conflict 判定不受影响；响应通常已无法送达断开连接的客户端）。
- **建议改法和验证点**: 二选一并保持公开契约不变——(a) 把 `IOException` 拆到 `Code.SERVICE_UNAVAILABLE` 分支，`IllegalArgumentException` 保留 422；或 (b) 若接受其为既有 customer 边界统一写法，则在 plan §3.1.8/实现报告处显式记录该例外，并补一个 mock `HttpServletRequest` 令 `getInputStream()` 抛 `IOException` 的 Web 单元用例，固定当前预期，避免后续 reviewer/agent 误判为 bug。验证点：`CustomerOrdersWebTests` 新增/扩展断言 exact status+code+redaction（`type/title/status/code/traceId` 五字段），且 `CustomerOrdersIT.invalidKeysAndForgedBodiesNeverWrite`（`:132-138`）的零 delta 断言仍成立。
- **修复风险（低/中/高）**: 低。改动局限于单个 catch 分支，不触及事务、锁、幂等、consent 或事实顺序；(b) 方案零行为变更。
