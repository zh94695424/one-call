## Findings

### 01-未修复-高-Golden vector encodes `DOWNLOAD`, which is not a valid `Purpose` enum; the declared expected payload/MAC is not an issuable/verifiable claim

- **位置**: Plan §5 "Golden vectors" (purpose `DOWNLOAD`, 177-byte payload hex, expected MAC), and the §5 field table row "purpose | strict UTF-8 enum name".
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口 / 状态机漏洞
- **当前写法**: "purpose is `DOWNLOAD`" in the fully specified golden vector; the same §5 says an "invalid enum" must be rejected.
- **反例/失败场景**: The codec computes the HMAC over the DOWNLOAD payload and the verifier must return a `VerifiedMediaClaim`. `VerifiedMediaClaim.purpose()` is typed `MediaAuthorizationRequest.Purpose`, whose only values are `PLAYBACK`, `SEEK`, `RENEW`. `Purpose.valueOf("DOWNLOAD")` throws, or the codec must reject the vector as an invalid enum. The test that stores the constant and asserts the encoder output either fails on its own golden vector or the codec accepts an enum that PA19 cannot carry.
- **为什么有问题**: The golden vector is the independent known-answer anchor for the security-critical codec; a vector that cannot correspond to a valid PA19 claim cannot validate issuance or verification. The plan also forbids the test from generating its own expected value at runtime, so there is no escape hatch.
- **直接证据**:
  - `backend/src/main/java/com/onecall/core/sharing/internal/publicadmission/MediaAuthorizationRequest.java:7` — `enum Purpose { PLAYBACK, SEEK, RENEW }`.
  - `backend/src/main/java/com/onecall/core/sharing/internal/playback/VerifiedMediaClaim.java:9-11` — `Purpose purpose`.
  - `backend/src/main/java/com/onecall/core/sharing/internal/playback/MediaPlaybackService.java:45` — `claim.purpose() != expectedPurpose`.
  - Independent decode: bytes 177; fields parse exactly as the table says, except the purpose field is `44 4f 57 4e 4c 4f 41 44` (`DOWNLOAD`).
  - Independent HMAC-SHA-256 over `onecall-media-playback\0v1\0` + `K1` + NUL + payload with key `00..1f` = `83dd9ea7d17332c29092b9e9dd64cfd2f3b048075e4528276d0ca90553b9a497`, i.e. the stated MAC is internally consistent with the invalid payload.
- **影响**: The central "independent golden bytes/MAC" acceptance item is false; implementation either ships an accepting parser for an impossible claim or a red test. Codegen and review are blocked on a one-word contract defect.
- **建议改法和验证点**: Use `PLAYBACK` (same 8-byte length, so the payload stays 177 bytes): replace `0008444f574e4c4f4144` with `0008504c41594241434b`. Corrected full payload hex: `4f4e4543414c4c2d4d454449412d504c41594241434b000100196f6e6563616c6c3a6d656469612d706c61796261636b3a763100000000000000000000000000000001000000000000000000000000000000020000000000000000000000000000000300000000000000000000000000000004000000070000000b0008504c41594241434b0006475ef6574f350006475ef6574f350006475fcceaf33500000e1000000000000000000000034630b8a000`; corrected MAC `657fe80ef35b9f8a33d0ea0fb6667ecaa2c447ca56f4b64557c30d7c5f8b3195`. Also state in §5 that the writable purpose set is exactly `PLAYBACK|SEEK|RENEW` and add one vector per purpose (lengths differ for SEEK/RENEW). Verification point: the golden test must round-trip to a `VerifiedMediaClaim` and pass `MediaPlaybackService.validShape`.
- **修复风险（低/中/高）**: 低

### 02-未修复-高-`@ConditionalOnMissingBean` ordering between the new authority bean and the persistence fallback is asserted but not mechanically pinned; dual-provider startup ambiguity remains possible

- **位置**: Plan §7 "The bean factory ordering is pinned: authority bean definition is evaluated before the unavailable admission fallback; ... `@ConditionalOnMissingBean(ShareMediaCredentialProvider.class)` ... cannot win when the authority bean is present."
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施 / 并发恢复风险
- **当前写法**: The plan states the desired ordering but gives no construction mechanism. The authority is declared in `MediaPlaybackConfiguration`; the fallback lives in `ShareAdmissionPersistenceConfiguration`.
- **反例/失败场景**: In the `persistence` profile with a valid authority configuration, if `ShareAdmissionPersistenceConfiguration` is processed first, its `unavailableShareMediaCredentialProvider()` is registered. The authority bean from the other `@Configuration` is registered later with no condition, so two `ShareMediaCredentialProvider` beans exist. `shareAdmissionService(... ShareMediaCredentialProvider credentials ...)` then fails with `NoUniqueBeanDefinitionException`, or Spring chooses one silently. The plan forbids `@Primary`, so no deterministic tie-break exists. Symmetrically, if the authority wins the ordering, the goal is met only by luck of class-scan order.
- **为什么有问题**: `@ConditionalOnMissingBean` is evaluated against bean definitions processed so far; Spring Boot documents it for auto-configuration, not as an order-independent user-config contract. `MediaPlaybackConfiguration` and `ShareAdmissionPersistenceConfiguration` are both regular `@Configuration` classes (the latter additionally `@Profile("persistence")` + datasource-enabled). "Pinned" in prose is not a mechanism the implementation agent can rely on.
- **直接证据**:
  - `backend/src/main/java/com/onecall/core/sharing/internal/persistence/ShareAdmissionPersistenceConfiguration.java:100-101` — `@Bean @ConditionalOnMissingBean(ShareMediaCredentialProvider.class)` fallback.
  - `.../ShareAdmissionPersistenceConfiguration.java:104-110` — `shareAdmissionService(... ShareMediaCredentialProvider credentials ...)`.
  - `backend/src/main/java/com/onecall/core/sharing/internal/playback/MediaPlaybackConfiguration.java:15-25` — plain `@Configuration`, no ordering/import relationship.
  - Plan §7 asserts "bean factory ordering is pinned" / "cannot win", with no code-level condition.
- **影响**: Target persistence deployment can fail at startup or silently select a different provider than playback. This is the exact split-brain/ambiguity that original finding 08 required the plan to pin.
- **建议改法和验证点**: Pin one deterministic composition, e.g.: (a) declare the authority and the unavailable fallback in the same configuration class so one `@ConditionalOnMissingBean` builder decides; (b) make `shareAdmissionService` take `ObjectProvider<ShareMediaCredentialProvider>` and resolve with an explicit "authority if unique, else unavailable" rule; or (c) use an explicit `@Import`/`@AutoConfigureBefore` ordering contract and state why it is stable. Add a context test that loads both configs in both registration orders and asserts exactly one provider bean and same-object identity for both interfaces.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 04-未修复-中-Replay metadata carrier is not pinned: `Issued` and `MediaAuthorizationCredentialRequest` cannot carry `evidenceId`/`issuedAt`/`notBefore`/`kid`

- **位置**: Plan §4 "The first successful PA18 authorization commits ... issuedAt/notBefore ... and active signing `kid`"; "The authority receives the prior committed success metadata on same-identity replay"; §6 "The authority receives an immutable authorized fact bundle".
- **问题类型**: 契约缺失 / 不可直接实施 / 状态机漏洞
- **当前写法**: The plan says what must be committed and reused, but not which allowlisted record fields carry it. The source records carry neither the evidence identity nor the replay anchor.
- **反例/失败场景**: `MediaAuthorizationCredentialResult.Issued` is `(String credential, Instant expiresAt)`; the service writes the event payload from `decision` and `issued.credential()` and has no accessor for `issuedAt`/`notBefore`/`kid`. `MediaAuthorizationCredentialRequest` has no `evidenceId` and no prior `issuedAt`/`notBefore`/`kid`. A codegen agent must either decode the credential in PA18 (forbidden by "never open/inspect secret material" spirit and by layer direction), extend the result/request records (not stated), or regenerate the anchor (defeating reconstruction). The plan does not say the service supplies `decision.priorSuccess().payload()` values on replay, nor how `evidenceId` reaches the authority.
- **为什么有问题**: This is the replay contract original finding 01 required. The plan's conceptual answer is correct (no secret storage; non-secret anchor + kid; verify-only replay-only), but the concrete carrier is the difference between codegen-ready and inventiveness. The allowlist (paths 1 and 2) is sufficient to extend the records, so this is a bounded documentation fix.
- **直接证据**:
  - `backend/src/main/java/com/onecall/core/sharing/internal/admission/ShareMediaCredentialProvider.java:14-40` — request has grant/admission/purpose/event/generations/expiries/fingerprint/eventId; `Issued` has credential+expiresAt only; no evidenceId, no prior anchor.
  - `DefaultShareMediaAuthorizationService.java:69-73` — builds the request; `:87-100` — writes the success payload and returns `issued.credential()`.
  - `ShareAdmissionRepository.java:34-40` — `GrantSnapshot.evidenceId()` is available to the service, but the request record does not carry it.
- **影响**: The replay path cannot be implemented byte-identically without an unstated record extension; a wrong choice can put secret material or a non-canonical anchor into the durable event.
- **建议改法和验证点**: Pin the exact additions in the allowlisted record file, e.g. `Issued(credential, expiresAt, issuedAt, notBefore, kid)` and request fields `evidenceId`, `priorIssuedAt`, `priorNotBefore`, `priorKid` (or a typed `ReplayAnchor`/`AuthorizedMediaFacts` bundle), with redacted `toString`. State: first issuance = current ACTIVE key + fresh clock anchor; replay (`decision.priorSuccess() != null`) = recorded anchor/kid (ACTIVE or VERIFY_ONLY) and never a fresh mint. Verification: byte-identical replay under advancing clock and a fresh authority instance, plus a test that the event payload contains exactly the non-secret anchor/kid fields and no token/MAC/key.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 06-未修复-中-PA19 "requested-window rule" is still factually false; PA19 enforces claim shape/bounds only and PA20 enforces the full window

- **位置**: Plan §3 "PA19 continues to enforce its requested-window rule; PA20 proves full-object transport"; §8 "explicitly distinguish PA19 requested-window validation from PA20 full-content transport".
- **问题类型**: 契约缺失 / 目标漂移 / 测试缺口
- **当前写法**: The plan attributes a "requested-window rule" to PA19 and asks the implementation to test PA19 requested-window validation.
- **反例/失败场景**: `MediaPlaybackService.authorizeAndOpen(OpaquePlaybackCredential, Purpose)` has no requested window input. `validShape` accepts any `0 <= start < end <= duration`, so an in-duration sub-window claim (`[1s, 2s]`) passes PA19 and reaches `reader.open`. Only `MediaGatewayFilter` rejects `start != 0 || end != durationSeconds` with 403. An implementation following §8 may write a PA19 test that asserts a sub-window is denied; that assertion is false.
- **为什么有问题**: This is the unclosed part of original finding 07. The plan correctly defers sub-windows and issues only the full window, but it still misattributes enforcement and directs a test of a nonexistent PA19 request rule. The window-ownership statement in the Control adjudication is precise; the plan's wording is not.
- **直接证据**:
  - `backend/src/main/java/com/onecall/core/sharing/internal/playback/MediaPlaybackService.java:30` — signature has no requested window; `:77-88` — `validShape` allows sub-windows.
  - `backend/src/main/java/com/onecall/core/sharing/internal/gateway/MediaGatewayFilter.java:78-81` — `!Duration.ZERO.equals(start) || !Duration.ofSeconds(duration).equals(end)` → 403.
  - `MediaPlaybackServiceTests.java` — no in-duration sub-window rejection test; the existing window test covers null/negative/start>=end/end>duration only.
- **影响**: Implementation agent may write a false or vacuous PA19 window test, and the security-relevant full-window enforcement stays misattributed to the wrong layer.
- **建议改法和验证点**: State: PA19 validates claim window shape and duration bounds; PA20 enforces the full-object window; PA21 issues only `[0, duration)`. Test that an in-duration sub-window passes PA19 shape and is 403-denied at PA20 (if the gateway is in scope) or, if not, assert PA21 never issues it and remove the "PA19 requested-window" claim.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Final conclusion

**fail**

The cumulative fix closes most of the original findings well: the window is now the correct full-object window with the correct `decision.grant().evidenceId()` accessor and no witness/schema change; legacy P2 `issue` is explicitly default-deny; the binary profile is substantially pinned and the stated MAC independently recomputes; the CI/POM baseline (29/196 + 13/204 = 42/400, 13 includes) is accurate and `ci.yml` is in scope. However, the plan is not yet code-generation-ready:

- The replay anchor carrier (`issuedAt`/`notBefore`/`kid`/`evidenceId`) is not specified (finding 04).

- The global `internal/` exact architecture set that will reject the new `credential` files is not named (finding 07).
