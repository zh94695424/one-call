### F-01 — Required accepted-context binding/HMAC change is not exercised

- **Severity:** Low
- **Path/line:** `backend/src/test/java/com/onecall/archtests/subjectnumber/CustomerSubjectClaimServiceTests.java:220-228` (`changedAcceptedContextAppendsExactlyOneConflict`); also `backend/src/test/java/com/onecall/archtests/container/CustomerSubjectClaimsIT.java:159-168` (`changedDuplicateContextAppendsOneConflictAndNeverUpdatesOwner`).
- **Scenario/input:** Plan §9.1 U13 requires the accepted-duplicate/context path to be tested for “Method/binding/HMAC/proof change”. The unit test only iterates two cases: (a) the server `proofRef` changes with method `SMS`, and (b) `verificationMethod` changes to `MANUAL_REVIEW` with the same server `proofRef`. The IT changes only the method (`SMS` → `MANUAL_REVIEW`) plus the server reference. No case changes `bindingId` or `numberHmac` while keeping row subject/account/null-organization/method compatible.
- **Actual branch:** `DefaultCustomerSubjectClaimService.java:108-109` and `:121-125` compare the full decoded `Payload` (`bindingId`, `numberHmac`, `proofRef`, subject, method), and `:130` appends one CONFLICT row when the payload differs. The production code therefore compares binding/HMAC correctly.
- **Expected:** A same-account accepted-context change that differs only in binding or HMAC must still return 409 `CLAIM_CONTEXT_CONFLICT`, insert exactly one CONFLICT row, and leave owner/revision unchanged.
- **Impact:** A regression that compared only `proofRef` (or compared ciphertext bytes) instead of the full logical payload would pass both current tests. The required adversarial case for two of the four identity dimensions is absent, so the suite does not prove the binding/HMAC axis of the accepted-duplicate branch.
- **Fix direction:** Add a stored accepted payload (or a second binding for the same subject) whose `bindingId` and/or `numberHmac` differs from the current command while subject/account/null-organization/method remain compatible; assert 409 `CLAIM_CONTEXT_CONFLICT`, exactly one CONFLICT row, no `setUnownedOwner`/revision change, and no disclosure of the old accepted result. Add the same case at IT level without changing production code.
