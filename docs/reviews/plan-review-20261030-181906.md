1. **`§3.7` wording vs T-S3-09 trigger name.** `§3.7 :262` says FK-satisfied cycle contradictions (including "decoy non-creation") fail "with class-level `P0001`/… — no named-trigger specificity", while the T-S3-09 row `:585` says the failure is "from `trg_evidence_record_creation_cycle`". In T-S3-09 the decoy event is non-creation, so only the record-side trigger can fire; naming it is deterministic and the test passes either way. This is an internal wording inconsistency, not an executable defect or a regression of the RR-007 source-mismatch fixture. Suggested clarification: narrow `§3.7`'s "no named-trigger specificity" to fixtures where both cycle triggers can fire, or explicitly permit the isolated T-S3-09 name. Owner: implementer/controller; destination: implementation-time test wording. Non-blocking.
2. **Cycle-negative fixtures' committed parent prerequisites.** S2 T-S3-09/10/11 commit valid parents first (subject/call/media) and the failing transaction rolls back only the record/event/artifact; the plan does not explicitly state that those committed method-local parents are later cleaned. Method-local UUIDs avoid collisions, and the shared helper can clean them if their ids are recorded, but this hygiene is not mandated for those fixtures. Non-blocking test-maintenance risk; suggested destination: apply the shared helper to all committed method-local prerequisites.
3. **Parent-domain deletion order.** The cleanup delegates `ivr`/reservation/subject parent ordering to "each parent domain in its existing own FK-safe order". The fresh-connection per-id zero-residue assertion will expose an incorrect order (for example `inbound_session`/`call_record`), so this is safely left to the existing FK-safe helper pattern, not a missing correctness contract.
4. **Cleanup-helper first-use documentation.** The shared cleanup helper is used by S1 (`:539`) and S2 (`:610`, `:624`), so S1 must introduce it; the allowed-files row and checklist explicitly allocate only `expectCommitFailure` as an S1 helper. The usage itself makes the allocation unambiguous and the helper is permitted in `PostgresContainerIT.java`, so this is a documentation-precision caution.
5. **Doc-14 T-S3-11 literal wording.** The spec row still says "under a pinned event-first insertion order" and "from the creation-cycle trigger". The plan still uses event-first insertion (`D,C` then `R`), and the class-level assertion is compatible because both possible failures are creation-cycle triggers and the same row's isolation sentence governs. No PA8 schema/behavior change; optional design-owner clarification only.
