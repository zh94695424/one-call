## Material Findings

### RR-007-未修复-[中]-T-S3-11 source-mismatch fixture is not FK-satisfied and pins a specific creation-cycle trigger, so the expected `P0001` depends on deferred-queue order and contradicts the doc-14 isolation rule

- **位置**: `docs/gateflow/pa8-v008-evidence-foundation-plan.md:590` (S2 classification table, "Mismatched identity" row), `:613` (S2 T-S3-11 bullet), `:357` (§4 order-sensitive table); `docs/14-production-data-model-and-flyway-schema-spec.md:4736` (T-S3-11).
- **问题类型**: 测试缺口 / SQLSTATE isolation / 不可直接实施 / 过度具体触发器断言.
- **当前写法**: The source-mismatch class says "Both rows present but identities differ; **pin event-first insertion** so the event-side FK is satisfied and the creation-cycle trigger is the only remaining check. Committed valid witness prerequisites first." It expects `P0001`/`EVIDENCE_CREATION_CYCLE_VIOLATION` **from `trg_evidence_event_creation_cycle`** and forbids accepting `{23503, EVIDENCE_CREATION_CYCLE_VIOLATION}`.
- **反例/失败场景**: With only the record and the mismatched creation event, the record-side composite FK `fk_evidence_source_event` is not satisfied: the record's `(source_event_domain, source_event_id) = ('EVIDENCE', X)` has no matching `evidence_event(event_domain, event_id)` because the event's `event_id = Y ≠ X`. The only reason `P0001` can beat `23503` is that the event INSERT was first, so the event-side cycle trigger is queued before the record-side RI check and aborts the transaction at commit before the RI check runs. That is an unproven deferred-queue ordering claim; if the order differs, the observed error is `23503` naming `fk_evidence_source_event`, which the plan says must not be accepted. Even if the order holds, the event-side cycle trigger may not be the only trigger able to fire; asserting it by name is over-specific for a frozen shared error code.
- **为什么有问题**: The doc-14 T-S3-11 contract says: "If a construction could also violate a deferred FK, isolate the target violation in the fixture (both parents present, identities otherwise FK-satisfying) rather than loosening the named constraints or accepting a union of SQLSTATEs." The plan's two-row fixture does not isolate the record-side deferred FK; it relies on event-first ordering. The task also explicitly requires an FK-satisfied source fixture with a pinned order and forbids requiring per-trigger specificity when the frozen shared error can only prove a class-level invariant. The wrong-owner crosslink correctly satisfies both FKs and asserts class-level only; the source-mismatch row is inconsistent with that standard.
- **直接证据**: Plan lines 357, 590, 613; doc-14 T-S3-11 line 4736; `fk_evidence_source_event` and `fk_evidence_event_record` definitions at plan §3.4/§3.6 and doc-14 §4.41/§4.43; the plan itself lists deferred trigger order as a static claim to be confirmed at implementation (lines 579, 611, residual risk).
- **影响**: S2 can be red with `23503` (which the plan forbids accepting) or can pass only for an order-dependent reason; the exact-trigger assertion is not guaranteed; the implementer may weaken the assertion, accept a SQLSTATE union, or stop unnecessarily.
- **建议改法和验证点**: Make the source-mismatch fixture FK-satisfied with a decoy: record R with source `(EVIDENCE, X)`; a non-creation decoy event D with `event_domain='EVIDENCE'`, `event_id=X`, `event_type` ≠ `EVIDENCE_CREATED`, `evidence_id=R`; and a mismatched `EVIDENCE_CREATED` event E1 with a distinct `event_id=Y` and `evidence_id=R`. Both deferred FKs pass; the record-side trigger has no `EVIDENCE_CREATED` with `event_id=X`, and the event-side trigger sees `record.source_event_id≠Y`; assert **class-level** `P0001`/`EVIDENCE_CREATION_CYCLE_VIOLATION`, not a named trigger. If the team instead keeps the two-row event-first construction, record the deferred-queue-order dependency explicitly as a stop-and-report condition and remove the exact-trigger claim; do not claim the record-side FK is satisfied.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### RR-008-未修复-[中]-S2 concurrency cleanup omits `evidence.recording` and the zero-residue assertion; the committed winner recording can survive or block media/call cleanup

- **位置**: `docs/gateflow/pa8-v008-evidence-foundation-plan.md:624` (concurrency method cleanup), `:710` (§10 "Dependency-order FK-safe cleanup" row), `docs/gateflow/pa8-v008-evidence-foundation-plan-fix-2.md:103` (fix-2 §3.5 cleanup summary).
- **问题类型**: 测试缺口 / 清理顺序 / 状态残留 / 不可直接实施.
- **当前写法**: "In one transaction: `DISABLE TRIGGER` those three, FK-safe delete both cycle sides in immediate-child-first order (artifacts, then events, then records, then media/parents), `ENABLE TRIGGER`, assert `pg_trigger.tgenabled='O'` restored for each. After delete, no queued INSERT/UPDATE creation-cycle trigger may reference the removed rows. Do not delete rows created by other methods."
- **反例/失败场景**: The same concurrency method races and commits a winner on `uq_recording_protocol_id` (and a winner `media_object` on `uq_media_object_version`). The cleanup list never deletes `evidence.recording`. If the winner recording has `media_object_id` set (UPLOADED/VALIDATED), deleting the media object first raises `23503` from `fk_recording_media_object` (immediate RESTRICT); if it is DECLARED and only references `ivr.call_record`, deleting the call parent raises `23503` from `fk_recording_call`, or the recording row survives if the parent is not deleted. The bullet also lacks the V007 per-id zero-residue verification, so "no survivor" is not proven after the cleanup transaction commits.
- **为什么有问题**: The plan's own §10 cleanup pattern is "leave container clean across methods; immediate children first" and the V007 `cleanupV007S2LocalRows` precedent deletes every method-local table and then asserts per-id zero residue (`PostgresContainerIT.java:10068-10167`). `recording` is an immediate child of both `media_object` and `ivr.call_record`; omitting it makes the cleanup FK-unsafe and defeats the no-survivor contract the task asks to confirm.
- **直接证据**: Plan lines 620-624 (concurrency creates recordings/media/records/events and defines the cleanup), line 710; fix-2 §3.5 line 103; V007 cleanup at `PostgresContainerIT.java:10068-10123` and zero-residue loop 10135-10167; FK definitions `fk_recording_call`/`fk_recording_media_object` at plan §3.3.
- **影响**: The concurrency method can fail during cleanup (`23503`) or leave method-local recording/media rows, violating test isolation and the "no survivor / clean catalog" claim. Later accepted slices may inherit contaminated state.
- **建议改法和验证点**: Add `evidence.recording` to the FK-safe deletion order before `evidence.media_object` and `ivr.call_record` (and any other method-local parents), using the owning role (`evidence_owner` or migration identity for recording, `ivr_owner`/`subject_number_owner`/etc. for parents). After commit, run the V007-style per-id zero-residue assertion for every method-local id (recordings, media objects, records, events, artifacts and parents) on a fresh connection. Keep the three named immutable triggers disabled/restored exactly as written.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
