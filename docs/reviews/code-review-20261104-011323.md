## Findings

### P1 — Stale column ACLs can survive V010 in five of the nine bounded schemas

`backend/src/main/resources/db/migration/V010__sharing_role_least_privilege.sql:52` through `:68` resets every relation/column only in `platform`, `audit`, `ivr`, and `entitlement_metering`. In `sharing`, `evidence`, `customer_iam`, `organization_access`, and `subject_number`, the same reset is restricted to the hard-coded V009 relations. The final checks at `:159` through `:172` count query-role `SELECT`, command-role `SELECT`/`UPDATE`, and table-level writes, but do not reject an extra command-role column `INSERT` (or command `REFERENCES`, or query column `INSERT`/`UPDATE`/`REFERENCES`) on a non-enumerated relation when the grantor is the owner and grant option is absent.

A pre-existing owner-granted column-level `INSERT` ACL on a relation such as `evidence.evidence_event` therefore survives V010 while `sharing_command_role` already has `evidence` schema `USAGE`. The exact grant matrix is violated, and the command principal can reconstruct an evidence write path. The clean-state catalog assertion in `backend/src/test/java/com/onecall/archtests/container/PostgresContainerIT.java:5142` would notice such an ACL only if a test database contained it; neither the catalog test nor the injected-failure snapshot test seeds a stale column ACL. The scratch failure pass covers command membership and role attributes, not stale relation/column ACLs.

Fix direction: reset every relation and column across all nine bounded schemas for `PUBLIC`, `sharing_role`, and `sharing_command_role`, or add a postcondition that rejects every non-allow-listed `attacl` row regardless of privilege type. Add a scratch PostgreSQL failure probe for a stale column `INSERT` grant outside the enumerated relations.

### P1 — Closed-world role-state enforcement covers only `sharing_command_role`

Preflight membership checks at `backend/src/main/resources/db/main/resources/db/migration/V010__sharing_role_least_privilege.sql:22` through `:38` and final checks at `:154` through `:156` inspect memberships and attributes only for `sharing_command_role`. Two material stale states remain accepted:

- `sharing_role` can remain a member of `pg_read_all_data` or any custom read-only role. Because the expected `sharing_role` has `rolinherit=true` (`PostgresContainerIT.java:5053`), `SET ROLE sharing_role` can inherit forbidden secret-column reads while the direct ACL counts remain exact.
- `sharing_owner` can retain an external member such as a login. That login can `SET ROLE sharing_owner` and bypass the query-role restriction entirely.

Altered `LOGIN`, `CREATEROLE`, or `BYPASSRLS` attributes on `sharing_owner`/`sharing_role` are likewise not rejected by V010, although the exact role census is asserted only after a clean test migration. `backend/src/test/java/com/onecall/archtests/container/SharingRoleLeastPrivilegeIT.java:198` and `:209` exercise only a stale command-role membership and command-role `BYPASSRLS`; `:235` checks only command-path membership. The shared membership check at `PostgresContainerIT.java:5054` also excludes external members of `sharing_owner` and outbound memberships of `sharing_role`.

Fix direction: fail V010 for any member of `sharing_owner`, any outbound membership of `sharing_owner`/`sharing_role`/`sharing_command_role`, and any unexpected attribute tuple for the sharing owner/query/command roles. Keep `roleid = sharing_role` membership rows legal for legitimate query logins, and add scratch probes for `sharing_owner -> stale_login`, `sharing_role -> read-only-role`, and stale attributes.
