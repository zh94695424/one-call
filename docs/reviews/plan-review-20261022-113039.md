## Assumptions tested

| Assumption / lens | Result |
| --- | --- |
| The 43-table catalog covers every confirmed goal fact. | Fails. A durable entitlement-issuance state and its transition history are not owned by `entitlement-metering`; `customer_order.entitlement_status` cannot represent per-line or per-installment issuance. |
| The three slices are behaviorally verifiable in S1→S2→S3 order. | Fails. S1 activation/consent depends on S2 `ivr.inbound_session` and S2 trial tables; S2 entitlement depends on S3 `catalog_order.customer_order`; the plan also states S2 depends on a “frozen S3 catalog/order contract.” |
| Activation, consent and first trial can be atomic without a cross-module table write. | Not established. The plan says `activation-consent` “creates the first trial,” but `trial_grant`, `entitlement_grant` and `entitlement_balance` are owned by `entitlement-metering`, and no published service or transaction contract is named. |
| The canonical-caller lock covers every path that can create a call or reservation. | Fails for direct DTMF authorization. The direct-authorization sequence takes no canonical-caller lock and does not recheck that the call is the `ENTER_CALLEE` no-task path. |
| Event identity is unique within its domain as D18/INV-35 claims. | Partially fails. `ivr.call_event` is unique only by `(call_id,event_id)`, not by `(event_domain,event_id)`; `ivr_decision` source-event uniqueness omits the domain; activation confirmation has no request fingerprint. |
| Payment and entitlement issuance are independently observable per order/installment/type. | Partially fails. Payment status is owned by `catalog-order`, but issuance status has no durable row/transition owner; a single `customer_order.entitlement_status` cannot represent multiple benefit lines. |
| The nine waves contain no forward table dependency. | Mostly true at SQL level, but the slice ordering is not consistent with the wave order, and several critical `call_id` FK parents are unnamed. |
| Validation proves the 43/35/9/3 counts and the claimed one-owner/completeness properties. | Partially. Counts and owner cells are checked; table-to-wave/table-to-slice completeness, FK parent order, duplicate table names and lifecycle-class coverage are not checked. |
| Unresolved production inputs have one owner and destination. | Mostly. Q1–Q19 are assigned, but issuance-state, lock-timeout, share-ticket-failure and event-registry details are not added as inputs even though they are design-critical. |
| The 43/35 counts are justified rather than frozen by assertion. | Not fully. Most tables map to independent facts, but the missing issuance state and the exact-count acceptance rule mean a necessary correction becomes a controller-level count exception. |

## Findings

### PR-001-未修复-[高]-切片顺序与真实依赖相反，S1 和 S2 均依赖后续切片
- **状态候选**: `accepted-candidate`
- **位置**: §13 S1 (plan lines 396-405), S2 (409-417), S3 (419-429), cross-slice summary (431-439); §12 waves V004-V007 (365-368).
- **问题类型**: 切片边界错误 / 前向依赖 / 验收不可执行
- **当前写法**: S1 “depends on none” and owns activation/consent; S2 “depends on S1; frozen S3 catalog/order contract for paid issuance only”; S3 consumes S1/S2. S1 completion asserts “no claim or consent path mutates another module’s table.”
- **反例/失败场景**: Implement S1 first. `activation_consent.consent_record.ivr_session_id` references `ivr.inbound_session` (V005, S2), the activation transaction creates `trial_grant` (V006, S2), and `customer_order.purchase_consent_id` is not available until S1’s own V007. Implement S2 next. `entitlement_grant.order_id` references `catalog_order.customer_order` (V004, S3). A reviewer cannot run S1’s activation tests without S2’s tables, and cannot run S2’s paid-grant tests without S3’s order table. The claimed S1/S2 acceptance signals are therefore unprovable.
- **为什么有问题**: The slice principle requires behaviorally verifiable boundaries. A slice that cannot be migrated or tested on top of earlier slices is not a boundary; it is a review partition over a shared schema. The plan states both “ordered slices” and later-slice prerequisites, which is a direct contradiction.
- **直接证据**: Plan line 435 says S1 “Depends on: none”; line 436 says S2 depends on “frozen S3 catalog/order contract”; line 400 lists activation in S1; line 416 says the paid path “freezes the S3 catalog/order contract”; request/row lines 169, 177-179, 186, 365-368; source `docs/12` line 295 requires consent, activation and first trial in one transaction.
- **影响**: S1/S2 cannot be accepted in order; gate cost shifts to rework; later work leaks into earlier slices (S3 catalog into S2, S2 trial/IVR into S1); the 3-slice claim is not demonstrated.
- **建议改法和验证点**: Re-slice by dependency order. A workable three-slice shape is: S1 = V001-V003 (platform/identity/subject), S2 = V004-V007 (catalog/order, IVR task/session, trial/entitlement/reservation, activation/consent) as the atomic transaction core, S3 = V008-V009 (evidence/sharing). If S2 is too large, request controller approval for a fourth slice rather than claiming three safe slices. If slices remain review partitions, remove “depends on none,” remove any later-slice prerequisite, and add a dependency script that fails when a slice references a table not in its own or an earlier slice. Validate by applying only the slice’s waves and running its named behavior tests.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-[高]-激活事务创建试用越过模块所有权且缺少 grant/balance 写入
- **状态候选**: `accepted-candidate`
- **位置**: §10 transaction 1 (plan line 309); table rows `trial_grant`/`entitlement_grant`/`entitlement_balance` (177-179); ownership contract (337-342); S1 completion (405); INV-08 (257).
- **问题类型**: 架构边界 / 跨模块写 / 事务不完整
- **当前写法**: “Lock the session and activation row … Append the consent record and create the first trial only if the subject/campaign is absent … commit.” `trial_grant` belongs to `entitlement-metering`; S1 claims “no claim or consent path mutates another module’s table.” No service call, grant row, balance row or transaction-propagation rule is named.
- **反例/失败场景**: (a) activation-consent writes `trial_grant` directly to satisfy the sequence, violating D9/§11; (b) it calls an entitlement service after commit, so activation may commit while trial issuance fails; (c) it creates only `trial_grant` without `entitlement_grant`/`entitlement_balance`, so the first `UsageReservation` cannot reserve and IVR activation appears successful but is unusable; (d) two confirmation events create one activation and two trials, or one trial without balance.
- **为什么有问题**: `docs/12` line 295 explicitly requires consent, activation creation/reuse and first-trial creation/reuse in one transaction. The plan’s ownership rule forbids the direct write that would satisfy this. The contradiction is not resolved by saying “activation remains separate from trial/reservation” in V007; separateness of tables does not permit a non-atomic trial.
- **直接证据**: Plan line 309; line 405; lines 177-179; line 342 (“collaborators … call a published service”); source `docs/12` line 295; source `docs/09` line 84 (trial unique, frozen at issuance); source `docs/12` line 296 (reservation only from valid trial/paid entitlement).
- **影响**: Either a cross-owner write (breaks the success signal) or a partial activation (breaks the business rule); first-trial issuance and balance consistency cannot be reviewed from this plan.
- **建议改法和验证点**: Define a published `entitlement-metering` service, e.g. `issueFirstTrial(subjectId, campaignKey, trialPolicyVersionId, actionEventDomain, actionEventId)`, callable inside the activation transaction, which alone writes `trial_grant` + `entitlement_grant` + `entitlement_balance` + Outbox and returns the first result on replay. Add `entitlement-metering` to INV-08’s collaborators. Test: injected trial/balance failure rolls back activation, consent and transition; duplicate confirmation returns the first result; concurrent confirmation yields one activation, one trial, one grant and one balance; privilege test shows activation role has no direct INSERT on entitlement tables.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-003-未修复-[高]-直接 DTMF 授权未取得主叫锁，也未证明处于无任务 ENTER_CALLEE 路径
- **状态候选**: `accepted-candidate`
- **位置**: §10 direct-authorization sequence (plan line 312), state machine (295), INV-11/INV-34 (260, 283); source `docs/13` §4.3 and §6.4.
- **问题类型**: 并发控制 / 信任边界 / 状态机绕过
- **当前写法**: “Authenticate the IVR call/session; reject any non-empty task ID; verify trusted caller, subject, activation, consent and available balance; create or reuse exactly one reservation for the callId; freeze the authorization decision … commit.” No canonical-caller lock, no active-call check, no check that the session’s current action was `ENTER_CALLEE` or that no PENDING/CLAIMED task exists.
- **反例/失败场景**: Two concurrent direct IVR calls from the same canonical caller both pass validation and create two reservations because `usage_reservation` is unique only by `call_id`; or a call that actually has a task sends an empty `taskId` to the direct endpoint and receives a second reservation without claiming/replacing the task. If `call_record` is not created in this transaction, the active-caller partial unique index offers no backstop.
- **为什么有问题**: `docs/13` lines 93-98 require create, replace, cancel, IVR claim **and direct IVR session establishment** to take the canonical-caller database mutex and check that no other active CallSession exists. `docs/13` lines 228-232 restrict the direct endpoint to the `ENTER_CALLEE` no-task path. The plan implements the first half for tasks but not for direct authorization.
- **直接证据**: Plan line 312; line 295 (“no task ID accepted” only); source `docs/13` lines 93-98, 208, 219-220, 228-232.
- **影响**: Concurrent direct calls or mixed task/direct calls can double-reserve the caller’s entitlement and create parallel calls, defeating the single-slot rule; a compromised/buggy IVR can bypass task ownership.
- **建议改法和验证点**: Require the canonical-caller lock in the direct-authorization transaction; recheck no PENDING/CLAIMED task and no ACTIVE/UNKNOWN call; require the inbound session’s current decision/action to be `ENTER_CALLEE` with no task match; create or bind the call record/active-call guard in the same transaction, or document the deferred FK and unique backstop. Add concurrency tests for two direct calls and for task-resolve vs direct-authorize on the same caller; an empty-taskId request on a task-backed call must reject.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-004-未修复-[高]-权益发放状态没有持久化归属，customer_order.entitlement_status 无法表达按行/期次状态
- **状态候选**: `accepted-candidate`
- **位置**: §10 entitlement state machine (plan line 302); `customer_order` row (186); `entitlement_grant`/`entitlement_balance`/`usage_reservation` rows (178-180); payment-to-entitlement sequence (315); S2/S3 handoff (416, 428).
- **问题类型**: 所有权缺失 / 状态机不可实施 / 跨模块状态
- **当前写法**: “Entitlement issuance: `NOT_ISSUED → PENDING → ISSUED`, with `FAILED` retryable”; unique “order/installment/type”; the consumer “writes grant, balance and Outbox in one transaction; payment state stays in `catalog-order`.” `customer_order` has one `entitlement_status` column owned by `catalog-order`; no entitlement-issuance row or per-grant status exists in `entitlement_metering`.
- **反例/失败场景**: An order with three benefit lines (recording minutes, AI minutes, storage) gets three grants; one line fails while two succeed. A single order-level `entitlement_status` cannot show “partially issued/failed”; if `entitlement-metering` updates that column, it writes another module’s table; if `catalog-order` updates it, it must trust or poll the consumer, making payment-to-entitlement non-atomic and non-observable per line. A 12-installment order also has no durable per-installment due/attempt state; `installment_no` has no check against the frozen order’s `installments`.
- **为什么有问题**: `docs/09` line 86 and `docs/10` line 22 require payment and entitlement status to be independent; `docs/12` line 328 requires separately observable states; `docs/12` line 368 requires uniqueness by order/installment/type. The plan’s state machine names a state that no table owns, and its only status column is too coarse and cross-owned.
- **直接证据**: Plan lines 186, 302, 315; source `docs/09` line 86; `docs/10` line 22; `docs/12` lines 328 and 368.
- **影响**: No code-generation-ready owner for `PENDING/FAILED`; multi-line and multi-installment orders cannot be represented; retries cannot be audited; a likely direct ownership violation.
- **建议改法和验证点**: Add an `entitlement_metering.entitlement_issuance` table/row (or a status/revision plus attempt history on a grant) owned by `entitlement-metering`: `order_id`, `installment_no`, `entitlement_type`, `status`, `attempt_count`, `revision`, `last_error`, `grant_id`, unique `(order_id, installment_no, entitlement_type)`, and state checks. Bind `installment_no` to the frozen order installment count/plan (check or service) and define the scheduler/due-date owner for future installments. Make `customer_order.entitlement_status` a derived read projection or remove it. Test a multi-line order with one injected failure, retry idempotency, and 12-installment issuance exactly once; update the 43-table count with controller approval.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-005-未修复-[中]-IVR 事件与决策未按事件域实施唯一性，和 D18/INV-35 冲突
- **状态候选**: `accepted-candidate`
- **位置**: D18 (plan line 145), INV-35 (284), `ivr.call_event` (175), `ivr.ivr_decision` (172), `usage_fact.source_event_id` (181); source `docs/13` §6.5 (243), §6.2 (174), `docs/10` §4 (49).
- **问题类型**: 约束缺失 / 事件域歧义 / 幂等性
- **当前写法**: D18/INV-35 say event/action identity is unique within its domain and that a table written by multiple domains stores `(event_domain,event_id)`. `call_event` enforces unique `(call_id,event_id)`; `ivr_decision` enforces partial unique `(call_id,source_event_id)` without `source_event_domain`; `usage_fact` has one `source_event_id` without a domain.
- **反例/失败场景**: An IVR replay sends the same `eventId` on call B after call A; `(call_id,event_id)` accepts both, so the same string exists twice in the IVR event domain. Two decisions on one call with the same source event ID but different source domains collide on the partial unique key. A usage fact from another source domain can collide with an evidence-domain source event.
- **为什么有问题**: `docs/13` line 243 says each `eventId` is unique in the IVR event domain. `docs/10` line 49 permits the same string across action domains but not within one domain. The plan’s D18 is a stated invariant; the table constraints do not implement it.
- **直接证据**: Plan lines 145, 172, 175, 181, 284; source `docs/13` lines 174 and 243; `docs/10` line 49.
- **影响**: Duplicate/misrouted IVR events and decisions can be accepted; replay/import validation cannot rely on the stated domain identity; audit traceability is weakened.
- **建议改法和验证点**: For `call_event`, either make the table IVR-domain-specific and unique `event_id`, or add `event_domain` and unique `(event_domain,event_id)`. For `ivr_decision`, use `(call_id,source_event_domain,source_event_id)` for the supplied-source-event constraint, or document that IVR event IDs are globally unique within the call. Add `event_domain` to any multi-domain source-event reference such as `usage_fact` if it is not exclusively one domain. Test the same ID on two calls, the same ID in two domains, and identical retries.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-006-未修复-[中]-激活确认缺少请求指纹/首结果契约，OPERATIONS 迁移事件身份未定义
- **状态候选**: `accepted-candidate`
- **位置**: `consent_record` row (plan line 169), `service_activation_transition` row (168), activation sequence (309), source `docs/10` §4 (49), `docs/13` §6.5 (241).
- **问题类型**: 幂等性缺失 / 事件身份 / 状态机
- **当前写法**: Activation sequence says a duplicate event returns the first result, but `consent_record` has only `event_domain`/`event_id` and no `request_fingerprint` or stored first-result reference; `service_activation_transition` has source action domain/event but no fingerprint. The table’s action domains include `OPERATIONS`, yet no operations action event ID source is specified, and unique constraints allow multiple NULL event IDs.
- **反例/失败场景**: The same `IVR_CONFIRM` event ID is retried with different consent text or prompt version. The DB unique `(event_domain,event_id)` rejects the duplicate as an error instead of returning the first result; or the service cannot compare fingerprints and accepts/rejects nondeterministically. An operations suspend/resume transition inserts a NULL `source_action_event_id`, so two operations transitions bypass the unique source-event identity and the transition history is not auditable by event.
- **为什么有问题**: `docs/10` line 49 requires same-domain same-key input changes to be atomically rejected while identical input returns the first immutable result. `docs/13` line 241 keys activation confirmation by `eventId + request fingerprint`. The plan declares the behavior in prose but does not provide the columns or a platform-idempotency binding.
- **直接证据**: Plan lines 168-169, 309; source `docs/10` line 49; `docs/13` line 241; source `docs/09` line 82 (operations source `OPERATIONS` and from/to revision).
- **影响**: Activation confirmation is not safely replayable; operations transitions can evade uniqueness; audit cannot prove one event per transition.
- **建议改法和验证点**: Add `request_fingerprint` and a first-result reference/snapshot to `consent_record` (or route the whole confirmation through `platform.idempotency_record` with scope `IVR_CONFIRM`), and require a non-null operations action event identity (for example, the audit request/event ID) for `OPERATIONS` transitions. Add checks that source action event IDs are non-null for all domains and unique. Test identical retry, changed consent/prompt on the same event ID, and two operations transitions.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-007-未修复-[中]-IVR call_id 链的父表 FK 未指定，INV-15 的 DB 约束无法生成
- **状态候选**: `accepted-candidate`
- **位置**: §8 ivr rows (plan lines 171-175), evidence call references (190-193), §10 sequence 3 (311), INV-15 (264), §12 V005/V006/V008 (366-369), final structural assertion 5 (547).
- **问题类型**: FK 缺失 / 迁移顺序 / 链接完整性
- **当前写法**: `ivr_decision.call_id`, `call_leg.call_id`, `call_event.call_id`, `call_record.call_id`, `usage_reservation.call_id`, `recording.call_id` and `evidence_record.call_id` are named, but only `ivr_decision.session_id` is explicitly assigned a FK; the plan says `call_id` is the protocol identity without naming the parent or deferring the constraint. The resolve transaction creates a reservation and decision but does not say it creates the call record.
- **反例/失败场景**: A generator creates the columns without FKs; orphan legs, events, reservations or evidence pass. Or it adds a FK from `ivr_decision`/`usage_reservation` to `call_record` in V005/V006, but resolve can create a decision/reservation before the first call event creates the call record, so the transaction fails. The plan’s “FK-linked chain” is then false in one direction or the other.
- **为什么有问题**: The success signal requires explicit FKs; INV-15 claims DB enforcement. A protocol identifier is not a substitute for a declared FK, and the final spec cannot choose the parent without deciding whether call record creation is part of resolve.
- **直接证据**: Plan lines 73, 171-175, 190-193, 264, 311, 366-369, 547.
- **影响**: Code generation can omit the critical IVR linkage; or create an ordering bug that only appears under the first inbound call; INV-15 is not actually enforceable.
- **建议改法和验证点**: Specify each `call_id` parent. Prefer `ivr.call_record.call_id` as the unique protocol parent for legs, events, reservation and evidence; either create/bind `call_record` in the resolve/direct-authorization transaction (status ACTIVE/UNKNOWN) or defer the decision/reservation FK until the call record exists. Name the exact wave and `ALTER TABLE` for any deferred FK. Test a fresh migration with only earlier waves, an orphan leg/event/reservation insert rejection, and resolve-before-call-record behavior.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PR-008-未修复-[高]-试用唯一约束允许非 FIRST-TRIAL campaign 绕过永久一次性规则
- **状态候选**: `accepted-candidate`
- **位置**: `trial_grant` (plan line 177), `trial_policy_version` (176), INV-16 (265), source `docs/10` line 20, `docs/09` line 84.
- **问题类型**: 唯一性约束 / 业务规则
- **当前写法**: INV-16 says `(subject_id, FIRST-TRIAL)` is permanently unique. `trial_grant` enforces unique `(subject_id, campaign_key)`; `trial_policy_version` permits any `campaign_key`; no check restricts the baseline trial to `FIRST-TRIAL` or a campaign registry.
- **反例/失败场景**: A rule-version change publishes a policy with campaign key `SECOND-TRIAL`; a second grant for the same subject is allowed. A typo or a future campaign key also creates a second trial. The unique key is satisfied because the campaign differs, while the source rule is violated.
- **为什么有问题**: The source fixes the trial uniqueness on the subject plus the first-trial campaign; claims, rule changes and re-entry must not reissue it. A per-campaign unique key is not equivalent.
- **直接证据**: Plan lines 176-177, 265; source `docs/10` line 20 (“`subjectId + FIRST-TRIAL` 永久唯一”); `docs/09` line 84 (`subjectId + campaignId` unique, frozen at issuance).
- **影响**: Multiple trials per subject are possible through a new campaign key; the core trial entitlement is not safely enforceable.
- **建议改法和验证点**: Add a check or campaign registry that admits only the approved first-trial campaign, and a unique partial index on `subject_id` for that campaign (or unique `(subject_id)` with `campaign_key = 'FIRST-TRIAL'`). Test a second campaign, a rule-version change, a claim and a cross-channel import; all must return the existing first trial.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-010-未修复-[中]-分享准入与 Redis 播放票据的失败重试契约未定义
- **状态候选**: `accepted-candidate`
- **位置**: §10 share sequence (plan line 317), state machine (305), `share_admission` (195), INV-26 (275), source `docs/12` §9.5 (335-338) and §10.1 (360).
- **当前写法**: PostgreSQL admission commits, then a Redis playback ticket is issued; “a ticket failure leaves the admission counted for an idempotent retry.” There is no admission/ticket status, no ticket key derivation, and no explicit retry path for a lost ticket.
- **反例/失败场景**: Redis is unavailable after the admission commit. The client retries with a new `admission_key` and consumes a second admission; or retries with the same key but cannot retrieve the ticket because the contract does not define how a ticket is keyed to the admission. A user is charged an admission without receiving a playback session, and no access event records the ticket failure.
- **为什么有问题**: The source requires only successful admission to count once and repeated same-admission submission to return the original session. The plan treats the admission as durable but leaves the ticket handoff and retry semantics outside the owned facts.
- **直接证据**: Plan lines 195, 305, 317; source `docs/12` lines 335-338; `docs/12` line 360 (Redis is reconstructible, not a permanent authorization fact).
- **影响**: Admission count can be over-consumed on retry; playback can be lost; the “count once” invariant is not testable across the Redis boundary.
- **建议改法和验证点**: Define the durable admission as the authorization fact and derive the ticket key from `share_grant_id + admission_id` (or the admission key). Require the same `admission_key` retry to return the existing admission and reissue the ticket without incrementing; add a `TICKET_FAILED`/`PLAYBACK_ISSUED` access event or a ticket generation/first-issued timestamp. If the source’s “create playback session in the same transaction” must be literal, store a durable playback-session fact and treat Redis as cache. Test Redis failure after commit, same-key retry, new-key retry, max admissions, and revoke/expiry generation checks.

- **严重程度（低/中/高/严重）**: 中

### PR-011-未修复-[中]-预占在缺少结束事件时的恢复/对账路径未进入计划
- **状态候选**: `accepted-candidate`
- **位置**: §10 usage reservation state machine (plan line 297), INV-19 (268), `usage_reservation` (180), source `docs/12` §9.1(7) (298), `docs/13` §7 (271).
- **当前写法**: States are `HELD → SETTLED / RELEASED`; “authorization expiry observed”; one terminal transition; no recovery transaction, no `RECONCILING`/`UNKNOWN` reservation state, and no rule for an expired HELD reservation whose IVR end event never arrives.
- **反例/失败场景**: The IVR never sends the end event. A naive expiry job releases the full reservation, so used recording seconds are uncharged and a later late event cannot recharge; or the reservation stays HELD forever, locking the balance. The source requires settling known use first, keeping the reservation occupied if authority is unavailable, alerting, and never full-releasing an unknown call.
- **为什么有问题**: Recovery is a confirmed goal condition; the plan records the happy path and state labels but not the partial-failure transition or owner. A code generator must invent the behavior, which the plan’s own “no invented business rules” rule forbids.
- **直接证据**: Plan lines 180, 268, 297; source `docs/12` line 298; `docs/13` line 271.
- **影响**: Silent undercharging or permanently stranded entitlement; no defined alert/reconciliation owner; INV-19’s “release once” is unsafe without an authority check.
- **建议改法和验证点**: Add an explicit recovery sequence and state: scan expired HELD reservations, query IVR authoritative usage by `callId`; if terminal/known, settle used units and release remainder; if unknown, keep HELD or enter `RECONCILING`, alert and block a new reservation for that caller; never release without authority. Add `reconciliation_due_at`/`reconciliation_status` or an equivalent fact, and a test for missing, late and duplicate end events.

- **严重程度（低/中/高/严重）**: 中

## Special review lenses

- **Goal-bound minimal design**: Partially passes. The plan maps the confirmed domains to tables and excludes AI/notary/refund/invoice/work-order/provider-configuration scope. It fails the “minimum complete” test because entitlement issuance has no durable state and activation/trial atomicity is not owned. The `platform-reliability` technical owner is a reasonable minimal cross-cutting choice, not a new product domain.
- **Architecture boundary**: Fails. Activation-consent “creates the first trial” in an entitlement-owned table; `customer_order.entitlement_status` is a cross-owned status; direct authorization bypasses the caller lock; cross-schema functions are the only intended write path but are not contractually defined.
- **Best practice**: Partially passes. Partial unique indexes, revision/conditional updates, append-only privileges, Outbox-in-transaction, HMAC lookup, ciphertext/masked fields and immutable snapshots are strong. Event-domain uniqueness, activation-confirmation replay, reservation recovery and share ticket handoff are not yet at the same standard.
- **Optimal solution**: Partially passes. The modular-monolith/PostgreSQL boundary and per-module ownership are the right path; the slice order and missing issuance state add avoidable review and implementation cost. A dependency-ordered transaction-core slice is simpler to verify than the current S1/S2/S3 split.
- **Overengineering**: Low risk overall. Separate tables for call legs/events, media, evidence events and share admissions are justified by independent facts/uniqueness; the plan avoids speculative AI/notary/refund tables. The 43/35 count freeze is a process overconstraint, not a modeling excess.
- **Overcoupling**: Fails/partially fails. S1 is coupled to S2 trial/IVR, S2 entitlement is coupled to S3 order, and S2 is said to depend on a “frozen S3 contract.” These are reverse dependencies; the plan needs a dependency-ordered contract or an explicit shared schema baseline.

## Slice-principle conclusion

The three slices are not behaviorally verifiable in the stated S1→S2→S3 order. S1 has forward dependencies on S2 tables and entitlement issuance; S2 has a forward dependency on S3 `customer_order`; and the plan explicitly says S2 depends on a frozen S3 catalog/order contract. This violates the controller’s slice principle and the plan’s own “later slices consume only frozen contracts from earlier slices” rule. The claimed “three slices are the minimum safe split” is not established. Recommended: re-slice by dependency order (S1 platform/identity/subject; S2 commerce+IVR+entitlement+activation transaction core; S3 evidence+sharing), or request controller approval for a fourth slice. Do not accept S1/S2 completion assertions until the slice dependency graph is acyclic and each slice can be migrated and tested on earlier slices only.
