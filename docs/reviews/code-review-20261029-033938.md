## 2. Findings

### F-PA5-AGG-B-01 - review launcher `wait` does not propagate child failures

**Entry / function:** `.pa5-s2-review-launch.sh` tail (lines 38-42).

**File / line:** `.pa5-s2-review-launch.sh:41` (`wait`), `:32` (per-role exit file), `:33` (`exit "$result"` inside subshell).

**Input scenario:** Both (or either) reviewer child subshells exit non-zero (for example timeout 124/137 or agent failure). The controller runs `bash .pa5-s2-review-launch.sh` and observes only the script's own exit status.

**Actual branch:** `launch A` and `launch B` start background subshells; bare `wait` collects them; `printf 'REVIEW_RUNNERS_EXITED\n'` runs; the script exits 0.

**Expected behavior:** A launcher that starts two review agents should surface a non-zero exit (or an explicit aggregated status) when any child fails, so a controller cannot mistake a failed review run for a successful one.

**Actual behavior:** Bash `wait` without arguments always returns 0 and does not propagate child exit codes. The script therefore prints `REVIEW_RUNNERS_EXITED` and exits 0 even when `$run_dir/A.exit` and `$run_dir/B.exit` hold non-zero values. `set -euo pipefail` does not help because `wait` itself succeeds.

**Direct evidence:** `.pa5-s2-review-launch.sh:41` is bare `wait`; `:32` writes `printf '%s\n' "$result" > "$run_dir/$role.exit"`; `:33` exits the subshell with that status; the parent never reads the `.exit` files. Empirically, `wait` with children exiting 7 and 9 returns 0.

**Impact:** A controller that gates on the launcher's exit status can proceed as if both reviews completed when one or both failed. The per-role `.exit` files are the only failure record and must be checked out-of-band.

**Fix direction:** After `wait`, read `"$run_dir/A.exit"` and `"$run_dir/B.exit"` and exit non-zero if either is non-zero (or use `wait -n` in a loop and accumulate statuses).

**Fix risk:** Low. The change is confined to the launcher's own exit path; it does not alter how reviewers are invoked or what they write.

**Severity:** Medium. This is an operational false-PASS risk in the S2 review pipeline, not a V005 data-integrity defect. It is pre-existing in a historical launcher that the aggregate-fix artifact explicitly left out of its fix scope; it is in this re-review's frozen scope.

### F-PA5-AGG-B-02 - plan §5.2 "Exact guard predicates" omits the post-fix terminal-freeze clauses

**Entry / function:** plan section "5.2 Exact guard predicates and error identifiers".

**File / line:** `docs/gateflow/pa5-v005-ivr-task-session-call-foundation-plan.md:296-309` (guard predicate lists), `:290` (aggregate-fix amendment prose that does describe the new semantics).

**Input scenario:** A reader relies on §5.2 as the authoritative "exact" predicate list after the aggregate fix.

**Actual branch:** §5.2 lists the pre-fix `guard_outbound_call_task` clauses (immutable set, terminal-to-live rejection, claim linkage) and the pre-fix `guard_call_record_parties` clauses (immutable set, task linkage) without the new terminal-fact-freeze clauses now present at V005:426-433 and V005:490-512.

**Expected behavior:** A section titled "Exact guard predicates" that is kept current with the implementation should list every rejection clause, including the terminal absorption rules added by the fix.

**Actual behavior:** §5.1's aggregate-fix amendment (line 290) describes the new terminal/confirmation/event semantics in prose, but §5.2's bullet lists were not extended. The two sections now disagree on what the guards reject.

**Direct evidence:** Plan:298 lists only `OLD.status NOT IN ('PENDING','CLAIMED') AND NEW.status IN ('PENDING','CLAIMED')` for the task guard; V005:426-433 also freezes status/reason/claim/terminal/updated/revision when the old status is terminal. **Impact:** Documentation drift inside the plan. A reviewer or implementer reading only §5.2 would under-estimate what the database rejects. The executable behavior is correct; this is a prose/authority inconsistency.

**Fix direction:** Extend the §5.2 bullets for `guard_outbound_call_task` and `guard_call_record_parties` to include the terminal-freeze clauses, or point §5.2 at the amendment as the authoritative post-fix predicate set.

**Fix risk:** Low. Documentation-only.

## 3. Verification of the three prior findings

### A-01 - terminal task/call facts could be rewritten

**Status: fixed.**

`ivr.guard_outbound_call_task` (V005:426-433) now rejects any substantive update when `OLD.status NOT IN ('PENDING','CLAIMED')`, covering status/reason, claim linkage, `terminal_at`, `updated_at`, and `revision`, with `OUTBOUND_CALL_TASK_TERMINAL`. The prior terminal-to-live rejection remains.

`ivr.guard_call_record_parties` (V005:490-512) treats `ENDED`, `FAILED`, and `REJECTED` as absorbing: their status, task/linkage, bridge/recording/end facts, authoritative seconds, reason, and revision cannot be rewritten. An `UNKNOWN` call may only converge to `ENDED` or `FAILED`; `UNKNOWN -> UNKNOWN` fact/revision rewrite and `UNKNOWN -> REJECTED` are rejected.

Probes: `v005TaskTtlLifecycleAndGuardBackstops` (IT:12765-12773) asserts `OUTBOUND_CALL_TASK_TERMINAL` for terminal-to-live and terminal fact rewrite. `v005SessionCallCanonicalCallerAndReciprocalLinkBackstops` (IT:13195-13242) asserts terminal call fact rewrite rejection, `UNKNOWN -> REJECTED` rejection, `UNKNOWN -> UNKNOWN` fact rewrite rejection, and the legal `UNKNOWN -> ENDED` convergence.

### A-02 - confirmed subject identity was not bound to session subject

**Status: fixed.**

`ck_inbound_session_confirmed_shape` (V005:134-140) now requires `confirmed_subject_id IS NOT DISTINCT FROM subject_id` and requires `confirmed_subject_id IS NULL` for every non-`CONFIRMED` status. Existing status/timestamp coupling is unchanged.

Probes: IT:13409-13420 assert exact `23514` and `ck_inbound_session_confirmed_shape` for a mismatched confirmed subject and for a non-`CONFIRMED` row carrying a confirmed subject. The confirmed-subject FK probe (IT:14062-14098) uses a savepoint-isolated drop of `fk_inbound_session_subject` to observe `fk_inbound_session_confirmed_subject` with exact `23503`, then restores both FKs.

Deparse map (IT:427-428) records PostgreSQL 16's canonical rendering of `IS NOT DISTINCT FROM` as `NOT (... IS DISTINCT FROM ...)`.

### A-03 - redacted event JSONB accepted missing/ill-typed members

**Status: fixed.**

`ck_call_event_payload_redacted` (V005:291-316) now requires `source.eventType` as a nonblank string, `source.legId` and `source.sequenceNo` as present values with their documented string/number-or-JSON-null types, and `receipt.eventFingerprint` as a lowercase 64-character SHA-256 string.
