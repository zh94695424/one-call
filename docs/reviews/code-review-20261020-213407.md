### C-02-部分修复-中-Web 固话生命周期仍可绕过规范状态

- **入口/函数**: Web 号码详情页的停用/重新开通动作，经 `setNumberActivation` 更新号码状态。
- **文件(行号)**: `web-prototype/evidence-hub.html:2123-2143`, `web-prototype/evidence-hub.html:2580-2593`; 当前回归仅覆盖 `web-prototype/qa/qa.js:222-272` 的 `phone-6208`。
- **输入场景**: 在个人号码列表打开仍提供生命周期按钮的固话 `fixed-6688`，先停用，再重新开通。
- **实际分支**: `setNumberActivation` 找不到与该号码关联的规范 `subjectId`，于是返回 `{ok:true,value:null,local:true}`；调用方继续修改页面本地号码状态并展示成功。
- **预期行为**: 任何可停用/重新开通的号码都应绑定规范主体，并通过共享 `setActivationStatus` 提交状态、修订号、迁移记录和幂等事件；找不到主体时应拒绝动作且不展示成功。
- **实际行为**: 页面状态在 `已停用` 与 `可取证` 之间切换，但 `businessSnapshot()` 在两次动作后均保持不变，且没有匹配主体或迁移。停用页同时显示整体 `已停用`、`ONECALL 内部服务: 已开通` 和 `内部记录待关联`；重新开通继续复用旧的静态授权事实。
- **直接证据**: `phone-6208` 的修复路径会调用共享 owner，但同一函数显式把缺失规范主体处理为成功的本地 fallback。可见 Playwright 复现中，`fixed-6688` 的 transition count 始终为零，停用及恢复前后的规范快照逐字节不变。现有 QA 只选择 `phone-6208`，没有覆盖该分支。
- **影响**: Web 可继续承诺一个无法被 Operations、Mini 或导出快照观察到的生命周期；状态、内部服务文案与授权事实彼此冲突。原 C-02 在单一手机号路径上已修复，但同类可操作号码仍保留原来的双真源问题。
- **建议改法和验证点**: 删除成功型本地 fallback。为每个可操作号码建立规范主体映射，或对非规范号码禁用生命周期动作并明确其只读状态。对全部号码类型做 stop/restore 参数化回归，断言规范状态、revision、transition/event ownership、授权事实、跨端导入、幂等重放和失败原子性。
- **修复风险（低/中/高）**: 中。需要明确固话记录与规范主体的身份映射及历史授权迁移策略。
- **严重程度（低/中/高/严重）**: 中。

### N-01-未修复-中-Operations 暂停/恢复绕过共享生命周期 owner

- **入口/函数**: Operations 用户详情中的暂停/恢复动作；共享 owner 为 `setActivationStatus`。
- **文件(行号)**: `operations-prototype/onecall-operations-admin.html:1193-1198`; `shared/onecall-business.js:231-247`; 不完整断言位于 `operations-prototype/qa/qa.js:52-53,139`。
- **输入场景**: 在 Operations 暂停普通活动主体；或先导入具有合法 `ACTIVE -> SUSPENDED -> ACTIVE` 历史的主体，再执行暂停。
- **实际分支**: Operations 复制快照后直接写入 `subject.activation` 和 `subject.revision`，再导入候选状态，没有调用 `setActivationStatus`，因而没有创建 `activationTransitions` 或 `processedEvents.ACTIVATION_STATUS`。
- **预期行为**: `shared/README.md:36` 声明 `setActivationStatus` 是暂停/恢复内部服务的共享所有者。所有入口都应通过该 owner 产生一致的状态、修订和可审计迁移。
- **实际行为**: 对没有迁移历史的 `SUB-1002`，暂停可把 `ACTIVE -> SUSPENDED`、revision `1 -> 2`，但两个迁移账本均保持为空，且快照仍被接受。对已有合法 Web 生命周期历史的主体，同一按钮反而返回 `业务校验拒绝变更，请检查当前对象与字段`，状态不变，因为直接写入与最后一条规范迁移冲突。
- **直接证据**: 直接状态写入发生在 Operations `1193-1198`；共享 owner 在 `231-247`。两个可见探针分别复现了“成功但无审计迁移”和“合法历史后控制失效”。现有 Operations QA 只检查状态及 grant 保持，不检查 transition/event ownership。
- **影响**: 同一个生命周期状态机存在两个写入者。Operations 可制造不可审计的规范状态，也无法继续管理已由 Web 合法推进的主体，导致跨端行为取决于主体历史。
- **建议改法和验证点**: 为共享 owner 增加明确的 `OPERATIONS` channel 或独立 actor/source 字段，并让 Operations 仅调用该 owner。增加无历史、已有 Web 历史、重复键、冲突键及导入回放测试，逐项断言迁移链、事件 ownership、revision 和失败原子性。
- **修复风险（低/中/高）**: 中。需要扩展共享 channel 契约并保持现有 Mini/Web 事件语义兼容。
- **严重程度（低/中/高/严重）**: 中。

### N-02-未修复-中-迁移账本缺少权威顺序且旧键重放跳过完整链校验

- **入口/函数**: `setActivationStatus` 的旧键重放、`snapshot`/`loadReviewSnapshot` 的 `activationTransitions` 校验，以及 `mutate` 的提前返回。
- **文件(行号)**: `shared/onecall-business.js:231-247`, `:512-521`, `:590-597`, `:630-631`, `:642-652`, `:675-682`。
- **输入场景**: 一是导入 `ACTIVE -> SUSPENDED`、`ACTIVE -> SUSPENDED` 的不连续链后重放第二个旧事件键；二是创建合法暂停/恢复历史后反转迁移数组，并把主体状态改成反转后数组尾部的 `SUSPENDED`。
- **实际分支**: 旧键路径只运行 coverage helper；`mutate` 收到 `DUPLICATE` 后在完整 `validateState` 前返回。完整校验只按当前数组顺序检查相邻 `from/to` 和数组尾部状态，迁移记录没有 revision/ordinal，时间字段也没有强制单调。
- **预期行为**: `shared/README.md:40` 承诺导入、任一旧键重放和新键写入共用完整域校验。迁移历史必须具有不可歧义的规范顺序，当前主体状态必须对应最后一个真实事件。
- **实际行为**: 第一组状态的 `snapshot` 返回 `INVALID_TRANSITION`，但重放第二个旧键返回 `{ok:true,code:'DUPLICATE'}`；新键才会正确拒绝。第二组反转后的历史被 `snapshot` 和 `loadReviewSnapshot` 接受，允许把当前状态回滚到较早的暂停事实，随后还能继续追加迁移。
- **直接证据**: 链连续性仅在 `validateState` 的 `512-521` 执行；coverage helper `590-597` 不验证顺序；`mutate` 在 `642-652` 对 replay 提前返回。两组独立 Node 探针分别证明旧键结果与快照有效性不一致，以及数组重排可改变权威当前状态。
- **影响**: 调用方可能在不可导出的损坏历史上收到成功重放；导入方也可通过重排合法记录回滚主体生命周期。后续动作会建立在错误的“当前状态”上，削弱审计和跨端一致性。
- **建议改法和验证点**: 给迁移持久化不可变 revision/ordinal，并校验唯一、连续、单调且与主体 revision/status 对齐；提取单一完整迁移账本校验器，供导入、旧键和新键路径共同调用。补充乱序、重复 revision、不连续链、尾状态错配、时间逆序及旧键原子拒绝测试。
- **修复风险（低/中/高）**: 中。需要决定 schema 兼容策略，并避免把数组位置继续当作未声明的顺序协议。
- **严重程度（低/中/高/严重）**: 中。
