### F-08-未修复-[高]-停用主体的 IVR 激活确认仍追加同意并尝试发放首试用

- **位置**: Plan §10 activation confirmation sequence line 424; activation state machine line 406; `inbound_session` row line 220; INV-08 line 365; INV-10 line 367; source `docs/10` line 29; `docs/12` §9.1 lines 295-296; `docs/09` line 82; `docs/13` §6.3 line 216.
- **问题类型**: 状态机漏洞 / 业务规则违反 / 权益与同意风险 / 不可直接实施.
- **当前写法**: Sequence 1 says: "If the activation row is absent, create it `ACTIVE` with an initial transition; if it exists `INACTIVE`, append one `INACTIVE → ACTIVE` transition ...; if it exists `ACTIVE`, keep the state and append no duplicate activation transition; if it exists `SUSPENDED`, do not self-resume; append the consent record; call `entitlement-metering.issueFirstTrial` ...". The `SUSPENDED` branch has no rejection; the sequence unconditionally appends consent and attempts the first trial. The activation confirmation state machine line 406 likewise says "insert consent/transition" without a suspension gate, and `inbound_session` line 220's `CONFIRMED` requirements are trusted caller, key `1`, current consent version and same confirmed subject only. INV-10 only prevents the state update, not the trial/consent.
- **反例/失败场景**: Operations suspends a subject for abuse or fraud. The subject has no prior trial. An IVR call from the trusted caller presses key `1` on the current prompt. The plan's transaction takes the `SUSPENDED` branch, appends a consent record, and calls `issueFirstTrial`. Because no `trial_grant` exists, `issueFirstTrial` returns `GRANTED` and writes `trial_grant`, `entitlement_grant`, `entitlement_balance` and Outbox while the activation remains `SUSPENDED`. The suspended subject has received a new trial and a consent fact; if the subsequent resolve/authorization path only checks activation status, the call may be rejected, but the trial/consent side effects already committed. If a later operations resume occurs, the trial is already there and is not a first-use grant after resume.
- **为什么有问题**: `docs/10` line 29 is explicit: only when the trusted caller, key `1`, current consent version and **subject not suspended** are all true may the session be confirmed, internally activated and a one-time trial attempted. `docs/12` §9.1 line 295 says the transaction "检查主体未停用" and line 296 says a suspended/without-valid-entitlement new session fails closed. `docs/09` line 82 says suspension only blocks new use, preserves history and does not reissue a trial. `docs/13` §6.3 maps a suspended subject to `REJECT_SUSPENDED` and no task claim. The plan's sequence directly contradicts these binding rules.
- **直接证据**: Plan line 424 (SUSPENDED branch "do not self-resume; append the consent record; call issueFirstTrial"); line 406 (activation confirmation inserts consent/transition without a suspension gate); line 220 (CONFIRMED requirements omit non-suspended status); line 367 (INV-10 only says cannot self-resume); source `docs/10` line 29 ("主体未停用时"); `docs/12` lines 295-296; `docs/09` line 82; `docs/13` line 216 (`REJECT_SUSPENDED`).
- **影响**: A suspended subject can receive a new trial and a consent record through IVR, leaking entitlement and contradicting the lifecycle. The state/history becomes inconsistent: `service_activation` remains `SUSPENDED` but `trial_grant` exists. An implementation agent following sequence 1 will generate the wrong behavior; tests that only check "no self-resume" will pass while the trial leak remains. This is a user-visible/account-abuse risk and a direct source-rule violation.
- **建议改法和验证点**: After locking the session and activation row, read the current `service_activation.status`. If `SUSPENDED`, reject the confirmation with a stable outcome (e.g., `REJECT_SUSPENDED`) and perform no consent, transition, trial, grant, balance, reservation or Outbox side effect; if the design needs to retain the rejected attempt, store only a rejected confirmation/access fact, not an accepted consent or trial. Test `GUIDE_ACTIVATION → DIAL_TASK_CALLEE`, `→ ENTER_CALLEE`, `→ GUIDE_PURCHASE`, `→ REJECT`, `REJECT_SUSPENDED`; an already-`ACTIVE` confirmation; a repeated confirmation; a repeated resolve after activation; and a task that expires between activation and recheck.
