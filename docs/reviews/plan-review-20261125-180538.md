- **影响**: 生成错误代码 / 路由不可用 / 实施 Agent 跑偏 / 验收不可通过。
- **建议改法和验证点**: 将 `backend/src/main/java/com/onecall/core/customer_iam/internal/web/CustomerBoundaryFilter.java` 加入 §13.4 修改路径，明确：(a) 新增 GET 集合与 GET `{orderId}` 的精确准入；(b) GET 不要求 `Idempotency-Key`/`Content-Type`，POST 行为不变；(c) 别名、额外路径段、错误方法仍 404；(d) web 测试同时断言“GET 被准入 + POST 别名仍 404”。

### RR-A6-未修复-中-投影暴露契约只点名非校验的 `projection(...)`，未定义 `storedSnapshot`/哈希比较的公开复用
- **位置**: 计划 §13.1 “expose existing `CustomerOrderSemantics.projection(...)` ... Validate stored hash and semantics before emission”。
- **问题类型**: 契约缺失 / 不可直接实施 / 架构边界。
- **当前写法**: 仅要求暴露 `projection(String full, String hash)` 并另行声称“Validate stored hash and semantics”。`projection` 本身只解析并重组字段，不检查 `snapshot_sha256`、键集合或语义（`CustomerOrderSemantics.java:195-202`）。
- **反例/失败场景**: 现有写路径的完整校验是三段式：`storedSnapshot(snapshot)` → `sha(canonical(parse(snapshot))).equals(snapshot_sha256)` → `projection(snapshot, hash)`（`JooqCustomerOrderRepository.java:104-113`）。如果新读路径只调用 `projection`，损坏/不匹配的快照仍会被“成功”投影；若实现者自行补校验，又违反“do not duplicate the mapper”，且没有计划授权暴露 `storedSnapshot` 或新增校验入口。若在公开接口新增 static 方法，还会触发 RR-A5 中 `getDeclaredMethods()==1` 的守卫冲突。
- **为什么有问题**: A1/B2 的接受结论不仅要求“映射正确”，还要求复用既有语义与哈希校验；当前计划只描述了一半（映射），校验入口和跨包复用方式未闭合。
- **直接证据**: `CustomerOrderSemantics.java:178-202`；`JooqCustomerOrderRepository.java:104-113`；`CustomerOrderCreationBoundaryTests.java:31`。
- **影响**: 生成未校验投影 / 契约与数据完整性缺口 / 门后返工。
- **建议改法和验证点**: 在 `catalog_order.customerorder` API 边界定义一个**校验型**投影入口（内部依次执行 `storedSnapshot`、DB `snapshot_sha256` 与重算哈希比较、`projection`），明确其公开签名、异常到 500/503 的映射，以及如何满足 `CustomerOrderCreationBoundaryTests` 的方法数/文件数守卫；增加“哈希不匹配/键集合漂移 → fail closed”的仓储或单元测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

- **问题类型**: 契约自相矛盾 / 不可直接实施。
- **当前写法**: “assert no pre-existing target grant for the grantor, then execute” 随后的 `GRANT SELECT (17 columns)` 块；同时又说 `432→449`（即 14 个新增 order 列）。
