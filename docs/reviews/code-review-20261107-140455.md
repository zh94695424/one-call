### F-02 — Authoritative `SELECT … FOR UPDATE` runs inside a read-only REQUIRES_NEW template; PostgreSQL will reject it, mapping every authorization to 503 (High; static runtime blocker)
- Entry/function: `DefaultShareMediaAuthorizationService.java:27-29` (`reads.setReadOnly(true)`), `:54` (`reads.execute(status -> authoritative(...))`), `:97` (`repository.lockGrant(...)`); `JooqShareAdmissionRepository.java:30-34` (`SELECT … FOR UPDATE OF grant_row`); `ShareAdmissionPersistenceConfiguration.java:64-78` (`DataSourceTransactionManager` with `setEnforceReadOnly(true)`, `TransactionTemplate` `readOnly=false` used to build the service).
- Triggering input: any valid `POST …/media-authorizations` request. The preliminary token read (also read-only) succeeds; the authoritative phase then opens a new read-only transaction and issues `SELECT … FOR UPDATE`.
- Expected: the authoritative read/lock transaction must be a read-write transaction (as PA17 does: `DefaultShareAdmissionService.java:75` uses `writes.execute(...)`, while PA17’s `reads` is used only for non-locking discovery at `:58-65`).
- Actual: `DefaultShareMediaAuthorizationService` builds `reads` from the same `sharingAdmissionTransactionManager` that has `enforceReadOnly(true)` and marks it read-only. PgJDBC applies the read-only mode to the explicit transaction; PostgreSQL rejects row-locking `SELECT … FOR UPDATE` in a read-only transaction (SQLSTATE 25006). The service’s `catch (RuntimeException)` at `:92-93` maps that to `DEPENDENCY_UNAVAILABLE` → HTTP 503. No PA18 test exercises this path (F-01), so the 295 green tests cannot refute it.
- Impact: the one required externally verifiable behavior is non-functional against PostgreSQL; every valid authorization returns 503. If the lock were reached without FOR UPDATE, the authoritative behavior would still be semantically wrong because the mutation phase is incorrectly read-only.
- Concrete fix + validation: use a read-write `TransactionTemplate` (e.g. the injected `writes` template, or a separate non-read-only `locks` template) for `authoritative`, keeping `reads` for the non-locking preliminary lookup; add a real PostgreSQL IT that performs an authorization through the production wiring and asserts 200 plus one durable success event. Validation: transaction manager `enforceReadOnly=true` and `SELECT … FOR UPDATE` must coexist only in read-write templates.
- Fix risk: Low (template switch); behavior becomes testable.

### F-03 — Lock order is inverted versus PA17 and the accepted plan (grant `FOR UPDATE` before ranks 7/8/9) (High; deadlock/contract)

### F-04 — An ended session/admission window maps to `SHARE_SESSION_POLICY_UNAVAILABLE` (503), never to `SHARE_SESSION_EXPIRED` (410) (High; frozen error surface)

### F-05 — Provider outage on a same-purpose success replay appends a new FAILURE event, and `Decision.priorSuccess` is dead state (High; replay semantics)
- Entry/function: `DefaultShareMediaAuthorizationService.java:145-155` (prior success stored in `Decision.priorSuccess`), `:195` (record component), `:66-77` (provider called unconditionally; on non-`Issued`/invalid result `appendFailure(...)` is invoked unconditionally), `:158-166` (`appendFailure` always inserts).
