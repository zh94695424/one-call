## 3. Assumptions tested

1. **The verifier port can be secure without a test bypass.** Test verifier is confined to `src/test` inside explicitly imported `@TestConfiguration`; no production bean/`test`/`dev` profile; zero/multiple adapters fail closed. This is structurally sound.
2. **Bearer parsing/audience/401-403-503 ordering cannot leak account existence.** The plan rejects malformed/multiple/tabbed/trailing-whitespace/query/cookie bearers before the verifier; missing/disabled account and invalid/revoked/disabled/wrong-audience sessions all return the same 401 shape; verifier/database unavailability is 503. No account selector exists. This is sound.
3. **Server-derived channel/account/workspace truth and one atomic snapshot.** Channel comes only from the verifier; the account filter is the authenticated UUID; one prepared statement projects account/membership/org under the same PostgreSQL statement snapshot. This is sound.
4. **Exact `customer_iam_role` grant, no reverse module dependency, no writes/locks.** The plan uses only granted columns, no DML/DDL/locks/caches, a read-only `REQUIRES_NEW` transaction with `SET LOCAL ROLE` and `current_user` assertion. This is sound.
5. **Optional-field/omission semantics and ordering.** The DTO/JSON matches the OpenAPI shape; personal omits org fields; org rows are DB UUID-ordered. Two ambiguities remain (see A-03/A-04).
6. **PA10 coexistence.** Qualified pools/DSLs/transactions and separate profiles are correct; the qualifier-only PA10 edit is required and does not change behavior.
7. **Spring MVC vs Spring Security and dependency firewall.** MVC is sufficient for one stateless bearer GET; custom filter avoids a Security dependency; default non-web is preserved by `web-application-type: none` and smoke tests. The JAR allowlist needs to be completed for the actual resolved graph (A-05).
8. **Test inventory.** 21+34 and 74+10 are internally consistent, but the reachability and test-context composition of the new web tests are underspecified (A-01/A-02).

## 4. Findings

### A-01-未修复-[中]-Reserved 403/422/429 mappings have no lawful HTTP producer but the plan requires them to be exercised by the actual HTTP test
- **位置**: Plan §7 error table (403/422/429 rows), §8 `CustomerMeWebTests` #8 and its "actual HTTP / no mocked boundary / no controller invocation" preamble, §4 no-bypass rules, §3 no input DTO.
- **问题类型**: 测试缺口 / 不可直接实施 / 过度验收标准.
- **当前写法**: 403 (`FORBIDDEN`), 422 (`VALIDATION_FAILED`) and 429 (`RATE_LIMITED`) are "reserved mapping[s]" with no role gate, no selector/body validation and no limiter. Test #8 nevertheless claims `allFrozenProblemMappingsAreClosedAndSanitized` via "known six codes via controlled test failures".
- **反例/失败场景**: A real `GET /api/v1/customer/me` with any headers/query/body cannot produce 403 (there is no `/me` role gate), 422 (there is no input DTO/body binding) or 429 (there is no rate limiter). To exercise them the test must either invoke `CustomerProblemWriter` directly (not the actual HTTP runtime) or add a test-only producer/controller/filter, which contradicts the stated no-bypass/no-mocked-controller rules.
- **为什么有问题**: The plan claims a 55-test exact inventory and real-HTTP evidence but does not name a lawful mechanism for three of the six codes. An implementation agent must invent one; either test-only production machinery appears or the assertion is weakened.
- **直接证据**: Plan §7 ("Reserved mapping is directly tested, not a new input policy"; 429 "reserved mapping only"), §8 `CustomerMeWebTests` #8, §8 preamble "Do not mock the boundary filter or invoke controller methods instead of HTTP", §3 `CustomerMeController` "accepts only servlet-derived Principal" (no input DTO), §4 "no production verifier bean ... no test bypass".
- **影响**: Hidden test bypass, weakened assertions, or CI inventory failure; the 55-test completion claim becomes unverifiable.
- **建议改法和验证点**: Choose and document one of: (a) test 403/422/429 at `CustomerProblemWriter` unit level with exact status/code/title/trace, and restrict HTTP assertions to 401/404/500/503; or (b) add a named, explicitly isolated test-only producer in the nested test configuration, justify it as test-only, and prove it cannot ship (JAR/source checks). Update the method names/counts and the CI inventory accordingly.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中.

### A-02-未修复-[中]-`CustomerMeWebTests` test-context composition is underspecified and collides with the production lazy persistence graph
- **位置**: Plan §8 `CustomerMeWebTests` preamble ("explicitly imported test-only verifier/repository configuration; no PostgreSQL"), §3/§4 `CustomerPersistenceConfiguration` (defines `customerContextRepository` and `customerContextService`, all `@Lazy`), §3 `CustomerMeController` (`ObjectProvider<CustomerContextService>`).
- **问题类型**: 不可直接实施 / 架构边界 / 测试缺口.
- **当前写法**: The web test uses the real filter/controller and a test-only verifier/repository, but the production `@Profile("web")` `CustomerPersistenceConfiguration` still defines qualified `customerContextRepository`/`customerContextService` beans. Spring Boot disables bean-definition overriding by default.
- **反例/失败场景**: `@SpringBootTest(classes = OneCallApplication.class)` + `@Import(TestConfig.class)` with a test repository/service: (i) a test bean with the same name collides (`BeanDefinitionOverrideException`); (ii) a differently named test repository makes the qualified production service still choose the production repository; (iii) the production service is lazy but the controller resolves it, so its `TransactionTemplate`/`DSLContext`/`DataSource` graph initializes and the empty `onecall.customer.persistence.*` credentials produce 503 for every authenticated request instead of the intended success path.
- **为什么有问题**: The plan says the web test is no-PostgreSQL but does not specify how to exclude the production persistence configuration or provide a test `TransactionTemplate`/`DSLContext`/repository/service. This is exactly the kind of wiring a code-generation agent must redesign.
- **直接证据**: Plan §3 (`CustomerPersistenceConfiguration` graph), §4 ("All persistence bean definitions are @Lazy"; controller holds `ObjectProvider<CustomerContextService>`), §8 (`CustomerMeWebTests` test-only verifier/repository). `SharingPersistenceConfiguration` shows the same bean-definition/qualifier pattern.
- **影响**: The authenticated success-path web test is not implementable as written without adding an unspecified test slice/exclusion mechanism; likely false 503s or bean failures.
- **建议改法和验证点**: Specify the exact test slice: exclude `CustomerPersistenceConfiguration` (test-only `@SpringBootApplication`/`TypeExcludeFilter`/registry post-processor), provide named test `TransactionTemplate`, `DSLContext`, `CustomerContextRepository` and `CustomerContextService` beans, and assert the production pool/service is absent. Add that test support file to §3's write set and to §8's support inventory.
- **修复风险（低/中/高）**: 中.
- **严重程度（低/中/高/严重）**: 中.

### A-03-未修复-[中低]-PERSONAL row synthesis is not specified; the SQL LEFT JOIN yields a NULL personal row only when the account has no usable organizations
- **位置**: Plan §5 ordering/projection, §6 SQL and "account with no usable organizations -> PERSONAL only", §8 `CustomerContextServiceTests` #2, `CustomerMeIT` #2/#4.
- **问题类型**: 契约缺失 / 不可直接实施.
- **当前写法**: §5 says "exactly one PERSONAL first, then ORGANIZATION rows"; §6 SQL is a `LEFT JOIN` to a derived table filtered to ACTIVE memberships/orgs, ordered by `w.organization_id ASC NULLS FIRST`; §6 says "account with no usable organizations -> PERSONAL only".
- **反例/失败场景**: For an ACTIVE account with two ACTIVE organizations, the derived table returns two matched rows and no `organization_id IS NULL` row; a repository that maps only `NULL -> PERSONAL` returns two ORGANIZATION workspaces and no PERSONAL. A repository that always prepends PERSONAL must special-case the no-org NULL row or it returns two PERSONAL entries for an account with no organizations.
- **为什么有问题**: The merge rule between the SQL result and the synthesized PERSONAL workspace is not explicit, yet the frozen JSON requires exactly one PERSONAL first in both cases. The named tests only cover personal-only and ordering, not "both personal and organizations".
- **直接证据**: Plan §5 ("exactly one PERSONAL first"), §6 SQL ("LEFT JOIN … ORDER BY w.organization_id ASC NULLS FIRST"), §6 ("account with no usable organizations -> PERSONAL only; filtered memberships must not remove the personal workspace"), §8 `CustomerContextServiceTests` #2 and `CustomerMeIT` #2/#4.
- **影响**: Missing or duplicate PERSONAL workspace; frozen response shape wrong; test #2 may pass while multi-org success is broken.
- **建议改法和验证点**: State explicitly that the repository always synthesizes exactly one PERSONAL row and appends DB-ordered ORGANIZATION rows, and that the SQL's NULL row is only the no-org case. Add a test case with both PERSONAL and ORGANIZATION rows plus an account with no organizations; assert exactly one PERSONAL in both.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中低.

### A-04-未修复-[中低]-The plan requires the service to reject "bad order" but does not define a PostgreSQL-compatible UUID comparator
- **位置**: Plan §5 ordering decision ("Test UUIDs crossing Java signed-UUID comparison boundaries; do not re-sort with UUID.compareTo"), §8 `CustomerContextServiceTests` #4 ("bad status/order ->500").
- **问题类型**: 并发/排序正确性 / 不可直接实施.
- **当前写法**: The service must reject an invalid projection, including bad order, while the repository orders UUIDs in PostgreSQL. The plan warns against `UUID.compareTo` but gives no validation comparator.
- **反例/失败场景**: PostgreSQL compares UUIDs as unsigned 128-bit values; Java `UUID.compareTo` compares two signed longs. A service-side order check using `UUID.compareTo` rejects a valid DB-ordered list whose UUIDs cross the sign boundary (or accepts a wrong order), producing 500 on valid data. The plan's own sign-boundary fixtures make this failure visible.
- **为什么有问题**: The plan requires an invariant that cannot be validated correctly without specifying the exact comparator, and the only comparator named is explicitly forbidden for sorting.
- **直接证据**: Plan §5 ordering paragraph; §8 `CustomerContextServiceTests` #4; `CustomerMeIT` #4 sign-boundary fixtures.
- **影响**: Valid contexts fail; tests may be written against the wrong comparator; inconsistent 500s.
- **建议改法和验证点**: Define an unsigned/lexicographic PostgreSQL UUID comparator for service-side validation and test fixtures, or move order validation to the repository/test and remove it from the service invariant list. Add a sign-boundary unit test against the chosen comparator.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 中低.

### A-05-未修复-[中低]-The JAR-firewall allowlist prose omits real transitive infrastructure (Micrometer, Jakarta annotation API) from the planned web graph
- **位置**: Plan §4 dependency list, §8 "CI and dependency firewall" (allowed MVC/Tomcat/Jackson family, one-to-one BOOT-INF/lib comparison).
- **问题类型**: 架构边界 / 依赖图与门禁缺口.
- **当前写法**: §8 says "Allow Boot MVC/servlet/Tomcat/Jackson infrastructure and their starter dependencies only; Framework spring-web/spring-webmvc compile; Tomcat embedded core/websocket/EL only when actually in that graph; … Jackson3 and its actual annotation dependencies are allowed". §4 enumerates the BOM-managed versions.
- **反例/失败场景**: Offline resolution of the planned `spring-boot-starter-webmvc` graph adds `io.micrometer:micrometer-observation:1.17.2`, `io.micrometer:micrometer-commons`, `jakarta.annotation:jakarta.annotation-api:3.0.0`, and `com.fasterxml.jackson.core:jackson-annotations:2.21`, none of which appear in the allowed-family prose. A hand-written positive allowlist rejects them; a negative-only regex (which does not ban Micrometer/Jakarta annotation) admits them without the promised exact manifest/version check.
- **为什么有问题**: The plan promises a one-to-one resolved-coordinate/BOOT-INF/lib firewall but lists only part of the actual graph; the firewall is only trustworthy if derived from the entry probe rather than the prose.
- **直接证据**: Offline `mvn dependency:list -DincludeScope=runtime` with the planned starter and PA10 persistence dependencies; plan §4/§8; cached starter POMs (`spring-boot-webmvc`, `spring-boot-http-converter`, `spring-boot-tomcat`, `spring-boot-starter-tomcat-runtime`).
- **影响**: CI/JAR gate false failure or unapproved artifact; implementation churn; the "exact" firewall evidence becomes incomplete.
- **建议改法和验证点**: Derive the allowlist from the entry-probe resolved runtime graph and `BOOT-INF/lib`; explicitly record Micrometer observation/commons, Jakarta annotation API, Jackson annotations and the existing r2dbc/reactive/checker support jars with versions/scopes; retain the negative firewall; update the README dependency inventory.

- **严重程度（低/中/高/严重）**: 中低.

### A-06-未修复-[低]-Global `spring.jackson.default-property-inclusion: non_null` is an over-broad serialization policy for one DTO
- **位置**: Plan §3 `application-web.yml`, §5 omission semantics.
- **问题类型**: 过度耦合 / 过度设计 / 契约风险.
- **当前写法**: The web profile globally sets Jackson inclusion to `non_null` so PERSONAL omits null organization fields and `Problem` omits optional fields.
- **反例/失败场景**: A future web endpoint relies on a nullable field (for example the canonical `*Page.nextCursor`, which docs/15 says may be null) or a contract that requires an explicit `null`; the global profile setting silently removes it. The current `/me` response is correct, but the setting is application-wide for a single-GET goal.
- **为什么有问题**: The omission requirement applies to three DTO records, not to every future JSON response. A profile-wide serialization policy creates a hidden contract dependency that is not part of the accepted scope.
- **直接证据**: Plan §3 (`application-web.yml` `non_null`), §5 omission rules; docs/15 §5 nullable `nextCursor`; OpenAPI optional fields are `additionalProperties:false` but not nullable where omitted.
- **影响**: Future contract regressions when the same web profile is reused; current security behavior unaffected.
- **建议改法和验证点**: Use targeted `@JsonInclude(NON_NULL)` on `CustomerContext`/`WorkspaceSummary`/`Problem` (or explicit response writers) and remove the global setting, or document the global policy as an explicit contract-wide decision with a regression test for nullable future fields.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

### A-07-未修复-[低]-44 new tests for one GET is heavy; several cases duplicate coverage or target unreachable codes
- **位置**: Plan §8 test inventory (34 Surefire + 10 Failsafe).
- **问题类型**: 过度设计 / 测试缺口.
- **当前写法**: Seven new Surefire classes (34 methods) and one Failsafe class (10 methods) for one GET. Boundary tests, web tests and service tests repeat parser/401/503/redaction cases; the 403/422/429 cases have no producer (A-01).
- **反例/失败场景**: The suite increases CI time and maintenance, and test fragility can force implementation to follow test scaffolding rather than behavior; the unreachable-code tests cannot prove the runtime path.
- **为什么有问题**: The security-critical invariants justify substantial coverage, but the plan does not justify the duplication or the reserved-code tests; 44 tests is disproportionate unless each maps to a distinct frozen contract or safety property.
- **直接证据**: Plan §8 method lists; A-01; PA10's 10 IT precedent and 21 Surefire baseline.
- **影响**: Not a security blocker; excess maintenance/CI cost and potential test-only scaffolding.
- **建议改法和验证点**: Keep the boundary/HTTP/PostgreSQL security tests; merge duplicated parser/redaction cases where the same code path is already covered; reduce 403/422/429 to writer-level unit coverage; state the mapping from each remaining test to a frozen contract or invariant.
- **修复风险（低/中/高）**: 低.
- **严重程度（低/中/高/严重）**: 低.

## 5. Open questions

1. **Reserved-code evidence (A-01)**: Will 403/422/429 be proven at `CustomerProblemWriter` unit level or through a test-only producer? The answer changes the 55-test inventory and must be explicit before implementation.
2. **Web-test service wiring (A-02)**: Does `CustomerMeWebTests` intend to run the real `CustomerContextService` with a test repository, or a test service? Which production configuration is excluded, and how is bean-definition ambiguity avoided?
3. **PERSONAL synthesis (A-03)**: Does the repository always prepend PERSONAL, and is the SQL NULL row only the no-organization case? A test with both personal and organization rows should be named.
4. **Order validation (A-04)**: Will the service validate order at all, and if so with which PostgreSQL-compatible comparator? If not, the test #4 "bad order" case must be reclassified.
5. **JAR allowlist (A-05)**: Will the allowlist be generated from the entry-probe manifest (recommended) rather than a hand-written family list? Micrometer/Jakarta annotation/Jackson annotations must be recorded.
6. **Global Jackson policy (A-06)**: Is `spring.jackson.default-property-inclusion: non_null` intentionally contract-wide, or should it be narrowed to the `CustomerContext`/`Problem` records?
7. **Test budget (A-07)**: Is the 44-test budget justified by distinct invariants, or should duplicated cases be merged?
8. **Profile-specific web type**: The plan relies on `application-web.yml` `spring.main.web-application-type: servlet` to override `application.yml` `none`. This is standard Boot config-data behavior, but the implementation-entry gate should record an actual startup proof before product edits.
9. **Entry-probe dependency graph**: The plan honestly states the MVC starter JARs are not resolved in the planning sandbox. The entry gate must record the effective POM, dependency tree, enforcer result and exact `BOOT-INF/lib` manifest before implementation.
10. **Query plan/index use**: The specified derived table does not bind `m.account_id` in the subquery; the planner may or may not push the outer authenticated UUID through the LEFT JOIN. Correctness is unaffected, but the plan's performance residual should include the actual `EXPLAIN`/index-use evidence if large membership tables are expected.

## 7. Final plan review conclusion

The plan is strongly grounded in the current code and canonical contracts: the V002 grants, OpenAPI `CustomerContext`/`Problem` shapes, docs/12/14/15/17, PA10 qualifier-only coexistence, default non-web behavior, module boundaries and baseline 21/74 inventories all check out. The security direction — custom MVC filter, provider-neutral verifier port, no production verifier/test bypass, one read-only statement under `customer_iam_role`, sanitized Problems, no writes/locks — is structurally sound and goal-aligned.

The material issues are implementation-readiness and test-design gaps, not a structural security failure: reserved 403/422/429 codes have no lawful HTTP producer (A-01), the web test context collides with the production lazy persistence graph (A-02), PERSONAL synthesis is unspecified (A-03), UUID order validation lacks a comparator (A-04), the JAR allowlist omits real transitive infrastructure (A-05), and the global Jackson inclusion is over-broad (A-06). A-07 is a low-severity test-budget observation. These are fixable without re-planning the single slice; however, A-01/A-02 should be resolved (or explicitly bounded) before the plan is treated as code-generation-ready.
