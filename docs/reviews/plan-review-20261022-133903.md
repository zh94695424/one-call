### F-09-部分修复-[中]-激活后 DIAL 分支只按“有效任务”判断，未把可用权益作为前提；复查也遗漏任务授权/工作区权限与风险状态

- **位置**: Plan §10 sequence 1 line 425; §8 `ivr_decision` row line 225; §11 `ivr.record_activation_next_action` row line 488 and contract line 490; §13 S2 completion line 759; test bullets lines 506-514; source `docs/13` §6.3 lines 208/219/224; `docs/12` §9.1 lines 295-296; `docs/10` lines 29/33; `docs/11` lines 11/46/69.
- **问题类型**: 契约缺失 / 状态机漏洞 / 权限边界 / 测试缺口 / 不可直接实施.
- **当前写法**: Sequence 1 says: "Recheck the current session/caller, the still-`ACTIVE` activation and consent, the current unexpired task using `clock_timestamp()`, and the available entitlement, then ... `DIAL_TASK_CALLEE` when a valid task exists (atomically claim the task, create or bind the active `call_record`, and create one reservation ...), otherwise `ENTER_CALLEE` when the subject is active with available balance, `GUIDE_PURCHASE` when active with no available balance, or `REJECT` ...". The DIAL branch's stated condition is a valid task only. The recheck also does not name current task authorization/workspace permission, subject risk/access, or the claim's `expires_at` guard at update time.
- **反例/失败场景**: (a) A subject has an unexpired `PENDING` task but zero available seconds (trial exhausted and no paid balance). The recheck sees a valid task and the branch returns `DIAL_TASK_CALLEE`, claims the task, creates a reservation and authorizes a call that the entitlement service cannot fund; or the reservation service fails and the whole confirmation rolls back, so an activation that should yield `GUIDE_PURCHASE` fails instead. (b) A task created under an organization workspace remains `PENDING`; the account's organization membership is revoked (or an `OPEN` risk is recorded) during the IVR prompt. The recheck sees the caller/session, activation, unexpired task and entitlement and claims/dials without rechecking current workspace permission or risk, unlike the resolve path. (c) The task is unexpired at the recheck but expires between the recheck and the claim `UPDATE`; the claim does not restate the `expires_at > clock_timestamp()` condition, so an expired task can be claimed.
- **为什么有问题**: `docs/13` §6.3 table line 219 requires DIAL only when the subject is activated, has available entitlement **and** has a valid task; a no-balance subject maps to `GUIDE_PURCHASE` (line 218). Line 224 requires the post-activation recheck of the still-valid task and entitlement and says activation success must not skip current state validation; the resolve checks current workspace permission, subject state and available entitlement (line 208). `docs/12` §9.1 step 5 requires the post-activation recheck of activation, consent and entitlement before reservation. `docs/11` line 69 makes server-side account/organization/membership/resource authorization the security boundary, and line 46 freezes the task's initiator/workspace/subject/callee. `docs/10` line 33 says an `OPEN` risk blocks claims. The plan's branch and recheck are narrower than these binding rules. The user's round-3 criterion explicitly requires rechecking task validity/authorization/expiry and entitlement after activation.
- **直接证据**: Plan line 425 (DIAL "when a valid task exists"; recheck list omits workspace permission/risk and task authorization); line 488 (service "claims the task" without the resolve's access checks); line 759 (S2 completion rechecks "session, caller, activation, task expiry and entitlement", not task authorization/workspace/risk); tests 513 (only expiry before the recheck); `docs/13` lines 208/218-219/224; `docs/12` line 296; `docs/11` lines 46/69; `docs/10` line 33.
- **影响**: A code-generation agent following the branch text can authorize a dial without available entitlement or after the task's workspace authorization/risk state changed, producing an unauthorized or unfunded call. Alternatively the reservation service fails and a legitimate confirmation cannot complete. The missing tests leave the primary post-activation priority path unverified. This is a material correctness/authorization gap in the S2 primary flow.
- **建议改法和验证点**: State the branch condition as `DIAL_TASK_CALLEE` only when the task is `PENDING`, unexpired at the claim `UPDATE` (`expires_at > clock_timestamp()`), caller/subject match, current workspace/creator access is valid, no `OPEN` risk blocks the claim, and available entitlement is positive. Otherwise return `GUIDE_PURCHASE` when active with no available entitlement, and `ENTER_CALLEE` only when no valid task and balance remains. Add to the recheck the current task authorization/workspace permission, subject risk/access and the task's PENDING/unexpired state; reuse the same claim WHERE conditions as the resolve sequence. Add tests for valid task + zero balance, membership revocation during the prompt, `OPEN` risk during the prompt, task replacement/cancellation during the prompt, and expiry between recheck and claim.

### F-10-未修复-[中]-同一 call 的不同 eventId 重复确认与 `(call_id, ACTIVATION_NEXT_ACTION)` 唯一约束冲突，返回或拒绝行为未定义

- **位置**: Plan §8 `ivr_decision` row line 225; §10 activation-confirmation state machine line 407 and sequence 1 line 425; §11 service row line 488 and contract line 490; §13 S2 completion line 759; tests lines 511-512; source `docs/13` §6.5 line 241 and §6.3 line 224; `docs/10` line 49.
- **问题类型**: 契约缺失 / 状态机漏洞 / 幂等性 / 测试缺口 / 不可直接实施.
- **当前写法**: Activation confirmation idempotency is `platform.idempotency_begin('IVR_CONFIRM', eventId, requestFingerprint)`; only an identical `eventId` replay is specified. `ivr.ivr_decision` is unique by `(call_id, purpose)`, the ACT purpose is one per call, and the service is described as persisting "exactly one" decision. The contract says "A repeated confirmation returns the stored `nextActionDecisionId` and action", but the sequence has no read-existing decision step for a *different* event ID, and the tests only cover "an identical confirmation replay" and "a repeat" after already-`ACTIVE`.
- **反例/失败场景**: The IVR sends a second confirmation for the same call with a new `eventId` (a re-prompt, a duplicate key press with a new event, or a client retry that regenerates the event ID). `begin` returns `NEW` because the key is different; `record_activation_confirmation` appends a second accepted consent (and no transition when already `ACTIVE`); `issueFirstTrial` returns `ALREADY_GRANTED`; then `ivr.record_activation_next_action` attempts a second `ACTIVATION_NEXT_ACTION` row for the same `call_id` and hits the `(call_id, purpose)` unique constraint. The whole transaction rolls back, including the second consent, but the IVR receives an opaque unique-violation rather than the session's next action, and a retry with the same new event ID repeats the failure. If the subject was suspended between the two confirmations, the SUSPENDED branch tries to mark an already-`CONFIRMED` session `REJECTED` and insert a second rejected decision; the plan has no `CONFIRMED → REJECTED` transition and the unique constraint again blocks it.
- **为什么有问题**: `docs/13` §6.5 line 241 defines activation-confirmation idempotency as `eventId + request fingerprint`; a different event ID is therefore a distinct request, not a replay. `docs/13` §6.3 line 224 requires the confirmation endpoint to return the session's next action, and `docs/10` line 49 requires identical input to return the first immutable result while a changed input is rejected. The plan's eventId-scoped idempotency and the call-scoped unique decision key collide for a second event ID, and the plan neither mandates returning the existing decision when the fingerprint matches nor defines a stable conflict for a changed fingerprint. The "repeated confirmation returns the stored decision" sentence does not specify the read-existing/fingerprint-comparison mechanism or its interaction with the SUSPENDED branch. The S2 completion assertion and tests do not cover a different event ID.
- **直接证据**: Plan line 225 (unique `(call_id, purpose)`; "same call/purpose with a different fingerprint is a conflict"); line 425 (begin by eventId; no read-existing step); line 488 ("Exactly one `ivr.ivr_decision`"); line 490 ("A repeated confirmation returns the stored ..."); tests 511-512 (identical replay/already-ACTIVE repeat only); `docs/13` line 241 (eventId + fingerprint) and line 224 (same call next action); `docs/10` line 49.
- **影响**: A duplicate confirmation with a new event ID can fail closed with an opaque uniqueness error or, if implemented naively, mark a `CONFIRMED` session `REJECTED`/attempt a second decision in violation of the state machine. The implementation agent must invent the behavior; retries can loop; the primary session's next action can be lost. This is a material idempotency/state-machine gap in the new fix-3 design.
- **建议改法和验证点**: In `ivr.record_activation_next_action`, under the canonical-caller lock, first select the existing `(call_id, ACTIVATION_NEXT_ACTION)` decision.
