### 5-未修复-高-重放"首凭证"前提为假：凭证不落盘、服务总会再调 provider，无状态 authority 无法在活时钟下保证首凭证一致

- **位置**: Plan §4/§5（issuer determinism、无 repository 的 authority）、§8（replay 语义）、§10（相关测试措辞）、§13（stop condition 引用的成功信号）；对照项目控制文件成功信号。
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口

- **严重程度（高）**

### 6-未修复-中-二进制编码未达 code-generation-readiness：长度前缀覆盖范围含糊，微秒精度拒绝规则与 PA18/活时钟冲突

- **位置**: Plan §4（binary token profile / canonicalization / timestamp precision / parser bounds / error mapping）。
- **问题类型**: 契约缺失 / 最佳实践偏离 / 不可直接实施
- **当前写法**: §4 描述 `ocmp1.<kid>.<payload-b64url>.<mac-b64url>` 二进制 payload 布局与"拒绝不可微秒表示"的时间戳规则，意图可直接生成 parser。
- **反例/失败场景**:
  1. 长度前缀（uint16 等）是否覆盖 UUID 字段、整数字段、变长字段未逐字段定义 → 两个实现（生成侧/校验侧）可对同一字节流产生不同解释，MAC 校验前的结构解析即分叉；
  2. "reject non-micro-representable" 与 PA18 `providerExpiry.truncatedTo(ChronoUnit.MICROS)` 混用：截断后可微秒表示，但若实现拒绝的是**截断前**来源或对 `Clock.systemUTC()` 纳秒值直接拒绝，则生产发证路径会随机失败（同一逻辑时刻纳秒余数非零即拒）；
  3. parser 边界（kid 长度、payload 最大字节数、未知字段）与错误映射（哪类错误 → `Invalid` vs `Unavailable`）若未逐条绑定到 PA19 三态，错误会被映射成 `Unavailable` 触发降级而非拒绝。
- **直接证据**: plan §4 文本；`DefaultShareMediaAuthorizationService` L79 `.truncatedTo(ChronoUnit.MICROS)`；`MediaPlaybackService`/`MediaCredentialVerifier` 三态（`Verified/Invalid/Unavailable`）；PA19 `validShape` 对窗口/时长的校验顺序。
- **影响**: 生成错误代码 / 跨实现不兼容 / 生产发证偶发失败（难复现）；错误映射不当导致本应拒绝的凭证被当作依赖不可用。
- **建议改法和验证点**: §4 增加逐字段编码表（偏移、类型、长度前缀是否适用、字节序）、canonical 序列化规则、精确到字段的微秒规则（明确"对截断后值判定，且截断发生在 issuer 侧"）、解析上限常量表，以及每个失败类别到 `Invalid`/`Unavailable` 的显式映射。验证点：用 plan 表格生成一组 golden bytes 与一组必拒样本，作为 `MediaPlaybackCredentialCodec` 测试的固定输入。
- **修复风险（低）**: 纯文档/契约补全，不改行为。
- **严重程度（中）**

- **问题类型**: 过度耦合 / 契约缺失 / 最佳实践偏离
- **当前写法**: §6 描述同一个 authority 同时作为 `MediaCredentialVerifier`（playback）与 `ShareMediaCredentialProvider`（admission）接入，但未钉死 bean 定义位置、条件注解与回退顺序。
- **反例/失败场景**: `ShareAdmissionPersistenceConfiguration` 有 `@ConditionalOnMissingBean(ShareMediaCredentialProvider.class) unavailableShareMediaCredentialProvider()`；`MediaPlaybackConfiguration.resolve()` 对 verifier/evidence/state/reader 在 `limit(2).count() > 1` 时抛 `IllegalStateException("Ambiguous playback authority")`。若新 authority 以两个 bean 类型分别注册且其中一个由 fallback 提前满足 → 要么 playback 侧看到两个 `MediaCredentialVerifier` 直接启动失败，要么 admission 侧拿到 unavailable fallback 而 playback 拿到真实实现 → 两接口行为分裂（同一凭证在发证侧有效、播放侧 `Unavailable`）。plan 未规定 bean 归属（`@Primary`/单一 bean 双接口/条件装配顺序）。
- **直接证据**: `MediaPlaybackConfiguration` L17–30（`resolve` + 歧义检查 + unavailable 回退）、L38–47（persistence 条件装配）；`ShareAdmissionPersistenceConfiguration` L115 附近 `@ConditionalOnMissingBean` unavailable provider。
- **影响**: 启动期歧义异常或静默的双实现分裂；环境差异（仅 persistence profile）导致行为漂移。
- **建议改法和验证点**: §6 明确：authority 注册为**单一 bean 同时实现两接口**、定义所在 `@Configuration`、与 `@ConditionalOnMissingBean` fallback 的先后关系，以及 `ObjectProvider` 消费方看到的数量恒为 1。验证点：上下文测试覆盖"仅 playback"、"仅 admission+persistence"、"两者皆开"三种组合，断言无歧义且 fallback 不与真实实现并存。
- **修复风险（低）**: 装配声明层面的收口。
- **严重程度（中）**
