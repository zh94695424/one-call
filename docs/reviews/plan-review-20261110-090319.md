## 3. Material findings

### 1-未修复-中-explicit-file-selection-can-be-suppressed-by-foreign-tencent-metadata

- **位置**: Plan §5 "Runtime configuration contract" conflict rules; §9D test `tencentAndFileMetadataConflictsCreateNoBuiltinProvider`; plan G5 "Explicit file selection survives"; binding control success signal at `project-execution-control.md:22`.
- **问题类型**: 范围漂移 / 目标漂移 / 状态机漏洞（provider selection semantics）
- **当前写法**: Plan §5 says: "a Tencent metadata property present with `provider=file`, or `bundle-path` present with `provider=tencent-ssm`, suppresses that built-in provider entirely." The plan's own test is named `tencentAndFileMetadataConflictsCreateNoBuiltinProvider` and §9D says conflicts create no built-in provider, including a file-only selector with foreign/empty fields.
- **反例/失败场景**: A deployment explicitly sets `onecall.sharing.media-playback.signing-key-source.provider=file` and a valid `bundle-path`, while an unrelated `...signing-key-source.tencent.region=ap-guangzhou` (or `tencent.secret-name`, or a timeout field, depending on the unspecified "metadata" predicate) is present from a prior Tencent attempt, shared config, system property or environment binding. Under the plan, the **file** provider is suppressed, so the application has zero key providers and the sole authority becomes permanently `Unavailable`; every playback issuance/verification fails closed with an availability outage even though the operator explicitly selected the file adapter.
- **为什么有问题**: The binding success signal says "The file adapter remains explicitly selectable and cannot become an implicit fallback. Unknown or conflicting provider selection creates no Tencent provider; multiple provider beans remain ambiguity-before-read." The control requires that conflicting selection creates no **Tencent** provider; it does not require suppressing the explicitly selected **file** provider. The plan's stricter rule goes beyond the contract and contradicts its own G5 "Explicit file selection survives". It also leaves "Tencent metadata property present" under-specified: region/name/version only, or all `tencent.*` including timeouts; `containsProperty` versus non-null/empty value. Different implementations will produce different file-suppression behavior.
- **直接证据**: Plan §5 conflict paragraph; plan §9D exact method and description ("conflict even on empty foreign fields"); plan §2 G5; control line 22 success signal. Current PA22 selector creates the file provider from literal `provider=file` and `bundle-path` only (`MediaPlaybackKeySourceConfiguration.java:11–19`); no existing behavior suppresses a selected file provider.
- **影响**: 实施 Agent 会按 plan 生成"provider=file + 任一 Tencent 字段 → 零 provider"的代码和测试；在真实配置混入时导致显式 file 选择失效、播放接口整体不可用。若 Controller 本意只是"不创建 Tencent provider"，则 implementation/test 需返工；若本意是"零 provider"，则 binding success signal 需显式修订。两种情况都不是干净通过。
- **建议改法和验证点**: Narrow the conflict rule to the control contract: when `provider=file`, ignore unselected `tencent.*` metadata and create the file provider only; when `provider=tencent-ssm` with `bundle-path` present, create no Tencent provider. Alternatively, if zero built-in providers is intentional, amend the Goal Confirmation/G5 wording and make the rule exact (enumerated conflicting keys and presence semantics). Update `tencentAndFileMetadataConflictsCreateNoBuiltinProvider` accordingly; add a test for stale foreign Tencent metadata with explicit file selection; assert zero SDK construction and zero file-bean suppression (or the amended behavior) in the architecture/config tests.
- **修复风险（低/中/高）**: 低（localized selector/condition and one test-name/assertion set; no production adapter or wire change）
- **严重程度（低/中/高/严重）**: 中

Status: `accepted-candidate` — plan text and control text are the direct evidence; Controller should adjudicate whether the stricter rule is intended.

## 4. Special review lenses

- **Goal-bound minimal design**: G1–G4 map to one adapter, one client and the unchanged parser/authority. G5 maps to selector/coexistence plus exact build/CI inventory. The plan does not add a cache, registry, audit writer, saga, public API, migration or deployment change. Finding 1 is the one place where a composition rule exceeds the confirmed success signal and contradicts G5.
- **Architecture boundary**: Only `TencentSsmSecretStringClient` is allowed to import the SDK; the provider stays in the existing keysource package behind `MediaPlaybackSigningKeyProvider`; the sole authority, codec, playback service and gateway remain untouched. Internal files are not exported as a named interface. This is consistent with the existing sharing boundary and PA21/PA22 ownership.
- **Best practice**: Fail-closed mapping, no secret logging, bounded UTF-8 parsing, no BOM/duplicate/trailing-token tolerance, immutable snapshots and defensive copies follow existing project conventions. Test determinism and network-free requirements are explicit. Gaps: SDK `TCLog` redaction is asserted from out-of-snapshot source inspection and is not exercised by the mocked-client tests (OQ-4); per-call SSM reads have unanalyzed rate-limit/cost implications (OQ-7).
- **Optimal solution**: Direct official `CvmRoleCredential` + pinned SSM SDK + unchanged PA22 parser is the smallest credible path that satisfies the confirmed goal without a generic cloud-secret SPI. A custom metadata client, cache or resilience framework would exceed the over-design boundary. The main solution risk is the CVM-only deployment assumption (OQ-1).
- **Overengineering**: The nested settings/reader/client-factory seams are bounded and non-exported; no new source file is proposed for conditions/settings. The strict region/name/version/timeout validation is more than the minimum but is defensive, deterministic and testable; I do not classify it as material overdesign. The exact firewall/test-count contract is heavy but consistent with the repository's established CI pattern.
- **Overcoupling**: The single slice legitimately couples config → SDK read → response conversion → parser → real authority tests, because that is the security boundary under review. It does not couple public contracts, DB/migrations, deployment or a second authority. The CI inventory and firewall changes are necessarily coupled to the same slice; the plan keeps parser/file/credential/playback files unchanged. The 43-method/test-count contract is brittle to an unverified mockability assumption (OQ-3), which is a rework risk rather than architectural overcoupling.
