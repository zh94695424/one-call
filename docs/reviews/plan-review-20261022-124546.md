### F-01-未修复-[高]-V001 提前创建 entitlement 函数，S1 的 INV-40/完成断言依赖 S2 表

- **问题类型**: 切片过粗 / 架构边界 / 迁移顺序 / 不可直接实施。
- **当前写法**: V001 "schemas and roles; ... then the four named functions and append-only triggers"；S1 覆盖 V001-V003，并声明四个跨 schema 函数通过 privilege、atomicity、replay、redaction 和 `search_path` 测试；INV-40 标注 "Verified in slice S1"。

### F-02-未修复-[高]-`platform.idempotency_begin` 没有首结果落库/完成路径，REPLAY 无法返回首结果

- **位置**: §6 item 10 行 138；§8 `platform.idempotency_record` 行 192；§8.3 矩阵行 290；§9 INV-27 行 374；§10 激活序列行 413；§11 函数表行 454。
- **问题类型**: 契约缺失 / 幂等性 / 并发恢复风险 / 不可直接实施。
- **当前写法**: §6 要求 "idempotency begin/complete"；§11 只定义 `platform.idempotency_begin`，返回 `NEW`/`REPLAY`/`CONFLICT` 和 `result_type`/`result_id`/`result_snapshot`；`NEW` 时 "returns NEW with no result"，`REPLAY` 时返回 "the stored first result"，但 "Never updates a stored result"；`platform.idempotency_record` 是 `APPEND_ONLY`。
- **反例/失败场景**: 第一次激活事务调用 `begin` 得到 `NEW` 和空结果，提交领域事实；客户端重试调用 `begin`，命中已有行，返回 `REPLAY`，但 `result_*` 仍为 NULL，无法返回首次结果。若调用方尝试直接 `UPDATE platform.idempotency_record` 补写结果，则违反 D9 的跨 schema 写限制和 APPEND_ONLY 生命周期；若增加一个 `complete` 函数但没有定义，生成器只能自行发明。并发下两个事务同时 `begin` 同一个 `(scope,key)`，朴素实现会触发唯一约束异常，而不是返回 `REPLAY` 或在同指纹下稳定串行化。
- **为什么有问题**: `docs/10` 第 49 行要求同域同键、输入一致时返回首次处理时保存的不可变结果快照；`docs/12` 第 281 行要求写请求保存请求指纹和首次结果；D10/INV-27/激活序列都依赖这个结果。没有完成路径，该契约不可实现。
- **直接证据**: 计划行 138（begin/complete）、192（append-only、result 列）、290（APPEND_ONLY）、374（first result on replay）、413（return stored first result）、454（begin semantics）。
- **影响**: 激活确认重放可能返回 NULL 结果或直接报错；生成器会发明不一致的 finalize 路径；幂等/审计验收无法执行；跨 schema 写边界可能被绕过。
- **建议改法和验证点**: 新增 `platform.idempotency_complete(p_record_id, p_result_type, p_result_id, p_result_snapshot, p_result_sha256)`，只允许在结果为空且指纹匹配时写入一次；或把 begin/complete 合并为一个原子函数。明确并发行为：`ON CONFLICT DO NOTHING` 后重新 `SELECT`，同指纹返回 `REPLAY`，不同指纹返回稳定 conflict SQLSTATE。测试：首次 NEW、同键同指纹 REPLAY、同键不同指纹 conflict、并发同键只产生一个结果、领域失败回滚 idempotency 行。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### F-03-未修复-[高]-证据创建事件 FK 目标不是唯一键，单列 FK 无法在 PostgreSQL 创建

- **位置**: §8 `evidence.evidence_record` 行 230；§8 `evidence.evidence_event` 行 232；§12 FK 行 579；§12 deferred FK 行 503；§10 sequence 9 行 421；INV-25 行 372。
- **问题类型**: 契约缺失 / 迁移不可生成 / 数据库约束错误。
- **当前写法**: `evidence_record.source_event_id` 有一个 "deferrable FK to evidence_event.event_id"；`evidence_event` 的唯一约束是 `(event_domain, event_id)`，`event_domain` 有 check `EVIDENCE`；deferred constraint trigger 在 commit 校验恰好一个 `EVIDENCE_CREATED` 事件且 event ID 相等。
- **反例/失败场景**: 最终 spec 生成 `ALTER TABLE evidence.evidence_record ADD CONSTRAINT ... FOREIGN KEY (source_event_id) REFERENCES evidence.evidence_event(event_id) DEFERRABLE INITIALLY DEFERRED;`。PostgreSQL 要求被引用列集合上有唯一约束或主键；`event_id` 单独没有唯一约束，只有 `(event_domain,event_id)`，因此该 DDL 报错 "there is no unique constraint matching given keys for referenced table"。迁移失败；deferred trigger 永远不会运行；PR-009 的 "reciprocal ownership" 没有按声明交付。
- **为什么有问题**: 这是 PostgreSQL 的硬性语义，不是风格问题。单列 FK 不能利用复合唯一约束的成员列；`event_domain` 是常量 check 也不改变被引用列集合必须唯一的要求。
- **直接证据**: 计划行 230（source_event_id）、232（unique `(event_domain,event_id)`）、579（FK 行）、503（deferrable FK 文本）、421（sequence 9）；原始 review PR-009 要求 "either a FK ... or an enforced trigger/service check"。
- **影响**: 迁移无法执行；最终 spec 不可 code-generation-ready；证据创建所有权无法按数据库约束验收；实现阶段会被迫重做 FK/触发器设计。
- **建议改法和验证点**: 二选一：(a) 在 `evidence_event` 增加 `UNIQUE (event_id)`（由于 `event_domain` 被 check 固定为 `EVIDENCE`，这是安全的），保留单列 deferrable FK；或 (b) 把 FK 改为 `(source_event_domain, source_event_id) REFERENCES evidence_event(event_domain, event_id)`，`source_event_domain` 列已存在，保留 deferred trigger。用 `psql` 验证迁移、唯一创建事件、重复/不匹配/缺失创建事件均按预期拒绝；同时验证循环插入在 deferrable FK 下可提交。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。

### F-04-未修复-[中]-`operations_audit.append_fact` 位于未声明的 schema，实际表属于 `audit`

- **位置**: §8 `audit.audit_fact` 行 194；§11 函数表行 456；D3 行 154；§12 V001 行 486/593；ownership contract 行 442-445。
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施。

- **建议改法和验证点**: 将函数统一命名为 `audit.append_fact`（与 `audit.audit_fact` 同 schema），更新 D11/INV-29/§8 行/§11 表/测试；或显式把 `operations_audit` 加入 schema ownership 矩阵、V001 创建顺序和授权模型，并把 `audit.audit_fact` 迁入该 schema。验证：`\df audit.append_fact` 可解析、owner 正确、domain role 无表权限但可 EXECUTE、search_path 不可被 shadow。
