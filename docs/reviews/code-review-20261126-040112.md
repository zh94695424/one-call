## Findings

### F-01 — High (blocking pending execution confirmation): privileges IT issues a bare `GRANT … TO PUBLIC` under a non-owner runtime role

- File: `backend/src/test/java/com/onecall/archtests/container/CustomerOrderReadPrivilegesIT.java:144,158,159`, in `customerRoleCanReadOnlyApprovedColumns`.
- Sequence: line 144 `SET LOCAL ROLE customer_iam_role` on the `pa27_customer` runtime connection (`connection.setAutoCommit(false)`); … line 158 `execute(connection, "GRANT SELECT(id) ON catalog_order.customer_order TO PUBLIC");` … line 159 asserts the customer ACL set still equals `current449Oracle()`.
- Static analysis says line 158 cannot succeed:
  - `pa27_customer` is provisioned `LOGIN NOINHERIT NOSUPERUSER …` (`backend/ops/postgresql/pa25-runtime-identities.sql:4304`); after `SET LOCAL ROLE` the effective `current_user` is `customer_iam_role`.
  - `customer_iam_role` is **not** the owner of `catalog_order.customer_order` (V020’s OWNERSHIP/PRESERVATION checks require `catalog_order_owner` to own the relation/schema, and `upgrade()` succeeding proves this).
  - Per the test’s own `current449Oracle()`, every `customer_iam_role` grant on `customer_order` carries `is_grantable = false`; V020 grants without `WITH GRANT OPTION` and its ACL equality would reject any `true`. So the role holds `SELECT(id)` **without** grant option.
  - PostgreSQL therefore raises `ERROR: permission denied for table customer_order` (SQLSTATE `42501`) for this GRANT.
- Because the statement is executed on the `autoCommit=false` runtime connection **without a savepoint**, the error aborts the transaction and propagates out of `execute(...)`; the method never reaches the intended ACL-oracle assertion at line 159. The test should therefore **error**, not pass.
- Consequence for the gate:
  - The implementation report §4 claims the PA42 Failsafe phase produced **"privileges 10 / 0 / 0 / 0"**. Either (a) this committed test cannot pass, so the ACL success signal is unproven and the candidate is not green as claimed, or (b) the executed bytes / reported evidence differ from the reviewed candidate. Both are blocking for a code-review close.
  - This does **not** indicate a product-code defect; the production read path and ACL model are consistent (below). It is an ACL-evidence/oracle defect.
- Recommended resolution (author’s call, outside this review’s edit authority):
  - If the intent is “a PUBLIC grant must not perturb the exact customer ACL set”, execute the GRANT on an owner/superuser connection (`fixture.admin()`), or wrap it with the existing `denied(connection, "GRANT …")` helper (/`setSavepoint` + rollback) if the intent is to prove denial. Then re-run `CustomerOrderReadPrivilegesIT` and refresh the report’s evidence.
- Caveat: Docker/PostgreSQL/Maven execution is not available in this review sandbox; confirm by running the single IT. The mechanism above is derived solely from the committed bytes and the accepted schema/provisioning.
