### F-01-未修复-高-T-S1-06 replay and same-account duplicate are not bound to the current request; a different organization can collapse into an accepted claim

- **Entry/function**: `T-S1-06` subject claim; replay branch and same-account duplicate branch.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1170-1177`; claim keys at `:720-721` and `:742`; INV-07 assertion at `:989`.
- **Input scenario**: (a) an existing accepted claim for subject `S`, account `A`, organization `O1` is replayed with the same `request_id` but a different `subject_id`, `account_id`, `organization_id`, binding or verification method; (b) a new `request_id` is submitted by `A` for `S` in organization `O2`, while an accepted `(S, A)` claim already exists for `O1`; (c) the same `request_id` is replayed after the current binding's risk state changed.
- **Actual branch**: Step 4 reads `subject_claim` only by `request_id` and returns the stored `ACCEPTED`/`REJECTED`/`CONFLICT` outcome without comparing the stored row's subject, account, organization, verification method or binding to the current inputs. Step 5 returns any accepted claim for `(subject_id, account_id)` without comparing `organization_id`. Step 6 only says to set `owner_account_id` or `owner_organization_id` when both are null and does not define whether a supplied `organization_id` requires organization ownership.
- **Expected behavior**: Claim replay is action-domain idempotency: the same key with changed semantic input must return a stable conflict, and identical input may return the stored immutable outcome. An organization-scoped claim must not silently reuse a personal or other-organization claim. The risk check must apply to the claim being replayed, not only to whatever binding the replay request happens to supply.
- **Actual behavior**: A client can receive `ACCEPTED` for a subject/organization combination that was never accepted; an accepted personal claim can make an organization-scoped request appear successful; a replay can bypass the original binding's open risk by supplying a different binding; and a subject can be treated as accepted for a different subject if the `request_id` is reused.
- **Direct evidence**: `subject_claim` stores `account_id`, optional `organization_id`, `verification_method` and `request_id`, but has no binding reference or request fingerprint (`:718-727`). The accepted partial key is `(subject_id, account_id) WHERE status = 'ACCEPTED'`, excluding organization (`:742`). T-S1-06 step 4 returns by `request_id` only (`:1173`); step 5 returns by subject/account only (`:1174`); step 6 leaves the owner choice indeterminate (`:1175`). The source rule requires same-domain idempotency to reject changed input and requires claim risk checks before replay (`docs/10-cross-channel-rules.md:49` and `:33`); the accepted plan's INV-07 requires risk before replay but does not authorize an unbound replay result.
- **Impact**: False accepted claims, cross-organization/cross-subject authorization ambiguity, risk-check bypass, and inconsistent subject ownership. Because `subject_claim` is append-only, the incorrect outcome cannot be corrected in place.
- **Suggested fix and validation**: Define an explicit claim replay identity (a canonical request fingerprint, or an explicit comparison of stored `subject_id`, `account_id`, `organization_id` null-safe, `verification_method`, and a binding/canonical-number identity when available). Return a stable `CONFLICT` on any mismatch and perform no owner change or new accepted row. Define the owner rule: if `organization_id` is present, the accepted owner must be that organization under the approved product semantics; if ownership is personal-only or organization is merely a workspace context, state that explicitly and reject an organization-scoped request that cannot be represented. Apply the check before returning any stored result and add tests for same request/different subject, same request/different account/organization, same account/different organization, and changed binding with open risk.
- **Fix risk**: Medium. A stored fingerprint or binding reference may require a spec/plan decision; the minimum service-level fix can compare stored subject/account/organization and revalidate the current binding.
- **Severity**: High.

### F-02-未修复-高-T-S1-06 fresh claim does not require the current binding, account and organization lifecycle predicates

- **Entry/function**: `T-S1-06` fresh subject claim before risk/replay/owner decision.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1170-1176`; binding status/verification at `:685-696`; workspace/account rules at `:1155-1158`; lifecycle writers at `:1207-1211`; source rule at `docs/10-cross-channel-rules.md:33` and `docs/12-technology-stack-and-system-architecture.md:265`.
- **Input scenario**: A claim names target subject `S` but supplies a binding whose `subject_id` is a different subject, a `DISABLED`/`RETIRED` binding, a disabled customer account, or an organization whose membership is `ACTIVE` while the organization is `SUSPENDED`/`DISABLED`.
- **Actual branch**: Step 1 describes the binding as “verified,” the account as “authenticated,” and the organization as “validated as an active membership.” Step 2 locks the subject/binding/risk rows. Step 3 performs the risk read for the supplied binding and proceeds to owner decision. There is no stated check that `caller_number_binding.subject_id = target subject_id`, `status = 'ACTIVE'`, `verified_at IS NOT NULL`, that the account is `ACTIVE`, or that the organization is `ACTIVE` as well as the membership.
- **Expected behavior**: The claim must use a currently active verified binding belonging to the target subject; the authenticated account must be active; an organization-scoped claim must require an active organization and an active membership. A retired/other-subject binding must be rejected with a stable error before risk, replay or owner mutation.
- **Actual behavior**: The service can claim subject `S` using another subject's number, use a retired binding as the claim evidence, or attach a claim to a suspended organization. Risk is evaluated against the supplied binding, so the risk check can be performed on the wrong number. The subsequent owner update can create an owner/claim relation that was never validly verified.
- **Direct evidence**: The binding table permits `DISABLED` and `RETIRED` (`:685`); only `ACTIVE` requires `verified_at` (`:696`). T-S1-06 step 1 supplies the binding and organization but states no status/subject/ownership predicate (`:1170`). The workspace rule requires `organization.status = 'ACTIVE'` (`:1157`), and lifecycle writers take the corresponding row locks (`:1211`). The source explicitly requires a verifiable number consistent with the target subject (`docs/10-cross-channel-rules.md:33`).
- **Impact**: Cross-subject claim, risk-check bypass on the actual number, claim into a non-usable organization, and an append-only accepted claim based on invalid evidence.
- **Suggested fix and validation**: After acquiring the locks, add explicit predicates: binding subject equals target subject, binding `status = 'ACTIVE'` with `verified_at` set, account `status = 'ACTIVE'`, and for an organization claim both organization and membership are `ACTIVE`. If the canonical number is supplied, verify its HMAC matches the binding. Return stable claim errors and add tests for other-subject, retired, unverified, disabled-account and suspended-organization bindings.
- **Fix risk**: Low. These are explicit predicates using existing columns and locks.
- **Severity**: High.

### F-03-未修复-高-Grant matrix grants function EXECUTE without schema USAGE, so the four V001 functions are not callable by the intended roles

- **Entry/function**: `platform.idempotency_begin`, `platform.idempotency_complete`, `platform.outbox_append`, `audit.append_fact` invocation by S1 runtime roles.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:77-79` (USAGE only on own schema; PUBLIC no USAGE), `:1262` (“cross-schema callers do not need table privileges”), `:1344-1347` (EXECUTE only), `:1450-1451` and `:1468` (migration grant steps).
- **Input scenario**: `customer_iam_role`, `organization_access_role`, `operations_iam_role`, `subject_number_role` or `operations_service_role` calls a function in `platform` or `audit`.
- **Actual branch**: The grant matrix grants `EXECUTE` on the functions but never grants `USAGE` on the `platform` and `audit` schemas to those roles. Section 2.1 states a module runtime role receives `USAGE` only on its own schema, and `PUBLIC` receives no schema `USAGE`.
- **Expected behavior**: A caller needs both `USAGE` on the containing schema and `EXECUTE` on the function. The specification should grant `USAGE` (without `CREATE`) on `platform` and `audit` to the named function callers, including `operations_service_role`, and include privilege tests.
- **Actual behavior**: PostgreSQL will reject the call with a schema permission error even when `EXECUTE` is granted. The V001/S1 privilege tests and every later S2/S3 caller contract would fail; an implementer might compensate with an undeclared broad grant.
- **Direct evidence**: `:77` limits module `USAGE` to the module's own schema; `:79` removes `PUBLIC` usage; `:1344-1347` lists only `EXECUTE`; `:1450-1451` says “grant EXECUTE per section 10.8.” No `GRANT USAGE ON SCHEMA platform/audit` appears in the grant matrix or migration steps.
- **Impact**: The central S1 cross-schema functions are unusable as specified; this blocks S2/S3 and invalidates the S1 completion assertions for function invocation.
- **Suggested fix and validation**: Add explicit `USAGE` grants on `platform` and `audit` (no `CREATE`, no table privileges) to the exact S1 role set in section 10.8, plus later roles in their waves, and add a privilege test that each granted role can execute the function while a non-granted role cannot.
- **Fix risk**: Low. This is a missing grant statement, not a design change.
- **Severity**: High.

### F-04-未修复-高-S1 grant matrix omits the cross-module SELECT privileges required by T-S1-04 and T-S1-06

- **Entry/function**: `T-S1-04` login/workspace resolution and `T-S1-06` organization validation; read-only collaborators declared in section 3.2.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:78` (cross-module reads use `SELECT`), `:166` (collaborators may read stable columns), `:983` (INV-01 assertion), `:1157` (workspace resolution reads organization/membership status), `:1170` (claim validates an active organization membership), and the grant matrix at `:1344-1357`; migration grants at `:1458` and `:1468`.
- **Input scenario**: `customer_iam_role` resolves the organization workspace list by reading `organization_access.organization_membership` and `organization_access.organization`; `subject_number_role` validates an optional organization membership and organization status for a claim; a collaborator reads a stable subject/binding column as declared in section 3.2.
- **Actual branch**: Section 2.1 states that cross-module reads use `SELECT`, and section 3.2 declares read-only collaborators. The grant matrix lists only the owning role's own-table privileges; it contains no cross-module `SELECT` grants for `customer_iam_role`, `organization_access_role`, `subject_number_role`, or any other collaborator. T-S1-04 step 3 requires reading `organization.status`; the INV-01 assertion at `:983` lists only `auth_identity`, `customer_account` and `organization_membership`, omitting `organization` even though the workspace rule requires its status.

Update the INV-01 read-set assertion to include organization status. Add a privilege test that each collaborator can read only the declared columns and cannot write the parent tables.
- **Fix risk**: Low. This is a grant/contract completion, not a new data model.
- **Severity**: High.

### F-05-未修复-高-Declared immutable identity, membership, binding and subject-owner relation columns remain fully updatable by application roles

- **Entry/function**: Identity bind/unbind, membership mutation, number-binding replacement, and subject owner mutation.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:490` (provider tuple immutable; identity never rebound), `:172` (no rebind), `:591` (re-grant membership inserts a new row), `:669` (owner immutable after claim), `:708` (binding replacement creates a new row), and the full-table grants at `:1351-1355`; migration grants at `:1455-1458` and `:1462-1468`.
- **Input scenario**: An owning runtime role executes an ordinary `UPDATE` that changes `auth_identity.account_id`, `provider`, `provider_scope`, `provider_subject_ciphertext` or `provider_subject_hmac`; `organization_membership.organization_id` or `account_id`; `caller_number_binding.subject_id`; `identity_profile.account_id`; or `business_subject.owner_account_id`/`owner_organization_id` after the owner was set.
- **Actual branch**: `customer_iam_role` receives `SELECT/INSERT/UPDATE` on all customer_iam tables, `organization_access_role` receives `SELECT/INSERT/UPDATE` on the organization tables, and `subject_number_role` receives `SELECT/INSERT/UPDATE` on `business_subject` owner columns and `caller_number_binding` (`:1351-1355`). No trigger or column exclusion prevents changing the relation columns. The only column-level restriction in the migration is for subject real-name (`:1467`).
- **Expected behavior**: The provider/subject tuple and identity-to-account relation are immutable; a membership or binding relationship cannot be moved to another organization/account/subject; and subject owner is set-once from null. Changing any of these requires a new row or an explicit approved transfer, not a same-row rewrite.
- **Actual behavior**: A service bug or a compromised module role can rebind an identity to another account, transfer a real-name profile, move a membership to another organization/account, reassign a business number to another subject, or overwrite a subject owner. The unique keys and FKs constrain current cardinality but do not prevent rebinding. This contradicts the dictionary's immutability text and the “no invisible account merge or historic evidence rewrite” success signal.
- **Direct evidence**: The explicit immutability statements at `:490`, `:591`, `:669` and `:708` have no corresponding trigger or column-level grant. The grant matrix at `:1351-1355` grants broad table `UPDATE`; no `BEFORE UPDATE` guard is specified. INV-02 is listed as `DB` but its enforcement location at `:984` names only the unique tuple and the account FK, neither of which rejects an update of `account_id`.
- **Impact**: Invisible account/identity migration, cross-account real-name transfer, membership history rewrite, subject/number reassignment, and a claim owner transfer that the state machine forbids. The database-enforcement claim for INV-01/02/03/05/06 is not satisfied.
- **Suggested fix and validation**: Either revoke `UPDATE` on the immutable relation columns and grant only the mutable columns, or add `BEFORE UPDATE` guard triggers that reject changes to `auth_identity.account_id`/provider tuple, `identity_profile.account_id`, membership `organization_id`/`account_id` outside the documented new-row flow, binding `subject_id`, and non-null subject owner changes. Add tests that direct role updates are rejected and that the approved status/role/revision updates still succeed.
- **Fix risk**: Medium. Column grants interact with the existing broad role design; triggers may need to tolerate migrations and privileged owner maintenance.
- **Severity**: High.

### F-06-未修复-高-`subject_identity_verification_role` has no SELECT on `business_subject.id`, so the only real-name writer cannot locate the row it is allowed to update

- **Entry/function**: Subject-level real-name verification flow (`subject_identity_verification_role`).
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1354` (SELECT/UPDATE on `real_name_status`, `real_name_verified_at`, `revision`, `updated_at` only), `:1467` (V003 real-name column grants), `:669` (only this role writes the two columns), `:995` (INV-33).
- **Input scenario**: The verification service executes `UPDATE subject_number.business_subject SET real_name_status = ..., real_name_verified_at = ..., revision = revision + 1, updated_at = ... WHERE id = :subject_id`.
- **Actual branch**: The grant lists `SELECT` and `UPDATE` only on the real-name columns, revision and updated_at. It does not grant `SELECT` on `id` or the relation/identity columns needed to read the row and return it.
- **Expected behavior**: The role needs `SELECT` on `id` (and the minimal read columns it must authenticate/return) to locate the subject, plus `UPDATE` only on the real-name columns and the revision/timestamp columns. A column-level update cannot safely locate the row without reading the key column.
- **Actual behavior**: PostgreSQL will require SELECT privilege on `id` for the `WHERE id = :subject_id` predicate. The specified role cannot perform its only intended update without an additional grant. An implementer may work around this by granting broader SELECT or by using `subject_number_role`, weakening the separation that INV-33 relies on.
- **Direct evidence**: `:1354` and `:1467` list the columns explicitly and omit `id`; `:669` says this role is the only writer of the real-name columns; `:995` makes that separation the INV-33 enforcement.
- **Impact**: INV-33's only writer is not usable with the stated grant matrix, or the separation is bypassed by an undeclared broader grant.
- **Suggested fix and validation**: Grant `SELECT` on `id` (and only the specifically needed read columns) to `subject_identity_verification_role`, keep `UPDATE` limited to the two real-name columns plus revision/updated_at, and test a successful update by ID plus rejection of owner/source writes.
- **Fix risk**: Low. This is a minimal column-grant correction.
- **Severity**: High.

### F-07-未修复-中-T-S1-07 replacement does not specify locking or validating the new canonical number, so replacement can race to a raw unique violation

- **Entry/function**: `T-S1-07` number binding create/replace.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1117` (the canonical-number key “protects … binding replacement”), `:1183-1189` (T-S1-07 steps), `:703` (partial unique active number), `:100` (raw unique errors are not a protocol success).
- **Input scenario**: A replace transaction retires binding `B1` for number `N1` and inserts a new binding for number `N2` while a concurrent create transaction binds `N2` to subject `S2` (or re-enables a disabled `N2` binding).
- **Actual branch**: Step 1 acquires “the” canonical-number advisory lock and step 2 reads the active binding for `number_hmac`; the sequence does not state whether these refer to the old or new number. Step 4 locks only the owned old binding row, retires it, and inserts a new binding for a different canonical number. No step acquires the new number's lock or validates that the new number has no active binding for another subject.
- **Expected behavior**: The replace operation should acquire both canonical-number locks in a deterministic order (or otherwise serialize both numbers), validate the new number's active binding, and convert any active-number unique loser into a stable conflict/current-state response.
- **Actual behavior**: A concurrent create/re-enable for `N2` can interleave. The partial unique index is the only backstop; the loser receives a raw unique violation, which contradicts the stable-outcome rule, and the spec does not define which caller wins or how the old binding is restored.
- **Direct evidence**: The canonical-number key is described as protecting binding replacement (`:1117`), but T-S1-07 step 4 names only the old owned row lock (`:1186`). The active-number uniqueness is a partial unique index (`:703`); the service contract forbids exposing a raw unique error as a protocol success (`:100`), and step 7 covers only concurrent operations on “the same binding row” (`:1189`).
- **Impact**: Binding replacement concurrency can produce an unexplained unique error, an ambiguous failure, or a replacement that cannot safely restore the old binding. This is in the S1 ownership/concurrency goal, not a later-slice behavior.
- **Suggested fix and validation**: State that replace acquires the canonical-number advisory locks for both the retired and new numbers in a fixed order (for example, sorted HMACs), reads the new number's active binding under that lock, rejects a different-subject active binding with a stable conflict, and handles the unique loser with one bounded reread. Add a concurrent replace/create test and a same-number replacement test.
- **Fix risk**: Low/medium. The additional lock is local; deterministic ordering is required.
- **Severity**: Medium.

### F-08-未修复-中-T-S1-05 account-active check is not serialized with account disable, so an identity can commit against a concurrently disabled account

- **Entry/function**: `T-S1-05` login identity bind; account disable writer.
- **File (lines)**: `docs/14-production-data-model-and-flyway-schema-spec.md:1163-1165` (bind checks account ACTIVE “at bind time”), `:1207-1211` (disable writer takes a row lock), `:1156` (login later requires account ACTIVE).
- **Input scenario**: Account `A` is disabled in one transaction while another transaction binds a new `auth_identity` to `A`.
- **Actual branch**: The bind service reads the account status, then inserts the identity, without locking the account row or making the account-status check conditional on a revision/state. The disable writer takes the account row lock and commits independently. Either serial order is possible; the bind can commit an `ACTIVE` identity row against an account that is now `DISABLED`.
- **Expected behavior**: The “a disabled account cannot gain a new active login identity” rule should hold for both serial orders: either the disable commits first and the bind fails, or the bind commits first and the subsequent disable leaves the account disabled with the identity retained. The bind should lock the account row and recheck status under the lock.
- **Actual behavior**: The identity can be inserted after the account is disabled; the inverse order can also leave an identity whose parent is disabled. Login is still blocked by the account status check, so this is not a direct authentication bypass, but it violates the bind-state contract and the missing serial-order test.
- **Direct evidence**: `:1165` states the requirement but `:1163-1164` define no account lock; `:1207` and `:1211` say the disable writer uses a row lock, so the bind must join that lock to serialize. The S1 invariant expansion's INV-02 test at `:984` covers concurrent identity inserts, not bind-versus-disable.
- **Impact**: A stale identity can exist for a disabled account and later be treated as a re-enable candidate; audit/state evidence does not match the rule; the claimed serialization test is absent.
- **Suggested fix and validation**: In T-S1-05, select the account row `FOR UPDATE` (or use an equivalent conditional check) and require `ACTIVE` immediately before the identity insert. Ensure the account disable/re-enable writer locks the same row. Add two-order concurrency tests asserting bind-fails-after-disable and bind-wins-before-disable.
- **Fix risk**: Low. A row lock on an existing parent is the minimum correction.
- **Severity**: Medium.

## Open Questions

- **Function-inserted row IDs.** The table dictionary says every `id` is application-generated with no database default (`docs/14-production-data-model-and-flyway-schema-spec.md:286`), but `platform.idempotency_begin`, `platform.outbox_append` and `audit.append_fact` have no `p_id` argument (`:1270`, `:1304`, `:1321`). Is the intended body `gen_random_uuid()` (PostgreSQL 16) or should the contract add an application-supplied ID? This is not counted as a finding because both are implementable, but the exact generation rule should be explicit before code generation.
- **S1/S2 lock-order compatibility.** S1 orders `business_subject` row lock before `caller_number_binding` (`:1116`), while the accepted plan's later S2 order reads/`FOR SHARE`s the caller binding and the subject owner after session/call/activation locks (`docs/gateflow/a0-production-data-model-schema-spec-plan.md:463`). If the S2 subject-owner access is a row lock in that order, it can invert S1's subject-then-binding order and deadlock. If it is a non-locking read, the S1 “later writers must use the same order” sentence should say so. Clarify without changing accepted plan policy.
- **Claim binding evidence at replay.** The accepted `subject_claim` column set has no binding reference or request fingerprint (`:718-727`). F-01 can be fixed for the stored subject/account/organization and the current binding's subject/status, but it cannot prove that a replay used the original binding unless the service re-verifies the current binding or the controller/plan authorizes a schema/contract addition. This needs an explicit decision rather than an inferred column.
- **Organization-scoped claim ownership.** The source requires production clarification of personal versus organization ownership (`docs/11-account-identity-and-workspaces.md:26` and `:67`), while T-S1-06 allows an optional `organization_id` and an indeterminate owner choice (`:1175`). If organization is only a workspace context, the claim must say so and must not set `owner_organization_id`; otherwise the claim must set organization ownership and reject a different organization. A Product/Subject-number policy decision is needed; F-01 must not guess it.
- **Subject real-name audit.** `subject_identity_verification_role` is the only writer of subject real-name fields, but it is not granted `EXECUTE` on `audit.append_fact` (`:1344-1347`).
