## Findings (severity sorted)

### F1 [Low] Paired Outbox delivery order is not guaranteed by the durable Outbox contract

**Direct evidence**
- `platform.outbox_append` inserts both events with `available_at = pg_catalog.now()`
  and a random UUID `id` (`backend/src/main/resources/db/migration/V001__platform_schemas_roles_idempotency_outbox_audit.sql:344-351`).
- The only pending-work index is `ix_outbox_pending_available (available_at, id)`
  (`V001...sql:97`). A dispatcher using that index can therefore see the two events in
  UUID order, not append order.
- PA38 appends the retirement first and the candidate publication second
  (`.../JooqCatalogSaleLifecycleRepository.java:134-135`), and tests assert only that
  append order (`OperationsCatalogVersionLifecycleIT.java:38`; `CatalogSaleLifecycleRepositoryTests.java:34`).
- No dispatcher implementation is present in `backend/src/main/java`; the ordering
  contract is therefore not visible in current bytes.

**Actual branch:** `codex/pa38-next-work-unit` (recorded; snapshot is Git-less).

**Impact:** A future consumer that naively processes events by
`(available_at, id)` per product can see `CATALOG_VERSION_PUBLISHED` for the new version
before `CATALOG_VERSION_OFFSALE` for the retired version. The payload carries
`versionNo` and `publishedAt`, so an order-aware consumer can disambiguate, but that
requirement is not documented as a contract. This is an integration-consistency risk,
not a current PA38 state-machine defect: both rows commit atomically.

**Fix direction:** Document a required consumer ordering key/event precedence (for
example aggregate `versionNo`, then `publishedAt`, then event type), or add a monotonic
delivery sequence in a later Platform/Operations migration. Do not add a schema object
in this gate.

**Fix risk:** Low for documentation/consumer contract; Medium if a future schema
sequence is chosen.

### F2 [Low] Outbox same-payload dedupe is silent; the historical fix1 artifact describes it as an error/rollback

**Direct evidence**
- `platform.outbox_append` performs `ON CONFLICT (event_domain, dedupe_key) DO NOTHING`,
  then selects the existing row for update. If the existing `payload_sha256` equals the
  incoming hash it **returns the existing id**
  (`V001...sql:344-369`); only a same-key/different-hash collision raises
  `OUTBOX_DEDUPE_CONFLICT` (`V001...sql:371`).
- `docs/gateflow/pa38-operations-catalog-sale-lifecycle-aggregate-deepreview-fix-1.md:40`
  states: “a duplicate paired Outbox raises a uniqueness error and rolls back the
  transaction, including its audit append.” That is not the shipped function's
  same-payload behavior.
- Current wording is closer but still imprecise: the implementation report says “an
  Outbox uniqueness failure rolls both back”
  (`docs/gateflow/pa38-operations-catalog-sale-lifecycle-implementation.md:18`), and
  fix2 says “paired Outbox `uq_outbox_domain_dedupe`”
  (`...aggregate-deepreview-fix-2.md:55`) without naming the same-payload return path.
- No current PA38 path reaches a duplicate append: the advisory lock plus the
  post-lock state short-circuit returns replay/stale before `appendAudit`/`appendOutbox`
  (`JooqCatalogSaleLifecycleRepository.java:116-123`), and `audit.audit_fact.request_id`
  has no uniqueness constraint (`V001...sql:394-418`; only a length check at line 416).

**Actual branch:** `codex/pa38-next-work-unit` (recorded; snapshot is Git-less).

**Impact:** The product behavior remains safe for PA38 because the state short-circuit,
not the Outbox error path, prevents a duplicate append. The documentation can mislead a
future unpaired audit writer or recovery hardening into believing that an Outbox
duplicate always raises and rolls back the audit; for identical payloads it silently
returns the existing event, so an audit-side duplicate would not be blocked by that
mechanism alone.

**Fix direction:** Correct the current implementation report/fix2 wording (and add a
correction note for the historical artifact rather than rewriting history): same-payload
duplicate → existing event id (idempotent, no exception); same-key/different-payload →
`P0001` and rollback; the durable replay guard for PA38 is lock + state short-circuit.
Do not add an audit uniqueness constraint or migration.

**Fix risk:** Low (documentation only).
