### 3.1 Exact graph and important limits

There are **six login identities**, **seven distinct effective roles** (four NOLOGIN roles plus the three direct logins), **ten distinct managed nodes**, and **four membership edges**:

```text
GRANT sharing_role         TO LQ WITH ADMIN FALSE, INHERIT FALSE, SET TRUE;
GRANT customer_iam_role    TO LC WITH ADMIN FALSE, INHERIT FALSE, SET TRUE;
GRANT sharing_command_role TO LW WITH ADMIN FALSE, INHERIT FALSE, SET TRUE;
GRANT evidence_role        TO LW WITH ADMIN FALSE, INHERIT FALSE, SET TRUE;
```

The placeholders in this explanatory SQL must be quoted as identifiers by implementation, not interpolated. `CustomerShareCommandsIT:76` explicitly grants both command/evidence memberships; its evidence projection assertions at lines 421–422 prove the second role is used on the same connection. Granting `evidence_role` to `sharing_command_role` instead would be a **reversed/wrong graph**, not equivalent provisioning. PostgreSQL checks role switching against the authenticated session's membership paths, including when its current role is already changed.

Allowed `SET ROLE` targets for the three assumption logins are respectively 1, 1 and 2; for direct logins there are no *other* allowed targets. Own-role operations, `RESET ROLE` and `SET ROLE NONE` are legal PostgreSQL identity restoration, not escalation. PostgreSQL cannot grant transaction-local switching while forbidding session-wide `SET ROLE` to the **same approved** role. The application chooses `SET LOCAL`; acceptance must not assert the stronger impossible distinction.

`NOINHERIT` on a PostgreSQL 16 login is insufficient by itself: every stored membership must additionally have `inherit_option=false`, `set_option=true`, `admin_option=false`. No nested edges, duplicate grantor edges, migration/owner role memberships, additional members of the four service roles or memberships granted *to* a managed login are allowed in this currently wired contract. Membership grantors must be non-runtime superusers; replay keeps the original compatible edge/grantor rather than issuing a duplicate GRANT under a different administrator.

**Do not confuse a query transaction with a SELECT-only database role.** Frozen `customer_iam_role` has V001/V002 writes/routines; frozen `evidence_role` has V008 evidence writes/routines. `LW` can therefore obtain the existing evidence-role capabilities, not merely one projection. PA25 neither narrows nor expands them. Tests prove query-path READ ONLY and deny cross-service role switching; they must not claim compromised customer/command credentials lack the broader already-approved capabilities of those roles. This residual belongs to Backend/Security, not a hidden PA25 ACL change.

### 4.4 Creation-only provenance; no adoption of existing unproven roles (A OQ-1)

**Decision for accepted `PA25-PLAN-A-01` / A OQ-1:** use one durable, nonsecret `COMMENT ON ROLE` marker on each script-created external login; no operator-attestation input or adoption mode. Compatible attributes, a chosen name, a password, or even the exact approved membership graph do not establish provenance. A pre-existing unmarked role is never adopted, even on initial apply. Platform/Database must choose absent approved names or obtain a separately authorized external disposition; this script never stamps an existing role to resolve a collision.

The exact marker grammar is `onecall:pa25:v1:db=<database_oid>:role=<role_oid>:slot=<slot>:name=<login_name>`, with no whitespace or final newline. Decimal OIDs have no leading zeros; `<database_oid>` is the current database's `pg_database.oid`, `<role_oid>` is that login's `pg_roles.oid`, and `<login_name>` is its validated current chosen name. The fixed slot mapping is `sharing_login` → `sharing_query`, `customer_login` → `customer_context`, `command_login` → `sharing_command`. The trusted provisioner constructs the marker from catalogs after CREATE ROLE and writes it using identifier/literal quoting (`format('%I', ...)` / `%L`); it is not a caller-supplied string. These OIDs are local identity bindings, not environment-pinned ACL-oracle OIDs. No secret, verifier, operator identity, endpoint or free-form payload belongs in the comment.

In **both modes**, global preflight reads the shared role comment for every existing `LQ/LC/LW` using `shobj_description(role_oid, 'pg_authid')` (the corresponding `pg_shdescription` row is keyed by role OID and class `pg_authid`) and compares it byte-for-byte to the marker independently reconstructed from the current database, role OID, slot and chosen name. NULL/empty, malformed, unsupported-version, changed or mismatched comments reject with `PA25_PROVENANCE_REJECTED` before any CREATE/ALTER/COMMENT/GRANT anywhere in the transaction. Do not accept a prefix match or infer/restore a missing marker from memberships. `check` additionally requires all three external roles and all four edges; `apply` alone may create absent roles and repair approved missing edges of marked roles. After reconciliation, both modes' exact postcondition verifies all three markers again along with the unchanged graph/ACL/history rules. Replay preserves existing marker bytes and OIDs; it never rewrites them.

Role rename, drop/recreate with a copied old comment, copying a marker between slots/roles/databases, and deletion or modification of a marker fail closed whenever the bound values no longer match. Comments are cluster-wide, so these bindings intentionally reject reuse of a marked login for another database. Restores that change OIDs require external disposition, not auto-restamping. The comment is an administrative provenance assertion, not a cryptographic signature: an authorized catalog-writing administrator can forge an exactly matching marker. Platform/Database/Security must control and audit such authority and serialize cluster-wide changes; neither this script nor a nonsecret attestation can authenticate against a malicious superuser. Direct-login and NOLOGIN migration roles retain their existing migration/history-based contract and receive no PA25 comment.

Any failure rolls back new roles, their comments, attribute reaffirmations and memberships together; existing unrelated roles/comments remain untouched. Missing/tampered provenance blocks rollout and is escalated to Platform/Database/Security; no automatic comment repair, adoption, revoke, rename, drop, password change or destructive rollback is allowed. There is no persistent helper schema/table/function, new migration, new role, datasource or generic identity registry.
