## 1. Goal, motivation, success signal

### 1.1 Binding goal (from Control, confirmed 2026-11-24)
Implement only the frozen operation `GET /api/v1/customer/catalog/offers`, operationId `listCustomerCatalogOffers`, through the existing customer datasource/pool and `customer_iam_role`, returning the currently authorized in-sale catalog offers using the merged V019 column privileges. Account, workspace and session channel are trusted facts; query parameters may only narrow within that authority. One existing customer-pool read-only transaction explicitly enters and verifies `customer_iam_role`, preserves pool state, and adds no pool, login, credential, role, membership, schema grant or migration.

### 1.2 Motivation
PA40A delivered the least-privilege ACL prerequisite (V019, 22 owner-issued column SELECT tuples) but deliberately added no HTTP endpoint, cursor, row visibility or application predicate. The frozen OpenAPI already defines this operation and its schemas; docs/15 §3.2 and docs/17 freeze its behavior. PA40B is the single end-to-end behavioral slice that turns the merged ACL into a working, fail-closed customer read without widening any contract.

### 1.3 Success signal
Real customer HTTP requests with a real customer login return only authorized ACTIVE offers; adjacent columns, wrong contexts, hidden fields and cursor widening are denied; DRAFT/OFFSALE/WITHDRAWN/wrong-channel/wrong-audience facts never appear; success, denial and dependency-failure paths cause zero business/audit/outbox/idempotency writes; PostgreSQL16 and web tests prove exact bytes, headers, error precedence, role restoration and that existing customer routes remain unchanged.

## 4. Endpoint contract decisions (exact)

### 4.1 Authentication and scope (goal clause 1)
Reuse `CustomerBearerAuthenticator`, `CustomerRequestPrincipal`, `TrustedCustomerCaller`, `CustomerBusinessNumberQueryService.requireScope`, and `JooqCustomerBusinessNumberAccessRepository.requireActiveContext` unchanged. Session channel (`TrustedCustomerCaller.Channel`) and selected workspace are the only authority. Audience is derived: `SelectedCustomerWorkspace.workspaceType == PERSONAL → PERSONAL`, `ORGANIZATION → ENTERPRISE`. Query `channel`/`audience` may only narrow: absent → trusted value; equal → trusted value (no-op); different → 403 FORBIDDEN (authority widening attempt). `offerType` absent → no narrowing (all four types); present → that type. An `offerType` whose intersection with the derived audience is empty (PERSONAL+QUOTE, or ENTERPRISE+SUBSCRIPTION/ONE_TIME/ADD_ON) is a valid narrowing yielding 200 `items:[]`, not an error. Account/workspace/price/token selectors are never trusted; no such query parameter exists or is read.

### 4.2 Customer-pool transaction (goal clause 2)
Add a dedicated `customerCatalogOfferTransactionTemplate` = ISOLATION_REPEATABLE_READ + PROPAGATION_REQUIRES_NEW + readOnly, on the existing `customerQueryTransactionManager`/`customerQueryDataSource`/`customerQueryDsl`. Inside it: `SET LOCAL ROLE customer_iam_role`, verify `current_user`, recheck current lifecycle, run the offer query and the benefit batch on the same snapshot. No Operations pool/identity. Pool role/transaction/settings restoration on success and failure is proven by IT (mirror `customerPoolRestoresRoleTransactionAndSettingsOnSuccessAndFailure` and `cleanPool`).

### 4.3 Owner boundary (goal clause 3)
Add ONE named `catalog_order` customer-query port `CustomerCatalogOfferReader` in a new package `com.onecall.core.catalog_order.customercatalogquery` annotated `@NamedInterface("customer-catalog-offer-query")`, plus internal jOOQ implementation `JooqCustomerCatalogOfferReader` and `CustomerCatalogOfferQueryConfiguration` in `com.onecall.core.catalog_order.internal.customercatalogquery`, wired to `@Qualifier("customerQueryDsl")`. Customer web/application imports only the public seam, never `catalog_order.internal`. A new named interface (rather than overloading `customer-subject-count-query`) preserves the count interface byte-frozen and follows the one-named-interface-per-capability convention; it requires customer allowed-deps 12→13.

### 4.4 Visibility and projection (goal clause 4)
Join product/version/offer/benefit only where `version.sale_status='ACTIVE'` AND `offer.offer_status='ACTIVE'` AND `offer.channel = trusted channel` AND `version.audience = derived audience` (+ optional `version.offer_type`). Never infer ACTIVE from the offer alone; never return DRAFT/OFFSALE/WITHDRAWN/other-channel/other-audience facts. Return exactly the 13 `CatalogOffer` fields and 4 `CatalogBenefitLine` fields. QUOTE `priceCents` is explicit JSON null; `currency` is the stored value (CNY). `versionToken` is the matching stored `catalog_offer.version_token`. Canonical benefit order = `entitlement_type` ascending (C collation; total because of `uq_catalog_benefit_version_type`). Zero benefit lines → `benefitLines:[]` (valid). Duplicate `(version,entitlement_type)`, orphan version id, null/out-of-range/unknown-enum fact → sanitized 500 INTERNAL (fail closed, list precedent).

### 4.5 Keyset pagination (goal clause 5)
Order `productCode asc, versionNo desc, catalogOfferId asc`; fetch `limit+1` offers BEFORE benefit fanout; default 20, inclusive 1–100; no offset/count. Anchor = `(productCode, versionNo, catalogOfferId)`. Mixed-direction keyset predicate (after anchor): `(p.product_code COLLATE "C" > ?) OR (p.product_code COLLATE "C" = ? AND v.version_no < ?) OR (p.product_code COLLATE "C" = ? AND v.version_no = ? AND o.id > CAST(? AS uuid))`. `hasMore = rows.size() > limit`; return first `limit`; `nextCursor` from last returned row, null on tail; empty page → `items:[]`, `nextCursor:null`, `hasMore:false`. Request-local REPEATABLE_READ snapshot; inter-request moving-row semantics are documented keyset (no global no-skip/no-duplicate promise): a committed insert before the anchor may appear, a deleted anchor is skipped, lifecycle is rechecked each request.

### 4.6 Cursor (goal clause 6)
New endpoint-isolated `CustomerCatalogOfferCursorCodec` + `CustomerCatalogOfferCursorProperties` (`@ConfigurationProperties("onecall.customer.catalog-offers")`, `cursorHmacKey`). Reuse the existing configured-secret mechanism: canonical standard base64 of exactly 32 bytes, no production default, mandatory even for first/empty pages, missing/invalid → sanitized 503 (lazy, after structural input validation). DOMAIN `onecall:customer-catalog-offers:cursor:v1\n`. Payload (big-endian): version byte `0x01`; 32-byte scopeBinding = SHA-256(`onecall:customer-catalog-offers:v1\n` + `productCode:asc,versionNo:desc,catalogOfferId:asc\n` + accountId + `\n` + workspace PERSONAL/ORGANIZATION:uuid + `\n`); 32-byte filterDigest = SHA-256(`onecall:customer-catalog-offers:filters:v1\n` + channel + `\n` + audience + `\n` + offerType-or-`ALL` + `\n`); 1-byte codeLength + ASCII productCode bytes; 4-byte versionNo; 16-byte catalogOfferId (msb/lsb); 32-byte HMAC-SHA256 over DOMAIN||preceding bytes. Total 118+codeLength bytes; `codeLength ∈ [2,64]` (V004 `ck_catalog_product_code` and OpenAPI `productCode` minLength 2 / maxLength 64), so 120–182 bytes. Base64url **without padding** length = `ceil(4N/3)`: N=120 → 160, N=182 → **243** (182 = 3·60+2 → 60·4+3). The exact unpadded range is **160–243 chars** (244 is the padded form, which the codec rejects); `nextCursor`/`Cursor` maxLength 512 remains satisfied. Decode precedence: structural corruption → CURSOR_INVALID; constant-time MAC mismatch → CURSOR_INVALID; constant-time scopeBinding mismatch (account/workspace/endpoint/sort replay) → CURSOR_INVALID; constant-time filterDigest mismatch (normalized channel/audience/offerType change) → CURSOR_FILTER_MISMATCH. `MessageDigest.isEqual` for all comparisons. Limit is deliberately not cursor-bound. Authorize adding `CURSOR_FILTER_MISMATCH` to `CustomerContextException.Code` and `CustomerProblemWriter` (400, title "Cursor filter mismatch"); do not broaden other endpoints.

Pinned public codec API (no implementer invention; mirrors `CustomerBusinessNumberCursorCodec` but variable-length):
```
public final class CustomerCatalogOfferCursorCodec {
    // Mirrors CustomerBusinessNumberCursorCodec Scope binding: organizationId == null ⇒ PERSONAL,
    // else "ORGANIZATION:" + organizationId. channel/audience are the trusted normalized values.
    public record Binding(UUID accountId, UUID organizationId,
                          String channel, String audience, Optional<String> offerType) { /* compact constructor: non-null accountId; non-null channel/audience valid enums; non-null Optional offerType (empty = ALL, no narrowing) */ }
    public record Anchor(String productCode, int versionNo, UUID catalogOfferId) { /* productCode ^[A-Z][A-Z0-9_-]{1,63}$ (2..64), versionNo>=1, non-null id */ }
    public CustomerCatalogOfferCursorCodec(CustomerCatalogOfferCursorProperties properties) { /* lazy key resolution: canonical base64 32 bytes else SERVICE_UNAVAILABLE */ }
    public String encode(Binding binding, Anchor anchor);            // round-trips validateStructure; failure → INTERNAL
    public static Anchor validateStructure(String value);            // structural only, no key needed; returns anchor or CURSOR_INVALID
    public Anchor decode(Binding binding, String value);             // CURSOR_INVALID / CURSOR_FILTER_MISMATCH per precedence
}
```

### 5.8 Anchor record mapping (codec ↔ request ↔ reader)
Three structurally identical records exist in distinct namespaces, each pinned earlier: `CustomerCatalogOfferCursorCodec.Anchor` (§4.6, customer web), `CustomerCatalogOfferReader.Anchor` (§5.1, catalog_order owner port), and the anchor carried by the service `Request`/`Page` (§5.4). They are **distinct types**, never assignable/castable to one another; the mapping is an explicit field-by-field copy, not an assignment.
- The unqualified `Anchor` in §5.4's `Request`/`Page` is **`CustomerCatalogOfferReader.Anchor`** (now qualified inline): the service speaks the owner port's anchor vocabulary, mirroring `CustomerBusinessNumberQueryService`, which uses `CustomerBusinessNumberReader.Anchor`.
- **Decode path (controller → service → reader):** the controller calls `codec.decode(binding, value)` → a **codec** `Anchor`, maps it field-by-field to a **reader** `Anchor` (`new CustomerCatalogOfferReader.Anchor(a.productCode(), a.versionNo(), a.catalogOfferId())`) and puts that in `Request.anchor`. The service passes `request.anchor()` (reader Anchor) directly to `reader.fetchOffers(scope, anchor, fetchSize)` with no further mapping.
- **Encode path (reader → service → controller):** the service builds `Page.nextAnchor` as a **reader** `Anchor` from the last returned `OfferRow` (`new CustomerCatalogOfferReader.Anchor(row.productCode(), row.versionNo(), row.catalogOfferId())`); the controller maps it field-by-field back to a **codec** `Anchor` and calls `codec.encode(binding, codecAnchor)` to produce `nextCursor`.
- This keeps the codec's own `Anchor` record exactly as pinned by A-04/B-06 (§4.6) and the reader's `Anchor` as pinned in §5.1; the trivial boundary copy is the only mapping. (The accepted business-number/evidence precedent collapses codec and reader to one shared reader `Anchor` type; PA40B keeps the two pinned records and maps explicitly at the web boundary, which is behaviorally identical and adds no path, method or total.)

## 8. State/error/cursor/HTTP matrices and ordering

### 8.1 Deterministic error precedence (exact)
1. Route/method/alias/trailing/encoded mismatch → 404 NOT_FOUND (boundary filter, before auth).
2. Authentication missing/malformed/cross-audience → 401 UNAUTHENTICATED; verifier outage → 503 SERVICE_UNAVAILABLE.
3. **Accept incompatible / q=0 → 500 INTERNAL** (boundary filter `CustomerBoundaryFilter.java:139–148`, after auth and before the controller runs; matches `CustomerEvidenceWebTests.java:443–444`). This gate is positioned explicitly so `errorPrecedenceIsDeterministic` asserts e.g. "incompatible Accept + invalid limit → 500", not 422.
4. Workspace selection shape invalid (null/inconsistent) → 503 SERVICE_UNAVAILABLE (requireScope, controller/service).
5. limit repeated/non-numeric/out-of-range → 422 VALIDATION_FAILED.
6. channel/audience/offerType repeated/unknown enum → 422 VALIDATION_FAILED.
7. channel/audience conflict with trusted authority → 403 FORBIDDEN (controller; service backstop per §5.4 step 1).
8. cursor repeated/structural corruption → 400 CURSOR_INVALID.
9. cursor key absent/invalid → 503 SERVICE_UNAVAILABLE (lazy).
10. cursor MAC/scope-binding mismatch → 400 CURSOR_INVALID.
11. cursor normalized-filter-digest mismatch → 400 CURSOR_FILTER_MISMATCH.
12. DB role entry/transaction/pool/dependency failure → 503 SERVICE_UNAVAILABLE.
13. lifecycle recheck inactive account/organization/membership → 403 FORBIDDEN.
14. projection/corrupt-fact failure → 500 INTERNAL.
Rationale: the boundary filter resolves route→auth→Accept before the controller; filters must be normalized before the cursor filter digest can be verified, so authority/conflict (7) precedes cursor decode (8–11); this mirrors the accepted business-numbers precedence (route→auth→workspace→limit→structural cursor→key→MAC/scope→lifecycle) with the Accept gate and the two new filter steps inserted deterministically.
**No invented limiter / no 429.** `RATE_LIMITED` remains in the frozen OpenAPI error-code set (§3.1) but this endpoint never emits it: there is no rate limiter in the customer read path, and PA40B adds none (same accepted position as the Operations read slices). `CustomerProblemWriter` keeps its existing `RATE_LIMITED→429` case for other endpoints unchanged; no §8.1/§8.2/§8.3 row produces 429.
