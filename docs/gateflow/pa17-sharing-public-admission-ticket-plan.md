## 2. Frozen contract to implement

### 2.1 Request and lookup

1. For POST admission only, construct `ShareAdmissionCapabilityToken` from the path: non-null, exactly 1–512 Unicode code points, no NUL, UTF-8 encodable (reject unpaired surrogates), and no path-separator/encoded-path confusion after the existing boundary filter. Invalid shape maps to `422 VALIDATION_FAILED` before any DB access. Hash its defensively copied exact UTF-8 bytes without normalization with `@Qualifier("sharingAdmissionSha256Provider") ShareAdmissionSha256Provider`; query only `sharing.evidence_share_grant.capability_token_hash`. Never log, persist, return, or include the raw token or digest in an HTTP response, problem detail, event payload, test diagnostic, or exception message. A missing or retired digest is uniformly `404 SHARE_TOKEN_INVALID`.
2. Bind the body as a closed JSON object with exactly `admissionRequestId` and `verification`. `admissionRequestId` is a nonblank 1–128 UTF-8-code-point stable request key with no normalization or case folding. `verification` is a closed object with discriminator `mode` and exactly one of `NONE`, `EXTRACTION_CODE`, `DESIGNATED_MOBILE`, or `ORGANIZATION_MEMBER`:
   - `NONE`: only `{mode:NONE}`; result `NOT_REQUIRED`; never a verified identity.
   - `EXTRACTION_CODE`: `{mode, code}`; `code` is write-only, 1–128, never echoed, logged, persisted, or fingerprinted in raw form. Compare through a provider using the grant salt/hash and current `code_generation`; do not invent KDF parameters.
   - `DESIGNATED_MOBILE`: `{mode, verificationProofId}`; the provider must prove approved trusted SMS possession for the exact grant-bound normalized number and intended share/action. HMAC knowledge or a supplied phone number is not proof. Missing, malformed, ambiguous, or unavailable proof fails closed.
   - `ORGANIZATION_MEMBER`: `{mode}` only; require the trusted current `CustomerRequestPrincipal` and current session account. No account, organization, membership, or tenant identity is accepted from request JSON.
3. Use the existing strict Jackson binder pattern (`FAIL_ON_TRAILING_TOKENS`, duplicate detection, explicit key allowlist) and return only the frozen `Problem` envelope. Path, body, content-type, schema and auth validation all precede new proof and any replay success. The boundary filter retains priority for any present invalid/ambiguous bearer (401 before controller/body processing); otherwise invalid JSON, unknown/duplicate keys, trailing tokens, unsupported content-type or wrong verification branch always produce `422 VALIDATION_FAILED`, even when the request key already exists, and never replay. Only a schema-valid same-key request may ignore changed, denied, malformed-at-provider or unavailable newly submitted proof; malformed request structure is never ignored. Do not edit OpenAPI; the existing operation and schemas are authoritative.

### 2.2 Verification and ordering

- Compute `admissionKey = "admission:" + lowercaseSha256(canonicalJson({shareGrantId, admissionRequestId}))`, with canonical UUID text and the exact request ID. Persist only its exactly 74-character value (`admission:` + 64 lowercase hex); raw `admissionRequestId` is never persisted, logged, audited, returned, emitted or stored as a standalone field. It may be consumed only to derive deterministic `admissionKey` and `requestKeyDigest` via the frozen SHA-256/canonical functions; derived digests are permitted where frozen and never expose the raw value.
- Replay ordering is binding: resolve the token digest and grant identity without a row lock; derive the admission key; perform a bounded preliminary admission/witness existence read. That read is read-only/advisory-only: for `ORGANIZATION_MEMBER`, any lifecycle advisory locks needed by replay/current-member checks are transaction-scoped inside this short read transaction, and no grant row is locked. If an admission exists, close the preliminary read and use the replay write transaction below; do not verify newly submitted proof. If no admission exists, close every transaction and lock before fresh proof. A schema-valid same-key replay ignores changed or unavailable newly submitted proof and reconstructs from the witness only after the final authoritative checks below. `LOCKED` permits an already-admitted unexpired session to replay; a new key is denied. Replay never repeats verification.
- Only a preliminary miss proceeds to fresh proof. Obtain the approved policy and perform fresh code/mobile/member proof with no PostgreSQL transaction, row lock, advisory lock, provider, Redis, or media I/O overlap. Provider unavailable or malformed is a fail-closed non-admission; proof denied appends at most one deterministic redacted `VERIFICATION_FAILED` observation in its own short transaction and consumes no admission. Freeze docs/14 §2.12 identity as `"share-observation:" + lowercaseSha256(canonicalJson({shareGrantId, eventType:"VERIFICATION_FAILED", requestKeyDigest}))` (82 characters). The exact payload/fingerprint input is `{shareGrantId, eventType:"VERIFICATION_FAILED", result:"DENIED", reasonCode, requestKeyDigest, verificationMode}`, with null-safe `reasonCode`/`verificationMode`, the fixed denied result, the provider's bounded non-secret denied reason code (null when absent) and the request mode, never provider diagnostic text; `payload_sha256 = lowercaseSha256(canonicalJson(payload))` under docs/14 §2.5. `requestKeyDigest = lowercaseSha256(exactUtf8(admissionRequestId))`, with no normalization or case folding. Same identity/fingerprint returns the first event without append; changed fingerprint conflicts without append. Raw key/code/proof is excluded. Unavailable is not a failed proof.
- Define `ShareAdmissionCodeVerifier.verify(CodeVerificationRequest)` over write-only code, grant salt/hash, and generation under approved policy; it never invents KDF parameters. Define `DesignatedMobileProofVerifier.verify(MobileProofRequest)` to prove approved trusted SMS possession for the exact grant-bound number HMAC, share, and action; HMAC knowledge alone is insufficient. Both return sealed `Verified`, `Denied`, `Unavailable`, or `Malformed` outcomes with redacted diagnostics. Production defaults return `Unavailable`; deterministic adapters are test-only.
- For a new admission, require an approved, unambiguous Q22 session/ticket policy before the durable admission write; unavailable/malformed policy returns 503 `SHARE_SESSION_POLICY_UNAVAILABLE` with no admission/count/event rows. The production adapter returns unavailable unless an explicitly approved value is injected; no numeric TTL is added to source, deployment, or documentation by this slice. Existing-key replay reuses the persisted admission and witness session/admission/grant windows without recomputing or renewing them. After the authoritative replay transaction commits/closes successfully, call `ShareAdmissionPolicyProvider.ticketPolicy(...)` exactly once for a fresh approved current Q22 ticket TTL, before any credential/ticket/Redis/media I/O. Only ephemeral ticket expiry is recomputed under §2.4; no session, admission, grant or count is minted or lengthened. Unavailable/malformed replay policy returns that same 503, preserves the admission, and performs no ticket/Redis/media call or `TICKET_FAILED` append; a later same-key retry looks up policy afresh.
- For `ORGANIZATION_MEMBER`, acquire organization, membership, and account lifecycle advisory locks in ranks 7/8/9, followed by non-locking re-reads only; take no foreign row lock. Re-read exact current active organization, membership `(organization_id, account_id)`, and account predicates. A tenant/account mismatch is `SHARE_WRONG_TENANT`; revoked/suspended membership, disabled account, missing session, or unavailable current context fails closed. The request never supplies identity. Define sharing-owned `TrustedShareAdmissionCaller`; the controller maps the authenticated `CustomerRequestPrincipal` into it. Sharing must not import `customer_iam.TrustedCustomerCaller`.
- Re-read the exact subject ownership/captured binding/current active binding and `subject_risk_state` projection under the frozen S3 ordering. Any `OPEN` risk is `403 SHARE_RISK_BLOCKED`; absent/unresolvable risk or subject projection fails closed without admission. Risk is checked before count and again on replay/reconstruction where required; a later risk opening never erases a committed admission.
- **Single final authoritative predicate/error order (also binding on §2.3 and §5):** (1) terminal status/state `REVOKED`/`EXPIRED`; (2) lock-time expiry/validity using `T`; (3) generation witness comparison (including current mode/code/revocation generations against fresh-proof context or replay witness); (4) current subject ownership, captured/current binding and risk (`OPEN` -> `SHARE_RISK_BLOCKED`); (5) organization/member/account/tenant predicates (`SHARE_WRONG_TENANT` for mismatch, otherwise fail-closed membership/auth); (6) same-key existing admission/witness resolution and replay, including session expiry; (7) only for a missing key, new-key `LOCKED` denial and admission-limit check; (8) insert/count/event. This is observable denial precedence, not permission to change lifecycle lock ranks: acquire locks/read facts first as required, then evaluate predicates in this order. Witness facts may be fetched for generation comparison before step 6 without resolving replay early. Fresh proof may precede this transaction, but every final transaction rechecks this sequence. `SHARE_ADMISSION_LIMIT_REACHED` must never mask an OPEN-risk denial. OpenAPI `x-onecall-replay-order: verification-and-risk-before-count` remains authoritative.

### 2.3 Preliminary read, fresh proof, and authoritative PostgreSQL write transaction

The service uses short `TransactionTemplate` executions with `READ_COMMITTED`, `REQUIRES_NEW`, and the dedicated admission datasource. The preliminary execution is read-only/advisory-only; the final execution is writable and authoritative. Transaction work returns typed committed outcomes (`AdmissionCommitted`, `ReplayCommitted`, `DeniedCommitted`) instead of throwing a denial before commit; the controller maps the outcome only after `execute` returns. No provider, Redis, or media I/O occurs while any transaction or lock is open.

1. Resolve token digest/grant identity and derive the exact 74-character admission key before any row lock. The bounded preliminary read runs read-only, takes no grant row lock, and may take only transaction-scoped lifecycle advisory locks at ranks 7/8/9 for `ORGANIZATION_MEMBER`; it non-lockingly reads the admission/witness and current replay predicates, then closes before the next phase. A preliminary miss never authorizes a write without the locked recheck.
2. If the preliminary read finds an admission, close it and enter the replay write transaction. Acquire required lifecycle advisory locks only at ranks 7/8/9, non-lockingly collect current member/risk facts, lock the local grant with `FOR UPDATE`, sample `T` after the lock, and recheck §2.2's exact final order: terminal state, T-based expiry/validity, generation witness, subject/binding/risk, organization/member/account/tenant, same-key admission/witness replay, missing-key LOCKED/limit, insert/count/event. A witnessed admission replays even if grant status is `LOCKED`; changed, denied, malformed-at-provider or unavailable newly submitted proof is ignored only after schema validation. Expired replay returns the corresponding frozen current-state outcome in §2.2 order; an ended session window returns committed 410 `SHARE_SESSION_EXPIRED` and never renews. Only after a successful `ReplayCommitted` has returned and every transaction/row/advisory lock is closed, invoke `ShareAdmissionPolicyProvider.ticketPolicy(...)` exactly once for the current approved ticket TTL, then enter §2.4. No policy lookup or provider I/O occurs inside either transaction. Replay denial never reaches policy or ticket I/O; replay policy failure preserves all durable admission/witness/count facts and appends no event.
3. If the preliminary read misses, close all transactions and locks. Obtain the approved policy and perform fresh mode proof outside PostgreSQL. Unavailable/malformed policy returns 503 `SHARE_SESSION_POLICY_UNAVAILABLE` before any durable admission write, with no admission/count/event rows; provider unavailable or malformed proof is a fail-closed non-admission; proof denied appends at most one deterministic redacted `VERIFICATION_FAILED` observation in its own short transaction. No proof result authorizes insertion until the final locked recheck. A true fresh insert uses this approved session/ticket policy; it does not require a second policy lookup after commit.
4. Enter the authoritative write transaction: acquire required lifecycle advisory locks only at ranks 7/8/9, non-lockingly collect current member/risk facts, lock the local grant with `FOR UPDATE`, then take one `T = clock_timestamp()` sample after the grant lock. Recheck §2.2's exact final order: terminal state, T-based expiry/validity, generation witness, subject/binding/risk, organization/member/account/tenant, same-key admission/witness replay, missing-key LOCKED/limit, insert/count/event. If another request committed the key during proof, discard the precomputed proof and policy for reconstruction, reuse the committed witness windows, and after `ReplayCommitted` closes every transaction/lock perform exactly one fresh post-transaction `ticketPolicy(...)` lookup as in step 2. The earlier preliminary-miss policy lookup supplies no reconstructed-ticket TTL or renewed window. Only a still-missing active key at the last available slot may insert. `REVOKED`/`EXPIRED`, stale generation, and new-key `LOCKED` return their frozen outcomes. Expiry uses docs/14 §2.12 identity `"share-transition:" + lowercaseSha256(canonicalJson({shareGrantId, actionType:"EXPIRE", sourceIdentity:{kind:"EXPIRY", expiresAt}}))` (81 characters), with the recorded grant expiry in RFC 3339 UTC, never `T` or a generated timestamp. Freeze `actionFingerprint = lowercaseSha256(canonicalJson({shareGrantId, actionType:"EXPIRE", reasonCode:null, newExpiresAt:null, expiresAt}))` under docs/14 §2.5; `newExpiresAt` has a business value for EXTEND only and is the fixed null placeholder here, consistent with the existing transition canonical input shape. The exact redacted EXPIRED payload is `{actionType:"EXPIRE", expiresAt, actionFingerprint, status:"EXPIRED", codeGeneration:OLD.codeGeneration, revocationGeneration:OLD+1, revision:OLD+1}` and `payload_sha256 = lowercaseSha256(canonicalJson(payload))`; resulting values do not enter `actionFingerprint`. Set exactly `status = EXPIRED`, `revocation_generation = OLD + 1`, `revision = OLD + 1`, leave code generation/count unchanged, append that deterministic event, commit `DeniedCommitted(SHARE_EXPIRED)`, then map to 410. A same-action retry reads the deterministic event before transition status/revision preconditions and reuses its recorded outcome; same identity with changed fingerprint is a stable conflict, with no mutation/append. This transition-idempotency check does not reorder admission predicate precedence.
-5. For a fresh insert, explicitly supply `admitted_at = T`; do not rely on V009 `admitted_at DEFAULT now()`. Compute `admissionExpiresAt = grant.expires_at` and `sessionExpiresAt = min(T + approved Q22 TTL, admissionExpiresAt)` from that same `T`, and append exactly one `ADMISSION_GRANTED` witness with deterministic event ID `admission-granted:<grant_uuid>:<admission_uuid>` (canonical lowercase UUID text, never random per retry). Its canonical redacted payload is exactly `{verificationMode, revocationGeneration, codeGeneration, grantExpiresAt, admissionExpiresAt, sessionExpiresAt}`, plus `recipientAccountId` and `recipientOrganizationId` only for `ORGANIZATION_MEMBER` (the original trusted recipient, canonical lowercase UUIDs). In fresh admission, where no existing witness exists, derive both recipient IDs from the trusted current caller; do not require a pre-insert witness and do not fail the final fresh write for its absence. Apply account-to-recipient, membership-pair-to-witness, and grant-owner-to-witness equality checks only after an existing witness is found for replay/reconstruction. `verificationResult` is persisted in immutable `sharing.share_admission.verification_result` and returned in API `ShareAdmission`; it is excluded only from the `ADMISSION_GRANTED` event payload and event fingerprint. Freeze `payload_sha256` as lowercase SHA-256 of those exact payload fields using docs/14 §2.5 canonical JSON; no token/digest, raw request key, code/OTP/phone, credential, Redis key or other field enters that payload/fingerprint. Same ID and fingerprint reuses the first event; same ID with a changed fingerprint is a stable conflict with no append. Current expiry comparisons and ticket TTL calculations use post-lock `clock_timestamp()` samples and positive windows only.
6. Update the grant exactly `admissions_used = admission_no`, `revision = OLD + 1` with expected old revision; V009 guard and unique keys remain backstops. Any failed insert/event/count update/conflict aborts all durable transaction effects. Commit admission + event + count + revision before ticket/provider I/O, and never perform provider, Redis, or media I/O while this transaction or any lock is open.

### 2.4 Ticket issue, failure, and reconstruction

- Define `ShareMediaCredentialProvider.issue(MediaCredentialRequest)` returning sealed `Issued`, `Unavailable`, or `Malformed`, and `ShareAdmissionTicketProvider.write(TicketWriteRequest)` returning sealed `Written`, `Unavailable`, or `Malformed`; production defaults fail closed. Compose strictly after PostgreSQL commit and, on replay, successful current ticket-policy lookup: issue the opaque credential with expiry bounded by ticket/session/admission/grant windows; build and write the deterministic ticket containing approved material only; then append success event. Once ticket operation starts (after policy approval, including ticket-window validation), credential/ticket/Redis/event failures use the seven frozen `TICKET_FAILED` reasons, return 503 except the frozen nonpositive-window 410, preserve admission, recount nothing, and reconstruct by same-key replay. Unavailable/malformed policy is pre-ticket, never a `TICKET_FAILED` reason. No transaction/lock spans provider or Redis I/O.
- The deterministic Redis contract is `share-ticket:<shareGrantId>:<shareAdmissionId>`. `ticketExpiresAt = min(clock_timestamp() + approved Q22 ticket TTL, sessionExpiresAt, admissionExpiresAt, current grant expires_at)`; Redis TTL is positive `ticketExpiresAt - clock_timestamp()` only, and all current expiry decisions use post-lock `clock_timestamp()` samples. The adapter must reject malformed material, non-positive windows, wrong IDs/generations, missing expiries, and any secret-bearing log/display path.
- After successful ticket write, append deterministic redacted `TICKET_ISSUED` with `ticket-issued:` plus lowercase SHA-256 of canonical `{shareGrantId, admissionId}`. Any post-commit credential/ticket/Redis/event failure appends exactly one deterministic redacted `TICKET_FAILED` with `ticket-failed:` plus lowercase SHA-256 of canonical `{shareGrantId, admissionId, admissionKeyDigest}`, deletes/expires best-effort, returns 503, preserves admission, and recounts nothing. Unavailable/malformed policy returns 503 `SHARE_SESSION_POLICY_UNAVAILABLE` before ticket operation starts: on fresh admission it is before the durable write with no admission/count/event rows; on replay it is after authoritative transaction/lock closure, preserves existing admission/count/windows/events, and appends no `TICKET_FAILED` or other event. Neither case calls credential/ticket/Redis/media providers; a later same-key retry looks up policy afresh.
- Freeze the post-commit event payloads without secret facts: `TICKET_ISSUED` has exactly `{shareGrantId, admissionId}`; `TICKET_FAILED` has exactly `{shareGrantId, admissionId, admissionKeyDigest, reasonCode}`. Here `admissionKeyDigest = lowercaseSha256(exactUtf8(admissionKey))`, not a raw request ID. Allowed failure reasons are exactly `MEDIA_CREDENTIAL_UNAVAILABLE`, `MEDIA_CREDENTIAL_MALFORMED`, `TICKET_WRITE_UNAVAILABLE`, `TICKET_WRITE_MALFORMED`, `TICKET_WINDOW_EXPIRED`, `TICKET_EVENT_UNAVAILABLE`, and `INTERNAL_FAILURE`; map adapter outcomes to these constants, never exception text, credentials, ticket material, Redis keys, provider identifiers or secret facts. Each `payload_sha256` is lowercase SHA-256 of the exact canonical payload under docs/14 §2.5. For either identity, same-identity retry with the same fingerprint reuses the first event and never appends; a changed fingerprint is a stable conflict and never appends or overwrites. A later differing failure reason cannot create a second failed event under that identity; successful reconstruction may create its distinct issued event once. If the event store itself is unavailable, return 503, preserve admission, claim no successful event append and retry the deterministic event on recovery.
- Same-key retry after lost response/cache/provider failure uses §2.3's authoritative replay transaction and exact §2.2 predicate/error order, re-reads the PostgreSQL witness, commits/closes that transaction, invokes `ShareAdmissionPolicyProvider.ticketPolicy(...)` exactly once for fresh approved current ticket TTL, and only then reconstructs/reissues without inserting or recounting. Persisted witness `sessionExpiresAt`/`admissionExpiresAt` and original grant-window facts remain unchanged; current grant `expires_at` bounds each ticket. A later approved TTL may change ephemeral ticket expiry under the frozen minimum formula, never extend a persisted session/admission/current grant window. No original ticket TTL or policy reference is persisted or added to schema/event fields. A valid existing admission with `LOCKED` grant may replay; a new key may not. Valid same-key replay with an unexpired session returns 201 only if all current predicates pass. After session/admission/grant expiry, return the corresponding frozen current-state outcome in exact §2.2 order; an ended session window returns 410 `SHARE_SESSION_EXPIRED`, never a new ticket or second admission.
- Response is exactly the existing `ShareAdmission` shape: `admissionId`, `verificationMode`, `verificationResult`, `admittedAt`, `sessionExpiresAt`, `admissionExpiresAt`, and `mediaAuthorization {credential, expiresAt}`. Never add IDs, hashes, generations, grant identifiers, policy values, Redis keys, internal evidence/media facts, or raw verification material. Both first admission and same-key replay success return the sole OpenAPI success status `201`.

### 2.5 Error precedence

Optional bearer behavior exactly follows the existing public GET precedence. Absent `Authorization` permits anonymous `NONE`, code, and mobile modes. Any present invalid, malformed, or ambiguous Authorization is rejected as `401 UNAUTHENTICATED` by the boundary filter before body/controller processing. `ORGANIZATION_MEMBER` requires a valid current session. For schema-valid requests, perform token lookup and preliminary replay/proof phases in §2.1–§2.3, then apply exactly §2.2's final authoritative predicate/error order; preliminary proof never exempts the final recheck. Risk precedes count, so OPEN risk wins over an exhausted limit. Both success paths are 201. New-admission unavailable/malformed Q22 policy is pre-durable-write 503 `SHARE_SESSION_POLICY_UNAVAILABLE` with no admission/count/event rows. On an existing-key hit all authoritative replay/current-state/witness checks and their frozen denials precede policy lookup. Only successful `ReplayCommitted` after transaction/lock closure reaches exactly one fresh current ticket-policy lookup; unavailable/malformed replay policy returns the same 503 without credential/ticket/Redis/media I/O, event append, recount, second admission or session renewal, preserving the admission for later same-key retry. This is not one of the seven `TICKET_FAILED` reasons and cannot map to `INTERNAL_FAILURE`. Media credential/ticket dependency failure is post-commit 503, preserves the durable admission, and uses same-key reconstruction without recount. Existing public GET and creator mappings are unchanged. `CustomerProblemWriter` adds `write(HttpServletResponse, ShareAdmissionException.Code, UUID)` with the exact PA17 mapping below, without changing any existing overload/mapping. Preserve `type=about:blank`, the existing trace UUID behavior (`traceId` string from the request trace), `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `application/problem+json`, and `WWW-Authenticate: Bearer` on 401. `PublicSharesController` adds dedicated `@ExceptionHandler(ShareAdmissionException.class)` ahead of its generic handler, routing through that overload; pre-transaction validation/token/binder errors reach it rather than degrading to generic 500. Committed denials use the same mapping after transaction completion.

## 3. Database principal, pool, and V012 decision

### Decision

Add privilege-only `V012__sharing_admission_least_privilege.sql`. Reusing `sharing_command_role` would give a public capability endpoint the broader creator create/revoke/rotate write surface and its existing cross-module/function privileges. That violates least privilege and makes the PA16 read-only/public separation unverifiable. PA16's `sharing_public_read_role` remains exactly read-only and byte-identical. V012 must not alter V001–V011 definitions, grants, role attributes, or lifecycles.

### Role and runtime topology

- Role: `sharing_admission_role`, `LOGIN` for the explicitly qualified runtime pool, with no usable migration password (`PASSWORD NULL`) and deployment authentication provisioned separately; `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`, no membership, no settings, no ownership, no default privilege, no `PUBLIC` grants, and no database `CREATE`/`TEMPORARY`.
- Pool: `sharingAdmissionDataSource`, explicitly qualified URL/username/password properties `onecall.sharing-admission.datasource.url`, `.username`, `.password`; require nonblank values and exact username `sharing_admission_role`; properties `toString()` is redacted. Configuration is `@Profile("persistence")` and additionally conditional on the explicit `onecall.sharing-admission.datasource.enabled=true` property. It is independent of PA16 public-read and creator-command pools; never fall back to either credential. Default and web-only contexts remain database-free.
- Transaction/DSL: `sharingAdmissionTransactionManager` enforces writable transaction (`READ_COMMITTED`, `REQUIRES_NEW`, rollback on commit failure), `sharingAdmissionTransactionTemplate`, and `sharingAdmissionDsl` with prepared/indexed statements and no SQL logging. The service asserts `current_user`/`session_user` before the first write and never uses `SET ROLE` to a broader principal.

### V012 exact ACL intent

V012 grants only the minimum needed by the admission transaction and trigger backstops:

- `USAGE` on `sharing`, `evidence`, `customer_iam`, `organization_access`, and `subject_number`; no `CREATE`.
- `sharing.evidence_share_grant` column `SELECT` is exactly all 20 V009 columns: `id, share_id, capability_token_hash, evidence_id, created_by_account_id, owner_organization_id, verification_mode, code_salt, code_hash, code_generation, valid_from, expires_at, max_admissions, admissions_used, download_allowed, content_snapshot, content_sha256, status, revocation_generation, revision`. This is required because immutable `sharing.guard_share_admission()` is SECURITY INVOKER and executes `SELECT *`. Do not grant table-level SELECT. Column `UPDATE` only `status, admissions_used, revocation_generation, revision`; expiry sets exactly `status`, `revocation_generation = OLD+1`, and `revision = OLD+1`; code generation and admission count remain unchanged. Admission count sets `admissions_used = admission_no`, `revision = OLD + 1`. No grant INSERT/DELETE/TRUNCATE.
