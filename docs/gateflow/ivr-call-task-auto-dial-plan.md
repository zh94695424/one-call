# IVR 呼入自动外呼设计修订计划

## Goal confirmation / scope contract

- Goal：根据用户最新明确要求，修正小程序待拨任务链路：可信主叫呼入 IVR 后，呼入决策一次领取当前唯一有效任务，按任务冻结的被叫号码自动外呼；被叫接通后由现有自研 IVR 桥接主叫与被叫语音并录音，不要求主叫在声讯电话里确认被叫号码。
- Motivation：旧方案把任务领取与被叫按键确认分成两步；声讯电话无法可靠完成被叫号码核对，且自动外呼能力已经由自研 IVR 提供。
- Success signal：专项设计、架构总览、业务摘要和验收入口不再描述任务路径的被叫按键确认；`resolve` 对有效任务原子领取、绑定 `callId`、预占录音权益并返回被叫及授权，重试不会重复领取或外呼；外呼失败幂等终结任务并释放未用预占；IVR 将 A/B 两路接入同一双向通话会话并负责录音，通话和录音事实仍由 IVR 上报。
- Non-goals：不实现生产 API、数据库迁移或 IVR 引擎；不改变单主叫单待拨任务、默认 30 秒可配置 TTL、直接 IVR 未实名试用/开通告知、录音告知与适用的同意要求、套餐/开通/权益边界；不加入多任务 FIFO、DTMF 被叫确认、PIN/短信确认或运营商业务系统。
- Scope boundary：修改 `docs/13-ivr-call-task-and-inbound-design.md`、`docs/12-technology-stack-and-system-architecture.md`、`docs/09-business-activation-and-lean-admin.md`、`docs/10-cross-channel-rules.md`、`docs/04-acceptance-roadmap.md`、`docs/03-technical-solution.md` 和 `docs/README.md` 中直接冲突的生产规则、架构摘要、验收场景或覆盖说明；并更新本修订的 Gateflow 计划/控制/评审/实现记录及原 IVR 工作单的历史状态说明。保留独立的直接 IVR 输入被叫与开通/试用规则。
- Confirmation basis：用户明确要求“IVR呼入一次就取走任务了”，按任务被叫号码自动呼出，被叫接通后桥接并录音，不在声讯电话里确认被叫号码；此前已确认自研 IVR 拥有完整通话与上传能力。

## First-principles evidence

- `docs/13-ivr-call-task-and-inbound-design.md` currently returns `CONFIRM_CALLEE`, reserves quota only after another IVR request, and treats callee confirmation as protection against late calls.
- `docs/12-technology-stack-and-system-architecture.md` repeats the same claim in §1.1 and §9.2, so updating only the detail doc would leave the architecture summary contradictory.
- Current business and acceptance summaries in `docs/09-business-activation-and-lean-admin.md`, `docs/10-cross-channel-rules.md` and `docs/04-acceptance-roadmap.md` also describe confirmation before dialing; `docs/03-technical-solution.md` retains an older carrier/vendor-owned call flow that must be marked as superseded for this path.
- `callId` is generated by IVR after inbound; the telephone network does not carry the miniapp `taskId`. The current single-pending-task-per-caller lookup cannot distinguish a delayed old inbound from a replacement task.
- The current system already gives IVR authority over A/B calls, bridge events, recording, duration, hangup and uploads; no media-engine replacement is required.

## Design decisions

| Decision | Goal alignment |
| --- | --- |
| `resolve` returns `DIAL_TASK_CALLEE` only after current caller/task/permission/entitlement checks; task claim, `callId` binding and `UsageReservation` commit atomically | A valid inbound consumes exactly one task and receives authorization in the fast path, without a second callee-confirmation round trip |
| Response freezes task, callee, reservation, authorized recording seconds and authorization deadline; same `callId` plus fingerprint returns the same response | Retries cannot select a different task or create a second outbound leg |
| IVR automatically dials the frozen callee; on answer it connects A caller and B callee into the same bidirectional session (the caller, callee and IVR media bridge form the logical three-party call) and records under the authorization limit | Directly expresses the requested call behavior while preserving IVR ownership of media facts; it does not introduce a separate human party or carrier conference feature |
| No quota or task claim is committed when caller, task, permissions, activation or available entitlement fail; failed/unanswered B leg settles zero effective recording seconds and releases reservation | Prevents consuming intent/entitlement without an authorized attempt or valid recording |
| Recording notice/consent remains separate from callee verification; existing direct IVR activation/trial flow remains unchanged | Removes only the rejected confirmation and avoids silently weakening recording or onboarding rules |
| Caller-only matching and delayed inbound misbinding remain explicit first-release residual risk; no task code/PIN/queue is added | Respects current confirmed scope without inventing telephony capabilities |

## Contract, state and failure behavior

- `PENDING → CLAIMED` remains the task-consumption transition. For a valid task path, the same database transaction also creates the unique reservation for `callId` and freezes the outbound decision. A failure rolls back both claim and reservation.
- `callId` replay returns the frozen authorization and never creates another task claim or B leg. IVR must use `callId` as its outbound operation idempotency identity.
- Response action for task path is `DIAL_TASK_CALLEE`, with `taskId`, `calleeNumber`, `reservationId`, `authorizedRecordingSeconds` and `authorizationExpiresAt`. `CONFIRM_CALLEE` is removed from current task-path enums and docs.
- For a matching task, `resolve` returns the frozen decision only after the claim and reservation transaction commits. If the response is lost, IVR repeats `resolve` with the same `callId`; its own durable call-operation idempotency must prevent a second B leg. Unanswered, rejected or failed B legs are terminal for that task; a retry requires a newly created task.
- Caller mismatch/untrusted number, expired/missing task, caller already in an active call, suspended subject, revoked access, no usable entitlement, conflicting task records, or backend failure do not authorize external dialing.
- After authorization, busy/rejected/unanswered B leg, A-leg hangup before bridge, or bridge failure reports an idempotent terminal failure, consumes zero effective recording seconds and releases the unused reservation. Unknown call outcome remains occupied until IVR authoritative reconciliation; no TTL-based task replay.
- Call recording follows the separately approved notice/consent policy; this change removes only callee-number confirmation. The exact notice/consent timing remains a legal/product residual, and cannot be silently replaced by the removed callee confirmation.

## Risks / open questions

- Residual risk: inbound telephone metadata does not include `taskId`; after replacing a task, an old delayed inbound from the same caller can claim the new single pending task and automatically dial its callee. Track for telephony/product decision before launch; determine whether the existing line can carry a per-task route identifier. This correction does not invent one.
- Residual risk: exact recording announcement/consent wording and timing remain product/legal decisions; callee confirmation is not a substitute.
- No blocking question for the requested documentation correction: current behavior is explicitly caller-to-sole-pending-task automatic dialing, with the above risk disclosed.
