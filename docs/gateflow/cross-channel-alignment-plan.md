## 3. Minimal implementation architecture

### 3.1 One canonical source, inline packaging, no distributed state system

Add `shared/onecall-business.js`: a dependency-free UMD-style module (`module.exports` in Node, `window.OnecallBusiness` in the browser). It owns only this work unit's demo catalog, labels, support configuration, scenario fixtures and narrow business transitions. It must not become a generic rules engine, backend emulator, persistence/event bus or replacement UI framework.

Add `shared/build-prototypes.js`. In each of the three editable HTML sources, a single bounded section `<!-- ONECALL_BUSINESS:START -->` … `<!-- ONECALL_BUSINESS:END -->` precedes its application script. The build copies the canonical module as inline script, escaping any `</script` sequence. The inserted section is generated; all surrounding UI is hand-maintained. It then remains available even when an HTML source or preview is opened with file://. Normal mode updates only those sections, compares before writing and fails on missing/duplicate markers; `--check` exits nonzero for drift without writing. No browser fetch, localStorage synchronization, server, symlink or runtime CDN is introduced for business rules.

All three QA runners invoke this generator before their existing preview creation. Miniapp continues using the existing fragment renderer; the other runners continue copying source to preview. Commit generated previews after validation, not by hand. Tests must assert the embedded canonical hash/version is equal in all sources and previews. Shared rule-source changes require regeneration; identical generated text is packaging, not three independently maintained rule sources.

Each UI holds its own in-memory business-state clone and existing unrelated UI state. Refresh resets demo mutations as today. Admin publication does not silently update another browser tab. The integrated QA deliberately transfers a JSON snapshot between surfaces through local demo/review-only hooks to verify common interpretation; README must say this is fixture handoff, not live integration. These hooks are test infrastructure for the local prototype files, not a public or production interface. This repository has no production build to conditionally remove them; if any prototype is later reused as a release artifact, disabling/removing the hooks belongs to a separate build/release work unit and is a production-release prerequisite.

### 3.2 Exact shared contract

Expose `schemaVersion: 1`, `labels`, `support`, `demoCatalog`, `createDemoState(now)`, `validateCatalogVersion`, `visibleOffers`, `createOrder`, `applyPaymentResult`, `issueEntitlements`, `activateService`, `grantTrialOnce`, `claimSubject`, `startIvrSession`, `confirmIvrSession`, `consumeTrial`, `trialStatus`, `snapshot` and `loadReviewSnapshot`.

Functions accept an explicit business state and `now` where time matters, return `{ok, code, value}` and do not partially mutate on rejection. Expected codes include `NOT_FOUND`, `CONSENT_REQUIRED`, `VERIFICATION_REQUIRED`, `CLAIM_CONFLICT`, `RECYCLED_NUMBER_REVIEW`, `SUSPENDED`, `TRIAL_DISABLED`, `TRIAL_EXPIRED`, `TRIAL_EXHAUSTED`, `NOT_SELLABLE`, `STALE_VERSION`, `PAYMENT_UNRESOLVED`, `INVALID_TRANSITION`, `DUPLICATE`. `DUPLICATE` returns the original resulting object without a second grant/order/recording. UI maps codes to precise instructions and retains user input on errors. Existing local UI helpers may wrap these exports; the same business predicate must not be independently reimplemented per surface.

`createDemoState` and `businessSnapshot()` use exactly these allowed top-level business fields: `{schemaVersion, catalog, rule, subjects, claims, trialGrants, sessions, evidence, activations, orders, entitlements, processedEvents, sequence}`. Here `sessions` means `IVRSession[]` only; it is required business evidence context and must round-trip with its linked evidence. IDs and timestamps are demo-only; no raw personal identifiers are added. `processedEvents` is only an in-memory idempotency-key map with result identity, not a message framework.

### 3.3 Transitions and invariants

1. Ordinary miniapp/Web flow retains the existing identity-onboarding requirement, then number verification, explicit service consent, internal activation. IVR returning flow is separate: login → verify the same number → claim check → existing state. It must not route through a fake new activation/grant, nor silently set identity VERIFIED. Existing IVR trial remains usable as allowed; paid activation/purchase still follows ordinary identity gates. A missing identity offers “继续实名后购买”, without deleting the trial/history.
2. `activateService({subjectId,channel,verified,consentVersion,confirmed,eventId}, now)` requires a resolved verified subject for client channels, ordinary identity gate for new client activation, explicit consent and non-suspended state. It records ACTIVE and invokes `grantTrialOnce`; repeat events return the original activation. No activation creates a paid order.
3. `grantTrialOnce(state,subjectId,now)` queries subject+FIRST-TRIAL, including exhausted/expired grants. If any exists it returns that grant untouched. Only a first grant uses the current rule; disabled rule means no grant, not deactivation. Claim, unbind/rebind UI, new rules, resume and channel switches do not grant again. Initial grantedSeconds, ruleVersion and expiresAt are never overwritten.
4. `claimSubject({subjectId,accountId,verification:{verified,subjectId,method},requestId},now)` requires login, matching subject verification and mobile or fixed-line-appropriate method. Login alone or mismatching verification rejects. CONFLICT/RECYCLED rejects and directs offline review, showing no historical evidence even if current SMS succeeds. Success appends one association and updates only the target subject's account association/revision; before returning it preserves all IVR-session `subjectId`/`confirmedSubjectId` values and all evidence records byte-for-byte. It does not rewrite subject ID, identity, evidence subject or trial. Existing same-account association is idempotent; another account rejects. No account transfer or risk override UI is added.
5. `startIvrSession({scenario},now)` uses named fixtures, not user-entered personal numbers. `confirmIvrSession({sessionId,key,eventId},now)` requires trustworthy caller, explicit key 1, current versioned consent and non-suspended subject. On success it resolves exactly one existing/new subject and atomically freezes the same non-null ID into `subjectId` and `confirmedSubjectId`; neither field is later mutable through a domain action. Missing caller/timeout/other key does not newly activate or grant. Repeat/new-call-for-same-number resolves the stable subject and existing grant; completed events are idempotent. IVR identity is allowed UNVERIFIED and accountId null.
6. `consumeTrial({sessionId,eventId,seconds},now)` has no caller-supplied `subjectId`. Before looking up or mutating a grant, evidence, sequence or `processedEvents`, it requires exactly one IVR session with `status=CONFIRMED`, non-null `subjectId` and `confirmedSubjectId`, equality between those two frozen IDs, and exactly one existing subject matching that ID. Any unresolved, missing, duplicated, altered or cross-subject association returns `INVALID_TRANSITION` without mutation. Only then does it derive that subject's `subjectId + FIRST-TRIAL` grant, accept positive safe-integer effective recording seconds, bound consumption to remaining grant, reject suspended/expired/exhausted state, and append exactly one metadata record whose `subjectId` equals the IVR session's frozen confirmed subject. A requested 60 seconds with 20 remaining records/charges 20 and marks “额度耗尽，结束取证”; no charging menu/ringing or automatic overage. This deterministic simulation does not prove atomic reservations or real hangup. Zero/negative/NaN, duplicate delivery, A-IVR-session/B-subject tampering, unresolved IVR session and removed/replaced subject references create no evidence/usage/idempotency record and do not advance the sequence.
7. `visibleOffers({channel,audience})` returns current ACTIVE versions in configured sort order; IVR is never a purchase channel. `createOrder` requires logged-in/verified ordinary purchase eligibility, explicit purchase consent, exact still-sellable selected version and no unresolved checkout. It freezes product, rights, price, term, rules and consent. Changed/off-sale selection returns NOT_SELLABLE/STALE_VERSION and requests reselection; do not silently substitute a product/price.
8. Payment button creates/reuses UNPAID order and opens the simulated payment result, rather than claiming paid+issued. Review-only “模拟服务端支付结果” may move UNPAID → UNKNOWN/PAID/CLOSED; UNKNOWN can be resolved to UNPAID/PAID/CLOSED. PAID does not regress; CLOSED does not reopen in this demo. UNKNOWN keeps a query-result action and blocks duplicate checkout. `applyPaymentResult` sets PAID/PENDING but does not issue rights. Separate `issueEntitlements` permits PAID+PENDING/FAILED → ISSUED once. Duplicate callback/issue is a no-op. Unknown/closed/unpaid never grants; paid+pending and paid+failed are visible distinct scenarios. Real late-callback/reconciliation belongs to production work, not finance mutations here.
9. Trial and paid rights are separate ledgers. Demo first purchase grants one isolated entitlement snapshot; do not implement renewal/add-on stacking or quota-priority arithmetic. Current front-end assertions such as “赠送优先、再加量、再套餐” are unapproved and become “叠加/抵扣规则待确认，以下为独立购买演示”. No auto-renew charge or promise. This preserves existing purchase screens without deciding production stacking policy.
10. Offline support is one configuration: `{mode:'OFFLINE', configured:false, contactLabel:'人工客服联系方式待配置', contactValue:null, hours:null, instructions:{consultation,refund,invoice,claim}}`. Shared instructions list needed order/number/time/problem or invoice information, avoid requesting complete identity documents in the prototype, promise no SLA or eligibility. Unconfigured contact displays a non-actionable placeholder; no dummy tel/mail/WeChat ID, fake sent message, receipt number, online progress or guaranteed refund.

“Known IDs” means unique, nonempty IDs of the expected shape plus structural/referential validity inside the imported snapshot; it is not an allowlist of seed fixture IDs. The loader requires every confirmed IVR session to reference exactly one subject with `subjectId === confirmedSubjectId`; every evidence item must reference an existing confirmed IVR session and subject with `evidence.subjectId === ivrSession.subjectId === ivrSession.confirmedSubjectId`; and all grant, claim, activation, order and entitlement references must resolve to exactly one compatible imported object. Unresolved, duplicate, cross-subject or mismatching references reject the entire load before replacing existing state. A valid dynamically created IVR session and its linked evidence must export/import/export unchanged.

Each HTML exposes a bounded local-prototype QA hook: existing `__onecallOps` plus new `__onecallMini` and `__onecallWeb`, each with `businessSnapshot()`, `loadReviewSnapshot(snapshot)`, `setReviewScenario(name)`, and existing-safe navigation. Snapshot is deep data only. Scenario setters select fixed fixtures, not free-form identity/risk overrides. The UI and READMEs label these hooks “仅本地演示/评审”; they are not production APIs or runtime synchronization. Production reuse is explicitly deferred to a later build/release work unit that must remove or disable the hooks before publishing a real client.
